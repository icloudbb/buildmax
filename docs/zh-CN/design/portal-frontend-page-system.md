## 决策

Portal 是否应采用一套小而可执行的页面与组件系统，让相同操作在列表、详情、编辑和诊断页面拥有一致的视觉优先级与行为？**决定采用。** 保留当前克制的中性色视觉语言，先定义操作层级和页面结构，再从核心工作路径开始迁移。只给现有页面换配色无法解决内容层级和重复操作问题。

此方向已确定，目前仅部分实现。已交付行为和后续迁移以当前状态文档为准；该决策本身不改变产品模型或路线图中的 Beta 验收门槛。

## 用户目标、证据与约束

目标是让 Space 成员扫一眼页面就能找到当前的下一步、理解工作状态，并预期控件的行为，不必逐页重新学习。运维人员能分清 Space 工作与整个部署的管理权限。同一流程在宽屏、紧凑屏、窄屏及明暗两种主题下都应可用。

2026-09-19 的只读走查使用本地常驻 QA Portal `http://localhost:8080`；页面资源文件名与检出版本 `95e3f0be` 的 `portal/dist` 一致。走查覆盖 Chat、Issues 与 Issue Detail、Agent 与 Task、Workflow 与 Workflow Run、Schedules、Files、Artifacts、Space settings 和 Administration，并检查了 1280 与 390 CSS 像素宽度。未修改产品数据。这是抽样走查，不是用户研究，也没有完成一条完整的 Issue 执行链路。

具体观察：

| 页面 | 观察到的问题 | 来源 |
|---|---|---|
| 空的 Schedules 列表 | 页头的白色 **New schedule** 与空状态中的黑色 **New schedule** 同时出现，作用相同而视觉等级矛盾。 | `SchedulesPage.tsx` 同时提供两个操作；`EmptyState.tsx` 强制其操作使用 `.btn--primary`，而 `.page-activity__action-btn` 是次级样式。Issues、Workflows、Agents 也有同类重复的可能。 |
| Portal 按钮 | `.btn`、`.page-activity__action-btn`、`.modal__btn`、`.admin-button`、`.tp-btn` 和页面局部样式分别决定尺寸、颜色、焦点；部分创建或提交操作用了次级样式。 | `portal/src/css/`、`gui/src/modal.css` 及调用处。 |
| Issue Detail | 首屏主要是可编辑标题和八行描述框，最新结果排在表单与子 Issue 之后。窄屏上，顶部标题、面包屑、泛称 **Issue Detail** 和表单标题重复传达位置。 | `IssueDetail.tsx` 的 Overview 顺序及 `Layout.tsx` 的窄屏页头。 |
| Workflow Run | 运行 ID 和元数据排在结果之前；固定 52px 高度的图节点裁切文字。 | `WorkflowRunDetail.tsx`、`WorkflowGraph.tsx` 和 `workflows.css`。 |
| 全局管理 | Administration 解释的是部署级权限，却仍显示可操作的 Space 切换器。 | `Layout.tsx` 复用的 `SidebarNavContent`。 |
| 标签与加载 | 面向用户的行和表单直接显示 `todo`、`in_progress`、`succeeded`、`workflow_step`、`agent_task` 等机器值；列表加载时可短暂显示“0”和分页。 | Issues、Task、Workflow Run 和列表页各自渲染的内容。 |

现有基础应保留：带 Space 的路由、Issue 的四个用户级分区、分开的 Save 与 Run、状态和权限模型、窄屏抽屉及 Artifact 预览。Portal 与 Desktop 通过 `@buildmax/gui` 共享展示组件；共享包不能包含 Portal 的路由、数据、认证或领域策略。Issue 仍是主要共享工作对象，Task 与 TaskRun 保持执行权威。已有响应式与状态设计记录继续有效。

## 建议的视觉方向

采用克制的操作界面：中性画布、明确的文字层级、少量边框，只有表达含义时才使用语义颜色。保留当前明暗主题的反转。主按钮在亮色主题可以是深色，在暗色主题可以是浅色；即使字面颜色变化，它的**角色**必须一致。不要为了填充空白页面而随意使用实心按钮。

从现有 `@buildmax/gui/theme.css` 颜色出发，只补足能够消除页面重复决策的变量：

| 变量类别 | 初始约定 |
|---|---|
| 颜色 | 画布、抬高表面、弱化表面、主次文字、边框、焦点、主操作、危险操作和状态色。页面 CSS 使用语义变量，不再自行添加十六进制色值。 |
| 字体 | 正文、小号元数据、分区标题及页面或对象标题各一档。只有作为技术细节显示的 ID 与代码使用等宽字。 |
| 间距 | 4/8/12/16/24/32px 的短刻度；宽屏页面边距 32px，窄屏 16px。 |
| 形状与动态 | 一种控件圆角、一种面板圆角，覆盖层使用克制的阴影，并支持减少动态效果。避免页面各自设置过渡。 |

最终变量值应先通过样本页面和浏览器评审确定。两种主题均需检查文字对比度、可见焦点与状态含义。变量名表达用途，不为每个组件或页面创建专属变量。

## 操作与按钮规则

用一套展示型 `Button`／`IconButton` 统一尺寸、焦点、悬停、禁用、忙碌状态与图标对齐。它可用于按钮或链接语义，但遵循同一视觉规则。领域代码负责操作本身、权限、文案及加载状态。

| 层级 | 外观 | 位置与例子 |
|---|---|---|
| 主要 | 实心、高对比 | 当前范围内的一个下一步：列表上的 **New issue**、准备就绪的 Issue 上的 **Run Agent**、编辑器中的 **Save changes**。 |
| 次要 | 描边或轻微抬高 | 同级但不那么关键的操作：**Edit**、**Download**、**Cancel**。 |
| 三级 | 文字或透明背景 | 导航与辅助操作：**Back**、**Refresh**、**View details**。面包屑保留链接语义。 |
| 危险 | 明确的危险色描边，必要时确认 | **Delete**、**Revoke**、**Destroy**；不借用普通主按钮样式。 |

页面组件应执行以下规则：

1. 一个视图在当前任务下只有一个主要操作。进入编辑模式后，表单可以有自己的主要 Save 操作；只读视图和编辑表单是不同范围。状态标签不能看起来像按钮。
2. 同一可见页面中，不在页头和空状态重复渲染同一个操作。页头负责列表创建；空状态解释情况，可以指向该操作。若页头没有操作，空状态可承载唯一的主操作。独立长滚动区域只有在原按钮不可见且经过验证时才可重复入口。
3. 视觉优先级由用户下一步决定，不由组件来自哪里决定。通用 `EmptyState` 不应把传入的任何操作都强制设为主要。
4. 禁用或忙碌操作说明原因、阻止重复提交、保持宽度稳定。纯图标操作有可访问名称，点击目标至少 44px。
5. 文案使用动词和对象名称。Save 只持久化，Run 会调度执行。未保存的执行者变更不能悄悄改变 Run 的目标，也不能与实际目标不一致。

对目前空的 Schedules 页，保留页头一个实心 **New schedule**。空面板只写“No schedules yet. Schedule an Agent to run at a set time.”，不放第二个按钮。Issues、Workflows、Agents 遵循同一规则。创建对话框中，**Create** 是主要按钮，**Cancel** 是次要按钮；目前有些创建提交按钮仍是次级样式。

## 页面结构与模板

应用框架只传达一次作用域。宽屏与紧凑屏显示当前 Space 和资源导航；全局 Administration 路由显示部署上下文，不提供活动 Space 切换器。窄屏显示 Space 和菜单按钮，页面自己拥有一个真实 H1。详情页显示父级／返回面包屑，避免连续三层重复当前标题。

| 模板 | 结构 | Portal 页面 |
|---|---|
| 列表 | 作用域和 H1 → 一个主要创建操作 → 可选筛选与数量 → 列表或具体的空／错误状态 → 分页。若页面只有一个列表，不再加“All X”标题。 | Issues、Agents、Workflows、Schedules、Artifacts |
| 对象详情 | 对象名称和状态 → Owner／Executor 与下一步 → 最新结果或有用摘要 → 关联内容 → 历史与诊断。先读后编辑。 | Issue、Agent、Workflow、Artifact |
| 工作／运行详情 | 结果与 Artifacts → 当前状态及恢复操作 → 执行步骤 → 来源与 Trace。ID 是可复制的次要元数据。 | Task、Workflow Run、Issue Runs |
| 编辑器 | 对象名称与未保存状态 → 分组字段和就近说明／错误 → 窄屏固定的 Save／Cancel。保存成功说明对象及具体效果。 | Issue 编辑、Workflow 编辑、Agent 配置、设置 |
| 管理 | 部署作用域标识 → 分区导航 → 状态概览 → 面向任务的表格与表单。敏感操作保留明确权限和反馈。 | Administration；Space settings 属于 Space 范围 |

这些是组合式页面模板，不是新的持久化实体。建议只保留少量 Portal `PageHeader`、`CollectionFrame`、`DetailHeader`、`StatusLabel`，并复用已有 `EmptyState`／`Alert`；避免带几十个开关的万能页面组件。Tabs 与折叠交互应有一种语义实现。只有足够中立、适合 Desktop 的展示组件才进入 `@buildmax/gui`；Portal 自己负责对象词汇与页面组合。

## 状态、响应式与无障碍

- 使用现有资源状态模型。加载时框架稳定并显示进度，成功响应前不宣称数量为零或列表为空。空、错误、禁止访问、过期数据和刷新中保持区别，并给出就近的下一步。
- 业务状态、运行状态和生命周期状态各使用统一的展示词汇。状态包含文字，必要时辅以形状或图标；颜色不单独承载含义。技术枚举仍可在详情中查看。
- 在 390、768、1280 CSS 像素下，操作层级保持不变。页头操作可移到标题下方或具名菜单中，但保留优先级与可访问名称。390px 和 200% 缩放时不产生整页横向滚动。
- 焦点、键盘顺序、提示播报、对比度、减少动态效果、弹窗焦点与 44px 目标遵循已有响应式／无障碍设计。迁移页面前，样本应包含明暗主题、加载、空、错误、禁止访问、禁用、忙碌和长内容状态。

## 归属与迁移

1. **审计与样本。** 盘点按钮样式家族和重复操作；用当前 Portal 内容制作可评审的组件与页面样本，在 390／768／1280px 和两种主题下查看。记录基线旅程和具体视觉缺陷。这是设计产物，不是新应用。
2. **基础组件。** 在 `@buildmax/gui` 增加语义变量与共享展示型按钮；Portal 专属页面组合保留在 `portal/`。迁移旧按钮时删除旧规则，不长期保留别名。同时处理弹窗提交操作、空状态、焦点与忙碌状态。
3. **核心工作页。** 迁移 Issues 列表／详情、Task、Workflow Run 和 Chat，修正结果层级、状态文案、重复操作与图节点裁切。若 UI 正确性依赖创建／运行契约，应一致地修改拥有该行为的 service/API，而非在前端遮盖歧义。
4. **其余页面。** 迁移 Agents、Workflows、Schedules、Files、Artifacts、Space settings、Administration 和 Marketplace。每一片完成后删除过时 CSS，避免长期并存两套风格。
5. **文档与验证。** 更新用户手册及中文镜像、Portal 贡献者架构、当前状态说明，并为上线的用户可见变化添加 changelog。运行 `./make check gui`、`./make check portal`、聚焦的浏览器旅程及行为变化所需的 `./make e2e kind`。让未参与实现的运维人员复走旅程，再声称它更容易。现有 Beta 候选资格仍是独立门槛。

首个实现切片包含共享按钮、四个工作集合的创建入口、先阅读后编辑的 Issue 详情、Workflow Run 的结果层级，以及 Administration 的部署作用域提示。第二个切片把相同的操作层级和面向用户的运行状态用于 Task 详情与对话中的 Task 卡片；Chat 起始页增加可见标题、可用方向键操作的标签页和真正的 Files 链接。Task 操作失败时，错误保留在对应卡片上；Task 列表加载失败时，对话仍可阅读并提供重试。Workflow 详情现在也使用共享按钮和可读的生命周期状态，分别把发布、运行或保存作为相应视图的主要操作。其他详情与管理页面、旧按钮规则清理、Issue 原子创建及独立操作员评审仍待完成。后续每个切片都应有独立可观察的结果与验证。

## 方案比较与非目标

| 方案 | 权衡 |
|---|---|
| 逐页微调 CSS | 局部修复快，但保留互相竞争的按钮系统和重复操作规则，不足以解决跨页面问题。 |
| **小型页面系统加分阶段迁移（推荐）** | 统一操作规则与五种页面模板，先改善核心工作路径，并随迁移删除过时样式。 |
| 引入新视觉框架或大型组件库 | 在现有 Portal 模式确定前增加依赖与概念；当前没有用户目标要求它。 |

本设计不增加 Dashboard、Board、新工作实体、品牌视觉活动或 Desktop 页面重设计。Board 仍由独立提案决定。只有在 Desktop 展示经过评审和验证时才向它应用共享基础组件变化；Portal 专属布局不能进入 `@buildmax/gui`。

## 证据与验收

首个完整切片只有满足以下条件才算完成：

- Schedules、Issues、Workflows、Agents 的空列表对同一创建动作最多只有一个可见控件，且其角色与样式和有数据时一致。
- 已迁移页面的主要、次要、危险操作均使用统一按钮契约；页面 CSS 不再改写按钮尺寸或焦点行为。
- 成员打开 Issue 后，无需先穿过编辑表单，就能识别状态、Owner、Executor、最新结果和可用的下一步。Save 与 Run 继续分开；未保存变更不能调度意外的执行者。创建失败不能留下含糊的部分创建 Issue。
- 已完成的 Task 或 Workflow Run 在 Trace 级细节之前提供结果和 Artifact。Workflow 图在参考宽度及 200% 缩放下完整显示每个节点的名称和状态。
- 全局 Administration 不暗示其权限随当前 Space 切换。原始机器枚举或不透明 ID 不作为工作对象或操作的主要名称。
- 键盘路径、焦点恢复、可访问名称、明暗对比度及加载／错误／空状态通过现有 Portal 浏览器矩阵。由一位未参与实现的运维人员完成 Issue 到结果、失败到诊断的旅程；记录步骤、障碍和边界，不虚构满意度分数。

## 开放问题

1. 在运维旅程验证之后，默认 Space 入口应保持 Chat，还是改为 Issues？页面系统无需先决定此事。
2. 应使用哪些真实 Issue 结果和失败状态作为样本与运维评审数据？本次走查的现有 QA 数据没有完成 Issue 到结果的整条链路。
3. 经过改进的筛选列表验证后，Issue 看板提案是否仍应优先实施？页面系统支持两种答案。
