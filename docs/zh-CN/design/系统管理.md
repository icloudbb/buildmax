## 1. 决策

BuildMax 引入一个部署范围的主体——**系统管理员（System Administrator）**，以可撤销授权的形式持久化在某个用户身上，绝不从其在某个 Space 中的成员身份推导而来。

三个备选方案都经过权衡后被否决：

- **让运维工作继续留在 CLI、数据库和集群里。** 这正是今天的现状。它使得日常账户管理必须依赖数据库密码，并且不会产生任何“谁做了什么”的可问责记录。
- **把 Space 所有者当作全局管理员。** 这会瓦解掉这个产品实际拥有的唯一边界。Space 是 Issue、Conversation、Artifact 和轨迹的所有权边界；一个能够跨 Space 读取内容的所有者，会让这条边界形同虚设。
- **在配置中写死一个管理员邮箱。** 它能一行代码就完成启动，但第一天之后就处处失灵：不能有第二个管理员，撤销权限需要重新部署，而且审计记录能指认的只有配置文件里的一个字符串。

一个持久化的授权，是唯一能同时支持多个管理员、无需重新部署即可撤销、并且审计记录能指名一个真实账户的方案。

这项授权是**运营这套部署的权力，而不是打开其内容的钥匙**。一名系统管理员可以创建和禁用账户、读取系统状态、跨 Space 搜索审计轨迹、查看 Space 与配额的元数据。但如果不是某个 Space 的成员，他们无法读取该 Space 的提示词、工具输出、Artifact、文件或运行轨迹。这一点由每一个其他调用方都要经过的同一套 Space 检查来强制执行，并且由一项测试来证明，而不只是本文档里的一句承诺。

## 2. 产品目标

一个私有部署的运维人员，应当能够在不使用数据库客户端、不执行 `kubectl exec`、也不知道 JWT 密钥的情况下回答以下问题：

- 谁拥有账户，他们上次登录是什么时候，现在还能登录吗？
- 有人今天要离职——我现在要怎么立刻停掉他们的访问权限？
- 有人忘记了密码——我要怎么帮他们重新登进去？
- 这套部署是否健康，运行的是哪个版本，应用了哪个 schema？
- 谁在哪个 Space 里、什么时候、修改了访问权限、模型，或配置？
- 存在哪些 Space，它们各自有多大，在用什么？

而他们不应当能够通过这个界面回答：“那个 Space 正在做什么工作”。

## 3. 现行基线

今天已经存在的东西，以及本设计所依托的这些锚点：

- Space 角色与 Space 授权辅助函数：`internal/core/space/space.go`、`internal/core/space/policy.go`。
- 每一条 JWT 路由用户身份的唯一入口：`internal/server/access` 中的 `Guard.ActiveUser`。每一个已认证的 handler 都通过它取得用户 id。
- 路由归属：各个 handler 子包自己的 `Register` 方法，并配有一项覆盖测试 `space_authz_matrix_test.go`，它会读取每一条路由，一旦某条 Space 范围内的路由没有对应的授权记录就会失败。
- 只增不减的审计轨迹：`internal/core/audit/audit.go`、`internal/service/audit`、`internal/infra/db/audit.go`，以及仅限 Space 所有者访问、限定在该 Space 范围内的 `GET /api/spaces/{space_id}/audit-events`。
- 已经在用数据库凭据运行的运维命令：`internal/bootstrap/user_admin.go`（`buildmax-server user create | login-code`）和 `internal/bootstrap/model_admin.go`（`buildmax-server model add | list | enable | disable`）。
- 会话：`model.RefreshTokenStore` 可以撤销单个会话（`RevokeSession`），而访问令牌是一个服务器从不存储的签名 JWT。
- 存活性、就绪性与版本信息：`internal/server/health.go`、`internal/bootstrap/server.go` 中的 `readinessChecks`，以及 `config.VersionString()`。
- Schema 状态：`internal/infra/db/migration.go` 中的 `schema_migration` 表。

由此可以归纳出五个缺口，而它们正是第一批次要补上的：

1. 完全不存在部署范围的主体。`system_admin` 以任何形式都不存在，包括作为 `user` 上的一个标志位。
2. `buildmax-server user ...` **不写任何审计事件**。创建账户、设置密码、签发验证码——这些运维人员所能采取的最敏感的操作——都不留任何记录。`model_admin.go` 确实会记录自己的改动，所以这是一处不一致，而不是既定策略。
3. 没有任何东西能够禁用一个账户。一条用户记录要么存在，要么不存在。
4. 没有任何东西能够列出或撤销某个用户的会话。`docs/deploy/authentication.md` 已经说明了这一点：今天要让某人下线，意味着要手动删除 `user_refresh_token` 表中的记录。
5. 一个 Space 的配额档位只在创建时从 `default_quota_tier` 设置一次。`internal/infra/db/quota_tier.go` 有 `GetQuotaTier` 和 `SeedDefaultQuotaTiers`，但没有任何方式能在事后为其指定另一个档位。

## 4. 主体及各自的可达范围

威胁模型是一张关于各类主体的表格，因为本设计需要防止的失败情形，正是某个主体悄悄获得了另一个主体的可达范围。

| 主体 | 认证方式 | 可以触达 | 不能触达 |
|---|---|---|---|
| **User** | 来自密码或登录验证码的访问令牌 | 自己所属 Space 的资源，按其角色所允许的范围 | 自己不在其中的任何 Space 里的任何东西 |
| **Space 所有者** | 同一个令牌，加上一条 `owner` 成员记录 | *该* Space 的成员关系、共享自动化，以及审计轨迹 | 任何其他 Space；任何部署范围的界面 |
| **系统管理员** | 同一个令牌，加上一条有效的授权记录 | 账户、授权、系统状态、脱敏后的配置、跨 Space 的**元数据**与审计、模型目录状态 | 自己不在其中的 Space 的提示词、消息、工具输出、Artifact、文件与运行轨迹 |
| **Worker 运行** | 一个指名单次运行的运行令牌 | 该次运行对应的四条 `/api/worker/*` 路由 | 每一条用户路由；每一次其他运行 |
| **基础设施运维人员** | 数据库、集群与密钥访问权限 | 依其构造方式，可触达一切 | — |

有两条推论值得明说，而不是留作言外之意。

**系统管理员不是权限阶梯的顶端。** 它是一个拥有不同权限轴的主体。Space 所有者在一个 Space 内拥有纵深权限；管理员则在整个部署的运营层面拥有广度权限，却在任何地方都没有纵深权限。这份权限不会与成员身份叠加：一个同时也是某 Space 成员的管理员，在该 Space 中获得的恰好就是普通成员的可达范围，不多也不少。

**基础设施运维人员仍然比系统管理员拥有更大的权力**，本设计并不改变这一点。它降低的是任何人需要*成为*基础设施运维人员的频率——这才是真正的目标：一个能通过一个受审计的界面完成日常工作的运维人员，就不再需要为此把数据库密码交出去。

下面这两种攻击场景塑造了具体的设计细节：

- **一次被攻破的管理员会话。** 爆炸半径受限于这个 API 所能返回的内容：只有元数据和状态，绝不会有内容。它所采取的每一个动作都会带着操作者的用户 id 出现在审计轨迹中。这个会话可以被任何其他管理员结束，也可以通过运维命令撤销该用户的全部会话来结束。
- **一次跨 Space 的读取尝试。** 一名管理员在没有成员身份的情况下调用某个 Space 的内容路由，会被现有的 Space 检查拒绝，因为管理路由是一棵独立的路由树，`authorizeSpaceAction` 从不会去查询这份授权。§11 把这一点变成了一项测试，而不只是一句断言。

## 5. 权限模型

### 5.1 一种角色，以授权记录的形式持久化

`internal/core/identity/system_grant.go` 定义 `SystemGrant` 和 `SystemGrantStore`。公共 ID 是不透明字符串，`GrantedAt` 为 `time.Time`，`RevokedAt` 为可选的 `time.Time`。数值关系键留在 store 内部，见 [实体身份](实体身份.md) 和 [时间戳表示](时间戳表示.md)。

`systemGrantRow` 持久化到 `system_grant`。唯一索引为 `(user_id, role, live_marker)`：存活时 marker 为固定非 NULL 值，撤销时与 `revoked_at` 一同更新并清空。包含可空 `revoked_at` 的唯一键会允许 MySQL 中出现重复存活授权，已不是当前机制。

`RevokeSystemRole` 原子地检查 `keepLastHolder` 并撤销。API 保留至少一名有效持有者，即拥有未撤销授权且账户启用的人；账户禁用使用相同保护。数据库直连运维路径可为恢复而主动撤销最后一份授权。MySQL 并发证据位于 `internal/infra/db/system_grant_test.go`。

三个形态选择，各自都曾采用过另一种方案：

- **是一个 `role` 字段，而不是一个布尔值。** 该提案的问题 1 曾问过：现在是否需要一个只读的 `system_observer` 角色和一个支持角色。答案是不需要——没有人提出过这个需求，而凭空发明一个用不上的角色，正是 §16 所警告的那种错误。但这个字段今天的代价只是一个 `varchar`，而这正是“日后新增一个角色”和“日后迁移一个布尔字段”之间的区别。在第二个角色真正有调用方之前，这个存储只接受 `system_admin`。
- **不是 `user` 上的一个标志位。** 一个标志位没有授权发起人，没有时间戳，也没有历史记录。而这三样东西正是这里全部的意义所在。
- **没有 `superuser`。** 一个作用域没有被明确写下来的权限，会悄悄地不断膨胀。每一条管理路由都要指名它所需要的角色，而 §11 会在某条路由没有这样做时使构建失败。

### 5.2 如何进行检查

一个与 Space 检查并列、但从不嵌入其中的独立辅助函数：

```go
// internal/server/handlers/system_authz.go
func (h *Handler) requireSystemAdmin(w http.ResponseWriter, r *http.Request) (userID string, ok bool)
```

它先调用 `requireAuth`，再调用 `ActiveSystemRoles`，并在写出响应之前，先以空的 `space_id` 记录一次 `access.denied`（如果被拒绝的话）。

`authorizeSpaceAction` 不会被修改，也绝不能被修改。一份授权不应成为 Space 检查的参数；一旦它成为参数，§4 中所述的边界就不再成立，而且不会有任何测试察觉到这一点。

### 5.3 状态码

- 没有凭据，或凭据无效：**401**，与其他任何路由一致。
- 凭据有效但没有授权：**403**。

不是 404。隐藏 `/api/admin/*` 的存在本身是做不到的——这些路由都在开源的路由注册代码里，也在 Portal 的构建产物里——假装它们不存在，只会白白牺牲掉一个正确状态码本应带来的清晰度。真正不能泄露的是数据，而 403 不携带任何数据。这与现有的、仅限所有者访问的审计路由采用的是同一种形态，Portal 也早已把从那里收到的 403 理解为“这不是给你看的”，而不是当作一个 bug。

## 6. 启动与锁定恢复

第一份授权来自一条运维命令，而不是来自配置：

```text
buildmax-server admin grant <email>     # grant system_admin
buildmax-server admin revoke <email>    # revoke it
```

它与 `user` 和 `model` 一起，遵循这两者早已遵循的同一条规则：它读取的是服务器自己读取的那份 `server.yaml`，因此在容器或 Pod 中都能原样工作，并且它需要数据库凭据——这正是铸造部署级权限应付出的正确代价。

这就回答了提案中的问题 2，而回答的方式是**不**新增一个配置项。`server.yaml` 中的一份 `system_admins:` 列表，会成为审计轨迹无法描述的第二个权限来源，一个撤销操作在不重新部署的情况下无法触及它，而且在每一种边界情形下，它都必须与这张表分出胜负。一个来源，一套说法。

恢复机制正是从同一个选择中自然得出的：这条命令无论存在零个还是十个管理员都能工作，不需要一个正在运行的服务器，也不需要一个 Portal 账户。这里没有需要存储、轮换或可能泄露的紧急救援凭据，因为恢复路径本身就是那条日常路径。

有一条不变量守护着两者之间的这道缝隙：

- **API** 拒绝撤销或禁用最后一名有效的 `system_admin` 持有者，并给出一条指名该命令的消息。管理员不能靠点几下鼠标就让整个部署一个管理员都不剩。
- **命令**允许这样做，并会打印出这意味着什么。那个管理员已经离职的运维人员，需要的正是这个；而且他们本就已经持有让这条限制形同虚设的凭据。

如果还有另一名管理员在场，通过 API 自我撤销是被允许的。禁止这样做，只会变成要求一位同事替你做同一件事。

### 6.1 运维界面

运维界面按调用方能出示的权限划分，而不是按功能划分：

| 界面 | 用途 | 认证方式 | 可用性 |
|---|---|---|---|
| `buildmax-server` | 仅用于紧急救援与引导，外加运行 Server 本身 | 直接访问 Server 配置、数据库和签名密钥 | 不依赖 Portal，也不依赖健康的公共 Server |
| Admin API（`/api/admin/*`） | 日常管理的稳定编程契约 | 用户会话加一份有效的系统授权 | 需要 Server |
| `buildmax admin` | 可脚本化的日常管理 | Admin API，复用 `buildmax` 客户端登录 | 需要 Server |
| Portal | 引导式日常管理 | Admin API | 需要 Server 和 Portal |

`buildmax admin` 与 Portal 是同一个 Admin API 的对等客户端，两者都不接触数据库。`buildmax-server` 只保留必须紧挨着数据库或签名密钥的操作：

- `admin grant | revoke` —— 第一份授权、从零管理员状态恢复，以及强制撤销最后一名持有者（§6）；
- `run-token` —— 用于诊断单次运行 worker 路由的凭据；
- `space recover-owner` —— 在公共 Server 或 IdP 不可用时执行 §8.4 中仅限所有者均已禁用的 Space 恢复；
- `user create | login-code` 与 `model add | set-key | list | enable | disable` —— 在任何客户端能够认证之前为新部署播种数据。它们是引导原语，不是日常界面；日常的账户与模型工作走 Admin API。

已认证界面不提供某项操作，只能出于以下理由，并在本应出现该操作的位置说明：

- 第一份授权与从零管理员状态恢复，不能依赖一个已经认证的管理员；
- 强制撤销最后一名持有者，刻意保留为需要数据库授权的操作；
- 运行令牌是用于 worker 路由诊断的 bearer 凭据，不是日常管理结果；
- 进程启动配置无法通过单个 Server 副本如实编辑（§7.2）。

规则是每种变更只有一个所属服务。HTTP handler 是它之上的适配层，`buildmax-server` 则以系统操作者身份直接调用同一个服务，因此 HTTP API 宕机时引导与恢复仍能工作。授权归 `internal/service/systemadmin`，账户停用归 `internal/service/accountlifecycle`，所有者恢复归 `internal/service/spacerecovery`，模型创建与凭据归 `internal/service/llmcatalog`，插件目录归 `internal/service/plugin`。收敛尚未完成：账户创建、登录验证码和会话撤销仍是管理 handler 与 `buildmax-server user` 直接发起的单次存储调用，各自记录审计事件；`buildmax-server model list | enable | disable` 也绕过了 Admin API 所用的目录服务。

## 7. 服务器管理 API

所有路由都在 `/api/admin/*` 之下，全部要求 `system_admin` 权限，并且没有一条会接受 `space_id` 路径参数——一条看起来像是 Space 范围内的管理路由，恰恰会引发 §4 想要防止的那种混淆。

### 7.1 路由

本表即已注册的路由面；由 `internal/server/handlers/admin` 负责。

| 路由 | 返回内容 | 拒绝返回的内容 |
|---|---|---|
| `GET /api/admin/me` | 调用者自己的授权：角色、授予时间、授予人 | — |
| `GET /api/admin/grants` | 有效授权，按请求也可包含已撤销的 | — |
| `POST /api/admin/grants` | 向某个用户 id 授予 `system_admin` | 对一个不存在的账户授权 |
| `DELETE /api/admin/grants/{user_id}` | 撤销授权 | 最后一名有效持有者（§6） |
| `GET /api/admin/users` | 账户列表，按最新排序，支持按邮箱 `?q=` 搜索，分页 | 密码哈希、登录验证码、令牌值 |
| `GET /api/admin/users/{user_id}` | 单个账户：邮箱、姓名、配额档位、上次登录时间与平台、`has_password`、`disabled_at`、按角色列出的 Space 成员关系、活跃会话数 | 上一行中的任何内容 |
| `POST /api/admin/users` | 创建一个账户及其个人 Space | — |

### 7.2 有意不包含的内容，及其原因

- **模型创建与提供商凭据 — 后续已实现。** `POST /api/admin/llm/models`、Portal 和 `buildmax admin model add` 现可接受只写凭据，并在部署 KEK 下加密。缺少加密边界时拒绝带凭据的模型。`buildmax-server model add` 保留为数据库直连引导原语。
- **配置写入。** `GET /api/admin/config` 是只读的，原因是机制性的，而不是出于谨慎：`server.yaml` 是在进程启动时被读取的，而一个多副本部署中每个副本各有一份文件。通过 Portal 写入，只会改变其中一个副本对世界的看法，或者谁的都不改变。在有了一个真正的配置存储之前——那是一项独立的工作——配置将继续由源代码管理。这回答了提案中的问题 6。
- **日志。** 这一批次中没有日志端点。这回答了提案中的问题 4，答案是：原始日志留在部署自身的可观测性系统里。构建一个脱敏后的日志查看器，意味着要拥有一个脱敏器，而它一旦失效，就会把一段提示词或一个密钥泄露到一个本应是安全的界面里；`GET /api/admin/system` 加上审计轨迹，再加上现有的运行视图，已经覆盖了 §2 列出的那些问题，不需要日志查看器。如果某个真实事故中的证据表明这里确有缺口，那份证据会指名需要新增的具体字段——这比凭猜测构建一个日志查看器要好得多。
- **跨 Space 内容。** 这里没有任何东西能读取提示词、Artifact、文件或轨迹。这回答了提案中的问题 5，答案是“这一批次里不会有”。一条能够触达 Space 内容的支持路径，需要自己独立的设计，涵盖请求、Space 同意、过期时间、脱敏，以及一个独立的审计动作；它不会是这张表里某条路由上的一个参数。
- **配额档位分配。** `GET /api/admin/spaces/{space_id}` 会显示档位以及相对该档位的用量。要修改它，需要一个目前还不存在的存储方法（§3，缺口 5），而这也是本文档里唯一一项属于“新功能”而非“对现有状态开一扇窗”的内容。它尚未实现，等待真正需要它的部署。实现时，它只分配已有档位——档位定义在有证据表明不足之前继续由种子数据提供——经由 `internal/service/quota` 而不是由 handler 直接操作原始存储；拒绝未知档位；在下一次配额检查时生效，不终止正在运行的工作；并记录 `space.quota_tier_changed`，指名操作者、Space，以及新旧档位。若用户级的重复配额档位已无其他读取方，则一并移除。

## 8. 账户禁用语义

`userRow` 上的 `disabled_at` 是可空时间戳，普通账户为 nil，它是部署范围的闸门。不存在 `space_member` 记录则是单个 Space 的闸门。每一条准入或派发工作的路径都检查这两者（§8.2）。让一个人离开，是对这两个既有状态的协同使用，而不是一个员工、离职任务或策略实体。

两道闸门性质不同，把它们分开，恢复才可预测：

- **账户禁用是覆盖在保留状态之上的可逆闸门。** 成员关系、Space 数据和未退役的 webhook 密钥都会保留，并在 `disabled_at` 生效期间被拒绝。启用会直接重新放开它们，无需任何恢复步骤。`email` 仍是唯一键，因此被禁用的账户保留自己的地址：同一个人通过重新启用该账户回来，一个地址绝不会被重新绑定给另一个人。释放地址需要删除账户，而账户删除并不存在（§16）。
- **移除成员是对单一关系的破坏性变更。** `space_member` 记录被硬删除，之后的再次邀请是一次新的加入，带有新的 `created_at`。见 [Space 成员生命周期](Space成员生命周期.md) §5.5。

三条不变量对两者都成立：

- **数据比访问权活得更久。** 成员关系、Task、结果、Artifact、轨迹、用量和审计记录既不删除也不重新归属。其余成员通过 Space 保持访问——保留边界是 Space，而不是创建者。
- **恢复必须显式进行。** 启用账户或重新邀请成员，不会复活已撤销的会话、已退役的 webhook 密钥、已取消的运行或已暂停的 Schedule。
- **历史保留原始操作者。** 创建者 ID 绝不会被改写成运维人员或继任者。恢复操作记录它们自己的操作者。

### 8.1 凭据与工作

| 内容 | 禁用后的效果 | 原因 |
|---|---|---|
| **密码登录** | 在密码校验通过*之后*被拒绝，返回 `account_disabled` 和 403 | 如果在校验之前就检查，会告诉一个未认证的调用方哪些地址已经注册。在校验之后检查，只会把真相告诉那个本就已经能证明这个账户属于自己的人 |
| **登录验证码** | 同上，且任何未使用的验证码都会被作废 | 在禁用之前签发的验证码，不能成为一条重新进入的途径 |
| **刷新令牌** | 拒绝；禁用时立即撤销所有会话 | 这是真正可以被撤销的那种凭据，所以立刻撤销它 |
| **访问令牌** | 在下一次请求时被拒绝 | 见下文 |
| **Webhook 密钥** | 禁用期间在 `POST /api/webhook` 处被拒绝。暂停使用时保留，因此有意的重新启用会原样恢复集成；带 `retire_webhook_keys` 的离职禁用会永久撤销它们。由运维人员主动选择：API 字段和 Portal 复选框默认都保留密钥 | 需要比某个人存续更久的集成，需要一个单独设计的机器主体，而不是一个被遗忘的个人凭据 |
| **该账户创建的已启用 Schedule** | 以 `pause_reason = creator_disabled` 暂停 | 否则 Schedule 会在每个到期时间继续以已收回的权限准入工作 |
| **该账户发起的 PENDING 运行** | 禁用会记录取消请求；派发闸门（§8.2）在运行令牌或 worker 存在之前，把被认领的运行转为 `CANCELED`，`cancel_reason = creator_disabled` | 这些运行还没有开始，而权限被收回是一次取消，不是一次失败 |
| **SCHEDULED 与 RUNNING 运行** | 以 `cancel_reason = creator_disabled` 请求取消。worker 在下一次取消轮询时停止并报告 `CANCELED`；从不回应的 worker 由陈旧运行兜底机制结算 | 已经开始的工作被停止，而不是被改写。部分输出和 Artifact 仍作为证据保留；正在进行的工具调用或外部写入可能会完成，BuildMax 不回滚外部副作用 |
| **已完成的运行** | 不变 | 它们是 Space 的历史 |
| **已经铸造好的运行令牌** | 无法撤销 | 它是一个签名，不是一条数据库记录。它受作用域和 `worker.run_token_ttl` 约束，[部署——认证](../deploy/authentication.md)中已有说明。worker 拉取闸门（§8.2）会阻止禁用前刚铸造的令牌启动 Agent |

访问令牌是这里面有意思的一个。它是一个服务器不存储的已签名 JWT，所以“撤销它”实际上意味着“不再认可它”，而唯一能做到这一点的地方，是身份被解析出来的那个环节：`requireAuth`。在那里加上这项检查，每一次已认证的请求都要多付出一次主键读取的代价。

这个代价是可以接受的，而且值得说清楚为什么：产品中每一条 Space 范围的路由，本就已经在每次请求时调用 `ListSpaceMembers`，那是一次比这里更宽泛的读取。把禁用检查放进 `requireAuth`，严格来说比同一个请求本就要做的工作还要便宜。如果日后的性能画像显示情况并非如此，解决办法是在它前面加一层短 TTL 的缓存——同时诚实地说明：有了缓存，就会有一个窗口期，让一个已禁用的账户仍然能用。第一版实现里没有缓存。

另一个方案——干等访问令牌自然过期，默认是七天——被否决了。“禁用这个账户”如果意味着“大约一周之后生效”，那就不是这个功能想要的效果。

启用只会翻转这道闸门，不做任何其他事情。会话仍然保持已撤销，已取消的运行仍然是已取消，已暂停的 Schedule 仍然暂停，已退役的密钥仍然退役，这个人则可以重新登录。撤销这次禁用的所有效果，不是这里的目标。

### 8.2 执行资格

`internal/core/eligibility` 负责回答一个问题：这个用户现在能否在这个 Space 中运行工作？`Checker.Check(ctx, userID, spaceID)` 返回 nil、`ErrAccountDisabled`（账户已禁用或不存在）、`ErrNotSpaceMember`，或在权限存储出错时返回 `ErrUnavailable`。普通成员身份即可；它不判断任何特定角色的管理权。

主体始终是运行的发起者 `task_run.created_by`，它同时也是运行令牌中的用户声明。`task.created_by` 是持续 Task 的来源记录，不是其后续轮次的权限依据，因此即便 Task 的创建者已被禁用，一位有资格的同事发起的 Continue 仍会运行。见 [Agent 执行与 Task 线程](Agent执行与Task线程.md) §10。

无人值守的工作在四个位置接受检查：

| 检查点 | 位置 | 无资格时 | 权限存储不可用时 |
|---|---|---|---|
| Schedule 触发 | `ScheduleDispatcher`，认领到期触发之前 | 以 `creator_disabled` 或 `creator_not_member` 暂停 Schedule，不准入任何工作 | 不触发也不认领；到期时间保持到期，不计为失败触发，下一个周期重试 |
| 派发 | `Scheduler`，认领 PENDING 运行之前 | 以相应的 `cancel_reason` 转为 `CANCELED` | 不派发；运行保持 `PENDING`，下一次轮询重试 |
| Worker 拉取 | worker 对自身运行的 `GET` | 记录带原因的取消请求，因此 worker 不启动 Agent 并报告 `CANCELED` | 返回 `503`，不交出运行；正在启动的 worker 以退避方式重试，最长两分钟 |
| 对账器 | `EligibilityReconciler`：每分钟一次，扫描尚无取消请求的活跃运行，每批 200 条 | 带原因请求取消 | 不动该运行；下一次扫描再次检查 |

权限存储不可用时失败即关闭，但不破坏工作：任何闸门都不会启动无法确认其发起者的工作，也不会凭猜测取消或暂停。因此持续的故障会让无人值守的工作停滞，而不是继续运行。派发器按最早的 PENDING 运行优先处理，所以一个无法判定的运行会阻塞队列，直到存储恢复响应。正在启动的 worker 若耗尽重试预算，会以非零状态退出：在本地运行器下这会使运行失败，在 Kubernetes 下则消耗 Job 的退避次数。每次拒绝都会连同运行或 Schedule 以及发起者一并记录日志。

人类请求保留各自的逐请求检查：`access.Guard` 检查账户与会话，Space 授权辅助函数检查成员身份。IM 渠道消息调用同一个 Checker，并在任何错误（包括存储不可用）时拒绝。

对账器不需要离职记录，因为资格本身就是持久的“未完成工作”判定：只要一个无资格的发起者还拥有活跃工作，一次扫描就能找到它。每个动作都是幂等的，并经由既有的受保护运行状态转换执行，因此并发的禁用、移除、派发、完成和取消会收敛，终态运行永远不会被改变。

与既定契约的偏差，记录在此而不隐藏：

- **Task 准入不在服务层再次检查。** Create、Continue 和 Retry 依赖 HTTP 守卫；Task 服务不调用 Checker。
- **Workflow 对账不检查资格。** 后续步骤的 TaskRun 以 WorkflowRun 创建者的身份被准入，并在派发或 worker 拉取时被拦下；其 `CANCELED` 步骤会把 WorkflowRun 结算为 `canceled`。
- **移除成员不会触发即时清理。** 被移除成员在该 Space 中的活跃运行会在一次扫描内被对账器处理，其在该 Space 的 Schedule 在下一个到期时间暂停。在此之前，一个触发频率很低的 Schedule 会一直显示为已启用。

### 8.3 停用编排与影响

`internal/service/accountlifecycle` 负责编排一次禁用，handler 不做这件事。它先提交账户闸门，然后撤销会话、按要求退役 webhook 密钥、暂停该账户已启用的 Schedule，并为其活跃运行请求取消。闸门才是权威，因此清理失败只是不便，不会带来授权：每条准入和派发路径都已经在拒绝，对账器也会收敛这些运行。某一步失败不会阻止其后的步骤。`PUT /api/admin/users/{user_id}/state` 返回重新加载的账户和清理计数（`sessions_revoked`、`webhook_keys_retired`、`schedules_paused`、`runs_canceled`），作为彼此独立的事实。闸门一旦提交，即使清理失败，该调用也返回 200 并记录 `user.disabled`：此时响应在 `cleanup_failed` 中列出失败的步骤（`sessions`、`webhook_keys`、`schedules`、`runs`），事件的 detail 为 `cleanup incomplete: <steps>`。再次禁用是安全的——每一步只作用于仍然有效的对象——它就是重试方式：Portal 以"Retry cleanup"提供重试，`buildmax admin user disable` 会打印重试命令并以非零状态退出。错误状态码表示闸门未提交；唯一的例外是重新读取账户失败，其消息会说明变更已经生效。

`GET /api/admin/users/{user_id}/deactivation-impact` 是运维人员首先看到的只读投影：有效会话、webhook 密钥、共享 Space 的成员关系与角色、该账户唯一拥有的共享 Space、已启用的 Schedule、按状态统计的活跃运行，以及取消时限。它只返回计数和 ID——不含提示词、输入、输出、Artifact 名称、轨迹、原始错误或密钥。这个时限是固定值，即 worker 五秒的取消轮询加上陈旧运行兜底机制两分钟的取消宽限期，而不是读取配置得出。Portal 在禁用之前通过 `DeactivationImpactModal` 展示这一投影，并在那里提供 webhook 密钥退役选项。

仅在 IdP 侧停用仍然是有界的，而非即时的：没有 SCIM 或经过验证的登出通道时，提供方禁用一个人，BuildMax 一无所知。受支持的即时流程是 BuildMax 账户禁用；OIDC 绝对会话寿命就是仅 IdP 停用的上限，由[企业身份与访问](企业身份与访问.md)第 3 阶段的验证记录。

### 8.4 Space 所有者恢复

计划内的路径是即将离开的唯一所有者先转移所有权；影响投影会列出需要这样做的 Space。紧急禁用绝不会因所有权而被阻止，因此可能留下一个所有者都无法登录的共享 Space。`internal/service/spacerecovery` 是为这种情形准备的唯一一项狭窄的系统管理员操作：

- 仅当共享 Space 的每一位已记录所有者都已被禁用时适用；
- 继任者必须已经是一名已启用的成员；
- 拒绝个人 Space，也不创建任何成员关系；
- 复用普通的所有权转移，把一名已禁用的所有者降为 admin；
- 不给管理员任何成员身份或内容访问权；并且
- 记录 `space.ownership_recovered`，指名操作者、继任者和被降级的所有者。

它可通过 `PUT /api/admin/spaces/{space_id}/owner`、Portal 管理区 Spaces 中的 “Make owner”，以及在公共 Server 或 IdP 不可用时使用的紧急救援命令 `buildmax-server space recover-owner <space_id> <successor_email>`（操作者为 `buildmax-server`）访问。它不是转移一个健康 Space 的通用权力。这条审计事件和其他审计写入一样（§9），在转移提交之后尽力写入，而不是事务性的。

## 9. 审计事件

新增的动作，一旦写入就永久保留：

```go
AuditSystemAdminGranted = "system.admin_granted"
AuditSystemAdminRevoked = "system.admin_revoked"
AuditUserCreated        = "user.created"
AuditUserDisabled       = "user.disabled"
AuditUserEnabled        = "user.enabled"
AuditLoginCodeIssued    = "user.login_code_issued"
AuditSessionsRevoked    = "user.sessions_revoked"
AuditModelEnabled       // exists
AuditModelDisabled      // exists
AuditAccessDenied       // exists; reused for admin routes, with space_id empty
```

全部以空的 `space_id` 写入，因为它们都不属于任何 Space。`AuditEvent` 的结构早已支持这一点——它当初就是为 `user.login` 设计的——所以不需要改动 schema。所有者恢复（§8.4）后来新增了 `space.ownership_recovered`，它带着被恢复 Space 的 id 写入，因此该 Space 自己的轨迹也能看到它。

新增这些事件带来了两个后续问题：

**运维命令需要记录。** `buildmax-server user create` 和 `login-code` 会写入与其 API 对应操作相同的动作，`actor_type` 为 `system`，`actor_id` 为 `"buildmax-server"`——这正是 `model_admin.go` 早已在使用的那个操作者 id，因此同一个行为不会获得两个不同的名字。这在 M1 中补上了 §3 中的缺口 2。`model_admin.go` 早就这样做了；`user_admin.go` 会与之保持一致。一个不留任何记录的运维操作，比一个只能指名机器、指不出具体人的记录还要糟糕，而指名机器正是对实际发生情况的诚实描述。

**这条轨迹需要一个不限于 Space 范围的读取方式。** `ListAuditEvents(spaceID, ...)` 无法返回一次登录或一次授权，因为它们不属于任何 Space。因此 `GET /api/admin/audit-events` 需要一个新的、带有可选过滤条件的存储方法：

```go
SearchAuditEvents(ctx context.Context, f AuditFilter, limit, offset int) ([]AuditEvent, int, error)
```

`AuditFilter` 携带可选的 `SpaceID`、`ActorID`、`Action`、`Since`、`Until`。现有那条仅限所有者访问的 Space 路由保留它原有的狭窄方法：一个 Space 所有者问的是一个更窄的问题，不应该意外获得那个更宽泛的方法。

失败处理策略不变。一次失败的审计写入会被记录日志并丢弃，而不会导致对应的操作本身失败，这与 `internal/service/audit` 今天所记录的策略完全一致。这项策略是已经定案的，而不是悬而未决的——参见[《Space 治理》](./Space治理.md)§12 问题 2——本设计不会重新讨论它。本设计要做的，是让其中唯一仍然悬而未决的部分变得更加尖锐：这里新增的这些动作，恰恰是“尽力而为”这套策略论据最薄弱的地方，因为一次已经发生却没有被记录下来的授权，正是一次调查最需要查清的情形。一次授权是否应当获得一次事务性保证的记录，正是这个残留问题，本设计让它变得更加紧迫，而不是给出了答案。

## 10. Portal 管理界面

Administration 与 Space 设置分离，并且只有在 `GET /api/admin/me` 确认
授权后才作为侧边栏一级入口出现。进入后侧边栏切换到部署作用域：Space 切换器
被替换为静态的 “Deployment” 标签，侧边栏直接列出各管理区块（来自
`portal/src/features/admin/nav.ts` 中共享的 `ADMIN_NAV`），其后是 “Back to
space” 返回项；页面只渲染当前区块，不再自带 tablist。导航只是表现层；Server
会独立授权每次请求。

`portal/src/pages/admin/AdminSettings.tsx` 与 `portal/src/features/admin`
负责八个区块：

1. **Overview** — 构建与 readiness、worker 模式、run 计数、调用者授权，
   以及可折叠的脱敏配置。
2. **Administrators** — 当前及历史授权、按账户邮箱授予权限，以及带最后有效
   持有者保护的撤销操作。
3. **Accounts** — 分页筛选、可刷新恢复的详情、账户创建、登录码、禁用／启用，
   以及有效 Session 列表和单个／批量撤销。禁用前会先展示停用影响（§8.3）和
   webhook 密钥退役选项。
4. **Spaces** — 分页元数据、成员关系和用量，以及用于仅限所有者均已禁用时恢复
   （§8.4）的 “Make owner”；不提供内容访问或 quota tier 变更。
5. **Models** — 列出模型、使用加密的只写凭据创建模型，以及启用／禁用。
   读取响应不会返回凭据。
6. **LLM calls** — 跨所有 Space 的受管调用账本：每次调用的模型、token、成本与
   状态，可按用户、模型、状态和 surface 过滤。不含提示词或生成内容。
7. **Plugins** — 目录和 release 的查看、退役、恢复与撤回；Portal 发布仍然推迟。
8. **Audit** — 跨 Space 元数据搜索与导出；时间范围筛选仍仅在 API 提供。

Session 撤销只影响 refresh token，不会使已签发 access token 失效；最近轮换
时间也不是实时在线状态。`portal/e2e/admin.spec.ts` 覆盖 Session 列表；单个
Session 撤销由 `TestAdminSessionsListAndSingleRevoke` 覆盖，因为浏览器场景会
有意保留自己的登录。

## 11. 授权矩阵

`space_authz_matrix_test.go` 中的 Space 路由矩阵之所以存在，是因为这些检查存在于各个 handler 的辅助函数里，而不是集中在一个中间件里，因此一条忘记调用检查的路由不会在编译时报错。管理路由恰好具有同样的性质，因此也得到了同样的处理——一个与之并列的 `system_authz_matrix_test.go`：

1. **该包注册的每一条 `/api/admin/*` 路由都必须有一条对应记录。** 没有对应记录的路由会使构建失败，一条指名了某个已不存在路由的记录同样会使构建失败，因为一条失效的记录读起来就像是有覆盖，实则没有。这一项在 M1 中上线，并通过新增一条未加保护的路由、观察它确实失败来验证——一项从未真正触发过的覆盖测试，不能算作已知有效。
2. **四种调用方以真实请求的方式驱动每一条路由**：一名系统管理员、一名没有授权的 Space 所有者、一名普通用户，以及一个匿名调用方。期望结果分别是：200 左右、403、403、401。
3. **一份被撤销的授权等同于非管理员。** 同一个用户在经过 `RevokeSystemRole` 之后，在每一条记录上都会得到 403。这证明了撤销是一次实时检查，而不是一次仅在启动时读取的结果。
4. **一份授权不是一把 Space 钥匙。** 一名没有任何成员身份的系统管理员去驱动那些 Space 范围的内容路由，在每一条上都会得到 403。这项测试正是让 §4 中那张表成立的依据，如果有人提议在 `authorizeSpaceAction` 内部查询这份授权，这也是应当首先查看的测试。M4 在最容易被当成例外的那个界面上再次重申了这一点：一名能够读取某个 Space 名称、规模和配额的管理员，依然打不开它的 Issue。
5. **任何管理员响应都不包含密钥。** 对账户和配置相关路由的响应体做断言，检查其中是否出现 `api_key`、`password`、`hash`、`secret`、`token`。这个方法很粗糙，但它能抓住那种现实中真会发生的失误：有人不小心返回了一个数据库记录结构体，而不是一个响应结构体。这一项在 M2 上线，因为那正是第一条可能携带这类内容的路由出现的地方。

第 1–4 项在 M1 中上线，还附带了两项草案里没有点名的内容：一次授权存储错误会导致拒绝而不是放行；一次被拒绝的管理员请求会以一个空的 space 被记录下来，而一次未认证的请求则什么都不会记录——因为没有一个操作者可以指名，而如果为一次未认证的请求也生成一条以某种键值标识的记录，就等于让任何人都能写入记录。

提案中“需要的证据”清单要求一次端到端的授权矩阵测试，以及一次锁定场景演练。第 1–4 项就是这份矩阵。锁定场景演练则是一项存储层面的测试：授权、通过 API 反复撤销直到只剩一个、观察 API 拒绝继续撤销、用命令撤销最后一个、再重新授权——全程都不直接触碰数据库。

## 12. 范围之外

- 第二个或第三个系统角色，在它真正有调用方之前都不会加入（§5.1）。
- 组织层级、自定义角色、按资源划分的 ACL。
- OIDC、SAML、SCIM。[企业身份与访问](企业身份与访问.md)记录负责这些内容。本设计对它施加的唯一约束是：一个身份提供方（IdP）可以*新增*授权，而这条运维命令必须继续可用，这样一次 IdP 故障就不会把一套部署锁死在自己的管理界面之外。
- 日志查看器、日志搜索，或任何 SIEM 形态的东西（§7.2）。
- 配置写入（§7.2）。
- 任何形式的跨 Space 内容访问（§7.2）。
- 审计导出、留存策略，以及删除控制。这些在[《Space 治理》](./Space治理.md)§12 中处于未决状态，本设计不改变那里的答案。
- 计费，以及任何关于严格支出控制的承诺。`llm_call` 台账只是事后记录了实际花费；预留额度机制并不存在。

## 13. 后端计划

### M1. 授权模型、命令与授权检查——已完成

`identity.SystemGrant` 与 `SystemGrantStore`、`system_grant` 表上的 `systemGrantRow`、不透明公共 ID、`buildmax-server admin grant | revoke`、`requireSystemAdmin`、相关审计动作，以及第一条路由——`GET /api/admin/me`——使矩阵测试从一开始就有东西可以覆盖。

验收已达成：可以从命令行完成授权、列出授权、撤销授权；一个获得授权的用户在 `/api/admin/me` 上得到 200，一个没有授权的用户得到 403；每一次状态变化都出现在审计轨迹中。

有两处与上文草案的落地方式不同，均为刻意为之：

- **审计中的操作者是 `buildmax-server`，而不是 `cli`。** `model_admin.go` 早就为同一类操作写入这个字符串，一条轨迹里为同一个操作者使用两个不同的名字，比一个只能说明是哪个二进制程序在运行的名字更糟糕。`system_grant.granted_by` 出于同样的原因携带同一个字符串。
- **`requireSystemAdmin` 先认证，再检查存储**，顺序与 `withUserAndStore` 相反。如果先检查存储，会告诉一个尚未证明自己身份的匿名调用方“系统管理功能未配置”这类信息，而这些信息本不该透露给他们。

### M2. 账户——已完成

`/api/admin/users` 系列路由、`disabled_at`、登录/刷新/webhook 的拒绝逻辑、会话撤销、调度器守卫、`requireActiveUser` 检查，以及账户相关的审计动作。`/api/admin/grants` 系列路由也在这一阶段落地，而不是在 M1——最后一条授权的不变量需要有一条路由去强制执行它，而账户生命周期与权限生命周期本就是同一个运维人员的工作。

验收已达成：运维人员可以创建一个账户、签发一个验证码、禁用它，并在下一次请求时看到这个被禁用的账户被拒绝——每一步都出现在轨迹中。

有三处与草案的落地方式不同：

- **待处理的运行当时是失败而不是取消。** 那时 `CANCELED` 尚不存在。后来的停用生命周期将其改为携带 `cancel_reason` 的取消（§8.1）。
- **`requireActiveUser` 只会拒绝一个确实存在且已被禁用的账户。** 一个指名了存储中不存在的账户的令牌会原样放行。因为没有任何东西会删除账户，所以这种状态在一个部署中根本不会出现，而“一个未知主体在每一条路由上意味着什么”是一个独立于禁用功能之外的改动。
- **管理员不能禁用自己的账户。** 否则他们会在请求进行到一半时就把自己锁在外面，除了运维命令之外没有别的回头路——这是一个很容易犯、却毫无意义去允许的错误。

### M3. 系统状态与脱敏配置——已完成

`GET /api/admin/system` 和 `GET /api/admin/config`。bootstrap 早已注册的那些就绪检查，被转换成管理 API 的探测形态并直接上报，而不是重新发明一套，因此状态页面和 `/readyz` 不可能出现不一致。脱敏采用的是一份“可以展示的字段”白名单，而不是一份“必须隐藏的字段”黑名单——黑名单在日后每新增一个字段时都会默认放行，是不安全的失败模式。

验收已达成，有三处决定值得记录：

- **脱敏视图位于 `internal/config`**，作为 `ServerConfig.Redacted()`，而不是放在 handler 里。这样一来，当有人新增一个配置字段时，“这个字段是否可以展示”这个决定，就落在了他们本来就要编辑的那个文件里。一项测试会遍历 `ServerConfig`，检查那些字段名标明是凭据的字段，一旦有遗漏就会失败，因此这份白名单不会悄悄落后于结构体本身。
- **版本与部署相关事实来自 bootstrap。** `internal/server` 不允许导入 `internal/config`——架构测试强制执行这一点——而正是这条把基础设施细节挡在就绪端点之外的规则，同样把配置细节挡在了这个端点之外。
- **`sandbox_surface` 上报为空**，而这不再是因为无内容可报：`internal/agentapp/taskrun` 现在会传入 `config.WorkerSandboxSurface()`。一个 Worker 最终解析出的沙箱面，取决于该 Worker 自己运行所在的环境，而这个端点回答的是服务器自己的环境。在今天上线的每一种部署里，两者恰好一致——因为都来自同一个镜像——但“因为构造方式而恰好一致”并不等于“实际观测到一致”，而一个只能推断出、却看不见真实边界的安全面，有可能指错边界。真正上报一次运行实际解析出的边界，应当由那次运行自己来做——它本就已经为审计目的钉住了自己的层级；把它接入这个端点是一项待开展的工作，而不是本记录已经做出的决定。

`GET /api/admin/system` 采用降级而非直接失败的方式：它的每一次读取都是尽力而为的，因为一个在自己五个问题中有一个答不上来时就返回 500 的状态页面，恰恰在运维人员因为故障而打开它的那一刻，什么都告诉不了他们。一个失败的依赖项会被指名，但不会被解释，这与 `/readyz` 的做法一致——连接错误会携带 DSN、端点地址和存储桶名称，而原因应当留在运维人员本就必须查看的日志里。

### M4. 跨 Space 审计与 Space 元数据——已完成

带有 `AuditFilter` 的 `SearchAuditEvents`、`GET /api/admin/audit-events`，以及两条 Space 元数据路由。现有的 Space 路由保持不动，这是刻意为之：一个 Space 所有者问的是一个更窄的问题，把那个更宽泛的方法交给这类读取方，正是一条 Space 范围的路由悄悄获得部署范围答案的方式。

验收已达成。有两个细节值得记录：

- **`space_id=none` 是一个过滤取值。** 一个空的 `space_id` 早已表示“任意 Space”，因此那些不属于任何 Space、任何 Space 范围的读取方都永远看不到的事件——登录、授权、账户操作——需要有自己专属的表达方式来请求。
- **`AuditFilter` 没有全文搜索字段，也不应该有。** 这条轨迹记录的是谁对哪个对象做了什么；一个文本查询会诱使系统对一个整个存在意义就是保持精简、结构化的字段做 `Detail LIKE` 扫描。

`AdminSpace` 不携带任何由成员撰写或由 Agent 产出的字段。这道边界所承受的压力是真实存在的，而且会以一个听起来很合理的请求的形式出现——先是一个 Issue 数量，然后是一份列表，再然后是标题——因此这项测试会断言响应内容完全不提及任何 Issue、Conversation、Artifact、Task、Workflow 或轨迹。

### M5. Portal `/admin` — 已完成

初始 Portal 切片已实现，并扩展到 §10 的八个区块，包括一级导航、授权管理、
分页、账户 Session 控制及脱敏配置。旧的五页面计划已不能描述当前 Portal。

验收已满足：管理员能看到该区域；非管理员看不到入口，并被送回首页而非禁止
页面；Server 无论如何都会拒绝未授权请求。

有三点值得记录：

- **每个页面都说明自己不展示什么。** Space 页面会说明这里展示的是成员和容量，不是具体工作内容；账户详情页会说明 Space 只按名称和角色列出。这不是装饰性文字——一个假设情况并非如此的运维人员，迟早会把这道边界本身误报成一个缺失的功能。
- **没有从一个 Space 指向其内容的链接。** 一个点了会返回 403 的链接，读起来像是一个 bug，而不是一道边界，所以这个页面不会提供这样的链接。
- **破坏性操作会先说明自己将要做什么，再执行。** 禁用操作会指名它将停用哪些凭据，说明会话将被撤销、排队中的工作不会启动，并说明这不是删除。一个登录验证码会说明它只显示一次，之后任何地方都无法找回。事后才发现这些，正是运维人员开始不信任这个界面的原因。

浏览器覆盖位于 `portal/e2e/admin.spec.ts`；测试账户需要持有授权，
`./make e2e` 会在签发登录码时一并授予。

### M6. 模型目录读取与开关 — 已完成

`GET /api/admin/llm/models` 与启用／禁用路由复用 `model_admin.go` 已写入的
审计 action。模型创建后来也通过 Admin API、Portal 和
`buildmax admin model add` 实现；数据库直连命令保留用于引导。

验收已达成：可以从 Portal 下线一个模型，目录响应中不包含任何密钥，而轨迹除了操作者之外无法区分一次 CLI 切换和一次 API 切换——命令记录的是二进制程序的名字，路由记录的是一个人的名字。

草案里没有的一项新增内容是：**响应会说明哪个模型名称是这套部署的默认模型**。目录中每一个启用的条目都可以被这套部署的每一个用户调用，它的唯一名称就是面向客户端的稳定标识符；别名层和按 Space 划分的模型策略已经被[《客户端模式》](客户端模式.md)撤回。

配额档位分配，如果确实需要，会在 M6 之后落地，拥有自己的存储方法和自己的审计动作。它是 §7.1 中唯一一项属于“新功能”而非“对现有状态开一扇窗”的内容，而目前还没有人提出这个需求。

## 14. 前端计划

1. **门禁与外壳。** `getAdminMe`、`admin` 路由段，以及一个只在请求成功时才渲染的导航入口。403 是一种预期之内的回答，而不是一个错误提示——这与 `features/audit/api.ts` 早已记录的约定一致。
2. **概览。** 来自 `GET /api/admin/system` 的状态卡片，一次失败的就绪检查会被指名但不加解释，与 `/readyz` 的做法一致，原因也相同。
3. **账户。** 一份可搜索的列表、一个详情面板，以及在禁用和撤销会话时弹出的确认对话框，说明这会对会话和待处理运行产生什么影响。一个登录验证码只显示一次，而且这一点会在生成之前而不是之后就说明清楚。
4. **Space。** 元数据表格，附带 §10 中的范围说明。
5. **审计。** 跨 Space 轨迹，复用 `features/audit/describe.ts`——它本就会把无法识别的动作原样渲染出来，这正是让一个版本落后于服务器的 Portal 不至于隐藏事件的那个特性。
6. **模型。** 目录表格，支持启用/禁用与模型创建表单。此前仅限 CLI 添加的限制，已被 Admin API 中加密的只写凭据处理方式取代。
7. **LLM 调用。** 基于 `GET /api/admin/llm/calls` 的可过滤列表，像 Space 范围的运行视图那样按每行自己的费率快照计价，并展示该视图隐藏的路由信息（`target_id`、`provider_type`、`upstream_model`）——因为这里的读者正是设定这套路由的运维人员。

## 15. 验证

后端：

```sh
./make test ./internal/server/handlers/... ./internal/service/audit ./internal/bootstrap
./make test mysql
```

前端：

```sh
cd portal && npm run build && npm test
```

完整：

```sh
./make check ci
```

人工验证场景，每一条都对应本文档中的一项主张：

1. 针对一个空部署，从命令行完成授权、列出授权、撤销授权。
2. 一个获得授权的用户能进入 `/admin`；一个没有授权的 Space 所有者不能。
3. 一名系统管理员在没有成员身份的情况下调用某个 Space 的内容路由会被拒绝。
4. 撤销一份授权会在下一次请求时立刻结束该管理员的访问权限，而不是等到令牌过期。
5. API 拒绝撤销最后一份授权；命令允许这样做，并会说明这一点。
6. 禁用一个账户：一个正在进行中的请求会失败，刷新会失败，密码登录会返回 `account_disabled`，一个 webhook 密钥会被拒绝，Schedule 以 `creator_disabled` 暂停，待处理和正在运行的运行以 `cancel_reason = creator_disabled` 结束为 `CANCELED`。
7. 以上每一步都会以正确的操作者身份出现在跨 Space 审计轨迹中。
8. `buildmax-server user create` 现在会以一个系统操作者的身份出现在轨迹中。
9. 任何管理员响应都不包含 API key、哈希值或令牌。

## 16. 风险

- **这份授权变成了一条捷径。** 一旦某个 handler 的授权逻辑变得难写，总会有人想直接在某个 Space 检查内部去查询这份授权。§11 第 4 项就是那个会因此失败的测试，它的注释应当继续解释清楚原因。
- **管理 API 逐渐膨胀成一个基础设施控制台。** 提案中“非目标”部分说得没错：BuildMax 应当上报自己的状态，而不是变成 `kubectl` 的替代品。每一次新增内容都应当对照 §2 的问题清单来检验。
- **元数据逐渐向内容蔓延。** “只是 Issue 标题而已”这句话，从一个角度看是元数据，从另一个角度看就是内容。这里的判定规则是：只要是某个 Space 成员写的，或者是某个 Agent 产出的，它就是内容。
- **通过一个配置项来完成启动引导。** 这个方案还会被再次提出，因为它在一份 Helm chart 里确实很方便。§6 已经给出了答案，而它的代价是一个审计轨迹无法描述的第二个权限来源。
- **一次授权只有尽力而为的审计写入保证。** 这是本设计中最薄弱的一点（§9）。这个薄弱点是继承来的，而不是本设计引入的：尽力而为这项策略本身已经定案，真正应当被重新提出讨论的，是 Space 治理问题 2 遗留下来的那部分——一次授权是否应当获得一次事务性保证的记录。
- **禁用不等于删除。** 这里的任何操作都不会删除一个账户或它的数据，一个把“禁用”理解为“移除”的运维人员会判断错误。删除属于 Space 治理问题 10 的范畴，而那个问题今天还没有答案。

## 17. 未决问题

1. `system_observer` 角色是否会有真正的调用方？这个字段本身已经存在（§5.1）；但在有人真正需要“只给某人状态和审计权限、不给账户控制权”之前，这个角色不应该被创建出来。
2. ~~`disabled_at` 是否也应当阻止一个个人 Space 中现有的 Task 运行被*同一 Space 的其他成员*重新触发？~~ **已决定：不需要。** 这个 Space 拥有这份工作成果，而权限跟随每次运行的发起者（§8.2）。禁用一个账户，收回的是这个账户请求工作的能力；它不会把一个其余成员状态正常的 Space 的积压工作也一并隔离起来。资格检查依据的是这次运行自身的 `created_by`，因此由另一个人重新发起的运行，是一次由未被禁用的操作者发起的新运行，可以正常派发。真正尚未解决的问题在更下一层，而且是一个 Space 模型层面的问题，而不是一个管理层面的问题：没有任何机制阻止一个所有者把成员添加进一个*个人* Space，而这正是这种情形之所以可能出现的唯一原因。
3. 管理 API 在其他事项之前，是否首先需要限流？今天登录本身就是不限流的（[部署——认证](../deploy/authentication.md)），而通过 `GET /api/admin/users?q=` 进行账户枚举，比那个问题要小得多——但这毕竟是一个带搜索参数的新界面。
4. 对于一个没有数据库的部署，管理员会看到什么？按设计，每一个存储都可以为 nil，相应路由会返回 503；至于 Portal 在这种状态下是否应该干脆不展示这个区域，尚无定论。
5. 等到 OIDC 落地之后，一份授权应当跟随账户，还是跟随身份？如果一个 IdP 的 subject 被重新关联到一条新的用户记录上，一份没有跟着走的授权会造成锁定，而一份跟着走的授权则是一次没有任何人批准过的权限转移。
6. ~~一次因禁用而停止的运行，是否应当与一次真正失败的运行区分开来？~~ **已决定：是。** 权限被收回的运行以 `CANCELED` 结束，并带有 `task_run.cancel_reason`（`creator_disabled` 或 `creator_not_member`），一经记录不可更改，且区别于 `user_requested`（§8.1）。
7. ~~一个账户的 webhook 密钥是否应当在禁用后继续存活？~~ **已决定：由运维人员选择。** 暂停使用时保留它们——禁用期间被拒绝，重新启用后可用；带 `retire_webhook_keys` 的离职禁用会永久撤销它们（§8.1）。
8. ~~模型别名是否应当可以通过 API 编辑？~~ **已撤销。**[客户端模式](客户端模式.md)移除了别名层：客户端直接指名部署范围内唯一的目录条目，而管理端的响应会指名当前配置的默认值。
9. 取消时限——worker 的取消轮询加上陈旧运行的取消宽限期——对第一个具名企业部署是否可以接受？还是运行器必须在一个更短的紧急时限之后删除或终止 worker？
10. 仅限所有者均已禁用时的恢复（§8.4）是否足够，还是部署必须要求在离职前存在第二位 Space 所有者？
11. 目标部署是否需要受管的 CLI 与 Desktop SSO？那会把原生会话和本地凭据清理加入离职流程。
12. 在观测到多大基数时，资格对账器需要一个持久工作队列，而不是对活跃运行做有界扫描？
13. `buildmax admin` 是否应当与 Portal 和 Admin API 对齐？它没有会话列表或单会话撤销命令，没有停用影响或 webhook 密钥退役选项，也没有所有者恢复；§6.1 没有给出把这些排除在自动化界面之外的理由。
14. Portal 的审计搜索与导出缺少 API 已有的 `since` 和 `until` 范围。增加它们只需要一个真正需要的调用方。
15. Portal 的插件发布已按决定推迟：`buildmax plugin publish` 仍是 release 发布界面，Portal 负责查看、归档、恢复和撤回。只有当没有代码检出的运维人员需要发布时才重新讨论。
16. 哪些运行时汇总对运维人员可操作、又不泄露 Space 内容——按状态和时长统计的 TaskRun、最久待处理时长、取消请求与陈旧运行候选、worker 心跳新鲜度、接近配额上限的 Space？任何此类视图都必须从持久状态或共享协调器获得部署范围的语义，绝不能来自单个进程的内存；按安全的错误类别而不是原始错误文本分组；并且在全局派发暂停、强制取消和跨 Space 重试各自获得独立的权限与多实例一致性决策及审计动作之前，不包含它们。
17. 哪些会话元数据有用，又不会变成设备指纹界面？平台和时间戳已经存在；IP 地址和 user agent 并未记录。
18. 权限变更是否应当获得事务性审计？`internal/service/systemadmin` 在存储调用提交之后才记录授权与撤销审计，因此一次已提交的变更并不保证有对应的审计记录（§9、§16）。验收需要在审计存储失败时回滚或给出明确报告的结果，并在 MySQL 上证明。
