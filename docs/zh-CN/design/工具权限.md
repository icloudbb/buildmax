## 1. 目的

BuildMax 目前只在两种情况下会在工具调用前询问用户：路径看起来敏感，或者 shell 命令看起来有风险。除此之外的一切都会不动声色地执行——覆盖一个源文件的 `Write`、一次 `Edit`，或者对一个用户一个月前配置、此后再也没想起过的第三方服务器发起的 `CallMcpTool`。

这并不是一个经过深思熟虑的立场，而是一个被设计出来却一直空置的权限层自然而然的结果。`llm.PolicyProvider`——用来回答“这个工具默认应该怎么处理”的接口——**在整个仓库里没有被任何一个工具实现过**。它上面那层可配置的覆盖 `ToolPolicy` 也只是个空壳：`interactivePolicy.Check` 和 `nonInteractivePolicy.Check` 都无条件返回 `ToolActionAllow`（`internal/agentapp/policy.go:12`、`:21`）。在 `resolveAction`（`internal/core/agent/agent.go:489`）遍历的五层里，有两层完全不起作用，还有一层实际回答的问题和它的名字暗示的完全不是一回事。

本记录要填补的正是这个空缺的层。它决定：

- 每个内置工具默认应该怎么处理，以及为什么这个答案应该被推导出来，而不是手工指定；
- 一个 MCP 工具该如何分类——在这种场景下唯一可用的信号，来自被分类的那个服务器自己给出的提示；
- 一个完全没有人参与的界面，遇到 `Ask` 该怎么办——这个问题决定了这套设计到底能不能落地，还是会成为一个破坏 worker 的回归；
- 用户或运维人员分别能在哪里覆盖以上这些默认值，以及双方各自如何看到当前实际生效的是什么。

本记录还定义了 `Access`——这是一种效果分类，[parallel-tool-execution.md](./并行工具执行.md) 会用它来判断哪些调用可以并发执行。那篇记录写得更早，一度自己承载了这个分类；但它本质上属于这里，权限才是它的第一个使用方。

## 2. 现状基线

**解析顺序确实存在，但大半是空的。** `resolveAction` 加上 `applyPolicyAndExecute` 会依次走过五层：

| # | 层 | 由谁实现 | 今天实际决定了什么 |
|---|---|---|---|
| 1 | `ToolPolicy.Check` | `interactivePolicy`、`nonInteractivePolicy` | 什么都没决定——两者都返回 `Allow` |
| 2 | `ArgChecker.CheckArgs` | `Read`、`Write`、`Edit`、`Grep`、`Bash` | 敏感性与命令风险 |
| 3 | `PolicyProvider.DefaultAction` | **无人实现** | — |
| 4 | `PreToolUse` hook | `HookManager` | 有效；是用户自己编写的关卡 |
| 5 | 默认值 | — | `Allow` |

**第 2 层回答的其实是另一个问题，而不是权限默认值。** `ReadFile.CheckArgs` 和 `WriteFile.CheckArgs` 逐字节完全相同（`internal/tool/read_file.go:57`、`internal/tool/write_file.go:51`）——对敏感路径都返回 `Ask`，否则都返回 `Allow`。它们判断的轴是*敏感性*，不是*效果*。读取 `~/.ssh/id_rsa` 会触发询问，写入 `main.go` 却不会。

**`Ask` 只有一种含义，但在一半的界面上它其实等同于 `Deny`。** 交互式界面会传入一个 `ApprovalHandler`（`internal/interface/cli/tui.go:27`、`internal/interface/desktop/app.go:163`）。打印模式、worker（`internal/agentapp/taskrun/runtime.go:332`）、评估流程以及 Portal 的对话运行时都不会传入，而当 `opts.Approval == nil` 时，`applyPolicyAndExecute` 会把 `Ask` 坍缩成 `Deny`（`agent.go:426`）。

**MCP 这一侧完全没有把守,而它唯一可用的信号也被丢弃了。** LLM 通过 `CallMcpTool(server, tool_name, arguments)` 访问 MCP，而这个工具没有实现任何一个可选接口——所以每一次 MCP 调用都是 `Allow`。与此同时，`serverState.toolsByName` 保存着 `map[string]*mcpsdk.Tool`（`internal/infra/mcp/registry.go:27`），而 `mcpsdk.Tool.Annotations` 携带着每次连接时从 `tools/list` 取回的 `ReadOnlyHint`。注册表只读取了这个结构体上的 `.Description` 和 `.InputSchema`，把 `.Annotations` 丢在一边。数据其实早就取回来放在内存里了，只是没有任何代码去读它。

**在一个地方，隔离已经在替代提示了。** 当沙箱以 `auto_allow` 模式启用、并且确实能够包容住这条命令时，`Bash.CheckArgs` 会把一个高风险命令的 `Ask` 降级为 `Allow`（`internal/tool/bash.go:107`）。本设计要做的，是把这个原则一般化，而不是扩大它的适用范围（§5.7）。

**存在一份运维人员专用文件，但恰恰在最需要它的界面上，它是失效的。** `config.PolicyFile` 读取 `<BUILDMAX_HOME>/policy.yaml`，其文档注释把这个文件保留给“后续阶段其他由运维人员控制的子系统”使用（`internal/config/sandbox.go:104`）。它存在的目的是一道文件系统层面的权限边界，而不是一层配置——用一份单独的文件，才能表达“用户可以读取这些键，但不能编辑它们”，这也是 `manual/sandbox.md` 把它描述为“当机器的所有者和机器的使用者不是同一个人时，请使用 policy 文件”的原因。

这个定位本身完全正确，但也正因如此，这份文件无法服务于本设计。在本地 CLI 上，所有者和使用者是同一个人：他们既能编辑 `settings.yaml`，也能编辑 `policy.yaml`，第二份文件因此毫无用处。而在 worker 上——所有者和使用者真正不同的那个界面——`BUILDMAX_HOME` 是 `RuntimeTaskRunGlobalDir`，这是一个每次运行都由 `ensureRunDirs` 用 `os.MkdirAll` 全新创建的目录（`internal/agentapp/taskrun/runtime.go:222`、`:227`、`:324`）。没有任何机制会把 `policy.yaml` 放进这个目录——Space 的文件被物化进的是 `runHome`，不是 `runGlobal`——所以 `LoadPolicySandbox` 在这里读到的永远是一份空配置。

也就是说，这份文件只在不需要它的那个界面上有效。本设计不会依赖它（§5.6），而现有的沙箱策略层也存在同样的局限——见 §10。

**`ResolveSandbox` 的分层方式依然值得照搬。** 先是界面默认值，再是 settings，并配一份用于展示的 `Sources` 列表（`internal/config/sandbox.go:170`）。本记录沿用这种分层方式，只是去掉了那一层不起作用的部分。

## 3. 缺口

### 3.1 声明层是空的

没有任何工具声明过自己是什么。`PolicyProvider` 没有任何实现，因此运行时无法区分一次文件读取和一次文件写入，五层解析中的第 3 层因此成了死代码。

### 3.2 写入操作是静默的

`Write`、`Edit` 以及所有 MCP 调用都会不经提示地直接执行，除非路径恰好触发了敏感性检查。对一个受信任的本地工作区来说，这本身是一个说得通的默认值；问题在于，这根本不是一个*默认值*，而是一种*缺失*。

### 3.3 MCP 因为无人过问而被默认信任

一个第三方服务器得到的执行待遇，和一次内置文件读取一模一样,同样不动声色，而本来能让运行时区分两者的 `readOnlyHint`，早已被 SDK 解析出来又立刻丢弃了。

### 3.4 加上任何默认值都会破坏每一个 worker

这正是决定整个设计走向的那个缺口。今天 worker 之所以能写文件，是因为 `WriteFile.CheckArgs` 返回的是 `Allow`。一旦给 `Write` 加上一个 `Ask` 的类别默认值，在 worker 上——没有 `ApprovalHandler`——它就会被解析成 `Deny`。任务运行将彻底无法再写入任何文件。

反过来修也更糟。如果让自主执行界面把 `Ask` 一律解析成 `Allow`，那也会连带把 `Bash.CheckArgs` 产生的那种*基于风险*的 `Ask` 一起放行，于是 worker 会开始执行它今天明确拒绝的那些高风险命令。用一个单一的标量来回答“这里的 `Ask` 到底是什么意思”，无法同时服务这两种场景。

### 3.5 用户无从覆盖，运维人员的覆盖也够不到

用户没有办法说“别再问我关于 `Write` 的事了”——`ToolPolicy` 本该是承载这句话的那一层，却只是个空壳。运维人员同样没有办法说“worker 上禁止一切 MCP 调用”，而根据 §2，那份看起来应该能承载这条指令的文件，压根就到不了 worker 那里。用户这一侧的缺口可以在本文档里补上；运维人员这一侧的缺口补不上，§7 会明说这一点，而不是交付一个看似存在、实则悄无声息就是不起作用的开关。

### 3.6 没有人能看到当前到底生效的是什么

`/tools` 只列出名称和描述（`internal/interface/cli/chat_tools.go`）。没有任何地方能像 `buildmax sandbox status` 展示已解析的沙箱配置那样，展示每个工具已解析出的动作。

## 4. 方向

- **P1——声明的是效果，推导出来的才是权限。** 一个工具声明的是它*做什么*。运行时决定的是*要不要问*。一个可以自行指定 `Allow` 的工具，迟早会这么做，到那时这个分类就不再有任何意义。
- **P2——`Ask` 意味着“去问一个人”，类别层这一档只在真的有人可问时才存在。** 一个完全没有人参与的界面根本不会产生类别提示——见 §5.3。基于风险的 `Ask` 依然维持今天坍缩成 `Deny` 的行为。
- **P3——不允许出现静默的行为回归。** 每一个内置工具在每一个界面上最终的行为都在 §6 中被明确写出，并有测试覆盖。已交付的默认值只改变交互式界面；自主执行界面必须逐字节保持不变。
- **P4——MCP 默认不受信任。** `readOnlyHint` 只用来影响提示的默认走向，它从不授予任何权限。只有运维人员或用户的白名单才能授予权限。
- **P5——只有在隔离确实起到了包容作用时，隔离才可以替代提示。** 把 `Bash` 自动放行背后的原则一般化；不要凭猜测就扩大它的适用范围。
- **P6——覆盖必须落在真正能生效的地方。** 面向用户的是 `settings.yaml`，再加一条能打印出已解析结果表及其来源的命令。运维人员对自主执行界面的控制，是由服务器下发、按 Space 限定范围的，这属于 P4 的工作，而不是一份本地文件——见 §7。

## 5. 范围内

### 5.1 `Access`：这个分类本身

有两个问题决定了一次调用是什么样的，而它们并不是同一个问题：

1. **这次调用会改变用户拥有的任何东西吗？** 这个问题驱动的是权限。
2. **`Execute` 是否是 goroutine 安全的？** 这个问题驱动的是调度，其答案并不能从第一个问题推出来。

`Access` 回答的是第一个问题。它和 `ArgChecker`、`PolicyProvider` 一起定义在 `internal/core/llm/tool.go` 中：

```go
// Access describes what a tool call does to the world. The zero value is
// AccessWrite, so a tool that declares nothing — or one that returns a value
// this runtime does not recognise — is treated conservatively.
type Access uint8

const (
    // AccessWrite: the call changes durable or process state.
    AccessWrite Access = iota
    // AccessReadOnly: the call observes and returns. It writes no file, no
    // session state, and no unsynchronised process state.
    AccessReadOnly
)

// AccessDeclarer is implemented by tools that classify their own calls.
// Arguments are passed, as with ArgChecker, so the answer can depend on the
// call: a read-only shell command is a different act from a destructive one.
type AccessDeclarer interface {
    Tool
    Access(args map[string]any) Access
}
```

一个没有声明的工具，其 `Access` 就是 `AccessWrite`。这个分类落地不需要改动任何一个现有工具。

### 5.2 推导默认值，以及两个证明它需要被覆盖的工具

推导出来的默认规则只有一行：**只读 → `Allow`，写入 → `Ask`。**

根据 P1，这个默认值是推导出来的，而不是声明出来的——一个可以自己指定动作的工具，迟早会给自己指定 `Allow`，到那时这个分类就会退化成一种形式主义。

但单纯依靠推导，对两个工具来说是错的，而这两个例外值得专门写出来，因为它们最清楚地证明了权限和调度其实是建立在同一个事实之上的两种不同映射：

| 工具 | `Access` | 正确的权限 | 正确的调度 |
|---|---|---|---|
| `TodoWrite` | 写入 | `Allow` | 不具备并发资格 |
| `NoteWrite` | 写入 | `Allow` | 不具备并发资格 |

两者都会通过 `NoteStoreFromContext` 修改 `Session`，而 `Session.SetNotes` 没有加锁（`internal/core/session/session.go:139`）——所以它们确实是在写进程状态，也确实不能并发执行。但它们写的是 Agent 自己的暂存状态，而不是用户拥有的任何东西。要求用户批准 Agent 给自己写一条待办事项，是荒谬的。

于是，推导出来的规则成了*兜底方案*，而 `PolicyProvider.DefaultAction`——这个接口自被写下以来就一直空着——则成了*覆盖方案*。`TodoWrite` 和 `NoteWrite` 是它最早的两个实现，也是它之所以存在的理由。

解析顺序变成了：

| # | 层 | 变化 |
|---|---|---|
| 1 | 配置出来的**拒绝**——一种一票否决的禁令 | 现在真正生效了（§5.6） |
| 2 | `ArgChecker.CheckArgs`——参数级别的风险判断 | 不变 |
| 3 | 配置出来的**允许/询问**——用户的类别偏好 | 现在真正生效了 |
| 4 | `PolicyProvider.DefaultAction`——工具明确声明的默认值 | 现在真正实现了 |
| 5 | **由 `Access` 推导得出** | **新增** |
| 6 | `PreToolUse` hook，之后是默认的 `Allow` | 不变 |

`ToolPolicy` 被拆分到第 1 层和第 3 层，而不是整个盖在最上面，这个拆分正是关键所在。`Read: allow` 的意思是“别再为读取操作问我了”，它绝不能同时意味着“不用告诉我就能打开 `~/.ssh/id_rsa`”。只有配置出来的 `deny` 能压过风险检查；配置出来的偏好则位于工具自身默认值之上，因为用户的权威高于工具作者。

**`ToolPolicy.Check` 返回的是 `(action, bool)`。** `ToolActionAllow` 的含义是*在其他每一层都弃权*，所以一个返回它的策略永远无法表达“允许这个，别再问了”——而这恰恰是配置一条策略的唯一意义所在。那个布尔值携带的信息是：这条策略到底有没有给出意见。这与 §5.4 中 MCP 遇到的陷阱如出一辙，只是发生在了第二个地方。

### 5.3 界面基线

只有第 4 层——仅此一层——的启用与否，取决于这个界面上是否有一个人在场：

```go
// interactive reports whether a human can answer a permission prompt.
func (o RunLoopOpts) interactive() bool { return o.Approval != nil }
```

这个设计最初的形式是一个名为 `PermissionSurface` 的字段，仿照 `config.SandboxSurface` 贯穿五个 `RunLoop` 调用点。实现过程证明这个形状是错的：审批处理器是否存在，本身*就已经是*那个事实。交互式界面会设置它，自主执行界面不会，而 `applyPolicyAndExecute` 一直以来判断“一个 `Ask` 是否能被回答”所依据的，就是这同一个 nil 检查。再加一个平行的字段，只会为同一个事实制造出第二个来源，而它能新增出来的那些状态本身就是自相矛盾的——比如一个自称是交互式界面、却根本没有任何办法弹出提示的界面。推导出来的答案不会出现漂移。

在一个自主执行界面上，推导出来的类别型 `Ask` 根本不会被产生出来。它既不是“被解析为允许”，也不是“被解析为拒绝”——它压根就不存在，因为没有任何人可以被它告知。第 1 到第 3 层依然照常运行，所以 `Bash.CheckArgs` 产生的那种基于风险的 `Ask`，依然会像今天一样坍缩成 `Deny`。

这正是让 §3.4 变得可以解决的关键，同时它回答的是问题本身的形状，而不只是表面症状：一次类别提示是*与一个人的对话*，而你没有办法用一个默认值来代替一场对话。想限制 worker 的运维人员，应该使用第 1 层——那里的决定是明确的、可审计的，而不是靠一个标量悄悄地重新解释系统里的每一个 `Ask`。

### 5.4 MCP

`CallMcpTool` **同时**实现了两个可选接口，而且两个都需要。更早的一版草案只使用了 `ArgChecker`；实现过程证明这样做不出 §6 那一行所要求的结果。

```go
func (t *callMCPToolTool) Access(args map[string]any) llm.Access {
    if t.readOnly(args) { return llm.AccessReadOnly }
    return llm.AccessWrite
}

func (t *callMCPToolTool) CheckArgs(args map[string]any) llm.ToolAction {
    if t.readOnly(args) { return llm.ToolActionAllow }
    return llm.ToolActionAsk
}
```

两者覆盖的是不同的两半，因为第 2 层的 `Allow` 意味着*弃权*，而不是*许可*：

| 调用 | 第 2 层 | 第 4 层 | 结果 |
|---|---|---|---|
| 只读，任意界面 | 弃权 | `AccessReadOnly` → 不询问 | 允许 |
| 写入，交互式界面 | `Ask` | 不会触发 | 提示 |
| 写入，自主执行界面 | `Ask` | 被关闭 | 拒绝（没有处理器） |

如果只有 `CheckArgs`，一次只读调用会在第 2 层弃权，随后又会在第 4 层被询问，因为 `Access` 默认就是写入。如果只有 `Access`，一次写入在自主执行界面上永远不会被拒绝，因为第 4 层在那里根本不运行。`Registry.ToolIsReadOnly` 读取的是注册表本来就持有、此前却被丢弃的那个注释；`LoadMcpTools` 会据此声明 `AccessReadOnly`。

**`AccessReadOnly` 无法蕴含并发安全。** 正是在这里，这一点变得清晰起来：`CallMcpTool` 报告的“只读”，靠的是第三方自己的一面之词，本运行时无法为其背书。接口文档现在已经说明了这一点，调度器必须把并发安全当作一个独立的条件单独要求——参见 [parallel-tool-execution.md](./并行工具执行.md) §5.1。

关于这个提示，有三条约束：

**缺失和 `false` 是无法区分的。** 在 go-sdk v1.7.0 中，`ToolAnnotations.ReadOnlyHint` 是一个 `bool`，而不是 `*bool`，所以一个省略了这个注释的服务器，解码出来的结果和一个明确写了 `false` 的服务器完全一样。两者都会落到 `Ask`。这是安全的那个方向，其代价是：一个行为良好、只是恰好省略了这个提示的只读服务器，也会触发提示。真正的出路是 §5.6 的白名单，而不是放宽默认值。

**这个提示只是服务器对自己的一面之词。** 它只影响提示的默认走向，不授予任何权限（P4）。一个撒谎的服务器，会在一次实际写入的调用上得到 `Allow`——这正是为什么真正的信任机制是白名单，而不是这个提示本身。

本记录最初还设想过一行审批提示文案，把这个声明明确归因到服务器身上（例如“server github reports: not read-only”）。**这部分没有实现。** 它需要一条专门从工具传到提示界面、只为承载这一行文字的通道，而提示界面本来就已经从参数里显示了 `server` 和 `tool_name`。它想回答的问题——“为什么会问我这个”——正是 `buildmax tools status`（§5.6）已经能直接回答的问题。如果以后用户提出需求，可以再重新考虑。

**以上这一切都不会改变自主执行界面的行为。** 根据 §5.3，推导出的这一档在那里根本不会运行；`CheckArgs` 对一次非只读的 MCP 调用返回 `Ask`，最终会坍缩成 `Deny`——相比今天一律 `Allow` 的做法，这是一次*收紧*。这是本设计中唯一一处会改变自主执行行为的地方，而且它是朝着更安全的方向改变的，§6 会明确写出这一点，而不是让它变成一个意外的惊喜。

### 5.5 会话级授权

一个无法被记住的提示，迟早会被用户关掉。审批提示因此新增了三种结果：

| 选择 | 按键 | 效果 |
|---|---|---|
| 允许一次 | `y` | 仅限本次调用 |
| 本会话内允许 | `a` | 授权会在下方定义的范围内保存在内存中 |
| 拒绝 | `n` / `Esc` | 与今天的拒绝行为一致 |

授权保存在一个 `SessionGrants` 存储中，从不落盘，并随进程一起消亡。把“始终允许”持久化下来，意味着代替用户写入 `settings.yaml`，这是有意排除在本文档范围之外的（§7）——内存级别的这一档，是让这个功能真正可用的原因；持久化的那一档，则会让它变得危险。

**在解析完成之后才会被查询，而不是在第 1 层之前。** 一次授权只是对一个此前已经问过用户的问题的缓存答案，而一次 `Deny` 从来就不曾成为一个问题。如果在解析之前就应用授权，会让一次批准绕过策略检查或敏感性检查，所以它只对 `Ask` 生效：

```go
action := resolveAction(...)
if action == llm.ToolActionAsk && opts.Grants.granted(scope) {
    action = llm.ToolActionAllow
}
```

**授权的范围以工具名为基础，工具在派发调用时可以进一步收窄它。** 工具名就是提示界面向用户展示过的东西，因此也是用户心目中自己批准了的对象。`llm.GrantScoper` 让一个会触达别处的工具可以自行声明这一点——`CallMcpTool` 返回的是 `server/tool_name`，否则为一次会话批准一次 MCP 调用，就会连带批准每一个已配置服务器上的每一个工具；`BrowserNavigate` 返回的是 URL 的来源，否则一次批准就会准入模型之后提到的每一个站点。审批提示会显示这个目标，让用户看到"本会话允许"覆盖的是什么。

更早的一版草案曾经把授权的键设为循环保护机制 `toolFingerprint` 的一个前缀。这个方案被放弃了：一个由参数派生出来的键，在提示界面上是不透明的，用户根本看不出自己批准的是什么，而且任何前缀的截取方式都是武断的。为本会话批准 `Write`，不应该要求用户为每一条路径重新批准一遍——这正是按名称限定范围的授权所能提供的效果。

**授权按会话保存，而不是按运行保存。** `AgentApp.grantsFor(sessionID)` 拥有这些存储。Desktop 在每条消息上都会重建自己的 `SessionContext`，所以如果把授权保存在那个包装对象上，它活不过被授予时的那一轮对话。

### 5.6 配置与可见性

只有一个来源，在 `settings.yaml` 中：

```yaml
tools:
  permissions:
    Write: allow                    # allow | ask | deny
    CallMcpTool: ask
    "CallMcpTool:github/*": allow   # server/tool qualifier
```

`config.ResolvePermissions` 依次叠加界面默认值和 settings，并返回一份 `Sources` 列表——这与 `ResolveSandbox`（`internal/config/sandbox.go:170`）的形状相同，只是去掉了 policy 那一层，理由见 §2。

这里不会有 `policy.yaml` 区块。加上一个，只会把一个面向运维人员的开关，放进一个 worker 永远不会读取的文件里，这比干脆不提供还要糟糕：运维人员写下规则，状态命令确认它确实存在,而 worker 却对它视而不见。运维人员对自主执行界面的控制应该落在哪里，见 §7。

可见性方面，仿照 `buildmax sandbox status`：

```text
$ buildmax tools status
TOOL          ACCESS      ACTION  SOURCE
Read          read-only   allow   derived
Write         write       allow   settings
Bash          write       ask     derived
CallMcpTool   write       ask     derived
  github/*    read-only   allow   settings
```

同样这一列已解析出的结果，也会被加进 `/tools` 面板，它今天只显示名称和描述。

### 5.7 与沙箱的交界处

`Bash` 的自动放行（`internal/tool/bash.go:107`）是 P5 现存的一个实例：当操作系统边界已经包容住了这条命令时，提示不会再增加任何额外保障，因此它会被降级。这个行为原样保留。

它被特意**不**扩展到 `Write` 和 `Edit`。沙箱存在的目的，是包容住工作区*之外*的写入；而工作区*内部*的写入，恰恰是它本来就允许的。一种根本没有包容住当前这个行为的隔离，是不能替代对这个行为的询问的。

Worker 在哪种边界内运行由 [sandbox-boundaries.md](./沙箱边界.md) 规定；Agent 与 Space 如何选择层级由 [agent-sandbox-policy.md](./Agent沙箱策略.md) 规定。本记录只是假定某种边界已经生效，并在这道边界之前拦截调用。

## 6. 最终行为

这是对 P3 的证明。列出每一个内置工具在两种界面上、改动前后的行为。

| 工具 | `Access` | 交互式界面（改动前） | 交互式界面（改动后） | 自主执行界面（改动前） | 自主执行界面（改动后） |
|---|---|---|---|---|---|
| `Read` | 只读 | 允许（敏感时询问） | 不变 | 允许（敏感时拒绝） | 不变 |
| `Glob` | 只读 | 允许 | 不变 | 允许 | 不变 |
| `Grep` | 只读 | 允许（敏感时询问） | 不变 | 允许（敏感时拒绝） | 不变 |
| `Skill` | 只读 | 允许 | 不变 | 允许 | 不变 |
| `WebFetch` | 只读 | 允许 | 不变 | 允许 | 不变 |
| `Write` | 写入 | 允许（敏感时询问） | **询问** | 允许（敏感时拒绝） | 不变 |
| `Edit` | 写入 | 允许（敏感时询问） | **询问** | 允许（敏感时拒绝） | 不变 |
| `Bash` | 写入 | 有风险则询问，灾难性则拒绝 | 不变¹ | 有风险则拒绝 | 不变 |
| `TodoWrite` | 写入 | 允许 | 不变（§5.2 的覆盖） | 允许 | 不变 |
| `NoteWrite` | 写入 | 允许 | 不变（§5.2 的覆盖） | 允许 | 不变 |
| `Task` | 按 Agent 类型为写入或只读² | 允许 | 除非 Agent 类型只读，否则**询问** | 允许 | 不变 |
| `LoadMcpTools` | 只读 | 允许 | 不变 | 允许 | 不变 |
| `CallMcpTool` | 写入 | 允许 | 除非有 `readOnlyHint`，否则**询问** | 允许 | 除非有 `readOnlyHint`，否则**拒绝** |

新增四处交互式提示，收紧一处自主执行行为，其余全部不变。

² `Task` 过去在这里是固定的写入类型。现在它按每次调用分别作答，遵循 [parallel-tool-execution.md](./并行工具执行.md) §5.7.1 的做法——那份记录需要知道一次委托出去的运行是否会写入：一个 `subagent_type`，如果它整套工具集都声明为 `AccessReadOnly`——内置的 `explore`，或者一个以同样方式被限制的用户自定义 Agent——就是只读的，推导出的这一档随后就会允许它。这两个消费方在这一点上是一致的，不像在 `TodoWrite` 上那样各说各话：一个只读子 Agent 只能触达那些本来就不会主动弹出提示的工具，而它自己的嵌套循环没有携带 `ApprovalHandler`，所以其中出现的敏感路径会被拒绝，而不是被询问。批准这样一次委托，等同于批准一系列读取操作。委托给 `general`、`shell`，或任何能触达至少一个写入工具的类型，依然会触发提示。

¹ `Bash` 之所以保持不动，唯一的原因是它自己声明了 `PolicyProvider.DefaultAction() = Allow`。实现过程表明，如果不这样做，推导出的这一档会叠加在它自己的风险分类器之上，导致每一次 `ls` 和 `git status` 都会触发提示——这是让人们最快把权限提示直接关掉的办法。推导出的这一档，是为那些自己没有判断力的工具准备的兜底方案；`Bash` 自己就有判断力，而且判断得更精准。

在自主执行界面上，`CallMcpTool` 是唯一一行会在没有人做出决定的情况下发生改变的行为。这一点在这里被明确写出，也会在变更日志中被专门指出。它同时也是最需要运维人员覆盖能力的一行——但根据 §7，这个界面上目前还不存在这样的覆盖通道，所以任何依赖非只读 MCP 调用的任务运行部署，都必须等到 P4 建立起服务器下发通道之后，再通过那条通道表达这个需求。在此之前，停留在拒绝上是当下唯一安全的选择。

## 7. 不在范围内

- **持久化的“始终允许”授权。** 这意味着代替用户写入 `settings.yaml`；内存级别的这一档先行交付，用来观察用户实际会授予什么样的权限。
- **改变 `Bash` 的风险分类逻辑。** `isRiskyBashCommand` 和 `isCatastrophicBash` 保持现有行为，继续作为 shell 命令的权威判断依据。
- **运维人员对自主执行界面的控制。** 本文档有意不解决这个问题，也不打算用一份本地文件来解决它。worker 的 `BUILDMAX_HOME` 每次运行都会全新创建（§2），因此唯一能够到达它的通道，就是它本来就在用的、承载模型策略和运行令牌的那条通道：由服务器下发，按 Space 限定范围。这属于 [space-governance.md](./Space治理.md) 的 P4 工作，而本记录的 §5.1–§5.4 正是它的前置条件——服务器得先有东西可以下发，才谈得上下发。在此之前，自主执行界面只会运行 §6 中推导出的默认值，不接受任何覆盖。
- **一个权限模式的总开关**（例如“接受所有编辑”“绕过一切”）。在 `settings.yaml` 中把每个工具都设为 `allow` 就能达到同样的效果；一个专门命名的模式只是语法糖，可以等有证据表明用户确实需要之后再做。
- **把“拒绝”做成面向用户的一等功能。** 配置语法里保留 `deny`，是因为运维人员需要它；一个面向用户的“阻止这个工具”交互，不在本设计的范围内。

## 8. 实施步骤

### 阶段 1——分类与推导

- 新增 `llm.Access` 和 `llm.AccessDeclarer`；按 §6 为每一个内置工具实现 `Access`。
- 为 `TodoWrite` 和 `NoteWrite` 实现 `PolicyProvider.DefaultAction`。
- 把第 4 层加进 `resolveAction`，以 `RunLoopOpts.interactive()` 作为门控条件。
- 导出 `ResolveToolAction` 和 `DeclaredAccess`——第 4 阶段的状态命令，以及 parallel-tool-execution.md 里的调度器，都需要和这个循环本身算出来的一样的答案，两者都不应该各自重新推导一遍。
- §6 的表格变成一个表驱动测试，再加一个断言：每一个自主执行动作都与改动之前的解析结果完全一致。这是整个阶段的验收关卡。

### 阶段 2——会话级授权

- `SessionGrants` 存储、TUI 和 Desktop 中三种结果的提示、第 1 层对它的查询。
- 没有这一步，阶段 1 对任何要编辑文件的人来说都是可用性上的一次倒退。这两个阶段可以一起上线；阶段 1 绝不能单独上线。

### 阶段 3——MCP

- `Registry.ToolIsReadOnly` 读取内存中早已存在的注释。
- `CallMcpTool.CheckArgs`；`LoadMcpTools` 声明 `AccessReadOnly`。
- 提示文案要把“只读”这个说法明确归因到服务器自己身上。

### 阶段 4——配置与可见性

- `settings.yaml` 中的 `tools.permissions`；`config.ResolvePermissions` 依次叠加界面默认值和 settings，并带上 `Sources`。
- `buildmax tools status`；在 `/tools` 面板中加入已解析动作这一列。

### 阶段 5——文档

- `manual/`——一篇任务导向的页面，说明哪些操作会触发提示，以及如何关闭它。
- `docs/reference/configuration.md`——补充 `tools.permissions`。
- `docs/contribute/architecture/tools.md`——补充 `Access`，以及一个工具作者需要声明什么。
- `docs/design/sandbox-boundaries.md`——加上到 §5.7 的交叉引用。
- `CHANGELOG.md` 的 `## [Unreleased]` 下面，追加在该小节末尾，明确点名 `CallMcpTool` 在自主执行界面上的这次收紧。

## 9. 验收

- §6 的表格作为一个跨两种界面的表驱动测试，能够通过。
- 一次 worker 任务运行，在没有 `ApprovalHandler` 的情况下写文件、编辑文件、执行非高风险的 shell 命令——改动前和改动后的转录记录完全一致。
- 一条高风险 shell 命令在 worker 上依然被拒绝。
- 一次对声明了 `readOnlyHint: true` 的服务器的 MCP 调用，无需提示直接执行；同一个服务器上非只读的工具，在交互式界面上会触发提示,在 worker 上则被拒绝。
- 一次对 `Write` 的会话级授权，在本次运行后续的调用中依然有效，但不会延续到下一次运行。
- `settings.yaml` 中的 `tools.permissions` 能够覆盖推导出的默认值，且 `buildmax tools status` 能为每一行标明它的来源。
- `PreToolUse` 依然能拦截一次此前每一层都放行了的调用。

## 10. 开放问题

- **现有的沙箱策略层存在完全相同的缺陷。** §2 已经指出 `<BUILDMAX_HOME>/policy.yaml` 在 worker 上是不可达的，而 `LoadPolicySandbox` 同样受此影响：[sandbox-boundaries.md](./沙箱边界.md) §4.1 和 `manual/sandbox.md` 里记录的那种运维人员锁定，只在本地 CLI 上有效,而在本地 CLI 上所有者和使用者恰恰是同一个人。这是已交付行为中的一个缺陷，不属于本设计要解决的问题，它需要一个自己的修复方案——要么把这份文件也物化进 `runGlobal`，要么把沙箱策略也挪到 §7 所说的那条由服务器下发的通道上。之所以在这里提出来，是因为本次调查发现了它；跟踪修复它是另一项独立的工作。
- **合适的授权粒度应该是什么？** 按整个工具授权太粗（相当于为整个会话允许在任何地方 `Write`），按精确参数授权又太细（每条路径都要重新批准一次）。§5.5 提出的方案是工具名加上指纹的一个稳定前缀；这个前缀具体怎么截取，需要对照真实的转录记录来选定。
- **`Task` 值得拥有一个专属的类别提示吗？** §6 对能够写入的类型给出的答案是肯定的——一个被委托出去的子 Agent 会运行数量不受限制的工具调用，而它自身的关卡就是同一道关卡,所以批准父级调用，本质上是在批准一整条策略，而不是一次具体的动作。只读类型被豁免（脚注 2），这回答了这个问题里关于噪音的那一半，也是模型最常发起的那种委托。仍然开放的是：剩下需要提示的那部分，是否应该携带 Agent 类型信息——它目前没有自己的 `GrantScope`，所以为本会话批准一次 `shell` 委托，也会连带批准之后每一次 `general` 委托。
- **敏感性检查是否应该并入 `Access`？** 两者最终都会走到 `Ask`，让它们保持分离的正是分层本身。等第 4 层真正落地之后，这个问题值得重新审视；但*不*应该在同一次改动里顺手解决它。
