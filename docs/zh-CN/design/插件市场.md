## 1. 决策

BuildMax 把插件当作可复用目录，主要包含可在 `.buildmax/` 下运行的能力。
实验性的本地 `connector.yaml` 是一个有边界的例外：它为 CLI 声明固定的应用
操作，尚无 worker 凭证或按次运行授权契约。见[委托提案](../proposals/agent-app-delegation.md)。

插件目录直接包含受支持的内容，**不会**再嵌套一层 `.buildmax/` 目录：

```text
code-review/
├── plugin.yaml
├── README.md
├── skills/
├── agents/
├── mcp.json
├── connector.yaml
├── hooks.yaml
└── hooks/
```

已安装的插件直接位于：

```text
<BUILDMAX_HOME>/plugins/<plugin-name>/
```

默认位置是 `~/.buildmax/plugins/<plugin-name>/`。遵循 `BUILDMAX_HOME`，
可以让测试、worker 和隔离安装都不去触碰贡献者真实的主目录。

BuildMax 会在同一套目录格式之上支持两种分发模式：

1. 直接把一个 Git 仓库克隆进插件目录；
2. 发布到该部署私有的插件市场、由用户显式下载的不可变版本。

这两种模式共享验证、发现、运行时解析和诊断逻辑。它们在更新与信任语义上
则刻意保持不同：仓库是开发者自己控制的工作树；市场发布是由管理员发布、以
版本号和摘要标识的 Artifact。

## 2. 为什么需要两种分发模式

这两种模式服务的是同一个生命周期里的不同阶段，而不是在互相竞争谁才是
唯一的安装方式。

| 关注点 | 仓库克隆 | 私有市场 |
|---|---|---|
| 适用场景 | 只有你自己依赖这份副本 | 还有别人依赖这份副本 |
| 建立方式 | 在插件目录下执行 `git clone` | 浏览目录，点击/运行安装 |
| 迭代方式 | 原地编辑、原地测试 | 发布一个新的不可变版本 |
| 更新方式 | 显式的 Git 操作 | 显式的市场更新 |
| 身份标识 | 插件名加仓库 URL | 目录 ID 加插件名 |
| 可复现性 | 提交哈希加工作树脏状态 | 发布版本号加 SHA-256 摘要 |
| 治理方式 | 仓库访问权限与代码评审 | 一个可供日后引用的稳定身份，加一个撤回开关 |
| 所需凭证 | 用户自己的 Git/SSH 凭证 | 已有的 BuildMax 登录 |
| 是否需要 BuildMax Server | 否 | 发布和安装时都需要 |
| 运行期是否依赖 Server | 克隆之后不需要 | 下载之后不需要 |
| 未来能否供 worker 使用 | 作为可变来源不合适 | 适合作为一个已固定版本的 Artifact |

### 2.1 为什么值得支持仓库克隆

如果要求作者每改一次就得打包、上传、发布、再下载一遍，插件开发的节奏会
被不必要地拖慢。开发者应当能够直接执行：

```bash
git clone git@code.example.com:agents/code-review.git \
  ~/.buildmax/plugins/code-review
```

然后在运行时下一次启动时被 BuildMax 发现。这个仓库可能处于某个分支上，
可能是一个游离的提交，也可能是本地脏状态。这种可变性在开发阶段是有用的，
应当被清晰地展示出来，而不是被禁止。

BuildMax 不会自动去拉取一个仓库。分支、凭证、合并冲突和脏工作树，这些
Git 本来就已经管好了；在一个更新器里重新实现这些规则只会很脆弱。未来的
`buildmax plugin clone` 命令或许能提供一层便利包装，但直接 `git clone`
依然是一条受支持的路径，而且不应该要求存在一份 BuildMax 生成的锁定记录。

### 2.2 为什么市场仍然要打包字节

市场不应该靠把发布者的仓库克隆到每个成员的机器上来完成安装。那样做会：

- 要求每个使用者都持有 Git 主机的凭证；
- 从使用者的视角看，一个分支或标签会变成可变的；
- 把“能否安装”这件事和 Git 服务器是否可用绑在一起；
- 让管理员审核过的字节，日后很难被指认出来；
- 让撤回、审计和确定性回滚都变得含糊不清。

因此，市场存储的是从同一个插件根目录打包出来的归档文件。一个已发布的
版本是不可变的，由 `(plugin, version, digest)` 这三元组标识。用户需要
执行一次显式的下载/安装动作；仅仅“发布”这个动作本身，永远不会改变任何人
本地的能力。

### 2.3 一份副本该属于哪种模式

把这两种模式简单描述成“开发环境”和“生产环境”很有诱惑力，但这是错误的
切分方式，这么说也会让这个设计声称一些并不成立的事情。

真正决定该用哪种模式的问题是：**还有没有别人依赖这份副本**。一个人在自己
机器上维护、只有自己使用的插件，永远保持克隆状态是完全合理的——对这个人
来说，这就是生产环境，把它推进管理员的发布流水线，不会给任何人带来任何
好处。而一个被三个 Space 在日常工作中使用的插件，哪怕它每周都还在变化，
也早就需要一个稳定的身份和一个撤回开关了。

由此得出两个结论，二者都不是需要以后修复的缺陷：

- **拥有一次部署，并不是使用插件的前提条件。** 市场归属于某一次 BuildMax
  部署（见 §7.1），从市场安装需要 Server 登录。CLI 可以作为完全不需要
  Server 的单一二进制运行，这是一项产品优先级，而不是一种降级模式。对于
  这种安装形态而言，克隆或手动放置的目录就是唯一的模式，而且是最终形态，
  不是一个过渡阶段。
- **即便一次部署确实拥有市场，也不能假定所有插件都来自市场。** 目前只有
  系统管理员才能发布（见 §7.1），所以一个工程师如果发现自己的插件对
  所在的 Space 确实有用，却没有自助获得稳定身份的途径。这些人中的一部分
  会选择继续维持克隆状态。一个在规模化场景下被悄悄违反的约定，比压根没有
  约定还要糟糕，因为它会造成“来源问题已经解决”的假象。§4.5 给运维者提供了
  一种在真正需要时把这条规则落到实处的办法；开放问题 4 则记录下了造成这种
  压力的权限缺口本身。

### 2.4 唯一的晋升路径

预期的流程是：

```text
Git repository
    ↓ clone and edit in ~/.buildmax/plugins
local validation and testing
    ↓ pack and publish a named version
private Marketplace release
    ↓ explicit user install
managed local copy in ~/.buildmax/plugins
```

仓库安装和市场安装之间不存在任何自动同步。把一种来源类型转换成另一种，
需要一次显式的替换操作，这样 BuildMax 就永远不会覆盖一棵工作树。

## 3. 插件目录契约

### 3.1 支持的内容

插件根目录可提供工作区 `.buildmax/` 内容及实验性的本地连接器：

| 路径 | 含义 |
|---|---|
| `skills/<name>/SKILL.md` | Skill 说明及其附带的资源 |
| `agents/<name>.md` | Subagent 定义 |
| `mcp.json` | MCP server 定义 |
| `hooks.yaml` | Hook 定义 |
| `hooks/` | `hooks.yaml` 所引用的脚本或资源 |
| `connector.yaml` | 固定的本地 OAuth 与 HTTP 操作；不是 worker 授权 |

`README.md` 和 `LICENSE` 可以与运行时内容放在一起。未知的运行时文件会
由验证流程报告出来，而不是被默默当成一种新的插件特性。

一个插件可以只包含其中一部分内容。一个只提供 Skill 的插件是合法的；一个
只提供 MCP 配置、不含任何 Skill 的插件同样合法。

### 3.2 `plugin.yaml`

面向作者的完整字段参考在
[manual/plugins.md](../../../manual/plugins.md)中；下面要说明的是这个
格式为什么止步于此。

这份清单承载的是一个目录自己无法推导出来的身份信息、一条在发布首个版本
之前就值得先讲清楚的兼容性下限，以及插件期望运维者提供的运行环境。至于
一个插件*实际做什么*，仍然完全由其载荷本身推导出来，而不是在这里声明。

```yaml
name: code-review
version: 1.2.0
description: Company code review skills and agents.

display_name: Code Review
homepage: https://code.example.com/agents/code-review
maintainer: Platform Space <platform@example.com>
license: Apache-2.0

min_buildmax_version: 0.9.0

env:
  GITHUB_TOKEN:
    description: Token the github MCP server authenticates with.
  REVIEW_WEBHOOK_URL:
    description: Where the post_tool_use hook posts review results.
    required: false
```

| 字段 | 是否必填 | 含义 |
|---|---|---|
| `name` | 是 | 稳定的本地身份标识，也是默认的目录 slug。要求小写、用连字符分隔。 |
| `version` | 发布时必填 | 下一个发布版本的语义化版本号。在一棵从未发布过的树上，可以不填。 |
| `description` | 否 | 一句话说明插件的用途，也是目录搜索与列表展示所用的文本。 |
| `display_name` | 否 | 供 Desktop 和 Portal 展示的可读标题，默认取 `name`。 |
| `homepage` | 否 | 供用户了解更多信息的地址，只会被展示，不会被抓取。 |
| `maintainer` | 否 | 自由格式的负责人信息——遇到问题该找谁；不是 BuildMax 会去验证的身份。 |
| `license` | 否 | 用于展示的 SPDX 标识符。 |
| `min_buildmax_version` | 否 | 已知该插件能正常工作的最旧 BuildMax 版本。 |
| `env` | 否 | 载荷预期用到的环境变量，按名称建立索引。 |

加载一个目录只要求填写 `name`。其余四个展示类字段都是“惰性”的：运行时
不会读取它们中的任何一个，一个填错的值只会误导阅读者，不会改变任何行为。

#### 版本号属于清单，而不是发布命令

BuildMax 自身的版本号取自 Git tag 而不是某个源文件，因为有一条流水线会
根据这个 tag 构建对应的发布版本。而一个插件是由某个人针对一个目录执行
命令来发布的，这个目录甚至完全可能根本不是一个 Git 仓库，所以同样的规则
在这里会失效：从 tag 推导发布版本需要依赖 Git，这会破坏 `local` 这种
来源类型，也会重新引入 §2.2 已经否决过的那种与 Git 的耦合。

把版本号放进清单里，能让版本升级变成一次 diff 里可评审的一行改动，而不是
藏在某个人 shell 历史记录里的一个命令行参数；这也让“重复发布同一个
`(plugin, version)` 会返回 `409`”这件事，有了一个显而易见的解决办法：
编辑并提交清单。

版本号只是对*下一个*发布版本的声明，从来不是对当前已安装内容的声明：

| 来源类型 | 用什么来标识本地这份副本 |
|---|---|
| `repository` | 提交哈希与脏状态。清单里的版本号只作为*声明值*展示，不代表已安装的身份。 |
| `local` | 目录路径。处理方式相同。 |
| `marketplace` | 发布记录本身：版本号与摘要，二者正是发布那一刻清单所声明的内容。 |

所以，一棵脏工作树即使清单上还写着 `1.2.0`，也没有说谎——状态展示从来不会
声称它*就是* 1.2.0。

#### 只有一个下限，没有约束语法

`min_buildmax_version` 是单个版本号，不是一个范围表达式。真正值得表达的
场景是“这个插件用到了 0.9.0 才新增的某个 Hook 事件”。上限和范围运算符会
需要一整套约束解析器，来服务一个本来就很少见、而且通常只是在猜测一个
尚未发生的未来的场景。

| 情形 | 行为 |
|---|---|
| 客户端版本更旧 | 安装和更新都会拒绝，并给出具体的版本下限。一个已经安装好的副本仍然可以加载，只是带一条警告。 |
| 客户端报告的是 `dev` 或未打 tag 的构建 | 视为满足任何下限；`validate` 会提示这项检查被跳过了。 |
| 字段缺失 | 不做任何约束。 |

“安装时拒绝、加载时只警告”是刻意的设计：安装是用户还能够选择另一个发布
版本的那个时刻，而如果因为一次降级就去阻止开发者已有的克隆继续运行，
造成的破坏反而会比让它继续跑更严重。

这个字段也给了发布版本选择逻辑一些可用的依据。不带 `--version` 的
`buildmax plugin install <name>` 会选择最新的那个满足以下条件的发布：
不是预发布版本、没有被撤回，且客户端满足其 `min_buildmax_version`。
像 `1.3.0-rc.1` 这样的预发布版本可以正常发布，但只能通过精确指定版本号
来访问。

#### 环境变量约定是文档，但会被交叉核对

验证逻辑本来就能推导出一个载荷引用了哪些环境变量的*名字*。它推导不出来的
是这个名字是做什么用的，以及插件在缺少它时会不会降级——而这恰恰是用户在
安装时最常遇到的困惑。`env` 恰好只补上这一块，别的什么都不做：名字、
一段说明文字，以及一个默认值为 `true` 的可选 `required` 标志。

因为一份没人核对的声明迟早会变成虚构的东西，验证器会把它和实际推导出来的
使用情况做比对：

| 情形 | 结果 |
|---|---|
| 已声明且被引用 | 作为该插件的环境变量约定被报告出来 |
| 已声明但从未被引用 | 警告：声明已经过时 |
| 被引用但未声明 | 警告：存在未记录的需求 |
| `required: true` 但在运行时组装时未设置 | 会在状态和诊断信息里报告出来；运行本身照常继续 |
| 某个条目下出现了看起来像值的键 | **错误。** 清单绝不能携带任何密钥 |

“未设置但必填”并不会阻塞一次运行，这与 MCP 和 Hook 现有的降级方式是
一致的：一个起不来的 server，只会报告自己起不来。清单的作用是让失败的
原因在失败发生之前就变得清晰可读，而不是新增一道关卡。

#### 未知字段

解析器会接受未知字段，这样格式才能持续做加法式的演进，`buildmax plugin
validate` 会把它们列出来。如果两个方向都保持沉默，`descripton:` 这样的
拼写错误就会变成一个看不见的隐患；而如果直接报错，又会让每一个旧版客户端
拒绝掉更新的插件。`manifest_version` 是预留字段，不填代表 1。只有在真的
出现不兼容的变化时，才应该要求必填这个字段。

#### 清单依然不会声明的内容

| 未包含的内容 | 原因 |
|---|---|
| 内容清单（`skills: [...]`） | 只是在重复目录本身这个已经存在的事实来源，而且每新增一个文件就会过时一次 |
| 声明式的权限或工具白名单 | 一个插件无法自己给自己授权（见 §8），而且一份声明完全可能与它身边的载荷本身对不上 |
| 对其他插件的依赖关系 | 需要一个解析器、一份锁文件，以及一套处理“菱形冲突”的方案。目前还没有任何一个具体插件需要它 |
| 为贡献出来的名字加一个命名空间或前缀 | 目前 §5 把冲突当作一个硬性错误处理。引入命名空间会改变面向工具的契约，应当等有了证据再做 |
| 可配置的载荷路径（如 `hooks_file:`） | 既有的约定已经能定位每一个受支持的文件 |
| 关键词与分类 | 单次部署的目录规模足够小，`description` 本身就足以承担搜索功能 |

### 3.3 插件相对路径的文件

MCP 和 Hook 配置有时需要引用插件自带的脚本。BuildMax 为此提供了一个
按来源作用域展开的变量：

```text
${BUILDMAX_PLUGIN_ROOT}
```

它会被解析成 `plugin.yaml` 所在的目录。每个插件的 MCP 和 Hook 配置，
都会先用各自的根目录展开，然后才会被合并到一起。这是一个由 BuildMax
提供的值，不是插件能够覆盖的进程环境变量。

Skill 在被调用时本来就会拿到自己所在的目录，不需要新的路径规则。
`WORKSPACE_ROOT` 保持它现有的含义：指的是 Agent 正在操作的工作区，
而不是插件所在的目录。

## 4. 发现与本地状态

### 4.1 目录发现是事实来源

启动时，BuildMax 会扫描以下目录的每一个直接子目录：

```text
<BUILDMAX_HOME>/plugins/
```

一个带有合法 `plugin.yaml` 的目录就是一个插件。这是刻意设计成这样的，
为的就是让一个手动克隆出来的仓库能够直接可用。发现机制不依赖任何由
BuildMax 生成的注册表。

以 `.` 开头的目录被保留给 BuildMax 自己的暂存、缓存和状态使用，不会被
当作插件。

清单里的 `name` 才是插件的身份，而不是它所在的目录名。市场安装总是会
创建 `<BUILDMAX_HOME>/plugins/<name>/`，但 `git clone` 接受一个目标路径
参数，开发者有时会把它克隆到别处。一个目录名与清单不一致的插件仍然会
被加载，只是会报告这个不一致——如果直接拒绝加载，就等于因为一个毫无实际
后果的细节而让一个插件整体失败。而两个目录声称同一个名字，则属于 §4.3
所说的冲突：两者都不会被加载，而且两个目录都会被点名，因为目录的扫描
顺序绝不能悄悄替用户选出一个赢家。

### 4.2 管理器状态只是补充信息

BuildMax 会在以下位置保存一些补充状态：

```text
<BUILDMAX_HOME>/plugins/.state.json
```

其中的条目是按目录名而不是插件名来建立索引的。在一份清单被解析出来
之前，目录名是唯一存在的身份标识；而一份解析失败的清单，恰恰正是“禁用”
标志仍然必须能被读到的那种情况。

它记录的是安装器已知的一些事实，比如：

- 来源类型：`repository`、`marketplace` 或 `local`；
- 仓库 URL，以及最后一次观察到的提交（如果可用）；
- 市场服务器、目录 ID、发布版本号和摘要；
- 该插件是否被禁用；
- 安装与更新的时间戳。

这份状态文件不会列出插件的具体内容，发现机制也不依赖它。一个手动克隆的
仓库，在 BuildMax 检查过它的 `.git` 元数据之前，会先表现为一个“未被
管理的仓库插件”；一个普通目录则会表现为一个“本地插件”。BuildMax 永远
不会把来源相关的元数据写进插件目录本身，因为那样做会弄脏一份 Git 检出。

状态更新使用进程锁和原子替换。如果 `.state.json` 丢失或损坏，合法的
插件目录依然会被加载，只是 BuildMax 会报告说市场来源信息或禁用状态
无法被恢复。

### 4.3 来源替换

同一个插件名不能同时从两个目录或两种来源被激活。具体来说，市场安装会
拒绝覆盖一个已存在的 Git 工作树，用户必须显式地移除、重命名或替换它。

市场更新会先暂存到一个保留的隐藏目录下、经过验证之后，再原子性地与当前
的活跃目录互换。之前那份被管理的副本可以保留在缓存里，用于回滚。仓库
更新则仍然是由用户自己执行的普通 Git 操作。

### 4.4 运行时快照

`agentapp` 在启动时解析出插件配置，并在整个已组装运行时的生命周期内
保留这份快照。一次克隆、拉取、安装、更新、禁用或移除操作，都不会影响
一次正在进行中的运行。CLI 会在它的下一次调用中看到变化；Desktop 则会在
一次被管理的插件操作之后重建自己的运行时。

一个在运行期间被编辑的仓库，仍然可能改动一个该次运行还没有读取过的
文件。因此轨迹会在运行开始时记录仓库的脏状态，UI 也会把仓库类插件描述为
“开发中的来源”，而不是不可变的输入。需要可复现性的作者，应当使用一次
干净的提交，或者一个市场发布版本。

### 4.5 运维者的来源策略

如果一次部署希望做到“这里只运行经过管理员发布的插件”，需要的是一个能被
检查的机制，而不仅仅是一句声明。`<BUILDMAX_HOME>/policy.yaml` 本来就是
现有的、由运维者控制的文件，所以这里只是在一个已经存在的机制上再加一个
配置块：

```yaml
# <BUILDMAX_HOME>/policy.yaml
plugins:
  allowed_sources: [marketplace]
```

不设置这个字段，就意味着任何来源都会被加载，这也是当前的行为。一旦设置
了它，发现阶段就会跳过任何记录来源不在名单内的插件，并且会按名称和来源
逐一报告每一个被跳过的目录，而不是把它悄悄隐藏起来：一个悄无声息就是不
加载的插件，比一个明确拒绝加载的插件更糟糕。

这也是唯一一处 §4.2 里那份补充状态不再是可有可无的地方。来源类型来自
`.state.json`，所以一个没有相应记录——或者记录已损坏——的目录，其来源就是
未知的，而“未知”并不等于 `marketplace`。一旦设置了这条策略，这样的目录
就不会被加载，给出的理由是“无法确认其来源”，而不是“来源不对”。发现机制
在什么都没有被断言的情况下保持失败开放，只有在运维者确实断言了某件事的
情况下才转为失败关闭——这正是这两种立场各自应得的行为方式。

这里有两条如实的限制，二者都源自 §8：

- **这是舰队管理手段，不是安全边界。** `policy.yaml` 存放在用户自己的
  `BUILDMAX_HOME` 里，所以本地用户可以编辑它。在运维者能够控制那台机器的
  场景下——比如一台受管设备、一个统一构建的镜像、一个容器——它是有价值的；
  但对一台未受管的笔记本电脑的使用者来说，它毫无意义，因为对方完全可以
  同样手写出这份配置。
- **它约束的是来源，而不是行为。** 限制来源说的是“这些字节从哪里来”；
  真正约束“这些字节能做什么”的，是工具权限、Hook 关卡和沙箱决策。

`internal/config/permissions.go` 里记录着方向相反但道理相同的先例：一个
针对工具权限的 `policy.yaml` 配置块曾经被指定过，后来又被撤销，原因是
worker 的 `BUILDMAX_HOME` 是每次运行都全新创建的，一份放在长期存活主机上
的运维策略不会自动传达到那里。因此，插件来源策略管的是它实际所在的那个
主目录里的发现行为；而决定一次后台运行能拿到哪些发布版本的，是 Space
激活配置和不可变的运行期固定版本，而不是某个长期存在的 worker 插件目录。

来源分类的逻辑放在发现阶段，而不是放在每一个展示它的界面里各自实现。
如果有记录下来的来源，那就是答案；否则就通过查找是否存在 `.git` 来分类，
这只是一次 stat 调用，而不是去调用 Git 本身——如果去问 Git，它会给出
最近那个外层仓库的答案，这样一来，一个位于某人主目录检出内部的插件目录，
里面的每一个插件看起来都会像是克隆出来的。

一份解析失败的策略文件会被报告出来，且不会应用任何限制。如果因为
`policy.yaml` 里的一个拼写错误就拒绝所有插件，那就是把一次笔误变成了
一次服务中断；扫描结果会说明它到底没能应用什么。

## 5. 运行时解析

插件在不改变现有工具契约的前提下，新增了第三种配置来源。优先级是：

```text
workspace .buildmax  >  user-global configuration  >  plugins
```

具体行为则由各个子系统各自决定：

| 内容 | 解析方式 |
|---|---|
| Skill | 先工作区，再全局，最后是按名字排序的插件；先出现的名字胜出 |
| Subagent | 先工作区，再全局，最后是按名字排序的插件；先出现的名字胜出 |
| MCP server | 插件先合并，再全局，最后工作区；后出现的 server ID 会替换先出现的 |
| Hook | 追加式顺序：全局设置、按名字排序的插件、工作区 |

两个插件贡献了同一个 Skill、Subagent 或 MCP server ID，会被视为一个
错误，并把两个来源都点名。字母顺序的存在是为了让加载和 Hook 派发保持
确定性；它绝不能被用来悄悄解决一次身份冲突。

一份全局或工作区级别的定义，可以有意覆盖一份插件定义。`buildmax plugin
status` 和 Desktop 的诊断界面会把这种情况展示为“被遮蔽”，而不是让这个
插件看起来完全生效。

## 6. 仓库分发

仓库分发靠的是一套约定，而不是一套新的服务器协议：

1. 作者把 `plugin.yaml` 和插件内容放在仓库根目录下。
2. 开发者把这个仓库克隆或检出到插件目录下。
3. `buildmax plugin validate <path>` 会解析每一项贡献的能力，报告冲突
   以及推导出来的影响。
4. BuildMax 在运行时下一次启动时，直接加载这个仓库。

在 Git 元数据可用的情况下，状态会报告：

- 远程 URL；
- 分支或游离状态；
- 完整的提交哈希；
- 是否存在已跟踪或未跟踪的改动。

BuildMax 不要求存在远程仓库，在发现阶段也不会执行拉取，更不会把 Git
凭证发送到任何地方。私有仓库的身份验证，仍然依赖用户自己既有的
Git/SSH 配置。

发现阶段保持离线，会带来一个真实的风险：一份克隆可能永远不会更新，也
没有任何东西会告诉它的所有者它已经落后了。因此 `buildmax plugin status
--fetch` **只有在用户主动要求时**才会去和远程比对，并报告当前检出落后了
多少。这种“显式、按需”的设计，既保持了“发现阶段不联网”这条不变式完好
无损，又让那个真正会咬到长期存活克隆的失败模式变得可见。

仓库分发拥有的是仓库来源信息，而不是市场发布来源信息。这只是“事后能
指认出什么”上的差异，而不是审查质量上的差异：一次对某个受分支保护的
内部仓库的克隆，其审查来源可能比一个管理员从自己笔记本电脑上传的目录
还要更可靠。市场真正新增的，是一个能在事件发生之后依然存活的身份——一个
几个月后仍然有人能够指认出来的版本号和摘要——以及一个撤回开关。§7.2
让这两种来源信息始终附着在一起，而不是让发布这个动作把第一种来源信息
丢掉。

## 7. 私有市场分发

### 7.1 范围与角色

市场归属于这次部署本身，而不是某个 Space：

| 操作 | 权限归属 |
|---|---|
| 浏览、检查、下载 | 任何一个处于激活状态的已认证用户 |
| 创建或编辑一个目录条目 | 系统管理员 |
| 发布或撤回一个版本 | 系统管理员 |
| 归档一个插件 | 系统管理员 |
| 在本地安装或更新 | 控制着那个 `BUILDMAX_HOME` 的用户 |

这样一来，系统管理员就能管理公司级别的能力，而不需要被授予对 Space 内
提示词、文件、Artifact 或轨迹的访问权限。按 Space 划分目录可见性的做法
暂缓引入，等到有证据表明一个部署级统一目录范围太宽之后再说。

发布权限是一个与目录可见性完全不同、而且更迫切的问题。在“只有管理员能
发布”的前提下，“某台机器上的一份克隆”和“面向全公司的一次发布”之间，
没有任何自助式的路径可走，所以一个对某个 Space 有用的插件，无处可以
获得一个稳定的身份。开放问题 4 承载着这个问题；§2.3 解释了为什么放着
它不管是有代价的。

### 7.2 打包与发布

发布动作以一个插件目录作为输入。版本号来自这个目录自己的 `plugin.yaml`
（见 §3.2），所以不存在单独的版本参数：

```bash
buildmax plugin publish ./code-review
```

客户端会验证并打包这个目录。当这个目录是一个 Git 检出时，客户端还会
把它的远程地址、提交哈希和脏状态，随归档文件一起发送过去。服务器会
独立地完成以下步骤：

1. 验证系统管理员的身份；
2. 一边计算 SHA-256，一边以有界的方式流式接收归档文件；
3. 验证路径、`plugin.yaml`，以及每一种受支持载荷各自的解析器；
4. 拒绝没有 `version` 字段、或版本号不是合法语义化版本的清单；
5. 推导出一份经过脱敏处理的能力报告；
6. 存储不可变的字节内容；
7. 创建发布记录和审计事件，记录下这次发布的 `min_buildmax_version`
   （供版本选择使用），以及客户端所报告的来源信息。

服务器读取的版本号来自打包后的清单本身，而不是信任客户端单独提供的
字段，这样发布记录和实际字节内容就不可能出现分歧。

来源信息正是让 §2.4 那条晋升路径不至于在最后一步崩掉的关键。如果没有
它，一次发布看起来就只是某人笔记本电脑上突然冒出来的一个目录，没有任何
东西能把“被评审过的那个提交”和“大家实际下载到的字节”联系起来。发布一次
脏检出，或者发布一个压根不是仓库的目录，仍然是被允许的，只是会被如实
记录和展示出来——一个由人工拼装而不是由提交生成的插件载荷，是一个合法
的场景，目录应该把这一点说清楚，而不是直接拒绝它。和版本号、摘要不同，
这份来源信息是客户端自己报告的，服务器无法验证；它展示出来的只是一种
关于字节从何而来的声明，而不是证明。

首次发布会创建对应的目录条目，其展示名称和描述取自清单本身。如果要求
必须先单独创建条目，会让上面这一条命令在第一次使用时就失败，而实际权限
其实完全一样：无论走哪条路径，都只有系统管理员能够到达。这次创建动作
会被记录为它自己的一条审计事件，这样一个意外产生的名字也是可见的，而
不需要靠推断。`POST /api/admin/plugins` 仍然是用来预先占用一个名字、或者
在不发布的情况下编辑元数据的方式。

重复发布同一个 `(plugin, version)`，即使字节内容完全相同，也会返回
`409`。要做修正，需要一个新的版本号，这意味着需要编辑并提交清单——这个
版本升级动作因此是可评审的，而不是随手敲进 shell 里的一次性操作。

### 7.3 安装与更新

一个成员会显式地安装某个发布版本：

```bash
buildmax plugin install code-review
buildmax plugin install code-review --version 1.2.0
```

安装过程会：

1. 使用面向所选服务器的现有 BuildMax 登录状态；
2. 选定一个发布版本——可以是精确的 `--version`，也可以是满足以下条件里
   最新的一个：不是预发布版本、没有被撤回，且客户端满足其
   `min_buildmax_version`；
3. 展示版本号、发布者、摘要、推导出的能力，以及任何声明过、但当前尚未
   设置的环境变量；
4. 下载到一个预留的暂存目录；
5. 在解压之前先校验 SHA-256 摘要；
6. 再次验证解压后的目录；
7. 原子性地把它放到
   `<BUILDMAX_HOME>/plugins/code-review/`；
8. 把市场来源信息记录进 `.state.json`。

如果客户端版本太旧，无法满足一个精确指定的 `--version`，安装会被拒绝并
给出具体的版本下限，而不是悄悄装上。

发布这个动作不会主动推送给客户端。更新是显式触发的，而且会在替换之前
展示新旧两份能力报告的对比。第一个版本里没有自动更新机制。

### 7.4 撤回与归档

- 撤回一个发布版本，会让它退出默认的安装与更新候选范围。已经下载好的
  副本会继续照常工作。要按精确版本恢复它，需要显式确认“我知道这个版本
  已被撤回”。
- 归档一个插件，会让它从默认目录里隐藏，并阻止发布新版本。它不会远程
  删除任何本地副本。
- 已发布的字节内容永远不会被原地替换。产品 API 不对外暴露任何硬删除
  操作，因为一个发布版本可能仍然是解释某次过去的安装或运行的唯一凭据。

### 7.5 存储与模型

服务器只需要两个部署范围内的概念：

- `Plugin`：稳定的目录身份、名称、描述以及归档状态；
- `PluginRelease`：所属插件、版本号、`min_buildmax_version`、摘要、
  对象存储键、大小、发布者、发布时间、经过脱敏的检查结果、客户端报告的
  来源信息，以及可选的撤回状态。

包字节存放在一个范围很窄的插件包存储接口之后，具备本地文件系统和
S3 兼容两种实现。它们不是 Task 的 Artifact，也不会继承 Space Artifact
的授权规则或保留策略。

具体实现使用单数形式的数据库表名和新的带前缀公开 ID，并会在同一次改动
里同步更新数据模型和 ID 相关的引用文档。具体的行结构和 API 请求形状，
属于实现阶段该做的事，不在这份最初的设计范围之内。

### 7.6 API 形状

预期的接口面很小：

```text
GET  /api/plugins                                            shipped
GET  /api/plugins/{plugin_name}                              shipped
GET  /api/plugins/{plugin_name}/releases/{version}/download  shipped

GET  /api/admin/plugins                                      shipped
POST /api/admin/plugins                                      shipped
GET  /api/admin/plugins/{plugin_name}/releases               shipped
POST /api/admin/plugins/{plugin_name}/releases               shipped
PUT  /api/admin/plugins/{plugin_name}/releases/{version}/state shipped
PUT  /api/admin/plugins/{plugin_name}/state                  shipped
```

以上两部分都已经交付。`internal/server/handlers/routes.go` 和
`internal/server/handlers/admin` 现在就是它们的事实来源。实现过程中
新增了两条路由：一条管理员专用的列表接口，因为如果对退休某个条目的人
都看不到它，就没有办法恢复它；另一条是与之对应的“取消归档”接口，沿用的
是模型相关路由早就在用的“启用/禁用”成对模式。

发布动作把归档文件作为请求体本身发送，而不是塞进某个文档里的一个字段，
这样字节就能直接从连接流向磁盘，中间不会有任何解码器把它们暂存起来。
发布者关于这次检出的说明，则通过 `source_remote`、`source_commit`、
`source_branch` 和 `source_dirty` 这几个查询参数传递，这样请求体就能
始终保持单一用途。下载接口也会以同样的方式做流式传输。

拒绝响应会区分“请求本身有问题”和“时机不对”：一个这次部署无法加载的包
返回 `400`；一次超出大小上限的上传返回 `413`；而一个已经发布过的版本，
或者一个已经退休的条目，返回的是 `409`——因为同样的请求如果早一点发出，
本来是会成功的，所以这次请求本身并没有任何格式上的问题。

浏览和下载只需要一个处于激活状态的账号，不需要更多权限。一个发布版本
在被人主动安装之前不会改变任何东西，所以读取目录不是一个需要特殊授权的
动作；而向目录发布内容则需要，这一半权限归系统管理员所有。

该安装哪个发布版本，由客户端自己决定，因为只有客户端知道自己的版本号。
详情接口会返回包括已撤回版本在内的每一个发布版本，并做好标记，下载接口
则要求精确指定其中一个。下载一个已撤回的版本会返回 `409`,除非请求里
带上 `allow_yanked=true`:撤回是一种“默认选择时排除”的控制手段，而不是
删除，如果直接拒绝下载，就会堵死 §7.4 本来允许的那条恢复路径。响应会在
`X-Buildmax-Digest` 里携带摘要值，这样客户端不需要发起第二个请求，就能
验证自己收到的内容。

审计轨迹会记录目录创建、元数据变更、发布版本的发布、撤回和归档这些
事件。它记录的是操作者、操作对象、版本号和摘要前缀，绝不记录包内容或
配置值本身。在第一个切片里，下载动作只是普通的已认证读取，不算作治理
事件。

## 8. 信任与能力检查

这两种来源模式都可能带来主动的行为：

- Skill 和 Subagent 是可能引发工具调用的指令；
- 基于 stdio 的 MCP 会启动一个进程，其中可能携带凭证；
- 基于 HTTP 的 MCP 和 Hook 都可能触达网络上的目标地址；
- command 类型的 Hook 会执行本地程序。

同一个验证器会检查这两种模式，并报告：

- Skill、Subagent 和 MCP 的名称；
- MCP 的传输方式、可执行文件名，以及 HTTP 主机；
- Hook 的事件、类型、可执行文件名，以及 HTTP 主机；
- 被引用到的环境变量名，以及它们与清单里 `env` 声明的对比结果；
- 通过 `BUILDMAX_PLUGIN_ROOT` 引用的本地文件路径；
- 冲突与被遮蔽的定义；
- 未知的清单字段。

它不会在目录检查记录里存储命令参数、请求头的值、环境变量的值、提示词
或文件内容。

市场发布这件事本身的含义是“由这位管理员发布”，而不是“安全”。仓库类
插件会带着自己的仓库信息和工作树状态一起被标记出来。现有的工具权限、
Hook 关卡、敏感路径检查、沙箱决策和运维策略，都会继续照常生效；一个
插件不能给自己授权。

包契约禁止嵌入任何凭证。清单里的 `env` 块只允许携带名字和说明文字，
一个看起来像值的条目会被判定为验证错误。验证逻辑还会拒绝明显的私钥
材料，并对可疑的 MCP 环境变量字面值发出警告，但它没有办法证明任意的
指令或文本内容里完全不含密钥。

直接克隆并不会削弱现有的执行边界：一个能够克隆到 `~/.buildmax/plugins`
的本地用户，本来就已经能够自己编写一份 `.buildmax` 配置。真正需要执行期
强制约束的部署，应当使用运维策略，而不是把“来自市场”当作强制约束的替代品。

## 9. 产品使用面

### 9.1 CLI

第一批有用的命令集刻意保持精简：

```text
buildmax plugin validate [path]
buildmax plugin list
buildmax plugin status [name] [--fetch]
buildmax plugin publish <path>
buildmax plugin install <name> [--version <version>]
buildmax plugin update <name>
buildmax plugin disable <name>
buildmax plugin enable <name>
buildmax plugin uninstall <name>
```

直接使用 `git clone` 本来就是仓库工作流的一部分；一个多余的 BuildMax
克隆命令是可选的。`uninstall` 绝不能悄悄删除一棵有脏改动的 Git 工作树。
对于仓库类来源，它会打印出路径，并要求用户自己管理或显式确认删除。

### 9.2 Desktop

Desktop 展示的是某个项目的运行时实际解析出来的结果，而不是插件目录里
放着什么：一个 Skill 如果被工作区覆盖了，那么无论对应的插件是怎么安装
进来的，它都不算是在贡献这个 Skill。安装、更新和移除走的都是与 CLI
相同的机制，而且每一次操作都会重新组装运行时——一个运行时会一直沿用
它启动时拿到的那份配置清单，而 Desktop 正是同一个人同时执行这两类动作
的地方。

它会展示：

- 来源是仓库、本地还是市场，以及运维策略是否限制了其中哪些来源可以加载；
- 提交哈希与脏状态，或者发布版本号与摘要，外加发布时记录下来的来源信息；
- 贡献出的能力，以及所需的环境变量名称；
- 冲突、遮蔽、验证和更新状态；
- 显式的安装、更新、禁用和卸载操作。

### 9.3 Portal

Portal 的系统管理区域负责管理目录条目和发布版本。普通用户可以浏览这个
目录，但 Portal 绝不能声称某个插件已经安装在一台它根本无法检查的本地
机器上。主要的安装入口是 CLI 和 Desktop；从 Portal 直接下载原始归档
文件是可选的能力。

## 10. 来源信息与 worker 使用

每一次运行都会在开始时记录当前生效的插件配置清单。

对于一个仓库类插件：

```text
name, source type, remote URL when present, commit, dirty flag
```

对于一个市场类插件：

```text
name, catalog ID, version, digest, source server
```

这份有界的元数据不包含任何包内容或密钥。Skill 调用、Subagent 启动、
MCP 调用和 Hook 事件，在其解析出的定义确实来自某个插件时，都应当携带
插件的来源信息。

Portal 和 worker 分发只会使用不可变的市场发布版本。服务器会把一个
Agent 命名引用的插件，与该 Space 的激活配置进行匹配解析，并把精确的
发布版本固定记录在 TaskRun 上；worker 只会用自己的运行令牌下载这些
被固定下来的版本，并在运行时组装之前完成物化。它绝不会克隆一个可变的
仓库，也不会拿到开发者的 Git 凭证，更不会在启动一次运行时去解析
“最新版本”是什么。D1 目前只接纳 Skill 和 Subagent。可执行的 Hook/MCP
以及密钥投递，仍然留在后续的
[《Space 插件分发》](./Space插件分发.md)设计里。

## 11. 实现归属

依赖方向保持不变：

- `internal/config` 负责发现插件根目录、解析与来源相关的路径，并合并
  插件配置层；
- `internal/agentapp` 负责为 CLI 和 Desktop 组装解析出的 Skill、
  Subagent、MCP server 和 Hook；
- `internal/core/plugin` 拥有市场领域记录及其存储接口；
- `internal/service/plugin` 拥有发布与目录生命周期管理；
- `internal/infra/db` 持久化目录元数据；
- `internal/infra/objectstore` 存储不可变的包字节；
- `internal/server/handlers` 拥有已认证的目录与管理路由；
- `internal/interface/cli` 和 Desktop 负责对外暴露本地工作流。

`internal/core/agent` 完全不知道插件的存在。它拿到的仍然是和今天一样的、
已经解析好的工具、指令和 Hook。

## 12. 交付阶段

### 阶段 A——目录格式与仓库工作流——已交付

- 根级插件格式与 `plugin.yaml` 清单；
- `<BUILDMAX_HOME>/plugins` 下的发现机制；
- 验证、合并规则、插件相对路径和诊断信息；
- 对直接克隆仓库的支持，包括按需触发的 `status --fetch` 漂移检查；
- 轨迹中的插件来源信息。

验收标准：把一个合法的仓库克隆进一个干净、隔离的插件目录后，其能力
无需复制文件、也无需写入任何生成的注册表，就能被 CLI 和 Desktop 使用。

### 阶段 B——私有市场——已交付

- 目录记录与包对象存储；
- 管理员的发布、撤回和归档流程；
- 已认证的浏览与下载；
- 带摘要校验的显式本地安装/更新；
- 记录在发布版本上的客户端来源信息；
- `policy.yaml` 里的 `allowed_sources` 运维控制项，在第二种来源类型
  出现之前，暂时没有什么可限制的；
- 审计事件与感知来源的本地状态。

验收标准：一位管理员从一个经过测试的仓库发布了一个版本；另一个公司
账号按名字把它装了下来；双方报告的摘要一致。这一点由 `cli` 端到端套件
里的 `TestMarketplacePublishThenInstall` 保证，它驱动的是已发布的二进制
文件，去对接一个与它不共享内存的服务器。执行安装的账号本身没有任何
额外授权，所以 §7.1 里权限划分的真实性得到了测试验证，而不只是假设。

### 阶段 C——产品 UI——已交付

- Portal 的目录管理与浏览界面；
- Desktop 的市场安装与更新；
- 清晰的能力、来源、脏状态与来源信息展示。

验收标准：一个成员无需编辑配置、也无需手动处理归档文件，就能发现并
使用一个市场插件。Portal 的账户区域列出这次部署发布了什么，并给出对应
的命令；Desktop 负责解析某个发布版本，展示它贡献了什么，并完成安装。

Portal 永远不会声称某个插件“已安装”。安装这件事发生在 Agent 实际运行的
地方，而服务器看不到那台机器，如果那里出现一个按钮，就等于在撒一个关于
“它到底跑在哪”的谎——所以 Portal 提供的是一条命令，而 Desktop 提供的是
一个按钮，各自只在自己那一侧能够兑现的边界内做事。

### 阶段 D——Space 与 worker 分发，进行中

这一阶段所需要的后续设计是
[《Space 插件分发》](./Space插件分发.md)。它决定的是 Space 层面的所有权、
谁可以启用可执行的 Hook 或基于 stdio 的 MCP、包如何物化、版本如何固定，
以及可执行内容一旦到达 worker 之后应受到怎样的约束；密钥的作用域则被
放进了它自己的另一份后续记录里。

## 13. 被否决的备选方案

### 只保留市场

这样能得到最干净的治理故事，但会让每一次开发中的编辑都不得不走一遍
发布流水线。这会把作者推回到手工复制目录的老路上，脱离产品本身。而
支持直接克隆仓库，能让创作循环保持直观，日后再把同一份字节推广进市场。

### 只保留 Git

这对开发者来说很惬意，但对广泛的公司级消费来说很糟糕。它要求具备 Git
凭证和相关知识，会暴露可变的引用，也没有中心化的发布、审计或稳定摘要。
它始终只是一种来源模式，不能成为公司统一管理的目录。

### 市场在安装时靠克隆 Git 来支撑

在目录里只存储仓库 URL 和引用，看起来比存储归档文件更便宜，但这会把
可变性、Git 身份验证和可用性问题带进每一次安装当中。被评审过的发布版本
必须就是用户实际下载到的那份字节，所以市场必须存储打包好的内容。

### 版本号只在发布时提供

早期的一份草案曾经让清单里只保留 `name` 和 `description`，版本号则从
`publish --version` 里取，理由是作者不应该在 Git 里迭代时还要去改动
一个字段。但实际上他们本来就不需要这么做：版本号只应该在发布时才升级，
而不是在编辑时升级。

那个命令行参数真正付出的代价，是丢掉了一个事实来源。版本号只存在于
某个人的 shell 历史记录里，导致 `409` 没有一个显而易见的解决办法，
发布记录和打包后的字节可能会出现分歧，而且评审过程里也没有任何东西
能显示出一次发布即将发生。把版本号移进清单，让这次升级变成了 diff 里
的一部分，而 §3.2 也确保它永远不会被误认成已安装的身份标识。

### 复制进全局配置

把 Skill 复制进 `<BUILDMAX_HOME>/skills`，再合并 JSON/YAML，会破坏
所有权信息。更新和卸载将无法区分哪些内容是用户自己写的、哪些来自插件。
让每个插件各自保留一个独立目录，才能让它的来源和生命周期保持可检查。

### 一套通用插件运行时

动态二进制或者一个全新的 SDK，会在 Skill、Subagent、MCP 和 Hook 之外
再创建一套扩展契约，也会扩大执行边界。而把现有行为打包分发，能够在
不付出这个代价的前提下实现复用。

## 14. 验证

在测试证明以下各项之前，本实现都不能算作完成：

- 一个插件根目录不需要内嵌 `.buildmax` 目录；
- 一份只写了 `name` 的清单能够加载，其余字段都是可选的；
- 一个未知的清单字段能够加载，并被 `validate` 报告出来；
- 发布会拒绝一份缺少 `version` 或版本号不合法的清单，且发布记录里的
  版本号来自打包后的清单；
- 一个仓库类或本地插件绝不会把自己声明的版本号报告成已安装的身份；
- 一个比 `min_buildmax_version` 更旧的客户端会在安装时被拒绝、在加载时
  收到警告，而一个 `dev` 构建两种情况都不会被拦下；
- 默认的发布版本选择逻辑会跳过预发布版本、被撤回的版本，以及客户端
  版本太旧无法使用的版本；
- “已声明但未被引用”和“被引用但未声明”这两种环境变量名，各自都会产生
  一条警告，而一个 `env` 条目下出现的值会被判定为错误；
- 一个必填但未设置的环境变量，会以可见的方式降级，而不会阻塞运行；
- 一个手动克隆的合法仓库，即使没有 `.state.json`，也能被发现；
- 一个目录名与清单不一致的插件会被加载，并报告这个不一致；两个目录
  声称同一个名字时，两者都不会被加载；
- 发现阶段绝不会发起网络请求或 Git 抓取，`status` 只有在显式带上
  `--fetch` 时才会触达网络；
- 不设置 `allowed_sources` 会加载所有来源，设置之后会跳过不在名单内的
  来源，并点名每一个被跳过的目录；
- 设置了 `allowed_sources` 之后，一个无法从 `.state.json` 确认来源的
  插件不会被加载，并会说明这属于哪一种情况；
- 发布一次脏检出，或者发布一个根本不是仓库的目录，都能成功，并会被
  相应地标记出来，记录下来的来源信息会以“客户端自称”的方式呈现；
- 仓库的提交哈希和脏状态会出现在状态和轨迹元数据里；
- 市场安装会拒绝覆盖一个 Git 工作树；
- 归档穿越、符号链接、重复路径、文件数量爆炸和解压后体积爆炸这几类
  攻击，在发布和安装时都会被拒绝；
- 一次被篡改或截断的下载会导致摘要校验失败，并且绝不会被安装；
- 一个已发布的版本无法被覆盖；
- 仅仅执行发布这个动作，绝不会改变任何一个已安装插件的状态；
- 工作区和全局定义的解析优先级都在插件定义之前；
- 两个插件的运行时名称发生冲突时会失败，并点名两个来源；
- 全局、插件和工作区三层 Hook 按照文档规定的顺序运行；
- `${BUILDMAX_PLUGIN_ROOT}` 的作用域被限定在发起它的那个插件之内；
- 一个正在运行中的运行时，在被管理的更新发生时依然保留自己解析出的
  那份快照；
- 一个非管理员无法修改目录，而一个管理员也不会因为目录相关路由而
  获得对某个 Space 内容的访问权限；
- 审计和轨迹记录里包含来源信息，但不包含任何配置值或密钥；
- CLI 和 Desktop 通过 `agentapp` 加载的是同一份插件配置清单；
- `git diff --check`、文档链接检查、聚焦的 Go 测试，以及相关的
  CLI/Desktop 端到端套件都能通过。

其中有两项是靠构造方式本身保证成立的，而不是靠某个测试证明的，值得
专门点出来，免得有人把这份清单读成“全部都已经被测试覆盖”。审计或轨迹
记录里没有任何一个字段能够携带配置值——这些数据结构从一开始就是这么
设计的——但没有任何测试对此做出断言；CLI 和 Desktop 之所以加载同一份
配置清单，是因为它们共用 `agentapp`，但也没有任何测试同时从两侧去驱动
验证这一点。

## 15. 开放问题

1. 未来那个便利性的克隆命令，应该去调用系统自带的 Git 二进制，还是
   只验证用户自己克隆好的仓库？
2. 市场应该自动保留上一个本地版本，还是让回滚重新下载一次精确的发布
   版本？
3. Portal 应该暴露原始归档文件下载，还是应该把用户引导去用 CLI/Desktop，
   以保证“已安装”这个状态展示始终真实可信？
4. 发布权限应该继续只限管理员，还是应该存在一种自助式的范围——比如一个
   由用户或 Space 拥有、管理员可以将其“扶正”的目录条目——这样一个被
   某个 Space 依赖的插件，就能在不需要管理员介入的情况下获得一个稳定
   身份？这是一个权限维度上的问题，与 §7.1 暂缓处理的“按 Space 划分
   可见性”问题是两回事，而 §2.3 论证了正是前者在制造对现有约定的压力。
5. 在 §5 已经把冲突当作硬性错误处理的前提下，什么样的证据才足以支撑
   插件之间的依赖关系，或者为贡献出来的名字引入一个声明式的命名空间？
6. `min_buildmax_version` 除了在安装时拒绝、在加载时警告之外，是否
   应该再多约束一些东西——比如，如果某个发布版本的载荷用到了一个比
   声明下限还要新的 Hook 事件，是否应该直接拒绝发布？
7. 受监管的部署，除了 TLS、管理员发布和服务器端计算的摘要之外，是否
   还需要离线签名？
