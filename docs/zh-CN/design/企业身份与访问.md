>
> **受众：** 贡献者、运维人员、产品审阅者与安全审阅者
>
> **状态：** 已于 2026-09-13 接受；2026-10-11 修订，增加通过 Portal 确认的原生 CLI/Desktop 登录（§14）。目前已构建：Phase 1（持久会话与 Portal Cookie 凭据）与 Phase 2（OIDC 登录与关联，指定提供方为 Okta）。Phase 3 资格验证仍待完成；原生登录修订（Phase 4）已决定，尚未构建。
>
> **主要领域：** 信任与安全

本记录取代了已退休的《企业身份与访问》提案。它延续了那份文档的方向与证据——最初在
`cceba61c` 处审查的仓库行为，对照 OpenID Connect Core/Discovery、OAuth 2.0 Security
BCP 以及下文链接的浏览器/原生客户端指南——并记录了接受时作出的三项决策。已交付状态与
当前代码表已于 2026-09-14 对照工作树复核。

1. **原生与 SSO 是一种涌现的、经过验证的姿态，而非一个模式枚举。** 切换由两个正交开关
   `oidc.enabled` 与 `local_login` 决定，而不是一个新的 `auth_mode` 字段。见 §4 与 §11。
2. **SSO 默认即时（just-in-time）预配。** 首次通过验证的登录会自动创建 BuildMax 账户，
   并受一份必须非空的允许邮箱域名列表约束。原生部署保留由运维人员创建的账户。见 §4 与 §5。
3. **当前只有一种外部协议，SAML 作为日后干净的扩展。** 目前只实现 OIDC；今天不存在任何
   SAML 字段、列或配置。扩展路径记录在 §8a，因此日后添加 SAML 是新增而非返工。

2026-10-11 的修订增加了第四项决策：

4. **原生客户端通过 Portal 确认登录。** CLI 与 Desktop 发起一个短期登录请求，本人以其
   账户本来的方式登录 Portal 后在其中确认该请求。这一机制借鉴 RFC 8628 设备授权的形态，
   同时覆盖桌面与无界面主机；不采用回环重定向。见 §14。

§19 中的开放事项是剩余提供方资格验证仍需的各部署输入，而不是关于是否要构建的问题。Git 历史保留了完整的提案。

## 1. 接受背景与证据

本记录为私有 BuildMax 部署定义了最小且自洽的企业登录路径。该方向已被接受，且不会把
SSO 置于私有部署 Beta 关卡之前。Phase 1 与 Phase 2 已实现；Phase 3 资格验证（§17、§20）仍待完成。

本设计建立在三类证据之上：

1. 原始证据在 `cceba61c` 处审查了仓库行为，包括账户与刷新令牌存储、认证服务与处理器、
   中心访问守卫、Space 成员资格与邀请、审计、配置、Portal 登录/会话代码及其测试；实现
   状态与 §3 已于 2026-09-14 对照当前代码树复核。
2. 当前文档与代码表明：OIDC 浏览器流程已经交付、应用自身仍无登录限流器、Space 成员
   资格是资源边界、System Administrator 是独立的部署权限，且本地执行不需要 Server。
3. 协议基线是 OpenID Connect Core 与 Discovery、OAuth 2.0 Security Best Current
   Practice，以及本记录所链接的浏览器/原生客户端指南。

方向已定，Okta 也已被选为目标提供方，但真实提供方测试租户与离职（offboarding）服务级
目标仍是各部署输入，而非实现应当猜测的细节。它们是剩余资格验证的前置条件，列于 §19；
它们不会重新开启是否要构建的问题。原生客户端需求已于 2026-10-11 确定（§14）。

## 2. 核心用户成果

员工应当通过其组织已在运营的身份系统进行认证，只能到达其已存储成员资格所允许的
BuildMax Space，并在其访问权被移除后于既定界限内失去启动或访问工作的能力。运维人员
必须能够区分并恢复身份提供方、BuildMax 账户关联以及 BuildMax 授权中的故障，而无需获得
对 Space 内容的访问权。

因此，接受性问题不是“登录页面是否有一个 SSO 按钮？”，而是：

> 运维人员能否说明：哪个企业身份成为了哪个 BuildMax 账户、它开启了哪个 BuildMax 会话、
> 该账户为何能到达某个 Space、每项权限如何以及何时终止，以及在 IdP 故障期间哪些功能
> 仍可用？

## 3. 已验证的现行约束

以下是当前代码，而非推断出的未来行为：

| 关注点 | 当前事实 | 设计后果 |
|---|---|---|
| 账户身份 | `external_identity` 将唯一的 `(issuer, subject)` 绑定到用户；管理员可在禁用账户后检查或解除关联 | 稳定身份是提供方键对；经验证邮箱只用于首次关联或 JIT 预配 |
| 账户创建 | 原生 `CreateUser` 与 OIDC JIT 预配会原子地创建账户、个人 Space、所有者成员资格，并在适用时创建身份链接 | 两条创建路径保持同一账户不变量 |
| 登录 | `/api/auth/login` 接受密码或运维人员签发的一次性代码；`/api/auth/oidc/*` 实现浏览器 OIDC 流程 | 每种凭证都开启同一 BuildMax 会话与授权平面 |
| 访问令牌 | HMAC JWT 携带 `sub`、`typ`、`sid`、`jti`、`iat` 与 `exp`；配置默认有效期为 15 分钟，守卫会在每次请求检查 `sid` 会话 | 持久会话限定登出与撤销；较短的默认值限定了该检查不可用时的重放窗口 |
| 刷新令牌 | 不透明、经哈希、可轮换的刷新令牌行属于 `auth_session`；不活动过期受会话绝对过期上限约束 | 保留轮换与会话绝对上限 |
| 撤销 | 登出与管理员撤销会停用 `auth_session` 及其刷新令牌行；守卫会在下次请求拒绝绑定到该会话的访问 JWT | 持久会话是撤销权威 |
| 账户禁用 | 每个已认证路由都会重新读取 `user.disabled_at` | 通过 BuildMax 禁用实现的离职在用户 API 边界上即时生效 |
| Portal 存储 | 刷新令牌通过 `Secure`、`HttpOnly`、`SameSite=Strict` Cookie 投递；访问令牌保存在内存中 | 可续期凭据不会暴露给 Portal JavaScript |
| 授权 | 中心守卫从数据库状态推导 Space 角色与 System Administrator 授予 | 在首个切片中忽略 IdP 的角色/组声明 |
| 邀请 | Space 邀请针对一个已经存在的账户 | `existing_only` 入职可在首次 SSO 登录前发出邀请；JIT 用户只有在预配之后才可被邀请 |
| 审计 | 身份链接、JIT 创建与解除链接事件和相应身份变更在同一事务中写入；普通登录及许多其他事件仍是尽力而为 | 身份生命周期有原子记录，但更广泛的审计系统仍不足以支撑合规性声明 |
| 部署 | Portal 与 API 通常共享一个公共源（origin）；由 Server 签名并持有的 OIDC 事务 Cookie 与共享数据库无需进程本地回调亲和性 | 代码已支持多副本行为；部署后的真实提供方资格验证仍待完成 |
| 本地界面 | CLI/TUI 与 Desktop 在没有任何 Server 的情况下本地运行；登录模式是可选的 | 企业 SSO 不得使本地执行依赖于 Server |

IdP 禁用某人这一事件当前对 BuildMax 不可见。仅靠 OIDC 并不提供目录同步或即时取消预配的
通道。任何在没有有界重新认证策略或预配集成的情况下声称“SSO 解决了离职者问题”的设计，
都是在作出协议并不支持的主张。

## 4. 最小设计

已接受的方向是：

1. **每个部署一个原生 OIDC 提供方。** BuildMax Server 是一个机密依赖方（confidential
   relying party），使用带 PKCE 的 Authorization Code Flow。SAML、受信任的代理头以及多个
   同时存在的签发方不在首个实现中；§8a 记录了日后如何在不返工的情况下添加 SAML。
2. **OIDC 只证明认证。** 经过验证的 `(issuer, subject)` 对标识一个外部的人。BuildMax
   仍然拥有账户、会话、System Administrator 授予、Space 成员资格、角色以及每一项资源
   授权决策。
3. **通过经过验证的身份来关联，绝不通过角色声明。** 一条新的 `external_identity` 记录把
   OIDC subject 绑定到一个已存在的 BuildMax 用户。经过验证的邮箱只用于首次关联或可选的
   JIT 创建；后续登录通过 `(issuer, subject)` 解析。
4. **SSO 默认即时预配；原生保留由运维人员创建的账户。** 在 SSO 部署中，对一个未知但属于
   允许域名的邮箱，首次通过验证的登录会自动创建普通账户与个人 Space（`provisioning:
   jit`）。JIT 不授予任何共享 Space 成员资格或系统角色，且空的 `allowed_email_domains`
   列表会拒绝 JIT，而不是表示“所有域名”。运维人员也可以改为设置 `existing_only`，只接受
   其预先创建的账户。原生部署（`oidc.enabled: false`）完全没有外部登录：System
   Administrator 像今天一样创建并分配账户。
5. **签发 BuildMax 凭据，而非 IdP 凭据。** 回调会校验并丢弃提供方令牌，然后开启与其他
   所有登录相同的 BuildMax 会话模型。提供方令牌绝不会到达 Portal、CLI、Desktop、Agent
   输入、日志或轨迹。
6. **把隐含的会话变成真正的权限记录。** `sid` 命名一条 `auth_session` 行，在已认证请求中
   与用户一起检查。因此登出、管理员撤销、绝对过期以及日后的提供方登出都能立即使一个
   已签发的 BuildMax 访问令牌失效。
7. **使用适合浏览器的凭据投递方式。** Portal 在内存中保留一个短期的 BuildMax 访问令牌，
   并把一个可轮换的刷新令牌保存在 Secure、HttpOnly 的 cookie 中。对于 OIDC 与本地回退
   登录，可续期凭据都离开 `localStorage`。
8. **诚实地为仅靠 IdP 的离职设定界限。** OIDC 会话有一个固定的最大存活时间，超过后必须
   再经由提供方返回。推荐的初始值为 12 小时，BuildMax 访问令牌默认为 15 分钟。即时的
   入职/离职（joiner/leaver）自动化需要日后的 SCIM 或提供方特定的生命周期集成。
9. **保留一条有审计的应急（break-glass）路径。** 在 SSO 部署中，本地密码/登录代码认证
   默认仅限 System Administrator。直接操作数据库的 `buildmax-server` 引导命令仍是恢复的
   根基。
10. **用两个正交开关而非一个模式枚举在原生与 SSO 之间切换。** `oidc.enabled` 开启或关闭
    外部登录；`local_login`（`all | system_admins | off`）管理谁仍可使用本地用户名与密码
    平面。部署的姿态是二者经过验证的组合——原生是 `oidc.enabled: false` 配 `local_login:
    all`；SSO 是 `oidc.enabled: true` 配 `local_login: system_admins`——并在管理员状态
    界面上报告。不引入单独的 `auth_mode` 字段：因为应急要求即便在 SSO 下本地登录对管理员
    仍然可用，单一的 native/sso 枚举无法独立存在，还会与 `local_login` 重复。保持这两个轴
    正交，也正是让日后的协议（§8a）成为第三个独立轴、而非一个新枚举值的原因。

本设计有意只引入两个持久概念：`external_identity`，因为签发方身份无法安全地寄存在
`user.email` 上；以及 `auth_session`，因为既有的 `sid` 已经命名了一个会话，而该会话的
撤销与过期在其他方面并不权威。其余一切都复用当前的账户、Space、令牌与审计模型。原生
登录修订（§14）增加了一条短期记录 `native_sign_in`：请求由不同的参与方发起、确认与兑换，
且可能落在不同副本上，因此需要它。请求一经兑换或过期即被删除。

## 5. 身份与账户关联

### 5.1 稳定键

外部身份键是精确的 OIDC `iss` 加 `sub` 对。两者都是区分大小写的协议值。邮箱、姓名、
首选用户名、组以及租户标签都是属性，绝非身份键。

回调在查询账户之前先校验 ID Token。它至少校验签名、精确的签发方、受众、适用时的授权方
（authorized party）、过期时间、签发时间界限、nonce 以及授权事务。首次关联额外要求一个
语法有效的 `email` 且 `email_verified=true`。如果提供方通过 UserInfo 返回邮箱，则
UserInfo 的 `sub` 必须等于 ID Token 的 `sub`。

### 5.2 关联算法

校验之后，一个事务按顺序应用以下规则：

1. 如果 `(issuer, subject)` 已有链接，使用该用户。邮箱变更不能把身份转移到另一个账户。
2. 拒绝其用户已被禁用的链接。启用该用户是运维人员的显式决策。
3. 如果不存在链接，且某个在用用户拥有该已验证邮箱，只有当该用户对此签发方没有身份时才
   进行链接。这是为运维人员创建的账户提供的迁移路径。
4. 如果该邮箱的账户已链接到此签发方的另一个 subject，拒绝并要求运维人员调查。绝不自动
   替换任一链接。
5. 如果不存在账户，`existing_only` 以一条通用的“未被授权访问此部署”响应拒绝。`jit` 则
   原子地创建用户、个人 Space、所有者成员资格与身份链接。
6. 只有在账户/链接事务提交之后，BuildMax 才可创建会话。

签发方是受运维人员信任的，但邮箱匹配仍是一次安全敏感的一次性链接。`jit` 是默认值，因为
被接受的结果是：一次经过验证的企业登录为其自身预配账户；其安全性来自必须非空的
`allowed_email_domains` 列表，而非来自运维人员预先为每个账户命名。空列表会拒绝 JIT，
而不是表示“所有域名”，且域名比较是规范化且精确的，而非字符串后缀检查。`existing_only`
仍可供那些更希望由运维人员为提供方可能主张的每个账户命名的部署使用；它以一条通用的
“未被授权访问此部署”响应拒绝未知邮箱。无论哪种方式，上面的规则 1–4 仍先行适用，因此
JIT 绝不替换或移动既有的 subject 链接。

### 5.3 属性漂移与恢复

`external_identity.last_seen_email` 与可选的显示名快照会在成功登录后更新。首个切片不会
自动改写 `user.email`：它已经是管理与邀请所使用的本地账户句柄，安全地更改它需要冲突与
通知语义。Portal 管理界面应当显示不一致，以便运维人员进行核对。

System Administrator 可以列出某个用户的身份链接。只有在用户被禁用时才允许解除链接，解除
会与删除一起原子地记录，且不会删除用户、成员资格、工作或审计历史。随后运维人员纠正
外部目录或本地账户状态，并在新的首次关联之前重新启用该用户。首个切片中不存在自助式的
链接或解除链接。

## 6. Space 成员资格、首次登录与邀请

OIDC 不分配 Space 权限。

| 历程 | 结果 |
|---|---|
| `existing_only` 入职 | System Administrator 创建账户；Space 所有者可在首次登录前邀请它；首次经过验证的 OIDC 登录通过邮箱链接；用户接受既有邀请 |
| JIT 入职 | 首次经过验证的 OIDC 登录创建账户与个人 Space；Space 所有者此后可邀请它 |
| 既有成员启用 SSO | 首次经过验证的 OIDC 登录链接当前账户；每一项既有成员资格保持不变 |
| IdP 邮箱变更 | 登录继续通过 `(issuer, subject)` 进行；成员资格不移动；管理界面显示属性漂移 |
| IdP 组变更 | 在首个切片中无影响 |
| 成员资格移除 | 下一次 Space 授权读取会拒绝该 Space；用户的其他 Space 与会话仍然有效 |
| 账户禁用 | 每个用户 API 请求都被拒绝；成员资格为来源留存，并在账户被有意启用时恢复 |

这保留了成员资格设计中账户存在性与 Space 邀请的分离。它还避免了在任何目标组织表明需要
之前引入组映射核对器、受保护所有者规则以及角色的第二个事实来源。

## 7. BuildMax 会话生命周期

### 7.1 单一会话模型

每一次密码、登录代码与 OIDC 认证都会创建一个 `auth_session`。该记录拥有：

- 用户与公开的 `sid`；
- 客户端平台；
- 认证方法（`password`、`login_code` 或 `oidc`）；
- 当方法为 OIDC 时的外部身份（尚未构建：已交付的行没有该列，需经由用户找到链接）；
- 原生客户端上报的客户端标签，例如 `alice-mbp · macOS`（随 §14 计划）；
- 创建时间、最后活动时间、绝对过期时间与撤销时间。

刷新令牌行隶属于此会话，而不是会话本身。访问 JWT 的校验要求 `typ=access` 且 `sid`
非空，随后中心守卫同时检查在用用户与在用会话。Space 角色与授予仍是后续的数据库读取，
不进入 JWT。访问 JWT 不携带签发方（issuer）、受众（audience）、scope 或客户端标识，因此
每个访问令牌都持有用户的全部权限；更窄的、受 audience 限定的凭据尚未构建。

### 7.2 有效期与重新认证

用于接受性测试的推荐默认值为：

| 边界 | 默认值 | 含义 |
|---|---:|---|
| BuildMax 访问令牌 | 15 分钟 | 当会话状态检查不可用或被日后某个路由有意绕过时，持有者重放的最大时长 |
| 刷新不活动 | 30 天 | 当前可轮换令牌的可用窗口 |
| 本地人类会话绝对存活期 | 90 天 | 一次在用的本地登录不能永久续期 |
| OIDC 会话绝对存活期 | 12 小时 | BuildMax 要求再次进行提供方授权之前的最大间隔 |

运维人员可以调整这些值，但管理员状态界面会报告生效值，并对多天的访问令牌或无界会话
发出警告。新的 OIDC 授权应在配置时发送 `max_age` 并校验 `auth_time`，使重启一个
BuildMax 会话不会悄无声息地接受任意陈旧的提供方认证。这一点尚未构建：已交付的流程既不
发送 `max_age`，也不读取 `auth_time`，因此当前的界限只是会话的绝对过期时间，从 BuildMax
登录时起算。

在 Portal 中确认的原生会话继承确认方会话的绝对过期时间（§14.5），因此这些界限对它同样
适用。

仅靠 OIDC 的取消预配是有界的，而非即时的：在没有 SCIM 或经过验证的提供方登出事件的
情况下，仅在 IdP 被禁用的人可能会保留当前的 BuildMax 会话，直到其 OIDC 绝对过期时间，
再加上至多剩余的访问令牌窗口。运维手册必须说明这个数字。

### 7.3 Portal 凭据处理

Portal 仅以 cookie 的形式接收当前可轮换的 BuildMax 刷新令牌：

- 在受支持的部署中为 `Secure` 与 `HttpOnly`；
- 可续期会话 cookie 采用 `SameSite=Strict`；
- 限定于 Portal 会话端点；
- 绝不在 JSON 中返回；
- 每次刷新时替换，登出时清除。

Portal 在登录与页面重新加载后获得一个短期访问令牌，将其保存在内存中，并继续把它作为
当前的 Bearer 凭据发送。这在去除 JavaScript 可读存储中的可续期权限的同时，保持了既有的
API 与 WebSocket 授权形态。本地密码/登录代码的 Portal 登录使用相同的投递路径，因此不
存在一个更弱的“回退”会话。

建立会话的 cookie 端点要求精确的同源 `Origin` 校验、适用时采用 JSON POST，且不使用宽松
的 CORS。这是在 SameSite cookie 之外的附加措施，而非其替代。

### 7.4 登录不附带签发机器凭据

成功登录只返回一对会话凭据。更长期的机器凭据——个人访问令牌（PAT）或服务账户凭据——
需要一个单独的显式操作来为其命名、选择或接受其 scope，并选择过期时间。

这让登出的含义毫不含糊：它结束所选的人类会话。它既不会留下登录时创建的隐藏令牌，也不会
意外删除为其他目的创建的自动化凭据。

### 7.5 登出与撤销

BuildMax 登出总是在报告成功之前撤销 `auth_session`、刷新令牌与 Portal cookie。随后中心
守卫会拒绝该 `sid` 已签发的访问令牌。管理员可以列出并撤销某个用户的会话。自助式会话
列举与撤销路由目前尚未构建；原生登录修订会添加它们（§14.5），因为该修订让本人可以为
其他机器创建会话。

首个切片的含义是“登出 BuildMax”，而非“在提供方处登出每一个应用”。如果 Discovery
公布了 `end_session_endpoint`，RP-Initiated Logout 可在取得互操作性证据后添加，并且即便
提供方重定向失败也会先执行本地撤销。前端通道（front-channel）与后端通道（back-channel）
登出是独立的可选能力，并不由 OIDC 登录隐含。

## 8. OIDC 协议与浏览器流程

BuildMax 仅使用带机密 Server 客户端的 Authorization Code Flow：

1. Portal 带着一个相对返回路径导航到 `GET /api/auth/oidc/start`。返回路径尚未构建：
   已交付的回调总是落到 `/`。Portal 确认页面（§14.4）是第一个需要它的路由。
2. Server 生成事务专用的 `state`、`nonce` 与 PKCE verifier，发送 `S256`，并把这些值连同
   返回路径绑定到浏览器中一个短期、Secure、HttpOnly、SameSite=Lax、受完整性保护的 cookie
   里。
3. 浏览器带着作用域 `openid email profile` 与一个从 `public_base_url` 派生的、精确注册的
   重定向 URI 访问被发现的授权端点。
4. 回调校验 cookie 与 `state`，从 Server 侧交换 code，校验 ID Token 与 `nonce`，并按
   §5.1 所述可选地调用 UserInfo。
5. 执行关联事务与会话创建。随后丢弃提供方的访问令牌与 ID Token；BuildMax 不请求
   `offline_access`。
6. Server 设置 BuildMax 刷新 cookie，并重定向到一个固定的 Portal 完成路由。URL 中不出现
   任何提供方令牌、BuildMax 令牌、邮箱或错误细节。
7. Portal 用该 cookie 换取一个内存中的访问令牌与当前用户，然后应用经过校验的相对返回
   路径。

该临时 cookie 是自包含的，并用一个从必需的部署 JWT 密钥派生并作域分隔的密钥进行完整性
保护。它可以包含 PKCE verifier，因为 TLS、Secure 与 HttpOnly 在传输中以及对页面脚本都
保护它；其完整性防止浏览器调换事务值。这避免了进程本地或仅依赖 Redis 的事务存储，因此
任何 Server 副本都可以接收回调。该 cookie 最多在十分钟后过期，并在每一个回调结果上被
清除。重放它无法重放提供方已经消费过的授权 code。

实现必须使用一个有维护的 OIDC 库来处理发现、令牌交换、JOSE 校验与声明规则。手写的 JWT
或 OAuth 解析不是可接受的小型实现。

规范性参考：

- [OpenID Connect Core 1.0](https://openid.net/specs/openid-connect-core-1_0.html)
- [OpenID Connect Discovery 1.0](https://openid.net/specs/openid-connect-discovery-1_0.html)
- [OAuth 2.0 Security Best Current Practice (RFC 9700)](https://www.rfc-editor.org/info/rfc9700/)
- [OAuth 2.0 for Browser-Based Applications (RFC 10017)](https://www.rfc-editor.org/rfc/rfc10017.html)
- [RP-Initiated Logout 1.0](https://openid.net/specs/openid-connect-rpinitiated-1_0.html)

## 8a. 可扩展性与未来协议

SAML 与任何其他企业登录协议都不在首个切片内，且今天不存在任何 SAML 字段、列、配置块或
`auth_method` 值。本节记录预期的扩展路径，以便日后添加时是有意的新增而非返工——它**不**
授权现在构建其中任何部分，且下面的任何内容都不应在一个有明确名称、确有需求的部署出现
之前实现。

本设计在协议上可扩展，因为认证与授权是分开的轴（§4、§13）。只有处理器层是协议特定的；
外部身份键、`auth_session` 模型、凭据投递与中心守卫都不是。因此日后的协议可在不引入第四
个概念的情况下嵌入三个既有轴：

1. **认证轴上的一个新值。** `auth_session.auth_method` 增加 `saml`。`local_login` 与 OIDC
   设置保持不变，因为“谁可以使用本地登录”与配置了哪种外部协议无关。这正是 §4 把
   native/SSO 保持为正交开关而非一个 `auth_mode` 枚举的原因：协议是某个轴上的一个值，
   而非一个新的顶层模式。
2. **`external_identity` 上的一个协议判别器。** 稳定键从 OIDC 的 `(issuer, subject)`
   泛化为 `(protocol, issuer, subject)`，其中 SAML 提供 `(saml, IdP EntityID, NameID)`。
   该判别器现在**不**添加——在只有一种协议时，它会是一个没有具体需求的字段——但 §9.1 中
   的唯一性约束被记录为“在所配置的签发方范围内”，以便日后的迁移是增加一列而非重新解释
   既有行。要求一个持久的、非瞬态的 `NameID`；瞬态 NameID 不能作为稳定的账户键。
3. **一个并列的提供方配置块。** 一个 `saml:` 块与 `oidc:` 并列，拥有自己的元数据 URL
   或 IdP 证书、实体 ID、NameID 格式以及断言签名要求，并以与 OIDC 块相同的方式校验。
   断言校验使用一个有维护的 SAML 库，绝不手写 XML 或签名解析，与上文的 OIDC 库规则一致。

有两个问题被明确推迟到那次日后的评审，而非在此回答：同时运行多于一个外部协议或签发方
（提供方选择的 UX、链接冲突与签发方迁移行为——见 §16），以及一个无法使用 OIDC 的目标
IdP 是否足以证明采用 SAML 的正当性。在此之前，本记录中单一外部签发方的假设一直成立。

## 9. 数据模型与归属

### 9.1 `external_identity`

| 字段 | 要求 |
|---|---|
| `id`、`public_id` | 内部键加上常规的 BuildMax 公开身份 |
| `user_id` | 既有的 BuildMax 账户；不级联删除，因为用户不会被删除 |
| `issuer` | 精确的已验证签发方，区分大小写 |
| `subject` | 精确的已验证 subject，区分大小写 |
| `last_seen_email` | 供运维人员诊断的已验证属性快照，链接之后不用于查找 |
| `last_seen_name` | 可选的显示名快照 |
| `last_login_at`、`created_at` | 生命周期证据 |

唯一性约束为 `(issuer, subject)` 与 `(issuer, user_id)`，作用域限定在所配置的单一签发方
之内。后者防止一个账户悄无声息地从该签发方累积两个 subject。第二种协议或签发方会在这些
键之前增加一个判别器列，而非重新解释既有行（§8a）。该行不包含任何提供方访问令牌、ID
Token、组列表、角色或 Space ID。

### 9.2 `auth_session`

| 字段 | 要求 |
|---|---|
| `id`、`public_id` | 内部键加上公开的 `sid` |
| `user_id` | 该会话所行使权限的账户 |
| `external_identity_id` | 可空；仅在 OIDC 认证时设置。尚未构建：已交付的行没有该列 |
| `platform`、`auth_method` | 所使用的客户端与凭证 |
| `client_label` | 随 §14 计划：可空，至多 64 个可打印字符，原样保存原生客户端的上报值；从不被信任 |
| `created_at`、`last_seen_at` | 会话生命周期元数据 |
| `absolute_expires_at`、`revoked_at` | 权威的有效性 |

`user_refresh_token` 引用 `auth_session`，只保留令牌轮换状态与过期时间。会话行不是第三种
凭据。它是已签发的 `sid` 当前所缺失的权威状态。

### 9.3 `native_sign_in`

随 §14 计划。每个待处理或已决定的原生登录请求对应一行：

| 字段 | 要求 |
|---|---|
| `id` | 内部键；没有公开 ID，因为除了代码或轮询密钥之外，没有任何东西寻址一个请求 |
| `user_code_hash` | 规范化后用户代码的 SHA-256，唯一 |
| `poll_secret_hash` | 轮询密钥的 SHA-256，唯一 |
| `platform` | `cli` 或 `desktop` |
| `client_label` | 客户端声称的标签，至多 64 个可打印字符 |
| `state` | `pending`、`confirmed` 或 `denied` |
| `interval_seconds`、`last_polled_at` | 按请求的轮询节奏（`slow_down`） |
| `decided_by_user_id`、`decided_session_id`、`decided_at` | 由确认或拒绝设置；该会话 ID 指向作出确认的 Portal 会话，原生会话继承其方法与过期时间 |
| `expires_at`、`created_at` | 带索引的过期时间；创建时间 |

该行不保存任何令牌、邮箱或 IP 地址。兑换在创建会话的同一事务中删除它；其余行在过期后
由 `CredentialCleaner` 删除。

### 9.4 归属

- `internal/core/identity` 拥有类型、与校验无关的存储契约、会话状态以及永久审计动作
  名称。
- `internal/service/identity` 拥有关联、预配、认证、会话创建与撤销工作流。
- `internal/infra/db` 拥有这两张单数命名的表，以及创建带个人 Space 与身份链接的 JIT
  用户的事务。
- `internal/server/handlers/auth` 拥有 OIDC 的 HTTP 状态、cookie、重定向、提供方协议
  适配以及 BuildMax 令牌签发。
- `internal/server/access` 仍是唯一的请求认证与授权汇聚点。
- Portal 只呈现方法并在内存中存储账户状态；它绝不解析 ID Token 或映射声明。
- 对原生登录（§14）而言：`internal/core/identity` 拥有请求类型、状态、有效期、代码格式与
  存储契约；`internal/service/identity` 拥有发起、轮询、确认、拒绝与兑换，包括准入重查与
  继承的过期时间；`internal/infra/db` 拥有 `native_sign_in` 与兑换事务；
  `internal/server/handlers/auth` 拥有路由；Portal 拥有确认页面；CLI 与 Desktop 只拥有
  呈现与轮询。

不引入任何新的“组织”、“租户”、“IdP 组”或 SSO 专用的用户类型。一个私有部署、一个外部
签发方、一个 BuildMax 账户以及一个或多个 Space 已经表达了所需的归属边界。

## 10. HTTP API 与 Portal 变更

已交付的公开路由：

```text
GET  /api/auth/methods
GET  /api/auth/oidc/start
GET  /api/auth/oidc/callback

POST /api/auth/portal/login
POST /api/auth/portal/session
POST /api/auth/portal/logout

GET    /api/admin/users/{user_id}/identities
DELETE /api/admin/users/{user_id}/identities/{identity_id}
```

`GET /api/auth/methods` 只返回本地登录与 OIDC 是否可用，以及运维人员设置的 OIDC 显示
标签。它不返回任何匿名调用方不需要的签发方元数据、客户端标识、域名允许列表或策略细节。

这三个 Portal 端点是位于当前 `/api/auth/login`、`/api/auth/token/refresh` 与
`/api/auth/logout` 所使用的同一身份服务之上的凭据投递适配器。既有路由仍作为原生客户端
的 JSON 传输；Portal 路由绝不序列化刷新令牌。凭据校验与会话状态转换不被重复实现。

Portal 的登录页面读取方法文档，只显示已配置的选项。SSO 按钮是导航，而非打开一个嵌入式
登录框。在回调或重新加载之后，认证上下文调用 Portal 会话端点，而不是从 `localStorage`
注水（hydrate）持有者凭据。UI 会区分：

- 提供方不可用或配置错误；
- 浏览器事务已过期，必须重新开始；
- 经过验证的身份未被授权访问此部署；以及
- 被链接的 BuildMax 账户已被禁用。

详细的提供方错误与声明保留在带请求关联 ID 的、经脱敏的 Server 日志中，而非浏览器响应中。

原生登录（§14）的计划路由如下。它们尚未构建，也尚未写入 `openapi.json`：

```text
POST   /api/auth/native-sign-ins            匿名：发起请求
POST   /api/auth/native-sign-ins/poll       匿名：凭轮询密钥轮询；确认后兑换一次
GET    /api/auth/native-sign-ins?code=      Portal 会话：查询一个待处理请求
POST   /api/auth/native-sign-ins/confirm    Portal 会话：{code}
POST   /api/auth/native-sign-ins/deny       Portal 会话：{code}

GET    /api/auth/sessions                   当前账户的在用会话
DELETE /api/auth/sessions/{session_id}      撤销其中之一
```

确认与拒绝采用 `POST` 动词而非 `PUT .../state`，因为它们作用于一个有客户端正在轮询等待
的实时交换，而且确认者手中唯一的句柄是代码，代码必须远离路径与日志——这与渠道配对用
`POST /api/channel-links {code}` 确认的理由相同。

## 11. 配置与部署

在本切片中保留当前的顶层认证设置，而不是顺带重构整个 `server.yaml`。原生与 SSO 的姿态是
既有平面（`local_login`）与新的 `oidc` 块经过验证的组合（§4 决策 10）；不存在单独的
`auth_mode` 字段。增加一个枚举和一个 OIDC 块：

```yaml
jwt_secret: ""                 # existing; normally injected
access_token_ttl: 15m          # existing field, proposed safer default
refresh_token_ttl: 720h        # existing inactivity window
session_absolute_ttl: 2160h    # new; local/login-code/password sessions
local_login: all               # all | system_admins | off; migration default

oidc:
  enabled: false               # false => native: operator-created accounts only
  display_name: Company SSO
  issuer: https://id.example.com
  client_id: buildmax
  client_secret: ""            # inject with BUILDMAX_OIDC_CLIENT_SECRET
  provisioning: jit            # jit (default) | existing_only
  allowed_email_domains: []    # required and non-empty for jit
  session_max_age: 12h
```

记录在案的两种姿态为：

- **原生（默认）：** `oidc.enabled: false` 配 `local_login: all`。System Administrator
  像今天一样通过 `buildmax-server` 引导命令创建并分配账户；没有外部登录。
- **SSO：** `oidc.enabled: true` 配为应急推荐的 `local_login: system_admins`。
  `provisioning: jit` 会在来自 `allowed_email_domains` 地址的首次经过验证的登录时自动
  创建账户；设置 `existing_only` 则只接受预先创建的账户。

当 `oidc.enabled` 为 false 时，`provisioning` 与 `allowed_email_domains` 被忽略；当
`oidc.enabled: true` 且 `provisioning: jit` 而 `allowed_email_domains` 为空时，启动会
拒绝。

回调精确为 `<public_base_url>/api/auth/oidc/callback`。启用 OIDC 时 `public_base_url`
是必需的，且必须为 HTTPS，除非处于显式的回环（loopback）开发模式。它绝不从 `Host` 或
转发头派生，从而避免攻击者影响重定向的构造。

`local_login` 的含义：

| 值 | 密码/登录代码会话策略 |
|---|---|
| `all` | 当前行为；在运维人员选择启用 SSO 强制之前的迁移默认值 |
| `system_admins` | 与 OIDC 搭配推荐；经过验证的本地凭据只为在用的 System Administrator 开启会话 |
| `off` | 没有本地 HTTP 登录；启动会警告恢复需要更改配置并重启 |

除非 `local_login: all`，否则 `allow_signup` 无效；JIT 属于经过验证的 OIDC 路径，不会
重新开启未经验证的邮箱注册。

客户端密钥是首个切片中唯一的新密钥。它在部署时注入，在每个配置/状态响应中脱敏，绝不
传递给 worker，并通过替换挂载的密钥与滚动 Server 副本来轮换。初始的客户端认证方法是
`client_secret_basic`；只有在目标 IdP 或威胁模型要求时才添加 `private_key_jwt`。

## 12. 失败、轮换、恢复与审计

### 12.1 发现与 JWKS

所配置的签发方是唯一的 URL 信任根。Discovery 必须返回完全相同的签发方，以及 HTTPS 的
授权、令牌、（使用时的）UserInfo 与 JWKS 端点。请求参数绝不提供签发方或端点，从而把
SSRF 限定在运维人员的配置范围内。

Discovery 与 JWKS 遵循缓存有效期。未知的签名 `kid` 会在拒绝之前触发一次立即的 JWKS
刷新，以支持正常的提供方密钥重叠。签名算法被限制为库与提供方元数据安全支持的那些；
`none` 以及把客户端密钥用作 ID Token HMAC 密钥都会被拒绝。

网络获取失败不会使 `/readyz` 失败：既有的 BuildMax 会话与本地工作仍然可用。如果不存在
可用的缓存元数据/密钥，新的 OIDC 启动或回调会返回一个可重试的 503。管理员系统视图会
报告已配置、可用/降级、最近一次成功的元数据/JWKS 刷新，以及一条经脱敏的最近错误。

### 12.2 轮换与配置变更

| 变更 | 所需行为 |
|---|---|
| 提供方签名密钥 | 自动 JWKS 刷新；在测试中验证重叠 |
| OIDC 客户端密钥 | 在旧密钥仍有效时于 IdP 处添加新密钥、滚动 BuildMax、验证登录、停用旧密钥；否则接受一段有界的登录中断 |
| BuildMax JWT 密钥 | 当前的访问 JWT 失效；在用的刷新/会话行可铸造替代；记录并测试运维流程 |
| 签发方变更 | 视为一个不同的身份命名空间；绝不按 subject 或邮箱悄无声息地重新链接；既有的 BuildMax 会话存续至正常撤销/过期 |
| OIDC 被禁用 | 停止新的 OIDC 登录；不悄无声息地撤销当前的 BuildMax 会话 |

因此更改签发方需要一个显式的迁移计划：在用户通过新签发方链接之前保留旧签发方，或在
运维人员控制下禁用/解除链接/重新启用账户。为平滑该迁移而支持两个在用签发方是日后的
需求，不隐藏在单提供方切片里。

### 12.3 应急与 IdP 故障

在强制执行 `local_login: system_admins` 之前，运维手册会创建至少两个 System
Administrator 账户，其强本地密码通过运维人员的应急凭据流程保存，并验证一次登录。当 IdP
或 HTTP 管理界面失效时，既有的直接操作数据库的创建、登录代码、授予与撤销命令仍然可用。

IdP 故障有如下已声明的结果：

- 既有有效的 BuildMax 会话继续；
- 新的 OIDC 会话与已过期的 OIDC 会话无法启动；
- 本地 System Administrator 恢复仍然可用；
- 本地 CLI/TUI 与 Desktop 直连模式不受影响；
- 就绪状态保持健康，而管理员诊断显示 OIDC 降级。

### 12.4 审计

对于成功的会话，复用 `user.login` 并带 `oidc` 细节。为 `user.external_identity_linked`
与 `user.external_identity_unlinked` 添加永久动作；JIT 创建还会记录既有的 `user.created`
动作并带 OIDC 细节。身份链接/解除链接及其审计行必须在同一个数据库事务中提交，因为它们
改变了谁能成为一个账户。登录成功与运营性失败可保留当前的尽力而为策略，并在运维文档中
说明已知的局限。

匿名回调失败仍是结构化的运营日志，而非以不受信任的邮箱或声明为键的审计事件。日志包含
一个关联 ID 与一个有界的原因类别，绝不包含授权 code、提供方令牌、客户端密钥、PKCE
verifier、nonce、cookie 或原始声明集。审计导出与保留保持其既有权限与策略。

原生登录（§14）增加两个永久动作：

- `auth.native_sign_in_confirmed` 与 `auth.native_sign_in_denied` 记录决定。执行者是
  作出确认的用户；目标是作出确认的 `auth_session`；细节是平台与客户端声称的标签，长度
  有界并标注为声称值。
- 兑换写入普通的 `user.login` 事件，目标为原生平台，细节为 `portal_confirmation`。会话行
  的 `auth_method` 保留继承来的方法，因此运维人员能同时看到来源与底层凭证。
- 自助撤销复用 `user.session_revoked`，执行者为用户本人。

这些事件遵循登录的策略，是尽力而为的写入，与 `user.login` 一样，不与决定在同一事务中
提交。匿名的发起、轮询与过期不是审计事件，而是带有界原因类别的运营日志，绝不包含用户
代码、轮询密钥或令牌。

## 13. 授权与 Agent 执行的影响

OIDC 改变的是谁能开启一个人类会话，而非该会话可以做什么。

- 每个 Space 路由继续解析当前成员资格与角色。
- System Administrator 仍是一项显式的 BuildMax 授予；任何 IdP 组都不能创建它。
- 移除一项 Space 成员资格在下一次 Space 请求时生效，不会终止此人的会话或其他成员资格。
- 禁用一个 BuildMax 账户会立即拒绝用户请求、撤销其会话、使已排队但尚未启动的工作失败，
  并像当前代码那样暂停计划任务。
- 一个已在其运行范围凭据下执行的 TaskRun 不会被 SSO 或成员资格变更悄无声息地取消。它的
  外部副作用无法撤销，其结果仍归 Space 所有。需要停止它的运维人员使用既有的取消路径。
- 继续、重试或启动后续工作会重新检查在用账户与当前 Space 权限，而不是继承旧运行的调用方
  访问权。

SCIM 或未来的组核对必须保持这些边界。特别是，目录组不能成为一个绕过
`internal/core/space.Allows` 的令牌声明，且核对绝不能使一个普通 Space 没有所有者。

## 14. CLI 与 Desktop 登录

首个切片只交付了 **Portal 浏览器 SSO**，留下一个缺口：原生 CLI/Desktop 登录走的是
密码/登录代码的 `POST /api/auth/login`，一旦部署设置推荐的 `system_admins`（或 `off`），
`local_login` 就会拒绝所有普通账户。在 SSO 部署上，员工可以使用 Portal，却完全无法把
CLI 或 Desktop 连接到托管模型、Issue 或 Remote Control。

**决策（修订，2026-10-11）。** 维护者决定：CLI 与 Desktop 必须能够登录账户采用企业 SSO
的服务器，并只选择一种机制——由 BuildMax 中介的登录请求，形态借鉴 OAuth 2.0 设备授权
（[RFC 8628](https://www.rfc-editor.org/info/rfc8628/)），由本人在 Portal 中确认。不采用
回环重定向，也没有第二种机制。本节其余部分是设计；请求的表见 §9.3，路由见 §10，审计见
§12.4，威胁见 §15。

首个切片的以下规则依然成立：

- CLI/TUI 与 Desktop 的本地/直连模式完全独立于 Server 与 IdP 的可用性。登录是客户端进入
  托管模式的方式（[客户端模式](客户端模式.md)）；这里的一切都不触及本地模式。
- Desktop 中不嵌入任何 IdP 页面，原生客户端不收集任何 IdP 密码。本人在自己的浏览器中
  登录 Portal，方式与其账户在 Portal 中的登录方式相同。
- 这是人类登录，不是 PAT、服务账户或无人值守凭据的设计（§7.4、§18）。

### 14.1 为何选择 Portal 确认

核心成果是：能够登录 Portal 的人，可以让自己掌控的机器上的 CLI 或 Desktop 获得一个属于
自己的 BuildMax 会话，而该客户端无需接触其 IdP 凭据。约束包括：

- Portal 已经拥有所有登录方式（密码、登录代码、OIDC，以及 §8a 下日后的任何协议）；
- IdP 只知道一个机密客户端及其唯一精确的重定向 URI（§8）；
- 客户端运行在笔记本上，也运行在没有浏览器的 SSH 主机与容器中；
- 服务器没有应用自有的登录限流器。

Portal 确认用一种机制满足了全部约束：

- **无需新的 IdP 集成。** IdP 看到的仍只是 Portal 既有的授权码流程：无需注册第二个重定向
  URI，没有公共客户端，IdP 处也没有按客户端的 PKCE。日后的协议或密码账户无需在此做任何
  改动即可使用。
- **覆盖无界面主机。** 本人在任何带浏览器的设备上确认，SSH 会话无需端口转发。回环重定向
  （[RFC 8252](https://www.rfc-editor.org/info/rfc8252/)）只在浏览器与客户端位于同一主机
  时可用，仍需为无界面主机提供设备式回退——这恰恰是本记录拒绝投机构建的“两者兼有”。
- **本人的决定是显式且可见的。** Portal 在签发任何东西之前先指明发起请求的客户端，这正是
  渠道配对先例所依赖的防御（[即时通讯渠道 §6](即时通讯渠道.md#6-配对)）。

代价是所有设备授权流程共有的已知弱点：一个人可能被说服去确认别人的请求（同意钓鱼，
RFC 8628 §5.4）。§14.4 与 §15 对其加以约束，但无法消除。

术语：本记录把存储的对象称为**原生登录请求（native sign-in request）**，本人对其**确认**
或**拒绝**。“设备”已用于指代 Remote Control 的观看端，“批准”已用于指代工具批准
（[Remote Control](远程控制.md)），因此这两个词都不用于本流程的路由、审计动作或界面文案。

### 14.2 流程

1. 客户端匿名调用 `POST /api/auth/native-sign-ins`，携带其平台（`cli` 或 `desktop`），
   以及由主机名和操作系统组成的客户端标签，例如 `alice-mbp · macOS`。
2. 服务器返回：
   - 一个**用户代码**，例如 `WDJB-MJHT`；
   - 一个**轮询密钥**；
   - 以秒为单位的 `expires_in` 与 `interval`；
   - `verification_uri`，即输入代码的 Portal 页面；
   - `verification_uri_complete`，即已填好代码的同一页面。
3. Desktop，以及运行在有桌面会话的机器上的 CLI，在系统浏览器中打开
   `verification_uri_complete`。每个客户端还会显示 URL 与代码，因为浏览器可能打不开，
   也可能在另一台机器上。
4. 本人进入 Portal，必要时登录：使用 SSO，或在 `local_login` 允许时使用密码。Portal 显示
   该请求（§14.4）。本人核对代码与客户端上显示的一致，然后选择**确认**或**拒绝**。
5. 同时，客户端按服务器设定的间隔，凭轮询密钥调用
   `POST /api/auth/native-sign-ins/poll`。
6. 确认之后，下一次轮询创建会话，并返回与 `POST /api/auth/login` 相同的 JSON 令牌对。
   客户端把它存放在既有原生登录的存放位置，从而以该账户登录。
7. 拒绝、过期或取消都会结束请求。除非发生了第 6 步，否则不存在任何会话。

Portal 页面是一个 hash 路由：完整 URI 为 `<base>/#/sign-in/<code>`，输入代码的页面为
`<base>/#/sign-in`。配置了 `public_base_url` 时 `<base>` 即为它，否则为客户端所调用的
源。hash 片段永远不会进入服务器或代理日志，这也是渠道配对链接使用它的原因。该 URL 只
返回给发起请求的调用方，从不用于服务端重定向，因此即便从请求源推导，伪造的 `Host` 也只能
误导调用方自己。

### 14.3 登录请求

| 属性 | 决定 | 理由 |
|---|---|---|
| 存储 | 每个请求一行 MySQL 记录 `native_sign_in`（§9.3） | 发起、确认与轮询可能落在不同副本上。所有凭据与配对状态本就存放在数据库中。协调存储只承载流、扇出与租约，没有持久的可过期记录 API；在 `local` 模式下它只在进程内。 |
| 有效期 | 自创建起 10 分钟，固定，不可配置 | 与渠道配对和 OIDC 事务 cookie 一致。它足够完成一次 IdP 登录，又足够短以约束钓鱼与猜测。确认也必须在此期间内完成。 |
| 用户代码 | 8 个字符，取自 `ABCDEFGHJKMNPQRSTUVWXYZ23456789`（31 个符号，约 40 位）。显示为 `XXXX-XXXX`，接受任意大小写，忽略连字符与空格。 | 这是渠道配对的字母表与规范化规则，共用一份实现而非复制。它没有易混字符（`0/O`、`1/I/L`），可以口头念出或在手机上输入。 |
| 轮询密钥 | `bmxsignin_` 后接 32 个随机字节的 base64url | 它是兑换会话的持有者凭证，因此具有完整熵。前缀便于密钥扫描器识别，与 `bmxlogin_`、`bmxrefresh_` 相同。 |
| 静态存储 | 只保存规范化用户代码与轮询密钥的 SHA-256，各自建唯一索引。创建时若冲突则重新生成代码。 | 读取数据库也无法还原其中任何一个。 |
| 单次使用 | 请求为 `pending`，随后变为 `confirmed` 或 `denied`；以第一个决定为准。已确认的请求只能兑换一次：创建会话的那次轮询在同一事务中删除该行。 | 重放的轮询密钥或第二个决定都找不到可操作的对象。 |
| 轮询间隔 | 从 5 秒开始。早于所存间隔的轮询返回 `slow_down`，并把所存间隔增加 5 秒，上限 30 秒。 | 这是 RFC 8628 §3.5 的语义。请求行保存按请求的状态，因此不需要限流基础设施。 |
| 清理 | 既有的每小时 `CredentialCleaner` 删除过期请求 | 它本就负责清理登录代码与刷新令牌 |

轮询使用服务器既有的错误体 `{"error": "<code>"}`，它也是 OAuth 的错误形态。代码采用
RFC 8628 的名称：

| 应答 | 含义 | 客户端行为 |
|---|---|---|
| `200` 附令牌对 | 已确认并兑换 | 保存令牌对并报告账户 |
| `400 authorization_pending` | 尚未决定 | 等待 `interval` 后再次轮询 |
| `400 slow_down` | 轮询过早 | 把自己的间隔加 5 秒 |
| `400 access_denied` | 本人拒绝了它，或作出确认的账户或会话已不可用 | 停止，并说明登录未被允许 |
| `400 expired_token` | 已过期、已兑换或密钥未知，三者有意不加区分 | 停止，并提供重新开始的选项 |

客户端在网络错误与 `5xx` 时也会退避（翻倍，上限 30 秒），并在 `expires_in` 到期时停止。
请求过期后它不再轮询。

### 14.4 在 Portal 中确认

Portal 向已登录的 Portal 会话显示确认页面。该页面在 Space 闸门之前渲染，因此没有可用
Space 的账户也能确认。如果尚无会话，先运行 Portal 的登录闸门，本人随后回到该页面。对于
本地登录，hash 路由本就能穿过闸门保留下来；SSO 则需要 §8 所述、经过校验的相对返回路径，
因为已交付的回调总是落到 `/`，会丢掉代码。

页面用 `GET /api/auth/native-sign-ins?code=` 查询请求（请求日志已经会脱敏名为 `code` 的
查询键），然后显示：

- 客户端种类（**BuildMax CLI** 或 **BuildMax Desktop**）及其客户端标签，标注为
  **由客户端上报，未经验证**。服务器无法验证客户端对自身的任何陈述；标签的作用是让本人
  能察觉异常，而不是证明请求来自何处；
- 大号显示的代码，附“请核对它与你的 CLI 或 Desktop 显示的代码一致”；
- 请求发起于多久之前、何时过期；
- 将以哪个账户登录（即当前的 Portal 账户），以及所产生的会话何时结束（§14.5）；
- 按钮上方的警告：“只有当这次登录是你本人刚刚发起的，才确认。如果是别人发给你的链接
  或代码，请拒绝。”

页面不显示请求方的网络地址。服务器没有受信任代理设置，因此在共享入口之后 `RemoteAddr`
是代理，而转发头是客户端随意写入的内容。显示其中任何一个都会把未经验证的事实当作证据
呈现。§19 第 9 项记录了改变这一点所需的条件。

页面加载时不作任何决定。即便代码已预填，本人仍需点击**确认**
（`POST /api/auth/native-sign-ins/confirm`，请求体 `{code}`）或**拒绝**
（`POST /api/auth/native-sign-ins/deny`，请求体 `{code}`）。错误、过期或已决定的代码都
显示同一个“此代码已失效”状态，不透露属于哪种情况。作出决定后，页面提示本人回到客户端，
并像聊天配对页面那样把代码从 URL 中移除。

谁可以确认：

- **只有 Portal 会话。** 该路由拒绝任何平台不是 `portal` 的会话。否则，被窃取的 CLI
  令牌就能铸造更多原生会话，而且每一个都能在铸造它的令牌被撤销后存活。确认是浏览器中的
  行为，发生在带有警告的页面上。
- **只有此刻仍能登录的账户。** 确认时会按作出确认的会话的方法重新应用当前的准入规则：
  `password` 或 `login_code` 会话只有在 `local_login` 准入该账户时才能确认；`oidc` 会话
  只有在 OIDC 仍启用时才能确认。账户必须处于活跃状态，且不是服务账户。因此，在运维人员
  收紧 `local_login` 之前开启的会话，无法借此洗白成一个新的原生会话。

**不要求近期登录。** 近期性无法防御真正重要的威胁：被钓鱼的人会有意确认，无论他多么近期
登录过。§14.5 的有效期界限已经保证原生会话不会比作出确认的登录活得更久。逐步提升的重新
认证会增加第二种 Portal 登录模式，而对 SSO 而言那只是一次 IdP 通常静默满足的重定向，
并无相应收益。当作出确认的会话剩余不足一小时时，页面会说明这一点并提供**重新登录**：它
登出 Portal 并返回此页面，让本人可以选择一个完整时长的会话。

### 14.5 所产生的会话

会话在已确认的请求被兑换时创建，而不是在确认时创建，因此永远不会存在一个没有客户端持有
的会话。兑换是一个事务：锁定请求；检查它已确认且未过期；检查账户活跃且作出确认的会话
仍然在用；通过所有登录共用的同一 `openSession` 路径创建 `auth_session` 及其刷新令牌；
删除请求。

| 字段 | 取值 |
|---|---|
| 用户 | 作出确认的账户 |
| `platform` | 请求的平台，`cli` 或 `desktop`。新路由会校验它，而 `/api/auth/login` 目前接受任意值。 |
| `auth_method` | 作出确认的会话的方法（`password`、`login_code` 或 `oidc`）；会话背后的凭证就是那次登录 |
| `absolute_expires_at` | 作出确认的会话的 `absolute_expires_at`，绝不更晚 |
| `client_label` | 请求中客户端声称的标签（新列，§9.2） |

**它绝不比确认它的那次认证活得更久。** 由 OIDC Portal 会话确认的原生会话，在该会话的
OIDC `session_max_age`（默认 12 小时）结束时结束；由密码会话确认的，在该会话的
`session_absolute_ttl` 上限结束。因此 `local_login` 通过作出确认的登录而生效：本流程在
`local_login` 的每个取值下都可用，因为本人是通过该取值本就准入的方式进入 Portal 的。在
`off` 且启用 OIDC 时，它是原生客户端登录的唯一方式；在 `system_admins` 下，它是普通 SSO
用户连接 CLI 与 Desktop 的方式。

签发之后，该会话是独立的。它轮换刷新令牌，遵循 30 天不活动窗口，并在 `buildmax logout`、
Desktop 登出、管理员撤销、账户禁用或绝对过期时结束。登出作出确认的 Portal 会话不会结束
它：Portal 登出的含义是“这个浏览器”，而原生会话是一个单独列出、可单独撤销的会话。

响应与客户端已在解析的 `LoginResponse` 相同（`access_token`、`refresh_token`、
`expires_in`、`user`），因此存储、刷新，以及[客户端模式 §8](客户端模式.md#8-登录过期不会静默回退)
中的过期/禁用/不可用分类都不变。成功后，两个客户端都会打印或显示当前登录的账户——这正是
本人察觉代码被错误账户确认的方式（§15）。

**列举与撤销。** 管理员会话列表在平台与方法旁显示新的 `client_label`。本流程也让本人
（而非运维人员）成为为其他机器创建会话的人，因此本人必须能够自行查看并结束这些会话。
在当前主体的前缀下增加自助列举与撤销：`GET /api/auth/sessions` 与
`DELETE /api/auth/sessions/{session_id}`，并在 Portal 的**账户 → 会话**中呈现，标出当前
浏览器会话。这取代了 §7.5 中“自助路由尚未构建”的说法。`/api/auth/login` 与两个客户端
也接受并发送 `client_label`，使通过密码登录的原生会话在该列表中同样易于辨认。

### 14.6 滥用界限

应用自有的登录限流器仍然不存在（§15、§19 第 7 项）。因此本流程借助它本就存储的状态
约束自身，再加上对每个匿名 `/api/auth/*` 路由仍属强制的外部按 IP 入口限流：

| 界面 | 界限 | 应答 |
|---|---|---|
| 发起，匿名 | 全部署范围内最多 500 个未过期的 `pending` 请求，在数据库中计数 | `503` `{"error":"too many pending sign-in requests"}` 并附 `Retry-After` |
| 轮询，匿名 | 按请求通过 `interval` 与 `slow_down` 约束；256 位的轮询密钥无需猜测限制 | §14.3 |
| 查询、确认、拒绝（已登录） | 每个账户每 10 分钟最多 10 次未知代码尝试，按副本、在进程内计数（同渠道配对的节流） | `429` |

这些数值是常量而非配置，直到某个部署表明需要。发起端没有按来源的限制，因为服务器无法
识别入口之后的来源（§14.4）。发起洪泛可能耗尽全局上限，短暂地让所有人都无法进行原生
登录，但它无法创建会话、触及账户或影响 Portal 登录。该残余风险列于 §15。

40 位代码已经足够，因为猜测需要认证、可归因且受节流。最多 500 个在用代码时，一次猜测
成功的概率低于 10⁻⁹；而猜中也只是让猜测者把陌生人的客户端确认到猜测者自己的账户中，
该客户端随后会显示这个账户。

### 14.7 客户端体验

Portal 与 Desktop 的界面文案按
[UI 体验专项 D5](UI体验专项.md#d5-通过共享的类型化文案目录实现本地化) 提供英文与简体中文。
CLI 输出与其他所有 CLI 命令一样保持英文，API 错误文本也保持英文。

**CLI。** `buildmax login` 保留服务器 URL 提示，然后默认发起登录请求，因为这是对所有
账户姿态都可用的唯一路径，且能让密码远离终端。它打印：

```text
To sign in, open this page in a browser and confirm the request:

  https://buildmax.example.com/#/sign-in

Check that the page shows this code: WDJB-MJHT
(The request expires in 10 minutes. Press Ctrl-C to cancel.)

Waiting for confirmation…
Signed in to https://buildmax.example.com as alice@example.com.
```

- 它复用应用连接器 OAuth 流程已在使用的 `openExternalURL` 辅助函数，在系统浏览器中打开
  完整 URI。当设置了 `SSH_CONNECTION` 或 `SSH_TTY`，或 Linux/BSD 主机既没有 `DISPLAY`
  也没有 `WAYLAND_DISPLAY` 时，跳过这一步。打开浏览器时也会打印完整 URI。
- `--no-browser` 强制只打印。
- `--password` 保留目前针对 `/api/auth/login` 的邮箱、密码与登录代码提示（§14.8）。
- 被拒绝、过期与被服务器拒绝的请求各打印一句平实的说明，并以非零状态退出。Ctrl-C 停止
  轮询，让请求自行过期。

**Desktop。** 登录页面保留服务器地址字段，然后通过一个新的绑定读取该服务器的
`GET /api/auth/methods`：

| `local_login` | 页面显示 |
|---|---|
| `all` | 与现在一样，密码表单在前；“或”分隔线下方是**在浏览器中登录** |
| `system_admins` | **在浏览器中登录**作为主要操作；密码表单收在“管理员使用密码登录”之后 |
| `off` | 只有**在浏览器中登录** |

启用 OIDC 时，浏览器按钮会写出提供方名称：**Continue with {display_name} in your
browser** / **在浏览器中通过 {display_name} 继续**；否则为 **Sign in with your browser** /
**在浏览器中登录**。

选择它会发起请求，通过 Wails 的 `BrowserOpenURL` 运行时调用在系统浏览器中打开完整 URI，
并用一个等待面板替换表单：

- 大号显示的代码；
- “Confirm this sign-in in the browser window that opened. Check that it shows this
  code.” / “请在已打开的浏览器窗口中确认此次登录，并核对页面显示的代码与此一致。”；
- 操作 **Open browser again** / **重新打开浏览器**、**Copy link** / **复制链接** 与
  **Cancel** / **取消**；
- 轮询在 Go 中运行，并以事件报告完成。

被拒绝或过期时，面板会说明（“Sign-in was denied in the browser.” /
“已在浏览器中拒绝此次登录。”；“The sign-in request expired. Start again.” /
“登录请求已过期，请重新开始。”）并回到表单。如果方法请求失败，页面显示既有的服务器
不可达状态，而不是猜测该提供哪些方法。

**Portal。** `#/sign-in` 页面及其各状态都有两种语言的文案：

- 请求卡片；
- “由客户端上报，未经验证”标记；
- 警告；
- **Confirm sign-in** / **确认登录** 与 **Deny** / **拒绝**；
- “请回到你的 CLI 或 Desktop”的结果；
- 代码失效状态。

**`GET /api/auth/methods` 不变。** 只要有人能登录 Portal，确认就可用，因此为它设置的
标志只会永远为真。客户端与服务器同步发布（没有 URL 版本），也就不存在需要客户端探测的
旧服务器。

### 14.8 密码与登录代码原生登录

`POST /api/auth/login` 保留，保持不变并继续受 `local_login` 约束。它是唯一不依赖 Portal
或第二台设备的原生路径：

- 当 Portal 或 IdP 路径本身发生故障时的运维应急（§12.3）；
- CLI 与 Desktop 的端到端测试套件；
- 原生部署上的脚本化登录。

客户端把它保留为显式的替代方式（`buildmax login --password`、Desktop 密码表单），但它
不再是唯一选项。移除它会让应急依赖 Portal，而对于不想要原生密码的部署，
`local_login: off` 已经提供了移除它所能带来的一切。

### 14.9 失败模式

| 情形 | 结果 |
|---|---|
| 本人关闭浏览器或始终未确认 | 请求在 10 分钟后过期，客户端报告此情况，不存在会话 |
| 客户端在确认之后、下一次轮询之前退出 | 已确认的请求未被兑换即过期，不创建会话 |
| 令牌响应在传输中丢失 | 请求已被兑换，下一次轮询返回 `expired_token`，本人重新开始。遗留的会话从未被使用，出现在会话列表中，并在过期或被撤销时结束。 |
| 被拒绝 | `access_denied`；客户端停止 |
| 兑换前账户被禁用，或作出确认的会话被撤销 | `access_denied`，不创建会话 |
| 作出确认的会话的方法不再被准入（`local_login` 收紧、OIDC 被禁用） | 确认以 `403` 被拒绝，并提示重新登录 |
| 被错误的 Portal 账户确认 | 客户端显示其登录的账户；本人运行 `buildmax logout` 或在 Desktop 中登出，该会话即被撤销 |
| 代码输错、已过期或已使用 | Portal 中显示同一个“已失效”状态，并计入查询节流 |
| IdP 故障 | 仍然有效的 Portal 会话可以确认；否则无法通过 SSO 进入 Portal，原生登录也随之等待，与 §12.3 对新 SSO 登录的声明一致 |
| Redis 或协调存储不可用 | 无影响；本流程只使用数据库 |
| 每一步由不同副本处理 | 无影响；每一步都读取共享的行 |
| 达到待处理请求上限 | 发起返回 `503` 并附 `Retry-After`；既有会话与 Portal 登录不受影响 |
| 浏览器所在主机无法访问 `<base>` | 本人在另一台设备上打开打印出的 URL，或由运维人员设置 `public_base_url` |

## 15. 威胁模型

| 威胁或失败 | 所需控制 | 残余界限 |
|---|---|---|
| 登录 CSRF 或 code 注入 | 事务专用的 state、nonce、PKCE S256、浏览器绑定、精确回调 | 被攻破的浏览器配置文件仍被信任为该用户 |
| 授权 code 被截获 | 服务端交换、机密客户端、PKCE；Portal 存储中无 code/令牌 | IdP 或 TLS 被攻破不在 BuildMax 范围内 |
| 签发方混淆（mix-up） | 单一配置的签发方、精确的 Discovery/ID Token 签发方与受众校验 | 多签发方支持需要一次新的评审 |
| 开放重定向 | 仅在受保护的事务状态内存储一个经过校验的相对 Portal 路径 | 不支持登录后的外部重定向 |
| 通过邮箱匹配的账户接管 | 已验证邮箱、JIT 必需的非空允许域名列表、原子唯一性、绝不替换既有 subject 链接 | 除非运维人员已禁用，被重新分配的企业邮箱可以主张一个从未链接过的陈旧本地账户；在 JIT 下，一个新的允许域名邮箱会预配一个全新账户，但不获得任何共享 Space 或系统权限 |
| 组/角色提权 | 忽略 IdP 组与角色；在本地推导授予与成员资格 | 目录驱动的角色有待一个显式的核对器设计 |
| BuildMax 访问令牌被窃取 | 短 TTL 加上在用会话与在用用户检查 | 一个绕过中心守卫的路由会绕过撤销，必须使架构测试失败 |
| 刷新 cookie 被窃取 | Secure/HttpOnly/SameSite、轮换、重用检测、精确同源会话端点 | 一个被完全攻破的浏览器源可以冒充该用户行事 |
| OIDC 令牌泄露 | 仅服务端交换；丢弃提供方令牌；脱敏日志/错误/轨迹 | 提供方观察到其自身的登录事务 |
| IdP 故障 | 既有会话继续、OIDC 登录降级、本地管理员应急 | 已过期的普通用户在恢复前无法登录 |
| IdP 禁用用户 | 固定的 OIDC 会话存活期；聊天关联在 `channels.sign_in_window` 之后若无新的登录即停止（[即时通讯渠道 §6](即时通讯渠道.md#6-配对)）；手动 BuildMax 禁用以立即生效 | 仅靠 OIDC 无法满足更短的离职 SLO；聊天访问最长持续到登录窗口结束，而非 OIDC 会话存活期 |
| JWKS 轮换 | 缓存加上一次未知密钥刷新、精确的签发方与算法限制 | 糟糕的提供方发布可能中断登录 |
| 客户端密钥被攻破 | 部署密钥注入、脱敏、重叠轮换运维手册 | 对称客户端认证仍弱于 `private_key_jwt` |
| Portal 中的 XSS | JavaScript 可读存储中无可续期凭据；内存中为短期访问令牌 | XSS 可在当前页面/会话期间行事 |
| 对本地回退的暴力破解 | 既有的外部入口速率限制仍是强制的；本地登录限定为管理员 | 内置的分布式认证速率限制仍然缺失 |
| 审计写入丢失 | 身份链接/解除链接事件是事务性的 | 普通登录审计仍是尽力而为 |
| 原生登录的同意钓鱼：攻击者发起请求并说服某人确认（§14） | 页面加载时不作决定。页面指明客户端及其声称的标签，要求本人核对代码，并警告不要处理别人发来的链接。请求只存活 10 分钟，只有 Portal 会话可以确认，决定会被审计，原生会话连同其标签被列出且可由本人撤销。 | 仍然确认的人会让攻击者获得一个持续到作出确认的登录过期为止的会话，在 SSO 下最长 12 小时；这是 RFC 8628 §5.4 的固有局限 |
| 伪造的客户端标签或平台 | 标签显示为“由客户端上报，未经验证”，任何授权都不依赖它 | 恶意客户端可以声称任何名称 |
| 会话赠送：被猜中或泄露的代码由另一个账户确认 | 约 40 位的代码只存活 10 分钟；查询需要认证且受节流；客户端显示其登录的账户 | 忽略该账户的人会在错误的账户中工作，直到登出 |
| 轮询密钥被窃取 | 256 位密钥，静态存储为哈希，只兑换一次，只由发起请求的客户端发送 | 请求被确认时持有该密钥的人获得会话 |
| 利用被窃取的令牌铸造更多会话 | 只有 `portal` 会话可以确认；作出确认的方法被重新准入；原生会话继承作出确认的会话的过期时间 | Portal 中的 XSS 可以确认攻击者的请求，获得一个比页面活得更久、最长到 Portal 会话过期的会话 |
| 匿名发起洪泛 | 全局最多 500 个待处理请求、强制的外部按 IP 入口限流，且除请求行外不写入任何东西 | 洪泛可能在请求过期前让所有人都无法进行原生登录；没有受信任的客户端地址就没有按来源的限制 |
| 通过查询猜测代码 | 需要认证、可归因，每个账户每 10 分钟每个副本最多 10 个未知代码 | 按副本计数会随副本数倍增；单次猜测的成功概率仍低于 10⁻⁹ |

SSO 本身并不使面向公共互联网的暴露成为受支持的配置。即使本地登录受限，当前缺少内置
登录限流仍是一项已声明的前置条件或被接受的部署界限。

## 16. 备选方案考量

| 方案 | 为何不在首个切片 |
|---|---|
| 认证型反向代理头 | 信任、头部剥离、签发方校验、登出与会话语义因代理而异；身份会变成部署特定的隐式状态 |
| 优先 SAML | 在没有证据表明首个目标需要它的情况下增加协议与元数据复杂度；仅为一个无法提供 OIDC 的有明确名称的 IdP 添加 |
| 同时 OIDC 与 SAML | 在一个集成尚未得到验证之前，就把回调、元数据、密钥/证书与测试矩阵翻倍 |
| 多个 OIDC 签发方 | 需要提供方发现 UX、链接冲突与签发方迁移行为；单个私有部署当前没有已证实的需求 |
| 永久把已验证邮箱当作身份 | 邮箱可能变更或被重新分配；它无法安全地维持账户连续性 |
| 把 IdP 组复制进 JWT 角色 | 使陈旧的外部声明成为授权的拥有者，并绕过即时的本地成员资格变更 |
| JIT 加上自动共享 Space 分配 | 在需求出现之前创建第二个成员资格权限与受保护所有者核对 |
| 存储提供方刷新令牌 | 扩大了密钥保管范围，且仍不能替代 SCIM 来处理目录生命周期；BuildMax 只需要认证结果 |
| 把 Portal 刷新令牌保留在 `localStorage` | 仅为最小化改动而在浏览器中保留可续期的持有者权限 |
| 将 IdP 可用性作为就绪条件 | 把一次登录依赖的故障变成对已认证工作与本地恢复的故障 |
| 在 SSO 切片中实现 SCIM | 它是一个独立的入站预配 API、凭据、核对生命周期与授权界面；仅为 OIDC 无法满足的离职 SLO 才构建 |
| 通过系统浏览器回环重定向进行原生登录（RFC 8252） | 只在浏览器与客户端位于同一主机时可用。SSH 与容器主机仍需第二种设备式机制，而 OIDC 那一段还需要自己的事务、返回处理以及与客户端绑定的回调。Portal 确认用一种机制覆盖两者。 |
| 同时提供回环与设备流 | 两种机制、两套测试矩阵、两组失败模式，而一种机制就能满足所需成果 |
| 使用 IdP 自身的设备授权授予 | 并非所有 IdP 都提供。它会让原生客户端成为需要第二次 IdP 注册的公共 OIDC 客户端，并绕过 Portal 的密码与应急路径。BuildMax 只需要知道是哪个 BuildMax 用户作出了确认。 |
| 从 Portal 复制令牌粘贴到客户端 | 把可续期的持有者凭据放进剪贴板与终端历史，实质上就是 PAT（§7.4、§18） |
| 原生会话有效期独立于作出确认的登录 | 从一个已有 11 小时的 SSO 会话确认，就能在提供方毫不参与的情况下铸造一个新的 12 小时会话，破坏 §7.2 的重新认证界限 |
| 确认时要求近期登录 | 挡不住有意确认的被钓鱼者；增加一种逐步提升的登录模式；继承已经约束了有效期（§14.4） |
| 移除密码与登录代码原生登录 | 会让应急与客户端测试套件依赖 Portal，而相对 `local_login: off` 并无收益（§14.8） |

## 18. 非目标

- 公共多租户 SaaS 注册或组织层级。
- 首个切片中的 SAML、LDAP bind、社交登录、受信任代理头或多个同时存在的 OIDC 提供方。
- SCIM、IdP 组到 Space 的映射、自定义角色或由 IdP 派生的 System Administrator 授予。
- 由 BuildMax 管理的 MFA，或在没有被接受的提供方特定保证策略予以验证的情况下声称 IdP
  使用了 MFA。
- 在没有单独互操作性证据的情况下的提供方级登出、前端通道登出或后端通道登出。
- 自助式身份链接、邮箱变更、账户合并或账户删除。
- PAT、服务账户凭据或无人值守客户端凭据。只有出现一个有明确名称的个人脚本或 API 使用
  场景时才重新考虑 PAT。Space 所属的服务账户已经存在
  （[Space Assistant §6](空间助手.md#6-service-account)）：它是一个 kind 为 `service` 的
  `user` 行，没有邮箱、密码、登录码、SSO 链接或会话，每条登录路径都会拒绝它，它也不持有
  任何凭据。更广泛的自动化主体生命周期归属
  [Agent 执行身份与委托](../proposals/agent-execution-identity-and-delegation.md)。
  现有的 webhook key 不是可以扩展成 PAT 的实现：它有名称、所有者、哈希与创建时间，但没有
  scope、audience、过期时间、最近使用时间或撤销状态，仍只是入站 webhook 凭据。
- 由原生客户端自行向 IdP 认证（回环重定向、IdP 的设备授权授予或嵌入的 IdP 页面）。原生
  客户端只通过 Portal 确认登录（§14），本地 CLI/TUI 与 Desktop 仍独立受支持。
- 一个新的身份提供方数据库实体、动态客户端注册，或一个会改动 `server.yaml` 及其密钥的
  管理 UI。
- 更改 Space 角色策略、所有权规则、邀请语义、TaskRun 权限或 worker 凭据。
- 在普通事件写入仍是尽力而为时声称具有合规级审计。

## 19. 各部署待定输入

方向已被接受。以下列表记录哪些部署事实已经确定，以及哪些仍是剩余资格验证的前置条件：

1. **目标提供方。** **已选定：Okta。** 它提供精确签发方 Discovery、PKCE S256、
   已验证的 `email`/`email_verified`、标准 UserInfo，以及使用 `client_secret_basic`
   的机密客户端。提供方无关的核心按 OpenID Connect Core/Discovery 构建，并用一个确定性
   的对抗式假签发方验证；固定的真实 Okta 端到端及其 `max_age`/密钥重叠细节属于 Phase 3
   资格验证，需要一个可复现的 Okta 测试租户。
2. **预配域名。** JIT 是被接受的 SSO 默认值；究竟哪些邮箱域名属于企业权威，是否有目标
   部署反而需要 `existing_only`？
3. **离职目标。** 12 小时的重新认证界限加上手动的即时禁用是否可接受？若不可接受，所要求
   的结果需要 SCIM、经过验证的后端通道登出或另一个有明确名称的生命周期通道。
4. **本地回退。** 运维人员是否会维护并演练两个本地 System Administrator 凭据，
   `system_admins` 对目标部署而言是否为正确的强制默认值？
5. **原生托管模式。** **已于 2026-10-11 决定：是。** 普通用户必须能够把 CLI 与 Desktop
   连接到 SSO 服务器。维护者只选择了一种机制：由 BuildMax 中介、形态借鉴设备授权、在
   Portal 中确认的请求，不采用回环重定向（§14）。
6. **要求范围。** 哪些目标部署结果需要超出 Portal 浏览器登录与经 Portal 确认的原生登录
   之外的 SSO？企业功能要求
   盘点可用于指导调研，但不能改变此处的安全或互操作性标准。
7. **速率限制。** 在受支持的拓扑中，哪个共享限流器保护剩余的本地登录与 OIDC 事务端点？
   在回答之前，当前的外部速率限制指南仍是强制的。原生登录不依赖它即可自我约束
   （§14.6）；共享限流器将取代其进程内查询节流，而不是再增加一个。
8. **改密码时的会话策略。** 修改密码时应撤销该账户的全部会话、仅撤销以密码认证的会话，
   还是都不撤销？目前修改密码后既有会话仍然有效（见
   [部署认证](../../deploy/authentication.md#passwords)）。由密码 Portal 会话确认的原生
   会话是否遵循同一答案？按 §14.5 它们继承该会话的方法，因此同一规则会覆盖它们。
9. **受信任的客户端地址。** 在入口之后 BuildMax 无法得出客户端 IP，因此确认页面不显示
   网络地址，原生登录的发起也没有按来源的限制（§14.4、§14.6）。一个 `trusted_proxies`
   设置可以让服务器只从入口读取转发地址，从而同时启用这两者以及第 7 项中的登录限流器。
   这是一项跨领域变更，因此要等到该限流器，或某个部署提出需要该地址时再做。

决策证据是一份书面的运维历程、IdP 配置导出或等效的可复现事实、一个约定的入职/离职界限、
一次威胁模型评审，以及一份提供方测试计划。功能对比表或“企业工具通常都有 SSO”是不够的。
