## 1. 接受背景与证据

本记录为私有 BuildMax 部署定义了最小且自洽的企业登录路径。该方向已被接受，且不会把
SSO 置于私有部署 Beta 关卡之前。Phase 1 与 Phase 2 已实现；Phase 3 资格验证（§17、§20）仍待完成。

本设计建立在三类证据之上：

1. 在 `cceba61c` 处审查了仓库行为，包括账户与刷新令牌存储、认证服务与处理器、中心访问
   守卫、Space 成员资格与邀请、审计、配置、Portal 登录/会话代码及其测试。
2. 当前文档表明：SSO 尚不存在、登录没有速率限制、Space 成员资格是资源边界、System
   Administrator 是独立的部署权限，且本地执行不需要 Server。
3. 协议基线是 OpenID Connect Core 与 Discovery、OAuth 2.0 Security Best Current
   Practice，以及本记录所链接的浏览器/原生客户端指南。

方向已定，但目标身份提供方、离职（offboarding）服务级目标以及原生客户端需求仍是各部署
的输入，而非实现应当猜测的细节。它们是每个构建切片的前置条件，列于 §19；它们不会重新
开启是否要构建的问题。

## 2. 核心用户成果

员工应当通过其组织已在运营的身份系统进行认证，只能到达其已存储成员资格所允许的
BuildMax Space，并在其访问权被移除后于既定界限内失去启动或访问工作的能力。运维人员
必须能够区分并恢复身份提供方、BuildMax 账户关联以及 BuildMax 授权中的故障，而无需获得
对 Space 内容的访问权。

因此，接受性问题不是“登录页面是否有一个 SSO 按钮？”，而是：

> 运维人员能否说明：哪个企业身份成为了哪个 BuildMax 账户、它开启了哪个 BuildMax 会话、
> 该账户为何能到达某个 Space、每项权限如何以及何时终止，以及在 IdP 故障期间哪些功能
> 仍可用？

## 3. 已验证的现行约束

以下是当前代码，而非推断出的未来行为：

| 关注点 | 当前事实 | 设计后果 |
|---|---|---|
| 账户身份 | `user` 拥有一个唯一邮箱、可选密码、禁用标志，且没有外部身份链接 | 增加关联；不要用签发方身份重载邮箱 |
| 账户创建 | `CreateUser` 原子地创建账户、个人 Space 与所有者成员资格 | JIT 预配必须在一个事务中保持该不变量 |
| 登录 | `/api/auth/login` 接受密码或运维人员签发的一次性代码 | OIDC 成为另一种开启同一 BuildMax 会话的凭证，而非另一个授权平面 |
| 访问令牌 | HMAC JWT 携带 `sub`、`typ`、`sid`、`jti`、`iat` 与 `exp`；默认有效期为七天 | 缩短持有者窗口，并让 `sid` 指向权威的会话状态 |
| 刷新令牌 | 以 `session_id` 分组的、不透明、经哈希、可轮换的行；轮换会重置 30 天的不活动窗口 | 增加绝对过期时间与认证来源；保留轮换 |
| 撤销 | 登出/撤销会停用刷新行，但已签发的访问 JWT 在过期前仍可使用 | 需要持久化的会话检查以实现即时登出与提供方会话撤销 |
| 账户禁用 | 每个已认证路由都会重新读取 `user.disabled_at` | 通过 BuildMax 禁用实现的离职在用户 API 边界上即时生效 |
| Portal 存储 | 访问令牌与刷新令牌存储在 `localStorage` 中 | 浏览器流程必须停止把可续期凭据暴露给 JavaScript |
| 授权 | 中心守卫从数据库状态推导 Space 角色与 System Administrator 授予 | 在首个切片中忽略 IdP 的角色/组声明 |
| 邀请 | Space 邀请针对一个已经存在的账户 | `existing_only` 入职可在首次 SSO 登录前发出邀请；JIT 用户只有在预配之后才可被邀请 |
| 审计 | 存在登录与权限事件，但写入通常是尽力而为（best-effort） | 在作出合规性声明之前，身份关联变更需要更强的原子记录 |
| 部署 | Portal 与 API 通常共享一个公共源（origin）；多副本 Server 使用共享的数据库/Redis | 回调与临时浏览器状态必须跨副本工作，不依赖进程本地亲和性 |
| 本地界面 | CLI/TUI 与 Desktop 在没有任何 Server 的情况下本地运行；登录模式是可选的 | 企业 SSO 不得使本地执行依赖于 Server |

IdP 禁用某人这一事件当前对 BuildMax 不可见。仅靠 OIDC 并不提供目录同步或即时取消预配的
通道。任何在没有有界重新认证策略或预配集成的情况下声称“SSO 解决了离职者问题”的设计，
都是在作出协议并不支持的主张。

## 4. 最小设计

已接受的方向是：

1. **每个部署一个原生 OIDC 提供方。** BuildMax Server 是一个机密依赖方（confidential
   relying party），使用带 PKCE 的 Authorization Code Flow。SAML、受信任的代理头以及多个
   同时存在的签发方不在首个实现中；§8a 记录了日后如何在不返工的情况下添加 SAML。
2. **OIDC 只证明认证。** 经过验证的 `(issuer, subject)` 对标识一个外部的人。BuildMax
   仍然拥有账户、会话、System Administrator 授予、Space 成员资格、角色以及每一项资源
   授权决策。
3. **通过经过验证的身份来关联，绝不通过角色声明。** 一条新的 `external_identity` 记录把
   OIDC subject 绑定到一个已存在的 BuildMax 用户。经过验证的邮箱只用于首次关联或可选的
   JIT 创建；后续登录通过 `(issuer, subject)` 解析。
4. **SSO 默认即时预配；原生保留由运维人员创建的账户。** 在 SSO 部署中，对一个未知但属于
   允许域名的邮箱，首次通过验证的登录会自动创建普通账户与个人 Space（`provisioning:
   jit`）。JIT 不授予任何共享 Space 成员资格或系统角色，且空的 `allowed_email_domains`
   列表会拒绝 JIT，而不是表示“所有域名”。运维人员也可以改为设置 `existing_only`，只接受
   其预先创建的账户。原生部署（`oidc.enabled: false`）完全没有外部登录：System
   Administrator 像今天一样创建并分配账户。
5. **签发 BuildMax 凭据，而非 IdP 凭据。** 回调会校验并丢弃提供方令牌，然后开启与其他
   所有登录相同的 BuildMax 会话模型。提供方令牌绝不会到达 Portal、CLI、Desktop、Agent
   输入、日志或轨迹。
6. **把隐含的会话变成真正的权限记录。** `sid` 命名一条 `auth_session` 行，在已认证请求中
   与用户一起检查。因此登出、管理员撤销、绝对过期以及日后的提供方登出都能立即使一个
   已签发的 BuildMax 访问令牌失效。
7. **使用适合浏览器的凭据投递方式。** Portal 在内存中保留一个短期的 BuildMax 访问令牌，
   并把一个可轮换的刷新令牌保存在 Secure、HttpOnly 的 cookie 中。对于 OIDC 与本地回退
   登录，可续期凭据都离开 `localStorage`。
8. **诚实地为仅靠 IdP 的离职设定界限。** OIDC 会话有一个固定的最大存活时间，超过后必须
   再经由提供方返回。推荐的初始值为 12 小时，BuildMax 访问令牌默认为 15 分钟。即时的
   入职/离职（joiner/leaver）自动化需要日后的 SCIM 或提供方特定的生命周期集成。
9. **保留一条有审计的应急（break-glass）路径。** 在 SSO 部署中，本地密码/登录代码认证
   默认仅限 System Administrator。直接操作数据库的 `buildmax-server` 引导命令仍是恢复的
   根基。
10. **用两个正交开关而非一个模式枚举在原生与 SSO 之间切换。** `oidc.enabled` 开启或关闭
    外部登录；`local_login`（`all | system_admins | off`）管理谁仍可使用本地用户名与密码
    平面。部署的姿态是二者经过验证的组合——原生是 `oidc.enabled: false` 配 `local_login:
    all`；SSO 是 `oidc.enabled: true` 配 `local_login: system_admins`——并在管理员状态
    界面上报告。不引入单独的 `auth_mode` 字段：因为应急要求即便在 SSO 下本地登录对管理员
    仍然可用，单一的 native/sso 枚举无法独立存在，还会与 `local_login` 重复。保持这两个轴
    正交，也正是让日后的协议（§8a）成为第三个独立轴、而非一个新枚举值的原因。

本设计有意只引入两个持久概念：`external_identity`，因为签发方身份无法安全地寄存在
`user.email` 上；以及 `auth_session`，因为既有的 `sid` 已经命名了一个会话，而该会话的
撤销与过期在其他方面并不权威。其余一切都复用当前的账户、Space、令牌与审计模型。

## 5. 身份与账户关联

### 5.1 稳定键

外部身份键是精确的 OIDC `iss` 加 `sub` 对。两者都是区分大小写的协议值。邮箱、姓名、
首选用户名、组以及租户标签都是属性，绝非身份键。

回调在查询账户之前先校验 ID Token。它至少校验签名、精确的签发方、受众、适用时的授权方
（authorized party）、过期时间、签发时间界限、nonce 以及授权事务。首次关联额外要求一个
语法有效的 `email` 且 `email_verified=true`。如果提供方通过 UserInfo 返回邮箱，则
UserInfo 的 `sub` 必须等于 ID Token 的 `sub`。

### 5.2 关联算法

校验之后，一个事务按顺序应用以下规则：

1. 如果 `(issuer, subject)` 已有链接，使用该用户。邮箱变更不能把身份转移到另一个账户。
2. 拒绝其用户已被禁用的链接。启用该用户是运维人员的显式决策。
3. 如果不存在链接，且某个在用用户拥有该已验证邮箱，只有当该用户对此签发方没有身份时才
   进行链接。这是为运维人员创建的账户提供的迁移路径。
4. 如果该邮箱的账户已链接到此签发方的另一个 subject，拒绝并要求运维人员调查。绝不自动
   替换任一链接。
5. 如果不存在账户，`existing_only` 以一条通用的“未被授权访问此部署”响应拒绝。`jit` 则
   原子地创建用户、个人 Space、所有者成员资格与身份链接。
6. 只有在账户/链接事务提交之后，BuildMax 才可创建会话。

签发方是受运维人员信任的，但邮箱匹配仍是一次安全敏感的一次性链接。`jit` 是默认值，因为
被接受的结果是：一次经过验证的企业登录为其自身预配账户；其安全性来自必须非空的
`allowed_email_domains` 列表，而非来自运维人员预先为每个账户命名。空列表会拒绝 JIT，
而不是表示“所有域名”，且域名比较是规范化且精确的，而非字符串后缀检查。`existing_only`
仍可供那些更希望由运维人员为提供方可能主张的每个账户命名的部署使用；它以一条通用的
“未被授权访问此部署”响应拒绝未知邮箱。无论哪种方式，上面的规则 1–4 仍先行适用，因此
JIT 绝不替换或移动既有的 subject 链接。

### 5.3 属性漂移与恢复

`external_identity.last_seen_email` 与可选的显示名快照会在成功登录后更新。首个切片不会
自动改写 `user.email`：它已经是管理与邀请所使用的本地账户句柄，安全地更改它需要冲突与
通知语义。Portal 管理界面应当显示不一致，以便运维人员进行核对。

System Administrator 可以列出某个用户的身份链接。只有在用户被禁用时才允许解除链接，解除
会与删除一起原子地记录，且不会删除用户、成员资格、工作或审计历史。随后运维人员纠正
外部目录或本地账户状态，并在新的首次关联之前重新启用该用户。首个切片中不存在自助式的
链接或解除链接。

## 6. Space 成员资格、首次登录与邀请

OIDC 不分配 Space 权限。

| 历程 | 结果 |
|---|---|
| `existing_only` 入职 | System Administrator 创建账户；Space 所有者可在首次登录前邀请它；首次经过验证的 OIDC 登录通过邮箱链接；用户接受既有邀请 |
| JIT 入职 | 首次经过验证的 OIDC 登录创建账户与个人 Space；Space 所有者此后可邀请它 |
| 既有成员启用 SSO | 首次经过验证的 OIDC 登录链接当前账户；每一项既有成员资格保持不变 |
| IdP 邮箱变更 | 登录继续通过 `(issuer, subject)` 进行；成员资格不移动；管理界面显示属性漂移 |
| IdP 组变更 | 在首个切片中无影响 |
| 成员资格移除 | 下一次 Space 授权读取会拒绝该 Space；用户的其他 Space 与会话仍然有效 |
| 账户禁用 | 每个用户 API 请求都被拒绝；成员资格为来源留存，并在账户被有意启用时恢复 |

这保留了成员资格设计中账户存在性与 Space 邀请的分离。它还避免了在任何目标组织表明需要
之前引入组映射核对器、受保护所有者规则以及角色的第二个事实来源。

## 7. BuildMax 会话生命周期

### 7.1 单一会话模型

每一次密码、登录代码与 OIDC 认证都会创建一个 `auth_session`。该记录拥有：

- 用户与公开的 `sid`；
- 客户端平台；
- 认证方法（`password`、`login_code` 或 `oidc`）；
- 当方法为 OIDC 时的外部身份；
- 创建时间、最后活动时间、绝对过期时间与撤销时间。

刷新令牌行隶属于此会话，而不是会话本身。访问 JWT 的校验要求 `typ=access` 且 `sid`
非空，随后中心守卫同时检查在用用户与在用会话。Space 角色与授予仍是后续的数据库读取，
不进入 JWT。

### 7.2 有效期与重新认证

用于接受性测试的推荐默认值为：

| 边界 | 默认值 | 含义 |
|---|---:|---|
| BuildMax 访问令牌 | 15 分钟 | 当会话状态检查不可用或被日后某个路由有意绕过时，持有者重放的最大时长 |
| 刷新不活动 | 30 天 | 当前可轮换令牌的可用窗口 |
| 本地人类会话绝对存活期 | 90 天 | 一次在用的本地登录不能永久续期 |
| OIDC 会话绝对存活期 | 12 小时 | BuildMax 要求再次进行提供方授权之前的最大间隔 |

运维人员可以调整这些值，但管理员状态界面会报告生效值，并对多天的访问令牌或无界会话
发出警告。新的 OIDC 授权在配置时使用 `max_age` 并校验 `auth_time`，因此重启一个
BuildMax 会话不会悄无声息地接受任意陈旧的提供方认证。

仅靠 OIDC 的取消预配是有界的，而非即时的：在没有 SCIM 或经过验证的提供方登出事件的
情况下，仅在 IdP 被禁用的人可能会保留当前的 BuildMax 会话，直到其 OIDC 绝对过期时间，
再加上至多剩余的访问令牌窗口。运维手册必须说明这个数字。

### 7.3 Portal 凭据处理

Portal 仅以 cookie 的形式接收当前可轮换的 BuildMax 刷新令牌：

- 在受支持的部署中为 `Secure` 与 `HttpOnly`；
- 可续期会话 cookie 采用 `SameSite=Strict`；
- 限定于 Portal 会话端点；
- 绝不在 JSON 中返回；
- 每次刷新时替换，登出时清除。

Portal 在登录与页面重新加载后获得一个短期访问令牌，将其保存在内存中，并继续把它作为
当前的 Bearer 凭据发送。这在去除 JavaScript 可读存储中的可续期权限的同时，保持了既有的
API 与 WebSocket 授权形态。本地密码/登录代码的 Portal 登录使用相同的投递路径，因此不
存在一个更弱的“回退”会话。

建立会话的 cookie 端点要求精确的同源 `Origin` 校验、适用时采用 JSON POST，且不使用宽松
的 CORS。这是在 SameSite cookie 之外的附加措施，而非其替代。

### 7.4 登出与撤销

BuildMax 登出总是在报告成功之前撤销 `auth_session`、刷新令牌与 Portal cookie。随后中心
守卫会拒绝该 `sid` 已签发的访问令牌。

首个切片的含义是“登出 BuildMax”，而非“在提供方处登出每一个应用”。如果 Discovery
公布了 `end_session_endpoint`，RP-Initiated Logout 可在取得互操作性证据后添加，并且即便
提供方重定向失败也会先执行本地撤销。前端通道（front-channel）与后端通道（back-channel）
登出是独立的可选能力，并不由 OIDC 登录隐含。

## 8. OIDC 协议与浏览器流程

BuildMax 仅使用带机密 Server 客户端的 Authorization Code Flow：

1. Portal 带着一个相对返回路径导航到 `GET /api/auth/oidc/start`。
2. Server 生成事务专用的 `state`、`nonce` 与 PKCE verifier，发送 `S256`，并把这些值连同
   返回路径绑定到浏览器中一个短期、Secure、HttpOnly、SameSite=Lax、受完整性保护的 cookie
   里。
3. 浏览器带着作用域 `openid email profile` 与一个从 `public_base_url` 派生的、精确注册的
   重定向 URI 访问被发现的授权端点。
4. 回调校验 cookie 与 `state`，从 Server 侧交换 code，校验 ID Token 与 `nonce`，并按
   §5.1 所述可选地调用 UserInfo。
5. 执行关联事务与会话创建。随后丢弃提供方的访问令牌与 ID Token；BuildMax 不请求
   `offline_access`。
6. Server 设置 BuildMax 刷新 cookie，并重定向到一个固定的 Portal 完成路由。URL 中不出现
   任何提供方令牌、BuildMax 令牌、邮箱或错误细节。
7. Portal 用该 cookie 换取一个内存中的访问令牌与当前用户，然后应用经过校验的相对返回
   路径。

该临时 cookie 是自包含的，并用一个从必需的部署 JWT 密钥派生并作域分隔的密钥进行完整性
保护。它可以包含 PKCE verifier，因为 TLS、Secure 与 HttpOnly 在传输中以及对页面脚本都
保护它；其完整性防止浏览器调换事务值。这避免了进程本地或仅依赖 Redis 的事务存储，因此
任何 Server 副本都可以接收回调。该 cookie 最多在十分钟后过期，并在每一个回调结果上被
清除。重放它无法重放提供方已经消费过的授权 code。

实现必须使用一个有维护的 OIDC 库来处理发现、令牌交换、JOSE 校验与声明规则。手写的 JWT
或 OAuth 解析不是可接受的小型实现。

规范性参考：

- [OpenID Connect Core 1.0](https://openid.net/specs/openid-connect-core-1_0.html)
- [OpenID Connect Discovery 1.0](https://openid.net/specs/openid-connect-discovery-1_0.html)
- [OAuth 2.0 Security Best Current Practice (RFC 9700)](https://www.rfc-editor.org/info/rfc9700/)
- [OAuth 2.0 for Browser-Based Applications (RFC 10017)](https://www.rfc-editor.org/rfc/rfc10017.html)
- [RP-Initiated Logout 1.0](https://openid.net/specs/openid-connect-rpinitiated-1_0.html)

## 8a. 可扩展性与未来协议

SAML 与任何其他企业登录协议都不在首个切片内，且今天不存在任何 SAML 字段、列、配置块或
`auth_method` 值。本节记录预期的扩展路径，以便日后添加时是有意的新增而非返工——它**不**
授权现在构建其中任何部分，且下面的任何内容都不应在一个有明确名称、确有需求的部署出现
之前实现。

本设计在协议上可扩展，因为认证与授权是分开的轴（§4、§13）。只有处理器层是协议特定的；
外部身份键、`auth_session` 模型、凭据投递与中心守卫都不是。因此日后的协议可在不引入第四
个概念的情况下嵌入三个既有轴：

1. **认证轴上的一个新值。** `auth_session.auth_method` 增加 `saml`。`local_login` 与 OIDC
   设置保持不变，因为“谁可以使用本地登录”与配置了哪种外部协议无关。这正是 §4 把
   native/SSO 保持为正交开关而非一个 `auth_mode` 枚举的原因：协议是某个轴上的一个值，
   而非一个新的顶层模式。
2. **`external_identity` 上的一个协议判别器。** 稳定键从 OIDC 的 `(issuer, subject)`
   泛化为 `(protocol, issuer, subject)`，其中 SAML 提供 `(saml, IdP EntityID, NameID)`。
   该判别器现在**不**添加——在只有一种协议时，它会是一个没有具体需求的字段——但 §9.1 中
   的唯一性约束被记录为“在所配置的签发方范围内”，以便日后的迁移是增加一列而非重新解释
   既有行。要求一个持久的、非瞬态的 `NameID`；瞬态 NameID 不能作为稳定的账户键。
3. **一个并列的提供方配置块。** 一个 `saml:` 块与 `oidc:` 并列，拥有自己的元数据 URL
   或 IdP 证书、实体 ID、NameID 格式以及断言签名要求，并以与 OIDC 块相同的方式校验。
   断言校验使用一个有维护的 SAML 库，绝不手写 XML 或签名解析，与上文的 OIDC 库规则一致。

有两个问题被明确推迟到那次日后的评审，而非在此回答：同时运行多于一个外部协议或签发方
（提供方选择的 UX、链接冲突与签发方迁移行为——见 §16），以及一个无法使用 OIDC 的目标
IdP 是否足以证明采用 SAML 的正当性。在此之前，本记录中单一外部签发方的假设一直成立。

## 9. 数据模型与归属

### 9.1 `external_identity`

| 字段 | 要求 |
|---|---|
| `id`、`public_id` | 内部键加上常规的 BuildMax 公开身份 |
| `user_id` | 既有的 BuildMax 账户；不级联删除，因为用户不会被删除 |
| `issuer` | 精确的已验证签发方，区分大小写 |
| `subject` | 精确的已验证 subject，区分大小写 |
| `last_seen_email` | 供运维人员诊断的已验证属性快照，链接之后不用于查找 |
| `last_seen_name` | 可选的显示名快照 |
| `last_login_at`、`created_at` | 生命周期证据 |

唯一性约束为 `(issuer, subject)` 与 `(issuer, user_id)`，作用域限定在所配置的单一签发方
之内。后者防止一个账户悄无声息地从该签发方累积两个 subject。第二种协议或签发方会在这些
键之前增加一个判别器列，而非重新解释既有行（§8a）。该行不包含任何提供方访问令牌、ID
Token、组列表、角色或 Space ID。

### 9.2 `auth_session`

| 字段 | 要求 |
|---|---|
| `id`、`public_id` | 内部键加上公开的 `sid` |
| `user_id` | 该会话所行使权限的账户 |
| `external_identity_id` | 可空；仅在 OIDC 认证时设置 |
| `platform`、`auth_method` | 所使用的客户端与凭证 |
| `created_at`、`last_seen_at` | 会话生命周期元数据 |
| `absolute_expires_at`、`revoked_at` | 权威的有效性 |

`user_refresh_token` 引用 `auth_session`，只保留令牌轮换状态与过期时间。会话行不是第三种
凭据。它是已签发的 `sid` 当前所缺失的权威状态。

### 9.3 归属

- `internal/core/identity` 拥有类型、与校验无关的存储契约、会话状态以及永久审计动作
  名称。
- `internal/service/identity` 拥有关联、预配、认证、会话创建与撤销工作流。
- `internal/infra/db` 拥有这两张单数命名的表，以及创建带个人 Space 与身份链接的 JIT
  用户的事务。
- `internal/server/handlers/auth` 拥有 OIDC 的 HTTP 状态、cookie、重定向、提供方协议
  适配以及 BuildMax 令牌签发。
- `internal/server/access` 仍是唯一的请求认证与授权汇聚点。
- Portal 只呈现方法并在内存中存储账户状态；它绝不解析 ID Token 或映射声明。

不引入任何新的“组织”、“租户”、“IdP 组”或 SSO 专用的用户类型。一个私有部署、一个外部
签发方、一个 BuildMax 账户以及一个或多个 Space 已经表达了所需的归属边界。

## 10. HTTP API 与 Portal 变更

拟议的公开路由：

```text
GET  /api/auth/methods
GET  /api/auth/oidc/start
GET  /api/auth/oidc/callback

POST /api/auth/portal/login
POST /api/auth/portal/session
POST /api/auth/portal/logout

GET    /api/admin/users/{user_id}/identities
DELETE /api/admin/users/{user_id}/identities/{identity_id}
```

`GET /api/auth/methods` 只返回本地登录与 OIDC 是否可用，以及运维人员设置的 OIDC 显示
标签。它不返回任何匿名调用方不需要的签发方元数据、客户端标识、域名允许列表或策略细节。

这三个 Portal 端点是位于当前 `/api/auth/login`、`/api/auth/token/refresh` 与
`/api/auth/logout` 所使用的同一身份服务之上的凭据投递适配器。既有路由仍作为原生客户端
的 JSON 传输；Portal 路由绝不序列化刷新令牌。凭据校验与会话状态转换不被重复实现。

Portal 的登录页面读取方法文档，只显示已配置的选项。SSO 按钮是导航，而非打开一个嵌入式
登录框。在回调或重新加载之后，认证上下文调用 Portal 会话端点，而不是从 `localStorage`
注水（hydrate）持有者凭据。UI 会区分：

- 提供方不可用或配置错误；
- 浏览器事务已过期，必须重新开始；
- 经过验证的身份未被授权访问此部署；以及
- 被链接的 BuildMax 账户已被禁用。

详细的提供方错误与声明保留在带请求关联 ID 的、经脱敏的 Server 日志中，而非浏览器响应中。

## 11. 配置与部署

在本切片中保留当前的顶层认证设置，而不是顺带重构整个 `server.yaml`。原生与 SSO 的姿态是
既有平面（`local_login`）与新的 `oidc` 块经过验证的组合（§4 决策 10）；不存在单独的
`auth_mode` 字段。增加一个枚举和一个 OIDC 块：

```yaml
jwt_secret: ""                 # existing; normally injected
access_token_ttl: 15m          # existing field, proposed safer default
refresh_token_ttl: 720h        # existing inactivity window
session_absolute_ttl: 2160h    # new; local/login-code/password sessions
local_login: all               # all | system_admins | off; migration default

oidc:
  enabled: false               # false => native: operator-created accounts only
  display_name: Company SSO
  issuer: https://id.example.com
  client_id: buildmax
  client_secret: ""            # inject with BUILDMAX_OIDC_CLIENT_SECRET
  provisioning: jit            # jit (default) | existing_only
  allowed_email_domains: []    # required and non-empty for jit
  session_max_age: 12h
```

记录在案的两种姿态为：

- **原生（默认）：** `oidc.enabled: false` 配 `local_login: all`。System Administrator
  像今天一样通过 `buildmax-server` 引导命令创建并分配账户；没有外部登录。
- **SSO：** `oidc.enabled: true` 配为应急推荐的 `local_login: system_admins`。
  `provisioning: jit` 会在来自 `allowed_email_domains` 地址的首次经过验证的登录时自动
  创建账户；设置 `existing_only` 则只接受预先创建的账户。

当 `oidc.enabled` 为 false 时，`provisioning` 与 `allowed_email_domains` 被忽略；当
`oidc.enabled: true` 且 `provisioning: jit` 而 `allowed_email_domains` 为空时，启动会
拒绝。

回调精确为 `<public_base_url>/api/auth/oidc/callback`。启用 OIDC 时 `public_base_url`
是必需的，且必须为 HTTPS，除非处于显式的回环（loopback）开发模式。它绝不从 `Host` 或
转发头派生，从而避免攻击者影响重定向的构造。

`local_login` 的含义：

| 值 | 密码/登录代码会话策略 |
|---|---|
| `all` | 当前行为；在运维人员选择启用 SSO 强制之前的迁移默认值 |
| `system_admins` | 与 OIDC 搭配推荐；经过验证的本地凭据只为在用的 System Administrator 开启会话 |
| `off` | 没有本地 HTTP 登录；启动会警告恢复需要更改配置并重启 |

除非 `local_login: all`，否则 `allow_signup` 无效；JIT 属于经过验证的 OIDC 路径，不会
重新开启未经验证的邮箱注册。

客户端密钥是首个切片中唯一的新密钥。它在部署时注入，在每个配置/状态响应中脱敏，绝不
传递给 worker，并通过替换挂载的密钥与滚动 Server 副本来轮换。初始的客户端认证方法是
`client_secret_basic`；只有在目标 IdP 或威胁模型要求时才添加 `private_key_jwt`。

## 12. 失败、轮换、恢复与审计

### 12.1 发现与 JWKS

所配置的签发方是唯一的 URL 信任根。Discovery 必须返回完全相同的签发方，以及 HTTPS 的
授权、令牌、（使用时的）UserInfo 与 JWKS 端点。请求参数绝不提供签发方或端点，从而把
SSRF 限定在运维人员的配置范围内。

Discovery 与 JWKS 遵循缓存有效期。未知的签名 `kid` 会在拒绝之前触发一次立即的 JWKS
刷新，以支持正常的提供方密钥重叠。签名算法被限制为库与提供方元数据安全支持的那些；
`none` 以及把客户端密钥用作 ID Token HMAC 密钥都会被拒绝。

网络获取失败不会使 `/readyz` 失败：既有的 BuildMax 会话与本地工作仍然可用。如果不存在
可用的缓存元数据/密钥，新的 OIDC 启动或回调会返回一个可重试的 503。管理员系统视图会
报告已配置、可用/降级、最近一次成功的元数据/JWKS 刷新，以及一条经脱敏的最近错误。

### 12.2 轮换与配置变更

| 变更 | 所需行为 |
|---|---|
| 提供方签名密钥 | 自动 JWKS 刷新；在测试中验证重叠 |
| OIDC 客户端密钥 | 在旧密钥仍有效时于 IdP 处添加新密钥、滚动 BuildMax、验证登录、停用旧密钥；否则接受一段有界的登录中断 |
| BuildMax JWT 密钥 | 当前的访问 JWT 失效；在用的刷新/会话行可铸造替代；记录并测试运维流程 |
| 签发方变更 | 视为一个不同的身份命名空间；绝不按 subject 或邮箱悄无声息地重新链接；既有的 BuildMax 会话存续至正常撤销/过期 |
| OIDC 被禁用 | 停止新的 OIDC 登录；不悄无声息地撤销当前的 BuildMax 会话 |

因此更改签发方需要一个显式的迁移计划：在用户通过新签发方链接之前保留旧签发方，或在
运维人员控制下禁用/解除链接/重新启用账户。为平滑该迁移而支持两个在用签发方是日后的
需求，不隐藏在单提供方切片里。

### 12.3 应急与 IdP 故障

在强制执行 `local_login: system_admins` 之前，运维手册会创建至少两个 System
Administrator 账户，其强本地密码通过运维人员的应急凭据流程保存，并验证一次登录。当 IdP
或 HTTP 管理界面失效时，既有的直接操作数据库的创建、登录代码、授予与撤销命令仍然可用。

IdP 故障有如下已声明的结果：

- 既有有效的 BuildMax 会话继续；
- 新的 OIDC 会话与已过期的 OIDC 会话无法启动；
- 本地 System Administrator 恢复仍然可用；
- 本地 CLI/TUI 与 Desktop 直连模式不受影响；
- 就绪状态保持健康，而管理员诊断显示 OIDC 降级。

### 12.4 审计

对于成功的会话，复用 `user.login` 并带 `oidc` 细节。为 `user.external_identity_linked`
与 `user.external_identity_unlinked` 添加永久动作；JIT 创建还会记录既有的 `user.created`
动作并带 OIDC 细节。身份链接/解除链接及其审计行必须在同一个数据库事务中提交，因为它们
改变了谁能成为一个账户。登录成功与运营性失败可保留当前的尽力而为策略，并在运维文档中
说明已知的局限。

匿名回调失败仍是结构化的运营日志，而非以不受信任的邮箱或声明为键的审计事件。日志包含
一个关联 ID 与一个有界的原因类别，绝不包含授权 code、提供方令牌、客户端密钥、PKCE
verifier、nonce、cookie 或原始声明集。审计导出与保留保持其既有权限与策略。

## 13. 授权与 Agent 执行的影响

OIDC 改变的是谁能开启一个人类会话，而非该会话可以做什么。

- 每个 Space 路由继续解析当前成员资格与角色。
- System Administrator 仍是一项显式的 BuildMax 授予；任何 IdP 组都不能创建它。
- 移除一项 Space 成员资格在下一次 Space 请求时生效，不会终止此人的会话或其他成员资格。
- 禁用一个 BuildMax 账户会立即拒绝用户请求、撤销其会话、使已排队但尚未启动的工作失败，
  并像当前代码那样暂停计划任务。
- 一个已在其运行范围凭据下执行的 TaskRun 不会被 SSO 或成员资格变更悄无声息地取消。它的
  外部副作用无法撤销，其结果仍归 Space 所有。需要停止它的运维人员使用既有的取消路径。
- 继续、重试或启动后续工作会重新检查在用账户与当前 Space 权限，而不是继承旧运行的调用方
  访问权。

SCIM 或未来的组核对必须保持这些边界。特别是，目录组不能成为一个绕过
`internal/core/space.Allows` 的令牌声明，且核对绝不能使一个普通 Space 没有所有者。

## 14. CLI 与 Desktop 范围

首个被接受的切片是**仅 Portal 浏览器 SSO**。

- CLI/TUI 与 Desktop 的本地/直连模式完全独立于 Server 与 IdP 的可用性。
- 它们既有的密码/登录代码 Server 登录只有在 `local_login` 允许该账户时才可继续。在推荐的
  `system_admins` 设置下，普通的已连接原生客户端在首个切片中无法使用托管的 Server 模式。
- Desktop 中不嵌入任何 IdP 页面，原生客户端不收集任何 IdP 密码。

只有在一个有明确名称的部署要求已连接的 CLI/Desktop 之后，才添加原生 SSO。首选路径是在
系统浏览器中使用带 PKCE 的 Authorization Code 并采用回环重定向，遵循
[RFC 8252](https://www.rfc-editor.org/info/rfc8252/)。一个无浏览器的终端可能足以证明
采用由 BuildMax 中介的设备流（device flow）的正当性，遵循
[RFC 8628](https://www.rfc-editor.org/info/rfc8628/)，包括短期代码、显式批准、轮询界限
与速率限制。不要投机地同时实现两者；应根据目标环境选择。

这两条路径都不是 PAT 或服务账户设计。无人值守客户端仍是客户端凭据提案中的独立决策。

## 15. 威胁模型

| 威胁或失败 | 所需控制 | 残余界限 |
|---|---|---|
| 登录 CSRF 或 code 注入 | 事务专用的 state、nonce、PKCE S256、浏览器绑定、精确回调 | 被攻破的浏览器配置文件仍被信任为该用户 |
| 授权 code 被截获 | 服务端交换、机密客户端、PKCE；Portal 存储中无 code/令牌 | IdP 或 TLS 被攻破不在 BuildMax 范围内 |
| 签发方混淆（mix-up） | 单一配置的签发方、精确的 Discovery/ID Token 签发方与受众校验 | 多签发方支持需要一次新的评审 |
| 开放重定向 | 仅在受保护的事务状态内存储一个经过校验的相对 Portal 路径 | 不支持登录后的外部重定向 |
| 通过邮箱匹配的账户接管 | 已验证邮箱、JIT 必需的非空允许域名列表、原子唯一性、绝不替换既有 subject 链接 | 除非运维人员已禁用，被重新分配的企业邮箱可以主张一个从未链接过的陈旧本地账户；在 JIT 下，一个新的允许域名邮箱会预配一个全新账户，但不获得任何共享 Space 或系统权限 |
| 组/角色提权 | 忽略 IdP 组与角色；在本地推导授予与成员资格 | 目录驱动的角色有待一个显式的核对器设计 |
| BuildMax 访问令牌被窃取 | 短 TTL 加上在用会话与在用用户检查 | 一个绕过中心守卫的路由会绕过撤销，必须使架构测试失败 |
| 刷新 cookie 被窃取 | Secure/HttpOnly/SameSite、轮换、重用检测、精确同源会话端点 | 一个被完全攻破的浏览器源可以冒充该用户行事 |
| OIDC 令牌泄露 | 仅服务端交换；丢弃提供方令牌；脱敏日志/错误/轨迹 | 提供方观察到其自身的登录事务 |
| IdP 故障 | 既有会话继续、OIDC 登录降级、本地管理员应急 | 已过期的普通用户在恢复前无法登录 |
| IdP 禁用用户 | 固定的 OIDC 会话存活期；手动 BuildMax 禁用以立即生效 | 仅靠 OIDC 无法满足更短的离职 SLO |
| JWKS 轮换 | 缓存加上一次未知密钥刷新、精确的签发方与算法限制 | 糟糕的提供方发布可能中断登录 |
| 客户端密钥被攻破 | 部署密钥注入、脱敏、重叠轮换运维手册 | 对称客户端认证仍弱于 `private_key_jwt` |
| Portal 中的 XSS | JavaScript 可读存储中无可续期凭据；内存中为短期访问令牌 | XSS 可在当前页面/会话期间行事 |
| 对本地回退的暴力破解 | 既有的外部入口速率限制仍是强制的；本地登录限定为管理员 | 内置的分布式认证速率限制仍然缺失 |
| 审计写入丢失 | 身份链接/解除链接事件是事务性的 | 普通登录审计仍是尽力而为 |

SSO 本身并不使面向公共互联网的暴露成为受支持的配置。即使本地登录受限，当前缺少内置
登录限流仍是一项已声明的前置条件或被接受的部署界限。

## 16. 备选方案考量

| 方案 | 为何不在首个切片 |
|---|---|
| 认证型反向代理头 | 信任、头部剥离、签发方校验、登出与会话语义因代理而异；身份会变成部署特定的隐式状态 |
| 优先 SAML | 在没有证据表明首个目标需要它的情况下增加协议与元数据复杂度；仅为一个无法提供 OIDC 的有明确名称的 IdP 添加 |
| 同时 OIDC 与 SAML | 在一个集成尚未得到验证之前，就把回调、元数据、密钥/证书与测试矩阵翻倍 |
| 多个 OIDC 签发方 | 需要提供方发现 UX、链接冲突与签发方迁移行为；单个私有部署当前没有已证实的需求 |
| 永久把已验证邮箱当作身份 | 邮箱可能变更或被重新分配；它无法安全地维持账户连续性 |
| 把 IdP 组复制进 JWT 角色 | 使陈旧的外部声明成为授权的拥有者，并绕过即时的本地成员资格变更 |
| JIT 加上自动共享 Space 分配 | 在需求出现之前创建第二个成员资格权限与受保护所有者核对 |
| 存储提供方刷新令牌 | 扩大了密钥保管范围，且仍不能替代 SCIM 来处理目录生命周期；BuildMax 只需要认证结果 |
| 把 Portal 刷新令牌保留在 `localStorage` | 仅为最小化改动而在浏览器中保留可续期的持有者权限 |
| 将 IdP 可用性作为就绪条件 | 把一次登录依赖的故障变成对已认证工作与本地恢复的故障 |
| 在 SSO 切片中实现 SCIM | 它是一个独立的入站预配 API、凭据、核对生命周期与授权界面；仅为 OIDC 无法满足的离职 SLO 才构建 |

## 17. 交付与验证

方向已被接受，但在一个具体部署确定 §19 中的 Phase 0 输入之前，不创建任何 backlog 条目。
下面的每个切片一旦其依赖与验收标准确定，就成为一个可独立评审的 backlog 任务：

### Phase 0 —— 证据与决策

- 命名首个受支持的 IdP，并记录其 Discovery、声明、客户端认证、登出与测试环境行为。
- 确认离职界限、JIT 允许域名列表（若某部署需要则为 `existing_only`）、本地回退模式，
  以及仅 Portal 的范围是否可用。
- 对确切的部署进行威胁建模，并批准配置契约。

### Phase 1 —— 会话与 Portal 凭据基础

- 添加 `auth_session`，要求在用的 `sid`，添加绝对过期，并把当前的会话列举/撤销迁移到
  其上。
- 缩短默认访问令牌有效期。
- 将既有密码与登录代码流程的 Portal 刷新投递迁移到 HttpOnly cookie 适配器；从
  `localStorage` 中移除认证令牌。
- 在模式迁移期间强制既有会话重新认证，而非臆造无法验证的认证来源。

### Phase 2 —— OIDC 登录与关联

- 添加配置校验、Discovery/JWKS 缓存、浏览器事务、回调、声明校验、`external_identity`、
  `existing_only` 关联，以及受其显式策略约束的 JIT。
- 添加 Portal 方法发现与 SSO 呈现。
- 添加原子的身份链接审计与管理员读取/恢复界面。

### Phase 3 —— 运营与认证（qualification）

- 添加经脱敏的状态与降级诊断。
- 演练 IdP 故障、JWKS 轮换、客户端密钥轮换、签发方变更拒绝、应急、禁用与回滚。
- 仅在证据所能证明的程度上，更新当前状态、认证/配置/运维文档、OpenAPI、部署清单、示例
  以及 Beta/支持边界。

### 所需验证

| 范围 | 证据 |
|---|---|
| 核心/服务 | 针对每个关联分支、被禁用用户、冲突、过期、撤销与授权无效应的表驱动测试 |
| 处理器 | state/nonce/PKCE、签发方/受众/签名/时间检查、cookie 属性、源检查、安全错误、重定向中无令牌 |
| 数据库 | 针对唯一性、并发首次登录、JIT 账户/个人 Space/链接原子性、会话撤销与事务性审计的真实 MySQL 测试 |
| Portal | 组件测试加上浏览器登录、重新加载、刷新、登出、错误、返回路径以及存储中无令牌的断言 |
| 协议 | 针对负面用例的确定性对抗性伪实现，加上针对一个固定的、符合标准的提供方的端到端登录 |
| 部署 | 多副本 kind 回调、IdP/JWKS 故障、密钥与客户端密钥轮换、应急以及既有会话连续性 |
| 授权 | 既有的 Space 与系统管理员矩阵不变地通过；显式测试证明 IdP 组/声明不授予任何权限 |
| 文档 | `./make check docs` 与 `git diff --check`；配置与路由保持与生成源一致 |

一个进程内伪实现证明的是 BuildMax 的分支，而非提供方的互操作性。一次单一的顺利路径
提供方登录既不能证明轮换也不能证明离职。在声称支持某提供方之前，两种形式的证据都是
必需的。

## 18. 非目标

- 公共多租户 SaaS 注册或组织层级。
- 首个切片中的 SAML、LDAP bind、社交登录、受信任代理头或多个同时存在的 OIDC 提供方。
- SCIM、IdP 组到 Space 的映射、自定义角色或由 IdP 派生的 System Administrator 授予。
- 由 BuildMax 管理的 MFA，或在没有被接受的提供方特定保证策略予以验证的情况下声称 IdP
  使用了 MFA。
- 在没有单独互操作性证据的情况下的提供方级登出、前端通道登出或后端通道登出。
- 自助式身份链接、邮箱变更、账户合并或账户删除。
- PAT、服务账户或无人值守客户端凭据。
- 没有目标历程的原生已连接客户端 SSO；本地 CLI/TUI 与 Desktop 仍独立受支持。
- 一个新的身份提供方数据库实体、动态客户端注册，或一个会改动 `server.yaml` 及其密钥的
  管理 UI。
- 更改 Space 角色策略、所有权规则、邀请语义、TaskRun 权限或 worker 凭据。
- 在普通事件写入仍是尽力而为时声称具有合规级审计。

## 19. 各部署待定输入

方向已被接受，但以下各部署事实是每个构建切片的前置条件，且仍然缺失：

1. **目标提供方。** **已选定：Okta。** 它提供精确签发方 Discovery、PKCE S256、
   已验证的 `email`/`email_verified`、标准 UserInfo，以及使用 `client_secret_basic`
   的机密客户端。提供方无关的核心按 OpenID Connect Core/Discovery 构建，并用一个确定性
   的对抗式假签发方验证；固定的真实 Okta 端到端及其 `max_age`/密钥重叠细节属于 Phase 3
   资格验证，需要一个可复现的 Okta 测试租户。
2. **预配域名。** JIT 是被接受的 SSO 默认值；究竟哪些邮箱域名属于企业权威，是否有目标
   部署反而需要 `existing_only`？
3. **离职目标。** 12 小时的重新认证界限加上手动的即时禁用是否可接受？若不可接受，所要求
   的结果需要 SCIM、经过验证的后端通道登出或另一个有明确名称的生命周期通道。
4. **本地回退。** 运维人员是否会维护并演练两个本地 System Administrator 凭据，
   `system_admins` 对目标部署而言是否为正确的强制默认值？
5. **原生托管模式。** 在首个客户历程中，普通用户是否必须把 CLI/Desktop 连接到托管模型？
   若是，应在接受仅 Portal 投递之前，根据实际环境约束在浏览器回环或设备授权之间做出
   选择。
6. **要求范围。** 哪些目标部署结果需要超出已接受 Portal 浏览器范围的 SSO？企业功能要求
   盘点可用于指导调研，但不能改变此处的安全或互操作性标准。
7. **速率限制。** 在受支持的拓扑中，哪个共享限流器保护剩余的本地登录与 OIDC 事务端点？
   在回答之前，当前的外部速率限制指南仍是强制的。

决策证据是一份书面的运维历程、IdP 配置导出或等效的可复现事实、一个约定的入职/离职界限、
一次威胁模型评审，以及一份提供方测试计划。功能对比表或“企业工具通常都有 SSO”是不够的。
