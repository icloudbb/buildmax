## 1. 目的

P0.5 §3.2 要求为命令与工具执行提供明确的沙箱模式，在工作区文件系统、外部目录、网络、环境变量、进程限制以及 worker/容器执行等方面建立一流的边界。

今天的 Agent Core 已经具备：

- **文件系统限制**：进程内文件工具通过 `internal/util.ResolvePath` 被限制在工作区根目录内。
- **Bash 启发式规则**：`internal/tool/safety.go` 中实现了灾难性命令拒绝加高风险命令询问。命令仍然在完整的父进程环境、完整的网络访问、没有资源限制（rlimit）、没有文件系统隔离的情况下运行。

在合理的范围内，我们直接照搬 Claude Code 的模型。引用其[文档](https://code.claude.com/docs/en/sandboxing)的说法：“沙箱隔离的是 Bash 子进程，其他工具运行在不同的边界之下。”这正是我们所模仿的设计：

- **沙箱 = Bash 子进程隔离。** Bash 命令及其子进程运行在操作系统级沙箱之下（Linux/WSL2 用 `bwrap`，macOS 用 `sandbox-exec`/Seatbelt），受由配置驱动的文件系统与网络策略约束。Bash 沙箱是本文档在既有强制机制之上新增的唯一一项。
- **非 Bash 工具继续沿用权限系统。** Read/Write/Edit/Glob/Grep/WebFetch 保持现有的 Go 层检查（`ResolvePath`、`safety.go`）以及 `internal/agentapp/policy.go` 中的审批策略不变，不会被强行接入新的守卫层。

这样既能把改动的影响面控制到最小，又能交付用户一说“沙箱”就会期待的能力。

## 2. 方向

三条原则，取自 Claude Code 文档：

1. **把 shell 装进沙箱，而不是对参数做匹配。** 对 bash 字符串做模式匹配并不可靠；操作系统级隔离才是经得起考验的答案。macOS 使用 Seatbelt；Linux/WSL2 使用 `bubblewrap` + `socat`。
2. **对用户是选择加入，对运维者是选择退出。** 本地 CLI/Desktop 默认 `enabled: false`（不引入行为回归）。**Worker 默认 `enabled: true` 且 `fail_if_unavailable: true`**，以满足信任保障文档中“比受信任的本地环境更严格”的要求。
3. **可见的失败胜过静默地放行。** 当 `enabled: true` 但后端无法启动时（例如缺少 `bwrap`，或平台不受支持），应显示清晰的启动提示；在 Worker 上则直接拒绝启动。

我们**不会**自行开发一套 `@anthropic-ai/sandbox-runtime` 的克隆实现，而是从 Go 代码里直接调用 `bwrap` / `sandbox-exec`，再配上一个小型的 Go 端 HTTP/SOCKS 代理来做网络出站过滤。

## 3. 架构形状

参照 hooks v2 的分层方式：

| 层级 | Hooks v2 | 沙箱 |
|---|---|---|
| 领域契约 | `core/agent/hook.go` | `core/agent/sandbox.go` —— `SandboxConfig`、`SandboxView` 接口 |
| 外部系统实现 | `infra/hook/*` | `infra/sandbox/*` —— `manager.go`（门面）、`bwrap_linux.go`、`seatbelt_darwin.go`、`unsupported_windows.go`、`proxy.go`（HTTP/SOCKS）、`violation_store.go`、`deps.go`（依赖检查） |
| 应用组装 | `agentapp/hook_manager.go` | `agentapp/sandbox.go` —— 解析并合并设置、把管理器注入 Bash 工具、暴露 `Status` |
| 配置 | `config/hooks.go` + `<ws>/.buildmax/hooks.yaml` | `config/sandbox.go` —— `sandbox:` 块内嵌在现有的 `settings.yaml` 中（外加可选的 `policy.yaml`） |

`infra/sandbox.Manager` 对应 Claude Code 的 `SandboxManager`：
- `Enabled() bool`、`Mode() string`（`"auto_allow"` | `"regular"`）
- `WrapBashCommand(ctx, cmd, shell) (wrapped string, error)`
- `ShouldSandboxCommand(cmd) bool`（遵循 `excluded_commands`）
- `Dependencies() DepsReport`、`UnavailableReason() string`
- `Refresh(cfg) error`、`Reset()`、`Close()`
- `Violations() *ViolationStore`

只有 Bash 工具和 `command` Hook 传输依赖 `SandboxView`（这样 `command` Hook 就无法被用来逃逸沙箱）。

## 4. 配置

沙箱配置内嵌在现有的 `settings.yaml` 中，正如 Claude Code 的 `sandbox` 块内嵌在 `settings.json` 里一样。键名按 CLAUDE.md §6.1 使用 snake_case，但结构与上游完全一致。

### 4.1 来源

| 范围 | 路径 | 说明 |
|---|---|---|
| 用户 | `<BUILDMAX_HOME>/settings.yaml` 的 `sandbox:` 下 | 默认位置 |
| 策略（运维者） | `<BUILDMAX_HOME>/policy.yaml` 的 `sandbox:` 下 | 可选的锁定手段 |
| 环境变量 | `BUILDMAX_SANDBOX_ENABLED` | 按进程覆盖 |
| CLI 运行 | `--sandbox [--sandbox-mode auto_allow\|regular]` | 强制某次 TUI 或 print 模式运行启用沙箱；不可用时按失败关闭处理 |
| Bash 调用 | `dangerously_disable_sandbox: true` | 由配置控制的、按调用生效的逃逸入口 |

标量值的解析优先级为：策略 > CLI 运行 > 环境变量 > 用户 > 使用面默认值。CLI 层只能要求启用沙箱，不能禁用它；显式指定 `--sandbox` 还会一并强制 `fail_if_unavailable`。策略可以设置 `allow_managed_domains_only: true` 和 `allow_managed_read_paths_only: true` 来锁定特定数组——一旦设置，更低优先级的来源仍然可以**追加拒绝项**，但它们针对该字段的**允许项会被忽略**（对应 Claude Code 的 `allowManagedDomainsOnly` / `allowManagedReadPathsOnly`）。

对于没有“仅受管”标志的数组类键（`excluded_commands`、`allow_write` 等），所有范围的条目会被取并集——这一点与 Claude Code 相同。

未来的按工作区配置文件 `<workspace>/.buildmax/settings.yaml` 才是承载项目级覆盖的合适位置；本文档不引入它，也不会另外创建一个只服务于沙箱的工作区配置文件。

### 4.2 完整键参考

对应 Claude Code SDK 中的 `SandboxSettings`（`src/entrypoints/sandboxTypes.ts`）。我们从上游裁掉的键在本节末尾列出。

```yaml
sandbox:
  enabled: false              # master switch
  fail_if_unavailable: false  # refuse to start if backend can't run
  auto_allow_bash_if_sandboxed: true   # skip approval prompt for sandboxed bash
  allow_unsandboxed_commands: true     # honor dangerously_disable_sandbox

  excluded_commands: []       # bash patterns to run *outside* the sandbox
                              # (convenience, not a security boundary)

  filesystem:
    allow_write: []           # extra writable paths beyond CWD
    deny_write: []            # explicit denials (override allow)
    allow_read: []            # re-allow within deny_read regions
    deny_read: []             # block reads
    allow_managed_read_paths_only: false  # policy-only knob

  network:
    allowed_domains: []       # host globs (e.g. "api.github.com", "*.npmjs.org")
    denied_domains: []
    allow_unix_sockets: []    # macOS only
    allow_all_unix_sockets: false
    allow_local_binding: false
    http_proxy_port: 0        # 0 = pick free port; non-zero = use custom proxy
    socks_proxy_port: 0
    allow_managed_domains_only: false  # policy-only knob

  ignore_violations: {}       # map[string][]string of violations to suppress
                              # (per-tool, claude-code parity)

  # Not part of upstream SandboxSettings; BuildMax's own extension for the
  # process-limits boundary trust-harness.md §3.2 lists. 0 = no limit from
  # this layer. max_memory_mb has no effect on macOS -- Darwin's setrlimit
  # does not support RLIMIT_AS, and Seatbelt's .sb grammar has no
  # resource-limit primitive either (§7.1) -- so it is Linux-only in
  # practice.
  process:
    max_cpu_seconds: 0
    max_memory_mb: 0
    max_processes: 0
    max_open_files: 0

  enable_weaker_nested_sandbox: false   # allow inside Docker w/o privileged ns
  enable_weaker_network_isolation: false # macOS: allow trustd for Go CLIs
```

我们**不会**从上游 `SandboxSettings` 引入的键：
- `enabledPlatforms`（Claude Code 用于 NVIDIA 灰度发布的逃逸开关；我们暂时不需要）。
- `ripgrep` 覆盖项（我们目前还没有内置 ripgrep）。

### 4.3 路径前缀约定

对于 `sandbox.filesystem.*` 下的路径，我们与 Claude Code 完全一致：

| 前缀 | 含义 | 示例 |
|---|---|---|
| `/path` | 相对于文件系统根的绝对路径 | `/tmp/build` |
| `~/path` | 相对于主目录的路径 | `~/.cache` |
| `./path` 或 `path` | 相对于设置文件所在目录（如果存在 `<workspace>/.buildmax/settings.yaml`，则是项目根目录；对于用户设置，则是 `<BUILDMAX_HOME>`） | `./output` |

我们刻意**不**照搬上游的 `//path` 权限规则前缀约定（他们那种“通过权限规则表达绝对路径”的特殊写法）。BuildMax 尚未有 `Edit(/path)` 这类权限规则语法，因此促成 `//path` 存在的那种歧义在这里并不出现。

### 4.4 默认值

开箱即用时，只要 `enabled: true` 且其余项均未设置，行为就与 Claude Code 的默认值一致：

- **文件系统写入**：仅限当前工作目录及其子树。
- **文件系统读取**：整台机器均可读，`deny_read` 中列出的除外。*注意*：这个默认设置仍然允许读取 `~/.aws/credentials`、`~/.ssh/` 等路径，在意这一点的运维者必须自行把它们加入 `deny_read`。我们会在 `config-examples/sandbox.example.yaml` 和 `CLAUDE.md` 中记录这一注意事项。
- **网络**：默认不预先允许任何域名。每个新出现的域名要么通过现有审批流程询问（交互式界面），要么直接拒绝（非交互式场景——`applyPolicyAndExecute` 在未设置 ApprovalHandler 时已经会把“询问”折叠为“拒绝”）。
- **设置文件自我保护**：`<BUILDMAX_HOME>/settings.yaml` 和 `<BUILDMAX_HOME>/policy.yaml` 会在每个范围内被自动加入 `deny_write`。

## 5. 沙箱模式

两种模式（对应 Claude Code `/sandbox` 面板的 Mode 标签页）：

- **`auto_allow`**——沙箱化的 bash 命令无需询问即可运行。自动批准是有条件的：显式的 `deny` 权限规则依然生效，且命中 `tool/safety.go` 中受保护路径（如 `rm -rf /` 等）的 bash 调用仍会走常规审批流程。
- **`regular`**——沙箱化的 bash 依然要走常规审批流程。沙箱负责强制约束，审批依旧是必须的一步。

模式由 `sandbox.auto_allow_bash_if_sandboxed` 决定：
- `true`（`enabled: true` 时的默认值）→ `auto_allow`
- `false` → `regular`

两种模式施加的操作系统级文件系统与网络限制完全相同，区别只在于审批行为。

`auto_allow` 是唯一一处用“隔离”取代“询问”的地方，而且这一替代仅限于 `Bash`。它刻意没有扩展到 `Write` 和 `Edit`：沙箱存在的意义是约束工作区*之外*的写入，而工作区*内部*的写入正是沙箱本就允许的行为，因此它并不能约束询问本来要防的那件事。参见[《工具权限》](./工具权限.md) §5.7。

## 6. `dangerously_disable_sandbox` 逃逸入口

对应 Claude Code 的 `dangerouslyDisableSandbox`。

Bash 工具接受一个可选参数：

```json
{ "command": "docker ps", "dangerously_disable_sandbox": true }
```

行为规则：

- 若 `sandbox.enabled: false` → 该参数被忽略；bash 照旧运行。
- 若 `sandbox.allow_unsandboxed_commands: false` → 该参数被忽略；调用无论如何都会被沙箱化。状态中会显示为“严格沙箱模式”（对应 `/sandbox` 面板 Overrides 标签页上的标签文案）。
- 否则 → bash 在沙箱**之外**运行，并走正常的审批流程（询问→弹出用户提示；非交互式场景→拒绝）。

Bash 工具的描述会告知 LLM 这个开关的存在，使其能够在失败后自行重试恢复，这对应 Claude Code 所说的“Claude 会分析失败原因，并可能带上 `dangerouslyDisableSandbox` 参数重试该命令”。

每一次被禁用沙箱的调用都会向违规存储写入一条 `Violation{kind: sandbox_disabled}`，这样[《Hook 系统》](./Hook系统.md)中描述的审计 Hook 就能感知到它。

## 7. 操作系统后端的工作方式

我们完全遵循 Claude Code 的平台支持范围：macOS、Linux、WSL2。**不支持**原生 Windows；Windows 用户需要在 WSL2 内运行 BuildMax，或者直接设置 `enabled: false`。

### 7.1 macOS — Seatbelt

`infra/sandbox/seatbelt_darwin.go` 会在 `<BUILDMAX_HOME>/sandbox/profiles/`（权限 0600）下为每个会话生成一份 Seatbelt 配置文件（`.sb`），然后调用：

```
sandbox-exec -f <profile.sb> /bin/sh -c <wrapped-command>
```

该配置文件由 `FSConfig`、`NetConfig`、`EnvConfig` 派生而来，使用 `(allow file-read*)`、`(allow file-write*)`、`(deny network-outbound)`，再加上针对代理端口的定向放行。

`enable_weaker_network_isolation` 会开放 `com.apple.trustd.agent`，使 Go 编写的 CLI（`gh`、`gcloud`、`terraform`）能够在经过 MITM 代理时正常校验 TLS——这与 Claude Code 文档中记录的取舍完全一致。

### 7.2 Linux / WSL2 — bubblewrap + socat

`infra/sandbox/bwrap_linux.go` 根据配置构建 `bwrap` 的参数：`--ro-bind`、`--bind`、`--dev`、`--proc`、`--unshare-net`、`--setenv`、`--rlimit`。网络出站流量通过沙箱内部的 `HTTP_PROXY` / `HTTPS_PROXY` / `ALL_PROXY` 环境变量，转发给 Go 端实现的 HTTP/SOCKS 代理；需要的地方由 `socat` 中继 Unix 域代理套接字。

宿主机上需要的软件包：
- `bubblewrap`（提供 `bwrap` 二进制）
- `socat`

可选：
- seccomp 过滤器（用于阻断 Unix 套接字），可以通过安装上游的 `@anthropic-ai/sandbox-runtime` 包获得，也可以手动复制其 `vendor/seccomp/*` 文件；`infra/sandbox/deps.go` 会在状态中把它报告为“可选”。

### 7.3 Ubuntu 24.04 + AppArmor

沿用上游记录的一个注意事项：Ubuntu 24.04 的默认 AppArmor 配置会阻止非特权用户命名空间。检测方式是读取 `/proc/sys/kernel/apparmor_restrict_unprivileged_userns`；若其值为 `1`，则在 `buildmax sandbox` 的状态输出中给出清晰的修复提示（引用上游那段用 `tee` 添加 `bwrap` 专属 AppArmor 配置的片段）。

### 7.4 容器 — `enable_weaker_nested_sandbox`

对应上游的做法。开启后，bwrap 会绑定挂载容器已有的 `/proc`，而不是挂载一个全新的。这被明确记录为一种更弱的选项，只应在外层容器本身已经提供隔离的场景下使用。

## 8. `buildmax sandbox` 命令

对应 Claude Code 的 `/sandbox` 面板。

子命令：

- `buildmax sandbox status`——相当于 Config 标签页。打印已解析的配置、各层来源、当前模式、后端、依赖检查结果以及最近的违规记录。
- `buildmax sandbox deps`——相当于 Dependencies 标签页。展示 `bwrap`、`socat`、ripgrep、seccomp 过滤器是否已就绪，并给出各平台的安装提示。
- `buildmax sandbox mode <auto_allow|regular>`——把 `auto_allow_bash_if_sandboxed` 写入用户设置。
- `buildmax sandbox overrides <strict|permissive>`——不在范围内（§14）：`allow_unsandboxed_commands` 是一次性写入 `policy.yaml` 的运维锁，而非逐会话的便捷开关，因此该子命令不予构建。
- `buildmax sandbox enable` / `disable`——写入 `sandbox.enabled`。

当某项必需依赖缺失时，`status` 和 `deps` 会是唯一有用的命令（对应上游“在你安装依赖之前，只会显示 Dependencies 标签页”的做法）。

## 9. 边界执行摘要

| 类别 | 由谁强制执行 | 位置 |
|---|---|---|
| Bash 文件系统 | 操作系统后端（`bwrap` 的 bind/ro-bind；Seatbelt 的 `file-read*` / `file-write*`） | `infra/sandbox/bwrap_linux.go`、`seatbelt_darwin.go` |
| Bash 网络出站 | Go 实现的 HTTP/SOCKS 代理（allow_list/deny_list）；沙箱会强制设置 `HTTP_PROXY` 环境变量 | `infra/sandbox/proxy.go` |
| Bash 环境变量 | 形似密钥的变量（`*_TOKEN`、`*_KEY`、`*_SECRET`，加上一份精确匹配列表）会被剥离，除非其名称是本次运行以 Space Secret 授权声明过的（`Manager.AllowEnvNames`）；`BUILDMAX_API_KEY`、`BUILDMAX_RUN_TOKEN`、`BUILDMAX_JWT_SECRET` 属于 `alwaysDenyExact`，任何允许列表都无法让它们重新放行。参见[《Space 密钥》](Space密钥.md) §13.1 | `infra/sandbox/env_scrub.go` |
| Bash 进程限制 | 以 `ulimit` 语句的形式前置在包装后的 `/bin/sh -c` 命令之前，每条限制单独一条语句——而不是用 `syscall.Setrlimit`，因为 `os/exec.Cmd` 没有仅对子进程生效的 pre-exec 钩子；`max_memory_mb` 在 macOS 上不起作用（Darwin 的 `setrlimit` 没有 `RLIMIT_AS`） | `infra/sandbox/unix_rlimit.go` |
| `command` Hook | 与 Bash 相同的包装与环境处理（因此 Hook 无法借此逃逸） | `infra/hook/command.go` 会咨询 `SandboxView` |
| `http` Hook | 使用与 `allowed_domains` / `denied_domains` 相同的匹配器 | `infra/hook/http.go` 会咨询 `SandboxView` |
| 非 Bash 工具（Read/Write/Edit/Glob/Grep/WebFetch） | **沿用现有的权限流程**（`policy.go`、`safety.go`、`util.ResolvePath`）——本文档不对其做任何改动 | `internal/tool/*` |

这两层（Bash 走沙箱，其余一切走权限系统）完全对应 Claude Code 文档中的说法：“内置文件工具 Read、Edit、Write 直接使用权限系统，而不经过沙箱。”

## 10. 使用面默认值

| 使用面 | 默认值 | 是否锁定 |
|---|---|---|
| CLI（`buildmax`） | `enabled: false`（不引入回归） | 否 |
| Desktop | `enabled: false` | 否 |
| Worker（`buildmax-worker`） | `enabled: true`、`fail_if_unavailable: true`、`allow_unsandboxed_commands: false`、收窄的 `allowed_domains`、`deny_read: ["~/.aws", "~/.ssh"]` | 是，通过随 worker 容器镜像一起发布的 `policy.yaml` 锁定 |
| Portal 进程内轮次 | 继承 Worker 的默认值 | 是 |
| TUI 子 Agent | 继承父级配置 | 不适用 |

Worker 的这套配置，正是[《信任保障》](./信任保障.md) §3.2 所说的“默认比受信任的本地环境更严格”的具体落地。如果某个 Worker 因为覆盖设置而最终解析为 `enabled: false`，它会在启动时发出一条 `WARN`，在轨迹中打上 `sandbox.downgraded=true` 标记，并在 `SessionStart` Hook 载荷中暴露是哪一层覆盖导致的（见 §11.2）。

这张表说明的是边界“是什么”。Agent 与 Space 层级选择由[《Agent 沙箱策略》](./Agent沙箱策略.md)规定。Pod 全局目的地强制属于[《信任保障》](./信任保障.md) §3.9 中条件触发的 Beta 后加固，不由本文档负责。下文所述的 Agent 内置代理只是按主机名过滤一个已被沙箱化的 bash 子进程流量，并不是 Pod 级出站边界。

## 11. 可见性

### 11.1 使用面展示

- **CLI / TUI 状态栏**：显示 `sandbox: on(auto)`、`sandbox: on(regular)`、`sandbox: off`，或 `sandbox: missing`（已启用但后端不可用——与上游的警告行为一致）。
- **Desktop**：会话信息面板展示相同信息，外加一个可展开的“查看边界”详情。
- **Portal Task Run 头部**：展示是否启用、当前模式，以及允许的域名数与可写路径数。
- **Worker 启动日志**：打印完整的已解析配置 JSON 与依赖检查结果。

### 11.2 Hook 载荷

每个 `agent.HookInput` 都会新增一个 `Sandbox` 字段：

```go
type SandboxInfo struct {
    Enabled     bool
    Mode        string   // "auto_allow" | "regular"
    Backend     string   // "seatbelt" | "bwrap" | "none"
    Sources     []string // ordered chain of overrides applied
    Downgraded  bool     // worker only; true if forced off by override
}
```

### 11.3 违规存储与 `ignore_violations`

一个按会话 ID 分组、大小有界的环形缓冲区：

```go
type Violation struct {
    Time     time.Time
    Kind     string  // "fs_deny" | "net_deny" | "sandbox_disabled" | "backend_unavailable"
    Tool     string
    Argument string  // redacted
    Reason   string
    Source   string  // "go_proxy" | "bwrap" | "seatbelt"
}
```

`sandbox.ignore_violations` 的行为与上游完全一致：一个 `map[string][]string`（例如 `{ "Bash": ["net_deny:metrics.example.com"] }`）会让匹配到的违规不再出现在状态或轨迹展示中，但它们仍会被计入内部统计，便于调试。

## 12. Hook 集成

沙箱与 Hook 是互补关系：

- 沙箱是*契约层面的拒绝*：确定性的、由操作系统强制执行、专为 LLM 设计（CLAUDE.md §6.4）。
- Hook 是*命令式的检查*：策略回调、审计、格式化（[《Hook 系统》](./Hook系统.md)）。Hook 在沙箱放行**之后**才运行；一次沙箱拒绝会触发 `Notification{kind: sandbox_denied}`，因此审计 Hook 依然能够感知到它。

Hook 传输本身也遵守沙箱约束，因此无法被用来绕过沙箱（见 §9——`command` 和 `http` Hook 都会咨询 `SandboxView`）。

1. ✅ **Worker 默认值已选定，并针对生产 Pod 的安全上下文完成了验证。** `agentapp/taskrun/runtime.go` 设置的是 `SandboxSurface: config.WorkerSandboxSurface()`，而不是最初尝试的、无条件的 `SandboxSurfaceWorker`：后者会在没有 `bwrap` 的裸机 Linux 主机上，以及在任何原生 Windows Worker 上，直接搞垮每一个 worker task（二者都会触发 `fail_if_unavailable: true`，却没有后端可用）。这个问题是被 `evaluation` 中的黑盒 worker-surface 测试和 Windows CI 捕获的，而不是本地在 Mac 上开发时发现的——因为 Mac 上 Seatbelt 始终存在，这个失败根本无法复现。`WorkerSandboxSurface` 只有在设置了 `BUILDMAX_SANDBOX_BACKEND_INSTALLED` 时才会选用严格基线——这是 `Dockerfile.buildmax`/`Dockerfile.release` 中的一行 `ENV`，凡是由这两个镜像构建出的容器都会带上它，因此任何 `k8s_job` Worker Pod 中都存在，而裸机主机上没有。但单靠选对这一项在配置齐全的镜像上仍然不够：一旦 Worker Pod 的能力（capabilities）被清空，`RuntimeDefault` seccomp 会拦掉 `bwrap` 所需的系统调用；同时在 `--unshare-pid` 下挂载一个全新的 `/proc` 会触发内核“挂载过于暴露”的保护机制，这与 seccomp 无关，是另一个独立的问题。两者现已都被修复——完整的根因链路，以及如何针对一个具备 Worker 真实安全上下文的实际 Pod 完成验证，见[《deployment/seccomp/README.md》](../../../deployment/seccomp/README.md)。部署冒烟测试现在还会做一次自然的端到端检查：让其模拟模型驱动一次真实下发的任务、经由真正的 server → worker → Job 路径调用 `Bash`，然后断言的是工具的执行结果——而不是任务预先设定好的最终文本（因为无论工具实际做了什么，那段文本都会一样）——确认命令确实执行了，并且工作区之外的写入被拒绝（`tools/mk/deploy_smoke.go` 中的 `assertWorkerSandboxConfines`，以及 `internal/testsupport/mockllm` 排队的工具调用装配与 `GET /control/requests`）。
2. ✅ **进程限制。** `sandbox.process.{max_cpu_seconds,max_memory_mb,max_processes,max_open_files}`（`config.SandboxProcessConfig`）被转换成前置在包装后的 `/bin/sh -c` 命令之前的 `ulimit` 语句——每条限制单独一条语句，而不是一次调用附带多个参数，这样 `max_memory_mb` 在 macOS 上彻底失效（Darwin 的 `setrlimit` 不支持 `RLIMIT_AS`）也不会妨碍其他限制生效（`infra/sandbox/unix_rlimit.go`）。已针对真实的 Alpine（`docker run`）和 macOS `/bin/sh` 完成验证：在 Linux 上四项限制全部生效（其中 CPU 时间限制确实终止了一个忙等循环），在 macOS 上 `max_cpu_seconds`/`max_processes`/`max_open_files` 均生效，`max_memory_mb` 则按文档所述静默地不起作用。零值表示不设限，这与 `worker.k8s.resources` 所记录的克制原则一致——不为 Worker 使用面选定默认值。
3. ✅ **Hook 传输会咨询 `SandboxView`。** `hook.Deps.Sandbox`（从 `app_builder.go` 中的 `AgentApp.sandbox` 接入）会同时传给两个驱动。`CommandDriver` 与 `Bash` 的 `spawnArgs`/`childEnv` 完全一致——同样调用 `WrapBashCommand`、同样处理 `excluded_commands`、同样使用擦除后的环境——但没有与 `dangerously_disable_sandbox` 对应的开关：Hook 是配置写就的自动化流程，不是运维者逐轮盯着、由 LLM 主动发起的调用，因此没有理由为它提供按次退出的参数。`HTTPDriver` 在构建请求之前复刻了 `WebFetch` 的 `HostAllowed` 检查，一旦被拒绝就直接让该 Hook 失败并给出沙箱自身的理由，根本不会触达网络。已针对一个真实的 `sandbox.Manager`（Seatbelt，而非桩实现）完成验证：一个 command Hook 先打印了自己的输出，随后尝试在工作区之外写入时被拒绝，报出与 `Bash` 完全相同的 `Operation not permitted`。

## 15. 验收

§3.2 在满足以下条件时视为达成：

- CLI、Desktop、Worker、Portal 的 Task Run 都能解析并展示一份沙箱配置（`enabled`、模式、后端、来源）。
- Worker 默认值为 `enabled: true, fail_if_unavailable: true, allow_unsandboxed_commands: false`；在缺少后端的平台上，Worker 会拒绝启动。降级情况会被记录日志、写入轨迹，并对 Hook 可见。
- Linux/macOS 上的 Bash 命令运行在 `bwrap` / Seatbelt 内部；子进程继承相同的边界。
- 从 bash 沙箱内部发起的网络出站流量，会由 Go 端代理依据 `allowed_domains` / `denied_domains` 过滤。
- `excluded_commands` 可以让特定命令不进入沙箱；`dangerously_disable_sandbox` 遵循 `allow_unsandboxed_commands` 的设置。
- 形似密钥的环境变量除非被显式列出，否则绝不会泄漏进沙箱。
- `command` 和 `http` 这两种 Hook 传输遵循相同的边界。
- `buildmax sandbox` 子命令涵盖 status、deps、mode、enable/disable。（`overrides` 不在范围内——§14。）
