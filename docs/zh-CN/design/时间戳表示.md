# 时间戳表示

> **翻译说明：** 本文是[英文原文](../../design/timestamp-representation.md)的简体中文派生翻译。若中英文存在语义冲突，以英文原文为准。

> **读者：** 贡献者与数据库审阅者 · **状态：** 已实现

BuildMax 如何拼写"这件事发生在时间线上的某一刻"这句话。三层各用一种
规则:Go 中用 `time.Time`,MySQL 中用 `DATETIME(6)`,JSON 中用 RFC 3339。

本文推翻了此前的规则——那条规则要求用 `bigint` 列存储 Unix 秒数,并
明确说永远不要用 `DATETIME`。现在实际生效的规则记录在
[data model](../contribute/architecture/data-model.md) 和
[conventions](../contribute/conventions.md)中;下文说明的是理由。

相关文档:[data model](../contribute/architecture/data-model.md)、
[store](../contribute/architecture/store.md)、
[conventions](../contribute/conventions.md)、
[entity identity](实体身份.md)——这是"用一次连贯的改动完成一项
Alpha 阶段架构变更"的先例——以及[configuration](../reference/configuration.md)
中关于数据库 DSN 的部分。

## 1. 问题

服务器中每一个被持久化的时刻,都曾经是一个从纪元开始计数的 `int64` 秒数。
这条规则是当初刻意设计并写入文档的;但一旦这套 schema 大到需要被人手动
查询、又被两个前端消费,它就不再是正确的默认选择了。

下面是这次改动所替换掉的那棵代码树的快照。`internal/core/model` 是当时
的领域包;此后它已经被拆分成每个领域各自一个包,所以下面这些计数反映的
是这次改动触及的范围,而不是今天代码树的实际结构:

| 位置 | 数量 |
|---|---|
| `internal/infra/db` 行结构体中的时间戳字段 | 63 |
| 其中由 GORM 的 `autoCreateTime` / `autoUpdateTime` 填充的 | 29 |
| `internal/core/model` 中的时间戳字段 | 73 |
| `internal` 下非测试代码中的 `XxxAt int64` 声明 | 69 个文件中共 222 处 |
| 非测试代码中通过 `Unix()` / `time.Unix()` 转换的调用点 | 116 |
| 读取某个 `*_at` 字段的 Portal 和 Desktop 文件 | 18 |

由此带来五项代价,这些代价源自这种表示方式本身,而不是某一个具体的
调用点。

**原始查询不可读。** `SELECT created_at FROM task_run ORDER BY
created_at DESC LIMIT 5` 给出的答案是五个十位数的整数。每一次临时的
排查都要用 `FROM_UNIXTIME` 包一层列,每一条手写的查询条件都要用
`UNIX_TIMESTAMP` 包一层参数,而被包裹过的列用不了索引。最可能去跑这类
查询的人——那些正在排查一次卡住的 Run 的运维人员——恰恰是被这种编码
方式服务得最差的人。

**秒级精度会发生碰撞。** 一波 `conversation_message` 或
`workflow_step_run` 记录如果都落在同一秒内,就会在时间上变得无法区分。
稳定的排序是一个独立的问题(见第 3 节 D6),但这种编码方式保证了碰撞
一定会发生,而不只是允许它发生。

**类型不携带含义。** `int64` 同时也是一个时长、一个 token 计数、一次
重试次数,或者一个毫秒级时间戳的类型。在包边界上,没有任何东西能区分
`EndedAt` 和 `TimeoutSeconds`;一个把毫秒误当成秒的错误可以顺利通过
类型检查、正常写入,读回来之后却变成了公元 57000 年的某个日期。

**"缺失"有两种拼法。** 大多数可为空的时间戳字段是 `*int64`,缺失意味着
`NULL`。但 `plugin.archived_at` 和 `plugin_release.yanked_at` 却是
`not null;default:0`,其中 `0` 表示"尚未归档"——这是一个哨兵值,但它
同时也是一个合法的时间点,而这套 schema 里明明已经有现成的可空写法
可用。

**代码仓库中其实已经在运行第二套约定。** 会话文件里携带的是
`CreatedAt time.Time` 和一个 RFC 3339 字符串
(`internal/core/session/session.go`);轨迹和 job 日志写入的是一个
RFC 3339 纳秒精度的 `ts` 字段(`internal/infra/trace/record.go`)。
也就是说,文件这一层早就选择了本文为数据库提议的这种表示方式,而它们
之间的每一处边界都需要做转换。而且这种转换方式也并不统一:
`trace/joblog.go` 用本地时间打上 `time.Now()` 的时间戳,而
`trace/record.go` 用的是 `time.Now().UTC()`。

BuildMax 目前处于 Alpha 阶段,不欠任何已发布 API 或现存数据库的兼容性
债务,这正是让这项改动现在做很便宜、以后再做会很昂贵的原因——这与
[entity identity](实体身份.md) 当初使用的是同一个论证、同一个时间窗口。

## 2. 目标与非目标

**目标。** 每一层只有一种表示方式,由字段本身的含义决定,而不是由它
旁边的字段决定。SQL 应当能被人直接读写,不需要转换函数。要有亚秒级
精度。"缺失"只用一种方式表达,即 `NULL`。每一次写入都使用 UTC,并且
把连接本身也固定住,让数据库对时区的理解与应用一致。这是一次连贯的
schema 变更,不存在双读路径。

**非目标。** 时长、配额、重试次数和 token 计数都不是时间点,它们不会
改变(见第 3 节 D7)。会话和轨迹文件的格式已经在使用 RFC 3339,本文不
涉及它们。排序语义不会改变:微秒级精度并不意味着可以仅凭一个时间戳
字段来排序(见 D6)。不引入数据库外键——这项决定由
[entity identity](实体身份.md) 第 8 节负责,本文不会重新讨论它。也不
引入带时区感知的"本地墙钟时间"类型:BuildMax 存储的是时间点本身,
用户所在的时区是一个展现层面的问题。

## 3. 决策

| # | 决策 |
|---|---|
| D1 | 一个被持久化的时间点,在 Go 中就是 `time.Time`。可选则意味着 `*time.Time`,`NULL` 表示这件事尚未发生——`ended_at IS NULL` 表达的仍然是"正在运行",而不是"未知"。 |
| D2 | MySQL 中的列类型是 `DATETIME(6)`。不是 `TIMESTAMP`,不是 `BIGINT`,也不是 `DATE`。理由见第 4 节。 |
| D3 | API 渲染出的是带 `Z` 偏移量的 RFC 3339。Go 的 `encoding/json` 本来就是这样序列化 `time.Time` 的;一个为 nil 的 `*time.Time` 会渲染成 `null`。 |
| D4 | 每一次写入都使用 UTC——即 `time.Now().UTC()`。`db.New` 会对传入的任意 DSN 做规范化处理:设置 `loc=UTC`,这样驱动就不再用进程的本地时区去解读 `DATETIME` 的值;同时把 `time_zone` 设为 `+00:00`,这样 `NOW()` 和 `CURRENT_TIMESTAMP` 才会与应用程序保持一致。这项规范化是在这里强制执行的,而不是在构建 DSN 的地方,这样运营方自己提供的 DSN 或测试用的 DSN 就无法绕开它。 |
| D5 | 不再使用哨兵零值。`plugin.archived_at` 和 `plugin_release.yanked_at` 改为 `*time.Time`,"未归档"表示为 `NULL`。 |
| D6 | 列表排序和基于键集的分页仍然使用 `created_at, id` 这个组合。微秒级精度只是缩小了碰撞发生的概率;它并不能让单独一列的排序变得稳定,一个只比较时间戳的分页边界仍然可能跳过或重复某一行。 |
| D7 | 时长、配额和计数仍然是 `int64` / `BIGINT` / JSON 数字类型,字段名本身携带单位信息:例如 `TimeoutSeconds`、`duration_ms`。一个以单位命名的字段永远不会是 `time.Time`。 |
| D8 | 一个纯粹的日历日期——也就是一个不携带有意义的具体时刻的值——用 `DATE` 类型,格式如 `"2026-08-23"`。目前的 schema 中还没有这样的字段;之所以定下这条规则,是为了不让将来第一个出现的这类字段,变成一个时刻固定在午夜的 `DATETIME(6)`。 |
| D9 | 一项架构测试会强制执行 D1、D2、D5 和 D7,写法参照
  `internal/architecture/entity_identity_test.go` 的风格:不允许行结构体
  或核心模型中出现 `XxxAt int64`,不允许把时间戳列声明成 `bigint`,也
  不允许出现 `not null;default:0` 的时间戳列。 |

GORM 的 `autoCreateTime` 和 `autoUpdateTime` 本来就原生支持
`time.Time`,所以那 29 个带标签的列保留了原有行为,只是不再需要
`Unix()` 转换。

## 4. 为什么选择 `DATETIME(6)`

相对于被取代的那条规则所用的 `BIGINT` 秒数方案,理由已经在第 1 节说
清楚了:可读性、精度,以及一个真正携带含义的类型。

相对于 MySQL 里另一种表示时间点的类型 `TIMESTAMP`:

| | `DATETIME(6)` | `TIMESTAMP(6)` |
|---|---|---|
| 存储的值 | 写入时的字面值 | 写入时从会话时区转换为 UTC,读取时再转换回来 |
| 正确性是否依赖连接状态 | 否 | 是——同一行数据在不同的 `time_zone` 设置下读出的结果不同 |
| 取值范围 | 公元 1000 年到 9999 年 | 1970-01-01 到 2038-01-19 |
| 历史遗留的自动行为 | 没有 | 根据服务器模式的不同,`DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP` 可能被隐式应用到第一列上 |
| 存储空间 | 8 字节 | 7 字节 |

`TIMESTAMP` 会让存储的值依赖于写入它的那个客户端所在的时区——而一个
运营人员的 `mysql` 命令行会话和服务器进程本身未必处于同一个时区——而
且 2038 年这个上限,落在存储的审计数据可能存活的合理年限之内。反正
D4 已经把会话时区固定死了,这就抹掉了 `TIMESTAMP` 唯一的优势,却仍然
保留着它的范围限制。

多出来的这点存储范围,并不会带来真正的额外成本:`DATETIME(6)` 占
8 字节,恰好和它取代的那个 `BIGINT` 今天占用的空间一样多,所以索引和
行的大小都不会发生变化。

## 5. 范围

| 层 | 变化内容 |
|---|---|
| `internal/infra/db` | 63 个行结构体字段改为 `time.Time` / `*time.Time`;`quota_usage.go` 中的聚合逻辑和审计搜索改为接受 `time.Time` 类型的边界;`schema_migration.applied_at` 也包含在内 |
| `internal/infra/db` 的连接 | `utcDSN` 会改写 DSN 中的 `loc` 和 `time_zone`;`store.New` 要求驱动使用 `DATETIME(6)`,而不是 GORM 默认的 `DATETIME(3)` |
| `internal/core/model` | 73 个字段;JSON 标签保留原有的 `snake_case` 命名,只改变类型 |
| Service、Handler、调度器、Bootstrap | 116 处 `Unix()` / `time.Unix()` 转换被移除,或者被挪到展示层边界上。审计功能的 `since` / `until` 查询参数现在接受 RFC 3339 格式,而不再是纪元秒数 |
| `internal/mock` | 11 处声明,用于保持内存态存储的类型兼容性 |
| Portal、Desktop、`gui` | 18 个文件;`new Date(x * 1000)` 变为 `new Date(x)`,API 类型把 `number` 改为 `string`。Desktop 端不需要任何改动:它的 Wails 绑定本来就已经在使用 RFC 3339 |
| `internal/infra/workerclient` | `api_types.go` 中的 `CreatedAt`——Worker API 是两个 BuildMax 进程之间的线上契约,它会随着二者一起变化 |
| 文档与测试 | `data-model.md` 中关于时间戳的段落及其 62 行列描述、`conventions.md` 中的一条新规则、`internal/architecture/timestamp_test.go`,以及一条 changelog 记录 |

以上全部内容作为一次改动整体落地。一棵只转换了一半的代码树无法编译,
而一条双读路径正是 Alpha 阶段存在的意义之一,就是为了避免这种情况。

有两处是最初盘点时没有预料到的。`internal/core/agent` 中的
`Note.WrittenAt` 和 `Todo.WrittenAt` 本来就从来不是时间点——它们计的
是循环迭代次数——现在改名为 `WrittenIteration`,这正是 D7 对字段命名
的要求。而 Portal 的访问令牌过期截止时间仍然保留为一个数字：它由
`expires_in` 计算，并与访问令牌一起保存在模块内存中，而不是作为本文
所管辖三层中任何一层的时间点持久化。

## 6. 现有数据库

`AutoMigrate` 只负责增量式的 DDL,而把一列从 `bigint` 改成
`DATETIME(6)` 并不是增量式的变化:MySQL 会尝试把 `1755950000` 当作
一个日期字面量来读取,结果要么直接拒绝,要么存成零值。
`internal/infra/db/migration.go` 中的 `var migrations []Migration`
目前是空的——entity identity 那次改动当初也采取了同样的立场——而且
记录迁移的那个钩子是在 `AutoMigrate` *之后*才运行的,这时候再想转换
一个 `AutoMigrate` 已经改动过的列,已经太晚了。

所以:一个 Alpha 阶段的数据库应当被重建,而不是被转换。本次不会附带
任何转换用的迁移脚本。如果一个运营方想要保留某个特定的数据库,就需要
在升级之前自己动手转换,逐列进行:新建一个 `DATETIME(6)` 列,执行
`UPDATE t SET new_col = FROM_UNIXTIME(old_col)`,删掉旧列,再重命名
新列。之所以把这一点写清楚,是为了不让任何人在升级过程中才意外发现
这件事。

如果未来某次改动确实需要一个真正在 `AutoMigrate` 之前执行的步骤,
那个执行顺序方面的钩子应当作为一项独立的决策来对待,而不是在这里
悄悄加进去。

## 7. 现状与开放问题

已实现。`internal/architecture/timestamp_test.go` 针对行结构体、核心
模型和 agent 包,强制执行 D1、D2、D5 和 D7。

**开放问题——RFC 3339 Nano 可变的精度。** Go 把 `time.Time` 序列化为
RFC 3339 Nano 格式,这种格式会去掉末尾的零:因此 `2026-08-23T14:30:00Z`
和 `2026-08-23T14:30:00.123456Z` 都可能出现,取决于具体的值。代码树中
每一个消费方用的都是 `Date` 或者 `time.Parse` 来解析,二者都能处理这
两种形式,所以目前保持默认行为不变。如果将来某个消费方确实需要固定
宽度的输出格式,那应该是针对某一个类型单独写一个自定义的序列化器,
而不是继续使用整数的理由。

**开放问题——CLI 和 TUI 的展示方式。** 那些原本打印 `time.Unix(...)`
的命令,现在把一个 `time.Time` 格式化为本地时间——比如
`util.FormatMinute`、运营方授权表,以及登录码过期时间那一行。这只是
一次机械式的转换,而不是一次重新设计:每个命令到底应该给人展示什么,
仍然是一个需要逐个命令单独考虑的问题。
