## 1. 目的

BuildMax 拥有一个基础的 Agent 运行时，以及三个面向用户的界面：

- Agent Core
- CLI/TUI
- Desktop
- Portal

当前的产品定位是：

> BuildMax 是一个开箱即用、可私有化部署的企业级 Agent 平台，由一个共享的 Agent Core 驱动。CLI 和 Desktop 直接暴露本地的单 Agent 能力；Portal 则把同一份能力面向 Space 落地为可运营的协作、Workflow、治理和结果管理。

这不是在"本地 Agent"和"Space 工作区"之间做二选一。用户既可以只使用本地界面,也可以为公司部署 Portal，或者两者一起使用。

## 2. 产品分层

### 2.1 Agent Core：基础层

Agent Core 是根本性的产品能力。

主要职责：

- 运行共享的 LLM/工具调用循环
- 提供具备文件感知能力的执行
- 组装工具、MCP、技能、subagent、会话和模型配置
- 同时支持本地交互式使用和远程 worker 的 Task 执行

所有重要的 Agent 能力都应该首先落地在这里，或者设计成可以在这里共享。CLI、Desktop 和 worker 的 Task 运行都不应该各自演化出独立的 Agent 实现。

### 2.2 CLI：本地 Agent 执行器

CLI 是最快捷的本地执行界面。

主要职责：

- 针对当前本地工作区运行一个 Agent
- 支持终端原生的工作流程
- 支持提示模式、会话、脚本化和开发者自动化

CLI 应当始终保持：

- 直接
- 可组合
- 本地优先
- 让技术用户用起来顺手

### 2.3 Desktop：本地个人 Agent 工作台

Desktop 是围绕同一个 Agent Core 打造的本地个人工作台。

主要职责：

- 围绕与 CLI 相同的本地执行角色，提供更丰富的本地界面
- 让本地会话、本地工作区、输出查看和结果处理比在终端里更轻松
- 在有用的地方连接 Portal，但不继承 Portal 的管理范围

Desktop 应该给人的感觉是：

> 一个使用 Agent Core 的舒适本地场所

而不是：

> 又一个用来管理 Space 工作的场所。

### 2.4 Portal：企业运营层

Portal 是同一个 Agent Core 之上的企业/Space 运营层。

主要职责：

- Space
- Issue
- Workflow
- Agent 定义
- Space 文件
- 结果与 Artifact
- 治理

Portal 拥有 Space 运营模型的所有权：

- 管理 Space、成员、角色和共享资源
- 把 Issue 作为面向用户的工作对象来管理
- 定义、发布和查看 Workflow
- 追踪 Task 运行、Artifact、用量，以及未来的审计/历史记录
- 提供权威的 Space 工作区视图

## 3. 定位决策

Desktop **不应该**变成 Portal 的本地翻版。

如果完全对齐 Portal，就意味着 Desktop 需要管理：

- Issue
- Workflow
- Space 设置
- 成员
- 角色
- 治理
- 云端执行历史

这超出了一个本地应用应有的自然边界，也会造成产品层面的混乱：

- 用户会有两个地方管理同一批 Space 对象
- Desktop 会变成 Portal 的本地复制品
- 云端管理功能会稀释本地优先带来的价值
- 实现复杂度会上升，却无助于让用户的心智模型更清晰

相反，Desktop 应该在"直接使用 Agent"这条轴上与 CLI 对齐：

- 本地工作区
- 本地 Agent 执行
- 本地会话
- 本地工具
- 本地文件

但 Desktop 应该提供比 CLI 更具视觉化、更持久的体验。

Portal 应该在执行能力上与同一个 Agent Core 对齐，它的附加价值在于企业级运营：在各个 Space 之间组织、复用、治理和观察这份能力。

## 4. 功能矩阵

| 能力 | Agent Core | CLI | Desktop | Portal |
| --- | --- | --- | --- | --- |
| Agent 工具调用执行 | 强 | 强 | 强 | 通过 worker 实现,强 |
| 本地工作区 Agent 执行 | 基础能力 | 强 | 强 | 非主要场景 |
| 终端脚本化与自动化 | 基础能力 | 强 | 弱 | 无 |
| 本地会话历史 | 基础能力 | 中等 | 强 | 独立的 Space 会话 |
| 本地文件上下文与编辑 | 基础能力 | 强 | 强 | Space 文件空间,而非本地磁盘 |
| 丰富的结果查看 | 基础能力 | 中等 | 本地体验强 | Space/云端体验强 |
| Space 与成员管理 | 无 | 无 | 无 | 强 |
| Issue 管理 | 无 | 无 | 仅有轻量收件箱/启动入口 | 强 |
| Workflow 编写 | 无 | 无 | 无 | 强 |
| Workflow 触发 | 执行底座 | 未来可能支持 | 对已发布 Workflow 可选支持 | 强 |
| Task/Run 可见性 | 运行时数据 | 弱 | 可选的、仅限已分配的子集 | 强 |
| Artifact 浏览 | 运行时数据 | 本地/简单 | 本地体验强,可选云端产出 | 云端产出体验强 |
| 离线/私有本地使用 | 支持 | 强 | 强 | 取决于部署方式 |
| 治理、配额、审计 | Hook/契约 | 无 | 至多只读提示 | 强 |

## 5. Desktop 的范围

### 5.1 范围之内

Desktop 应该聚焦于：

- 本地聊天会话
- 本地工作区选择
- 具备本地文件感知能力的 Agent 执行
- 会话的列表/详情/搜索
- 流式回复
- 本地结果与 Artifact 查看
- 本地设置与模型选择
- 在合适的场景下配置本地 MCP/工具
- 可选地登录 Portal 以获得身份和同步
- 可选地从 Portal 获取"已分配工作收件箱"
- 可选地把本地工作结果附加回某个 Portal Issue

### 5.2 范围之外

Desktop 不应该拥有：

- 完整的 Issue 跟踪管理
- Workflow 的编写或生命周期管理
- Space 成员管理
- 角色与权限管理
- 配额管理
- 审计/事件管理
- 云端工作区管理
- 成为 Portal 的完整离线副本

### 5.3 桥接范围

Desktop 可以在有限的范围内与 Portal 桥接：

- 把分配给我的 Issue 显示为收件箱
- 在浏览器中打开某个 Portal Issue
- 从某个已分配的 Issue 启动一次本地会话
- 把本地结果附加或总结回某个 Issue
- 在有助于本地工作的情况下触发某个已发布的 Workflow
- 显示与我的本地 Task 相关的云端结果链接

这种桥接应当被定义为：

> 接收云端工作，在本地完成工作，再把结果送回去

而不是：

> 在本地管理云端工作区。

### 5.4 本地工作台边界

Desktop 工作台把用户工具（终端、文件和 diff tab）放在 Agent 旁边，并允许多个聊天会话同时运行。以下三项决定使这些能力不会模糊权限边界；具体行为见 [Desktop 架构](../contribute/architecture/desktop.md#工作区-tab窗格与终端)。

- **终端 tab 是用户的 shell，不是 Agent 的 Bash 工具。** 它使用用户未经清洗的环境且不启用沙箱，是 CLI 默认关闭沙箱这一姿态的交互式对应物（[沙箱边界](沙箱边界.md) §10）。Agent 的 Bash 工具有作用域、可沙箱化、有上限，并属于一次运行的权限和 trace。两者分开，既避免让用户输入经过 Agent 策略，也避免借“用户”终端洗白 Agent 权限，因此没有任何 Agent 读取终端输出。按需为终端启用沙箱是以后可能的选项，而不是要求。
- **工作台 tab 仅限本地。** 终端、文件和 diff tab 通过进程内 Wails 桥接访问工作区，没有路由、socket 或服务器绑定，因此 Portal 和 worker 都无法驱动它们。
- **并发会话把写入隔离留给用户。** 运行按 Session 划分，因此同一 Project 的不同 Session 可以同时运行，而两个 Agent 写同一个工作区可能互相覆盖。用户已经有应对工具：Session 可以在自己的 Git worktree 中运行。在一个共享工作区里运行两个 Agent 是用户的选择，就像对同一工作区打开两个终端一样；平台不会在能够强制隔离之前扣留并发能力。终端、文件和 diff tab 不涉及写入者问题：终端是独立进程，保存是用户直接写入，diff 是只读的。

## 6. 产品心智模型

推荐的产品说明：

> BuildMax 是一个可私有化部署的企业级 Agent 平台，由一个共享的 Agent Core 驱动。CLI 和 Desktop 把这个核心在本地暴露出来;Portal 则让它面向 Space 落地为可运营的能力。

稍长一点的版本：

> BuildMax 让企业开箱即得实用的 Agent 能力。用户可以通过 CLI 或 Desktop 在本地运行 Agent，同时公司也可以部署 Portal，把同一份能力组织进 Space、Issue、Workflow、共享文件、结果、配额和治理之中。

针对各界面的版本：

> CLI 是最快捷的本地 Agent 界面。Desktop 是本地个人 Agent 工作台。Portal 是同一个 Agent Core 的企业运营层。

针对 Desktop 的一句话：

> Desktop 是用于个人 Agent 执行的本地 AI 工作台。它可以连接 Portal 以获得身份和已分配的工作,但它不管理 Space 的运营体系。

## 7. 对路线图的影响

### 7.1 Desktop 的近期优先事项

优先选择能够增强本地执行能力的功能：

1. 更好的会话管理。
2. 工作区选择器和最近使用的工作区。
3. 更完善的富文本聊天与流式体验。
4. 本地输出/结果查看器。
5. 本地文件/diff 感知能力。
6. 模型与本地工具设置。
7. 把登录 Portal 作为一个可选的连接项。

### 7.2 Agent Core 的优先事项

优先选择能够同时增强所有界面的功能：

1. 更可靠的工具执行与上下文窗口处理。
2. 同时适用于本地和 worker 执行的 MCP/工具配置。
3. 把技能和 subagent 作为共享的运行时能力。
4. 更好的 Artifact/结果生成约定。
5. 更安全的文件编辑与 diff 可见性。
6. 本地和 Portal 工作流都需要的运行时可观测性。

### 7.3 Portal 桥接的优先事项

在本地工作台足够扎实之后，再添加范围有限的云端桥接功能：

1. 已分配 Issue 的收件箱。
2. 从某个 Issue 启动本地会话。
3. 把总结/结果送回某个 Issue。
4. 把本地会话与云端 Issue 关联起来。
5. 在 Portal 中打开云端 Issue/Workflow/结果。

### 7.4 应当避免的路线图事项

除非产品方向发生明确变化，否则应避免把以下内容加入 Desktop：

- 完整的 Issue 增删改查
- Workflow 构建器
- Space 设置
- 成员管理
- 配额仪表盘
- 审计日志界面
- 重复的 Portal 导航树

这些都应该属于 Portal。

---

## 8. 决策小结

BuildMax 应该以 Agent Core 为先。

CLI 和 Desktop 呈现直接使用 Agent 的本地体验。Portal 则把同一份 Agent 能力打包成面向 Space、Workflow、治理和结果的企业级平台。Desktop 可以与 Portal 集成，但这种集成应当刻意保持狭窄：从 Space 体系中接收工作，在合适时于本地执行，再把结果送回去。

Portal 仍然是 Space 协作、Issue/Workflow 管理、共享结果和治理方面的权威数据来源。
