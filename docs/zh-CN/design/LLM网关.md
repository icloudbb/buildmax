## 1. 决策

BuildMax 将支持两种明确的 LLM 连接模式:

| 模式 | LLM 传输方式 | 供应商凭证的持有者 | 预期用途 |
|---|---|---|---|
| `direct` | CLI、Desktop 或 Worker 直接调用一个与 OpenAI 兼容的端点 | 运行 Agent 的那台机器 | 本地优先、离线、BYOK(自带密钥),以及已经自行运营网关的部署 |
| `managed` | 一个 BuildMax 远程 LLM 客户端调用 BuildMax Server | 该 BuildMax 部署 | 集中管理凭证、Space 模型策略、用量、配额和审计元数据 |

托管模式是可选的。直接模式仍然是一条完整的一等路径,不需要 BuildMax
Server。两种模式之间不存在自动回退,因为悄悄改变提示词和源代码实际经过的
路径,会违背运营方的预期。

Server 端的这个端点是一种 **BuildMax 推理协议**,而不是一个面向公众、与
OpenAI 兼容的透传通道。`internal/core/llm.LLMClient` 有一个新的远程实现,
负责在进程内契约与该协议之间做转换。Agent 循环和工具仍然运行在发起调用的
那一方。

目录中的一个目标会声明它所使用的线协议,网关据此构建匹配的客户端。
OpenRouter、LiteLLM,或其他由运营方自行管理的兼容网关,仍然可以通过
`openai_compatible` 提供广泛的供应商覆盖;一个目标也可以改为使用 OpenAI
Responses(`openai`)或 Anthropic Messages(`anthropic`)。新增一个适配器
必须通过的检验标准在第 13 节,而且没有改变:一个适配器的正当理由,是共享
契约能够表达的某项能力,而不是某个供应商拥有一个 API。参见
[llm-provider-adapters.md](LLM提供商适配器.md)。

拥有这个网关的理由是 **BuildMax 的治理能力**,而不是供应商数量:

- 供应商凭证不需要分发给用户或 Worker;
- 一个 Space 选择的是稳定的模型别名,而不是供应商的模型标识符;
- 每一次托管调用都可以被授权、计量、限流,并与一次 BuildMax 的 Run 关联;
- 供应商路由可以在不重写客户端配置的情况下变化。

## 2. 产品目标

一个私有 BuildMax 部署的运营方,应当能够在不向用户分发供应商密钥的情况下,
为某个 Space 提供获批准的模型。运营方应当知道是哪个 Space、哪个用户发起了
一次托管调用,使用的是哪个获批准的模型目标,报告了多少 token 用量,以及
这次调用是否成功。

一个本地用户仍然必须能够只凭一份 `settings.yaml` 和一个供应商或本地推理
端点来运行 CLI 或 Desktop。托管模式不能把 Server 的可用性、身份验证或
Space 成员资格变成本地使用的前提条件。

## 3. 当前基线

共享边界已经存在:

- `internal/core/llm.LLMClient` 是 Agent 循环所依赖的契约;
- `internal/infra/llm` 是它目前唯一与 OpenAI 兼容的实现,负责流式传输、
  重试、超时、错误分类和用量采集;
- `internal/agentapp` 负责解析已配置的模型并缓存客户端;
- `settings.yaml` 中包含 CLI 和 Desktop 使用的模型列表;
- `server.yaml` 中包含唯一的一个 `conversation.model`,供 Server 处理
  Tier 1 对话、供 Worker 处理 Task 的 Run 时使用。

目前各个界面的调用路径并不相同:

| 界面 | Agent 循环运行在哪里 | 供应商调用发起自哪里 | 凭证来源 |
|---|---|---|---|
| CLI / TUI | 本地进程 | 本地进程 | `settings.yaml` |
| Desktop | Desktop 进程 | Desktop 进程 | `settings.yaml` |
| Portal Tier 1 | Server | Server | `server.yaml` |
| Task 的 Run | Worker | Worker | `server.yaml` 加上环境变量覆盖 |

目前的配额统计以 Run 为中心。它汇总 Task 的 Run 的 token 字段和 Task
标题的 token 字段。Tier 1 对话调用和本地调用不会产生一份完整的服务端
LLM 调用账本。仅靠一个网关本身并不能解决这个问题;调用级别的持久化是
本设计选择方案的一部分。

身份验证方面也存在这份设计不应回避的局限。CLI 和 Desktop 默认会把访问
令牌和刷新令牌存放在操作系统的凭证存储中,或者在没有这类存储的机器上直接
存放在 `auth.json` 里——无论哪种情况,现在都已经有了刷新流程,因此一次
登录能存活得比一个访问令牌更久,而且一个会话可以被撤销。访问令牌本身则
仍然不能被撤销:因为没有撤销列表,一个已签发的令牌会一直有效到过期为止。
Space 成员资格的检查发生在服务端,可以用来收回对某个 Space 的访问权限,
但访问令牌不能被描述成一个可以独立撤销的网关凭证。

## 4. 为什么需要一个 BuildMax 网关

### 4.1 凭证托管

直接模式要求执行机器持有一个上游凭证。这对 BYOK 场景是合适的,但如果
运营方想要集中轮换凭证、或者希望 Worker 运行时不持有任何通用的供应商
访问权限,这种模式就不合适了。

托管模式用一个 BuildMax 凭证取代上游凭证,这个凭证的权限受到 Server
授权和 Space 模型策略的共同限制。但它并不会让客户端变得完全无需持有
任何密钥。

### 4.2 Space 模型策略

目前,本地的模型条目直接选择供应商 URL 和供应商模型。而一个托管客户端
改为选择一个稳定的别名,比如 `default`、`fast` 或 `reasoning`。Server
会把这个别名映射到一个由运营方定义的目标,并拒绝该 Space 不可用的别名。

客户端绝不能向托管端点提交上游 URL、供应商凭证,或不受限制的供应商模型
标识符。这样能让模型选择始终处于 Space 授权边界之内,也能防止网关变成
一个经过身份验证的 SSRF 代理。

### 4.3 用量与配额

每一次托管调用都会创建或完成一条调用账本记录。这条记录支持用量展示、
配额评估、事故调查,以及最终的成本报告,同时不存储提示词正文。

一次简单的调用前配额检查,并不能构成严格的支出保证:并发的调用有可能
在各自的最终用量被写入之前就都通过了检查,而且推理开始之前也无法知道
确切的输出体量。第一版可以做到:拒绝已经超出配额的 Space,并在调用结束
后对已报告的用量进行核对。要做到严格的执行,还需要预留机制、逐次调用的
输出上限,以及并发控制,网关才能被称为对多租户场景是安全的。

### 4.4 供应商独立性

单纯为了覆盖更多供应商,并不足以构成建设这个组件的理由。现有客户端已经
可以指向 OpenRouter、LiteLLM、本地推理,或其他与 OpenAI 兼容的端点。

但网关仍然创造了一道有用的分隔线:客户端使用的是一种 BuildMax 协议和
稳定的别名,而 Server 端的模型路由器负责选择 `LLMClient` 的具体实现。
未来可以在这个路由器背后引入一个原生适配器,而不需要改动 CLI、Desktop、
Worker 或 Agent Core 的传输层代码。

## 5. 已考虑的方案

| 方案 | 优点 | 局限 | 决定 |
|---|---|---|---|
| 只保留直接调用 | 系统最小;本地隐私和可用性最好 | 供应商密钥、策略和用量仍然分散各处 | 保留为 `direct` 模式 |
| 由 Server 下发模型配置 | 集中管理别名,便于接入 | 凭证仍然会到达客户端;调用仍然无法计量 | 不构成一个独立方案 |
| 与 OpenAI 兼容的透明代理 | 现有客户端只需改动 `api_url`;也方便第三方调用方使用 | 暴露了一个不必要地宽泛的公共契约,泄露了上游语义,使 BuildMax 自身策略和错误处理难以演进 | 不作为最初的端点 |
| BuildMax 托管推理协议 | 内部契约稳定、授权明确、错误标准化,并为供应商能力的演进留出空间 | 需要一个远程客户端和协议测试 | 采纳 |
| 现在就实现所有原生供应商 SDK | 最大限度地利用供应商特有功能 | 造成一个永久的兼容性表面,而当前核心并无此需求 | 推迟 |
| 要求使用 LiteLLM,不构建 Server 网关 | 把供应商归一化的工作外包出去 | 无法整合 BuildMax 的身份、Space、Run 或配额体系 | 是一种受支持的部署选项,但不是产品层面的决定 |

如果 BuildMax 日后打算向第三方应用提供服务,可以再新增一个与 OpenAI
兼容的公开端点。那是一个独立于"向 BuildMax 客户端提供模型"之外的产品与
安全决策。

## 6. 架构与归属

```text
CLI / Desktop ── RemoteLLMClient ─┐
                                  │
Worker ──────── RemoteLLMClient ──┼─ HTTP auth entry points
                                  │          │
Portal Tier 1 ────────────────────┘          ▼
                                      LLM Gateway service
                                             │
                                model policy + call ledger
                                             │
                                             ▼
                                        Model router
                                      ┌──────┼──────┐
                                      │      │      │
                              OpenAI-compatible   future native adapters
                                      │
                         OpenRouter / LiteLLM / provider / local model
```

这张图展示的是逻辑上的复用关系,而不是一次 HTTP 自调用。Server 自身处理
Tier 1 推理调用时,是在进程内直接调用模型路由器和计量服务的。它绝不能
把请求再发回自己对外的 HTTP 监听端口。一个远程 Worker 使用的是经过
Worker 身份验证的 HTTP 入口点,因此它不需要持有任何上游凭证。

| 关注点 | 归属 |
|---|---|
| 消息、工具定义、工具调用、用量契约 | `internal/core/llm` |
| Agent 循环与本地工具执行 | `internal/core/agent` |
| 本地模型装配与远程客户端选择 | `internal/agentapp` |
| 与 OpenAI 兼容的供应商调用 | `internal/infra/llm` |
| 远程 BuildMax 协议客户端 | `internal/infra/llmremote` 或等价的基础设施包 |
| 别名解析、Space 策略、配额协调、调用账本 | 新增的 `internal/service/llmgateway` |
| 用户端和 Worker 端的 HTTP 适配器 | `internal/server/handlers` |
| 进程装配与供应商凭证 | `internal/bootstrap` 和 `internal/config` |

`internal/core` 不得导入 Server、配置或供应商相关的包。网关消费的是核心
契约;它不会把网络策略或基础设施相关的内容搬进领域层。

## 7. 模型目录与解析

Server 需要一份由运营方拥有、独立于单一 Tier 1 模型的模型目录。目录中的
每一条记录包含:

- 一个不透明的目录 ID;
- 一个面向运营方的名称;
- 一种供应商类型或客户端工厂;
- 上游端点及凭证引用;
- 上游的模型标识符;
- 上下文窗口和超时时间;
- 已声明的能力;
- 启用状态。

Space 策略把一个或多个稳定别名映射到目录中的条目,并指定一个默认值。
别名是托管客户端唯一可以使用的模型标识符。因此解析过程是:

```text
(space_id, alias) -> authorized catalog entry -> LLMClient
```

这份目录就是 `llm_model` 表,通过 `buildmax-server model` 编辑。它不是
普通配置:它保存着供应商凭证,不应该随着一份 Kubernetes ConfigMap 被携带,
而且它会在服务器运行期间发生变化。凭证保存在这一行记录里,只由构建供应商
客户端的那条查询读取,因此静态存储时的保护责任在于运营方的备份策略,而
不是配置文件本身的策略。

Space 策略同样应该进入数据库,因为 Space 才是它的所有权边界。在这一点
实现之前,`server.yaml` 中一份部署级别的别名映射,可以把一小组经运营方
批准的模型暴露给每一个 Space。`conversation.model` 仍然是 Server 自己的
引导模型,这样在目录还一条记录都没有的时候,部署也能先应答对话请求。

供应商能力必须被显式声明,而不能从供应商名字里推断出来。第一版能力集
与当前核心契约一致:文本对话、工具调用、流式文本,以及用量报告。请求
如果需要一项未被声明的能力,应当在发出上游调用之前就失败。

## 8. 托管协议

只有在 `internal/server/handlers/routes.go` 中注册过的确切路由,才是
权威的。目前提议的用户端入口点是:

```text
GET  /api/spaces/{space_id}/llm/models
POST /api/spaces/{space_id}/llm/completions
```

Worker 端的入口点作用域限定在一次 Task 的 Run 上:

```text
POST /api/worker/task-runs/{task_run_id}/llm/completions
```

两个 HTTP 适配器调用的是同一个服务。用户端路由会在每一次调用中对当前
用户做身份验证,并核验其 Space 成员资格。Worker 端路由则从服务端状态中
推导出 Space、Task 和 Run,它不会信任由 Worker 自己提供的归属字段。

### 8.1 请求

这份带版本号的请求 DTO 只包含 BuildMax 能理解的字段:

```json
{
  "call_id": "client-generated idempotency key",
  "model": "fast",
  "messages": [],
  "tools": [],
  "stream": true,
  "call_profile": "agent_turn",
  "metadata": {
    "surface": "desktop",
    "session_id": "optional correlation value"
  }
}
```

这份 DTO 反映的是 `core/llm` 的语义内容,但它是一份带版本号的线上契约,
而不是把 Go 结构体直接暴露成 JSON。初始版本会拒绝未知的请求字段。不接受
供应商特定的请求体、凭证、URL,以及任意的生成参数。

`call_id` 标识的是一次逻辑上的调用。当一次连接在客户端得知 Server 是否
已经接受这次调用之前就失败时,它支持进行重复检测。它并不是重放一次
部分流式生成内容的许可。

`call_profile` 是调用方声明这次调用是为了什么——`agent_turn`、`title`、
`compaction`、`evaluation` 或 `probe`。它是操作层面的输入,而不是授权层面
的输入:Server 会把它和已获批准目标自身的缓存策略结合起来,因此仅仅命名
一个 profile,并不能选中一种运营方没有批准的缓存模式、保留策略或缓存键。
这个字段是可选的、附加性质的,可以省略;此时 Server 没有任何证据表明这段
前缀将来会被读取,而这不足以构成写入一次缓存的理由。一个 Server 不认识
的非空取值会被直接拒绝,而不是被默默接受,这样一个更新的客户端就不会
误以为自己要求的是一件事、实际却被按另一件事计费。参见
[prompt-cache-control.md](提示缓存控制.md)。

元数据是用于关联的上下文信息,而不是授权层面的输入。Server 从身份验证
结果中推导出用户 ID 和 Space ID,并在 Worker 路由上推导出 Task 的 Run
身份。

### 8.2 非流式响应

```json
{
  "content": "...",
  "tool_calls": [],
  "usage": {
    "prompt_tokens": 100,
    "completion_tokens": 20,
    "total_tokens": 120
  }
}
```

这份响应刻意返回的是 BuildMax 自己的工具调用和用量结构。它不会暴露上游
的响应体,也不会暴露携带供应商凭证的响应头。

### 8.3 流式响应

流式传输使用带类型的 SSE 事件,而不是逐字节透传的上游数据块:

| 事件 | 载荷 | 含义 |
|---|---|---|
| `delta` | 内容增量 | 需要交付给本地流接收端的文本 |
| `result` | 最终内容、工具调用、用量 | 完成这次 `LLMClient` 调用 |
| `error` | 稳定错误码、安全的错误信息、是否可重试的标志 | 以错误方式终止这次调用 |

现有的核心契约会在流式传输过程中暴露内容增量,并在流结束后返回组装好的
工具调用。托管协议应当保持这份契约,而不是暴露供应商特定的工具调用数据块。

每一个事件都会被及时刷新发送。客户端断开连接会取消上游的调用上下文。
在受支持的部署中使用的反向代理,必须禁用响应缓冲,并且允许比所配置的
模型调用超时更长的空闲超时时间。

### 8.4 错误

Server 会为身份验证、Space 访问、未知别名、不支持的能力、配额、超时、
取消、速率限制、上游身份验证、上游可用性以及格式错误的上游响应,返回
稳定的 BuildMax 错误码。

安全的供应商细节可能会被记录在 Server 的诊断信息里,但默认不会返回原始
的供应商错误体。这些错误体可能包含账户标识符、端点细节、请求片段,或者
策略信息。远程客户端会把这套稳定的错误分类,映射为与本地供应商客户端
相同的、人类可读的行为。

## 9. 流式传输、重试与幂等性

只有直接调用上游供应商的那个组件,才拥有供应商重试策略的所有权。在托管
模式下,那就是 Server 端的供应商客户端。远程客户端不得围绕一次已完成或
部分流式传输的网关调用,再叠加一层独立的重试循环。

以下规则适用:

1. 在第一个响应增量被发出之前,Server 可以按照供应商客户端的策略重试
   上游调用。
2. 一旦一个增量到达调用方之后,任何层都不会自动重试。
3. 一个正在执行中的重复 `call_id`,只有在协议明确支持挂接的情况下才会
   挂接到原调用上;否则会返回一个冲突错误。
4. 一个已经完成的重复 `call_id`,可以返回它存储的终态元数据,但在第一版
   中不要求重放完整的生成内容。
5. 客户端的取消操作会经过处理器和路由器,一路传播到上游请求。
6. 每一次尝试和这次逻辑调用本身,在 Server 的诊断信息中都是可区分的,
   这样重试就不会虚增用户可见的调用计数。

背压必须是有界的。一个缓慢或已断开连接的调用方,不能导致 Server 内存中
堆积无限增长的供应商增量队列。

## 10. 调用账本、配额与审计

每一次托管的逻辑调用,至少会记录以下内容:

| 字段组 | 数据 |
|---|---|
| 身份 | 调用 ID、Space ID、经过身份验证的用户 ID 或 Task 的 Run ID |
| 关联信息 | 界面、提供时的会话 ID、推导出的 Task 和 Run ID |
| 模型 | 请求的别名、解析出的目录 ID、供应商类型、上游模型标识符 |
| 时间 | 接受、上游开始、第一个增量、完成的各个时间戳 |
| 结果 | 状态、稳定的错误分类、重试/尝试次数 |
| 用量 | 提示、补全和总计的 token 数;用量是已报告、估算,还是不可用 |

默认情况下,提示词文本、工具参数、工具结果、源代码和生成内容都不会进入
调用账本。持久化的本地轨迹仍然拥有 Run 的详细信息。任何未来的、经用户
选择开启的正文采集功能,都需要一份独立的关于保留期限、脱敏、访问控制和
数据分类的决定。

这份账本是托管调用的计费依据。现有的 Task 的 Run token 字段仍然是有用的
汇总信息,但汇总时必须避免把同一次 Worker 调用在账本里算一次、在 Task 的
Run 总量里再算一次。

配额执行会分阶段演进:

| 阶段 | 行为 | 保证程度 |
|---|---|---|
| 可见性 | 调用结束后记录实际报告的用量 | 仅用于统计 |
| 软执行 | 当已记录用量已经超限时拒绝调用;限制请求时长和输出规模 | 并发调用仍可能超出限额 |
| 预留执行 | 在派发之前预留估算的额度,完成之后再核对 | 超出限额的幅度是有界的 |
| 多租户控制 | 增加逐 Space 和全局的并发/速率限制 | 保护 Server 容量,限制吵闹的邻居 |

在预留执行和并发控制真正建成之前,文档不得声称这个网关能提供严格的支出
上限,也不得声称它对不受信任的多租户 SaaS 部署是安全的。

审计事件记录的是配置和授权层面的动作,例如模型策略变更、被拒绝的模型
使用请求,以及凭证管理。高频的、逐次调用产生的操作记录,应当放进调用
账本,而不是放进治理层面的审计日志。

## 11. 身份验证与安全

托管推理提高了 Server 的数据分类等级,因为提示词、工具模式和工具结果都
要经过它。威胁模型必须涵盖:

- 提示词和源代码在日志、轨迹、崩溃报告和指标中暴露;
- 凭证通过配置、请求头或上游错误信息泄露;
- 跨 Space 的模型访问;
- 无边界的请求体、工具模式、流,以及并发数;
- 由用户可控的路由所导致的上游端点 SSRF;
- 一个 Worker 在其被分配的 Run 之外使用它的基础设施凭证;
- 调用持续时间超过一个访问令牌的有效期。

必需的控制措施包括:

- 在受信任的本地开发环境之外强制使用 TLS;
- 每一次用户调用都要经过身份验证和 Space 授权;
- Worker 调用使用的 Task、Run、Space 和模型策略均来自服务端推导;
- 只允许运营方配置的上游端点;
- 对请求、消息、工具模式、响应、超时和并发设置边界;
- 提示词正文不进入正常的访问日志或调用账本记录;
- 对凭证进行脱敏,并对错误信息做安全的规范化处理;
- 取消操作的传播,以及有界的流式队列;
- 针对调用元数据的明确保留策略。

原来那种共享的 Worker 令牌,不足以作为一个模型网关的合格凭证,因为它
不局限于某一次具体的 Run,所以 Worker 路由从一开始就没有接受过它。取而
代之的是一个运行令牌:一种在 Run 被派发时签发的、指名用户、Space 和 Run
的短期凭证。参见 [worker-run-token.md](Worker运行令牌.md)。此后这种共享
令牌已经从每一条 Worker 路由中移除,因此运行令牌是 Worker 持有的唯一
凭证。

用户访问令牌当时默认有效期为七天(现为 15 分钟),对于早期的可信部署试验而言这是可以接受的,
但还算不上一套完整的托管客户端生命周期。刷新机制此后已经上线,因此一次
登录能比一个访问令牌活得更久,而且一个会话可以被撤销。在把这项功能称为
生产就绪之前,仍然缺失的是原生的密钥存储、一个绝对的会话生命周期,以及
一个带受众范围(audience)限定的凭证——参见
[client sessions and API credentials](../proposals/client-sessions-and-api-credentials.md)。

## 12. 客户端配置与用户体验

托管模式必须在模型配置里被明确标示出来。如果复用 `api_url` 字段、把一个
登录用的 JWT 塞进 `api_key` 里,就会把两套凭证体系混在一起,把令牌重复
写入 `settings.yaml`,并让直接模式和托管模式的行为难以解释清楚。

一个示意性的形态是:

```yaml
models:
  - name: Space Fast
    model: fast
    transport: buildmax
    server_url: https://buildmax.example.com
    space_id: tm_example
```

上面这些具体字段只有在真正实现之后才会成为面向用户的文档。远程客户端从
`auth.json` 中读取身份验证信息;模型条目本身不会复制这份凭证。
`buildmax login` 命令和 Desktop 的登录流程负责建立 Server 身份,而模型
发现功能会列出所选 Space 可用的那些别名。

直接模式的条目保留它们现有的供应商 URL 和 API key 形态。如果一个直接
模式条目和一个托管模式条目拥有相同的显示名称,界面还必须显示传输方式
以及 Server/Space 上下文,这样用户才能知道数据将流向何处。

从托管模式回退到直接模式绝不会隐式发生。运营方或用户可以配置两个条目
并在其间选择,但 Server 出现故障时,绝不能悄悄把本应受治理的流量重定向
到某个人的私人供应商密钥上。

## 13. 供应商策略

模型路由器会针对已解析目标所声明的协议构建对应的客户端——
`openai_compatible`、`openai`、`anthropic` 或 `ollama`。运营方可以让一个
兼容型目标指向 OpenRouter、LiteLLM、一个兼容的供应商端点,或者本地推理。
BuildMax 不承诺每一项供应商特有的功能,都能在经过一层 OpenAI 兼容中介
之后完好保留。

`ollama` 是唯一**不需要凭证**的目标类型:它指向的是部署可以直接访问的
一个本地运行时,而授权这次调用的依据是"能够访问到这个守护进程",这是
部署所在网络的属性,而不是目录本身的属性。`llm.ProviderNeedsCredential`
就是这项豁免被声明的地方,而且它有意只覆盖这一种供应商——一个托管型
目标如果缺失密钥,那是一种配置错误,必须在选择阶段就失败,而不是发出
一个未经身份验证的请求。这类目标的其他一切都不受影响:运营方照常添加它,
一个 Space 仍然只能通过别名访问它,每一次调用仍然会进入账本。参见
[local-ollama-provider.md](本地Ollama提供商.md)。

适配器的规格定义在 [llm-provider-adapters.md](LLM提供商适配器.md) 中。
它们没有对这个协议做任何改动:`llmwire` 本来就携带消息、工具定义、工具
调用和用量信息,所以它早已描述了网关能够服务的每一种协议。

一个原生供应商适配器,只有在以下条件全部成立时才有正当理由:

1. 是共享的 Agent 产品需要某项能力,而不是某个单一界面想要一个供应商
   特定的捷径;
2. `core/llm` 已经有一种与供应商无关的方式来表达这项能力;
3. 这项能力会实质性地改变正确性、质量、延迟或成本;
4. 已受支持的兼容型上游无法可靠地提供这项能力;
5. 这个适配器具备契约测试、流式传输测试、用量测试、错误测试和工具调用
   测试。

供应商能力的例子包括结构化内容块、提示缓存控制、推理元数据、多模态
输入,以及供应商特定的用量信息。它们不会仅仅因为某个供应商的 API 暴露了
它们,就被纳入最初版本的网关。

## 14. 运维影响

托管模式把 Server 变成了一个推理数据平面。相比它目前的协调型工作负载,
它会增加长连接的响应、更多打开的连接、上游出网流量、背压、供应商速率
限制,以及 Server 出现故障时更大的爆炸半径。

因此,部署方面的工作必须涵盖:

- 反向代理的流式传输与缓冲配置;
- 请求、上游、空闲和优雅关闭方面的超时设置;
- 连接数、goroutine 数量和内存的容量规划;
- 全局以及逐 Space 的并发限制;
- 供应商出网策略和密钥注入;
- 能够区分 Server、路由器和上游各自故障的健康信号;
- 覆盖调用速率、首字节延迟、时长、用量可用性、取消次数,以及稳定错误
  分类的各项指标。

额外增加的这一跳网络开销,相对于推理本身预期是很小的,但在一次 Agent
的多轮运行中会累积放大。必须依靠实际测量而不是这个假设,来判断所支持的
部署拓扑是否可以接受。

目录投入使用后又暴露出两项运维需求。供应商自己的错误信息从不会到达调用方或
台账,它们只保留稳定的错误分类;但它仍是判断问题出在 key、模型 id 还是供应商
本身的唯一线索,因此网关会在服务端连同台账行的 ID 一起记录它。另外,目录中的
key 必须能原地替换:通过添加一个改了名的模型来轮换泄露或过期的 key,会改变每个
客户端所选用的名称。因此该行的凭证可以单独写入(两个命令界面上的 `set-key`,
以及 `PUT /api/admin/llm/models/{model_id}/credential`),而路由器以该行的
revision 作为客户端缓存键的一部分,使替换后的 key 在下一次调用时生效。

## 15. 交付计划

### M1. 契约与进程内路由器

- 在 `internal/core` 之外定义与供应商无关的路由器和模型解析接口。
- 增加一份运营方模型目录,以及部署级别的默认别名。
- 在路由器背后复用现有的、与 OpenAI 兼容的客户端。
- 让 Server 自身的 Tier 1 调用在进程内经过这个服务进行路由,而不改变
  外部行为。
- 测试别名、被禁用的目标、不支持的能力,以及不泄露密钥的错误信息。

### M2. 调用账本与非流式网关

- 增加调用账本的持久化契约及其数据库实现。
- 注册前面提议的用户端路由,附带 JWT 和 Space 授权检查。
- 实现非流式的托管调用,以及稳定的错误处理。
- 增加一个远程 `LLMClient`,并针对本地实现编写契约测试。
- 先记录用量、建立可见性,再谈配额执行。

### M3. 流式传输、取消与幂等性

- 增加带类型的 SSE 事件,并及时刷新。
- 传播断开连接导致的取消。
- 落实重试规则以及重复 `call_id` 的处理行为。
- 测试内容增量、最终的工具调用、用量、上游流中途失败、慢客户端,以及
  断开连接的情形。

### M4. 客户端发现与明确的托管模式

- 增加 Space 模型发现功能。
- 在 CLI 和 Desktop 中增加明确的直接/托管模式配置与选择。
- 从 `auth.json` 而不是 `settings.yaml` 中读取托管凭证。
- 记录数据流向、模型优先级、令牌过期,以及失败时的行为。

### M5. Worker 接入与治理

已完成:限定作用域为单次 Run 的入口点和凭证,以及从一个托管 Worker 身上
移除供应商凭证。按 Space 统计的运行令牌计数仍然独立于调用账本,因此配额
统计目前仍然只汇总 `task_run` 的总量——在解决重复计数问题之前,不要把
账本数据加进这个总和。

尚待完成:

- 增加软配额执行、有界请求、并发限制,以及面向运营方的诊断信息。
- 为模型策略和凭证的变更增加审计事件。
- 在创建时就把一个获批准的别名固定到某个 Task 或 Workflow 上,这样一次
  Run 使用的模型就是可复现的,而不是取决于派发那一刻部署的默认值。

### M6. 在有正当理由时引入严格配额或原生供应商

- 如果严格的支出上限成为产品需求,增加预留与核对机制。
- 只有在具备明确的策略和计费语义时,才增加路由或故障转移能力。
- 只有满足第 13 节标准时,才增加原生供应商适配器。

每一个里程碑都必须让直接模式在没有 Server 的情况下依然能正常工作。
面向用户的配置和路由发布上线时,需要相应更新 `guide/`、`reference/`、
OpenAPI 文档、配置示例,以及架构文档。

## 16. 验证

在以下行为都被覆盖之前,本设计的实现都不能算完成:

- 直接模式在没有 Server URL 或登录状态的情况下也能运行;
- `evaluation/` 下的评测运行使用的是直接模式,因此结果不会受到 Space
  模型策略、别名解析、配额状态或 Server 可用性的影响——CLI 适配器会
  直接拒绝一个托管模式的测试对象,而不是去测量一种和评测清单所声称的
  不同的传输方式;
- 托管模式下的阻塞式调用和流式调用,产生的核心内容、工具调用和用量
  结构,与直接调用同一个目标产生的结果一致;
- 一个用户不能在自己所在 Space 的策略之外调用某个别名;
- 调用方不能自行选择上游 URL 或供应商凭证;
- Server 自身的 Tier 1 推理不会产生一次 HTTP 自调用;
- Worker 的归属信息是从这次 Task 的 Run 推导出来的,而不是来自请求
  元数据;
- 提示词和工具内容不会进入正常日志或调用账本;
- 上游重试在第一个增量被发出之后就会停止;
- 断开连接导致的取消能够传播到上游请求;
- 缓慢的消费者不能导致内存无限增长;
- 不完整或不可用的供应商用量信息会被如实呈现;
- 一次托管的 Worker 调用不会被重复计数;
- 访问令牌过期和 Space 成员资格被移除,都会以明确的错误方式失败;
- 直接模式和托管模式的模型条目,在 CLI、TUI 和 Desktop 中是可以区分的。

按每次实现改动的规模,相应使用本仓库任务运行器中的检查。最终的网关
集成测试套件需要一个确定性的伪造上游,而不能要求一个真实的模型 API
密钥。

## 17. 首个版本范围之外

- 面向任意第三方客户端的公开 OpenAI 兼容 API。
- 原生的 Anthropic、Bedrock、Vertex 或其他供应商适配器。
- 未在 `core/llm` 中表达的供应商特定功能。
- 嵌入、图像、音频等其他非对话类推理端点。
- 语义级别的响应缓存。
- 以货币计价的账单。
- 由用户提供的供应商密钥托管。
- 当 Server 或供应商不可用时的自动直连回退。
- 不受信任的公共多租户 SaaS 运营。

## 18. 开放问题

以下这些选择需要在对应里程碑开始之前得到解决:

1. 刷新机制已经上线,因此一个托管客户端的登录状态现在能够在访问令牌
   过期之后继续存活。仍未解决的是:一个原生客户端应该把刷新令牌存放在
   哪里、一个会话是否应该有一个绝对的生命周期、一个访问令牌是否应该
   携带受众范围(audience)和权限范围(scope),以及一个无人值守的调用方
   应该如何完成身份验证——参见
   [client sessions and API credentials](../proposals/client-sessions-and-api-credentials.md)。
2. 用什么样的最小数据库结构来表示 Space 别名?目录本身已经定型——
   即 `llm_model`,凭证保存在行内——但别名目前仍然只是 `server.yaml`
   中一份部署级别的映射。
3. 第一个配额里程碑应该预留一个估算出的最大额度,还是明确地以软执行
   的方式发布?
4. 终态调用元数据应该保留多久,又有哪些 Space 角色可以查看它?
5. 一个本地客户端可以附加哪些上下文标识符用于关联,同时又不会让它能够
   冒充一次 Server 拥有的 Task 的 Run?

## 19. 建议的第一步改动

只从 M1 开始:引入模型目录、与供应商无关的解析器,以及进程内路由器;把
现有的、与 OpenAI 兼容的客户端放到它背后;并让 Tier 1 经由这个服务
路由,而不新增任何 HTTP 端点。

这能在 Server 变成一个推理数据平面之前,先验证包的归属划分、别名解析、
能力检查以及密钥处理是否正确。之后,网关路由、远程客户端、调用账本和
Worker 凭证,就可以作为一系列可以逐步评审的步骤陆续到来,而不是一次
牵连在一起的改动。
