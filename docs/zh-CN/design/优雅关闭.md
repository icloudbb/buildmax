## 问题

BuildMax 的部署会被常规地停止：滚动升级会替换服务器 Pod，`docker compose down` 会重启一套 Compose 栈，节点排空会驱逐一个 Worker Pod。这些都不是故障，但目前对某些组件而言，它们看起来就是故障。

服务器如今只正确处理了 HTTP 这一半，别的都没处理好。今天的一次停止，按顺序会发生：已连接的 Portal 流在事件中途被切断；一个正在运行的本地 Worker 会让进程一直存活到它这次运行结束为止；一个被杀死的 Worker 会让一次运行卡在 `RUNNING` 状态，直到六小时后陈旧运行回收器才把它判定为失败；而一个原本欠着某个 Conversation 一份“运行已完成”报告的场景，可能永远都不会收到通知。

上面这些各自是独立的缺陷，成因也各不相同，但它们共享同一个缺失的决策：**没有任何东西定义这个进程各部分应当以什么顺序停止，也没有定义当一次运行所在的进程即将消失时，这次运行的结果应当是什么。** 本记录要做的正是这个决策。

## 决策

两件事，合在一起。

**一个关闭梯队。** 停止是一个有总时间预算的序列，而不是一组互不相干的 `defer`。顺序由一条规则确定：*一个组件只能在所有依赖它的东西都已停止之后才能停止。* 由于 Worker 是通过服务器自己的 HTTP API 来报告结果的，这条规则把 HTTP listener 放在了序列接近*末尾*而不是开头的位置——这与当前代码的顺序正好相反。

**第三种停止原因。** 运行时已经区分了两种情况：被人取消的运行状态是 `CANCELED`，并保留其已产出的内容；而一个消失的进程则被视为“没有结果可以报告这次运行”（见 [`internal/agentapp/taskrun/runtime.go`](../../../internal/agentapp/taskrun/runtime.go)）。关闭既不是前者，也不是后者。它是进程*提前就知道*的一种停止，而这份提前知晓让运行得以说明发生了什么，而不是悄无声息地消失、数小时后才被判定为遗弃。这第三种原因就是**已中断（interrupted）**：运行停止，保留其输出与 Artifact，并报告一个终态结果，其中说明关闭是原因。

## 1. 这项工作的起点

有必要把这一点说清楚，因为这里的缺口比“完全没有优雅关闭”要窄得多，而 §2 正是第一阶段所改变的内容。

`Server.Run` 会捕获 SIGINT 与 SIGTERM，以 10 秒预算调用 `http.Server.Shutdown`，并把 `ErrServerClosed` 当作正常退出处理。`bootstrap.RunServer`（[`internal/bootstrap/server.go`](../../../internal/bootstrap/server.go)）会启动四个后台循环——调度器、凭据清理器、陈旧运行回收器和审计留存器——每一个都有一个关闭一个 channel 并等待循环 goroutine 结束的 `Stop`，并在 HTTP 服务器*之下*的一个 `defer` 中被调用。handler 的生命周期（[`internal/server/handlers/lifecycle.go`](../../../internal/server/handlers/lifecycle.go)）则由 `Server.Run` 自己启动和停止。

所以*机制*本身大体上是存在的。缺失的是顺序、边界，以及运行层面的语义。信号处理此后已经移到了 `RunServer` 中，因为它是唯一能看到整个梯队全貌的层；[`internal/server`](../../../internal/server/server.go) 为它暴露出 `ListenAndServe`、`Drain`、`Shutdown` 和 `StopBackground`，供其编排顺序。

## 2. 六个缺口

下面按发现时的原状描述每一个缺口，因为正是这些失败情形证明了这项设计的必要性。标题说明它现在所处的状态；§3 及之后描述的是最终建成的形态，§10 说明每一处分别属于哪个阶段。

### 2.1 调度器的停止没有边界——已修复

`LocalRunner.Run`（[`internal/server/scheduler/runner.go`](../../../internal/server/scheduler/runner.go)）调用 `cmd.Run`，它会一直阻塞到 Worker 进程退出为止，而它是从调度器的轮询循环里内联调用的。`Scheduler.Stop` 关闭 `stopCh` 并等待这个循环结束，所以一次落在派发过程中途的停止，会一直等到整次 Agent 运行结束——短则几分钟，长则几小时。在 systemd 或 Compose 下，宽限期会耗尽，进程无论如何都会被杀死；有序的停止路径根本走不到。

`K8sJobRunner.Run`（[`internal/infra/k8s/job.go`](../../../internal/infra/k8s/job.go)）只是创建一个 Job 就返回，所以生产部署不会遇到这个问题。Compose 与本地开发会遇到，而这恰恰是开发者对“停止会做什么”形成预期的地方。

该循环使用的 context 是 `context.Background()`，因此即便调度器想要放弃这次派发，也没有办法向子进程发出信号。

### 2.2 Worker 完全忽略信号——已修复

[`cmd/buildmax-worker/main.go`](../../../cmd/buildmax-worker/main.go) 运行在 `context.Background()` 上。SIGTERM 会以 Go 的默认处置方式直接杀死进程：不会上传这次运行的产出，不会报告状态，也不会刷写轨迹。这次运行会一直保持 `RUNNING`，直到 `StaleRunReaper`（[`internal/server/scheduler/stale_runs.go`](../../../internal/server/scheduler/stale_runs.go)）在默认六小时的 `worker.run_timeout` 之后将其判定为失败。回收器的设计对它本来要处理的场景——一个*已经消失*的 Worker——是正确的，但一个被要求停止的 Worker 还没有消失，拿回收器去处理这种情况，等于把一次本可以在五秒内完成的有序停止，变成了 Portal 里一个长达六小时的谎言。

这一点在生产环境中最为要紧，而不是最不要紧：一个 Worker Pod 就是一个 Job Pod，节点排空、抢占和驱逐都会送达 SIGTERM。

### 2.3 流式连接会耗尽整个预算——已修复

`http.Server.Shutdown` 会关闭 listener 并等待连接变为空闲。它不会取消正在进行中的请求 context，而一个 Server-Sent Events handler 永远不会空闲——[`internal/server/handlers/work/stream.go`](../../../internal/server/handlers/work/stream.go) 中的循环等待的是 `r.Context().Done()`，而关闭过程并不会触发它关闭。因此，只要有一个正在观察某个 Task 的 Portal 标签页，就必然导致 `Shutdown` 跑满整整 10 秒预算并返回 `DeadlineExceeded`（记为一条警告日志），之后进程照样退出，连接照样被切断。原本留给排空真实请求的预算，被浪费在等待一条根本不会结束的流上。

### 2.4 不存在排空状态——已修复

`readyzHandler`（[`internal/server/health.go`](../../../internal/server/health.go)）会探测依赖项，而在关闭期间它依然回答 `ready`。Kubernetes 在 SIGTERM 之后是异步移除 Endpoint 的，所以在这个传播窗口内，Service 仍会把新请求路由到一个已经停止监听的服务器——得到的是连接被拒绝，而不是一个可重试的 503。[`deployment/production/buildmax.yaml`](../../../deployment/production/buildmax.yaml) 和 [`deployment/buildmax-deploy.yaml`](../../../deployment/buildmax-deploy.yaml) 都没有设置 `terminationGracePeriodSeconds` 或 `preStop` hook，所以默认的 30 秒也就成了下面所有环节共用的全部预算。

### 2.5 终态回调的 goroutine 处于失控状态——已收窄

`Announcer.Announce`（[`internal/server/handlers/runterminal/runterminal.go`](../../../internal/server/handlers/runterminal/runterminal.go)）是在一个裸的 `go func()` 里、以 `context.Background()` 触发终态回调的。没有任何东西会等待它。若关闭恰好落在这个窗口期内，它当时正在做的事情就会被丢弃。

这部分工作有一半是可以恢复的：欠给某个 Conversation 的报告是一次持久化的投递，清扫器会重试它——这正是 [portal-execution-model.md](Portal执行模型.md) 所构建的持久性保证。但另一半不是：`workflow.HandleTaskRunTerminal` 把一个 Workflow 推进到下一步这件事，没有对应的清扫机制，因此一个 Workflow 可能停滞在一个其运行早已结束的步骤上。

### 2.6 HTTP 服务器没有设置超时——已修复

`&http.Server{Addr, Handler}` 既没有设置 `ReadHeaderTimeout`，也没有设置 `IdleTimeout`。这对关闭而言影响有限——空闲连接本来就会被 `Shutdown` 关闭——但一个从未发送完整请求头的连接，既不是空闲也不是活跃，它会把排空过程一直卡在那里、耗尽整个预算。它同时也是一个 slowloris 攻击面，单凭这一点就足以构成修复的理由。

## 3. 关闭梯队

一个信号处理器，一份预算，七级台阶。每一级都有一个从预算中推导出的截止时间；错过截止时间时会记录日志并前进到下一级，而不是阻塞在那里——因为一次挂起的关闭，比一次损失了一点点工作的关闭要糟糕得多。

| # | 台阶 | 等待什么 | 为何放在这里 |
|---|---|---|---|
| 1 | 进入 `draining` | 不等待任何东西 | `/readyz` 开始回答 503，使负载均衡器停止发送新工作 |
| 2 | 停止认领 | 轮询循环当前这一轮结束 | 一旦进程即将消失，就不应再开始任何*新*的运行 |
| 3 | 中断正在进行的运行 | Worker 进程完成报告 | 需要第 6 级的 API 仍在监听 |
| 4 | 关闭观察者流 | 观察者式的 SSE handler 返回 | 为第 5 级的排空腾出空间；并告知 Portal 重新订阅 |
| 5 | 排空工作 | 会话回合，然后是正在进行中的请求 | 普通 HTTP 工作正常结束；被劫持的 socket 上的回合会被显式等待（§5.1） |
| 6 | 停止监听 | `http.Server.Shutdown` 返回 | 已经没有什么还需要这个 API 了 |
| 7 | 停止后台循环 | 清扫器、回收器、清理器、留存器、终态回调 | 放在最后，因为上面任何一级都可能还会入队新任务 |

第 1、2 级是即时完成的。第 3 级占据了预算的大部分。第 4 到第 7 级都很短。

顺序被颠倒过来正是关键所在：**HTTP listener 在 Worker 报告期间保持存活。** 原先那种 `defer` 顺序做的恰恰相反，先关闭 API，让调度器在那里等待已经无法再与它通话的子进程。

这个梯队位于 `shutdownServer` 中（[`internal/bootstrap/server.go`](../../../internal/bootstrap/server.go)），因为 bootstrap 是唯一同时持有 HTTP 服务器与调度器的层。它通过一个小接口接收自己的操作目标，使测试能够直接断言这个顺序本身——这正是最容易被后续一次看似无害的修改悄悄破坏掉的性质。

### 3.1 预算

面向运维人员的旋钮只有一个：`server.yaml` 中的 `shutdown_grace`，默认 25 秒，各阶段的时长都从它推导而来，而不是分别配置。两个必须彼此保持一致的旋钮，恰恰是让它们变得不一致的最佳方式。

| 阶段 | 预算占比 | 默认值下 |
|---|---|---|
| Worker 中断（第 3 级） | 60% | 15 秒 |
| 关闭流（第 4 级） | 5% | 1.25 秒 |
| 请求排空（第 5–6 级） | 25% | 6.25 秒 |
| 后台循环（第 7 级） | 10% | 2.5 秒 |

25 秒低于 Kubernetes 默认的 `terminationGracePeriodSeconds`（30 秒），为 §7 中的 `preStop` hook 留出了空间。运维人员如果调高其中一个，就必须同时调高另一个；参考清单同时设置了这两个值，一个架构测试会在清单的杀死截止时间不再长于自身预算时报错，配置项的注释也说明了这一点。

某个阶段一旦超时，会记录日志并让位给下一级，而不是阻塞；而当宽限期小到无法再分配时，会被下取整而不是被当成“跳过整个梯队”的请求。

## 4. 服务器：排空

`Server` 持有一个门闩——用一个已关闭的 channel 而不是一个 bool，因为 §5 中的流式处理需要一个可供 select 的对象——它会在第 1 级被关闭。

- 处于排空状态时，`/readyz` 会先于探测依赖项之前，直接以 `status: "draining"` 回答 **503**。一个正在排空的服务器无论 MySQL 是否可达都算不上就绪，而在退出途中还去做探测只是浪费预算。
- `/healthz` 继续回答 **200**。它表达的含义是“这个进程还活着”，如果存活探针在关闭期间失败，就等于要求 kubelet 去重启一个本已在正常退出中的进程。

这种不对称正是 [`health.go`](../../../internal/server/health.go) 已经记录过的那种；排空只是它的又一个应用场景。

## 5. 服务器：关闭流

有两种方式可以让一个流式 handler 返回。

**被否决——取消一个 `BaseContext`。** `http.Server.BaseContext` 提供了每个连接上所有请求所派生出的 context，取消它会终结每一个 SSE 循环，且不需要改动任何 handler。但它同样会终结每一个*普通*的、正在进行中的请求：一个正处在模型调用中途的 Tier 1 回合，一次写到一半的 Artifact 上传。这会把第 5 级变成“中止一切”，而这恰恰是排空机制想要避免的结果。

**被采纳——一个显式的排空门闩，只用于观察者流。** 服务器持有 §4 中的那个 channel，在第 1 级被关闭，并通过配置传给各个 handler。一个观察者流会与 `r.Context().Done()` 一起对它做 select，写出一个说明原因的终态事件，然后返回。

并非每一个 SSE 响应都是一个观察者。区分的标准在于：这个连接是在*观察*工作，还是它本身*就是*工作：

| 流 | 类型 | 所属台阶 |
|---|---|---|
| `GET /api/spaces/{id}/tasks/{id}/stream` | 观察者——Portal 标签页在跟踪一次存在于数据库中的运行 | 第 4 级，以一个 `draining` 事件关闭 |
| `POST /api/spaces/{id}/conversations?stream=1` 及其消息变体 | 工作——一个正在产出答案的 Tier 1 回合 | 第 5 级，按正常方式排空 |
| `POST /api/llm/completions` 及 Worker 自身的 `POST /api/worker/task-runs/{id}/llm/completions` | 工作——一次正在进行中的推理调用 | 第 5 级，按正常方式排空 |

如果在第 4 级就关闭这两种工作流，恰恰会破坏排空机制本来要保护的东西。网关那一个尤其糟糕：`llmremote` 依设计从不重试——重放一个已经发出过若干增量的调用会导致输出重复——所以在 Worker 推理调用中途切断它，会使该次调用直接失败，而 Agent 循环会把它变成一次失败的运行。而且在 `k8s_job` 模式下，第 3 级根本不会停止这些 Worker，因为它们的 Job 正确地比派发它们的服务器活得更久。服务器的退出不应该连带拖垮它们的运行。

这种“选择性加入”式门闩的代价是，未来新增的观察者流可能会忘记接入它，从而悄悄地重新引入 §2.3 的问题。一个架构测试覆盖了这一点：每一个写出 `text/event-stream` 的 handler，要么观察这个门闩，要么出现在一份明确说明理由的工作流清单中。

Task 的 SSE 端点会在服务器关闭连接之前，发出一个名为 `draining` 的具名事件。消费该 API 的客户端必须把它当作重新连接的信号，而不是运行已完成的信号。Portal 现在已经不再消费这个端点了；它改用 Space 的 WebSocket 事件作为失效通知，并据此重新加载 Task 状态。

### 5.1 更大的漏洞根本不在流里

Task 的 SSE 端点在 Portal 中已经没有实际消费者了，Portal 改为通过 WebSocket 观察一次运行。这并不意味着第 4 级毫无意义——这个端点仍然是 API 的一部分——但这意味着在关闭期间真正承载用户可见工作的连接是那个 socket，而 socket 在两方面都比 SSE 流更棘手。

它是被**劫持（hijacked）**的，所以 `http.Server.Shutdown` 不会等待它就直接返回。而且它承载着 **Tier 1 回合**：`conversation.create` 和 `conversation.message` 是在 socket 自己的 goroutine 里运行一次模型调用、并写入消息历史的。两者叠加起来意味着，第 5 级可能在一个答案仍在生成过程中就返回，进程随后会在回合执行到一半时退出。

所以排空机制触达的是回合注册表，而不是 socket 本身。`turnqueue.Registry`（[`internal/server/turnqueue/turnqueue.go`](../../../internal/server/turnqueue/turnqueue.go)）新增了 `Drain` 和 `Wait`：从第 1 级开始，新的回合会被以 `ErrDraining` 拒绝——在 HTTP 层面表现为一个可以对另一个实例重试的 503——而第 5 级会在 listener 关闭之前，等待已经在运行的回合结束。出于同样的原因，新的 socket 升级请求也会被拒绝，而 Portal 的 WebSocket 客户端本就已经具备带退避的重连机制。

已经打开的 socket 不会被提前关闭。它们承载着第 5 级正在等待的那个回合，提前关闭它们会使这个等待失去意义。

## 6. 调度器与 Worker

### 6.1 两阶段的调度器停止

`Stop()` 变为 `Stop(ctx context.Context) bool`，分两个阶段：

1. **停止认领。** 向循环发出信号；它最多完成手头正在进行的这一轮轮询，不再认领任何新任务。
2. **排空派发。** 取消派发用的 context，然后在 `ctx` 限定的时间内，等待已经在进行中的派发结束。它会报告这些派发是否全部完成。

这两个阶段之所以能够分离，只是因为派发已经不再运行在轮询循环上了。过去它是这样运行的，这正是旧版 `Stop` 之所以没有边界的原因：那个循环*就是*正在运行的 Agent。现在它运行在自己的一个 goroutine 上，一次一个——这正是内联版本原本具备的并发度。认领与派发仍然发生在同一轮轮询中，中间没有任何环节可供一次停止插入进去打断，所以不存在“已认领但未派发”这种需要额外释放的状态。

对 `K8sJobRunner` 而言，第二阶段是瞬时完成的：派发只是一次 `CreateJob` 调用，而 Job 的存活时间比创建它的服务器更长，这是正确的行为——一次运行并不需要它的调度器持续运行才能完成。

对 `LocalRunner` 而言，第二阶段才是运行真正发生的地方，runner 为此新增了两个 `exec.Cmd` 字段：

```go
cmd.Cancel = func() error { return cmd.Process.Signal(syscall.SIGTERM) }
cmd.WaitDelay = workerHardKillGrace
```

取消派发用的 context，会按照 §6.2 定义的方式要求 Worker 停止；如果它不停止，`WaitDelay` 会将其杀死。在 Windows 上，由于 [`internal/infra/proc/kill_windows.go`](../../../internal/infra/proc/kill_windows.go) 已经记录了那里没有礼貌信号可用，因此不设置 `Cancel`，默认的杀死方式照旧生效；本地 Windows Worker 会因此丢失其正在进行的运行，回退到 §2.2 描述的行为，而参考部署本来也不是本地进程模式。

派发逻辑还需要知道另一件事：一个因为*这个*进程正在停止而停止的 Worker，其实已经报告过自己的结果了，而 `cmd.Run` 无论如何都会为此返回一个错误。如果把这记为一次派发失败，就会用一条关于服务器的消息覆盖掉这次运行实际产出的结果，所以一个 context 被取消的派发，不会记录任何东西。

### 6.2 Worker 会响应 SIGTERM

[`cmd/buildmax-worker/main.go`](../../../cmd/buildmax-worker/main.go) 改用 `signal.NotifyContext`，而 `RunWorker` 原有的 `context.WithCancelCause` 新增了第二个原因 `model.ErrRunInterrupted`，与取消监视器所用的 `model.ErrRunCanceled` 并列。

`RunTask` 随后会以处理“取消”时同样的方式处理“中断”：保留目前为止已产出的输出与 Artifact，在一个新的、有限时长的 context 下上传运行状态并登记输出——`reportFinishTimeout` 早已正是为此而存在的机制——并报告一个终态。它之所以保留为一个独立的原因，是因为这两类事件并非同一回事，在 Portal 中也不应显示成一样。

**报告的状态：`FAILED`，附带一条指明关闭为原因的错误消息。** 曾经考虑过、后来否决的方案：

- *`CANCELED`*——对每一个消费方而言，包括 Workflow 引擎和 Conversation 报告，这都读起来像“有人主动停止了这次运行”。但事实上没有人这么做。
- *一个第四种终态 `INTERRUPTED`*——诚实，而且在 Alpha 阶段、没有任何存储形状被冻结的前提下代价也不高。之所以否决，是因为终态集合被 Portal、报告路径、`RunStatusTerminal`、Workflow 的步骤状态机以及配额机制多处消费，而在运行重试机制真正落地之前，它们每一个都不得不用“是的，暂时算失败”来回答“这算失败吗”这个问题。在重试机制存在之前就新增一个唯一正确处理方式是*重试*的状态，买到的只是一次数据迁移，而不是一项真正的能力。
- *把状态释放回 `PENDING`*——这才是真正正确的答案，但超出了本记录的范围。重新派发需要一个尝试次数计数器、一个上限，以及对首次尝试已经产生的副作用该如何处理的决策。这正是路线图上已有的运行重试工作，本记录应当为它交出一个干净的起点，而不是把它做一半。§10 说明了这部分工作落在哪里。

之后 Worker 会**以退出码 0 退出**。它已经报告了自己的结果，而在 `RestartPolicy: OnFailure` 配合 `BackoffLimit: 3`（[`internal/infra/k8s/job.go`](../../../internal/infra/k8s/job.go)）的情况下，一个非零退出码会重启一个 Pod，而这个新进程会因为该运行已不处于 `SCHEDULED` 状态而立刻拒绝它。这与 `main.go` 已经对一次被取消的运行、以及一次在工作中失败并已上报 FAILED 的运行（`ErrRunFailed`）所采用的逻辑是一致的。

现在这条逻辑也适用于 `ErrAlreadyClaimed`——这正是状态守卫和丢失的 `RUNNING` 迁移所报告的情形。此前这种情况会以退出码 `2` 退出，理由是调度器可以据此把它与一次启动失败区分开来——但实际上没有任何代码去读取这个退出码，`2` 依然是非零值，因此仍然会重启 Pod；而在本地 runner 下，一个非零退出码还会让调度器把另一个 Worker 正在处理中的运行判定为失败。

退避次数本身仍保持为 3。它存在的目的不是为了那些“无法重新执行”的运行，而是为了这样一种 Worker：它在*认领*任何运行之前就已经死亡——比如正在读取配置、拉取运行信息，或者解析其模型的过程中——此时运行仍处于 `SCHEDULED` 状态，一个全新的 Pod 确实能够成功接手。把它设为零就等于白白扔掉这种可能性。而在认领之后遭遇强制杀死所付出的代价是有限的，也不再那么要紧：Pod 会重启一次，新的 Worker 以退出码 0 退出，而 §6.4 的存活性清扫无论如何都会在几分钟内关闭这次运行。

对于一个真正消失了的 Worker——SIGKILL、节点丢失、进程崩溃——陈旧运行回收器仍然是答案，本设计只是去掉了它原本被拿来替代“Worker 本可以自己作出的报告”的那一种情形。`worker.run_timeout` 在这里维持原样；§6.4 会重新审视这个答案应该多快到达才合适。

### 6.3 两个窗口必须彼此嵌套

在 `docker compose down` 或 systemd 默认的 `KillMode=control-group` 下，SIGTERM 会在同一时刻送达服务器及其 Worker 子进程。因此，Worker 自身的排空窗口必须短于服务器的第 3 级，否则一个 Worker 有可能在它要报告的 API 已经停止监听之后，还在继续上传数据。这个时长是推导出来的，而不是单独配置的：Worker 使用 `shutdown_grace` 中 Worker 阶段份额的 80%，通过 runner 已经在构建的环境变量传入。

Kubernetes 场景下，Worker Pod 自身的 `terminationGracePeriodSeconds` 与其排空窗口之间也存在同样的约束；Job 规约显式设置这个值，而不是意外地继承默认的 30 秒。一个 Worker Pod 是由一个不会等待它的 runner 派发出去的，因此它得不到来自环境变量的窗口时长，只能使用运行时默认值——该默认值经过选择，以适配那 30 秒的范围。

### 6.4 一个从未被要求停止的 Worker

§6.2 覆盖的是每一种以信号开始的停止。剩下的那些则不然：SIGKILL、OOM kill、一个消失的节点、`kubectl delete pod --force`。进程在能够报告之前就已经消失，而唯一能够关闭这次运行的东西，就是回收器——在默认六小时的 `worker.run_timeout` 之后。

对于回收器要回答的那个问题——一次已经停止推进的运行，是不是仅仅因为它慢——六小时是一个合适的答案。但把它当作*唯一*的答案就不对了，因为一个 `RUNNING` 的运行并不是沉默的：`WatchCancel` 会在整个运行执行期间，每五秒轮询一次 `GET /api/worker/task-runs/{id}`，以便能够察觉一次取消。这个心跳其实早就存在了，只是从来没有任何东西记录过它。

于是这条轮询路径现在会写入 `task_run.last_seen_at`，而回收器新增了一次清扫：将那些静默超过存活宽限期的 `RUNNING` 运行判定为失败。以下几点决策值得说明：

- **只有这条路径会写入时间戳。** 流式路径每秒会触发很多次，把它也用来写心跳会造成写放大。终态的 `PATCH` 调用同样是针对该次运行的调用，如果也让它写入时间戳，会把这个时间戳推到工作实际停止之后——而这个列唯一应当表达的含义，恰恰就是工作何时停止。
- **只清扫 `RUNNING` 状态的运行。** 这恰好就是能够保证轮询正在进行的那个窗口。一个 `SCHEDULED` 的运行已经认领了自己，但可能正在具体化一个工作区或拉取插件包，尚未触碰 API，而一次缓慢的初始化并不等于一个已经死亡的进程。`SCHEDULED` 状态继续沿用原有的超时机制。
- **`NULL` 的时间戳永远不会被清扫。** 没有记录到任何信号，也就谈不上“曾经安静下来”。证据缺失属于超时机制要处理的情形，而不属于这里。
- **是两分钟，而不是十五秒。** 一个轮询失败的 Worker 仍然在正常工作：`WatchCancel` 会重试，而不是把一次失败的轮询当作一次取消来处理，理由是一个连不上的服务器，并不等于一个主动取消了它的服务器。因此过早清扫并不会拦住一个网络分区中的 Worker——它只会白白丢弃那个 Worker 本来即将报告的结果，而 `TransitionTaskRun` 的预期状态守卫会让这份迟来的报告悄无声息地失效。二十四次错过的轮询，就是为了避免这种情况所付出的代价。
- **不会重新运行任何东西。** 这次运行会被记录为已结束，而不是被重试。一个在运行中途死亡的 Worker，可能已经写了文件、调用过某个 API，或者开出了一个 pull request，而这里的任何东西都不知道这个任务重复执行是否安全。是否重试，仍然是一个留给人来做的决策，这也正是它本来就该所在的位置。

这里没有做到的是：它只能说明一个 Worker 停止了报告，却说明不了原因。从服务器的视角看，一次 SIGKILL、一个被驱逐的 Pod 和一次网络分区，是完全相同的一次观测，记录下来的消息也只能说明这么多——这与另外两个清扫机制早已遵循的规则是一样的。要归因具体原因，需要用到调度器已经存储在 `k8s_job_name` 中、但目前还没有任何东西读取的 Job 状态；那是一项独立的改动，而且只会覆盖 `k8s_job` 这一种 runner。

## 7. 部署

两份参考清单都会在服务器 Deployment 上新增：

```yaml
terminationGracePeriodSeconds: 45   # > shutdown_grace, with room for preStop
lifecycle:
  preStop:
    exec:
      command: ["sleep", "5"]
```

`preStop` 的这次 sleep 是为了覆盖 Endpoint 的传播过程：kubelet 会同时发送 SIGTERM 并移除 Endpoint，如果没有这个 sleep，在那个窗口期内被接受的请求就会遇到一个已经关闭的 listener。五秒钟“正在排空但仍在监听”的服务器，就足以把这种情况变成一次正常的、可重试的 503。

Worker 的 Job 规约会按照 §6.3 新增自己的 `terminationGracePeriodSeconds`。

## 8. HTTP 超时

| 字段 | 取值 | 原因 |
|---|---|---|
| `ReadHeaderTimeout` | 10 秒 | 一个半打开的连接既非空闲也非活跃，会一直卡住排空过程。这同时也是 slowloris 攻击的修复 |
| `IdleTimeout` | 120 秒 | 限制 keep-alive 连接的存活时间，使排空开始时打开的连接更少 |
| `ReadTimeout` | 不设置 | Artifact 上传体积大，合理情况下速度也会很慢 |
| `WriteTimeout` | 不设置 | 设置它会截断每一条 SSE 流以及每一次长时间的模型调用 |

不设置在这里是一个刻意的决策，而不是遗漏，代码注释中也说明了这一点。

## 9. 管理终态回调

`Announcer` 现在接收一个小型的运行组——一个 `WaitGroup` 加一个已关闭标志位——而不是一个裸的 `go func()`。第 7 级会在其预算份额内等待它完成。标志位被设置之后，`Announce` 会**同步**运行这些回调，而不再另起 goroutine：此时调用方正是 Worker 的最终报告，原地内联完成这项工作，既有时间上限，也比直接丢弃它要好。

这缩小了 §2.5 的窗口，但没有完全消除它。一个因 SIGKILL 而丢失了步骤推进的 Workflow 仍然会停滞，因为和 Conversation 报告不同，这里没有一份持久化的、可供重试的意图记录。让 Workflow 的推进变得持久化是一个真实存在的缺口，但它属于 Workflow 引擎的范畴，而不属于本记录，它被列在 §10 中，而不是被悄悄暗示为已经解决。

## 10. 各阶段

**第一阶段——服务器自身的停止。已完成。** 关闭梯队、排空状态、排空门闩及观察它的观察者流、`draining` 事件在 Portal 一侧的处理、回合静止（§5.1）、HTTP 超时、受管理的回调组，以及清单改动。这一阶段自成一体，不涉及任何运行层面的语义，单靠它自己就修复了 §2.3、§2.4、§2.5 和 §2.6。

调度器现在已经在第 2 级停止，而不是在 HTTP 服务器之下的一个 `defer` 里停止，所以 §2.1 所依赖的顺序已经就位。尚未就位的是边界：在 `local_process` 模式下，`Scheduler.Stop` 仍然会等待它所派生出的 Worker 进程，而梯队自身的超时，是唯一能防止一次停止无限期挂起的东西——代价是留下一个孤儿 Worker。第三阶段解决了这个问题。

**第二阶段——Worker 的停止。已完成。** `ErrRunInterrupted`、信号处理器、`RunTask` 的中断路径，以及退出码 0。修复了 §2.2。它独立于第一阶段，即便没有第一阶段也有其自身价值：无论服务器做什么，一个因节点排空而停止的 Worker Pod 都不会再对自己的运行撒谎。

它附带了一处不在原计划之内的服务器端改动。此前 Worker 端的 API 只为 SUCCEEDED 和 CANCELED 两种状态登记运行文件，因此一次报告 FAILED 的中断运行，会先上传其输出，随后又被丢弃——由状态决定这份工作是否被保留。现在登记逻辑跟随报告本身：凡是发送了文件的运行，无论其报告的状态是什么，这些文件都会被登记；而一次在自身工作中就失败了的运行，则不会发送任何文件。

**第三阶段——调度器的停止。已完成。** 两阶段的 `Stop`、带有 `Cancel`/`WaitDelay` 的 runner，以及彼此嵌套的窗口。修复了 §2.1。它同时依赖前两个阶段——依赖第二阶段，使 Worker 拿到信号后有事可做；依赖第一阶段，使 API 在 Worker 这样做的时候仍在监听。

派发逻辑被移出了轮询循环，以使这两个阶段能够分离，并被限制为一次只能有一个在进行——这正是该循环在内联派发时本就具备的并发度。这个上限本身是一个吞吐量方面的决策，本记录并不打算去做这个决策；它只是拒绝在无意间悄悄改变它。

**留待以后，而非现在。** 把一次被中断的运行释放出去以便重新派发（运行重试），以及 Workflow 的持久化推进。

## 12. 未决问题

1. **第 3 级是否应该等待那些它没有派发的运行？** 在 `k8s_job` 模式下，Job 比服务器活得更久，第 3 级形同空操作，这对于一次滚动升级而言是正确的，但对于一次彻底下线整个部署而言就不对了。在关闭时删除 Job，会在一次普通升级期间销毁正在进行的工作，所以答案大概率是“永远不这么做”，但这一点应当被明确写出来，而不是留作隐含假设。
2. **`FAILED` 作为一种过渡状态是否足够清楚？** 它是诚实的，也是一个终态，但一个 Portal 用户如果不去读错误消息，是无法区分“这个 Agent 失败了”和“集群重启了”的。如果这在运行重试机制落地之前被证明会造成困惑，那么在 Portal 中做一个仅限展示层面的区分，要比新增第四种状态代价更低。
3. **在一次滚动升级期间，一个 Worker 正在进行中的推理调用会怎样？** §5 把网关流排除在第 4 级之外，所以它会按正常方式被排空——但如果这次调用超出了请求预算，第 6 级依然会关闭它，而 `llmremote` 是刻意不重试的。于是这次运行会因为一个与它本身毫无关系的原因而失败。这里的设计没有解决这个问题；候选方案包括一个可恢复的调用 ID、把重试限定在尚未产生任何增量的调用上，或者干脆在运行托管推理服务的部署上设置一个更长的请求阶段。
4. **`shutdown_grace` 是否应当针对清单文件做校验？** `internal/architecture` 已经在解析参考 ConfigMap，以防止配置与清单出现漂移；断言 `terminationGracePeriodSeconds > shutdown_grace` 是同样的思路，能够捕获那种会悄悄让这里的一切保护失效的错误配置。
