## 1. 现状

本记录所描述的共享协调机制已经实现。基础/kind 与生产清单都使用 `coordination.mode: redis` 运行两个 `buildmax-server` 副本；Compose 仍是单 Server 的 `local` 路径。Redis 支撑的 Task stream、连接事件扇出、可续租的 Conversation turn lease、配置 Redis 不可达时拒绝启动，以及清单拓扑检查均已交付。

租约的 fencing token 已在 Conversation 消息历史写入路径中强制执行：携带的 token 低于该会话已接受的最高值的写入会被拒绝，因此一个在租约过期后才恢复的持有者，无法追加到取代它的副本之后。部署级资格验证缺口现已关闭：由 `./make kind smoke` 运行的 [`kindCoordinationProbe`](../../../tools/mk/coordination_probe.go) 直接驱动两副本 + Redis 的 kind 栈，证明跨副本流投递、跨副本 turn lease 串行化以及 Redis 重启后的恢复——正是 R1 要求的投递、串行化与恢复证据（第 10 节）。进程内与 miniredis 测试证明机制，本探针证明候选拓扑。把失租信号传递给正在运行的回合（第 11 节）以及 Server 滚动更新演练仍属未决，但它们是 R3 部署资格验证的问题，而非协调正确性缺口。

## 2. 问题

有三处服务器结构保存着只有单个进程才能看到的状态：

- **流式中枢**（`internal/server/websocket/hub.go`）会缓存某次 Task 运行的流式增量，并将其扇出给该 Task 的 SSE 订阅者。Worker 把增量推给它的 HTTP 调用恰好落到的那个副本；浏览器则订阅它的 SSE 请求恰好落到的那个副本。当两者不是同一个副本时，浏览器在持久化结果到达之前什么也看不到。
- **连接注册表**（`internal/server/websocket/registry.go`）持有实时 WebSocket 连接，把事件扇出给正在关注某个 Space 的每个连接。在一个副本上触发的 `task.status.changed` 失效事件，只能送达该副本恰好持有的那些 socket；另一个副本上的浏览器则会一直显示陈旧状态。
- **回合队列**（`internal/server/turnqueue/turnqueue.go`）负责将一次会话的各个回合串行化，确保两个回合不会交错读写同一份消息历史。锚定在单个进程上的串行化机制看不到运行在另一个副本上的回合。这一处出问题时会**损坏数据**，而不只是让视图降级：同一会话的两个回合分别被两个副本接纳，各自都以为自己是唯一的写入者。

调度器和陈旧运行回收器在 N 个副本下已经是安全的：它们通过原子的条件 `UPDATE` 来认领工作，所以更多副本只意味着更多轮询者，而不是重复的工作。上面三处结构却没有这样的锚点。

## 3. 决策

引入一个由配置项选择的共享协调后端：

- `coordination.mode: local`（默认值）保持当前的进程内实现不变。CLI 相关的单实例部署以及每一种开发部署都使用这个模式；只要模式是 `local`，受支持的拓扑就只能是恰好一个服务器副本。
- `coordination.mode: redis` 把上述三处结构统统路由到 Redis，让 N 个副本共享实时状态。运行超过一个副本的部署必须设置这个模式。

之所以让 Redis 承载全部这三种需求——可回放的按 Run 分流、低延迟的按 Space 广播、按会话的互斥租约——是因为它们全都是 Redis 的一等原语，一个依赖、一个连接池就能覆盖整个需求面。曾经考虑过把它拆成 MySQL 咨询锁加独立消息代理的混合方案，但按奥卡姆剃刀原则被否决了：这种方案在没有去掉低延迟扇出真正依赖的那个后端的前提下，反而多引入了一个后端。

**失败即关闭。** 当配置为 `mode: redis` 而 Redis 在启动时不可达时，服务器会拒绝启动。如果在两副本场景下静默回退到 `local`，就会重新引入本记录本来要防止的那种回合串行化损坏——这与 Worker 沙箱的原则完全一致：绝不能因为后端不可用就在无约束状态下运行。

## 4. Coordinator 接缝

`coordination.Backend` 位于 `internal/infra/coordination` 包中。它持有共享的 Redis 客户端，在构造时执行一次健康检查，并向服务器提供三个所需的后端实现：

- 一个 `websocket.StreamHub`（该接口已经预留了 Redis 实现的位置），
- 一个供连接注册表广播使用的事件发布/订阅器，
- 一个回合队列在运行回合之前需要获取的 `turnqueue.Locker`。

每个消费者都依赖自己定义的一个小接口，由 infra 包去实现——依赖方向始终是 `server → infra → core`，绝不反过来。传入一个 `nil` 后端就会选中进程内行为，因此 `local` 模式并不是第二条代码路径，而是共享路径的缺席。`bootstrap` 从 `ServerConfig` 构造出后端，并把它交给 `NewHandler`——目前 `NewHandler` 是直接创建这三个内存结构的。

## 5. 流式投递

流式中枢按 `task_run_id` 而非 `task_id` 建键：一个 Task 的每一轮对话各自拥有一个独立缓冲区。一个 Run 的缓冲区会在其自身结束后短暂保留（一个较短的 done-TTL，好让掉线重连的订阅者仍能读到收尾内容），但下一轮是一个新 Run、新键，因此已完成 Run 的输出绝不会被回放给下一个 Run 的观察者。SSE handler 会解析出该 Task 当前活跃的 Run（`GetActiveTaskRunByTask`）并订阅那个 Run 的键；前端仍以 `task_id` 访问该端点，从不接触 Run 键。

Redis 版的流式中枢把 `StreamHub` 映射到一个键为 `stream:{task_run_id}` 的 Redis Stream 上。

- `Append(runID, delta)` 对应带 `MAXLEN ~` 近似裁剪的 `XADD`，像内存版 2 MiB 缓冲区那样限制内存占用，并刷新一个 TTL，使被遗弃的运行对应的流会过期而不是持续泄漏。
- `Subscribe(runID)` 会 tail 订阅点之后追加的条目（从当前最后一个 id 开始执行 `XREAD BLOCK`），投递实时增量——语义与内存版中枢一致，因此两种后端共用同一条代码路径。
- `Buffer(runID)` 返回当前快照（`XRANGE - +`，去掉终止标记），让迟到的订阅者能够补齐历史，行为与内存版完全一致。`Subscribe` 与 `Buffer` 之间存在一个小的重叠窗口，可能导致某个片段被重复投递；这与内存版中枢可接受的行为一致，对纯追加式文本而言只是外观上的瑕疵。
- `Done(runID)` 追加一条终止标记条目并设置一个较短的 TTL；读到该标记的订阅者会发出 `[[DONE]]` 哨兵值并停止。

这样一来，一个副本上 worker 的 `XADD` 与另一个副本上浏览器的 `XREAD`，现在看到的是同一条流。

## 6. 事件扇出

每个副本仍然完全保留自己的连接注册表：一个 socket 物理上归属于它所连接的那个副本，只有该副本才能向它写入数据。跨副本的可达性是通过发布机制补齐的，而不是靠共享那张 map。

- `Broadcast(space, user, type, payload)` 把事件信封发布到单一的 Redis Pub/Sub 频道上，而不是遍历本地的 socket。
- 每个副本都在该频道上运行一个订阅者。每收到一个信封，就执行原本由 `Broadcast` 内联完成的那件事——对自己的 socket 执行 `audience(space, user)` 本地扇出。
- 发布方自己也会通过 Pub/Sub 收到自己发布的消息，并在那里完成扇出，因此发布路径本身从不做本地扇出。这样一条代码路径就能把消息投递到每个副本上的每个连接，且不会重复发送。

选择单一频道而不是按 Space 划分频道是出于简单性考虑；信封中携带 Space id，由各个副本自行过滤。如果将来跨 Space 的流量证明确有必要，再拆分为按 Space 划分的频道，作为后续的优化项。用于串流服务端自发回合增量的 `BroadcastSink` 同样复用这一个 `Broadcast`，因此无需自身做任何改动，就自然获得了多副本正确性。

## 7. 会话回合的串行化

回合队列保留其进程内的运行机制——按会话划分的 goroutine、待运行列表、位置上报、`OnDequeue` 以及排空逻辑——因为同一副本上的两个回合在那里依然可以廉价地串行化。一个分布式租约专门守护那条必须跨副本成立的边界：开始一个回合。

- 在调用某个作业的 `run` 之前，队列的 goroutine 会先获取 `lock:conv:{conversation_id}`（通过 `SET NX PX` 实现，采用带上限等待的阻塞方式）。一个看门狗会在回合运行期间按固定间隔续租；释放锁则会丢弃该锁。
- 未能获取到锁的副本会等待，这正是所需要的跨副本串行化效果。若某个副本在回合执行途中崩溃，它的租约会过期，于是另一个副本可以接管，而不会陷入死锁。
- 该租约携带一个单调递增的 **fencing token**，暴露在租约对象上，并被贯穿到该回合的每一次消息历史写入中。会话会记录它已接受的最高 token，并以 `ErrStaleTurnWrite` 拒绝更低的 token，因此一个租约已过期、之后又恢复运行的持有者，无法在夺得锁的副本之后交错写入。这是针对“暂停时间超过 TTL”这种情况的安全网，叠加在租约持有及其续期所提供的互斥之上。在单实例（`local`）路径上 token 为零，不强制 fencing，因为进程内队列是唯一的写入者。
- 队列**位置**会变成按副本计算，因而在跨副本场景下只是近似值。这是可以接受的：位置只是界面展示给用户的一个 UX 提示，而不是保证，它所提示的那种串行化现在已经由租约来强制保证了。

由于该租约在滚动升级期间短暂的两副本重叠阶段依然生效，服务器得以继续使用 `maxUnavailable: 0` 的 `RollingUpdate` 策略——B-i 消除了退回到 `Recreate` 策略或单副本上限的必要性。

## 8. 配置与失败策略

`server.yaml` 新增一个 `coordination` 段：

```yaml
coordination:
  mode: local            # 或: redis
  redis:
    address: redis:6379   # host:port
    username: ""          # 可选(Redis 6+ ACL)
    password: ""          # 可选;可被 BUILDMAX_COORDINATION_REDIS_PASSWORD 覆盖
    db: 0                 # 逻辑数据库
    tls: false            # 是否通过 TLS 连接
```

- `mode` 默认值为 `local`。除 `local` 或 `redis` 之外的任何取值都是配置错误，会导致服务器拒绝启动。
- Redis 密码遵循与数据库密码相同的环境变量覆盖模式：`BUILDMAX_COORDINATION_REDIS_PASSWORD` 会覆盖配置文件中的值，使凭据不必落盘。
- 当 `mode: redis` 时，构造过程会连接 Redis 并发送一次 `PING`。失败即致命错误——服务器会直接退出，而不是在多副本清单下以进程私有的协调方式提供服务。

## 9. 部署拓扑

- `deployment/buildmax-deploy.yaml` 与 `deployment/production/buildmax.yaml` 都包含 Redis `Deployment` 和 `Service`，在 Server `ConfigMap` 中设置 `coordination.mode: redis` 及其地址，并以两副本运行 `buildmax-server`。kind 演练基础清单，生产清单使用相同的协调形态。
- 在首个受支持的拓扑中，Redis 自身是单实例部署。它的状态是可重建的——流与锁都是实时数据而非持久数据，Redis 重启最多只会丢失在途的流增量，以及需要短暂地重新获取会话租约——因此不需要持久化卷。这一限制被记录在部署文档中，而不是被隐藏起来。
- Compose 以单 Server 使用 `mode: local`。kind 使用基础清单的两个 Server 与 Redis，因此常规集群冒烟测试会直接演练受支持的多副本拓扑。

## 10. 测试

- 单元测试针对每一种后端实现，使用进程内的 [miniredis](https://github.com/alicebob/miniredis) 进行验证，因此协调行为在每次构建时都会运行，无需 Redis 服务。这只能证明机制，不能证明候选部署拓扑（第 1 节）；真实 Redis 的测试范围留给候选演练，而非在此断言。
- 一个跨实例测试会构造两个共享同一个 Redis 的 `Handler`，并断言三项保证：一个实例上的 `Append` 能被另一个实例上的 `Subscribe` 读到；一个实例上的 `Broadcast` 能到达注册在另一个实例上的 socket；一个实例持有的回合租约会阻塞另一个实例上针对同一会话的回合。
- `stream_multireplica_test.go` 会专门把 Task delta 写入一个 handler，再从另一个 handler 读取；它的 local-backend 对照用例还会证明同样的投递不会意外穿过进程私有的 hub。
- 一个失败即关闭测试断言：当 `mode: redis` 配合一个不可达的地址时，服务器构造会返回错误，而不是一个可用的 handler。
- 存储范围测试（`./make test mysql`）验证写入路径的 fencing：一旦某会话在某个 token 下接受了消息，`AppendMessage` 就会以 `ErrStaleTurnWrite` 拒绝更低的 token，未携带 token 的写入不会降低门槛，且被拒绝的写入不会留下任何行。
- 一个架构测试断言：生产清单中 `buildmax-server` 的副本数与所配置的协调后端保持一致，因此一份在未设置 `coordination.mode: redis` 的情况下就扩展服务器副本数的清单，会导致构建失败。
- 一个部署级探针关闭了 miniredis 测试留下的缺口。[`kindCoordinationProbe`](../../../tools/mk/coordination_probe.go) 在 `./make kind smoke` 末尾、与沙箱及 worker API 边界探针并列运行，把每个 `buildmax-server` Pod 各自转发到一个本地端口，直接对着真实 Redis 手动驱动两个副本。它在候选拓扑上证明三件单元测试无法证明的事：一个任务的 worker 输出能到达在任一副本上打开的流（投递）；一个在某副本上因模型 stall 而持有会话租约的回合，会让在另一副本上发起的回合在它释放前无法到达模型（串行化）；以及在 Redis Pod 重启后两者都能恢复（恢复）。在共享 mock 上武装的 stall 正是用来在任何回复写出前打开观察窗口的，而每个回合都携带一个逐次运行的 nonce，因为 mock 的请求日志会跨运行累积。

## 11. 范围之外与未决问题

- Redis 高可用方案（Sentinel 或 Cluster）在首个受支持的多副本拓扑中并非必需，交由运维人员自行管理其 Redis。
- 跨设备共享持久化的 Session 状态是另一个独立方向（参见[持久化 Agent 会话](../proposals/durable-agent-sessions.md)提案）；本记录只覆盖实时的服务器协调问题。
- 按 Space 划分的 Pub/Sub 频道、针对慢订阅者的背压指标，以及一个在 Redis 故障时能够降级而非直接退出的就绪信号，这些都推迟到一个真正运行中的多副本部署证明确有需要之后再考虑。
- 续租会丢弃 Redis 错误，且在所有权丢失时不会取消或通知正在运行的回合（`internal/infra/coordination/lock.go`）。写入路径的 fence 让这样的回合只是白跑一次而不会损坏会话：它之后的追加会以 `ErrStaleTurnWrite` 失败。把失租信号传递给回合，是候选证据层面的问题，而不是数据安全缺口。
