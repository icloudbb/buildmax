## 1. 摘要

BuildMax 需要一个衡量其产品承诺的评估系统，而不是把现有编码冒烟测试简单放大的版本。

该产品是一个通过本地工作台和私有 Space 平台对外提供的共享 Agent 运行时。它的有效产出不仅仅是一句助手回复：而是对工作区或 Space 状态进行的有意图、有边界、可解释的变更，其结果用户可以检查、运维人员可以治理。因此，评估必须覆盖能力、可靠性、信任，以及跨本地与 Worker 执行的端到端产品结果。

本设计确定 BuildMax 将：

1. 淘汰现有的 `eval/` 目录、`internal/agenteval` 和现有的基准运行器，不保留它们的任务或结果格式；
2. 在主仓库中新建一个顶层的 `evaluation/` 工作区；
3. 拥有一套与提供商、框架都无关的自有契约，用于描述任务、评估对象、试验包、评分结果与实验比较；
4. 通过黑盒执行适配器评估构建产物和部署 Artifact，而不是把内部 Go 函数当作基准接口；
5. 在外部框架各自擅长的领域使用它们——例如用 Inspect 做实验控制与统计、用 Harbor 跑 Terminal-Bench 2.1 及其他容器基准，并把一个自托管的可观测性平台作为可选查看器——但不让任何一个框架拥有 BuildMax 的评估语义；
6. 把公共基准当作外部参照坐标，由产品自有的测试套件来决定 BuildMax 的发布与资格认证；
7. 优先面向维护者与私有部署运维人员设计，同时刻意为 Space Agent 与 Workflow 在发布前的评估留出路径。

已接受的产品与治理决策，以及仍需由证据决定的技术选择，记录在[第 15 节](#15-决策)中。

## 2. 问题与当前背景

### 2.1 现有基准回答的问题过于狭窄

现有测试框架向一个临时工作区发送一条简短提示，然后执行一个 Shell 评分器。它的目录里是一些体量很小、人工合成的 Go 任务。这作为早期冒烟测试是有用的，但它无法代表当前的产品：

- 它测量的主要是短时程的本地编码；
- 它只运行一次试验，报告一个二元的通过/失败结果；
- 任务指令与评分器逻辑共享同一个 fixture 目录，而这个目录对 Agent 可见；
- 用户设置、Hook、插件、权限与沙箱配置都可能改变被测对象本身；
- 格式错误的任务和缺失的 fixture 并不能可靠地让实验失效；
- 它无法区分 Agent 故障与评分器故障、基础设施故障；
- 它不评估 Portal 编排、Worker 执行、Artifact、托管推理、治理，或跨表面的一致性；并且
- 尽管每次运行都已经产生一条持久化轨迹，但结果格式并没有利用这条轨迹来评分或诊断。

本设计把现有实现及其格式都视为可以丢弃的东西。一些 fixture 的思路也许会作为低价值的冒烟用例被重建，但兼容现有目录并不是目标。

### 2.2 产品已经超出了"只评估模型"的范畴

BuildMax 的行为并非仅由模型产生，它还取决于：

- 共享的 Agent 循环与 BuildMax 版本；
- 提供商、模型、推理配置、上下文窗口与输出限制；
- 系统指令、工作区指令、记忆、技能与 Agent 定义；
- 内置工具、MCP 服务器、插件与 subagent；
- Hook、权限、审批与沙箱解析结果；
- 本地、Worker 或 Conversation 执行表面；
- 操作系统、容器镜像、资源限制、网络可用性与模型传输方式；以及
- 运行开始前已经物化好的状态。

因此，被评估的对象是一个 **Agent 系统配置**，而不是一个模型名称。一个无法标识该配置的结果，不能支撑模型资格认证或回归决策。

### 2.3 产品正确性有多种不同的证据

单元测试可以证明某个工具会拒绝一个非法路径，但它不能证明真实的 Agent 会稳定地选择正确的工具。模型评分的量表可以评估一份报告是否有用，但它不应该用来判断是否发生了未授权的写入。Portal 浏览器测试可以证明结果被正确展示，但它不能证明 Worker 在五次独立试验中都产生了正确的业务结果。

BuildMax 应当让确定性测试、行为评估、安全场景、公共基准与生产反馈保持各自独立。评估系统可以汇总它们的证据，但绝不能把它们压缩成一个具有误导性的单一分数。

## 3. 产品问题

评估系统应当回答：

> 在产品承诺的表面与执行边界之内，这个 BuildMax 配置能否可靠且安全地把用户意图转化为一个有用、可检查的结果？

这个问题引出四个评估领域：

| 领域 | 问题 | 典型证据 |
|---|---|---|
| 能力 | Agent 能否完成有价值的工作？ | 最终状态、测试、Artifact、量表维度 |
| 可靠性 | 它能否稳定地完成工作，并从常见故障中恢复？ | 重复试验、pass^k、故障分类、方差 |
| 信任与控制 | 它是否始终待在指令、授权与执行边界之内？ | 策略与轨迹断言、对抗性场景、边界记录 |
| 产品结果 | 完整的本地或 Space 平台流程能否交付预期结果？ | Conversation、TaskRun、Artifact、状态、轨迹、账本与 UI 证据 |

这些领域各有独立的评分卡和门槛。能力不能弥补信任违规，一份措辞漂亮的最终回复也不能弥补一个错误的最终状态。

## 4. 评估使用者

### 4.1 BuildMax 维护者

维护者需要在修改 Agent 循环、指令、工具、适配器、模型默认值、策略或执行环境之后，把候选版本与基线进行比较。系统必须能够指出逐用例的回归、统计不确定性、故障类别、成本，以及复现路径。

### 4.2 私有部署运维人员

运维人员需要针对有代表性的私有工作场景，对某个模型和部署配置做资格认证：

- 一个已获批准的模型是否有足够的能力用于本地与 Worker 场景；
- 应当预期什么样的可靠性、延迟、令牌用量与基础设施错误率；
- Worker 与模型传输是否落实了预期的边界；以及
- 部署特有的依赖是否会导致产品故障。

除非运维人员明确导出，否则运维人员的数据集和轨迹必须留在部署内部。

### 4.3 Space Agent 与 Workflow 作者

未来的一个产品表面也许会让 Space 作者在发布一个 Agent 或 Workflow 之前先运行私有场景。本设计并不对该 UI 或数据模型做出承诺，但它要求 Task、评估对象、试验和评分器的契约不能假设评估只面向维护者。

## 5. 目标

- 定义一套独立于模型提供商和评估框架、由 BuildMax 自有的稳定评估契约。
- 评估用户与运维人员实际运行的 Artifact：构建出的二进制文件、Worker 镜像与已部署的表面。
- 让本地与 Worker 之间的差异变得明确且可衡量。
- 在评判自然语言风格之前，优先评判最终状态与可观察的结果。
- 把持久化运行轨迹用作结构化的过程证据，但不把精确的轨迹匹配作为默认要求。
- 支持重复试验、成对的基线比较、不确定性度量，以及独立报告的基础设施可靠性。
- 让隐藏评分器和私有留出集与 Agent 隔离。
- 保留足够、有边界的证据，以便复现和诊断失败。
- 允许集成外部基准与分析工具，但不要求必须依赖某个 SaaS。
- 把评估工具的依赖保留在产品运行时和 Go Core 之外。

## 6. 非目标

- 保留现有任务的 Markdown 格式、内嵌 Shell 评分器、结果 JSONL 或基准 CLI 的行为。
- 建立一个公共排行榜或通用的评估 SaaS。
- 把某一个公共基准当作 BuildMax 的产品分数。
- 用真实模型试验取代确定性的单元测试、集成测试、架构测试或端到端测试。
- 默认把私有的提示词、轨迹、工作区或评分器输出发送给 BuildMax 或第三方。
- 要求日常的 CLI 与 Desktop 使用依赖 Server、Python、Node、Docker 或某个评估平台。
- 在维护者与运维人员的工作流尚未得到验证之前，就把面向 Space 的评估产品化。
- 在未针对人工或确定性标签做校准的情况下，就宣称某个 LLM 评委代表事实标准。

## 7. 设计原则

### 7.1 结果优先

对于一个会改变状态的 Agent 来说，权威的答案通常是最终的环境状态。一句"报告已上传"的回复并不能证明 Artifact 确实存在；一句"预订已完成"的回复也不能证明数据库确实发生了变化。只要可行，确定性的状态检查和契约检查就应当优先。

### 7.2 过程证据，而非唯一的标准路径

轨迹应当能够回答：Agent 是否使用了禁止的工具、是否越过了边界、是否遗漏了必需的验证、是否陷入循环、是否发生了压缩、是否进行了委派，或者是否遇到了工具错误。只有当顺序本身就是产品或安全契约的一部分时，才应当要求精确的工具调用顺序。一条具有创造性、但仍在边界内到达有效结果的路径，应当被允许通过。

### 7.3 评估实际发布的系统

进程内的测试辅助工具对开发有用，但它不是主要的能力基准。权威的执行适配器应当以一份冻结的评估对象清单，去调用真正构建出来的产物。

### 7.4 把能力故障和评测框架故障分开

Agent 故障、无效任务、基础设施故障、评分器故障、超时与取消，这些是不同的结果。基础设施故障不能被悄悄算作模型故障，也不能从报告中消失。

### 7.5 全局分数不能掩盖严重失败

报告可以给出套件层面的汇总，但任何加权平均都不能把一次信任违规变成一次通过的发布，哪怕别处的编码质量有所提升。关键断言始终是硬性门槛。

### 7.6 默认本地优先、默认私有

试验包默认留在产生它们的机器或部署环境内。导出必须是明确的、经过脱敏的、有边界的，并且可以与执行过程分离。可选的托管工具绝不能成为评估或正常产品运行的必需依赖。

## 8. 提议的系统模型

拟议的流程是：

```text
dataset + experiment
        |
        v
subject resolver --------> immutable subject manifest
        |
        v
execution adapter --------> isolated trial environment
        |
        v
canonical trial bundle <-- trace + final state + artifacts + usage + errors
        |
        v
graders ------------------> per-dimension scores, labels, explanations
        |
        v
experiment comparison ---> qualification report and gates
```

### 8.1 Task

一个 Task 定义了：

- 稳定的 ID、版本、所属套件、标签，以及目标评估领域；
- 指令或多轮场景；
- 可见的初始状态；
- 执行表面与所需能力；
- 墙钟时间、轮次、工具调用次数、令牌与资源限制；
- 必需与可选的评分器；
- 试验次数的默认值；
- 环境与依赖版本；以及
- 对隐藏验证材料和一个 Oracle 的引用。

每一个已提交的 Task 都必须通过预检：

1. 其初始状态尚未满足所要求的结果；
2. 其 Oracle 能够完成该任务；
3. 所有必需的评分器都能通过该 Oracle；
4. 重复运行该 Oracle 在既定的解释下足够确定；以及
5. Agent 无法透过试验边界访问隐藏的评分器或 Oracle 材料。

### 8.2 评估对象

评估对象清单冻结了被评估的配置，包括：

- BuildMax 的提交、构建标识与脏状态摘要；
- 二进制文件或容器镜像的摘要；
- 表面与执行适配器的版本；
- 提供商传输方式、目标模型或别名、推理与生成限制；
- 生效系统提示与工具 Schema 的摘要；
- 提示层、技能、插件、MCP 与 Agent 定义的来源；
- 权限、Hook 与沙箱的解析结果；
- 操作系统、架构、CPU、内存与网络配置；以及
- 数据集与契约版本。

密钥与完整的私有指令正文不属于该清单。它们的摘要与可安全披露的来源足以标识评估对象，而不会让结果本身变成一个凭证或内容存储。当某个提供商无法披露确切的模型版本时，该清单应记录这种不确定性，而不是凭空捏造出一份精确的记录。

### 8.3 试验

一次试验是一个评估对象针对一个 Task 的一次独立尝试。它的终止状态是以下之一：

| 状态 | 含义 |
|---|---|
| passed | 所有必需的评分器都通过了 |
| failed | 执行已完成，但一个或多个必需的评分器未通过 |
| agent_error | Agent 运行时在产生可评分结果之前就失败了 |
| infrastructure_error | 环境或依赖出现故障，与 Agent 能力无关 |
| grader_error | 必需的评分未能完成 |
| timed_out | 共享的 Task 墙钟时间预算已耗尽 |
| canceled | 实验控制器终止了该试验 |
| invalid_task | 预检或任务完整性检查失败 |

### 8.4 标准试验包

试验包是稳定的交换边界。它包含或安全引用了：

- Task、数据集、实验、评估对象与试验的身份信息；
- 输入与初始状态的摘要；
- 终止状态与故障分类；
- 在保留策略允许的情况下，最终回复与结构化结果；
- 持久化轨迹与子轨迹的引用；
- 最终工作区或数据库状态的证据；
- Artifact 的身份、哈希与验证输出；
- 评分器版本与各维度的评分结果；
- LLM 调用、工具调用、令牌数、耗时与资源观测数据；以及
- 一段有边界的复现说明。

该契约是版本化的，并且无需 BuildMax 进程即可序列化。运行器和查看器可以添加扩展字段，但资格认证的门槛只读取 BuildMax 自有的字段。

## 9. 执行适配器

该契约支持多种适配器，因为没有哪一个单一环境能够代表整个产品：

| 适配器 | 用途 |
|---|---|
| Agent Core / 本地 | 针对共享本地运行时进行快速的行为验证 |
| CLI 二进制文件 | 验证已发布的本地命令与工作区行为 |
| Desktop 运行时 | 验证 UI 呈现层之下的本地工作台一致性 |
| Worker / TaskRun | 验证物化、非交互式执行、Artifact、传输与边界 |
| Conversation | 验证前台回复、可选的 Agent 任务委派、结构化结果投影，以及多轮对话结果 |
| 部署 | 验证 Compose 或 Kubernetes 依赖及运维人员可见的故障行为 |
| Harbor | 运行 Terminal-Bench 2.1 及其他标准化容器基准 |

确定性的端到端套件仍然是独立存在的。它们可以与评估适配器共享环境和进程启动方面的辅助工具，但一个基于脚本模型的协议测试与一次概率性的真实模型试验，仍然保留各自不同的名称、结果与发布层面的解读方式。

## 10. 评分器

### 10.1 确定性结果评分器

只要可行就优先采用：

- 测试与静态分析；
- 文件、Artifact、Schema 与内容断言；
- 数据库或 API 状态验证；
- 授权与所有权检查；
- 部署与依赖健康证据；以及
- fail-to-pass 加 pass-to-pass 的回归检查。

### 10.2 轨迹与策略评分器

它们检查的是结构化事件，而不是自然语言文本：

- 禁止或缺失的工具使用；
- 参数与作用域的有效性；
- 审批、Hook 与沙箱的决策；
- 重试、循环、压缩与过早停止的行为；
- 完成前是否进行了必需的验证；
- subagent 谱系与继承的策略；以及
- 边界或脱敏方面的违规。

现有的持久化轨迹还不能表达所有期望的事件。缺失的 Hook 执行、文件变更、逐命令边界与重试证据，都应当被明确记录为空白，而不是从自由文本中推断出来。

### 10.3 模型评分器

用于那些无法简化为状态检查的维度，比如有用性、可靠依据（groundedness）、覆盖面、清晰度，或者一次澄清是否恰当。每个维度都有独立的、结构化的评分标准，以及一条 `unknown` 路径。模型评分器会记录自己所用的评估对象和成本。

一个模型评分器要成为硬性门槛之前，必须先在一个冻结的人工标注集合上，评估它的一致性、自我一致性、位置或风格偏差，以及对抗鲁棒性。确定性的失败不能被模型评分器推翻。

### 10.4 人工评分

人工审查用于校准模型评分器、裁定 Task 或评分器本身的缺陷，并对重要的、来自生产环境的用例进行抽样。它不需要在每一次常规实验中都出现，事后的人工判定会与最初的自动化结果分开记录。

## 11. 测试套件策略

第一批产品自有的套件应当是：

| 套件 | 主要目的 |
|---|---|
| Agent Core 回归 | 工具循环、恢复、压缩、并行调用、排队输入、停止 |
| 本地工作台 | 编码、文件、结构化数据、研究、会话、本地 Artifact |
| Worker 与 TaskRun | 物化、托管/直接传输、Artifact、取消、重试、超时 |
| Conversation 与 Workflow | 意图处理、澄清、委派、结果交付、多轮状态 |
| 信任与控制 | 权限、Hook、沙箱、注入、密钥、路径、网络、Space 范围 |
| 可扩展性 | MCP、技能、插件、subagent、缺失依赖、来源 |
| 跨表面一致性 | 同一个抽象 Task 在本地与 Worker 环境中的表现 |

套件应当同时包含正向和负向用例。举例来说，测试 Agent 是否在需要时进行搜索，就必须配上一些搜索是不必要甚至被禁止的用例。能力套件包含仍有提升空间的困难任务；回归套件包含几乎应当每次都通过的行为。

公开的开发套件是透明且可复现的。私有或轮换的留出集使用同一份契约，但通过不可变的数据集版本和摘要来获取。私有数据不是 Git 子模块，也不会让公开套件的执行依赖于私有访问权限。

## 12. 指标、比较与门槛

每个套件报告的是一个向量，而不是单一的项目级分数：

- 由独立试验估计出的 pass@1；
- 当多次尝试是一种合理产品行为时的 pass@k；
- 当一致性才是要求时的 pass^k；
- 置信区间与逐用例方差；
- 必需评分器与关键用例的失败情况；
- 基础设施、评分器、超时与取消的比率；
- LLM 与工具调用次数、提示与补全令牌数；
- 墙钟时间与相关的延迟百分位数；
- 只有在定价输入明确、有版本且适用时才计算的成本；以及
- 以计数和具名用例形式呈现的信任、策略与边界违规。

候选评估对象与基线评估对象在同一组 Task 上运行，并尽可能在相同的时间窗口和基础设施配置下运行。比较按 Task 和试验序号成对进行。报告会展示绝对结果、成对差值、不确定性、变好的用例、变差的用例，以及无法评分的失败。

建议的节奏是：

| 节奏 | 评估内容 |
|---|---|
| 每个拉取请求 | 确定性的 Schema、Oracle、评分器、适配器与模拟模型检查 |
| 有风险的 Agent 变更，按需 | 一次小规模的成对真实模型回归实验 |
| 每晚 | 已固定的回归用例集合，多次试验 |
| 每周或资格认证事件 | 更广泛的能力、部署与模型矩阵 |
| 发布 | 关键的信任与可靠性用例，加上已接受的成对回归阈值 |
| 定期的外部评估 | 公共基准子集与可复现性审计 |

默认情况下，真实模型试验不应作为每个拉取请求的门槛。提供商漂移、凭证管理、延迟与开销，使它们不适合替代确定性验证。只有在这个套件本身的方差、任务有效性、基础设施可靠性和预期预算都被测量清楚之后，它们才能成为硬性门槛。

## 13. 仓库与依赖边界

新的 `evaluation/` 工作区最初应当留在主仓库内。需要的是逻辑上的隔离，而不是一个独立的 Git 仓库。

预期的所有权划分是：

| 区域 | 职责 |
|---|---|
| contract | Task、评估对象、试验包、评分结果与实验的 Schema |
| suites | 公开的、产品自有的 Task 与场景目录 |
| adapters | CLI、Worker、Conversation、部署适配器，以及外部测试框架的桥接 |
| graders | 可复用的确定性、轨迹、策略与语义评分器 |
| environments | 本地、容器、Compose 与 Kubernetes 的试验定义 |
| runner | 实验执行、重复、比较、统计与报告 |

这是一个所有权模型，而不是一份已经确定的目录结构。当第一个切片确立了实际形态之后，实现会更新仓库布局这份权威文档。

评估工具可以使用 Python、容器或其他带有自己锁文件的开发依赖。这些依赖不会进入 Go module、产品二进制文件，也不会成为正常本地与部署场景的先决条件。跨平台任务运行器仍然是贡献者的统一入口。

体量较大的输出应放在被忽略的 Artifact 区域，而不是纳入源代码版本控制。私有留出集可以存放在受访问控制的 Git 仓库、对象存储或 CI Artifact 仓库中，但它们要实现主仓库的这套有版本的契约。只有当独立的所有权、发布节奏、访问控制、规模或复用需求，使跨仓库的兼容成本低于共同开发的成本时，才应当考虑建立一个独立的评估仓库。

## 14. 外部框架与基准

### 14.1 框架角色

没有哪个外部框架是系统的权威记录。[第 15.3 节](#153-实验控制器与实现语言)把一个用 Go 编写的轻量级 BuildMax 控制器定为默认选择；这个切片会用 Inspect 对它做一次 spike 验证，Inspect 必须靠证据赢得切换，而不是仅仅打成平手。Harbor 是一个独立的环境与基准适配器，而不是另一个候选控制器。其余的集成都保持可选，只有在某个已验证的工作流确实需要时才会被引入。

| 框架类别 | 候选角色 | 边界 |
|---|---|---|
| Inspect AI | 挑战默认控制器：轮次、限制、评分、日志与统计 | 必须能产出并消费 BuildMax 的试验契约；一旦采用它，也就同时采用了 Python，因此必须先满足第 15.3 节的推翻条件 |
| 轻量级 BuildMax 控制器 | 默认控制器 | 只负责契约中缺失的最小编排；不能演变成一个 LLMOps 平台 |
| Harbor | 首选的容器与公共基准适配器，从 Terminal-Bench 2.1 开始 | 是一个执行适配器，不是控制器，也不是产品结果模型 |
| Phoenix 或 Langfuse | 之后可选的、自托管的轨迹、实验与标注 UI | 查看器/导出目标；永远不是必需或权威的；只有在本地报告被证明不够用之后，才最多选择其中一个 |
| Promptfoo | 可选的对抗性提示与红色场景生成 | 生成出的用例会回归到 BuildMax 自有的 Task 与评分器中；它不在主评估路径上 |
| 提供商评估 API | 可选的语义评分器或比较服务 | 核心工作流不会因此对任何提供商产生硬依赖 |

这次 spike 是在检验默认方案，而不是重新打开这个问题。它必须至少覆盖一个本地 Task、一个 Worker Artifact Task、一个 Portal 委派 Task、一个信任边界 Task，以及一次重复比较，并记录双方在适配器代码量、Schema 阻抗、诊断质量、并发行为和运维依赖上的差异。只有当 Inspect 能省下足够多的控制器工作、其收益超过它带来的 Python 工具链成本，并且不会削弱标准契约、默认私有的执行方式、诊断能力或可移植性时，才会被选用。Harbor 单独评估，因为它最强的角色是容器后端与公共基准的桥梁。

### 14.2 公共基准的角色

> **更新（2026-09-19）：** 锁定的目标已经推进到 Terminal-Bench 4.0
> （`terminal-bench/terminal-bench`，66 个任务），并且 `pins.json` 是 harness、
> 数据集摘要与金丝雀的唯一事实来源。金丝雀现在被用作一个小型的本地回归子集——
> 五个廉价、仅限 Linux 的任务，用真实模型跑一遍以捕捉产品回归——而不是通往排行榜
> 分数的一步。下文的 2.1 论述作为“为什么选择 Terminal-Bench”的决策记录保留；其中
> 与版本相关的数字描述的是 2.1。

Terminal-Bench 2.1 是第一个外部能力基准，也是被接受的 Harbor 集成目标。2.1 版本取代 2.0 成为 BuildMax 的基线：它自己的 README 说明，89 个任务中有 26 个被修改过——涉及 bug、超时、资源和抗奖励作弊的健壮性——因此绝不能把 2.0 的分数和 2.1 的分数相提并论，仿佛只有 Agent 发生了变化。本段在记录被接受时曾写成 28，但上游的实际数字是 26。

选择它是因为它现场的排行榜会把 Agent 和模型分别命名，接受自定义 Agent，报告带不确定性的重复试验，并且包含 Codex、Claude Code 与 Harbor 的参考 Agent。这使它成为一个比那些固定单一脚手架、主要比较模型的排行榜更好的测试框架坐标。它确定性的容器结果也天然契合 BuildMax 的黑盒与最终状态契约，不需要模型评分器。

这次集成有以下边界：

- 锁定 Harbor 的版本、`terminal-bench/terminal-bench-2-1` 数据集的发布版本与摘要、BuildMax 适配器的版本，以及每一个可能改变结果的容器或提供商依赖。
- 通过 Harbor 的自定义 Agent 边界暴露构建出的 BuildMax Artifact。Harbor 拥有 Task 物化与官方验证；BuildMax 不维护第二套运行器，也不把 Terminal-Bench 的 Task 复制进产品套件。
- 在为完整基准投入之前，先在一个命名的金丝雀子集上验证适配器、证据转换与 Oracle 边界。一次完整的、可比较的运行会使用全部 89 个 Task、每个 Task 五次尝试，并且不修改排行榜的资源与超时策略。
- 把每一次尝试都转换成 BuildMax 的试验契约，并将 Harbor 的 Task 身份、结果、日志、资源限制、用量与测试框架故障，同 Agent 故障分开保留。外部验证器仍然是基准结果的权威来源。
- 金丝雀运行、完整资格认证与基线比较只作为明确的、计划内的或发布时的任务来执行。它们绝不是普通拉取请求的常规门槛。

有两个操作层面的事实，都是在构建适配器的过程中发现的，而且都比最初假设的要窄。运行该基准并不需要一个 Harbor Hub 账户：Harbor 的客户端在未登录时是匿名的，公开读取照常可用，因此已锁定的公开数据集下载与试验运行都不需要账户。登录只是发布、`--upload`、组织与密钥管理，以及私有数据集所必需的。而且截至写作时，社区向 2.1 排行榜的提交是关闭的——只有维护者自己提交的结果会被收录——因此这里得到的结果可以与已发布的行做比较，但目前还不能成为其中的一行。这两点都不会改变所测量的内容，但都会改变一次运行能被用来做什么。

主要的测试框架比较会固定模型、推理力度、提供商、Task 版本、资源和尝试次数，只改变 Agent 适配器。BuildMax 应当首先与 Harbor 的参考 Agent 比较，并在能够访问相同模型的情况下，与 Codex 和 Claude Code 比较。原生的 Codex/模型和 Claude Code/模型组合仍然是有用的产品坐标，但它们之间的差异并不能证明某个测试框架更有优势，因为模型本身也变了。

每次实验都会对相关的现场排行榜行做一次快照，而不是把会变化的分数直接抄进这份设计记录里。报告会标明完整的评估对象元组——Agent 及其版本、模型及其版本、推理力度、提供商、Harbor 与数据集版本、环境与资源配置——并展示带不确定性的通过率、逐 Task 结果、成本、令牌数、延迟、超时与测试框架故障。一个没有这份元组的头条百分比数字，不能算作 BuildMax 的资格认证结果。

- 类 SWE-bench 的 Task 以及 [SWE-rebench](https://swe-rebench.com/) 提供了后续代码仓库编辑方面的坐标，但它们不定义产品，也不能取代第一个 Harbor 目标。
- [BoundaryBench](https://github.com/boundary-bench/boundary-bench) 为后续的沙箱策略坐标提供参考。它复用了 Terminal-Bench 的 Task，但施加了更严格的策略，因此它是对未修改的 2.1 基线的补充，而不是替代。
- [METR 的脚手架比较](https://metr.substack.com/p/2026-02-13-measuring-time-horizon-using-claude-code-and-codex)发现，在其测试的模型和 Task 分布上，Codex 或 Claude Code 相对于其默认脚手架并没有普遍具有统计显著性的优势。这可以作为同模型成对比较的证据，但不能被当作某个测试框架具有普适倍增效应的依据。
- 类 tau-bench 的场景为多轮用户、策略、工具与最终状态评估提供参考。
- BFCL 提供的是模型/工具调用层面的坐标，而不是端到端的 BuildMax 分数。
- 由于计算机使用还不是核心产品表面，GUI 计算机基准暂缓考虑。

公共基准的版本、测试框架版本、补丁、排除项、资源、尝试次数，以及所有其他偏差都会被报告出来。一个没有这些上下文的排行榜数字，不能算作资格认证结果。Terminal-Bench 可以确立相对的终端与容器任务能力；但它无法确立 Worker 治理、Portal 交付、跨表面一致性、私有部署可运维性，或者其他 BuildMax 的产品结果。

## 15. 决策

### 15.1 评估边界

| 决策 | 已接受的方向 |
|---|---|
| 遗留兼容性 | 淘汰现有目录与测试框架；不保留它们的格式 |
| 位置 | 在主仓库中使用一个新的顶层 `evaluation/` 工作区 |
| 仓库 | 初期不新建独立仓库 |
| 评估接口 | 在 BuildMax 自有契约之后，以黑盒方式对待构建出的 Artifact |
| 框架姿态 | 外部框架都是可替换的适配器或查看器 |
| 产品指标 | 产品自有套件驱动发布决策；公共基准只是外部参照坐标 |
| 聚合方式 | 能力、可靠性、信任与产品结果各自独立的评分卡；不存在全局分数 |

### 15.2 产品与治理的默认设定

| 决策 | 已接受的方向 |
|---|---|
| 受众 | 维护者与运维人员的资格认证都属于初期范围；面向 Space 的授权是之后的事 |
| 优先级 | 在投入实质性的新 Agent 能力之前，黑盒垂直切片是近期的使能性工作 |
| 私有留出集 | 资格认证可以使用受访问控制或轮换的数据，只要它遵循公开 Schema、具有不可变版本与摘要，并且存在一个完全可运行的公开开发套件 |
| 真实模型门槛 | 计划内和发布时的资格认证可以消耗提供商凭证和一份有限预算；普通拉取请求默认仍保持确定性 |
| 试验隐私 | 默认情况下，原始提示词、回复、轨迹、工作区快照与评分器正文都保留在本地/私有环境中，需要明确的、有边界的导出操作 |
| 未来的 Space 范围 | 契约要支持未来面向 Space 发布前的 Agent 与 Workflow 评估，但不承诺任何面向 Space 的 UI 或路线图阶段 |

### 15.3 实验控制器与实现语言

控制器和它的实现语言是一个决策，而不是两个。选择 Inspect 就等于同时选择了 Python，而剩下的组合——Python 加上一个 BuildMax 自己再写一遍的控制器——是两者中最差的一种：花钱买了第二套贡献者工具链，却没有换来本该为此买单的轮次、限制、评分和日志查看器。这种组合被排除在考虑范围之外。

| 决策 | 已接受的方向 |
|---|---|
| 控制器 | 一个轻量级的 BuildMax 控制器，用 Go 编写，只使用标准库，放在主模块内 |
| 语言 | 默认使用 Go；Python 只会随 Inspect 一起进入，绝不会单独引入 |
| 推翻条件 | Inspect 的 spike 证明它省下的控制器工作量，超过第二套工具链和运维人员的安装成本 |

按权重从高到低，有三点决定了这个选择：

- **运维人员要自己运行它。** 第 4.2 节要求私有部署的运维人员能在自己的环境中对模型、配置和部署做资格认证。这个产品是一个不需要 Node 的单一二进制文件，私有部署理应是"无聊"的。要求运维人员在做任何资格认证之前先装好 Python、创建虚拟环境、维护锁文件，直接违背了这一点。
- **不引入新依赖，现有门槛也是免费获得的。** 一个基于标准库的控制器不会给 `go.mod` 增加任何东西，这正是第 13 节所要求的。因为它就在主模块内，`./make test`、`vet`、`lint` 和 `govulncheck` 已经通过 `./...` 覆盖到它；评估系统自身的正确性不需要第二条 CI 流水线、锁文件或版本锁定方案。
- **轨迹漂移会在编译期就失败。** 一个 Go 控制器通过 `internal/infra/trace` 中的记录类型来解析轨迹，因此轨迹格式的变化会直接导致构建或测试失败。而一个 Python 控制器需要手工转录这份 Schema，漂移只会在运行时才暴露出来——这正是第 19 节中"框架演化风险"的自制版本。

统计能力是支持 Python 最有力的论据，但它比看上去要弱。第 12 节需要的是二项分布置信区间、pass^k、成对比较与逐用例方差：这不过是几百行输入输出固定的纯函数，恰恰是最容易被测试的一类代码。更重的分析——功效分析、分层抽样、评分者间一致性模型——属于第 2 阶段及以后，并且可以作为一个读取已提交 JSON 试验包的离线 Python 脚本来实现。这份契约是语言无关的，所以这条路始终敞开，不需要现在就做决定。

Harbor 和 Terminal-Bench 2.1 同样不能构成支持 Python 的理由。第 14.2 节让 Harbor 作为一个独立进程去调用一个 BuildMax Agent 适配器——这是一个外部工具在调用一个 BuildMax 二进制文件，而不是一个 BuildMax 控制器去导入一个 Harbor 库——因此控制器所用的语言并不会触及它。

真正的成本是存在的，这也是推翻条件所要衡量的：实验控制（重复、并发、限制、取消、恢复）和报告渲染都必须自己写出来，而 Inspect 会连同一个日志查看器一起把它们提供出来。

### 15.4 仍需依据证据决定的技术选择

垂直切片必须用证据而不是偏好来解决以下选择：

- Harbor 面向 Terminal-Bench 2.1 的精确自定义 Agent 适配器机制；
- 报告渲染器——鉴于上面提到的统计能力是自己实现而不是引入的；以及
- Phoenix、Langfuse，还是不用外部查看器。

物理层面的试验包编码方式已经不再是悬而未决的问题。第 1 步把它确定为一个目录，而不是单一文档：一份试验包的大部分内容本来就是文件——JSONL 轨迹、工作区状态、产出的 Artifact——把它们内联进单一文档反而违背了它们本应服务的有边界证据规则，而"每次尝试一个目录"正是第 17 节所要求的复现路径。`evaluation/contract` 实现了这套布局。

其余每一项都源自这个黑盒垂直切片，并且必须保持与上述契约和隐私决策一致。

## 16. 选项与权衡

| 选项 | 优势 | 主要顾虑 |
|---|---|---|
| 扩展现有的 Go 基准 | 眼前改动最小 | 保留了一个早期的编码任务抽象，它无法干净地代表当前的产品 |
| 采用某个外部框架作为权威记录 | 更早获得成熟的通用运行器、评分与 UI | BuildMax 的产品语义、可移植性与隐私都会从属于另一个框架的模型 |
| 现在就构建一个完整的自研评估平台 | 控制力最大 | 在代表性任务和运维人员需求得到验证之前，就前置投入一个庞大的 LLMOps 产品 |
| 自有契约与产品套件；使用可替换的运行器、后端与查看器 | 在复用成熟基础设施的同时，把产品含义与隐私牢牢掌握在 BuildMax 手中 | 需要有纪律的契约设计和适配器一致性 |

已接受的方向是最后一个选项。

## 17. 交付顺序

### 阶段 0：评估章程与契约

- 定义有版本的 Task、评估对象、试验包、评分结果与实验契约。
- 定义保留、脱敏与导出边界。
- 定义故障分类和资格认证报告的语义。
- 对照所需的过程证据，审计现有的持久化轨迹。

### 阶段 1：黑盒垂直切片

- 构建一个覆盖本地、Worker、Conversation 与信任行为的小型代表性套件。
- 在隔离环境中运行构建出的二进制文件或镜像。
- 保留隐藏评分器与一个可执行的 Oracle。
- 每次尝试产出一个标准试验包。
- 对基线与候选评估对象进行多次重复试验的比较。
- 对 Inspect 与一个轻量级控制器做 spike 比较，并添加一个面向 Terminal-Bench 2.1 的 Harbor 适配器。

当一次失败能够给贡献者提供分类结果、轨迹、最终状态证据、评估对象清单和一条有边界的复现路径时——而不只是一个更低的汇总分数——这个切片就算成功。

阶段 0 和阶段 1 被拆分成一系列有序的增量步骤，连同它们所依赖的轨迹审计和适配器草图，记录在[第 18 节](#18-垂直切片实施计划)中。

### 阶段 2：维护者与运维人员的资格认证

- 扩充回归、能力、Worker、信任与跨表面套件。
- 建立可度量的节奏、重复次数、提供商预算与门槛。
- 添加模型/配置与部署方面的资格认证报告。
- 添加一个有版本的私有或轮换留出集。
- 在本地工作流足够好用之后，添加向自托管查看器的可选导出。

### 阶段 3：生产反馈闭环

- 在所属部署内部，对合规的失败用例和用户反馈进行抽样。
- 在把用例提升进数据集之前，要求人工脱敏与审查。
- 把 Task 与评分器的缺陷同 Agent 自身的缺陷分开追踪。
- 在发布前，用候选评估对象重新跑一遍已提升的用例。

### 阶段 4：面向 Space 的评估（若被单独接受）

- 让一个 Space 为某个 Agent 或 Workflow 定义私有场景。
- 在 Space 的授权和配额范围内运行这些场景。
- 在发布前比较不同定义版本。
- 让评估结果、轨迹和数据集都保持在 Space 范围之内。

这个阶段需要一次独立的产品与数据模型决策。前面几个阶段只是为它保留一条契约层面的路径。

## 18. 垂直切片实施计划

第 17 节给出了阶段方向，本节是阶段 0 和阶段 1 在实施开始前写就的可执行拆解，并且承担着[第 20 节](#20-实施过程中所需的证据)第 2、3 项所要求的证据：轨迹字段清单，以及黑盒适配器草图。

这里的内容不会改变第 15 节中已经接受的决策。它落实了第 15.3 节的控制器决策，并解决了第 15.4 节交给这个切片去决定的问题。

### 18.1 现有测试框架留下的遗产

| 资产 | 处置方式 |
|---|---|
| `eval/001-read-summarize` … `eval/013-worker-pool` | 删除。其中一些可能会在新契约下重建为低价值的冒烟用例 |
| `internal/agenteval` | 删除，连同其格式一起 |
| `tools/eval` | 重写为新契约与运行器的入口点 |
| `./make eval` | 重写为分发给新运行器；默认跑 CLI Task，Worker 与全表面运行需要显式选择 |

有四个缺陷是决定重写而不是延续的理由，它们比第 2.1 节说的更具体：

- `internal/agenteval/catalog.go` 把 Task 目录本身当作 fixture，因此运行器会把 `task.md` 以及其中包含的评分脚本一起复制进工作区。评分器不只是和 Task 放在一起，它对被评估的 Agent 而言是可读的。
- `internal/agenteval/runner.go` 把缺失的 fixture 目录只当作一条警告处理，然后照样在一个空工作区上运行该 Task。一个本身无效的 Task 因此会被记录成 Agent 故障，这正是第 7.4 节所禁止的那种混淆。
- `internal/agenteval/runner.go` 通过 `agentapp.NewAgentApp` 在进程内构造运行时。它测量的任何东西都无法区分 CLI、Worker 或部署行为，也没有运行任何真正构建出来的产物。
- `internal/agenteval/result.go` 只记录一个布尔值加上令牌计数。没有评估对象身份，没有轨迹引用，没有重复试验，除了"Agent 故障"和"评分器故障"之外也没有更细的故障分类。

### 18.2 轨迹证据审计

这是第 20 节要求的、在评分设计确定之前必须完成的清单。它是对照 `internal/infra/trace/record.go` 和 `internal/infra/trace/summary.go` 做出的。

| 评分器需要的证据 | 现有轨迹中是否存在 | 差距 |
|---|---|---|
| 运行身份、模型、工作区、subagent 谱系 | `run_start`，带有 `trace_version` 以及父运行/工具调用的链接 | 对这个切片而言没有差距 |
| 指令来源 | `context_sources`，即使为空也会写入，与同一次运行的记忆与压缩来源并列 | 无 |
| 扩展来源 | `plugins`，带有仓库插件的可变性信息 | MCP 服务器与技能没有被单独命名 |
| 沙箱边界 | `sandbox_boundary`，每次运行一条，`sandboxed` 会明确写为 false 而不是缺省不出现 | 没有逐命令级别的决策 |
| 工具使用与参数范围 | `tool_start`、`tool_end`，带有耗时 | 参数和结果被截断在 4096 字节，因此大负载相关的断言不能依赖它们 |
| 被拦截的调用 | `tool_denied`，带有 `deny_reason` | `summary.go` 把 Hook 拒绝和策略拒绝都归并成同一个 `Denied`；需要区分两者的轨迹评分器只能去解析原因字符串 |
| 上下文压力与循环 | `iter_start`、`llm_start`、`context_compacted` | 无 |
| 令牌、缓存与成本核算 | 每次调用及累计的 `llm_end`、`run_end` 总计、`cost_incomplete` | 无 |
| 运行中途的指令变化 | `user_input`、`user_input_blocked` | 无 |
| Hook 执行 | 缺失 | 在信任与控制套件可信之前，这是必需项 |
| 文件变更 | 缺失；只能从有边界的工具参数里推断 | 在结果评分能够归因到具体变更之前，这是必需项 |
| LLM 重试与提供商错误 | 缺失 | 在可靠性评估能把提供商噪声和 Agent 行为分开之前，这是必需项 |

这个切片就在现有条件下推进。能力、可靠性，以及信任维度中权限那一半，今天就是可评分的。Hook 执行和文件变更事件是信任与控制套件的前提条件，而不是这个切片的前提条件，它们属于[信任保障](信任保障.md)和[持久化运行轨迹](持久化运行轨迹.md)的后续工作，不会顺带在这里补上。

### 18.3 黑盒适配器草图

CLI 适配器是这个切片的权威执行路径：

```text
BUILDMAX_HOME=<trial home>   buildmax -p <instruction>
                             --workspace <trial workspace>
                             --model <subject model>
                             --output json
```

试验用的 home 目录由评估对象解析器构建，而不是继承自贡献者本人的环境。这正好消除了第 2.1 节提到的问题：本地设置、Hook、插件与权限悄悄改变了被测量的对象。

`internal/interface/cli/print_format.go` 已经会输出一份稳定的信封结构，携带回复内容、工具调用次数、耗时、用量、缓存与成本明细、上下文占用率、退出码和 `policy_denied`。`internal/interface/cli/exit_code.go` 中的退出码是一份文档化的契约，它们可以直接映射到第 8.3 节的分类上：

| CLI 退出码 | 试验状态 |
|---|---|
| `ExitOK` | 由评分器决定 `passed` 还是 `failed` |
| `ExitUsage` | 若是 Task 提供了错误输入则为 `invalid_task`，若是试验 home 本身有问题则为 `infrastructure_error` |
| `ExitPolicyDenied` | 由评分器决定；一个信任类 Task 可能恰恰要求被拒绝，所以这本身并不算失败 |
| `ExitModelError` | `agent_error` |
| `ExitUserCancelled` | `canceled` |
| `ExitIterationCap` | `timed_out`：一个既定的预算耗尽了，这是对评估对象本身的判断，而不是测试框架本身坏了。此项为后续添加；参见[第 18.7 节](#187-构建并首次运行-harbor-适配器带来的变化) |
| 墙钟时间预算耗尽 | `timed_out` |
| 必需的评分器无法运行 | `grader_error` |

要让这个适配器能够工作，需要一处产品改动。`agentapp.RunResult` 已经携带了 `TraceID` 和 `TracePath`，但 CLI 的信封结构并没有把它们暴露出来，导致外部调用者无法确定一次运行到底写了哪个轨迹文件——一个有多次运行的会话会持有好几个轨迹文件。这个切片把 `trace_id` 和 `trace_path` 添加到打印模式的信封结构中。这项改动的可见性超出了评估的范畴，因为它也是一个人查找自己刚跑完的那次运行的轨迹的方式，所以它附带了一条 changelog，以及对 `manual/cli.md` 的更新。

Worker 适配器紧随这个切片之后完成构建。原本以为缺失的东西——一种无需 Portal 用户即可提交试验并收集其试验包的方式——结果证明根本不需要专门造一个。一个 Worker 通过 HTTP 联系它的服务器，此外什么都不做：拉取运行任务、上报状态、流式输出、轮询取消状态。于是适配器就在回环端口上，为恰好一次运行自己实现了这个 API。这里面没有数据库，没有 Space，没有调度器，也没有任何 Portal 用户参与，这和 `mockllm` 在模型这一侧所做的事情如出一辙。

它的调度方式和一个调度器一样：命令行上给出一个运行 ID，环境变量里给出一个运行令牌，再加上一个指向控制平面的 `server.yaml`。它所验证的、CLI 无法验证的部分，正是只有 Worker 才有的那一半产品：把 Space 的持久化工作区物化进一个运行专属目录，在没有交互式表面的情况下执行，并把结果通过 API 而不是终端上报出去。结果是从 Worker 上报的内容中读取的，而不是从它的退出码中读取：一个运行失败的 Worker 会上报 FAILED 并以非零状态退出，而一个被杀死的 Worker 则什么都不会上报，只有控制平面能区分这两种情况。

Conversation 与部署适配器仍未构建。

### 18.4 隐藏评分器边界

Task 目录中存放着指令、初始状态、评分器和 Oracle。只有声明过的初始状态会被物化进试验工作区。Task 目录中的其他任何东西，在工作区内部都不可达。这就是针对 18.1 节第一个缺陷的具体修复方案，而且它是这个切片会直接测试的一项属性：一个评分器材料出现在工作区中的 Task，会在预检阶段就失败，而不是产出一次通过的试验。

### 18.5 不依赖提供商密钥的确定性检查

`internal/testsupport/mockllm` 已经能够根据一份已提交的场景来回答模型，并支撑着 CLI 端到端套件。这个切片复用了它，从而让第 12 节节奏表里"每个拉取请求"那一行是真实存在的：契约的往返序列化、Task Schema 校验、评分器单元测试、适配器进程启动与信封解析，以及退出码到状态的映射，全部都可以在没有任何提供商凭证的情况下运行。这维持了仓库的一条规则：一次完整的检查不需要模型 API 密钥。真实模型只会被按需实验、每晚实验和发布实验所触及。

复用它需要一处刻意做出、而不是遗漏造成的架构改动。`internal/architecture/architecture_test.go` 通过扫描 `internal`、`cmd` 和 `deployment` 三棵目录树，把 `internal/testsupport` 挡在发布代码之外；一个新的顶层 `evaluation` 目录树，如果不被列进这条规则，就能逃过检查，而这是一个错误的"被允许"的理由。这个切片把 `evaluation` 加入了被扫描的目录树列表。

除了 `deployment/smoke` 之外，它没有再加任何豁免——本节此前的草稿曾经预期需要一个。这条规则本来就会跳过 `_test.go` 文件，所以评估自身的端到端测试可以不带任何豁免地导入 mock 模型；而如果给整棵目录树开豁免，反而会额外放行一件必须继续被禁止的事情：一个运行器或适配器如果去回答它自己提出的模型请求，那它验证的就是这个 mock 本身，而不是被评估的对象。

| 5. Harbor 适配器——**已完成** | `evaluation/harbor`：锁定版本的测试框架、数据集引用与适配器版本；一个把构建出的 CLI 上传进 Task 容器并运行一次提示的 Python 自定义 Agent；把跑完的作业归档成试验包的导入器；`./make doctor harbor` 与 `./make eval harbor` | 证明该契约对一个 BuildMax 不拥有其验证器的外部测试框架同样成立。Oracle 冒烟测试跑通了 5/5，一次单任务金丝雀测试端到端跑通并完成了导入，说明适配器已经能针对一个 Task 驱动这个真实的测试框架。它对其余 88 个 Task、重复尝试或者一个分数都还什么都没说明 |
| 6. 金丝雀运行与比较——**待完成** | 金丝雀子集已锁定在 `pins.json` 中，`--canary` 用于选中它；运行它是待完成项，接下来是在排行榜未经修改的资源与超时策略下，以每个 Task 五次尝试跑完全部 89 个 Task，并与 Harbor 的参考 Agent 做基线比较 | BuildMax 到底表现如何。一个通过的 Task 算不上一次测量 |

这个切片还发现了五件值得延续下去的事情。在预算耗尽时杀死一个评估对象，并不会真正结束这次调用：进程本身死了，但它启动的任何孙子进程仍然让输出管道保持打开，于是一次原本设计用来限定运行边界的等待，反而变成了永远不会返回的东西。而且现有的持久化轨迹无法区分一次 Hook 拒绝和一次策略拒绝，因此一个需要断言其中之一的信任评分器，只能去读原因字符串；第 18.2 节列出了这个差距，而第一个真正的信任套件，就是这个差距不再能被容忍的地方。

一个评分器命令和一个 Oracle 都是按照 Task 目录来解析路径的，但它们运行时的工作目录都是工作区，因此一条套件内的相对路径，最终会按工作区来解析——而工作区恰恰是评分器绝不能被满足的地方。任何未来运行 Task 提供材料的适配器，都继承了这个问题。

而且第 8.1 节"Task 的初始状态不能已经满足其所要求的结果"这条规则，并不适用于一个负向 Task——它所要求的结果就是"什么都没发生"。这类 Task 需要声明为 `negative`，而不是逐个豁免；一个负向 Task 必须携带一个必需的轨迹评分器或模型评分器：没有它，它就只能断言"什么都没发生"，而一个根本没运行过的评估对象也会满足这个断言。这是这个切片自己挣得的一项契约补充，而不是预先假定好的。

而且这两个表面把 Task 的初始状态放在不同的位置。一次 CLI 运行会被直接给到工作区；而一个 Worker 会把 Space 的文件物化进它所在运行目录下的一个 `home` 子目录中。因此，一条路径断言是与表面相关的——这正是第 11 节"一致性是指两个 Task 陈述同一个目标，而不是同一个 Task 被运行两次"这句话已经暗含的意思，但如果直接把一个 Task 从一个表面复制到另一个表面，就很容易违反它。预检会把内容物化进该 Task 自身所属表面所使用的布局，因此一个断言是照着 CLI 写的 Worker Task，会在产生任何成本之前就先失败。

评估对象的定义也由此而来：通过两个不同适配器构建出来的产物，是两个不同的评估对象，因此运行器会把执行路径逐次试验地打印到评估对象上。如果共用同一个身份，就会让一个 CLI 结果和一个 Worker 结果被配对成同一个配置的两次测量。

Inspect 与 Harbor 的 spike 紧随第 3 步之后进行。第 14.1 节已经把框架选择安排在这个切片之后进行，如果在一份标准试验包存在之前就跑这次 spike，那就是拿适配器去和一份仍在变动中的契约做比较。

### 18.7 构建并首次运行 Harbor 适配器带来的变化

构建它带来了六项发现，其中四项是契约或产品层面的决策，而不只是适配器细节。实际运行它又带来了另外三项，而这三项最值得读一读：没有一项是靠测试就能发现的，其中两项本会让一个已发布的数字出错，而不只是缺失。

**迭代上限需要有自己的退出码。** Agent 循环的上限原本固定为 200，一旦触达就会以 `ExitModelError` 退出——和一个不可达的提供商用的是同一个退出码。但这两者对测试框架的要求截然相反：提供商故障是一个值得重试的错误，而预算耗尽是一个答案——对它重试等于为同一个上限再付一次代价，更糟的是，还会丢弃验证器对已经真实发生过的工作所给出的判定。这个上限现在可以通过 `agent.max_iterations` 和 `--max-iterations` 配置，触达它时会以 `7` 退出，错误类型为 `iteration_cap`。Harbor 适配器只吞掉这一个退出码，让 Task 自己的验证器仍然能对工作区做出判断，并把这次触顶记录为该试验的故障类别。这正是让"耗尽的预算"不至于污染第 7.4 节想要保护的那个能力判读的关键。

**`Limits.Iterations` 曾经只是摆设。** 该契约自第 1 步起就带着这个字段，却没有任何适配器把它传给任何东西：一个声明了迭代上限的 Task，实际跑的是二进制文件自己的默认值，试验报告里记录的是一个没有人真正应用过的限制。在上面这项改动之前，根本没有旗标可以把它传下去。

**尝试序号是分配出来的，不是读出来的。** Harbor 不会给尝试编号——一次试验的名字是 Task 名加一个随机后缀——因此导入器会按开始时间的稳定排序，给每个 Task 的尝试逐一编号。所以这个序号是导入过程的产物，而不是一个外部身份，两次对同一个作业的导入必须给出一致的结果，否则一次成对比较每跑一次就会配对到不同的尝试。

**Artifact 摘要应当由持有该文件的那段代码来计算。** 第 7.3 节说的正是这个摘要，才是让一个结果成为黑盒测量的关键，而 Harbor 只记录了指向某个二进制文件路径的那个关键字参数。如果导入器直接采信调用方给出的摘要，调用方就能随口指认一个从未真正运行过的文件，而下游没有任何环节能够核实。适配器会对它自己上传的那个二进制文件计算哈希并记录下来；版本和提交信息则来自容器内该二进制文件自己上报的内容。缺少摘要的试验会被拒绝导入，而不是在没有摘要的情况下被放行。

**跨越语言边界的事实需要一道守卫，因为一旦出错，故障是无声的。** 试验 home 的设置文件和评估对象元组，都是在 Python 一侧生成、在 Go 一侧消费的。如果某个键在两边拼写不一致，这并不会报错——加载器或者 map 查找只会悄悄漏掉它——于是运行照常继续，只是那个字段没有被设置，结果被归因给了一个从未真正那样配置过的评估对象。有三组测试把这些配对互相钉在一起：设置项的键名对照 `evaluation/adapter` 自己的结构体，元数据的键名对照导入器自己的结构体，以及 Python 适配器的版本号对照 `pins.json`。

**一个留下后台进程的 Bash 命令，让 Agent 永远挂住了。** 这是一个产品层面的 bug，和评估本身没有关系，只是恰好在跑这个基准的过程中才被发现。Bash 工具是通过一个管道来读取输出的，而 Go 的 `Wait` 只有在每一个写端都关闭之后才会返回——所以一个 Task 早些时候启动的服务器，一直让这个管道保持打开，导致一条在自己的截止时间被杀死的命令，却永远没有返回。一次金丝雀试验就这样在一个工具调用上卡了两个小时，而它文档记录的超时时间是 120 秒。现在这个工具会对这个等待设定上限。

仓库里其实早就记录过这个故障：`evaluation/adapter/cli.go` 就针对适配器自己启动的那个进程，把它写得清清楚楚。它没有做到的是，把同样的推理再往下应用一层——应用到那个负责启动命令的工具自身身上。一个只在一处记录下来的隐患，并不等于在所有地方都被修复了，这一点值得在下一次写下类似记录时被重新记起。

**一次没有产出可用证据的尝试，不应该拖累整个作业。** 一个在运行中途被杀死的评估对象，会留下一个空的结果信封——因为 shell 会在二进制文件写入任何一个字节之前就先创建好这个文件——而把这种情况当作破坏了输出契约来处理，结果是因为一个被杀死的容器，连累了五次原本良好的导入。现在的做法是，导入过程会把这次试验降级并记录下这个缺口，而不是直接拒绝整个作业。

对照实际输出和源码所暗示的内容，还发现了四个较小的问题：试验结果文件其实是 `result.json`，而不是 Harbor 自己的文档字符串中两次写到的 `results.json`；一个 Task 的名字是 `<org>/<name>` 这种形式，而一个试验包的 Task ID 字段容纳不了它，Task 过滤器却又需要它；`task_checksum` 是一段裸的十六进制值，而同一棵树上对应的 ref 却是带标签的。这四处都是从代码里读出来的假设，而不是亲眼验证过的事实，而且每一处都会在第一次真正的导入中出错。

**取消一个协程，并不等于停下一个容器。** Harbor 用 `asyncio.wait_for` 来限定 Agent 阶段的时长，这个形状本身以及每个 Task 的预算都是对的——但它什么实际效果都没有。取消一个正在等待 `docker compose exec` 的协程，只会结束这次等待；真正终止客户端的，只有环境自己的每次执行超时，而适配器从未设置过这个值。于是容器会在 Harbor 已经放弃它之后，继续运行这个 CLI，一个声明了三十分钟预算的 Task，被观察到在第九十八分钟时仍在运行、仍在消耗资源。

一次超出预算的运行，不只是精度稍差一点，它根本不具备可比性，因为排行榜上的每一个 Agent 都被限定在那个预算之内。这个适配器现在会在取消操作本来就会运行的清理流程中，回收容器内的进程，这才让测试框架自己的超时真正有意义。预算本身仍然归 Harbor 所有：一个自定义 Agent 无法读取它——Harbor 只把 `agent_timeout_sec` 传给它自己的 Oracle Agent——所以任何试图自行强制执行预算的适配器，都只是在重新猜测一个它本来就无从得知的、逐 Task 而定的数字。

**成本没办法完整地经由这个测试框架往返传递。** Harbor 会重新编码一个 Agent 上报的内容，并把成本保存为以美元计的浮点数，而运行时内部保存的是整数纳米单位。因此导入器会优先采用 BuildMax 自己的打印模式信封——适配器会把它留在试验的 Agent 目录里——只有在完全没有这个信封时，才会退回去用 Harbor 给出的数字，并把这种情况下恢复出来的成本标记为不完整，因为一个经过浮点数取整的总数，不应该被当作精确值来读。

### 18.8 有意排除在切片之外的内容

最初交付的这个切片有意排除了 Conversation 与部署适配器、模型评分器的校准、私有或轮换的留出集、任何外部查看器、公共基准，以及 Hook 执行和文件变更这两类轨迹事件。这个排除只是为第一个切片划定了范围，并不是对后续工作的否定。第 14.2 节现在已经把 Terminal-Bench 2.1 接受为第一个外部目标，其余各项仍然保留在它们原有的归属位置。

## 19. 风险与缓解措施

| 风险 | 缓解措施 |
|---|---|
| 评估系统过早变成第二个产品 | 在做 UI、数据集管理或通用化服务之前，先交付黑盒垂直切片 |
| Task 测试的是实现细节，而不是产品能力 | 明确说明每个套件所度量的构造；要求对 Oracle 和 Task 进行评审 |
| Agent 读取或利用评分器 | 用真实的执行边界把可见材料和隐藏材料分开，并对评分器做对抗性测试 |
| LLM 评委奖励风格，或者可以被操纵 | 对照冻结的标注做校准，维度相互独立，允许 unknown，并让确定性门槛始终具有最终决定权 |
| 提供商或基础设施噪声被当作回归报告出来 | 成对运行、重复试验、明确的评估对象/资源清单，以及独立报告的基础设施状态 |
| 公共 Task 被污染或被过拟合 | 私有/轮换留出集、来自生产环境的用例，以及定期刷新 Task |
| 试验包变成一个敏感数据湖 | 默认本地/私有、有边界、脱敏、有保留期限、清单不含内容，以及明确的导出操作 |
| 外部框架的演进破坏评估系统 | BuildMax 自有的、有版本的契约，以及适配器一致性测试 |
| 主仓库的工具链拖累普通贡献者 | 独立锁文件和可选启用的重量级命令；确定性的仓库检查保持轻量 |
| 分数鼓励优化基准本身，而不是优化产品 | 多个产品领域、定性的失败复盘、公共基准单独处理，以及不设全局分数 |

## 20. 实施过程中所需的证据

在选定某个框架之前，产品方向本身已经被接受。实施工作在越过第一个切片之前，不得没有以下证据支撑：

1. 一组有代表性的、真实的 BuildMax 故障或人工排查场景；
2. 一份关于可用于结果与信任评分的轨迹字段的清单，标明哪些已具备、哪些还缺失——由[第 18.2 节](#182-轨迹证据审计)提供；
3. 面向本地与 Worker 执行的黑盒适配器，加上一份针对 Conversation 执行的草图——已构建的适配器和剩余的差距记录在[第 18.3 节](#183-黑盒适配器草图)中；
4. 对试验内容、保留期限与导出方式的隐私评审；
5. 一份初步的提供商成本与重复次数估算；
6. 一次 Inspect/控制器 spike，以及一次针对 Terminal-Bench 2.1 的 Harbor 自定义 Agent 适配器 spike；以及
7. Oracle 与评分器评审，证明最初的这批 Task 确实度量了它们所声称的能力。

外部实践支持这个方向，但并不能替 BuildMax 决定自己的产品契约：

- [Anthropic 的 Agent 评估指南](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)区分了 Task、试验、评分器、转录记录、结果与 Agent 测试框架；建议采用重复试验，并把能力与回归分开；并且把最终环境状态，和 Agent 自己声称的结果区别对待。
- [Google ADK 评估](https://github.com/google/adk-docs/blob/main/docs/evaluate/index.md)同时评估最终回复和工具调用轨迹，包括多轮标准和用户模拟。
- [Inspect AI](https://inspect.aisi.org.uk/tasks.html)把 Task 建模为数据集、求解器、评分器、沙箱、限制和轮次的组合，它的[度量指标](https://inspect.aisi.org.uk/metrics.html)包含不确定性和评分者间一致性。
- [Harbor](https://github.com/harbor-framework/harbor)在容器环境中评估任意 Agent，是 [Terminal-Bench 2.1](https://www.tbench.ai/leaderboard/terminal-bench/2.1) 的官方测试框架。[2.1 版本的发布说明](https://www.tbench.ai/news/terminal-bench-2-1)记录了那些让 2.0 的结果只能算作另一份不同数据集、而不是同一基线的修正内容。
- [Agentic Benchmark Checklist](https://github.com/uiuc-kang-lab/agentic-benchmarks/blob/main/ABC.md)强调 Task 与结果的有效性、隐藏的事实标准、Oracle 求解器、污染控制，以及不确定性报告。

## 21. 文档生命周期

在评估系统被实现之前，这份记录拥有其中的理由与分阶段方向。第一次实现完成后，必须用实际的所有权边界、命令、数据格式和运维工作流，去更新仓库布局文档和测试文档。等这份计划全部完成之后，把其中经久有效的契约内容迁移进贡献者文档或参考文档，并删除这份处于活跃状态的计划；决策背景会保留在 Git 历史中。
