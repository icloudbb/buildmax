## 问题

Agent 经常遇到本应由用户做的决定：需求有歧义、几种做法各有取舍需要选择，或者
缺少一个它自己查不到的事实。在此之前，它只能用文字提问然后结束本轮。runtime
只能去猜测是否提了问题：轮次摘要仅在 `asksUser` 于回复末尾附近发现问号时才提供
建议回复。用户阅读问题、输入答案，再开始新的一轮。

这一需求来自实际使用而非推测。Claude Code 提供了多选项提问工具，维护者经常使用
它：从 Agent 给出的选项中挑一个，明显比读完文字再打字回复更快，也能让 Agent 在
不该独自做的决定上继续推进。

## 决定

新增一个工具 `AskUser`。它在工具调用内部阻塞，直到会话前的人作答；答案作为工具
结果返回，本轮继续进行。这与维护者依赖的交互方式一致，并让问题与答案在历史中
作为一次调用和一个结果保持在一起。

之所以可以阻塞，是因为阻塞只发生在有人在场的地方。无人值守的 worker TaskRun 不能
阻塞：那会占用 worker 及其租约，却没有人能释放它们，违背 [Task 线程](Agent执行与Task线程.md)
中「等待输入的 Task 不占用 worker」的规则，以及 [Workflow 运行时 §14](Workflow运行时.md#14-持久化的人工请求)
中「人工请求不是阻塞式 Agent 调用」的规定。因此 worker 得到的是该工具的延迟形态：提问会
结束本轮，运行带着问题结束，用户之后通过 Continue 这个 Task、用自己的话作答。答案以
下一条用户消息而非工具结果的形式到达——这是延迟形态唯一放弃的东西，而 Task 线程本来就
承载这条消息。

该机制仿照工具批准实现，而不是在其上扩展。批准由权限关卡给出三种固定决定之一；
提问由工具发起，携带自由文本和选项。两者形态相同（单次运行的 handler、请求 id、
经由运行 context 取消），但不共用类型。

## 契约

- **参数。** `questions` 包含一到四个问题，作为一组一起提问。Agent 往往同时
  需要做几个决定，而且形式各不相同；合成一组可以省去每个决定都来回一次。每个
  问题有必填的 `question`（最多 1000 个字符），以及可选的 `header`（最多 24 个
  字符，显示为该问题的标签页）。问题还可以带最多四个 `options`，每项包含最多
  80 个字符的 `label` 和可选的、最多 200 个字符的 `description`，以及
  `multi_select`（至少需要两个选项）。有选项且没有 `multi_select` 时，用户选
  一项；有 `multi_select` 时，用户可以勾选多项；没有选项时，用户用自己的话
  作答，而每种形式也都允许这样作答。问题文本和选项标签不区分大小写，必须互不
  相同。这些限制由 `agent.ValidateQuestions` 负责。
- **结果。** `agent.Answer.Values` 按顺序为每个问题保存一个答案：一个标签、
  以 `, ` 连接的多个勾选标签，或用户自己的话。工具返回 `The user answered:`，
  后面每个问题一组 `Q:`/`A:`，让每个答案都与它所回答的问题保持在一起。忽略
  作用于整组问题，并返回一条指令：不要再问，按说明过的判断继续。没有 questioner 的运行会返回「按说明过的判断继续」的
  指令，而不是失败。
- **权限。** `DefaultAction` 为 `Allow`，因为一个征求「能否显示提示」的许可
  提示对谁都没有帮助。配置的 deny 仍然优先。
- **调度。** `Access` 为 `AccessWrite`，因此该调用从不与其他调用共处一个并行
  组：它会占住运行，而界面一次只显示一组问题。
- **管线。** `agent.UserQuestioner` 是单次运行接口。界面通过
  `RunPromptOpts.Questioner` 传入，`RunLoop` 把它安装到工具读取的 context 上。
  registry 按模型缓存，因此工具不能自行持有。`RunLoop` 总会安装这个值，包括
  nil。子 Agent 运行在父运行的工具调用 context 上，nil 会清除继承来的
  questioner，而不是让子 Agent 接触到父运行的用户。
- **提示层。** 拥有该工具的运行还会得到一个 `ask_user` 系统提示层。它要求
  模型使用 `AskUser`，而不是在回复末尾提问，把几个相关的决定放在一次调用里
  问，并把推荐选项放在第一位。这一层
  之所以存在，是因为仅靠工具描述并不够。在一次真实模型的 Desktop 运行中
  （GPT-5.6 Luna，2026-09-27），「Add a LICENSE file to this project」得到的是
  一个列出四种许可证的文字提问，随后本轮结束。加上这一层后，同样的提示词
  触发了带三个选项的 `AskUser` 调用；输入的答案作为结果返回，Agent 在同一轮
  内写好了文件。
- **Hook。** 问题显示之前，`RunLoop` 触发类型为 `user_question` 的
  `Notification`，携带调用 id 和问题文本，就像批准关卡触发 `approval_required`
  一样。通知器因此能区分「需要决定」与「已完成」。

## 注册范围

`AppConfig.AskUser` 在 `BuildAgentTypes` 之后注册该工具，因此任何子 Agent 定义都无法
点名它；它还指定形态：`AskUserInteractive` 或 `AskUserDeferred`。

| 运行 | 是否注册 | 原因 |
|---|---|---|
| TUI | 交互式 | 终端前有人 |
| Desktop 项目聊天 | 交互式 | 聊天前有人 |
| Worker TaskRun | 延迟式，服务端允许时 | 运行旁无人，但有人会 Continue 这个 Task |
| Workflow 步骤 TaskRun | 否 | 它的 Task 由 workflow 推进，没人会 Continue |
| Desktop 定时触发、无项目会话 | 否 | 按目录托管的 app 没有批准或提问 handler |
| `buildmax run`（print 模式） | 否 | 运行中途没人作答；脚本读取的是最终回复 |
| 子 Agent | 否 | 它向父 Agent 汇报，由父 Agent 决定是否提问 |
| Portal Conversation、评估 | 否 | 它的回复本来就会送达用户；评估中无人作答 |

服务端按运行决定：`GET /api/worker/task-runs/{id}` 会设置 `ask_user`，除非该运行是为
Workflow 步骤而创建的。评估控制面或旧版服务端不会发送该字段，因此在那里工具保持关闭。

在已启用的 app 上，没有提供 questioner 的运行仍会提供该工具，工具会告诉模型
没有人能作答。

## 各界面

**TUI。** `TUIQuestionHandler` 把这组问题发送给程序，并在带缓冲的 channel 上
阻塞。面板显示期间独占键盘。每个问题每个选项占一行，最后一行是它自己的答案
输入框，因此用户自己的答案就输入在它所回答的问题下面，而不是聊天输入框里。
这修正了第一版的问题：当时输入的答案会进入屏幕底部、远离问题的聊天输入框。面板显示期间，聊天输入框及其
「queue message」提示会被隐藏，只留下一个输入位置。
上下键在各行之间移动，光标位于输入框时，输入框接收键入。Enter 选择高亮的
选项或发送输入的答案。对多选问题，空格或数字键勾选选项，Enter 发送已勾选的
内容以及输入的文字。不在输入框时，数字键直接选择对应选项。有多个问题时，
标签行显示各问题的 header，已回答的带勾号。作答后自动跳到下一个未回答的问题，
Tab / Shift+Tab 在问题之间切换。所有问题都有答案后，整组才会被发送。Esc 忽略
整组问题。每个问题及其答案都会打印到回滚区。

**Desktop。** `runQuestioner` 与 `runApprover` 并列，按运行绑定。它发出
`desktop/question-request`，携带 `question_id`、`project_id`、`session_id` 和
`questions`，前端通过 `RespondQuestion(question_id, answers, declined)` 作答，
每个问题一个答案。待处理问题与批准共用按 id 记账的结构（`pendingAnswers[T]`），因此一个 id
最多被回答一次，过期答案不会到达任何运行。非忽略的空答案会被拒绝，因为 Agent
会把它理解为用户有意什么都不说。问题面板位于输入框上方，一次显示一个问题，
有多个问题时带标签页。点击选项按钮即选择该项；对多选问题则是勾选，再用
Confirm 按钮发送。每个问题都有自己的答案输入框，Dismiss 按钮忽略整组问题。
焦点不在文本框内时，数字键可选择或勾选选项。与批准按键一样，提问
按键只在获得焦点的 pane 中生效。不在屏幕上的聊天仍会表明自己在等待：当其他 tab
处于激活状态时，琥珀色圆点会标在它的 tab 上，也会标在侧边栏中对应的会话行与项目行，以及折叠起来的
Projects 标题上。待处理的批准也会点亮同一个圆点，因为两者都会让运行停下来等用户。

**Remote Control。** 开启 Remote Control 的 TUI 会话会像转发批准一样转发每组问题：
`agent.question` 以 `agent.Question` 的形态携带问题组，`agent.question_resolved` 让它
退场，查看端的 `agent.question_response` 回答它。Portal 会话页与 Desktop 渲染的是同一个
表单——`@buildmax/gui` 中的 `QuestionForm`——因此两个界面不会走样。先回答者生效：本地
面板和远端副本都通过同一个待处理条目投递，落后的一方到达不了任何运行，已了结的问题组会被
广播出去，让另一端撤下它。远端答案在投递前会与它所回答的问题组核对（每个问题一个非空
答案），并像本地答案一样打印到 TUI 回滚区。

**Worker。** 服务端允许的 worker TaskRun 会得到 `NewDeferredAskUser`，其描述说明调用
即结束本轮；还有一个提示层，要求模型只在受阻时提问，其余情况自行决定并说明假设。它的
questioner 记录问题组并以 `Deferred` 作答。当前这批工具调用结束后，循环会结束本轮，
不再调用模型，也不做结构化输出提取。随后运行以 `SUCCEEDED` 结束：问题以「Waiting for
your answer」为标题附在输出末尾，并作为 `questions` 随终态报告一起上报。服务端只从
成功的运行中保留有界的 JSON 数组，存入 `task_run.questions`，并把 `awaiting_answer`
投影到 Task 上；下一个运行在创建时会清除它。

用户以纯文本 Continue 这个 Task 来作答。会话恢复会把问题、工具结果和答案依次放在模型
面前。所有读取运行输出的地方无需新增渲染就能显示这些问题：Task 线程、Issue 报告评论，
以及聊天渠道的结果消息（会说明该任务在等待回答）。Portal 会把这样的 Task 标为「Needs
your answer」，并相应地修改输入框占位文字。Issue 报告和渠道报告在输出过长时保留末尾——
问题就在那里——而不是把它截掉。

## 生命周期与失败

- **取消。** 被取消的运行会撤回待处理的问题并返回 context 错误。TUI 会关闭
  面板。在 Desktop 上，流结束会清除面板，之后迟到的 `RespondQuestion` 会失败。
- **没有超时。** 问题的等待时间与运行一样长。暂时离开的人仍然是需要做决定的
  人，而取消本轮随时可用。
- **历史与 trace。** 调用和结果构成一对普通的工具记录，因此问题和答案会保留
  在会话历史以及有界、已脱敏的 trace 中，不需要单独的存储。
- **循环守卫。** 重复提出相同问题会像其他重复调用一样被拦截。
- **worker 中无人作答。** 没有任何东西过期，也不占用 worker。Task 一直等待，直到有人
  Continue 或重新开始。worker 的报告是不可信输入，因此格式错误或超大的问题组会被丢弃，
  而运行的输出中仍然带有这些问题。

## 考虑过的替代方案

- **所有界面都以提问结束本轮。** 答案会作为用户的下一条消息到达，在所有界面上都可行，
  且没有待处理状态，是提案的推荐方案。维护者为交互式界面选择了阻塞形态，因为这是他们
  每天使用的交互方式。结束本轮的做法保留在它唯一安全的地方：worker TaskRun。
- **扩展 `ApprovalHandler`。** 这会把三值权限决定变成通用提示通道，并耦合两个
  调用方不同的关注点：批准来自权限关卡，提问来自工具。
- **持久化人工请求。** Workflow §14 的请求实体（含应答者、过期与审计）是受治理
  批准的正确形态，但对澄清问题来说过大，而且要等 Space 治理就绪。

## 推迟事项

- **无人值守运行中的提问率。** 在本可自行决定时提问的 worker Agent，会让工作停下，
  直到有人读到为止。延迟形态的描述与提示层对此加以引导；评估中工具保持关闭，因此评估
  衡量的是行动而非提问。在真实 Space 工作上测量提问率仍待进行。
