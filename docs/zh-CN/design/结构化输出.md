## 1. 决策

共享 Agent 运行时新增一套**与提供商无关的结构化输出契约**：调用方可以为一次
运行的最终回答声明一份 JSON Schema，运行时要么返回一个已**按该 Schema 验证**
的值，要么返回一个带类型的失败。无论请求最终落到哪个提供商，Schema 与验证后
的值都统一经由 `internal/core/llm` 这一个接口传递；每个适配器把契约映射到自身
提供商的原生机制，遇到没有对应机制的提供商就执行回退，并**记录实际生效的是
哪种机制**。

结构化输出是对运行文本输出的**补充，而不是替代**。一次运行仍然会产出完整的
助理轮次文本（参见[《Agent 执行》——运行输出即完整轮次](Agent执行与Task线程.md)）；
结构化值只是与文本并列的、另一个机器可读字段。人读文本，Workflow 路由、规划器
或评估器读结构化值。

这里划的边界与 Workflow 已经确立的原则一致：**模型提出一个值，运行时依据声明
的 Schema 验证它并记录结果。**没有通过验证的值不会被悄悄接受。

这项能力解锁了好几个已被接受的设计正在等待的东西：Workflow 的类型化路由、
有界规划器和评估器循环（见 [Workflow 运行时第 13 节](Workflow运行时.md)）——
它们节点输出信封里的 `structured` 字段，在这份契约落地之前只能是 `null`
（见 [Workflow 运行时第 9 节](Workflow运行时.md)）；此外还有比自由文本更丰富
的 Task 结果。

## 2. 问题与当前基线

共享运行时目前没有办法向模型索要一个机器可校验的答案。

- `internal/core/llm.Request` 只带 `Messages`、`Tools`、`Profile` 和
  `CacheScope`——没有输出 Schema。
- `internal/core/llm.Completion` 只带 `Content`、`ToolCalls`、`Usage` 和
  `ProviderState`——没有结构化值。
- 现有适配器（`anthropic.go`、`ollama.go`、`openai_chat.go`、
  `openai_responses.go`）没有一个会构造 `response_format`、强制
  `tool_choice`、`format`，或任何 JSON 模式相关字段；在 LLM 相关包里搜索这些
  关键词，什么也搜不到。

于是每一个答案都只能是自由文本。需要拿到一个值的消费者只能自己解析文本，
祈祷格式正确。Workflow 的自适应层原本设计成依赖一个可信的 `structured` 字段，
结果这个字段一直是 `null`；Task 的结果也就无法携带类型化的结论。这是“自适应
Workflow”和“更丰富的结果信封”这两个方向共同缺失的同一块基础能力。

## 3. 目标与非目标

### 3.1 目标

- 提供一种与提供商无关的方式，用来请求一个受 Schema 约束的最终值，并得到一个
  已验证的值或一个带类型的失败。
- 由适配器把契约映射到各提供商的原生机制，调用方不需要按提供商分支处理。
- 如实报告能力：运行会记录 Schema 究竟是被原生机制强制执行、通过强制工具调用
  折中实现，还是仅靠提示词加事后解析——绝不会声称一种实际并未发生的强制保证。
- 结构化值是文本输出之外的补充，不会压制或取代文本。
- 提供一份有文档说明、受支持的 JSON Schema 子集，并与 Workflow 现有的输入
  Schema 子集共用，让同一份定义只需验证一次，且在两处边界含义完全一致。
- 验证逻辑只在运行时里实现一次，Portal 的解析器或 Workflow 的处理器都不必再
  重新实现一遍。

### 3.2 非目标

- 不做通用的语法或正则约束解码引擎。这份契约是 JSON Schema 的一个子集，不是
  任意上下文无关文法（CFG）的输出。
- 不对*每一次*中间 LLM 调用都做结构化约束。契约只约束一次运行的**最终**答案，
  不涉及途中调用工具的那些轮次（见第 5 节）。
- 不在结构化对象尚在拼装过程中就把它流式推给 UI（见第 10 节）。
- 不取代工具调用。工具仍然是模型采取行动的方式；结构化输出是运行汇报结果的
  方式（见第 14.1 节）。
- 不发明一门新的 Schema 语言。JSON Schema（子集）就是契约本身。
- 不在本文里冻结一张逐提供商的能力矩阵；能力应当在运行时被发现并记录（见
  第 8 节），而不是写死在文档里。

## 4. 契约

在 `internal/core/llm` 中新增两组与提供商无关的类型：

```go
// On Request: an optional schema the final answer must satisfy.
type OutputSchema struct {
    Name   string          // a stable name for the schema (some providers require one)
    Schema json.RawMessage // the JSON Schema, in the supported subset (§6)
}

type Request struct {
    Messages   []Message
    Tools      []ToolDef
    Profile    CallProfile
    CacheScope string
    Output     *OutputSchema // nil = free text, today's behavior
}

// On Completion: the validated value plus how it was obtained.
type Structured struct {
    Value    json.RawMessage       // validated against the schema, or nil on failure
    Mode     StructuredMode        // native | forced_tool | prompted (§7, §8)
    Enforced bool                  // true only when the provider guaranteed the shape
    Err      *StructuredError      // set when the model's value did not validate
}

type Completion struct {
    Content       string
    ToolCalls     []ToolCall
    Usage         Usage
    ProviderState *ProviderState
    Structured    *Structured // set only when the Request asked for output
}
```

`Content`（文本）保持不变，照常生成。`Structured.Value` 就是那个机器可读的
答案。请求过输出的调用方读取 `Structured`；没请求的调用方完全不受影响——
`Output` 为 `nil` 正是今天的行为，所以这是一处纯增量的改动，所有既有调用点
都能继续正常工作。

`LLMClient` 接口的签名不变：只是给 `Request` 和 `Completion` 新增了字段；
`ContextWindow` 不受影响。

## 5. 结构化输出是运行的最终值

一次 Agent 运行是一个循环：模型调用工具、读取结果、再调用更多工具，最终写出
一个最终答案。结构化输出约束的是**这个最终答案**，而不是中间的那些轮次——
调用工具的轮次是在“行动”，不是在“汇报”，强行给它套上 Schema 只会和工具调用
本身打架。

因此这份契约是一个附着在**运行**本身上的属性，由 `RunLoop` 负责解析：

- 只要模型还在调用工具，调用过程与今天完全一样——工具照用，自由文本叙述照
  产出，运行依然会按“运行输出即完整轮次”的既有决定保留这些内容；
- 一旦模型给出了一个会终止循环的答案（不再调用工具），且该运行请求过结构化
  输出，运行时才会对这个终止性答案套上 Schema 约束并加以验证。

具体来说，`RunLoopOpts` 新增一个可选的 `Output *llm.OutputSchema`。`RunLoop`
把它应用到那个可能终止循环的调用上，并在返回文本回复的同时一并返回已验证的
`Structured`。文本回复依旧是完整的轮次；结构化值则是最终答案的机器版本。

这样一来，结构化输出与工具使用彼此正交：同一次运行既能产出一份人类可读的
完整记录，也能产出一个类型化的结果。

## 6. Schema 子集

这份契约接受**一个具名的 JSON Schema 子集，由本契约与 Workflow 的
`input_schema` 共同引用**（见 [Workflow 运行时第 6.1 节](Workflow运行时.md)），
只定义一次，使一份定义在两处边界验证结果完全一致、且不会在两者之间发生漂移
（见第 15 节 D1）。两处边界目前都尚未实现各自的子集，所以这是一份共享定义，
而不是两份逐字节相同的副本。一份为 Workflow 节点的 `output_schema` 编写的
Schema，拿到这里同样能通过验证。一个 Workflow 若声明的输出 Schema 超出了这个
子集的范围，发布时就会失败——这和今天一个不受支持的输入 Schema 会失败是同一
套规则。

这个子集会在实现时随 API 一起写入文档。它一开始刻意收得很窄——对象、一组固定
的标量类型、枚举、数组、`required`，以及 `additionalProperties: false`——
因为每一个关键词都必须既能在每一家提供商的原生机制里表达出来，也必须能被
运行时自己的校验器检查。只有某一家提供商支持的关键词，不会被纳入这个子集：
运行时能力划的是下限，不是以任何单一提供商的上限为准。

## 7. 提供商映射

每个适配器都把 `Output` 映射到自己提供商的原生机制，并报告实际使用的
`Mode`：

| 提供商家族 | 原生机制 | `Mode` |
|---|---|---|
| OpenAI（Chat 与 Responses 两种接口） | `response_format: {type: "json_schema", …, strict: true}` | `native` |
| Anthropic | 构造一个输入 Schema 就是输出 Schema 的单一强制工具，把 `tool_choice` 固定在它上面；工具的输入即最终值 | `forced_tool` |
| Ollama | 把 `format` 设为该 JSON Schema（若只需要“是个对象”，则设为 `json`） | 模型遵守时为 `native`，否则为 `prompted` |
| 没有可用机制的提供商 | 把 Schema 写进提示词，再解析模型的输出 | `prompted` |

只有适配器这一层知道提供商具体用的是什么机制。往上一层，调用方看到的只是
带 `Mode` 和 `Enforced` 标志的 `Structured`，永远不需要按提供商分支处理。
Anthropic 的强制工具映射复用了现成的工具调用管线（`toolcalls.go`）：运行时
新增一个合成工具、强制模型调用它，再把它的参数当作结果值读出来——这一切对
只声明了一份 Schema 的调用方完全不可见。

## 8. 能力如实报告与回退

不是每个模型都能强制执行一份 Schema，运行时绝不能声称它做到了。这遵循的是
本项目一贯的信任边界原则：**记录实际生效的边界，而不是暗示一种并不存在的
保证**（见[《产品愿景》——信任边界必须可见](产品愿景.md)）。

- `Structured.Mode` 记录实际用的机制；只有当提供商真正保证了输出形状时，
  `Structured.Enforced` 才为 true——这包括 `native`，也包括那些确实会针对
  Schema 校验工具输入的 `forced_tool` 情形。
- `prompted` 回退只是尽力而为：运行时仍然会用自己的校验器去验证解析出来的值，
  所以一个坏值得到的是一个带类型的失败，而不是静默混入的垃圾数据——但
  `Enforced` 会是 false，这个事实会一路传到轨迹里，也会传给在意它的任何消费者。
- 需要强保证的调用方——比如分支选择必须可信的 Workflow 路由——可以要求
  `Enforced` 为真，并把 `prompted` 当作失败处理。这是消费者自己设定的策略，
  运行时不会替它悄悄做这个决定。

某个提供商/模型具备怎样的结构化输出能力，是由适配器和模型记录在运行时发现的，
而不是冻结在本文档里——能力矩阵变化太快，无法写死；而且第 2 节已经指出，
现状里根本没有什么需要兼容保留的既有行为。

## 9. 验证与失败

验证工作只由运行时承担一次：

1. 适配器返回模型给出的候选值——它可能来自 `response_format`、强制工具的
   参数，也可能来自对提示式输出的解析；
2. 运行时用自己的校验器依据 `OutputSchema` 验证这个值——即便是 `native`
   模式也要重新验证一遍，这样即使提供商自身有缺陷，也不可能把一个不符合
   Schema 的值偷偷带过契约；
3. 验证成功时，`Structured.Value` 就是验证通过的值；失败时
   `Structured.Err` 是一个带类型的错误，`Value` 为 nil。

失败之后怎么处理，属于**消费者**自己的策略，这一点与 Workflow 是一致的：
[Workflow 运行时第 13.1 节](Workflow运行时.md)已经规定，无效的结构化输出要
遵循节点显式设定的重试策略，否则该节点直接失败；其验证方案也确保了“输出
无效时绝不会执行任何未声明的边”。本文只负责提供已验证的值和带类型的失败，
重试还是失败由 Workflow 决定。一次直接的 Agent 运行则会把失败直接呈现在
TaskRun 上，不会假装存在一个值。

模型负责提出值，运行时负责验证并记录；下游任何一层都不需要重新验证，也不
需要重新解析。

## 10. 流式传输

结构化输出可以和逐 token 的流式传输共存，且不会把一个还没拼完的对象当作
“结果值”推流出去：

- 运行仍然照常实时流式发送**文本**增量——一次运行在得出答案途中产出的叙述
  本来就是文本，照常流式传输；
- **结构化值**只在终止性答案形成时才会被解析出来，并在整次运行完成时一次性
  交付、且已经过验证。一个尚未拼装完成的 JSON 对象，永远不会被当作结果值
  呈现出来。

因此 Task 页面照常保留它的实时文本流（也就是流式的叙述内容），结构化结果则
会在运行结束——也就是文本落定的那一刻——一并出现。不需要引入任何新的流式
协议。

## 11. 对外呈现位置

- **Agent 运行时：** 由 `RunLoopOpts.Output` 发起请求，`RunLoop` 在返回文本
  回复的同时返回已验证的 `Structured`（见第 5 节）。
- **TaskRun：** 运行的输出信封会在文本之外新增一个 `structured` 字段，正是
  [Workflow 运行时第 9 节](Workflow运行时.md)预留的那个字段；对于没有请求
  结构化输出的运行，它是 `null`。`internal/infra/db` 中的 `xxxRow` 结构体
  仍然是 schema 的事实来源，落地时会为其新增一个可为空的结构化列。
- **Workflow：** `agent_task` 节点的 `output_schema` 会成为一条真正生效的
  约束。运行时会在节点判定成功之前验证其结构化输出，类型化路由或规划器则从
  信封的 `/structured/...` 中读取数据（见 [Workflow 运行时第
  13.1–13.2 节](Workflow运行时.md)）。不再需要 Portal 端的解析器来做验证——
  运行时已经做过了。
- **Task 结果信封：** Task 的结果除了文本之外，还可以携带结构化值，这样想要
  类型化结论的调用方能拿到它，同时人依然能读到那份自然语言的答案。

## 12. 交付计划

BuildMax 仍处于 Alpha 阶段；每个阶段都会同步修改 `llm` 的类型、各适配器和
各消费者，不会为旧的数据形状保留任何兼容解释层。

**阶段 1——运行时契约。** 在 `internal/core/llm` 中加入 `OutputSchema` 和
`Structured`、实现第 6 节子集对应的运行时校验器，并在两个 OpenAI 适配器中
实现 `native` 映射。用一个脚本化的提供商验证“请求 → 已验证的值”这条路径能
跑通。此时还没有真正的消费者；`Output` 为 nil 时行为不变。

**阶段 2——其余的提供商。** 实现 Anthropic 的 `forced_tool` 和 Ollama 的
`format`，以及如实的 `Mode`/`Enforced` 报告。`prompted` 回退**推迟**：当前
四个提供商都有原生机制，没有任何路径会触发它，且它的触发条件（无机制的
提供商，或对拒绝 `response_format` 的 OpenAI 兼容端点做能力探测）本身就是
一项待定设计。它仍是有文档记录的兜底下限（第 7、14.2 节），按奥卡姆剃刀在
某个消费方需要时再加入；届时无机制的模型将由运行时自己的校验器来把关。

**阶段 3——运行边界。** 加入 `RunLoopOpts.Output`（及其上层的
`RunPromptOpts.Output`），按第 5 节所述：当模型给出无工具调用的答案后，再重发
一次受约束的调用把这个已定型的答案渲染成结构化值，在回复旁于 `RunResult` 上
返回校验后的 `Structured`。选择"终止时重发"而非"每轮都带 Output"，正是为了让
结构化输出不与工具使用冲突——尤其在把输出映射成强制工具的提供商上：循环自由
运行，只有定型的答案才被渲染成值。

**TaskRun 的结构化字段及其持久化移到阶段 4**：在 Workflow 消费方设置 `Output`
之前，没有任何路径会给 TaskRun 设置它，因此持久化应当与写入它的生产方一起落地，
而不是提前加一个恒为 null 的列（奥卡姆剃刀）。阶段 3 是运行级的可复用原语；
直接设置 `RunPromptOpts.Output` 的调用方已经能在 `RunResult.Structured` 上拿到值。

**阶段 4——消费者侧。** 实现 Workflow 的 `output_schema` 强制校验、类型化
路由，以及规划器/映射器读取 `/structured/...`；加入 TaskRun 的结构化列及其
持久化；扩展 Task 结果信封的结构化字段。这正是本文为 R5 阶段的 Workflow 工作
所解锁的第一个真正的消费者，并把持久化与第一个生产方一起交付。

阶段 1–3 构成的是共享的基础能力；阶段 4 是它第一个真正的消费者，会随着需要
它的那些 Workflow 功能切片一起交付，包括值存储在哪里。

## 13. 验证方案

- **运行时校验器：** 第 6 节所定义的子集——对象、标量、枚举、数组、
  `required`、`additionalProperties: false`——应当接受所有合法的值，并对每一类
  违规返回一个带类型的错误；即便是 `native` 提供商给出的值，也要重新验证一遍。
- **适配器映射（脚本化提供商）：** 逐一验证每种 `Mode`——`native` 请求应当带上
  `response_format`；`forced_tool` 应当新增并强制一个合成工具、再读取它的参数；
  `prompted` 应当把 Schema 渲染进提示词并解析输出；每种情形都应报告正确的
  `Mode`/`Enforced`。
- **运行边界：** 一次先调用工具、再返回受 Schema 约束答案的运行，应当同时
  产出完整轮次的文本和一个已验证的 `Structured`；一个偏离 Schema 的答案应当
  只产出一个带类型的失败，而不是产出一个值。
- **消费者侧：** 带 `output_schema` 的 Workflow 节点只应在值通过验证时才算
  成功；一个无效的值应当遵循该节点的重试/失败策略，且不会执行任何未声明的
  路由边（这正是[已有的 Workflow 验证用例](Workflow运行时.md)，如今变成了
  真实场景）。
- **能力如实报告：** 一次 `prompted` 的运行应当记录 `Enforced=false`；要求
  强制保证的消费者应当把它当作失败处理。
- 某个真实模型遵守 Schema 的可靠程度如何，这件事应由评估来测量，而不应由
  确定性测试来断言。

## 14. 备选方案

### 14.1 用工具调用代替一个独立的契约

调用方原本也可以自己定义一个输入即输出 Schema 的工具，再读取它的参数——
这其实正是 Anthropic 的那种**映射方式**（见第 7 节）。但把它当作*契约本身*
是被否决的：这会把提供商的具体机制泄漏给每一个调用方，把“模型在行动”和
“运行在汇报”这两件事混为一谈，而且也让 OpenAI/Ollama 没法用上它们自己的
`response_format`/`format`。强制工具只是某一个适配器内部的实现细节，不应该
成为对外的接口。

### 14.2 靠提示词约定解析自由文本

在提示词里要求模型给出 JSON，再解析它的回复——不需要改动任何类型。这正是
第 8 节里的 `prompted` 回退方案，而不是这份契约本身：它从不真正强制格式，
给不出如实的能力信号，还会把验证工作甩给每一个消费者去重复实现。它只被保留
作为“没有任何机制可用”时的最低保底方案。

### 14.3 一整套 JSON Schema 或语法引擎

支持完整的 JSON Schema，或者支持任意上下文无关文法的约束解码。作为第一步，
这个方案被否决了：共享子集里的每一项能力，都必须既能被运行时检查，也必须能在
每一种提供商机制里表达出来；而奥卡姆剃刀的原则是——等真有消费者需要某个
关键词时再加，而不是提前加上。这个子集本身是可以扩展的；如果将来真的出现
需要语法引擎的用例，那应该是一份独立的设计。

### 14.4 交给消费者自己验证

让 Portal 或 Workflow 的处理器各自去验证模型返回的 JSON。这被否决了：验证
逻辑会被重复实现，而且不同调用方之间会逐渐产生行为分歧；而 Workflow 明确
希望在节点判定成功之前，由运行时——而不是某个 Portal 解析器——来完成验证
（见 [Workflow 运行时第 9 节](Workflow运行时.md)）。所以最终只保留运行时里
的这一个校验器。

## 15. 开放问题

### 已决定

- **D1 —— 一个具名的共享子集。** Schema 子集是一份具名定义，由本契约与
  Workflow 的 `input_schema` 共同引用（见第 6 节），而非两份逐字节相同的副本。
  两处边界目前都尚未实现各自的子集，因此没有需要协调的东西——定义只写一次、
  两边引用，这也正是第 14.4 节所担心的漂移不会发生的原因。第一版的关键词为:
  对象、各标量类型（`string`/`number`/`integer`/`boolean`）、`enum`、带 `items`
  的 `array`、`required`、`additionalProperties: false`，以及 `description`
  （Portal 表单生成与提示词渲染都需要它）。没有跨提供商映射或运行时无法校验的
  关键词——`oneOf`/`anyOf`/`allOf`、`$ref`、`patternProperties`、`format`
  校验——不在第一版范围内，只有当某个消费方需要时才加入（见第 14.3 节）。
- **D2 —— 不设 `Strict` 字段;始终“验证通过或带类型的失败”。** 契约只有一种
  行为:运行时按 Schema 校验候选值,要么返回校验通过的值,要么返回一个带类型的
  失败（见第 9 节）。没有“尽力符合形状”的模式。`Enforced`（见第 8 节）已经承载
  了唯一重要的细微差别——即形状是由提供商保证的（`native`、`forced_tool`），
  还是仅在 `prompted` 兜底后靠运行时自己的校验存活下来的。一个遇到不合 Schema
  的结果也不失败的“尽力而为”值,给消费方的是不可信的东西,因此不值得为它多设
  一种模式。

### 仍然开放

- 对于映射到工具调用的提供商，一次运行应当如何做到只为**最终**答案请求
  结构化输出，而不会让模型过早触发那个强制工具调用——也就是说，需要怎样的
  提示词和终止条件，才能在实践中守住第 5 节所说的“只约束最终答案”。将在
  Anthropic `forced_tool` 映射落地时（第 2 阶段）解决。
- Task 结果信封里的结构化字段可能携带的是抽取出来的数据，它是否需要一套
  区别于文本输出的、独立的保留期限和脱敏规则。
- 携带推理状态的提供商（`ProviderState`），是否会与结构化输出产生某种需要
  适配器显式排序处理的交互。
