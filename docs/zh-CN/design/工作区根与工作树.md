## 1. 本记录决定了什么

工作区根从"构建期状态"变成了"会话状态"：Agent 可以创建一个 Git 工作树、把会话迁移进去、在里面工作、离开、再清理——全程不需要用户手动操作。

五个阶段均已实现。根是每次工具调用都会查询的会话状态；一个 `Worktree` 工具负责创建、进入、离开、列出和移除工作树；根所决定的各项配置会随着迁移一起跟随；三个 Hook 事件会通知发生了什么；委托对象也可以拥有自己的工作树。本记录存在的意义，是让实现不必重新推导"根的哪些依赖项应当随之迁移、哪些不应该"——因为真正容易出错的地方正是这个问题本身，而不是 worktree 命令本身。

## 2. 为什么

### 2.1 决定往往发生在对话进行到一半时

在工作树里开始一个会话早已可行：`buildmax --workspace ../repo-refactor` 会把文件工具、Bash、Hook、技能和 `/diff` 的根都设为该目录，不会有任何缺失。但这个选项只能在第一轮对话之前使用。

本记录要解决的是相反的情形，而且是更常见的情形：对话进行了好几轮之后，约束条件和改动的形状都已经明确，这时才发现工作应该转移到另一棵独立的树上进行。在新会话里重新开始，虽然能拿到工作树，却会丢失使这个决定成立的上下文。而要求用户去运行 Git 命令、打开终端、再重启 Agent，虽然两者都能保住，却要付出这个 Agent 原本应该替用户省去的那次打断的代价。

### 2.2 是什么在阻碍这件事

| 阻碍 | 位置 |
|---|---|
| 根在运行时组装完成后就固定下来，之后没有任何东西会再改变它 | `internal/agentapp/app.go`，`internal/interface/cli/root.go` 中的 `--workspace` |
| Read、Write、Edit、Glob、Grep 会拒绝任何超出根目录范围的路径 | `internal/tool/base.go`，经由 `internal/util/workspace.go` 中的 `ResolvePath` |
| 每一次 Bash 调用——无论前台还是后台任务——都会重新从根目录启动，所以 `cd` 永远不会保留下来 | `internal/tool/bash.go` |
| 没有任何界面能切换根；TUI 没有对应的命令 | `internal/interface/cli/chat.go` |
| 子 Agent 和后台任务在设计上就与父会话共享同一个根 | `internal/tool/task.go`，`internal/agentapp/job` |
| 沙箱只把工作区绑定为可写，而且仅限工作区 | `internal/infra/sandbox/manager.go` |

`internal/tool/safety.go` 里的高风险前缀列表并不包含 `git`，而且 Bash 校验的是命令而不是路径，所以 Agent 其实已经可以创建一个工作树，并把它当作一个"外部目录"来操作：把每条命令都重新加上 `cd` 或 `git -C` 前缀，把每次读取都改成 `cat` 而不是 Read，把每次搜索都改成 `grep` 而不是 Grep。模型只要有一次忘记加前缀，就会写错树，而系统中没有任何东西会察觉。正是这种失败模式，决定了这必须是一项能力，而不是一条提示词层面的约定。

## 3. 范围

**在范围内。** 一次会话，一次只有一个根，可以由用户指示或 Agent 自主发起迁移：创建、进入、工作、离开、移除。每个工具都会跟随当前的根，不需要新增任何语法。用户始终能看到会话当前所在的根是哪一个。

**不在范围内。** 分叉会话或分支其上下文。分叉已作为一份与父会话共享工作区的历史副本单独交付（[本地会话存储](本地会话存储.md) §8.3）；需要独立工作树的分叉通过本记录的工具进入一个。同样不在范围内的还有：在一个监督者下运行多个并发会话、对工作树的改动做自动合并或变基、在 Portal 或 worker 运行中使用工作树路径（它们从不暴露本地路径），以及面向非 Git 工作区的版本化快照——其设计记录已被撤回，目前也没有待办计划。

让子 Agent 或后台任务拥有自己的工作树属于本记录的范围，但从不是强制性的——见 D7。这回答的是与本记录其余部分不同的诉求：是把工作委托到另一棵树上，而不是在一棵树里工作，但它复用同一套机制——`Task` 接受一个可选的 `worktree` 名称，对应的树会被创建并保持占用，父会话的根不会移动，该 Agent 类型的工具会针对这棵新树重新构建。

## 4. 根不仅仅是一个路径

`internal/agentapp/app_builder.go` 只在组装阶段从根解析一次工作区 Hook、MCP 服务器、技能和子 Agent 定义。沙箱管理器也是基于根构建的。每一轮对话，`BuildEffectiveSystemPrompt` 都会从根读取工作区的 `AGENTS.md`。`/diff` 读取的是 `App.WorkspaceRoot()` 所在的 Git 工作区，TUI 也把这个路径报告为会话当前所在的位置。

以上每一项都需要一个答案，而且答案并不相同：

| 从根派生的内容 | 决定 |
|---|---|
| 工作区 Hook（`<workspace>/.buildmax/hooks.yaml`） | 切换时重新加载 |
| MCP 服务器 | 重新解析，然后只重启定义发生变化的服务器——在同一仓库的不同工作树之间通常不会有变化 |
| 技能与子 Agent 定义 | 切换时重新解析 |
| `AGENTS.md` 提示词层 | 重新读取；见 D2 |
| 沙箱可写绑定 | 必须跟随根迁移，否则沙箱会拒绝新树里的每一次写入 |
| `/diff` | 跟随根；只展示当前这棵树，绝不会把两棵树合并展示 |
| TUI 头部 | 必须跟随根迁移，否则用户看到的就是错误的树 |
| 插件 | 不受影响：插件从 `<BUILDMAX_HOME>/plugins/` 加载，而不是从工作区加载 |

## 5. 决策

### D1. 工作树位于 `<repo>/.buildmax/worktrees/<name>`

登记在 `.git/info/exclude` 中，而不是仓库的 `.gitignore`。在使用它的仓库里，`.buildmax/` 本身是一个受版本控制的目录——本仓库就跟踪了 `README.md`、`agents/`、`mcp.json` 和 `skills/`——所以需要一条忽略规则；而 `.git/info/exclude` 是按克隆生效的：它能让工作树对 Git 不可见，又不会产生一次需要用户审阅的提交，也不会带来用户没有要求过的 diff。

被否决的方案：放在 `<BUILDMAX_HOME>` 下的集中位置——这样便于统一清理，但会让树远离仓库本身，用户的编辑器也够不到；以及同级目录 `../<repo>-<name>`——不需要忽略规则，但会污染父目录，并且在多个仓库之间会发生冲突。

### D2. 切换时会重新读取 `AGENTS.md` 提示词层

四个提示词层在一次会话内保持稳定，正是为了让它们组成可缓存的前缀。切换根会改变第 3 层，这里只有两个诚实的选项：要么重新读取并让前缀失效，要么冻结它，并接受"已加载的指令描述的是另一个目录，而不是正在被写入的这个目录"这一事实。

本记录选择重新读取。一次会话切换根的次数最多也就几次，所以这个代价是有界的，也会体现在用量统计里；而冻结这一层带来的失败模式不会报出任何错误，只会悄悄产生错误的改动。另外三层——运行时提示词、`<BUILDMAX_HOME>/AGENTS.md`，以及本次运行的附加系统提示词——都不会改变，压缩摘要是由 `RunLoop` 追加在这些层之后的，因此也不受影响。

### D3. 根只能迁移到当前仓库的某个工作树

这一点会通过 `git worktree list` 校验。`ResolvePath` 拒绝离开根目录，这在今天是一项安全属性；把根变成可移动的，就是把一个固定的边界变成一个可移动的边界，而这条约束能让"可达到的根的集合"保持封闭且可枚举，而不是"模型说的任何目录都行"。在一个根内部，路径包含关系的规则不变。

一个会话可以进入一个它自己没有创建的工作树，但前提是该工作树里没有其他存活的会话。一棵空闲的树——由更早的会话留下，或者是这个会话在恢复之前自己创建的——是可以被进入的。而另一个存活会话当前正把某棵树当作自己的根，进入请求会被拒绝，拒绝信息会指出占用者是谁。

两个会话同时写同一棵树，正是这整个功能要避免的竞争，所以这里选择直接排除，而不只是报告。拒绝的代价很小：第二个会话完全可以创建自己的工作树，只是一次工具调用而已。而彻底禁止进入的代价则更大——一个恢复的会话将无法回到自己的工作现场，一个被搁置的分支也永远无法再被人接手。

占用状态由 D10 定义。这里的任何决定都不取决于"是谁创建了这棵工作树"：本记录中没有任何决定需要这项信息，所以也就没有记录它。

### D4. 创建和进入被允许；移除需要询问

遵循[工具权限](工具权限.md)的原则，这里的分级是刻意做成非对称的：

| 动作 | 层级 |
|---|---|
| 创建一个工作树、进入它 | 允许 |
| 移除一个工作树 | 询问 |
| 移除一个包含未提交改动或未合并提交的工作树 | 拒绝，除非用户已经明确表示要丢弃它们 |

在一个新分支上创建一个空目录并不具有破坏性，不应该打断用户——这份自主性正是这个功能的意义所在。而删除一棵可能保存着唯一一份成果的树，则是另一种风险，所以它仍然保留确认提示。

### D5. 工作树永远不会被自动移除

如果会话在仍处于某个工作树内时结束，系统会询问用户是保留还是移除它，默认选项是保留。这是整个功能里唯一一个 Agent 的自主性可能毁掉用户成果的地方，所以默认值必须是无破坏性的那一个。

同样的答案也适用于因会话崩溃而遗留下来的工作树：这里没有回收器、没有基于时间的清扫，下次启动时也不会自动清理。一个已经终止的进程，并不能证明它那棵树里的工作已经完成了——而这恰恰是"这棵树可能是唯一副本"的情形。清理是用户自己的事，BuildMax 欠用户的是可见性而不是自动化——列出仓库中的工作树、哪些树当前有存活会话在使用、每一棵树里还有哪些尚未提交的内容。

### D6. 起始树不干净时会被报告，而不是被自动处理

工作树是从当前的 `HEAD` 创建的，没有一并带过去的未提交文件会被明确列出来。沉默是不可接受的：对话中描述的代码，新的树可能根本看不到。

工作树不会通过自动 stash 来填充。同一仓库的所有工作树共享同一个 stash 栈，所以自动 stash 会对该仓库里正在工作的其他所有会话构成隐患。"干脆拒绝创建工作树"这个方案也被否决了：常见情况是树是干净的，或者脏的部分无关紧要，而拒绝创建只会把用户逼回这个功能本该省掉的手动 Git 操作。将来若在分叉时创建工作树，也会面临同样的问题；除非找到只适用于分叉的理由，否则应当沿用同一个答案。

### D7. 除非模型另行指定，委托对象默认继承当前根

切换之后启动的子 Agent 和后台任务默认使用当前的根。已经在运行的那些则保留它们启动时的根，并在输出中说明这一点——后台任务本来就会记录自己的工作区。如果在有任务正在运行时拒绝切换，恰恰会在最需要切换的时候（比如某次测试正在跑）挡住切换；而悄悄把正在运行的进程重新挂到新根上，也不是一个可接受的选项。

也可以给委托对象单独分配一棵属于它自己的工作树。这只是一个可选项，从不是强制的：没有任何机制强制"每个子 Agent 一棵工作树"，是否值得做这种隔离，由模型针对每一次委托自行判断。一棵树里出现两个写入者是真实存在的风险——[本地后台任务](本地后台任务.md)当初刻意接受了这个风险，因为当时工作树隔离还不可用——但为一次只读的探索性任务单独开一棵树同样有代价：既占用磁盘，又会在 D5 之下留给用户一次手动清理。这个判断交给模型，其地位与"是否值得启动一个子 Agent"这个判断是一样的。

### D8. CLI 和 TUI 拥有完整能力；Desktop 只展示根

TUI 拥有运行时工具、一个 `/worktree` 命令，以及头部中显示的当前根。这个命令是 D5 所说"可见性"面向用户的一面：它会列出每一棵工作树、哪个会话占用着它、里面有哪些未提交的内容，并允许用户在同一个视图里移除某一棵——这是"看到一棵没有任何东西会去回收的树"之后唯一合理的后续动作。这里的移除同样遵循 D4：当前所在的树，以及另一个会话正占用的树都会被拒绝；一棵干净的树在确认后即被移除；一棵有工作内容的树只有在确认提示明确说明将丢弃什么之后才会被移除。这是用户主动发起的清理，而不是 D5 所否决的那种自动化。Desktop 只展示当前的根，不提供切换。Desktop 里的 `Project` 是本地 UI 状态，不是服务端实体；至于一个工作树最终应该变成一个 `Project`、变成某个 `Project` 内部的一种状态，还是 Desktop 干脆不展示它——这是一个产品问题，本记录不需要回答它就已经足够有用。

### D9. 工作树及其分支的名字由模型来起

名字是模型在创建时根据具体工作内容起的。固定命名方案只会产生 `worktree-1`、`worktree-2` 这样的名字，用户在列表里看到它们完全无法判断哪棵树装的是什么——而模型恰恰是唯一一个在创建那一刻就知道这个分支是为了什么的角色。用户仍然可以自己指定名字；模型起的名字只是默认值，不会覆盖用户明确给出的名字。

冲突的处理方式是直接失败，而不是悄悄加后缀：创建一个名字或分支名已经存在的工作树，会返回一个明确指出"哪一个发生了冲突"的工具结果，由模型另选一个名字。悄悄加上 `-2` 后缀的话，一个原本想回到已有工作树的模型反而会创建出第二棵树。

### D10. 占用状态是保存在工作树 Git 管理目录中的一把建议性锁

一棵链接工作树的 `.git` 其实是一个文件，指向 `<repo>/.git/worktrees/<name>/`，Git 会在那里保存这棵工作树自己的 `HEAD`、`index` 和 `locked`。这个目录正是存放占用标记的合适位置：它在工作树之外，因此永远不会出现在用户的 `git status` 里；而 `git worktree remove` 和 `git worktree prune` 在删除工作树时会一并删掉它，占用标记也就不可能比它所描述的对象活得更久。其他工具也是这样用这个目录的——Claude Code 就在那里写入一个 `CLAUDE_BASE` 文件。

这个标记是一把由会话进程持有的建议性文件锁，只要进程还在这棵树里，锁就一直打开，它记录的不是某个进程 ID。进程退出时——即便是崩溃退出——操作系统都会释放这把锁，所以判断"空闲"不需要任何过期启发式规则，也不需要防范 PID 被复用。这正是让 D3 的拒绝逻辑能够安全实施、也让 D5 里"用户可以收回这棵树"这句话成立而不是空话的关键——否则一棵树可能会被一个早已死掉的会话永远锁住。标记里*包含*的内容——会话 ID、起始时间——只是用来在拒绝信息里指出占用者是谁，而不是用来判断锁是否仍然存活。

不使用 `git worktree lock`：那是防止被 `prune` 清理的保护机制，设计上是持久生效的，与"哪个进程正在哪里工作"无关。复用它会把两种含义混为一谈，导致树在所有人都已经离开很久之后仍然显示为锁定状态。

代价是需要按操作系统分别实现——`flock` 对 `LockFileEx`——而 `internal/infra/sandbox` 出于同样的原因已经承担了这部分成本。

## 6. 用户看到的内容

这是一个示意，不是措辞规范：

```text
user  > 这个重构不小，开个 worktree 并行做

agent > Created .buildmax/worktrees/refactor-tool-roots on branch
        worktree/refactor-tool-roots, from HEAD (a1b2c3d).
        Two uncommitted files stayed behind in the original tree:
        internal/tool/bash.go, docs/ROADMAP.md.
        This session is now working in the worktree.

        … ordinary work: Read, Edit, Grep, Bash, /diff all in the new tree …

user  > 提交了，回主目录吧

agent > Left the worktree; it and its branch are kept at
        .buildmax/worktrees/refactor-tool-roots.
        This session is back in /Users/…/buildmax.
```

正是这一行显示当前根的头部信息，让 D4 里"允许"这一档的设定站得住脚：用户永远不会处于那种分辨不出 Agent 正在往哪棵树里写入的境地。

## 7. 落地位置

| 职责 | 归属 |
|---|---|
| 工具与沙箱共同依赖的工作区契约 | `internal/util`（`Workspace`、`FixedRoot`） |
| 作为会话状态的当前根 | `internal/agentapp`（`MovableRoot`） |
| 工具按每次调用而不是按构造时读取根 | `internal/tool`（`workspaceTool`、`Bash`、`Monitor`、`Task`） |
| Git 工作树的机制：添加、列出、移除、排除，以及移除会丢失什么 | `internal/infra/git` |
| 操作系统在进程退出时释放的占用锁 | `internal/infra/flock` |
| 单个会话的生命周期：可以进入什么、谁占用着它，以及如何迁移 | `internal/agentapp/worktree` |
| 作为迁移的一部分，重新解析根所决定的各项内容 | `internal/agentapp`（`sessionRoot`） |
| 运行时工具接口及其权限层级 | `internal/tool`（`Worktree`） |
| `/worktree` 面板、footer，以及让 `/diff` 跟随根 | `internal/interface/cli` |
| 针对委托对象的根，重新构建该 Agent 类型的工具 | `internal/agentapp`（`agentTypeToolsAt`） |
| 沙箱可写绑定跟随根迁移 | `internal/infra/sandbox` |
| 记录下来的工作区与恢复行为 | `internal/agentapp/session_manager.go`、`internal/agentapp/session_context.go` |

`internal/core` 不受影响：根是运行时组装状态，不是领域状态，这里的任何内容都没有给 Agent 循环增加新的概念。

## 8. 分阶段交付

**阶段 1——根成为会话状态。已实现。** `util.Workspace` 是契约，`agentapp.MovableRoot` 是状态，文件工具、Bash、`Monitor`、`Task`、沙箱的可写绑定、TUI footer 以及 `/diff` 都会按每次调用读取它。`util.FixedRoot` 服务于所有从不迁移的界面和测试。此阶段还没有工作树能力，`--workspace` 的行为与之前完全一致。这是唯一可能让既有行为出现回归的阶段，所以它先单独交付、单独测试。

**阶段 2——工作树生命周期。已实现。** `internal/agentapp/worktree` 负责这部分逻辑，`internal/infra/git` 负责 Git 层的机制，`internal/infra/flock` 负责占用锁。`Worktree` 工具和 TUI 的 `/worktree` 面板是这里的两个入口。D3 的包含关系校验、D4 的分级、D5"绝不自行删除任何东西"的原则、D6 的脏树报告、D9 的命名规则，以及 D10 的锁，在这一阶段全部生效。

**阶段 3——派生配置。已实现。** 迁移根，以及重新解析根所决定的内容，被做成了同一个操作，位于 `sessionRoot.Set` 中：任何只迁移根而不做后者的实现，都会让会话一边跑着一棵树的 Hook 和技能，一边操作着另一棵树的文件，而这从外部完全看不出哪里不对。Hook 会重新合并，技能和子 Agent 定义会重新解析，缓存的工具注册表会被清空，MCP 会重新协调。`AGENTS.md` 这一层不需要重新加载——提示词本来就是每一轮都基于当前根重新构建的，因此它天然就是跟随的；这一点由一项测试来保证，而不是靠一句声称如此的注释。失败会被记录日志，而不会被回滚：迁移已经发生了，让会话被困在两棵树之间，比降级到某一层配置更糟糕。

阶段 2 比阶段 3 早一个版本交付，这之所以可以接受，仅仅是因为同一个仓库的不同工作树通常携带完全相同的工作区配置，所以那份过时的快照往往和最新快照并无二致。这个理由在 D3 被放宽之后就不再成立了，但现在也不需要它成立了：阶段 3 已经落地。

**阶段 4——其余的界面能力。已实现。** `WorktreeCreate`、`WorktreeRemove` 和 `CwdChanged` 会随着生命周期触发，全部是建议性的：工具调用此时已经通过了 `PreToolUse`，所以第二道关卡至多只能让一棵工作树创建到一半就中断，而一个失败的 Hook 也永远无法撤销一次已经发生的迁移。Desktop 不需要任何代码改动——它展示的项目文件夹本身就是它的根，而它又不支持工作树，所以这个根根本不会迁移。用户文档位于 [manual/tools.md](../../../manual/tools.md) 和 [manual/hooks.md](../../../manual/hooks.md)。

**阶段 5——面向委托对象的工作树。已实现。** `Task` 接受一个可选的 `worktree` 名称。对应的树会被创建，其占用锁会在委托对象运行期间（无论前台还是后台）一直持有，父会话的根不会因此迁移：委托进入一棵树，并不等同于切换到那棵树。委托对象的工具会针对这棵新树重新构建，因为父会话的工具实例持有的是父会话的根，直接把它们交给委托对象只会让隔离形同虚设。回复中会指明这棵树的名字，这一点在这里比在其他任何地方都更重要——因为没有任何东西会在事后移除它，否则委托对象做出的改动就会留在一个父会话永远不会知道的地方。

## 9. 开放问题

- D2 的提示词缓存代价目前只能靠第一性原理推断，还应当等用量统计能够展示出来之后再实测记录。
- "列出"这一手段是否足以防止工作树不断堆积。D5 不会自动移除任何工作树，而委托对象现在还能创造出更多工作树，唯一的制衡手段就是用户能看到有哪些树存在、每棵树里有什么。这是一个只有靠实际使用才能回答的问题；如果"列出"最终被证明不够，答案应该是做出更好的列表，而不是引入一个回收器。

## 10. 用户文档义务

本记录承载的是设计理由。等各阶段真正落地之后，面向用户的那一半内容应当写进 `manual/`——如何请求一棵工作树、Agent 在遇到未提交改动时会怎么做、清理是如何进行的——而 `/worktree` 命令则应当归入 [manual/cli.md](../../../manual/cli.md)，其覆盖范围由一项测试强制保证。这两处都不应该重复上面的决策内容。
