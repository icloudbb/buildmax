## 1. 决策

Artifact 是一个一等的 BuildMax 对象,而不是某次 Task 运行的副产品。系统提供一种统一的 Artifact 能力,任何会产出一份用户应当保留的文件的东西——一个 Agent、一次后台运行、一次直接上传——都使用这同一种能力。一个想要保留自己输出的 Task 运行,和其他生产者一样调用 Artifact 服务。这样一来,一次 Run 依旧保留着它可复现的输出目录，而它产出的文件却可以在完全不知道其 Task 或 Run ID 的情况下被找到、被引用、被分享。

这正是这套模型与迁移 `0001_artifact_tables_to_task_run_artifact` 所移除的 `artifact`/`artifact_item` 表之间的区别。那两张表是某次 Task 运行的子结构：没有 Run 就没有 Artifact，而给一个 Artifact 命名的唯一方式就是它挂靠的那次 Run。本文档描述的对象则拥有自己的身份和生命周期，并把生产者记录为一种来源（provenance），而不是父级归属。

一个 Artifact 的身份就是它不透明的公开 ID。这个 ID 是服务返回的东西、工具汇报的东西，也是用户引用的东西。URL 只是某个界面对这个 ID 的一种呈现方式，而不是身份本身。

Artifact 是一种 server 能力。它们存在于一个 Space 命名空间里,而 Space 正是既有的授权边界；单独工作的用户由自己的个人 Space 来代表，无需在界面上看到 Space 这个概念。CLI 和 Desktop 通过登录到一个 BuildMax server 来访问 Artifact——这正是本产品所服务的私有化部署场景。一个直接对接模型提供商、没有 server 的本地会话,完全不具备 Artifact 能力，它的工具列表里也不会出现任何 Artifact 工具。

共享的 Agent 运行时只会在具备这种能力的地方暴露一个 `UploadArtifact` 工具。它接受一个明确指定的本地文件，把它流式传输给 Artifact 服务,记录一条 Artifact，并返回该 Artifact 的 ID 和规范 URL。

对象存储始终是一个实现细节。一个 BuildMax Artifact URL 既不是一个存储桶的键,也不是一个对象存储的预签名 URL。

## 2. 产品目标

一个 Agent、一个用户，或一次后台运行，都应该能够把一份有用的文件提供给整个 Space,并给接收方一个可以长期使用的引用。接收方应当能够：

- 在拥有 Space 访问权限时预览或下载它；
- 把它附加到一个 Issue、会话或结果上，而不必复制存储密钥；
- 把这个引用保存在一份文档或一条消息里，并且它始终能被正确解析；以及
- 在确实需要 Space 之外的访问时,有意地创建一个可撤销的外部分享链接。

产品语言用的是 **artifact**，而不是存储桶、对象、结果目录，或者 worker 输出路径。

## 3. 现状基线

BuildMax 已经具备了大部分存储原语，但还没有对应的产品对象：

| 能力 | 当前行为 | 局限 |
|---|---|---|
| 对象存储 | `internal/infra/objectstore` 支持本地文件系统和 S3 兼容存储，包括 MinIO。 | 键是基础设施层面的细节。 |
| Space 文件 | Portal 接受把文件上传进一棵可变的 Space 文件树。 | 一个文件没有持久身份、来源、不可变版本或分享模型。 |
| Task-run artifact | Worker 会把 `artifacts/` 归档，并记录 `task_run_artifact` 路径。 | 一个文件只能通过它所属的 Task Run 和相对路径来定位，无法被独立引用。 |
| Artifact 查看 | Space 成员可以通过经 Space 身份验证的 task-run 路由取回运行输出。 | 它面向文本/Markdown，不是一个通用的文件预览或下载契约。 |
| ID | `internal/util/id.go` 中曾保留 `ar_` 和 `f_` 前缀。 | 它们命名的资源已被移除，见下文。类型前缀现在已经完全取消——见 [entity-identity.md](实体身份.md)。 |

`task_run_artifact` 有意被设计成一组路径，而不是一个持久资源：它没有公开句柄，也没有时间戳。新模型绝不能把这张表误当作已经提供了所需契约来重新解读。

在首次公开发布之前,曾经存在一对 `artifact`/`artifact_item` 表。`internal/infra/db/migration.go` 中的迁移 `0001_artifact_tables_to_task_run_artifact` 移除了它们：它把 `artifact_item` 的内容拷贝进 `task_run_artifact`，丢弃这两张表，并从 `task` 和 `chat` 表中去掉了 `last_artifact_id` 和 `artifact_seq` 两列。那套模型是某次 Task 运行的子结构，这正是为什么把它压缩成一份路径索引不会丢失任何值得保留的东西。在任何已经执行过迁移 0001 的部署上，重新使用 `artifact` 这个表名是安全的，而本设计创建的表,基于第 1 节给出的理由,是一个完全不同的对象。

## 4. 范围

### 4.1 范围之内

- Space 命名空间中的一个 Artifact——个人工作区就是用户自己的个人 Space——以一个稳定的不透明 ID 作为其规范引用。
- 在第一个切片里，每个 Artifact 对应一个不可变的文件。
- 由 server 中介的上传、元数据查询、预览与下载。
- `UploadArtifact` 作为一个普通的共享 Agent 工具，只在具备已验证身份的 Artifact 服务的界面上注册。
- 记录 Agent 上传、Task-run 输出以及用户直接上传的来源（provenance）。
- 稳定的、经过身份验证的 URL,以及独立、可撤销的外部分享链接。
- Portal 的 Artifact 卡片、列表/详情视图,以及安全的轻量预览。
- 把新产生的 worker 输出文件迁移进这套统一模型，同时为兼容性保留既有的 task-run artifact 列表。
- 在 Artifact 边界上实现 Space 授权、删除/标记删除、保留策略钩子、配额，以及审计事件。

### 4.2 范围之外

- 为没有 server 登录的 CLI 或 Desktop 会话提供一个本地 Artifact 存储。这样的会话保持它原有的本地输出行为，也没有任何 Artifact 工具；见第 7.1 节。
- 一个通用的可编辑网盘或本地同步文件夹。
- 取代可变的 Space `home/` 文件空间。
- 一个默认公开的文件托管服务。
- 在第一个切片里支持多文件归档、文件夹、版本历史、去重，或客户端加密。
- 在 server 上传契约和控制手段被证明足够之前，支持浏览器直传 S3。
- 一个完整的文档编辑器、任意文件格式转换服务，或恶意软件扫描器的具体实现。API 必须为这些控制手段预留空间,但不需要现在就实现它们。
- 跨 Space 的 Artifact 归属转移，或者在不同部署之间复制 Artifact。

## 5. 领域模型

### 5.1 Artifact

Artifact 模型里,每个 Artifact 对应一个不可变的内容对象。`SpaceID` 是必填项，因为 Space 就是授权命名空间,即便是一个人独自在自己的个人 Space 里工作也是如此：

```go
type Artifact struct {
	ID              uint   `json:"-"`
	ArtifactID      string `json:"artifact_id"`
	SpaceID          string `json:"space_id"`
	Filename        string `json:"filename"`
	MediaType       string `json:"media_type"`
	SizeBytes       int64  `json:"size_bytes"`
	SHA256          string `json:"sha256"`
	StorageKey      string `json:"-"`
	CreatedByType   string `json:"created_by_type"`
	CreatedByID     string `json:"created_by_id"`
	SourceType      string `json:"source_type"`
	SourceID        string `json:"source_id,omitempty"`
	Title           string `json:"title,omitempty"`
	DeletedAt       *int64 `json:"deleted_at,omitempty"`
	ExpiresAt       *int64 `json:"expires_at,omitempty"`
	CreatedAt       int64  `json:"created_at"`
}
```

Artifact 只有一套存储。一个已登录的 CLI 或 Desktop 会话，通过 Portal 所使用的同一个服务，在同一个 Space 命名空间里创建出一模一样的 Artifact；不同界面之间的差别只在于如何呈现结果。如果将来真的要新增一个纯本地存储，它从一开始就必须签发规范的公开 ID，这样一来，工具返回的引用在任何界面上含义都是一致的。

`StorageKey` 是私有的，由存储适配器生成。任何 API、工具输出、轨迹或界面都不会暴露它。`SHA256` 是在流式上传过程中计算出来的，用来证明存入的正是这份内容；它不是一个跨 Space 的去重键。

初始的来源类型有：

| 来源类型 | 来源 ID | 含义 |
|---|---|---|
| `agent` | 可用时为 Agent 运行或会话 ID | 由一个 Agent 调用 `UploadArtifact` 产生。 |
| `task_run` | task run ID | 由 worker 把这份文件作为运行输出物化出来。 |
| `user_upload` | 可选的请求/审计关联 ID | 由一个成员直接上传的文件。 |
| `system` | 可选的操作 ID | 由 BuildMax 在没有 Agent 调用的情况下生成的文件。 |

`created_by_type` 用来区分是用户、Agent、worker 还是系统这几类行为者；它不会为自动化工作凭空编造一个用户 ID。这遵循的是既有审计模型里关于"行为者"的规则。

一个 Artifact 不包含任何自由格式的元数据 JSON 列。上面列出的字段都是刻意设计成可查询、有边界的。只有当某个产品行为确实需要时，才新增一个具体字段；任意的 JSON 很容易变成内容、提示词和凭证悄悄泄漏进持久化元数据的地方。

### 5.2 与工作的关联

一个 Artifact 可以与某次 Task 运行、某个 Issue、某个会话，或某张结果卡关联起来。在第一个切片里，`source_type` 和 `source_id` 记录了产生这个 Artifact 的那次操作，具体展示时再由这个来源反推出相关的 Task/Issue/会话。一张独立的多对多关联表被推迟到"一个 Artifact 必须同时挂载到多个独立工作对象上"这种需求真正出现之后再引入。

`source_id` 保存的是这次 Task **运行**，而不是这个 Task 本身。运行才是真正产出这份文件的操作，也是区分"这一次尝试"和"另一次尝试"的依据；而 Task、Issue 和会话都可以从这次运行反查得到。反过来看,如果一个读者从 Issue 出发去问"这项工作产出了什么"，就必须收集这个 Issue 下每一个 Task 的每一次运行，而不能只看每个 Task 最后一次的运行，否则一次被重试过的 Task 就会把它更早那几次尝试所发布的内容藏起来。

这样也避免了让一份上传的文件仅仅因为它最初的生产者是一个 worker，就必须依附于某次 Task 运行。

### 5.3 Task-Run 的输出不是 Artifact

`task_run_artifact(task_run_id, relative_path)` 仍然只是一次运行对自己输出目录内容的索引，其中的任何东西都不会自动变成 Artifact。

这推翻了本节此前的一版草稿——那一版让每个上传的文件在运行终态处理时自动创建一个 Artifact。这种做法有两处问题。首先，重复存储是真实存在的：兼容路由仍然读取的是运行输出的键空间，所以把同一批文件再注册进 Artifact 的键空间，等于把每份输出都存了两遍。其次，这种"采集"正是第 11 节所否决的做法——一个 Agent 的输出目录恰恰就是 `.env` 文件、缓存和中间产物最容易堆积的地方，而这件事由 server 来做，并不会因此就变得更安全。

这两者是职责完全不同的两个对象。一次运行的输出目录是这次运行产出内容的可复现记录；而一个 Artifact 是某个人明确打算保留的文件。一个 Agent 通过一次明确的 `UploadArtifact` 调用，主动把前者转化为后者。

没有任何机制会把一条旧的 task-run 路径改写成一个 Artifact ID，旧的输出也不会被回填。对于已经存在的运行，task-run 路由会继续保持它现有的响应形式。

## 6. 访问与 URL

### 6.1 身份与路由

规范引用就是这个 Artifact 的公开句柄。这个句柄本身就是唯一的——96 位加密随机数据——所以定位一个 Artifact 不需要依赖任何其他东西。Space 是这条记录携带的一项授权事实，而不是地址的一部分。

由这个拆分自然衍生出两种路由形态：

```text
GET /api/artifacts/{artifact_id}          # detail
GET /api/artifacts/{artifact_id}/content  # content
GET /api/spaces/{space_id}/artifacts        # the space's listing
```

以 ID 寻址的路由会先解析出该 Artifact，读取它的 `SpaceID`，再要求调用者是该 Space 的成员。这是一条新的授权路径，它无法复用从请求路径里取出 Space 的 `access.Guard.UserAndPathSpace`，因此需要自己的 guard 方法，也需要在 Space 授权矩阵测试里加上自己的条目。

一个非成员的调用者只会得到 `404`，绝不会得到 `403`。不透明的 `artifact_id` 是一个标识符，不是凭证，任何响应都不能让它变成一个可以用来判断"这个东西是否存在"的探针——这正是第 13 节"不可枚举"标准在实践中的含义。

以 Space 为范围的路由是列表和 Space 视图专用的界面，它不是同一个 Artifact 的第二个地址。

除了这些 API 路由之外，Portal 还提供了一个面向人的详情路由：`#/artifact/{artifact_id}`，它通过同一个以 ID 寻址的 API 来解析同一个 Artifact，因此遵循同样的授权规则。基于本节给出的理由，它的地址里不带任何 Space 信息，拒绝访问时用的措辞和 API 的 404 一致——只说"未找到"，不透露该对象是否存在。列表页是 `#/artifacts`，是一个顶层区域，而不是某个 Space 设置里的一个选项卡,因为 Artifact 是工作的产出，而不是用来配置 Space 的一个开关。

### 6.2 外部分享链接

外部分享是一项独立的能力，不是规范 URL 上的一个开关。创建一个分享链接会生成一个高熵、不可猜测的分享令牌和一个形如下面这样的 URL：

```text
/shared/artifacts/{share_token}
```

一个分享链接标识一个 Artifact，并且至少携带：

- 创建者和创建时间；
- 可选的过期时间，部署方可以设置一个有边界的默认值；
- 撤销时间；以及
- 可选的下载次数，供审计和未来的限额使用。

MVP 阶段的策略是**仅限已通过身份验证的 Space 内成员访问**。公开分享现在已经在 [artifact-public-sharing-and-preview.md](./工件公开分享与预览.md) 中被重新开放并给出规格：一个可撤销的、持久化存储的分享令牌，一条匿名的 `/api/shared/...` 路由，以及一个由 server 渲染的公开链接。那份文档回答了本段留下的授权矩阵、撤销模型和审计事件问题。不要把永久性的 S3 预签名 URL 当作捷径来实现：它们绕开了 BuildMax 的授权体系，无法被集中撤销，还会把已经保存下来的链接和对象存储的具体配置绑死在一起。

### 6.3 内容分发

所有内容请求都会在真正取回对象之前先完成授权或校验分享令牌。server 既可以自己流式返回内容，也可以在完成授权之后重定向到一个短期有效的对象存储 URL；后者只是一种优化手段，不是公开契约的一部分。

内容响应头使用的是存储下来的、经过 server 校验的元数据；绝不能单凭一个上传时的文件名或调用方提供的 MIME 类型来行事。下载时使用安全的 content-disposition 和文件名。行内预览走的是白名单机制，而不是靠浏览器去猜：纯文本、经过既有净化器渲染的 Markdown，以及安全的图片/PDF 类型可以被有意地加入白名单。在第一个切片里，HTML、SVG、可执行内容,以及未知类型一律以附件形式下载。

## 7. Agent 工具契约

### 7.1 可用性

`UploadArtifact` 是一个共享的运行时工具，和其他默认工具一起在 `internal/agentapp` 中被组装起来。它只会在界面具备一个已验证身份的 Artifact 服务时才会被注册：可能是一次 server 部署自身的运行时，也可能是一个登录了某个 BuildMax server 的 CLI 或 Desktop 会话。`internal/interface/auth` 已经为这些本地界面回答了这个问题——`IsLoggedIn` 和 `CanAuthenticate(serverURL)`——所以这是工具组装阶段的一个前置条件,而不是在调用时才去发现的东西。

在没有这种服务的地方，这个工具会**从工具列表中彻底消失**，而不是以一种"每次调用都会失败"的状态被注册进去。一个存在的意义只是回答"不可用"的工具,只会白白浪费一次往返，也教不会模型任何东西；而一个根本不存在的工具,则是模型可以立刻据以行动的一个事实。

这个工具从不会靠返回一个源文件路径来模拟实现。某台机器上的一个路径不是一个可分享的对象，没有 server 的会话应当继续保持它原有的本地输出行为。

### 7.2 调用方式

Agent 需要提供：

| 参数 | 是否必填 | 规则 |
|---|---|---|
| `path` | 是 | 有效工作区内或允许的运行时输出目录内的一个可读的常规文件。 |
| `title` | 否 | 一个面向用户的简短标签；文件名依然是内容本身的名字。 |
| `purpose` | 否 | 供结果卡片展示的一条有边界、可读的说明,而不是任意的文件元数据。 |

这个工具必须拒绝目录、设备文件、逃出了允许根目录的符号链接、超出当前配额的文件，以及任何它无法安全打开的路径。它会以流式方式读取文件，只有在存储成功之后才创建这条 Artifact 记录，并返回 Artifact ID、文件名、大小和规范 URL。存储失败时会返回一个有意义的工具错误，并且不会留下任何"看似成功"的 Artifact 记录。

这个工具不会自动上传 Agent 写出的每一个文件。模型必须自己选择打算呈现的最终文件。这样可以让输出的内容一目了然，避免 `.env` 文件或缓存被意外公开，也能把存储成本控制在可预期的范围内。

### 7.3 提示与结果呈现

运行时提示词会告诉 Agent：对于那些应当被交付、保留或分享的文件，要使用 `UploadArtifact`，并在最终答复里引用返回的 Artifact 引用。一张 Artifact 结果卡片应当包含标题、文件名、产生它的运行或 Agent、创建时间、预览/下载操作，以及规范链接。

面向 LLM 的名称遵循 `internal/tool/names.go` 的规定；等实现真正加上这个常量之后，`manual/tools.md` 就会成为它的参数和可用性方面面向用户的权威说明。

## 8. 授权、治理与限额

Artifact 是一种 Space 资源。Space 成员身份是最基本的读取边界，用户自己的个人 Space 对应的就是私有的单用户场景。一个 Artifact 绝不会仅凭一个运行 URL 就获得授权。详细的权限矩阵留待实现阶段确定，但目前提议的第一个切片策略是：

| 操作 | 成员 | 管理员 | 所有者 | Space 之外 |
|---|---:|---:|---:|---:|
| 读取/下载 Space 内的 Artifact | 是 | 是 | 是 | 否 |
| 通过已获授权的 Agent/用户流程上传 | 是 | 是 | 是 | 否 |
| 删除自己直接上传的 Artifact | 是 | 是 | 是 | 否 |
| 删除 Space 内任意 Artifact | 否 | 是 | 是 | 否 |
| 创建/撤销外部分享链接 | 初期不可 | 未来支持 | 未来支持 | 否 |

删除首先是一次标记删除（tombstone）：它会立即隐藏元数据、阻断内容访问、记录一条审计事件，然后再按保留策略安排对象的物理删除。它不会改写 task-run 的历史记录。一个运行页面完全可以说明它先前的输出已被移除，而不会泄漏任何存储密钥。

`internal/server/scheduler` 中的 `ArtifactRetainer` 就是这套保留策略，也是除上传回滚路径之外唯一会移除 Artifact 内容的东西。它每小时分两个阶段扫描一次：先由过期阶段把 `ExpiresAt` 已过的 Artifact 标记删除，再由清除阶段回收那些在 `storage.artifact_purge_after_days` 天之前就已被标记删除的 Artifact 所占用的对象。这个宽限期默认是 **0**——因为在授权边界上，删除的效力已经立即生效，事后继续留着这些字节只是成本和风险，而不是安全保障。如果一个部署所用的存储桶工具支持"撤销删除"，才有理由把这个天数设大；BuildMax 本身不提供这种撤销能力。

一个 Artifact 的 `StorageKey` 就是它的字节是否还在被保留的记录。每个 Artifact 在创建时都会拿到一个 `StorageKey`，所以一条已被标记删除的记录如果这个键是空的，就意味着对象已经不存在了。清扫过程直接清空这个键，而不是另外新增一列 `purged_at`："没有键"和"什么都没存"其实是同一个事实,而两个本该始终一致的列，总有一天会不一致。

对象总是先被删除，然后才更新数据库行。反过来做的话，一次发生在两者之间的崩溃就会留下一行"字节已经没了"的记录，而存储桶其实还在为它计费；按现在的顺序，一次崩溃留下的是一行"对象还在"的记录，下一轮清扫会去删除一个其实已经不存在的对象——而第 9 节的内容存储契约把这种情况视为成功。

服务会在接受一个文件之前先执行单文件大小和 Space 存储配额的检查，并统计最终实际存储的字节数。单文件上限是 `storage.max_artifact_mb`；Space 层面的配额是配额层级里的 `max_storage_bytes`，通过 `artifact.StorageAdmitter` 来检查——为什么它是一项硬性准入检查，见 §12 问题 2。允许哪些 MIME 类型、是否集成病毒扫描,仍然是运营方的策略决定；Artifact 服务只是暴露出必要的决策点，不会在这些配置字段真正出现之前就凭空发明它们。

至少应当审计以下这些仅涉及元数据的操作：创建 Artifact、删除 Artifact、Artifact 过期、清除 Artifact、创建分享、撤销分享。过期要按每个 Artifact 单独记录，因为这是唯一一种没有任何成员主动要求、却发生了的标记删除，一个想弄清楚文件为什么消失的读者必须能按名字找到它。清除则按每次扫描记录一次，附带数量和字节总数，因为授权每一次删除的那条标记删除记录本身已经在审计轨迹里了，这里只需要说明这些字节现在确实已经没了。审计记录里不得包含文件内容、已签名的 URL、分享令牌，或者未经边界限制和审查的用户自定义描述。

## 9. 存储与失败语义

存储键是私有的，由适配器生成，和任何 URL 都没有关系。在一次 server 部署中，一种典型的键形态是 `spaces/{space_id}/artifacts/{artifact_id}/content`，它能让对象的归属一目了然，同时允许存储桶的具体布局在适配器背后自由演化。它和一条 API 路由长得像，纯属命名上的巧合，不是一份契约：适配器之外的任何代码都不允许解析、构造或依赖这个键。

既有的 task-run 输出是按创建它的用户来建键的，而不是按 Space。`objectstore.RunOutputFileKey` 生成的是 `<prefix>/<created_by>/artifacts/<conversation>/<task>/<run>/<path>` 这样的键。新的运行会改为通过 Artifact 服务写入它自己的键空间。在这套设计生效之前写入的对象则保留它们原来的键，只能通过兼容路由访问，也不会被拷贝过来。

`internal/infra/objectstore` 中一个原本叫 `ArtifactStorage` 的接口，其实一直是运行输出存储——它的方法接受的是 `RunRef` 和 `RunObjectRef`。现在它被改名为 `RunOutputStorage`，与已经在使用的 `cfg.RunOutputs` 和 `db/run_output.go` 命名保持一致。让两个不同的接口共用一个名字，会是日后某次改动悄悄把这套设计本来要修正的依赖方向重新颠倒回去的最简便途径。

这项原生能力的契约后来被挪到了它的消费方一侧，变成了 `internal/service/artifact.ContentStore`，引用类型则放在 `internal/core/artifact` 中。方向和本节所主张的完全一致，只是反过来表述：由服务说明自己需要什么，恰好有一个适配器满足了这个需求，而不是由存储包发布一个接口,再强迫服务去迁就它。

上传是一次写入、不可修改的过程：

1. 对源数据流进行授权和校验；
2. 预留一个 Artifact ID 和一个生成出来的存储键；
3. 在测量大小和 SHA-256 的同时，把内容流式写入一个临时或最终对象；
4. 只有在对象已经持久化之后，才提交这条不可变的 Artifact 元数据；
5. 失败时移除任何未提交的对象，并由一个协调器来处理存储和数据库操作之间发生崩溃的情况。

不存在任何"更新内容"的接口。一个发生变化的文件会创建一个新的 Artifact，日后如果产品需要维护版本谱系，再考虑把它和它的前一个版本关联起来。

存储接口在 server 的本地文件系统后端和 S3/MinIO 之间保持可移植性。这只是一个关于"一次部署的对象存储放在哪里"的选择，它和"一个 CLI 或 Desktop 会话是不是本地的"完全无关,那个问题由第 7.1 节按自己的标准来决定。定义产品契约的是 server 端的行为，而不是存储提供商的 URL 行为。

## 11. 被否决的替代方案

### 让 Artifact 只服务于 Worker

这样能保留目前最简单的实现,但会让已登录的本地会话、用户直接上传，以及未来非 worker 的执行方式都沦为二等公民。它还会迫使用户必须理解 task-run 的层级结构，才能保留一份有用的输出。

### 给没有 server 的本地会话一套自己的 Artifact 存储

一套本地存储可以让 `UploadArtifact` 在任何地方都存在，听起来很像是"本地优先"该给出的答案。但其实不然：这个工具会因为所在界面不同,返回两种完全不同的东西，模型还得向用户解释拿到的到底是哪一种。这还会让元数据模型和存储适配器都翻一倍，而且一旦有人想把本地内容发布到云端,马上就会引出第二个同步问题。

Artifact 存在的意义，是为了被别人找到、引用和分享。一个没有 server 的会话里根本没有"别人"。这样的会话继续把文件写在它原本就会写的地方，正是最适合它的行为方式。第 4.2 节把这个决定记录为"范围之外"，而不是"推迟"，第 5.1 节则记录了将来若要新增本地存储必须满足的那个条件。

### 把可变的 Space 文件直接当作 Artifact 复用

Space 文件属于工作区状态。它们可以被覆盖或删除，也不记录产生它们的具体操作。如果把它们称作 Artifact，就会导致一个已经保存下来的链接,随着工作区内容变化而改变含义。

### 直接返回对象存储 URL

这会暴露部署细节，在不同供应商之间表现不一，削弱审计和授权能力，还会让撤销行为依赖于对象存储自身的行为。短期有效的签名 URL 仍然可以在一个已获授权的 BuildMax 端点背后使用。

### 让每个 Agent 都能完全自动上传

自动采集目录看似方便，但只要一不小心把秘密信息、中间产物或大体积缓存也上传了，方便就变成了麻烦。一次明确的工具调用,能给模型和用户都留下一个清晰可辨的发布事件。

## 12. 未决问题与所需证据

1. **本地界面如何选择 Space：** ~~在第一个切片里已经解决~~。`POST /api/artifacts` 在请求没有指定 Space 时会解析出调用者的个人 Space，也会尊重调用者作为成员显式传入的 `?space_id=`。因此一个本地客户端完全不需要被告知任何有关 Space 的概念就能完成发布。真正悬而未决的只是客户端是否应当能够*选择*并记住某个 Space，这是一个设置层面的问题，而不是 API 层面的问题。
2. **Space 存储配额：** ~~已决定：以配额层级作为一项硬性准入检查~~。`max_storage_bytes` 加入到 `quota_tier` 中，和运行次数、令牌数限额并列，`QuotaService.CheckStorage` 会拒绝任何会突破这个上限的上传——和另外两项限额一样返回 429，因为文件本身没有问题,只是这个 Space 已经满了。它和 `Check` 是分开的，因为存储是一个存量,而另外两项是速率：这里没有时间窗口的概念，`period_days` 也不适用，总量只会在一个 Artifact 被删除时下降，而不会随时间推移自然下降。

   之所以是硬性拒绝而不是仅仅告警，恰恰和速率限额的逻辑相反。令牌在被统计到总量里的时候早已经被消耗掉了，事后拒绝新的工作只能阻止进一步的消耗；而字节一旦被接受存下来就一直占着，运营方事后才发现的话，在 BuildMax 内部没有任何补救手段。预置的各个配额层级刻意不设置任何存储上限，因此一次部署只有在主动选择时才会获得一个存储限额——这和 `audit.retention_days` 默认"保留一切"是同一个原则。
3. **敏感内容的管控：** 哪些私有化部署会要求在允许 Agent 上传之前先做恶意软件扫描、DLP，或者 MIME 类型限制？应当先收集运营方的实际需求，而不是硬编码一套面向云端场景的策略。
4. **外部分享：** ~~已决定：不做计划~~ → **已重新开放**。公开匿名链接现在已经在 [artifact-public-sharing-and-preview.md](./工件公开分享与预览.md) 中给出了规格；经身份验证的跨组织分享在那里仍然不在范围之内。参见第 3 阶段。
5. **预览支持：** 哪些类型可以在所有 Portal 客户端上被安全且有用地渲染出来？先从一份白名单开始，再根据实际需求来衡量。
6. **把运行输出当作 Artifact：** ~~已决定：不做~~。一次运行的输出目录不会被注册为 Artifact，也不打算对旧的输出做回填。这么做等于让每一份输出都多存一份副本——因为兼容路由仍然要读取运行输出的键空间——本质上和第 11 节针对 Agent 所否决的目录采集是同一件事，只不过这次采集的对象换成了 Agent 写出的一整个目录。一个想要保留某个文件的 Agent,应当用 `UploadArtifact` 有意地把它发布出来；一次运行的输出目录则始终只是这次运行留下内容的可复现记录。参见第 5.3 节。

7. **一次运行的状态可能悄无声息地不完整：** ~~待定~~ → **已决定：让运行失败**。这不是一个关于 Artifact 的问题——运行输出本来就有意不算作 Artifact（问题 6）——但它是"一次运行留下了什么"这个话题的另一半。`internal/agentapp/taskrun/runtime.go` 中的运行级全局上传过去会在上传被拒后只记一条日志，仍然报告 `SUCCEEDED`，同时继续指向一个存储里并不存在的 trace，并让下一轮赖以恢复的会话包缺失。现在，一次状态无法存储的运行会以 `FAILED` 结束，错误消息点明对象存储，并保留其回复与用量；只有 trace 真正存储之后才会记录 trace 指针。kind 写入拒绝演练（[端到端测试.md](端到端测试.md) §6.6）是部署层面的证据。

## 13. 验收标准

第一个可用的增量在满足以下条件时即为完成：

- 一个用户或经授权的 Agent 可以把一份明确指定的文件上传到一个个人或共享的 Artifact 工作区；
- 响应中携带一个稳定的不透明 ID，另一个经授权的 Space 成员可以解析它、在被允许时预览它，或者下载它；
- 一个没有 server 登录的 CLI 或 Desktop 会话，其工具列表里完全没有任何 Artifact 工具；
- 一个非成员既无法使用这个引用，也无法得知它是否存在；
- 对象键、提供商凭证和分享令牌不会出现在任何 API 响应、工具输出、轨迹或审计事件中；
- 一个由 worker 创建的结果,会以统一 Artifact 的形式出现，同时不丢失它的 task-run 来源信息；
- 上传失败绝不会报告出一条"成功"的 Artifact 记录，并会留下可恢复的存储/数据库状态；以及
- 删除操作会在 BuildMax 的授权边界上立即生效。
