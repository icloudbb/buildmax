## 1. 决策

端到端（E2E）验证是本地开发与 AI Agent 反馈循环的一部分，而不是一道必需的 Pull Request 门槛。

Pull Request 仍然保留其快速、确定性的检查：构建、lint、单元测试、集成测试，以及范围有限的前端测试。贡献者或 Agent 在改动一个用户流程之后运行与之相关的最小 E2E 套件，再借助它产出的证据诊断失败。全面的部署验证则在合并后、按计划，或在显式派发时运行；它为发布提供信心，而不必让每一次迭代都去等待容器、浏览器或集群。

“全面”指的是每一个重要的用户结果都至少拥有一条确定性的端到端路径，而不是说要把单元测试套件原样在 UI 上重跑一遍。后者更慢、更难诊断，只会让反馈循环变差。

## 2. 原因

BuildMax 有四个执行界面，它们的边界是普通测试无法一起证明的：

| 界面 | E2E 测试必须证明的边界 |
|---|---|
| Portal | 已发布的浏览器构建产物、运行时 API 配置、身份验证、承载一次会话双向往返的 WebSocket，以及可见的 Space Workflow，都能在一次真实部署上协同工作。 |
| Server 与 Worker | 已部署的 Server、存储、调度器、Worker、Artifact 路径，以及托管模型的传输通道协同工作。 |
| CLI 与 TUI | 发布的二进制文件、终端交互、审批闸门、本地工作区、会话持久化、策略，以及轨迹行为协同工作。 |
| Desktop | React 界面、Wails 绑定与事件、本地运行时、审批，以及持久化的 Project/会话状态协同工作。 |

常规的测试金字塔仍然是主要的回归手段：纯粹的展示决策属于前端单元测试，服务契约属于 Go 测试，处理器规则属于 HTTP/集成测试。E2E 测试只保留给那些其他手段都无法证明的边界。

## 3. 当前基线

仓库已经具备一些有用的部署证据，同时也存在一个比看起来更大的缺口。

- `./make compose smoke` 和 `./make kind up` 会用一个确定性的模拟模型跑一次真实部署，覆盖登录、个人 Space、文件存储、一次对话 Task、Worker 完成，以及 Artifact 检索。托管模式的冒烟测试还会额外证明 Worker 能通过网关访问模型。
- `./make e2e <cli|desktop|local|compose|kind|all>` 用来选择套件。Portal 相关的套件会在 `portal/e2e/` 下串行运行 Chromium Playwright 检查：登录、会话恢复、Portal 外壳、运行时 API 配置、审计与管理路由、Run 轨迹视图、Space 文件、Workflow，以及一个未被授权的账号会看到什么。`kind` 和 `compose` 会挂接到一个已经在运行的部署，`local` 拥有一套只服务于一次运行的专属 Compose 栈，`cli` 则完全不需要部署。
- `./make agent-smoke` **不是**确定性验证。它会构建 CLI 并运行 `buildmax -p "/smoke 0"`，驱动 `.buildmax/skills/smoke` 这个技能：由真实模型执行工具检查，并自行报告一张 PASS/FAIL 表。因此它需要提供商的 API key、每次运行都会生成不同的转录、由自己判断结果，而且它的退出码只反映进程是否跑完。它是一次有用的手动 Agent 演练，但它不是 CLI 套件——CLI 套件是 `internal/e2e/cli`，驱动构建好的二进制文件去对接一个脚本化的模型。它曾经叫 `./make smoke`，直到这个名字和另外两件确定性的事情撞了车，现在它会在开始前先说明自己需要什么。
- `./make eval` 用构建好的 CLI 跑 `evaluation/suite/` 中的 CLI 任务。Worker 任务需要用 `--surface worker` 显式加入，`--surface all` 会两者都跑。这是对 Agent 质量的行为评估，不是边界验证，因此被有意排除在下面的套件之外——但它运行的是同一个二进制文件、同样是在一个临时工作区里，所以 CLI 套件和 eval 运行器必须共享同一套进程启动与隔离辅助设施，而不是各自长出两套互不兼容的实现。
- Desktop 有 Go 桥接测试和前端单元测试，但没有 UI 层面的 E2E 套件。
- `gui` 在 CI 中既没有测试也没有 ESLint 步骤；Portal 浏览器套件目前是唯一会执行这个共享组件包的东西。由于 Portal 和 Desktop 都依赖它，把 E2E 移出 PR 门槛就会让这个包失去它唯一的 PR 时刻覆盖率。见 §8。

最近的两项设计改变了这些套件必须覆盖的内容，以及可以如何驱动它们：

- **审批闸门是真实存在的。** [tool-permissions.md](./工具权限.md) 填上了原本空缺的权限层，因此写入类工具现在会在执行前发起询问。`settings.yaml` 中的 `tools.permissions` 可以把任意工具钉死为 allow、ask 或 deny，这正是让一个套件能够确定性地触发一次审批提示、而不必寄望于模型恰好产生一次的原因。它也限定了触发方式：一个没有审批处理器的非交互式界面上，`Ask` 会退化为 `Deny`。打印模式正是这样一种界面——见 §6。
- **一次轮次会携带多次工具调用。** [parallel-tool-execution.md](./并行工具执行.md) 会并发运行相邻的只读调用，并承诺不会有任何可观察的变化：无论调度器做了什么，消息历史、Hook 顺序和审批提示都保持同样的顺序。这正是单元测试无法验证的一类主张，也使得批量回复从一个锦上添花的特性，变成了模型工具的一项硬性要求。

Portal 架构文档是现有浏览器套件及其与 API 部署冒烟测试之间刻意划分的权威说明；见 [contribute/architecture/portal.md](../contribute/architecture/portal.md)。

当前的部署冒烟测试工作流会在相关 Pull Request 上运行 Compose 和 kind。本设计改变了预期的策略：全面的部署与浏览器 E2E 必须移出必需的 PR 门槛，它们仍然作为合并后、按计划，以及手动派发的证据继续发挥价值。

## 4. 前提条件：确定性模型工具

下面的每一个套件都依赖一个模拟模型，而现有的那个撑不起它们。`deployment/smoke/mock-llm` 只应答一种线协议、回复一句写死的话，并且不保留任何状态。这对“一个 Task 完成了”已经够用；但它无法表达一次工具调用、一批工具调用、第二轮对话、一次拒绝，或者一次失败。而最重要的那些黄金路径——批准或拒绝一次工具调用、核实一次预期中的文件改动、恢复一次会话、在 Desktop 里处理一次审批——全都是多轮、带工具调用的路径。如果把这个模拟模型当作一个已经解决的原语，就会把最难的设计问题原封不动地藏进一行契约里，因此它是要第一个交付的部分，而不是留到后面才检视的细节。

这个工具必须满足以下要求。

| 关注点 | 必需行为 |
|---|---|
| 脚本化的轮次 | 一个场景文件为一次运行声明有序的回复序列：助手文本、带精确参数的工具调用、一种流式形状、一个提供商错误，或一份令牌/用量数据。模拟模型按顺序回放它们，绝不根据请求内容去推断回复。 |
| 一轮就是一批 | 一条场景条目可以携带多次工具调用，因为运行时现在会并发调度它们。一种假设“每轮只有一次调用”的格式无法表达 §6 要保护的场景，事后再去改造它会让每一份已提交的场景失效。 |
| 耗尽即失败 | 一个在脚本条目还没用完时就结束的场景，会让套件失败。这正是用来抓住那种提前一轮就不再调用模型的 Agent 的手段——没有任何针对最终输出的断言能看出这种错误。 |
| 每一种线协议 | 该模拟模型要服务 `internal/infra/llm` 中的全部三种协议——Anthropic Messages、OpenAI Chat Completions，以及 OpenAI Responses——按路由区分，每个套件声明自己跑的是哪一种。只支持单一协议的模拟模型会悄悄放过 [llm-provider-adapters.md](./LLM提供商适配器.md) 中描述的三个适配器里的两个，而那恰恰是提供商发生变化时最容易出问题的代码。 |
| 不需要容器 | 它对 CLI、Desktop 和 Go 层面的套件而言就是一个普通的 Go 进程，对 Compose 和 kind 而言则打包成现有的镜像。一份实现，两种打包方式；部署冒烟测试保持不变，包括它今天所断言的那句回复。 |
| 夹具与所属套件放在一起 | 场景文件提交在使用它们的套件旁边，不需要运行任何东西就能读懂，因此失败时可以对照保留下来的转录去读脚本来诊断。 |

这个工具属于测试支持代码，因此归属 `internal/testsupport`——生产代码不能导入它，`internal/architecture` 里的一个测试会强制这一点。那条规则只扫描 `internal/`，所以 `deployment/smoke/` 下那个把它打包成容器的很薄的 `main` 并不在扫描范围内，可以导入这个包。这是刻意为之，不是疏漏；如果以后要挪动这两部分中的任何一半，应当把这一点说清楚。

这个工具最终落地为 `internal/testsupport/mockllm`。它同时以阻塞和流式两种方式服务全部三种协议，一步只需描述一次回复，无论调用方以哪种方式获取它——需要在两者之间切换的套件不必写两份脚本。它的测试直接驱动 `internal/infra/llm` 里的真实适配器，因为拿一个手写的解析器去校验模拟模型，只能证明它和自己一致。

`deployment/smoke/mock-llm` 现在只是同一份代码的另一种打包，而不是第二份实现，所以一种回复形状对不对只需要在一个地方判断；部署冒烟测试可以通过挂载它来重放一个场景。它默认的场景会不断重复自己唯一的那一步：部署冒烟测试断言的是一次运行产出了什么，而不是产出它用了多少次模型调用。“重复”是需要显式开启的，原因也正在于此——在其它任何地方，跑过脚本末尾的调用才是需要被发现的问题。

## 5. 本地测试工具契约

每一个本地 E2E 套件都必须满足以下条件。

| 关注点 | 必需行为 |
|---|---|
| 确定性 | 使用上面的模型工具及其已提交的场景。不需要提供商 API key、付费模型、个人账号，或任何外部 SaaS。做不到这一点的就不是一个套件，而是一次手动演练，必须如实标注。 |
| 隔离 | 为每次运行创建临时的 `BUILDMAX_HOME`、工作区，以及唯一命名的测试资源。绝不使用贡献者真实的 home 目录、会话、凭据或工作区。 |
| 策略要写死，不能靠碰运气 | 依赖审批的套件要在其临时 `settings.yaml` 中用 `tools.permissions` 把工具钉死。靠猜模型会调用什么、或者靠某个内置工具当前的默认值去凑出一次审批提示，只会让套件在某天默认值因为好的理由而改变时突然失败。 |
| 测试数据 | 夹具辅助函数尽量通过公开边界创建所需的最小账号、角色、Space、Project 和内容，并清理自己创建的东西；如果某次部署必须保留证据，则要报告一个准确、安全的清理目标。 |
| 生命周期 | 一个套件既可以挂接到一个指定的、正在运行的部署上做诊断，也可以拥有自己一次性的本地部署生命周期。命令必须说明它选择了哪一种模式。 |
| 诊断信息 | 失败时保留 Playwright 的轨迹/截图、命令输出、脱敏后的 Server/Worker 日志、模型场景及其产生的转录，以及一条位于同一个可预期产出物目录下的简短复现命令。 |
| 可移植性 | 在 `tools/mk` 下添加任务运行器命令；不要另建一条依赖特定操作系统的 shell 脚本测试路径。平台特有的原生 Desktop 冒烟测试是一个明确的例外，它会报告自己不支持哪些平台。 |
| 时间 | 每个套件都要声明一个正常时长和一个超时时间，并遵守 §5.1 的预算。预检失败时要指出缺失的依赖或服务，而不是留到后面某个浏览器断言里才超时。 |
| 命名 | 命令名称要说明它是什么。`smoke` 曾经同时指三件不同的事——一次模型驱动的技能运行、一次确定性的部署检查，以及未来的 CLI 套件——所以模型驱动的那个现在叫 `./make agent-smoke`，并会在预检阶段就声明自己需要 API key。 |

### 5.1 时长预算

预算是设计的一部分，而不是事后才去衡量的结果。一个超出预算的套件本身就是一个缺陷：它原本要服务的那个反馈循环会因此停止被使用。

| 套件 | 正常时长 | 超时 | 为什么是这个数字 |
|---|---|---|---|
| CLI + TUI | 60 秒以内 | 3 分钟 | 它必须便宜到能被纳入默认的 `./make test` 循环。一个五分钟的 CLI 套件即便正确，也没人会去跑。这份预算涵盖了 §6 所需的伪终端路径，因此按算术推算，一个每次按键都要耗费数秒的终端驱动器就已经出局了。 |
| Desktop 桥接 | 5 分钟以内 | 10 分钟 | 一个 Wails 开发进程，加上少量流式交互。 |
| Portal + Compose | 10 分钟以内 | 20 分钟 | 包含把整套栈拉起来的时间；这是每日默认使用的部署方式。 |
| Portal + kind | 20 分钟以内 | 35 分钟 | 集群创建和镜像加载占了大头；只在涉及部署、Ingress、存储或 Worker 的改动时才运行它。 |

### 5.2 夹具隔离与挂接部署的对比

“每次运行都用唯一资源”和“挂接到既有部署”这两个既有做法方向相反，而现有的取舍是刻意为之：部署冒烟测试与 `./make e2e` 共用同一个固定账号 `deployment-smoke@buildmax.local`，把“已经存在”和“已经持有”都当作成功，并且带外传入一个一次性登录码——因为浏览器没法自己去取。Playwright 也因此用一个 worker 跑在同一个共享会话上。

因此这两种模式采用的是不同的规则，而不是一种折中：

- **自持生命周期。** 套件自己创建了这次部署，所以每个账号、Space 和资源在每次运行中都是唯一的，不需要任何清理——整个部署会被直接丢弃。
- **挂接模式。** 套件是一个访客。它沿用既有的固定诊断账号，只在其下创建唯一命名的资源并清理它们，并且绝不假设自己是唯一的客户端。它的命令输出会说明自己挂接到了哪个部署，以及留下了什么。

## 6. 黄金路径

最初的路径刻意保持数量少而有代表性。只有当一项新功能的跨界结果没有更低层、更快的测试可以覆盖时，才会为它新增一条 E2E 路径。

| 套件 | 初始黄金路径 |
|---|---|
| Portal + Compose | 登录；创建并使用 Space 资源；发起一次 Run；读取它的输出、轨迹和 Artifact；核实关键的、按角色区分的视图。Compose 是每日默认方式，因为它是最快的真实部署。 |
| Portal + kind | 通过 Ingress 和 Kubernetes Worker 路径证明同样的已发布构建产物契约成立。涉及部署、Ingress、存储或 Worker 的改动时在本地运行它。 |
| Server 与 Worker | 保留既有的直连与托管部署冒烟测试，再为取消、重试、授权拒绝和故障恢复补上部署层面的那一半——见 §6.1。 |
| CLI + TUI | 在一个隔离工作区里用模拟模型启动构建好的二进制文件；发送一条提示；批准并拒绝一次被钉死的工具调用；核实预期中的文件改动、会话恢复、轨迹，以及一次有用的失败信息。证明一次批量轮次会产生一份规范的历史记录和提示顺序。 |
| Desktop 桥接 | 用脚本化模型驱动已绑定的方法：创建一个 Project；流式接收一次响应；处理一次审批和一次拒绝；重新打开一个会话；并暴露一次提供商故障。它断言的是前端本应收到的那些事件，因为这就是 React 应用所能知道的全部。 |
| 原生 Desktop 冒烟测试 | 在受支持的原生 Runner 上启动打包好的应用，并证明一项关键交互可用。它的运行频率低于桥接套件，因为原生 WebView 因平台而异；它覆盖的是窗口、WebView 和 React 应用——这些都是桥接套件触及不到的部分。 |

Portal 路径应当优先使用语义化的无障碍定位器。不是被测对象的准备步骤可以使用夹具 API，但被断言的用户结果必须经过被测界面本身。这样既保留了既有的 Run 轨迹模式，又不至于让每一个准备表单都成为每一个断言的依赖。

**伪终端是必需的，不是可选项。** 审批是一种交互式能力：一个没有审批处理器的界面会把 `Ask` 退化为 `Deny`，而打印模式正是这样一种界面。所以 `buildmax -p` 能证明一次拒绝，却永远无法证明一次批准；CLI 套件最核心的那条路径——一个写入类工具发起询问、被批准、并改动了一个文件——只能在终端之下存在。打印模式仍然承载着所有未被闸门限制的部分：输出形状、会话持久化与恢复、轨迹内容，以及失败文本。这样拆分套件，正是为了让由终端驱动的那一小部分始终留在 §5.1 的预算之内：两个测试就能应答那次提示，其余部分则始终保持低成本。

伪终端背后并没有真的模拟器，所以这个工具要自己扮演这个角色，去应答 TUI 在启动时写出的能力查询。如果不去应答，每个测试都要多付出五秒钟去等 TUI 耗尽自己的超时——那看起来像是 Agent 变慢了，而不是终端根本不存在。

**Desktop 桥接需要一道接缝，这一点值得说出来。** Wails 是通过它内部某个包里的一个接口向前端发出事件的，因此这个模块之外没有任何东西能够替代前端。现在这个应用会通过自己的一层单行间接来发出事件，生产环境从不重新赋值它，而测试会用一个记录器去替换它。没有这一层，Desktop 界面就完全没有确定性覆盖——唯一的替代方案是跑一个 `wails dev` 加一个真实显示器，那是打包应用冒烟测试要做的事，而不是任何人在改代码时会去跑的套件。

**并发性必须被证明不会改变任何东西。** [parallel-tool-execution.md](./并行工具执行.md) 承诺无论调度器做了什么，可观察的行为都完全一致。一个批量场景——一轮里若干只读调用，以及一批把一个受闸门限制的写入和若干只读操作混在一起——会对照一份夹具去断言最终的消息历史、Hook 顺序和提示顺序。比这更低的层次都做不出这样的断言，因为它们都没有在真实的审批闸门之下运行真实的调度器。

### 6.1 Server 与 Worker 路径必须补上什么

取消、重试和授权拒绝已经有了处理器层面、跑在真实路由器和存储之上的 Go 测试。在这里重复它们的规则，正是这份设计所反对的“重建单元测试”。因此每条路径都必须点名一个处理器测试触及不到的部署层面事实：

- **取消**——信号真的送达了一次实时执行并让它停下来：一个正在运行的 Kubernetes Job 或 Worker 子进程真的结束了，而这次 Run 的终态与部署实际发生的情况一致。
- **重试**——第二次 Run 是真的被执行了，而不只是被记录下来：签发了一个新的 Run 令牌，第二个 Worker 真的运行了，托管路径也留下了归属到同一个用户和 Space 的第二条台账记录。
- **授权拒绝**——拒绝在部署边缘依然成立，要经过 Ingress 和已发布的路由，而不只是在被测的处理器内部成立。
- **故障恢复**——一个在一次 Run 进行到一半时就挂掉的 Worker，会让这次 Run 停在一个终态、可诊断的状态，其 Artifact 和日志仍然可以获取。

重试和授权拒绝最早是由部署冒烟测试覆盖的。取消现在也已经覆盖，§6.2 记录了具体做法——它所用的机制并不是本节最初提议的那个，而这背后的原因值得留存下来。故障恢复现在也覆盖了；§6.3 记录了具体做法，以及为什么部署只能证明其中由 Worker 自报的那一半，而其余部分由存储层的测试承担。

那个提议是让部署用的模拟模型支持不止一个场景，按一次 Run 所用的模型别名来选择。但它按原样根本造不出来：Portal 路径里没有任何东西是按 Run 去选择模型的。一个 Task 携带一段输入和一个可选的 `agent_id`；一个 `agentdef.Agent` 携带指令和插件，完全不携带模型。模型来自部署配置——`llm.default_model`，或者托管 Run 用的 `worker.llm.model`——因此栈里的每一次 Run 从结构上就注定会用同一个别名去应答。按别名选择场景就意味着要引入按次 Run 选择模型的能力，那是一个关于谁可以选模型、以及如何为此授权的产品决策，不是测试管线的事。这里的任何东西都不应该去逼出那个决策。

两个断言都是轮询而不是只读一次。一个 Task 会在它的 Run 输出可查询之前就报告 `SUCCEEDED`，所以只读一次会在一次一切正常的 Run 上失败；这种顺序是部署本身的一个特性，忽略它的断言测的是时钟，而不是系统。

### 6.2 故意让一次 Run 变慢

一个负向用例需要在一次 Run 仍在进行时对它采取动作。脚本化模型会立即应答，所以一个要求某次部署去取消一次 Run 的冒烟测试通常会发现它已经跑完了——而一个仅仅因为 Run 自己结束而通过的用例，什么都证明不了取消这件事。

因此，一次脚本化轮次的耗时是可以控制的，而且这也是关于一次轮次唯一可控的事情。一个步骤可以携带 `delay_ms`；而一个套件无法重新编排脚本的模拟模型——已经内置在一个镜像里、套件只能通过 HTTP 触达的那个栈——则可以用 `POST /control/stall` 拿到一次停顿。两者都不会从请求内容里推断任何东西。§4 定下的规则原样成立：一个会去猜自己被问了什么再作答的模拟模型，就不再是证据了。一次应答花了多久说明不了 Agent 做了什么，这正是它可以安全用作调节旋钮的原因。

这个停顿是带外武装的，并且会作用于此后的每一次回复，因此它没法只针对某一次 Run，甚至没法只针对某一个调用方。创建一个 Task 本身也要用到一次模型调用来生成标题，因此这次创建也会一并被停顿拖住；冒烟测试的做法是给这个创建请求一个足够耐心的客户端，而不是想办法在创建之后再去武装这次停顿。事后再武装会是明显更不稳定的选择：某次冒烟测试实测，从一个 Worker 生成到它的 Run 成功之间只间隔了 30 毫秒，而一个需要把一次 HTTP 调用精确插进这两个事件之间的用例，基本上就是在赌硬币。这也是为什么取消这个用例要放在部署冒烟测试的最后运行：一旦武装了停顿，后面的任何用例都会被这个模拟模型拖住，而不是被部署本身的节奏推进。如果某个用例需要把停顿只对准若干并发 Run 中的一个，那就需要另一种机制，应当明说，而不是依赖调用碰巧到达的顺序。

只有这个控制路由会在栈外部公开——Compose 下是一个发布出去的端口，kind 下是一条单独的 `Exact` Ingress 路径。模型协议本身则留在内网，因为一次 Run 能否到达它，正是这次冒烟测试要证明的一部分。两者都只存在于冒烟测试里；`deployment/production/` 下没有任何东西会暴露一个测试替身。

取消这个用例断言的，正是 §6.1 点名的那部分部署层面事实：这次 Run 到达了 `CANCELED` 而不是 `FAILED` 或者干脆没有终态；再次查询时它依然是 `CANCELED`；它列出的每一个 Artifact 都能下载。它**尚未**证明的是，取消之前产生的部分输出是否能留存下来，因为一次在第一次模型调用上就被停顿的 Run 根本没产生任何输出。这一半需要一个会先做一些事情、再触发停顿的场景，而这又需要把停顿对准某一次具体的 Run——见上文。

### 6.3 在一次 Run 进行到一半时丢掉 Worker

故障恢复这个用例（`tools/mk` 里的 `kindWorkerLossProbe`）把一次 Run 停在它的模型调用上，删掉正在运行它的 Kubernetes Job，然后断言这次 Run 到达一个点名 Worker 丢失的终态 `FAILED`，并且事后再查询时它的溯源信息仍然回答 `FAILED`。这正是 §6.1 点名、任何处理器测试都触及不到的事实：一次 Worker 已经消失的 Run，会停在一个可诊断的终态，而不是永远卡在 `RUNNING`，并且它的记录在这次丢失中存活了下来。

删除 Job 会通过 kubelet 用 `SIGTERM` 终止 Worker Pod，而 Worker 会捕获它并把这次 Run 报告为被中断。这是本部署里最常见的 Worker 丢失形态——一次滚动更新、一次驱逐、一个被排空的节点——所以它才是值得用一个部署断言去覆盖的那个。另一种形态,即一个 Worker 不作任何报告就消失（一次节点崩溃、一次内核 OOM 杀进程），则由服务端的存活性巡检来了结，而那条路径无法从这里复现：内核不会把容器内发给 Worker PID 1 的 `SIGKILL` 投递给它，而 kubelet 执行的任何有序删除都从 Worker 会据以自报的那个 `SIGTERM` 开始，因此这次 Run 总是会被它自己的报告在巡检的宽限期流逝之前先行了结。这个巡检由存储层的 `internal/server/scheduler/stale_runs_test.go` 里的 `TestReaperClosesRunsWhoseWorkerWentSilent` 覆盖；两条路径都会让这次 Run 落到本用例所断言的、同一个终态且可诊断的状态。

与取消不同，这个用例是在 Task 创建*之后*才武装停顿，而不是之前。它必须如此：创建一个 Task 本身要用一次模型调用来生成标题，一个事先就武装好的停顿会把创建拖住，而不是拖住 Run。它也能够如此：Worker 是调度器在创建返回之后才派发的一个 Job——Run 到达它的模型调用之前，那几秒的 Job 调度和 Pod 启动，正是一个足够从容的窗口去武装停顿，而 §6.2 里创建与运行近乎同时发生，根本没有这样的窗口。这个用例在删除 Job 之前仍会等待 `RUNNING`，因此它只对一个自己确实抓到、正在进行中的 Run 采取动作；一个已经先跑完的 Run 绝不会被误当成搁浅的 Run。

### 6.4 丢掉数据库

数据库中断探针（`tools/mk` 里的 `kindDBOutageProbe`）证明的是 Beta 就绪记录点名的依赖降级契约：当服务端在运行期丢掉数据库时，它通过 `/readyz`（System Status 管理视图读取同一批探针、如实镜像它）报告故障，并且是被移出 Service 而不是被重启，且一旦数据库回来它会自行恢复。这正是清单把就绪（`/readyz`，会 ping MySQL 并探测对象存储）与存活（`/healthz`，什么都不检查）分开背后的那个部署层面事实：一个在依赖中断时失败的存活探针会重启一个健康的服务端，把一次可恢复的中断变成崩溃循环。

中断数据库比听上去要费事。给 MySQL Pod 加一条 deny-all 的 `NetworkPolicy` 会拦住新连接，但服务端连接池里那条连接早已建立，而池没有设置任何生命周期，因此它会被无限复用、根本不会察觉这道拦截——`/readyz` 仍然就绪。所以探针还会弹一下 MySQL（一次优雅的 `mysqladmin shutdown`，之后 kubelet 会就地重启该容器，使其 emptyDir 数据存活），把那条已建立的连接打断；服务端随后的重连便撞上这条策略，中断一直持续到探针把它删除为止。选择拦截访问而不是删除 Pod，正是让「数据库恢复后正常服务随之恢复」成为一个真断言的原因：模式与数据行都还在，因此其后的一次登录会读写同一个数据库。探针直接从一个服务端 Pod 读取 `/readyz`，而不是经由 Ingress：一个未就绪的 Pod 会离开 Service，Ingress 会回它自己那条没有后端端点的 503，而不是应用那条点名了失败检查的 503；而恢复时的登录确实经由 Ingress，因为那才是「整条路径恢复」的主张。

这是运行期丢失的路径。在进程启动时丢失数据库是另一条、有意为之的快速失败：bootstrap 连接并迁移时不做重试，因此服务端会退出并崩溃循环，直到数据库可达为止。这种不对称是有意的——一个在启动时都够不到数据库的候选版本没有任何东西可服务——它不是本探针要演练的东西。

### 6.5 丢掉对象存储

对象存储探针（`tools/mk` 里的 `kindStorageDenialProbe`）是 §6.4 面向另一个有状态依赖的孪生：`/readyz` 会探测真实的桶可达性（用一个哨兵前缀调用 `persist.ListFiles`），因此当服务端在运行期丢掉对象存储时，`object_storage` 检查失败、Pod 被移出 Service 而不被重启，并在访问恢复后自行恢复——且桶内容完好。

中断需要与数据库相同的两步，原因也相同：给 MinIO Pod 加一条 deny-all 的 `NetworkPolicy` 会拦住新连接，但 S3 客户端那条已建立的 keep-alive 连接会被放行并复用，就绪探针因此察觉不到。MinIO 没有 MySQL 那种可借用的会话 kill，所以探针改为就地弹一下 MinIO——给它的 PID 1 发 `SIGTERM`，容器退出、kubelet 在同一个 Pod 里重启它，于是 emptyDir 上的桶存活，而服务端的重连则撞上策略。MinIO 重启很快且没有就绪门控，因此策略被移除时它已在重新服务，恢复只是一次快速重连。选择拦截访问而不是删除 Pod，正是让恢复能找到同一个桶的原因：丢掉 emptyDir 会留下一个没有桶的全新 MinIO，而正在运行的服务端——它只在启动时创建桶——不会去重建它。恢复后 `object_storage` 检查回到健康，本身就是桶带着内容回来的证据，因为该探针是去列桶而不是假定桶存在。

storage 被拒时 worker 的写路径——一次 Run 以运维者可理解的原因失败、且不留下声称某个缺失对象可下载的 Artifact 记录——是本探针未覆盖的另一种情形；它需要在 worker 的存储被拒时把一次 Run 驱动到一次 Artifact 写入，留待以后补充。

## 7. AI Agent 工作流程

这个工具是面向改代码的 Agent 的一等公民工具，而不只是 CI 的事后补充。一份面向贡献者的指南，以及工作区里的 `AGENTS.md`，必须告诉一个 Agent：

1. 哪个套件对应着被改动的子系统或用户流程；
2. 哪个命令可以安全运行，以及它是否会占用 Docker、kind、一个 Wails 进程，还是只用到一个临时目录；
3. 预期的耗时，以及这个测试所依赖的确定性夹具假设；
4. 失败产出物和脱敏日志在哪里；以及
5. 什么时候应该去跑一个更大的套件，而不是反复重试一个狭窄的套件。

一个 Agent 会从受影响范围最小的路径开始。它会在改代码之前先读一遍保留下来的产出物，修复被点名的那个边界，再重跑同一个套件。它不会用一次手动测试去搪塞一次 E2E 失败，也不会默认就去跑完整的矩阵。

操作手册本身是当前行为，而不是设计取舍，因此它放在 [`../contribute/testing.md`](../contribute/testing.md) 里，`AGENTS.md` 里只保留套件选择的摘要和一个链接。这份设计记录保留的是取舍本身；它绝不能变成操作手册。

## 8. CI 策略

| 触发方式 | 验证内容 |
|---|---|
| Pull Request | 只跑既有的快速检查。E2E 不是必需的门槛。 |
| 合并到 `main` | 部署与浏览器 E2E，失败时保留产出物。 |
| 计划任务 | 完整的直连与托管部署矩阵，外加当前 Runner 所支持的、平台原生的 Desktop 冒烟测试。 |
| 手动派发 | 为发布准备或某次疑似环境回归运行的任意昂贵套件。 |

路径过滤器可以决定合并后该跑哪个套件更划算，但绝不能把一次被策略跳过的 E2E 结果悄悄当作某条用户旅程已经通过的证据。工作流摘要必须把每个测试标注为已运行、被策略跳过、被取消，或者失败。

把 E2E 移出 PR 门槛是有代价的，这些代价必须被明确地承担，而不是留到日后才被发现。

- **并发不能再取消证据。** `deployment-smoke.yml` 目前按 `github.ref` 分组并设置了 `cancel-in-progress: true`，这在 Pull Request 上是对的，在 `main` 上却是错的：那里的 ref 是恒定的，所以第二次合并会取消第一次合并的验证，导致没有一次提交真正被证明过。合并后的任务要么不取消，要么按提交 SHA 分组。一次被取消的运行应当报告为“已取消”，而绝不能是“被策略跳过”。
- **`main` 变红需要一个负责人和一个截止日期——以及某种真正强制执行它的机制。** 一次合并后的 E2E 失败，由造成这次合并的作者负责排查；如果一个工作日内没有修复或回滚，就回滚这次合并。这条规则曾经只是写成了一句话、当成规矩发布出去，而它维持有效的时间，恰好等于碰巧有人在盯着它的时间：套件在一次合并上变红，并在之后的四次合并里持续保持红色，没有一次有理由被人注意到，直到一次无关的改动碰巧去看了那次运行。

  所以现在，红色状态会直接挡住下一次合并。`ci.yml` 里的 **Deployment smoke health** 任务会读取 `main` 上最近一次跑完的 `deployment-smoke.yml`，如果那次运行失败了，就让这个 Pull Request 也失败，并点名是哪次运行、哪次提交让它变红。它不对眼前这个 Pull Request 本身做任何验证——它只是拒绝在一个未经验证的 `main` 之上继续叠加改动，而这正是这条规则原本假定存在、却从未真正存在过的那种压力。用来修复该套件的 Pull Request 可以带上 `deployment-smoke-fix` 标签放行。

  另一种方案是把浏览器套件挪回 PR 门槛。那样可以更早抓住这次具体的故障，代价是每个 Pull Request 前面都要多排一次队——而且那把问题当成了“发现得太晚”，但真正的问题是没有人为一个大家都看得见的故障负责。
- **抖动的测试要被隔离，而不是重试。** 一个间歇性失败的测试要在当天就被移出门禁集合，并挂上一个 issue。不会引入无差别的重试：浏览器套件刻意把 `retries` 设为 `0`，因为一个被隐藏起来的抖动比一个显而易见的抖动更糟。
- **`gui` 包失去了它唯一的 PR 时刻覆盖率。** 这一点在这里是可以接受的，前提是替代方案足够便宜——而事实也确实如此：`gui` 现在有了自己的组件测试，前端任务会运行它们，所以一次共享组件的回归又能在合并前被抓住了。这个包仍然缺一个 lint 步骤，并且会一直被挡住，直到 typescript-eslint 支持它所使用的 TypeScript 版本。

## 9. 交付顺序

1. **构建确定性模型工具。** 脚本化的多轮场景、批量工具调用、全部三种线协议，既能作为普通进程运行，也能打包成既有的镜像。任何涉及工具调用的套件都要等它先落地。
2. **在各个界面里优先加上 CLI 路径。** CLI 是主要的单二进制界面，今天完全没有确定性验证，而且它是唯一一个不需要 Docker、几秒钟就能跑完的套件——所以它才是真正能兑现这份设计所追求的反馈循环的那一个。真实的二进制文件、临时的 home 目录、钉死的权限、脚本化的模型；打印模式覆盖不受闸门限制的路径，再加一个小型伪终端套件覆盖审批和 TUI 特有的行为。如果把它排在容器相关的套件之后，就会推迟这项工作真正的意义所在。
3. **稳定既有的 Portal 与部署套件。** 如果有两个人手，这一步可以和第 2 步并行：在上述两种生命周期模式下都做到夹具隔离、清理、可复现的产出物、预检诊断，以及在既有的挂接部署模式之外再加一个自持生命周期的本地封装。把全面的工作流从 PR 门槛挪到合并后、计划任务和手动触发，并在同一次改动里修好 §8 里点名的并发和责任归属规则。
4. **加上 Portal 的黄金路径**，覆盖 Issue/Agent 执行、Workflow 执行、文件、设置，以及成员/所有者/系统管理员的授权矩阵。让原有的 API 冒烟测试继续专注于部署行为，把 §6.1 里那些部署层面的断言交给 Server 与 Worker 路径。
5. **加上 Wails 桥接套件**，再在受支持的平台 Runner 上加一个小型原生打包应用冒烟测试。**已完成。** 桥接套件已经以 `internal/interface/desktop` 里的 `TestBridge*` 落地，由 `./make e2e desktop` 运行。

   此后又落地了第二个套件 `./make e2e desktop-ui`：它通过 `wails dev` 自带的浏览器开发服务器（见 tools/mk/desktop_ui.go），驱动 desktop/frontend 里真实的 React 应用及其绑定的 Go 方法。它覆盖的是 React 应用和桥接层两者的组合，跑在一个真实（尽管是以无头方式启动）的 Chromium 上——它比这一步最初的要求要窄，而且是刻意的：它说明不了原生窗口会如何渲染同一个页面，也说明不了那个已签名、已打包的构建产物是什么样子。`wails dev` 启动时确实也会顺带打开一个原生窗口，但这个套件不对它做任何断言。

   打包构建启动冒烟现已在 macOS 与 Windows CI 中，于 `./make build desktop` 后运行 `./make e2e desktop-launch`。它证明打包进程可以启动并在短暂观察期内保持运行，但不会驱动窗口或断言其渲染内容。

   这一步后来发现还有一个本记录当初没有点名的前提条件。在 `desktop-package.yml` 出现之前，**根本没有任何 CI 任务产出过一个打包好的应用**：`go build ./...` 只会通过构建标签里 `!desktop` 的那一半去编译 desktop 相关的包，而前端任务构建的 `desktop/dist` 从未被嵌入进去过。在有东西先把它构建出来之前，冒烟测试根本没有可以启动的对象，所以这一步的前半部分其实是构建本身——现在会在合并后、每周，以及按需在 macOS 和 Windows 上通过 `./make build desktop` 运行。

   签名并不属于这个前提条件的一部分，这一点值得单独说明，因为乍看之下容易让人以为它属于。Gatekeeper 会拒绝一个带着下载隔离属性到达的应用包；而一个在同一台机器上构建并启动的应用包没有这个属性，这也是为什么 `./make build` 之后紧跟 `./make run desktop` 是文档记录的贡献者路径。一台 Runner 面对的情形是一样的。签名和公证把守的是**分发**环节——这也是 `.goreleaser.yaml` 不打包这个应用、构建任务也不发布任何产出物的原因——它们把守不到冒烟测试这一关。

   托管的 macOS 与 Windows 任务现在已经回答了启动问题。原生窗口的视觉交互属于另一种成本更高的测试，不包含在这次冒烟声明中。
6. **在 `docs/contribute/` 下发布面向贡献者和 Agent 的操作手册**，包括套件选择、前提条件检查、产出物位置，以及发布时使用的全矩阵命令。已经以 [`../contribute/testing.md`](../contribute/testing.md) 的形式落地，`AGENTS.md` 里只保留摘要和链接，`./make e2e all` 则充当那个矩阵命令。

对模型驱动的 `./make smoke` 改名这件事，搭上了第 3 步的顺风车。给 `gui` 补测试搭上了第 4 步的顺风车——因为正是从那时起 Portal 的路径开始依赖这些共享组件；它的 lint 步骤仍然被挡住，直到 typescript-eslint 支持它所构建的 TypeScript 版本。

## 10. 成功标准

当一名开发者或者一个 AI Agent 能够从一份干净的检出开始，不需要任何隐藏凭据就能选中相关的本地套件，在不触碰个人数据的情况下执行它，并拿到足够修复一次失败的留存证据时，这个方向就算完成了。具体来说：

- 没有任何套件需要提供商 API key，也没有任何名字听起来像测试的命令会悄悄需要它；
- CLI 套件能在默认的 `./make test` 循环里、在预算之内跑完，包括那条由终端驱动的审批路径；
- 一次批量轮次被证明只会产生一份规范的历史记录和提示顺序；
- 每一次合并后的运行都会把每个套件报告为已运行、被策略跳过、被取消，或者失败，不会有任何一次提交带着一次被悄悄取消的验证走向发布；
- 一次失败会交回对应的场景、转录、脱敏日志，以及一条可以复现它的命令。

Pull Request 的延迟仍然由那些快速检查决定，而合并后与计划中的运行会持续验证更广泛的部署主张和原生界面主张。
