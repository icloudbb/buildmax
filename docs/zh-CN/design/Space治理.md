## 1. 决策

P4 应把 BuildMax 现有的 Space 控制能力，转化为一套适合私有 Space 运营的
实用治理基础。

已经具备的基础包括：

- Space 角色：`owner`、`admin`、`member`
- Space 级配额服务
- Space 用量端点
- 集中式的处理器授权辅助逻辑
- Workflow 生命周期：`draft`、`published`、`archived`
- Workflow 分配与运行检查

剩下的工作不是打造一整套庞大的企业策略平台，而是让现有的控制手段变得
足够可见、可测试、可追溯，从而让 Space 管理员能够信任共享自动化。

## 2. 产品目标

管理员应当能够清楚了解：

- 谁能做什么
- 受治理的共享资源有哪些
- Space 当前占用了多少容量
- 哪些 Workflow 处于草稿、已发布或已归档状态
- 敏感资产随时间发生了哪些变化

产品应当在不强迫用户面对沉重管理控制台的前提下，建立起这种信心。

## 3. 当前基线

后端锚点：

- 角色定义在 `internal/core/space/space.go`
- 角色/动作决策在 `internal/core/space/policy.go`，由
  `internal/server/access` 中的 `Guard` 应用到具体请求
- 配额服务在 `internal/service/quota/service.go`
- 配额路由在 `internal/server/handlers/space/usage.go`
- Workflow 生命周期在 `internal/core/workflow/workflow.go`
- Workflow 生命周期的执行约束在 `internal/service/workflow/service.go`
- Space 持久化在 `internal/infra/db/space.go`
- 默认配额层级的初始化在 `internal/infra/db/quota_tier.go`

前端锚点：

- Space 设置在 `portal/src/pages/settings/SpaceSettings.tsx`
- 共享设置 UI 在 `portal/src/pages/settings/shared.tsx`
- Workflow 页面在 `portal/src/pages/workflows`
- Issue 分配 UI 在 `portal/src/pages/issues`

当前的动作模型：

- `owner` 管理 Space 成员。
- `owner` 和 `admin` 管理 Agent、Workflow 以及 Workflow 分配。
- `owner`、`admin`、`member` 都可以运行 Workflow。

## 4. 主要缺口

### 4.1 治理不够可见

后端已经有角色和检查逻辑，但 UI 需要向管理员更清楚地说明：

- 每个角色分别意味着什么
- 某个操作为什么不可用
- 哪些 Workflow 状态可以运行
- 当前的 Space 用量和配额限制

### 4.2 权限边界需要更全面的测试 —— 已解决

**这项缺口已经解决。** 现在有一套矩阵会驱动真实请求经过 mux，分别以
owner、admin、member、其他 Space 的 member 以及匿名调用方的身份发起调用，
覆盖服务器注册的每一条 Space 级路由。之所以要驱动真实请求，而不是只对
授权辅助函数做单元测试，正是因为角色规则本身现在已经由 `core/space.Allows`
唯一实现，并配有自己的表驱动测试；这套矩阵要证明的是另一半——每条路由
是否真的去问过它。一条规则即便有唯一的实现者，如果某条路由从不咨询它，
这条路由依然是敞开的。为此还有第二项测试，会读取每一条路由注册：一旦某个
Space 级路由没有对应条目就会失败；一旦某个条目指向的路由已经不存在，
也会失败——因为一条失效的记录看起来会像是覆盖到了，其实并没有。

这套测试要证明的是：

- member 不能修改共享的自动化资产
- admin 不能执行涉及所有权的成员管理操作
- owner 可以管理成员
- Workflow 生命周期限制始终一致地生效
- Space 级资源不会跨 Space 泄露

### 4.3 Workflow 生命周期需要产品层面的打磨

生命周期本身已经存在，但在 Portal 中应当让用户一目了然：

- `draft`：可编辑，但不能被分配或运行共享工作
- `published`：可分配、可运行
- `archived`：保留作历史记录，不用于新工作

UI 不应该让用户靠请求失败去摸索这些规则。

### 4.4 敏感资产不可追溯 —— 已解决

**该缺口已经关闭。** 在会影响 Space 运行的共享资产当中：

- Space 成员及其角色 —— **已记录**
- 保存了服务商凭证的模型目录 —— **已记录**
- Space 创建及其配额层级 —— **已记录**（`space.created`）
- Webhook 密钥 —— **已记录**（`webhook_key.created`、`webhook_key.revoked`）
- Agent 定义 —— **已记录**（`agent.created`、`agent.updated`、`agent.deleted`；
  恢复历史版本视为一次更新）
- Workflow，包括发布和归档 —— **已记录**（`workflow.created`、`workflow.updated`、
  `workflow.published`、`workflow.archived`、`workflow.unpublished`）

第一批之所以选中这些资产，是按照“一旦泄露会造成多大损失”来衡量，而不是按变更
频率：成员变更会让人拿到 Space 内一切资源的访问权，目录变更则会改变提示词的去向
和支出。第二批就是剩下的这些——每一项只需要在变更点加一次 `Record` 调用，再加一个
永久性的动作字符串。

配额层级被承载在 `space.created` 的 detail 里，那里决定了一个 Space 起始的层级。
之后的变更属于系统管理员，而不属于任何 Space 角色：它被记录为
`space.quota_tier_changed`，带有新旧层级——见 [系统管理](./系统管理.md) §7.2 和
开放问题 4。

## 5. 范围内事项

### 5.1 Space 配额 UI 与文档

让配额出现在管理员会去查看的地方：

- 当前 Space 用量
- 层级名称
- 滚动周期
- 运行次数限额
- 令牌限额
- 超限后的行为

需要写明文档的内容：

- 配额是按 Space 计算的
- 个人使用由默认的个人 Space 表示
- 创建 Task 或重跑时检查的是当前活动 Space

### 5.2 角色与权限边界测试

为服务器处理器和服务添加一套表驱动的权限矩阵。

至少要覆盖的动作：

- 管理 Space 成员
- 创建/更新/删除 Agent
- 创建/更新/发布/归档 Workflow
- 把 Issue 分配给 Workflow
- 运行 Workflow
- 读取 Space 资源
- 创建普通工作

### 5.3 Workflow 生命周期 UI

打磨 Workflow 列表/详情页的文案和控件：

- 展示生命周期徽标
- 用清晰的文案禁用不可用的操作
- 把已归档的 Workflow 从默认分配选项中隐藏
- 保持已归档 Workflow 仍可查看
- 让发布/归档的状态切换变得明确

### 5.4 小型审计/事件模型 —— 已交付

`internal/core/audit/audit.go` 中的 `audit.Event` 就是已交付的形态。它与
本节最初的构想有三处不同，而这三处不同都是有意为之的决定，不是执行时的
走样：

- **用 `ActorType` 加 `ActorID`，而不是 `ActorUserID`。** Worker 和系统
  本身也会执行有意义的动作，为它们发明一个用户 ID 反而更麻烦，不如直接
  给行为主体加上类型。
- **没有 `MetadataJSON`。** 自由格式的 JSON 列最终会变成提示词、请求体
  和凭证的藏身之处。`Detail` 是一段简短、不敏感的说明——比如一个角色名、
  一个模型别名——仅此而已。
- **`SpaceID` 可以为空。** 登录并不属于某个 Space，如果强行要求非空，就
  等于要为登录事件凭空发明一个 Space。
- **`TaskRunID` 可以为空。** 它标识某个动作是代表哪一次运行而执行的（如果
  确实有的话），从而让一次运行所引发的受治理动作能够从运行侧被追溯到。见
  第 5.9 节。

这类事件不携带提示词、不携带生成内容、不携带工具输出，也不携带凭证，
只记录谁对哪个对象做了什么。运行诊断信息保存在持久化的运行轨迹里，
按次调用的计费信息保存在 `llm_call` 账本里，因为它们是不同的问题，
有着不同的保留策略。

`Store` 接口是只追加的——没有更新，也没有删除，因为一条可以被编辑的
记录算不上证据。动作字符串会被持久化，因此也就是永久性的：重命名一个
动作字符串，会改写所有按它筛选的读者所看到的历史。

动作列表以 `internal/core/audit/audit.go` 里的 `const` 块为准，那是唯一的
事实来源；它一开始只有身份和模型目录相关的动作，现在也覆盖了第 4.4 节的
第二批。有两条规则值得说给任何想扩展它的人听：登录失败被刻意排除在记录
之外，因为它说明不了行为主体到底是谁，记录下来只会让这条轨迹变成一个可以
随意写入任意字符串的地方；而 `access.denied` 恰恰是唯一一个在失败时记录的
动作，因为一次拒绝正好说明有人在试探边界。

写入失败时，只会记录日志并放弃这次写入，而不会让触发它的那个动作
本身失败。这是一个明确的决定，不是一个缺口：如果因为写入失败就拒绝
执行动作，就等于让一次日志系统的故障演变成了它本应记录的那件事情的
故障。这确实是一个真实的局限，`manual/support.md` 里也写明了——这条
轨迹记录的是数据库可达期间发生的事情，这和"保证每个动作都被记录"
并不是一回事。至于是否应该有某个动作改为事务性写入，属于开放问题 2
尚未解决的部分。

### 5.5 事件可见性 —— 已交付

`GET /api/spaces/{space_id}/audit-events` 按时间倒序、支持
limit/offset 分页地提供某个 Space 的审计轨迹，Portal 把它渲染成 Space
设置里的一个审计区块（`portal/src/features/audit/`）。

无论在 API 还是 UI 里，它都是**仅限 owner** 可见的。这条轨迹记录了谁
做了什么，包括谁被拒绝了什么，这属于管理性信息而非协作性信息——一个
member 并不需要看到某位同事被拒绝了某个操作。这就回答了开放问题 1。

### 5.6 保留策略 —— 已交付

`server.yaml` 中的 `audit.retention_days` 会让超出窗口期的事件过期。
它默认是 **0**，也就是保留所有内容，因为一个从未主动选择过策略的部署，
并不等于它已经决定要丢弃证据。

这项清理任务是 BuildMax 中唯一会删除审计事件的地方，专门收窄的
`AuditPruneStore` 接口就是为了保证这一点：轨迹的每一个读者和写者持有的
都是 `AuditStore`，谁都碰不到删除操作。没有任何手段可以删除*某一条特定*
记录——这项清理任务只接受一个截止时间和一个批量大小，这就是它全部的
"词汇量"。

每一次真正删除了内容的清理，都会写入一条 `audit.pruned` 事件，写明
被清理的时间范围和数量。正是这条记录，让"删除"这件事本身变得站得住
脚：一条从中途才开始的轨迹，必须能说清楚是策略缩短了它，还是有人把它
截断了，否则这两种情况看起来毫无区别。这条事件本身的时间晚于产生它的
那个截止时间，所以它不会被自己触发的这次清理删掉；等到窗口期推移到
把它也纳入范围时，后续的清理会用同样的方式为那段时期留下记录。

这就回答了开放问题 6：保留策略是配置项，默认选择保留，由部署这一层
决定，而不是由某个 Space 决定。

### 5.7 导出 —— 已交付

`GET /api/spaces/{space_id}/audit-events/export` 让 Space 的 owner
能拿到自己的轨迹，`GET /api/admin/audit-events/export` 让系统管理员
能在同样的过滤条件下拿到整个部署的轨迹。两者都以流式方式输出 CSV
或 JSONL。

有三个决定值得记住：

- **它是拉取，不是推送。** 开放问题 8 曾问过，导出是否需要"至少一次"
  投递语义，以及消费者要如何发现缺口。一个由用户主动下载的文件不存在
  这两个问题，先交付拉取模式,意味着事件的形态不需要在任何人能拿到
  数据之前就完全定型。将来若要做推送集成，仍然要回答问题 8；拉取模式
  不需要。
- **Space 级路由不接受过滤条件。** 导出的目的是把记录留存到别处，而
  在导出途中加上的过滤条件，恰恰是这份文件本身无法体现出来的一个决定。
  管理员路由则接受过滤条件，因为在那个场景下，过滤只是运维人员在收窄
  一份他本来就有权限查看的数据。
- **导出这个动作本身会被记录**，记为 `audit.exported`，并写明实际
  导出的条数，以及是否触达了上限。完整地读取这份记录本身就是对它的一次
  操作；一次不留痕迹的导出，会成为唯一一种能够查阅轨迹却不出现在轨迹里
  的方式。如果一次管理员导出被限定到某个具体 Space，这次导出也会被记进
  那个 Space 自己的轨迹里，这样它的 owner 就能看到部署方读取过这份数据。

分页使用的是键集游标，而不是偏移量。一次导出要跨越多轮请求才能读完，
而在此期间记录会不断在一端追加，也会因为保留策略在另一端被移除，
无论哪一种都会让它后面的所有偏移量整体错位——对于一份用作证据的导出
而言，漏掉一页是最糟糕的一类缺陷，因为这份文件表面上看起来仍然是完整的。

### 5.8 配额告警 —— 已交付

`QuotaService.Check` 会记录两类动作：当一个 Space 的用量超过限额的
80% 时记录 `quota.threshold_reached`，当工作因超限被拒绝时记录
`quota.exceeded`。这两类之所以分开，是因为它们需要不同的应对方式——
一个是提醒，另一个是工作确实没有执行。

这两类事件在每个周期、每项限额下最多只写一次，去重的依据就是轨迹本身，
这样一个不停提交工作的 Space 就不会把自己的记录变成一份重试日志。行为
主体记的是系统，而不是恰好把总量推过线的那个提交者：配额是属于整个
Space 的,把最后一个提交工作的成员记成主体,会显得像是在为一个共享预算
去归咎某个人。

这项检查必须放在准入路径上完成。用量是一个滚动窗口，因此不存在某个
明确的周期边界,可以让一次定时扫描发现某个 Space 恰好停在 80% 上。无论是
读取还是写入这条记录,都不能反过来影响准入决策——即便审计表不可达,
部署也必须照常运行工作,也必须照常执行限额。

Portal 会在 Space 设置里用同样的用量数据展示相同的信息。那是即时的答案；
这条轨迹才是持久的答案。

### 5.9 运行关联 —— 已交付

事件带有一个可选的 `task_run_id`：某个动作是代表哪一次运行而执行的（如果确实
有的话）。它回答了开放问题 7——从一条审计事件出发的调查，现在可以到达引发它的
那次运行；反过来，一次运行所引发的每一个受治理动作，也就成了对轨迹的一次筛选。

它的存储方式与行为主体和目标相同：一个不透明的公开句柄，而不是外键。轨迹刻意不
与执行面做联接，执行面的行有自己的保留策略——因此一次已经被清理掉的运行不会破坏
证据，而到达该运行的轨迹与 `llm_call` 账本靠的是这一个 id，而不是联接。一个架构
测试把这一点记录为数值引用规则的一个有意例外。

它由上下文填充，而不是由每一个调用点填充。一个运行范围内的 Worker 请求会在
Worker 中间件里被一次性打上它所属的运行标记，于是该路由下游记录的任何事件——
Worker 上传一个 Artifact、网关在服务某次运行时触及配额——都会继承这个 id。一个
显式命名了运行的事件会保留它自己的 id，因为一个比环境上下文更了解运行归属的调用
方,不应该被上下文覆盖。人直接执行的动作不带运行标记,而这些正是大多数动作。

它不会做的是把运行强行安到本就没有运行的动作上：登录、成员变更、模型目录编辑都
不是由运行引发的,因此它们保持无关联,而不是被赋予一个它们本就没有的运行。

## 7. 权限矩阵

建议的初始矩阵：

| 动作 | Owner | Admin | Member |
|---|---:|---:|---:|
| 查看 Space 资源 | 是 | 是 | 是 |
| 创建 Issue/Conversation 工作 | 是 | 是 | 是 |
| 运行已分配的 Workflow | 是 | 是 | 是 |
| 管理 Agent | 是 | 是 | 否 |
| 管理 Workflow | 是 | 是 | 否 |
| 把 Issue 分配给 Workflow | 是 | 是 | 否 |
| 管理 Space 成员 | 是 | 否 | 否 |
| 修改成员角色 | 是 | 否 | 否 |
| 查看 Space 用量 | 是 | 是 | 是 |
| 修改配额层级 | 否 | 否 | 否 |
| 查看活动事件 | 是 | 是 | 否 |

这份矩阵刻意保持简单。如果未来企业客户确实需要更精细的控制,应当基于
实际观察到的需求去构建,而不是现在就去发明一套自定义 RBAC。
修改配额层级不属于任何 Space 角色：层级是部署的容量,所以由系统管理员分配
（[系统管理](./系统管理.md) §7.2）。

## 8. 后端计划

### M1. 权限测试 —— 已完成

按第 4.2 节给出的理由,这项工作最终交付成了一套路由矩阵,而不是围绕角色
判定函数写的测试:因为判定函数本身没法证明某条路由确实咨询过它。服务器
注册的每一条 Space 级路由,都有一行记录写明谁可以调用它;这些记录会被
当作真实请求,针对五种调用方(包括另一个 Space 的 member)分别驱动执行,
一条没有记录的路由会导致构建失败。

验收目标已经达成:权限矩阵由测试强制执行,一条新的 Space 级路由如果没有
人明确决定谁可以调用它,就无法上线。

### M2. 治理服务边界

目前这个处理器辅助函数作为第一版是可以接受的。如果动作检查逻辑继续
扩散蔓延,再把这部分策略挪进一个小型的服务/包里。

目标 API：

```go
type SpaceAuthorizer interface {
	Authorize(ctx context.Context, spaceID, userID string, action SpaceAction) (role string, err error)
}
```

保持这套东西朴实无华：不要引入策略 DSL。

### M3. Space 事件存储 —— 已完成

已交付为 `internal/core/audit` 中的 `audit.Event` 和 `audit.Store`
（`RecordAuditEvent`/`ListAuditEvents`），并由 `internal/infra/db` 中的
`auditEventRow` 持久化到单数命名的表 `audit_event` 里。最终定名为
*audit*（审计）而不是*space event*（Space 事件），是因为登录并不属于
任何 Space，而这条轨迹本质上是证据,不是一份活动动态流。它的具体形态,
以及从最初构想中被砍掉的部分,见第 5.4 节。

### M4. 事件写入 —— 已完成

事件是在变更成功之后才写入的。写入失败时只记录日志并放弃这次写入,
所以一条治理记录永远不会导致它所描述的那个动作本身失败——这个取舍
在第 5.4 节和 `manual/support.md` 里都写明了,而不是留给运维人员在
排查事故时才意外发现。当初设想的紧凑 JSON 元数据方案没有沿用下来:
现在没有元数据列,只有一个简短的 `Detail` 字符串。

### M5. 事件 API —— 已完成

已交付为：

```text
GET /api/spaces/{space_id}/audit-events
```

授权规则是**仅限 owner**,比这里最初设想的 owner/admin 更窄,原因见
第 5.5 节。响应体是 `{"events": [], "total": 0}`,支持 limit/offset
分页。

## 11. 风险

- **治理引入得太早、太重**：在基础的可追溯性落地之前,先避免引入
  自定义角色和审批流程。
- **审计噪音**：第一批只记录真正有意义的敏感动作。
- **动作与事件不一致**：保持事件动作名称稳定,并写入文档。
- **UI 杂乱**：只在设置页和 Workflow 页面里体现治理信息,不要到处都是。
- **事件静默失败**：记录事件写入错误时要带上足够的上下文。

## 12. 开放问题

1. ~~member 是否应该能查看 Space 活动,还是应该仅限管理员？~~
   **已决定：仅限 owner**,比这两个选项中的任何一个都更窄。这条轨迹
   记录了谁被拒绝了请求,这是管理性信息——见第 5.5 节。
2. ~~事件写入应该尽力而为,还是对敏感动作而言必须成功？~~
   **已决定：尽力而为**,`internal/service/audit` 里带着这个理由:
   如果因为一次审计插入失败就拒绝登录,就等于把一次日志系统的故障
   变成了一次身份验证的故障。写入失败会以 error 级别记录下来,带上
   动作和行为主体,所以一次被丢弃的事件仍然会在别处留下痕迹。真正
   悬而未决的问题范围更窄——是否存在某个*单独*的动作,值得用一条
   必须成功的记录、并且和它描述的那个动作放在同一个事务里去写。
   [系统管理](./系统管理.md) §9 提出,授权类动作恰恰是"尽力而为"
   这个策略最薄弱的地方,因为一次已经生效却没有被记录下来的授权,
   正是事后调查最需要的那种记录。要回答这个问题,就要先决定:当动作
   成功而记录没有成功时,调用方应该看到什么。参见第 5.4 节。
3. Workflow 的发布/归档应该要求 owner,还是允许 admin 也能做？
4. ~~配额层级变更应该在 P4 里实现,还是先只写文档？~~
   **已实现**为系统管理员的层级分配,而不是 Space 所有者的动作；见
   [系统管理](./系统管理.md) §7.2。
5. Webhook 密钥的创建/吊销是否应该仅限 owner/admin？

剩下的问题来自已经退役的《审计与数据治理》提案。它给出的建议方向——
先做一套内部的 Space 账本,再做导出——正是最终交付的方案;下面这些是
这个方案交付之后仍未解决的部分：

6. ~~审计事件适用什么样的保留策略,这是配置项,还是运维责任？~~
   **已决定：是配置项,默认保留所有内容**——由 `audit.retention_days`
   控制,由部署这一层应用,而不是由某个 Space 应用,并且每一次清理
   都会记录自己删除了什么。见第 5.6 节。
7. ~~有哪些关联标识符,可以把 Task、Worker、模型调用和 Artifact 关联
   起来？~~ **已回答。** 一次运行的轨迹和它产生的 `llm_call` 记录本就已经
   在 Portal 的运行详情里被并排展示;现在审计轨迹也通过事件所携带的可选
   `task_run_id` 与它们关联了起来。从一条审计事件开始的调查可以追溯到触发
   它的那次运行,而一次运行引发的每一个受治理动作也成了对轨迹的一次筛选。
   这个 id 由运行范围的上下文填充,而不是由每个调用点填充,也不会被强行安到
   本就没有运行的动作上。见第 5.9 节。
8. ~~导出是否需要"至少一次"的投递语义,消费者又该如何发现缺口？~~
   **被绕开了,没有真正回答。** 第 5.7 节交付的是拉取式导出,这两个
   问题对它都不成立。这个问题对未来任何推送式集成仍然成立,而且在
   "尽力而为"的写入策略下(开放问题 2),缺口本身也未必总能和"什么都
   没发生过"区分开。
9. 谁可以读取运行轨迹、Artifact 和模型用量数据？审计轨迹这一层的答案
   已经定了;但这三者本身从未被放在一起统一决定过,而且它们承载的
   信息比审计轨迹更多——比如一份轨迹里就包含工具输出。
10. 一个 Space 能获得哪些删除控制手段？目前既没有导出/导入命令,也没有
    任何手段能删除一个 Space 的记录,所以"删除我们的数据"这个诉求,
    除了把数据库和对象存储整个丢弃之外,没有别的答案。
