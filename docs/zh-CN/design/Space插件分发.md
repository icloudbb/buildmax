## 1. 决策

一个 Space 可以为其后台 Run 激活已发布的插件版本。一条激活记录精确指定
插件、版本、摘要三者；Worker 会验证后，把与之完全一致的内容物化到该次
Run 专属的 `BUILDMAX_HOME` 中。在 Run 启动过程中，绝不会去解析"最新版本"
是什么。

激活规则按内容能做什么来划分，而不是按内容的作者是谁来划分：

- **指令类内容**——技能（skill）和子 Agent——只需由 Space 的所有者或管理员
  激活即可。它们会引发工具调用，而每一次由此引发的工具调用仍然要经过工具
  权限、Hook 门控和沙箱的检查。
- **可执行内容**——Hook 和 MCP 服务器——还需要一名系统管理员把该版本标记为
  "可用于无人值守场景"。它们会在运营方拥有的基础设施上启动进程、建立连接，
  而只有运营方才能在跨 Space 的层面上权衡这种风险。

激活是 Space 对"哪些插件可以被使用"作出的决定。而在今天，实际"使用"哪个
插件是由 Agent 定义决定的；第 16 节会加入未来的 Task 范围环境，它可以在
不修改 Agent 或 Space 的前提下，从已获准的目录中再选取插件。一次 Run 只
加载为它记录下来的那个不可变环境，插件不会仅仅因为被某个 Space 激活过就
自动进入某次 Run。参见第 5.3 节和第 16 节。

并不是每个 Space 都愿意去逐项维护插件列表。Space 可以在两种模式之间
选择：**策展（curated）模式**下，由管理员逐个激活插件；**开放（open）模式**
下，整个目录都可以被引用，激活记录会在 Agent 第一次引用某个插件时自动创建。
开放模式是默认值。两种模式最终产生的都是同一种被固定住（pinned）的记录，
区别只在于由谁来填写这份列表，而不在于是否存在这份列表。参见第 4.1 节。

密钥的分发被有意排除在本设计之外。一条激活记录只说明某个发布版本会读取
哪些环境变量；实际提供这些变量的值，需要另一份独立的记录和独立的信任边界。

## 2. 已经跨越这条边界的内容

这个问题其实比看起来要窄，因为 Space 的内容已经能够到达 Worker 了。

`internal/agentapp/taskrun` 会把 Space 持久化的 `home` 物化到 Run 目录里，
而 `WriteRunAgentsMd` 会把该 home 目录下的 `AGENTS.md` 提升为工作区自己的
`AGENTS.md`。也就是说，一个 Space 已经可以在它派发的每一次后台 Run 前面
放置任意指令，不需要激活、不需要审查，除了文件本身之外也不留下任何记录。

这种"提升"就是全部的现状，但值得说清楚它的边界，因为本文其余部分都建立在
这个边界之上。Space 的文件落在 `<run>/home` 下，而工作区的 Hook 是从
`<run>/.buildmax/hooks.yaml` 中读取的，所以今天一个 Space 的 home 目录
虽然能为一次 Run 贡献提示词，却不能为它贡献一个 Hook。指令性内容到达
Worker 早已不是新鲜事，可执行内容到达 Worker 才是。

所以本设计要守护的边界并不是"Space 的内容到达了 Worker"，而是**会执行的
Space 内容到达了 Worker**。一项技能是 Agent 可能会读到的文字；一个
`command` Hook 是无论 Agent 是否读了任何东西都会运行的程序。要求技能比
产品对 `AGENTS.md` 已有的要求承担更多仪式性步骤，本身就是不自洽的，这
正是第 1 节按这条线来划分的原因。

还有另外两个事实约束着这项工作：

- Worker 的 `BUILDMAX_HOME` 是每次 Run 都新建的（`RuntimeTaskRunGlobalDir`），
  所以它的插件目录一开始是空的，今天没有任何插件会被加载。这也是 Marketplace
  在发布时没有触及 Worker 的原因。
- Tier 1 对话会自建自己的工具注册表，并直接调用 `agent.RunLoop`，而不是
  去装配 `agentapp`，所以它们同样不会加载任何插件。把插件带入 Tier 1 是
  一个独立的决策，不在本文讨论范围之内。

## 3. 为什么激活是 Space 的决策

一份部署级别的目录只能说明存在哪些内容，它无法说明某个 Space 的后台 Run
应当拥有什么，因为发布插件的人和执行 Task 的人往往不是同一个人，也没有
共同的目的。

激活记录还回答了"这次 Run 为什么会拥有这项能力"这个问题——一旦一个发布
版本对所有人公开，就再也没有别的东西能回答这个问题了。按定义，一次 Worker
Run 是无人值守的：没有人来批准某次工具调用，也没有人会注意到某个 Hook
的触发。能替代"有人在场"的，只有此前由一个具名的人所作出的决定，而这个
决定会留下一条可追溯的记录。

Space 是正确的所有者，因为 Space 本来就已经是 Portal 资源的所有权与授权
边界，而且一次 Run 正是以某个 Space 的名义、针对某个 Space 的文件被派发的。

一个不想逐项做出这类决定的 Space，其实仍然做出了决定：它选择了开放模式，
只需选择一次，而这个选择本身就会被记录并可追溯到具体的人。第 4.1 节拒绝
的是让"不策展"变成"没有记录"。

## 4. 激活记录

每个 Space 和每个插件对应一行记录：

| 字段 | 含义 |
|---|---|
| space | 拥有这条激活记录的 Space，其后台 Run 会用到它 |
| plugin | 目录中的身份标识 |
| version、digest | 被固定下来的确切发布版本 |
| enabled | 是处于激活状态还是被挂起，但不会丢失这次固定 |
| origin | `curated`——由管理员激活——或 `automatic`（见第 4.1 节） |
| activated_by、activated_at | 谁做出的决定，以及决定的时间 |
| updated_by、updated_at | 谁最后一次移动了这次固定 |

"固定"（pin）才是重点。Marketplace 设计第 10 节禁止在一次 Run 启动过程中
去解析"最新版本"，而"固定"正是让这一点成为事实而非愿望的机制：五分钟前
刚发布的版本，不能改变一次已经派发出去、即将执行的 Run 会做的事情。移动
到更新的发布版本是一个 Space 层面的动作，有自己的审计事件，由一个人在
查看新版本的能力报告之后主动执行。

一个被撤回（yank）的发布版本仍然保持被固定的状态，继续正常工作。撤回
只是把某个发布版本从默认可选列表中移除；它不会侵入某个 Space 的激活记录，
因为那样做会在没有任何人做出决定的情况下改变一个 Space 的 Run 的行为。
撤回真正做的是让状态可见：该激活记录会显示为固定在一个已被撤回的版本上，
并附上原因，这样 Space 就可以有意识地做出下一步动作。

归档一个插件的行为与此相同。二者都不会删除任何东西。

### 4.1 策展型与开放型 Space

维护一份列表是需要投入精力的工作，而一个不愿意投入这份精力的 Space，不
应该被迫在"维护得很差"和"完全没有插件"之间做选择。因此，策展与否是一项
Space 级别的设置，取两个值，而这两种模式**唯一**的区别就在这项设置上：

| | 策展型 | 开放型 |
|---|---|---|
| Agent 可以引用什么 | Space 已激活的内容 | 整个目录 |
| 由谁创建激活记录 | 管理员，出于明确意图 | 系统，在 Agent 首次引用该插件时自动创建 |
| 固定在哪个版本 | 管理员选定的发布版本 | 当时最新的、符合资格且未被撤回的发布版本 |
| `activated_by` | 该管理员 | 保存了引用该插件的 Agent 修订版本的那个人 |
| 运营方资格审核（第 5.1 节） | 强制执行 | **同样强制执行，不受影响** |
| 固定版本、摘要、审计事件、轨迹记录 | 相同 | 相同 |

开放模式是默认值，因为跨 Space 真正要紧的关卡是资格审核，而不是策展本身；
一个希望在所有 Space 中都做策展的部署，完全可以主动声明这一点，而不必让
每个 Space 都各自去声明。

**开放模式是自动激活，而不是不激活。** 这条记录会在 Agent 第一次引用该
插件的那一刻创建，而不是等到 Run 启动的那一刻，因此在解析阶段（第 7 节）
总能找到一条已经固定好的记录可供解析。所以，Space 的这份列表在两种模式下
都存在：在策展模式下它是一道关卡，在开放模式下它是一本流水账。以后把一个
Space 从开放模式切换到策展模式，不需要任何重建工作——这份列表本来就已经
是准确而完整的。

**自动生成的固定记录不会自己移动。** 一旦创建，它的行为就和手动策展出来的
记录完全一样：新版本的发布不会改变任何东西，除非有人主动移动这次固定。
这不是一个日后可以优化掉的疏漏。"固定记录只有在有人移动它时才会移动"是
第 4 节赖以成立的不变量，也是第 7 节能够不必操心时机问题的原因；如果让
这条规则依赖于某个 Space 的设置项，就等于在本文的每一条论证下面都埋下一个
"除非该 Space 是开放模式"的例外。开放模式带来的好处只是没有人需要去
*创建*这次固定，而保持它是最新的仍然需要和其他情况一样的主动动作——第
10 节会让这件事变得可见，而不必让 Space 自己去发现。

**权限本身不变。** 在一个 Agent 中引用某个插件，本来就需要
`ActionManageAgents` 权限，而这正是第 5 节赋予激活操作的所有者或管理员
权限。开放模式省去的是一个步骤，而不是一项权限：任何本来就无权激活该
插件的人，都无法通过这条路径促成它被激活。

## 5. 谁可以激活什么

| 内容 | 权限 |
|---|---|
| 技能、子 Agent | Space 所有者或管理员 |
| Hook、MCP 服务器 | Space 所有者或管理员，**并且**该发布版本需要被一名系统管理员标记为可用于无人值守场景 |

"Space 所有者或管理员"这一要求，与 `internal/server/access` 中
`ActionManageAgents`、`ActionManageWorkflows` 所要求的权限一致：管理共享
自动化资产本来就需要这一权限，而激活恰恰属于这一类决定。设置 Space 的
策展模式（第 4.1 节）出于同样的理由需要同一权限；在开放模式下，自动激活
是由一次本来就已经需要该权限的 Agent 编辑动作引发的。

### 5.1 无人值守资格

资格是**某个发布版本**的属性，而不是某个 Space 的属性，由一名管理员在
自己已经掌控的发布版本上进行设置。这是一个标志位，而不是一个逐 Space
审批的队列,它把决定权放在了掌握相关知识的一方:运营方能够权衡在自己的
基础设施上启动这个进程要付出什么代价;而一个 Space 的管理员通常做不到这
一点。

策展模式并不影响这个标志位。一个开放模式的 Space 可以引用目录中的任意
插件;但它不能引用一个贡献了 Hook 或 MCP 服务器、且没有任何管理员将其
标记为合格的发布版本,自动激活会像策展模式下的手动激活一样,拒绝这样的
发布版本。开放模式放松的是 Space 自己的日常维护工作,而不会触碰运营方
把守的这道关卡。

之所以用"无人值守"而不是"Worker"这个词,是因为这项属性描述的是"没有人
在场"这种情形,而今天恰好有三个界面符合这个形状:Worker、打印模式和
Portal 对话。如果把某个具体界面写进这个名字里,等到第四个符合条件的界面
出现时,这个标志位的名字就会显得不准确。

把一个发布版本标记为合格,意味着一名管理员已经阅读过它的能力报告——它
会启动哪些可执行文件、会访问哪些主机、会注册哪些 Hook 事件——并且接受
让它在无人在场的情况下运行。这是对该发布版本本身作出的声明,因此不会
传递到下一个版本:一个新版本一开始总是不合格的,这正是让这次阅读不至于
沦为走过场的原因。

### 5.2 资格审核不做什么

它并不授予任何权限。技能、子 Agent 以及 MCP 服务器提供的工具,到达模型
时都是以"请求"的形式出现的:工具权限、Hook 门控、敏感路径检查都会像
应用于 Space 自身配置一样应用于它们,这些机制都不会因此而扩大一次 Run
可以做的事情。

Hook 命令是例外,而这正是资格审核存在的原因。无论 Agent 是否发起任何
请求,它都会运行,而且它本身并不受工具权限的约束。它仍然不能扩大 Agent
的权限——一个 Hook 可以阻止一次工具调用,却没有办法批准一次工具调用——
但它确实是以这次 Run 自身的权限在运行代码。这正是管理员在第 5.1 节中
所接受的东西,而第 9 节说明了它到底受到什么约束、又不受到什么约束。

### 5.3 粒度:Space 负责激活,Agent 负责选择

这一节吸收了已废弃的《后台 Run 的插件作用域》提案中的内容,那份提案对
本文最初假定的粒度提出了质疑。**结论:两个层级。** Space 的激活记录说明
它的后台 Run *可以*使用什么;Agent 定义说明一次 Run *实际*使用了什么。
单独任何一个层级都不对。仅靠 Space 级别的列表,会让每个 Agent 拥有同一个
权限等级。仅靠 Agent 级别的列表,则无处检查运营方的资格审核,也无法在
Space 层面回答"我们的后台 Run 可以使用什么"这个问题(见第 13 节)。

| 内容 | Space 激活记录 | Agent 定义 |
|---|---|---|
| 技能、子 Agent | 允许列表 + 固定版本 | 只有当 Agent 引用它时才会加载 |
| Hook、MCP 服务器 | 允许列表 + 固定版本 + 运营方资格审核 | 只有当 Agent 引用它时才会加载 |

**没有任何东西是被继承的。** 本文早期草案曾让惰性内容(inert content)
被继承——一个没有引用任何插件的 Agent,会自动获得其 Space 已激活的每一
项技能和子 Agent——理由是一项不需要的技能只会浪费一些 token,而一项不
需要的 Hook 却会在每次工具调用时触发。这种不对称被否决了。Agent 才是
一次 Run 的行为被声明出来的地方,而一项因为别人编辑了某个 Space 设置就
自动到来的能力,并不会出现在任何一个读 Agent 定义的人能看到的地方。
"代价小"不等于"不可见"。

第 16 节中 Task 范围的新增内容并不推翻这条规则。它们是一次显式的、被
审计的 Agent 动作,记录在一次 Plugin 环境修订版本中,而不是从 Space 的
激活列表中继承来的。

由此产生两个结果,而且都是改进。

**激活是纯粹许可性质的。** 激活一个发布版本不会改变任何现有 Agent 的
行为;它改变的只是一个 Agent *可以*被编辑成引用什么。这使得激活成为一个
没有爆炸半径、无需为之担忧的安全动作,也让"这次 Run 为什么拥有能力 X"
这个问题,单凭 Agent 本身就能回答。

**没有 Agent 的 Run 不会加载任何插件。** `Task.AgentID` 的类型是
`*string`,所以这是一种真实存在的状态,而不是一种假设;在"不引用就没有"
的规则下,这种情况只有一个自洽的答案:没有任何东西声明过需要它。一个
指向某个 Agent 的 Workflow 步骤,使用的是该 Agent 的选择项;一个不指向
任何 Agent 的步骤,就是这种"无 Agent"的情形。

**Agent 引用的是插件,而不是具体发布版本。** 版本和摘要来自 Space 的
激活记录;Agent 的选择项只是一组目录身份标识的集合。这正是让第二个层级
不至于重新制造出"仅靠 Agent 列表"这个方案的缺陷的关键:把一个插件移动
到新版本,永远只需要在一个地方编辑一次,因此阅读新的能力报告仍然是一个
真实的步骤,而不是一个人们随手点掉的对话框。这也是为什么在 N 个 Agent
中引用同一个插件是可以接受的成本,而在 N 个 Agent 中各自固定一个版本号
则不行。

**Space 是 Agent 可以引用范围的上限。** 在策展模式下,这个上限是 Space
已激活的列表;在开放模式下,这个上限就是整个目录,而引用的动作本身会
创建激活记录(第 4.1 节)。无论哪种模式,Agent 引用的插件都会由其 Space
的记录固定下来,而运营方的资格审核(第 5.1 节)正是针对这条记录进行的
检查——这也是为什么任何模式都不能让 Agent 触及一个从未经过这项检查的
发布版本。

**激活集合属于 Run 所在的 Space,而不属于 Agent。** Worker 已经会拒绝
一个所属 Space 与 Task 不同的 Agent——在 Worker 的 Run 路由中,解析
Agent 指令的地方,已经有 `a.SpaceID == task.SpaceID` 这样的检查。插件
选择遵循同一条规则,而不是另起一套:固定版本的解析针对的是
`Task.SpaceID`,而一个未通过该 Space 检查的 Agent,会走上文所说的"无
Agent"路径。

**一个 Agent 引用了、但其 Space 尚未激活的插件,会导致该 Run 失败。**
既不是"带着警告加载",也不是"直接跳过":第 7 节已经会在一个被固定的包
验证失败时拒绝启动 Run,原因是一次后台 Run 的输出会被一个当时并未在场
观察的人所使用。一个引用了某插件的 Agent,已经声明了自己需要这个插件,
而一次悄悄少做了定义所要求的事情的 Run,与前者是同一种错误的失败方式。
这项检查会在三个环节都执行,原因很简单——选择器只会呈现该 Space 的模式
所允许的内容,写入时要么拒绝一个尚未激活的名字要么直接激活它(第 4.1
节),而 Run 启动时会再检查一次——这是因为一次 Agent 修订是只增不改的
(append-only),所以 Space 在 Agent 保存之后再挂起一次激活、或切换到
策展模式,都是无法靠编辑 Agent 来消除的偏差。这种后果是刻意设计的,而且
应当体现在错误文案里:挂起一次激活,会让引用它的那些 Agent 明显地停摆,
而不是悄悄改变它们的行为。

两个层级带来的代价是:激活一个插件之后,它并不会立即可用,直到有 Agent
引用它为止。这正是上一段所说代价的体现,而第 10 节会偿还这个代价的另一
半——"要在两个地方查找一个插件为什么不在预期位置"——办法是在同一处
地方,同时展示一个 Space 已激活的集合,以及每一项被哪些 Agent 引用。

**粒度到此为止。** 无论在哪个层级,插件都是最小单位:无论是激活记录还是
Agent 的选择项,都不会引用一个发布版本的某一部分。要引入第三个"发布版本
内部"的层级,必须像第二个层级一样经受住同样的检验,而目前没有任何理由
支持这样做(见第 15 节)。

## 6. 密钥不在本设计范围内

今天,一个 Worker 的环境就是部署自身的环境,再加上 `BUILDMAX_HOME` 和
运行令牌——产品中目前不存在任何逐 Space 的密钥。

本设计不会为此新增机制。它新增的是诚实地失败:一条激活记录会记录该发布
版本会读取哪些环境变量名——这些名字取自目录中已经保存的检测结果——而
一次 Run 会报告其中哪些变量没有被设置。一个需要令牌的插件服务器会正常
启动、认证失败、并把这个情况报告出来——就像它在本地运行时一样。

要分发密钥,就必须决定谁有权命名一个 Worker 会持有的值、这个值存储在
哪里、它如何轮换,以及一份审计轨迹应该如何记录一个本不该被任何人读到的
值。这些是另一份独立记录要解决的问题,把它建在本文之内只会让两份记录都
变差。在它建成之前,本设计真正有用的那一半,是那些不需要任何凭证的技能、
子 Agent 和 MCP 服务器。

## 7. 物化一次 Run

```text
server                                        worker
  │                                             │
  │                    claims the run ◄─────────┤  GET /worker/task-runs/{id}
  ├─ read the run's space's activations          │
  ├─ intersect with the agent's named set (§5.3)│
  ├─ resolve each to (name, version, digest)    │
  ├─ record the pins on the run ────────────────►
  │                                             ├─ for each pin:
  │                                             │    GET the package with the run token
  │                                             │    verify the digest before extraction
  │                                             │    extract with the hardened reader
  │                                             │    inspect; refuse what would not load
  │                                             └─ place under <global>/plugins/<name>/
```

在这里被解析出来的每一条固定记录,在两种策展模式下都早已存在:一条开放
模式的激活记录是在 Agent 引用该插件的那一刻创建的,而不是在 Run 启动时
才创建(第 4.1 节),所以解析过程永远不需要凭空创造一条记录。

**由服务端负责解析,Worker 永远不解析。** 解析发生在 Worker 领取自己的
Run 的那条路由里——正是解析并记录 Agent 修订版本的同一个地方、同一个
时刻。如果让 Worker 去读取自己所在 Space 的激活记录,就相当于让一个
运行令牌读取 Space 的状态,而这是第 13 节所拒绝的做法;Worker 实际收到
的是一份已经解析完成的列表。

早期草案曾主张在派发之前就完成解析,理由是更晚一点解析可以捕捉到这段
时间内新发布的版本。但这行不通:一条激活记录指定的是确切的版本和摘要,
所以发布新版本不会改变任何东西,除非有人主动移动了固定记录。真正禁止
"启动时取最新版本"的是这个固定机制本身,而不是解析发生的时机。在 Agent
修订版本已经解析完成的同一个地方完成解析,避免了对"一次 Run 的定义在
什么时候被固化下来"这个问题给出第二个相互矛盾的答案,也意味着挂起一条
激活记录,仍然能够阻止一个已经派发、但尚未开始执行的 Run——这正是第
5.3 节所承诺的行为。

解析出来的固定记录会被记录在这次 Run 上,理由与记录 `TaskRun.AgentRevision`
的理由相同:事后,再没有别的东西能说明这次 Run 实际用过哪些版本。轨迹
记录也会记录这一点(见第 8 节),但轨迹本身是失败开放(fail-open)的,
存放在 Run 全局的存储中;而 Run 自身的那一行记录才是可查询的事实,重试
时读取的正是它。

这些字节内容是通过一条由运行令牌授权、Worker 专属的路由传输的,这条路由
只会提供该次 Run 的固定记录所指定的那些包。浏览和下载相关的路由则仍然
保持用户作用域:运行令牌不是用户,让它能读取整个目录就等于把它变成了
一个用户。

下载完成之后的一切都复用了已有的能力——`internal/infra/pluginarchive`
负责带有路径穿越、软链接、重复路径和体积等防护措施的解压,
`internal/service/plugininspect` 负责判断一个包是否能够被加载的检查。
为 Worker 单独实现一套是行不通的,那等于是为"一个归档文件里能包含什么"
另立一套规则。

一个验证或检查失败的包,会导致这次 Run 直接失败,而不是在跳过这个插件
的情况下继续启动。一次后台 Run 的输出会被一个当时并未在场观察的人所
使用;悄悄少做了 Space 已激活内容所要求的事情,是错误的失败方式。一个
Agent 引用了、却解析不到任何激活记录的插件,会以同样的理由导致同样的
Run 失败(见第 5.3 节)。

## 8. 一次 Run 会记录什么

轨迹记录中本来就已经携带每次 Run 的插件清单。对于 Worker 而言,清单中
的每一项都是一个 Marketplace 发布版本,因此会记录目录 ID、版本、摘要
以及来源服务器。每一项还会新增两个字段,因为 Worker 的清单要回答一个
本地清单不需要回答的问题:

- 是哪条激活记录促成了它,以及
- 是谁激活了那个发布版本。

正是这两个字段,把"这次 Run 用到了一个会往某处发帖的 Hook"这句话,变成了
"这个 Space 在这个日期激活了这个发布版本,而这正是应当被重新审视的决定"。

这份清单还会在每次 Run 中记录一次:是哪个 Agent、哪个修订版本的选择项
产生了这份清单——或者记录这次 Run 根本没有 Agent、因此没有加载任何
插件(见第 5.3 节)。如果没有这条记录,清单只能解释一次 Run *拥有*什么,
却无法解释它*没有*什么,而这正是双层级模型带来的新问题。

当第 16 节所述的内容实现之后,TaskRun 还会额外记录它不可变的基础 Plugin
环境修订版本,以及一次自主安装可能产生的可选结果修订版本。这份清单仍然
只是实际加载的基础环境在轨迹中的投影,而不是从当前 Task 的头部重新
构建出来的。

以上都不会携带任何包的内容、配置值或密钥,这与 Marketplace 设计第 10
节的要求一致。

## 9. 什么约束了可执行内容

约束它的不是 Bash 沙箱。本文早期草案曾让可执行内容这一半等待 Worker
沙箱界面接通,而那是对沙箱覆盖范围的误解。

沙箱只包裹一样东西:Bash 工具的子进程。`internal/tool/bash.go` 在
`spawnArgs` 中应用沙箱,并通过 `childEnv` 注入过滤代理。一个 Hook 命令
是从 `internal/infra/hook/command.go` 中派生出来的,一个 MCP stdio
服务器是从 `internal/infra/mcp/transport.go` 中派生出来的,二者都只是
普通的 `exec.Command` 调用,都不携带上述任何一种保护。这一点在每一个
界面上都成立,无论是否处于沙箱化环境中。接通 `SandboxSurfaceWorker`
只会改变一个 Worker 的 *Bash 工具*运行时所处的基线环境;它不会触及一个
Hook 进程或一个 MCP 服务器,而这两者恰恰是激活机制真正要把守的对象。

同样的事实也撤销了本文此前对出网(egress)所做的一项承诺。in-agent
代理只针对一个已经沙箱化的 bash 子进程按主机名过滤流量,而
[sandbox-boundaries.md](./沙箱边界.md) 已经明确指出它不是一个 Pod 级别
的出网边界。一个被激活的 MCP 服务器所建立的连接,根本不会出现在这个
代理里,所以"等 Worker 界面接通之后就能报告出网情况"这句话,本来就不是
这份设计能够兑现的承诺。

真正约束可执行内容这一半的是两件事,而且都不是被推迟的:

- **运营方的审阅。** 第 5.1 节正是这道关卡:一名具名的管理员在某个特定
  发布版本被允许在无人在场的情况下运行之前,先接受它的能力报告——它会
  启动哪些可执行文件、会访问哪些主机、会注册哪些事件。
- **部署自身的隔离环境。** 一个 Worker 运行在运营方为它准备的某种容器、
  Pod 和网络策略之内。这条边界属于运营方,它对一个被激活插件所产生的
  进程的约束力,和它对这次 Run 所做的其他任何事情的约束力是一样的。

由此带来两个结果。阶段 D2 不会被沙箱相关的工作阻塞;资格审核这个标志位
从它上线的第一天起就是有意义的。而限制 Hook 和 MCP 进程,则确实是一个
真实存在的缺口——这个缺口今天在本地 CLI 上就已经存在,并不只存在于
Worker 上——它属于[sandbox-boundaries.md](./沙箱边界.md)要解决的问题,
而不属于本文。

## 10. 产品界面

Portal 拥有激活功能,因为 Portal 正是管理一个 Space 共享自动化资产、以及
阅读审计轨迹的地方。

一个 Space 的插件区块会列出整个目录,标注这个 Space 激活了哪些插件、
激活在哪个版本上,并针对每个发布版本展示它贡献了什么内容——与本地安装时
展示的是同一份脱敏后的报告。一个不符合无人值守资格的发布版本会明确说明
这一点,并说明这是由管理员来决定的,而不是提供一个点了也会失败的按钮。

这个区块还会展示 Space 的策展模式(第 4.1 节),并清楚说明每个取值意味着
什么:在策展模式下,管理员要先激活,Agent 之后才能引用;在开放模式下,
引用的动作本身就会触发激活。一条自动创建的激活记录会被明确标注为
"自动",并附上是哪个 Agent、由谁编辑触发了它,这样一来,开放模式 Space
的这份列表读起来就是一份真实的历史记录,而不是一份被人为策展出来的列表。

由于固定记录在任何一种模式下都不会自己移动,这个区块还必须让"版本滞后"
的状态变得可见:一条已经有更新版本可用的激活记录会明确说明这一点,并在
旁边说明新版本改变了什么,更新则作为一个刻意的动作来执行。一个选择不做
策展的 Space,并不是选择永远运行上个季度的插件——它只是选择在插件首次
使用之前不需要被人过问。如果任由这种"版本滞后"自生自灭,开放模式就会
逐渐腐化。

由于选择项落在 Agent 上(第 5.3 节),这个区块还回答了双层级模型带来的
另一个问题:对于每一个已激活的发布版本,它会说明这个 Space 里哪些 Agent
引用了它——并且,由于没有任何东西是被继承的,一条没有任何 Agent 引用的
激活记录会被展示为"已激活但未被使用",而不是悄无声息地一直生效。一个
Agent 自己的页面则会列出它引用了什么、以及它的 Space 激活了但它没有
引用的内容。两个层级只有在都能从同一个地方看清楚时才是可以承受的代价;
如果要弄清楚这一点意味着要去读遍每一个 Agent 的定义,那就承受不起了。

一个 Agent 的插件字段,会呈现它所在 Space 的模式所允许的内容——策展模式
下是已激活列表,开放模式下是整个目录——并且会说明当前展示的是哪一种,
因为"这个名字将会为整个 Space 激活一个插件"这件事不该等到事后才被发现。
它在任何一种模式下都不提供版本选择:版本属于 Space(第 5.3 节),如果
选择器暗示可以在这里选版本,就等于把同一个固定版本分散放到了和 Agent
数量一样多的地方。

Portal 依然不会对本地机器上发生的事情做出任何声明。一个 Space 的激活
针对的是该 Space 的后台 Run;某个人在自己笔记本上安装了什么,仍然只能
通过本地的 `buildmax plugin list` 查看。

CLI 获得了一条只读路径——这个 Space 激活了什么、激活在哪个版本上——
这样一来,调试某次 Run 的人不需要打开浏览器就能看到这些信息。修改激活
记录的操作则仍然留在 Portal 里,因为审计轨迹和这个 Space 的其他共享
自动化资产本来就都在那里。

## 11. 实现归属

- `internal/core/plugin`——激活记录及其存储层契约。
- `internal/infra/db`——一张表,`plugin_activation`,单数命名,其公开
  标识符来自 `util.NewPublicID`(前缀方案已废弃;参见
  [entity-identity.md](./实体身份.md) 第 4.4 节)。
- `internal/service/plugin`——激活的生命周期、资格标志位,以及开放模式
  Space 的自动激活逻辑,此外还负责发布相关的逻辑。
- `internal/core/space` 和 `internal/service/space`——Space 的策展模式,
  默认值为开放模式。
- `internal/core/agentdef` 和 `internal/service/agent`——Agent 定义中的
  插件选择项,是 `AgentRevision` 上的一个 JSON 数组,记录目录名称,因此
  它会随定义的其余部分一起被版本化,一个旧的修订版本仍然能够回答当时
  该 Agent 引用了什么。
- `internal/core/task` 和 `internal/infra/db`——`TaskRun` 上解析出的固定
  记录,与 `AgentRevision` 放在一起,并在同一时刻写入(见第 7 节)。
- 同样这些所有者,再加上 `internal/service/plugin`,将拥有第 16 节所述
  不可变的、Task 范围的 Plugin 环境头,以及它的 base/result TaskRun
  引用;展开后的包目录仍然不属于数据模型的一部分。
- `internal/server/handlers/space`——Space 作用域的激活相关路由,权限
  要求见第 5 节。
- `internal/server/handlers/admin`——某个发布版本的无人值守资格标记。
- `internal/server/handlers/worker`——在 Agent 修订版本已经解析完成的
  同一处解析并记录本次 Run 的固定记录,随 Run 一起返回,以及那条只在
  运行令牌作用域内、只提供这些固定记录所指定的包的下载路由。
- `internal/agentapp/taskrun`——在装配运行时之前,把固定记录解析到
  Run 的插件目录中。
- `internal/infra/pluginarchive` 和 `internal/service/plugininspect`——
  解压机制,以及经过脱敏的应用层能力检测。

`internal/agentapp` 不需要在现有能力之外做任何改动:它本来就会从
`BUILDMAX_HOME` 中发现插件,只是对 Worker 而言,这个目录现在会在装配
之前而不是之后被填充。

## 12. 交付阶段

### 阶段 D1——Space 对指令类内容的激活

- 激活记录本身、它的存储层,以及 Space 作用域的路由;
- Space 的策展模式,默认值为开放,以及首次引用时的自动激活(第 4.1 节);
- 在 Worker 领取 Run 时,由服务端解析固定记录、记录到该次 Run 上,并
  将其物化到 Run 中(第 7 节);
- 仅限技能和子 Agent;任何贡献了可执行内容的发布版本都不能被激活,
  固定记录也不能移动到这样的版本上——一个下一版新增了 Hook 的插件,
  会停留在上一个版本;
- Agent 定义中的插件选择项,会在选择器、写入时、以及 Run 启动时都做
  一次检查(第 5.3 节);一个什么都不引用的 Agent 不会加载任何东西,
  一次没有 Agent 的 Run 同样如此;
- 激活及其来源会出现在审计轨迹和 Run 轨迹中;
- Portal 的 Space 插件区块。

验收标准:一个 Space 管理员激活了一个贡献了某项技能的发布版本,该 Space
的一次后台 Run 会加载它,该次 Run 的轨迹记录会说明激活记录、版本和摘要。
一个只引用了其中一部分的 Agent,只会加载那一部分,轨迹记录也会如实说明。
一个贡献了 Hook 的发布版本会被拒绝激活,并说明原因。在一个开放模式的
Space 上,同样的 Run 在没有任何管理员主动激活任何内容的情况下也能正常
工作,而它的激活记录会显示为自动创建、已固定,并归属于保存该 Agent
修订版本的那个人。

### 阶段 D2——可执行内容

- 由系统管理员为某个发布版本设置无人值守资格;
- 允许激活贡献了 Hook 和 MCP 服务器的发布版本;
- 把一次固定移动到一个新贡献了可执行内容的版本上,会像首次激活一样被
  拒绝;
- Hook 和 MCP 服务器只会为引用了它们的那些 Agent 物化——这与第 5.3
  节适用于其他一切内容的规则相同——这个阶段扩大的是"可以引用什么",
  而不是"引用如何生效"。

验收标准:一个贡献了 Hook 的发布版本,在被管理员标记为合格之前无法被
激活;一个已激活的 Hook 会在引用了它的 Agent 的后台 Run 中触发,而同一
Space 中另一个没有引用它的 Agent,运行时不会带上它。

### 阶段 D3——密钥分发,答案在别处

[space-secrets.md](Space密钥.md)是这项工作的后续记录。它决定了由
Space 拥有密钥的值,由一个 Agent 修订版本声明它需要哪些密钥、以及这些
密钥如何送达,而分发发生在 Run 这个层级,而不是送达某个具名的插件消费者。
后一项决定把发布版本的摘要从授权路径中移除了:一个送达 Run 的值,在这次
Run 里的每一个进程都能看到,所以固定"哪个插件版本能拿到它"起不到任何
保护作用。固定机制仍然控制着一次 Run 会加载哪些代码,这属于本文第 10
节关心的问题,不受此影响。

## 13. 被否决的方案

### 让 Space 安装到一个共享目录

给每个 Space 一个它自己管理的、像 home 目录一样被物化的持久插件目录,
这样确实不需要激活模型。但这也去掉了固定机制:Run 启动时目录里有什么,
Run 拿到的就是什么,而这正是第 10 节所拒绝的那种可变来源。这会导致一次
Run 仅仅因为有人在派发和启动之间编辑了这个目录,就改变了自己的行为。

### 用 Agent 定义取代 Space 列表

让 Agent 定义自己引用具体的发布版本,不设 Space 级别的列表,这把能力
放在了行为本来就存在的地方,而 `AgentRevision` 是只增不改的,所以一次
修订版本中的固定记录,可以精确回答一个 Agent 在任意时间点拥有什么——
这是一份可变的 Space 列表做不到的。这也不会削弱权限要求:编辑一个 Agent
需要的是 `ActionManageAgents`,与第 5 节赋予激活操作的权限相同。

但它因为两个站得住脚的反对意见而被否决。固定记录会散落在 N 个地方,
把一个发布版本移动到新版本,就意味着要编辑每一个引用了它的 Agent,而
理论上每次编辑之前都应当先阅读新的能力报告——这种摩擦恰恰会侵蚀它本应
促成的那种审查。而且,这样也就没有一个 Space 层面的地方能够回答"我们的
后台 Run 可以使用什么"这个问题,而这恰恰是运营方资格审核需要检查的地方。

本文此前还提出过第三个反对意见,但现在已经不成立,予以撤回而不是悄悄
保留:一次没有 Agent 的 Run 将无法定义自己拥有什么。在第 5.3 节的规则下,
它其实有一个明确答案——它什么都不加载。这个答案对纯 Agent 模型同样
成立,所以它并不构成支持 Space 层级的论据。

真正被否决的是"用 Agent 定义*取代* Space 列表"这个方案。而"在 Agent
定义中从 Space 列表中选择"是这个决定的另一半,是被采纳的方案;参见第
5.3 节。

### 不涉及运营方参与的激活

让一个 Space 管理员可以激活任何已发布的内容,方案更简单,而且在各个
Space 只是同一家公司不同部门的场景下是站得住脚的。但在一个部署的各个
Space 是彼此独立的客户的场景下,这就站不住脚了,因为那样一来,一个
Space 管理员就能导致任意程序在共享基础设施上运行。把资格设定为发布
版本的属性,而不是逐 Space 审批,能让运营方的决策成本足够低,不会因此
带来有意义的速度损失。

### 让资格在后续版本中继承

让这个标志位从一个发布版本延续到下一个,会让激活这件事感觉不那么像
走文书流程。但这也会让管理员的审阅变成走过场:他们当初接受的能力报告,
描述的是早已不存在的字节内容。一个新版本默认不合格,正是让这个标志位
真正有意义的原因。

### 让撤回或归档使整个 Space 失去激活

把撤回变成一个能一次性关闭所有固定在该版本上的激活记录的总开关,听上去
很像一个诱人的紧急停止按钮。但这会在没有任何一个 Space 上的人做出决定的
情况下,改变该 Space 的 Run 的行为,而且会让撤回这个动作比"从默认可选
列表中移除"要重得多——这反而会让管理员不敢使用它。真正存在的紧急停止
开关属于部署层面:把发布版本标记为不合格,这会立即停止可执行内容这一半
的生效。

### 让开放模式在每次 Run 时解析最新版本

让一个开放模式的 Space 完全跳过固定这一步——每次 Run 启动时都解析当时
最新的合格发布版本——听起来正是"我们不想维护这个"这句话想要的效果,
而且能让这样的 Space 永远免费保持最新。

但这被否决了,因为它会让固定机制变成有条件的。第 4 节所保证的"五分钟前
发布的版本不能改变一次即将执行的 Run 会做的事情",在策展型 Space 上
成立,在开放型 Space 上却不成立,而建立在这条保证之上的每一个论证——
第 5.1 节的重新审阅、第 7 节可以延后解析的自由、第 13 节对共享目录方案
的否决——都需要加上一条"除非该 Space 是开放模式"的但书。两个 Space
会对"这次 Run 为什么和上一次表现不同"这个问题给出不同的答案,而这正是
本文存在的意义所在,就是要回答这个问题。想要保持最新,应当靠一个可见的
提示来换取(见第 10 节),而不是靠牺牲这条不变量来换取。

### 让所有 Space 都必须做策展

要求所有地方都必须策展,听上去是更安全的默认选项,但它被否决的原因是
"不应作为默认值",而不是"不应作为一种能力"。大多数 Space 使用插件的
方式是技能和子 Agent,而第 2 节已经说明,这类内容早就可以被一个 Space
毫无仪式感地通过 `AGENTS.md` 放在 Worker 面前。要求为它们单独设立一道
激活步骤,却不对 `AGENTS.md` 提出同样要求,就是在产品已经决定不设置
仪式的地方强行加上仪式,而可以预见的结果是,Space 会选择不使用插件,
而不是选择去做策展。真正不能设为可选项的是运营方的资格审核,而这是一项
独立的控制机制,不受开放模式的影响(见第 5.1 节)。

### 在 Worker 上解析激活记录

让 Worker 在启动时读取自己所在 Space 的激活记录,确实可以从派发信息中
省掉一个字段。但这也变相地重新引入了"启动时取最新版本",而且意味着
一个运行令牌可以读取 Space 的状态。这两点都是本设计出于至今仍然成立的
理由而已经否决过的方案。

## 14. 验证

在测试证明以下各项之前,本文所述内容不算实现完成:

- 一条激活记录固定了某个版本和摘要,此后发布的新版本不会改变一次已经
  派发的 Run 会加载什么;
- Worker 会精确物化被固定的那个发布版本,并在解压前根据摘要完成验证,
  物化到该次 Run 专属的 `BUILDMAX_HOME` 中;
- 一个验证或检查失败的包,会导致 Run 直接失败,而不是在跳过该插件的
  情况下继续启动;
- 一个运行令牌只能下载自己所属 Run 的固定记录所指定的包,不能读取整个
  目录;
- 一个既非所有者也非管理员的 Space 成员,不能激活任何内容,也不能修改
  该 Space 的策展模式;
- 一个开放模式 Space 中的 Agent 引用了一个尚未激活的插件,会创建该
  激活记录,固定在当时最新的、合格且未被撤回的发布版本上,并归属于
  保存该修订版本的那个人;
- 一个策展模式 Space 中的 Agent 引用了一个尚未激活的插件,会在写入时
  被直接拒绝;
- 无论哪种模式,一条自动生成的固定记录都不会在新版本发布后自动前移;
- 开放模式不允许引用一个贡献了 Hook 或 MCP 服务器、且未被任何管理员
  标记为合格的发布版本;
- 一个贡献了 Hook 或 MCP 服务器的发布版本,在被管理员标记为合格之前
  不能被激活,把固定记录移动到这样的版本上,会被按照首次激活同样的
  条件拒绝;
- 资格不会从一个发布版本延续到下一个;
- 挂起一条激活记录,会使引用该插件的那些 Agent 的 Run 失败,并在错误
  信息中指明该插件,而不是让它们在没有这个插件的情况下继续运行;
- 撤回或归档不会影响已有激活记录的正常工作,但会报告出相应的状态;
- 审计轨迹会记录激活、去激活、固定记录变更以及资格变更,并注明操作者、
  Space、插件、版本和摘要前缀,但不记录任何配置值;
- 一个不引用任何插件的 Agent,不会加载任何插件,无论其 Space 激活了
  什么;
- 一个只引用了部分插件的 Agent,只会加载那一部分,不多不少;
- 激活一个发布版本,在有 Agent 引用它之前,不会改变任何已有 Agent 的
  行为;
- 一个 Agent 引用了其 Space 尚未激活的插件时,该 Run 会失败,错误信息
  中会指明该插件;
- 一次没有 Agent 的 Run 不会加载任何插件;
- 一个所属 Space 与该次 Run 不一致的 Agent,会被当作"没有 Agent"处理,
  与 Worker 路由中对其指令的现有处理方式一致;
- 一个 Agent 在其 Run 已经解析完固定记录之后被编辑,不会改变该次 Run
  所加载的内容;而一个在派发与解析之间被编辑的 Agent 则会改变——这与
  Agent 修订版本已经遵循的规则相同(第 7 节);
- 一次 Run 的轨迹记录会写明激活记录及其操作者,并写明是哪个 Agent 修订
  版本的选择项产生了这份集合——或者记录当时根本没有 Agent;
- Tier 1 对话仍然不会加载任何插件;
- 一个 Space 声明需要、但没有被设置的环境变量,会被该次 Run 报告出来,
  而不是被默默忽略。

## 15. 开放问题

1. 一个 Space 是否应该能够激活一个比它当前正在运行的版本*更旧*的发布
   版本?如果可以,Portal 中是否需要用一个不同于"更新"的词来表述这个
   动作?
2. ~~一条激活记录是否应该能够只引用一个发布版本内容的一部分——比如
   这一项技能而不是那一个子 Agent——还是说插件就是一个 Space 所接受的
   最小单位?~~ **已决定:插件就是最小单位**,在第 5.3 节定义的两个
   层级上都是如此。做选择是 Agent 定义的职责,它引用的是插件。要引入
   第三个"发布版本内部"的层级,必须像第二个层级一样经受住同样的检验,
   而对于惰性内容而言,答案只是省下一些 token,这买不来这个层级。
3. 当部署改变了 Worker 运行所处的边界——比如换了一个不同的容器或网络
   策略——一个此前已被认定合格的发布版本,是否需要重新审阅,即便管理员
   当初是在旧边界下接受它的?
4. Tier 1 对话是否应该在某一天加载插件?如果是,是否复用同一套激活记录
   来为它服务,还是说对话本来就是一个不同的作用域?
5. 当一个 Space 固定的发布版本被撤回时,它应该看到什么——一条可以被

6. 一个部署是否应该能够强制所有 Space 都使用策展模式,从而覆盖第 4.1
   节所说的逐 Space 选择权?在一个部署的各个 Space 是彼此独立的客户的
   场景下,这个能力是站得住脚的,但目前没有构建它:因为资格审核已经
   把住了真正跨 Space 的那道关口,而且至今没有任何部署提出过这个需求。
   以后再加上这个能力,只是加一项设置,不算重新设计。
7. 一个 Space 是否应该能够把某条激活记录标记为*强制*,使得每个 Agent

   第 5.3 节。

## 16. Task 范围的自主获取

一个 Agent 最终可能会发现,它已记录的选择项缺少当前 Task 所需要的某项
能力。BuildMax 将支持带类型的搜索、检测和安装,同时不会让
`BUILDMAX_HOME/plugins/` 变成一种持久状态。

Space 的激活记录仍然是能力的上限,而一项独立的 Space 策略会决定一个
正在运行的 Agent 是否可以发起自主获取的请求;普通的 Task 执行权限并不
隐含插件管理权限。在策展模式下,一次被允许的请求只能选择一个已经被
激活的发布版本。在开放模式下,它可能引发与今天一次经授权的 Agent 编辑
所引发的同一种自动激活,并将其归属于该 TaskRun 以及发起该请求的主体。
运营方资格审核、可执行内容的关卡、权限解析以及密钥授予仍然一概适用;
安装一个包,永远不会因此获得任何密钥。

其持久化的结果是一个不可变的 **Plugin 环境修订版本**。它会记录 Agent
修订版本的基线选择项,加上 Task 范围内新增的内容,均以精确的包引用、
版本、摘要、安装来源,以及已解析的权限修订版本的形式记录下来。位于该次
Run `buildmax-home/plugins/` 目录下的展开版目录,只是这条记录的一次性
投影:

```text
Space activation ceiling + Agent revision + Task additions
                             |
                             v
              immutable Plugin environment revision
                             |
                             | verify and materialize
                             v
          <task-run>/buildmax-home/plugins/<name>/
```

一个已经在目录中的包只会被引用,不会被重新上传。一个私有的、或者由
Agent 生成的包,在一个环境可以引用它之前,必须先经过规范化、检测、
摘要验证,并在 Plugin 包存储中保存一份。下载产生的文件、解压残留物、
缓存、凭证,以及未声明的可变 Plugin 状态,都不会通过遍历这个展开目录
而被捕获下来。一个确实需要持久化可变状态的插件,必须声明一个受到独立
治理的 Run、Task、Agent 或 Space 状态作用域;这种状态不属于包安装的
范畴。

一个 TaskRun 永远不会改变它已加载的 Plugin 集合。工具模式、提示词层、
MCP 服务器、Hook、沙箱规则和密钥需求,都是在运行时被装配的那一刻固定
下来的。一次成功的安装,只能影响之后的某个 TaskRun。Continue 使用的是
该 Task 的 Plugin 环境头;Retry 会重建被重试的那次 Run 的基础环境。一次
即时的能力交接,可能会在会话和工作区状态都提交之后创建一个后继
TaskRun,但它不能对当前进程做热加载。§16.1 规定了这一转移方式。

### 16.1 即时能力交接的转移方式

`PluginInstall` 永远不会改动正在运行的进程。它会把请求的发布版本暂存为
该 Task 的一个**待定 Plugin 环境修订版本**,并把这一结果返回给 Agent;
当前 TaskRun 已装配的工具集、提示词层、MCP 服务器、Hook、沙箱规则和
密钥需求都保持不变。Agent 可以用现有能力完成目标,也可以结束本轮,以便
在后继 Run 中启用这份被暂存的能力。

交接本身只发生在 TaskRun 边界上,并且由 Server 而非 worker 来编排:

1. **静默收敛。** worker 通过优雅关闭路径停止 Agent 循环以及它所拥有的
   每一个子进程,与一次正常终态上报完全相同。
2. **提交检查点。** worker 捕获 `workspace/` 和会话包,上传、校验,并请求
   Server 提交一个成功的结果检查点。这原样复用
   [task-workspace-checkpoints.md](./Task工作区检查点.md) §5.5 中的结果检查点
   协议,不作任何改动。
3. **提交环境。** 在接受终态上报并推进 `task.workspace_head_checkpoint_id`
   的同一个事务里,Server 把待定修订版本冻结为一个不可变的 Plugin 环境
   修订版本,记录为该 TaskRun 的 `plugin_environment_result_id`、状态为
   `committed`,并把 `task.plugin_environment_head_id` 推进到它。工作区头部
   和环境头部要么一起推进,要么都不推进。
4. **派生后继。** 在接受了一份带有"标记为即时交接的已提交环境"的终态上报
   之后,Server 会在同一个 Task 上创建一个后继 TaskRun,其基础是新的工作区
   头部、已提交的会话,以及新的环境头部。该后继以其失败关闭的准备关卡
   物化展开后的插件集,并继续该目标。产品 UI 可以把这两次 Run 呈现为一次
   连续执行;但记录会保留这个边界及其原因。

失败是失败开放的,并且绝不悄无声息。如果检查点或环境提交失败,两个头部
都不推进,不派生任何后继,待定修订版本也保持无引用状态以待垃圾回收;已经
完成的工作照常成立,用户可以按现有规则从上一个持久头部 Continue。如果
后继的物化失败,该后继会像任何一次恢复那样失败关闭——它不会退回到之前的
能力集合。

Retry 不受影响:重试交接前的那次 Run,会重建它不含新增内容的基础环境,
因为 Retry 重复的是一次尝试,而不是从它的结果恢复。一次被暂存的安装究竟
是请求一次即时后继,还是仅仅为下一次用户 Continue 推进头部,取决于
`PluginInstall` 调用本身的属性,所以一个只是在为未来能力做准备的 Agent,
不会被迫多跑一次 Run。

自主获取默认作用于 Task 范围,这样一个目标就能改善自己的能力,而不会
悄悄地改变这个 Agent 未来所有场合的行为。要把它提升为 Agent 定义或
Space 激活的一部分,需要一次独立的、经过授权和审计的动作。

本节是对已交付的 D1 路径的扩展,而不是对它的重新描述。其工作区、会话
和物化边界,在
[task-workspace-checkpoints.md](./Task工作区检查点.md)中有明确规定。
