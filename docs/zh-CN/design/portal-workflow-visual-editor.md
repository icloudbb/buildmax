## 决策

Portal 的 workflow 编辑器是否应让用户可视化地编排真正的依赖图，而不再只能编排一条
线性步骤卡片链、分叉全靠 raw JSON 兜底？**应该。** 编辑面变为两种模式：**可视化**
节点连线画布与 **raw JSON** 视图，二者由同一份草稿状态驱动，并由同一个
`validateSteps` 校验。结构化步骤卡片表单被退役，其每节点字段并入可视化编辑器的节点
检视面板。

workflow 定义是由 `needs` 边连接的 `agent_task` 节点组成的 DAG（见
[workflow 运行时](Workflow运行时.md)）。旧表单只能表达一条直线——某节点依赖它上面
那个——因此任何分叉或汇合都得手写 JSON。可视化编辑器让「图」成为首要的编排对象。

## 用户结果、证据与约束

编辑 workflow 的 Space 成员可以把步骤看作一张图，添加步骤，把一个步骤的完成连到另一个
步骤的开始，并编辑步骤的 agent、指令、Issue 访问与输入绑定，全程不必手写 JSON。分叉
计划（两个步骤共同喂给第三个）通过画边完成，而非记住 `needs` 数组语法。raw JSON 仍用于
精确查看，以及可视化面尚未编辑的字段。

因为编辑这张图就是本页的全部任务，图即页面：画布占满可用高度；workflow 的名称与描述
折叠进一个默认收起的「Settings」抽屉；编辑器不再在画布上方渲染那张与之重复的只读拓扑图。
创建 Workflow 是同一项任务，因此 **New Workflow** 在独立页面（`#/spaces/{space_id}/workflows/new`）
而非对话框中打开同一个编辑器；由于 Workflow 尚不存在，名称与描述在该页是可见字段。点击
**Create workflow** 之前不保存任何内容：服务端在创建时校验定义，不可用的 Create 会说明缺少什么。

编辑器使用编写者的语言，而非定义的语言（见
[工作与执行体验](Portal工作与执行体验.md#workflow-编写)）。步骤显示为“第 N 步”（按定义顺序
编号，与校验错误和运行页的步骤一致）及其 Agent 名称。Agent 选择器按名称列出 Agent，仅在两个
Agent 重名时附加区分信息（描述，否则 id）。Issue 访问以“不访问 Issue”“使用运行所属的 Issue
（如有）”“必须有 Issue”表示 `none`、`if_bound`、`required`，每项附一行说明。

约束：定义契约不变、由服务端拥有；编辑器只产出运行时已在校验的同一份 JSON。布局不属于
契约——节点位置是 UI 关注点，绝不写入定义。Portal 保留自身组合方式，`@buildmax/gui`
保持中立。

## 数据模型与往返

`steps.ts` 仍是唯一的序列化/解析/校验权威，`useWorkflowSteps` 仍是唯一的草稿状态。两处
改动使其无损且以图为先：

- **显式边。** 加载时每个节点的 `needs` 归一化为其有效值，使图无歧义、每次边操作都是
  普通数组编辑。线性默认（无 `needs` 的节点依赖上一个）仅作为读取未编辑的历史定义的解释。
- **无损保留。** 草稿现在原样携带节点的 `output_schema` 以及定义的 `input_schema` 与
  `result`，经解析与序列化往返，因此把声明了它们的定义切入可视化编辑器再保存不再丢弃。
  它们经 raw JSON 编写；可视化节点检视面板编辑 agent、指令、Issue 访问与绑定。

## 可视化编辑器

画布把每个步骤渲染为一个节点（其“第 N 步”标题、Agent 名称、指令片段、Issue 访问徽章与
错误标记），把每条
`needs` 渲染为指向依赖节点的边。`steps` 是内容与边的真相来源；React Flow 的节点**位置**为
纯 UI 本地态，由深度分列自动布局播种、可拖动调整，绝不持久化到定义。交互映射为草稿变更：
连边新增一条 `needs`、删边移除之、删节点移除该步骤及引用它的边、加节点追加一个根步骤供用户
连接。选中节点打开其字段的检视面板。节点 id 在创建时生成，并不出现在主要表单中：raw JSON、
绑定与运行诊断通过它引用步骤，因此它可在检视面板的 **高级** 折叠区中编辑，绑定来源则显示为
“第 N 步的输出”。重命名会
一步改写所有对它的引用——其它节点的 `needs` 边、读取其输出的绑定 source、以及定义的 `result`
选择器——因此可用有意义的 id（`collect`、`analyze`）替换生成值而不破坏图。会形成环的连接、
重复或空的 id、缺失的 agent、空指令都经由同一套门禁 Save 的校验暴露。`max_parallel_nodes`
是画布旁的工作流级控件。

宽度小于 768px 时画布既无法阅读也无法编辑。此时编辑器改为以有序列表显示步骤（每项含其
Agent、指令以及它之前需要完成的步骤），列表位于检视面板上方；选择一个步骤即在检视面板中
打开它，并有提示说明在依赖图上连接步骤需要更宽的窗口。概览中的计划在该宽度下使用同一列表，
因此无需横向滚动即可读到 Workflow 的步骤及其顺序。

## 依赖

画布使用 **`@xyflow/react`**（React Flow，MIT）——节点式编辑器的成熟 React 库——而非在
手写的只读 `WorkflowGraph` SVG 上叠加拖拽、连边与选中。只读的运行图与计划图继续使用
`WorkflowGraph`；只有编辑器引入该依赖。

## 选项与非目标

| 选项 | 权衡 |
|---|---|
| 保留线性卡片表单 + raw JSON | 无新依赖，但分叉 DAG 仍只能写 JSON——即已证实的缺口。 |
| **可视化画布 + raw JSON（推荐）** | 一个以图为先的编排对象；新增一个聚焦的标准依赖。 |
| 在 `WorkflowGraph` 上手写拖拽/连边 | 无依赖，但以高成本与高风险重造一套成熟交互模型。 |

本切片的非目标：为 `input_schema`、`result`、`output_schema` 提供专属表单控件（无损保留、
经 raw JSON 编写）；持久化节点位置；`agent_task` 之外的新节点类型；以及对定义契约或运行
模型的任何改动。

## 验证

`./make check portal`（lint、类型、单测）、`steps.ts` 对新保留字段与显式边归一化的往返单测，
以及扩展 workflow 浏览器规格：可视化地编排一个分叉；编写一个两步 Workflow，且不以步骤 ID、
Agent ID 或原始 Issue 访问值作为标签；在 390px 下无横向滚动地阅读步骤。`./make e2e visual`
在参考宽度与两种主题下固定编辑器的外观。
