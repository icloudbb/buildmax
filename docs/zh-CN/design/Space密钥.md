## 1. 问题

Worker 代表一个 Space 执行模型选择的命令，而有用的工作离不开凭证：驱动 `git` 和 `gh` 的 Agent 需要 GitHub 权限，调用内部服务的 Agent 需要该服务的凭证，负责部署的 Agent 需要云平台权限。

Phase 1 之前没有 Space 范围的 Secret 资源，凭据通过部署环境交付，没有逐 Agent 选择或消费审计。Phase 1 已补齐这一产品缺口。剩余 worker 环境凭据债务单独记录在 §13 和 Phase 0；添加 Space Secrets 并不会移除部署级对象存储凭据，也不会改变 run token 的交付。

促成这一变化的原因有两点；Phase 1 解决了第一点，第二点仍由 §13 跟踪：

- 旧版 `env_scrub` 采用的是拒绝名单，会剥离 `GITHUB_TOKEN` 之类的变量名，导致在 CLI 基线上本可使用的凭证到了 worker 里就消失了。Phase 1 用一个默认拒绝的基线取代了它：显式授权的环境变量名会被放行，而 BuildMax 自身的凭证依然被拒绝。
- worker 依然会收到根本不属于其 Space 业务范围的凭证——部署方的对象存储密钥，以及直连模式下的提供方 API Key。§13 记录了这些凭证必须被移除的原因。

## 2. 决策

BuildMax 新增一个服务端 Secret 代理（broker），它做以下几件事：

1. 把一个 Secret 表示为一个 Space 拥有的、带版本的资源，或者表示为对外部 Secret 管理系统的一个引用；
2. 把 Secret 的使用绑定到一个不可变的 Agent 修订版本上，由该修订版本声明需要哪些 Secret、以何种方式交付；
3. 在 worker 领取运行时，把这份授权快照到唯一一个 TaskRun 上；
4. 只具体化为这次运行计算出的值；并且
5. 把每个值以环境变量、渲染出的凭证文件，或两者兼有的形式交付进运行——具体采用哪种方式由 Agent 声明决定。

在所有面向用户的 API 中，值都是只写的。不存在回显（reveal）操作。

### 2.1 交付以运行为单位，而非按消费者交付

交付问题只有一个答案，值得把它作为一项决策明确写下来，而不是当成实现细节：凭证交付给的是**运行**本身，而不是运行内部某个被命名的进程。

早期的一种设计只向被命名的消费者交付值——一个 stdio MCP server 的显式环境变量、一个类型化的 HTTP 授权槽位、交给单个进程的一个文件——并拒绝向模型选择的命令交付。这种方案被否决了，原因在于 BuildMax 的 Agent 本质上是什么：Agent 在运行时组合 shell 命令、调用它自己选择的工具，包括运行过程中现写的工具。任何以“每个工具一个适配器”为工作单位的机制，都是针对一个无界集合去做适配，结果只能是认证了 `gh`，却认证不了模型一分钟后写出来的那个 Python 脚本。这不是这个功能的缩水版，而是一个压根解决不了问题的另一个功能。

因此，这两种受支持的模式都是运行级别的。§17 记录了这样做的代价，以及因此放弃了什么。

## 3. 这不能保护什么

两种交付模式都会把值放进运行内部，Agent 自己的命令因此可以读到它：`printenv` 会暴露一个环境变量授权项，`cat` 会暴露一个文件授权项；这里没有任何机制能阻止这一点，任何使用面都不得暗示它做到了。

剩下的防护措施，以及每一项各自的价值：

| 控制手段 | 换来了什么 |
|---|---|
| Space 所有权 | 一个 Space 的值，另一个 Space 的运行无法触及 |
| Agent 修订版本的消费配置 | 一次运行只会收到其 Agent 配置过的条目，而不是该 Space 的全部 Secret |
| TaskRun 快照 | 授权在运行被领取的那一刻就已固定，不能从运行内部扩大 |
| 短期凭证 | 泄露出去的值会过期；运行开始时的一次交换是主要的防泄漏手段 |
| 收窄的提供方作用域 | 一个仅限某个仓库的令牌，无论落在谁手里都无法在该仓库之外生效 |
| 加密存储 | 数据库或备份被窃取，并不会带来可用的值 |
| 没有回显 API | 无法通过管理界面恢复出值，值只能被一次已授权的运行使用 |
| 审计与撤销 | 每一次授予都可归因，并且可以被撤销 |
| 精确值脱敏 | 减少值意外出现在日志、轨迹和工具结果中的概率；不是一条保密边界 |

这份设计划出的边界是：**哪一次运行可以行使哪种权限、能行使多长时间、代表谁去行使**。它不是一条围住“一次运行被授权使用某个值之后，那些字节本身”的边界。

有两个后果，Portal 文案和用户文档都必须体现，因为一个误读了它们的 Space 会因此授予出本不该授予的凭证：

- 一个 Agent 可以读取授予给它这次运行的每一个 Secret；并且
- 任何能够触发一个共享 Agent 的成员，都能拿到该 Agent 持有的值，即便这个成员从未获得过属于自己的绑定权限或读取权限。

一个无法接受这一点的 Space，应该收窄凭证在提供方一侧的作用域、缩短它的有效期，或者换一个 Agent。交付方式不是可以扳动的那根杠杆。

## 4. 范围与所有权

**Space 是唯一的所有权范围。** 一个 Secret 只属于唯一一个 Space，这与拥有 Agent、插件激活状态和审计记录的边界是同一条边界。一个 Agent 定义只能消费自己所属 Space 的 Secret；引用了另一个 Space 的 Secret 的消费配置，在修订版本保存时就会被拒绝，而不是等到运行时才拒绝。

本设计有意不提供部署级、独立于 Space、可供跨 Space 的多个 Agent 引用的全局 Secret。要求这样一个全局 Secret 的呼声是真实存在的——运维者持有一份共享的内部凭证时，自然更愿意只录入一次——但目前拒绝提供，因为一个全局值没有可归因的所有者，没有可以从中撤销它的 Space，也回答不了“哪些 Space 的运行可以读取它”这个问题。如果两个 Space 需要同一份凭证，各自创建一个值相同的 Secret 即可；这份重复正是让所有权模型保持可追责所付出的、看得见的代价。

这不涉及 BuildMax 自身的凭证。数据库密码、JWT 签名密钥、KEK、对象存储管理凭证，以及托管的模型提供方密钥，都是运维者拥有的部署配置，永远不是 Space Secret，也永远不会作为一项授权交付给某次运行。§5.3 把这些类别分得清清楚楚。

本设计也没有引入服务端的 Project 或“部署环境”实体来限定 Secret 的范围。Space 才是 Server 端的所有权边界；`internal/core/localproject` 里的本地 `Project` 是客户端概念，与此无关。

## 5. 资源模型

一旦写好，`internal/infra/db` 中的 `xxxRow` 结构体仍然是数据库 schema 的事实来源；下面描述的是这些结构必须表达的内容。公共标识符按照 [entity-identity.md](实体身份.md) 使用 `NewPublicID`；时间戳遵循 [timestamp-representation.md](时间戳表示.md)。

这个模型故意只设计成两张表：一张 Secret 表，一张按运行记录的审计快照表。一次运行如何消费一个 Secret，根本不是一张表——它是配置在 Agent 修订版本上的内容（§6），而修订版本本身已经是仅追加的，因此修订版本固定了一次运行消费了什么，而 Secret 的值本身依然保持鲜活、可以随时轮换。

### 5.1 `secret`

一个由 Space 拥有的 Secret。**一个 Secret 是一个分组**：一个名字下面挂着若干命名**条目**——比如 `access_key_id` 和 `secret_access_key`，或者 `username` 和 `password`。单一值的凭证不过是只有一个条目的分组。

| 字段 | 含义 |
|---|---|
| `id`、`public_id` | 数字化的关系型主键，以及不透明的公开句柄 |
| `space_id` | 所有权与授权边界；见 §4 |
| `name` | 在 Space 内唯一、非敏感的显示名称 |
| `description` | 可选的、长度受限的说明；不得携带条目的值 |
| `provider` | `embedded`，或某个运维者配置的外部提供方名称 |
| `state` | `active`、`disabled` 或 `destroyed` |
| `ciphertext`、`nonce` | 经 AEAD 加密的条目映射，或加密后的提供方描述符 |
| `item_names` | 存在哪些键，以明文存储 |
| `wrapped_dek`、`key_id` | 被 KEK 封装后的 DEK，以及是哪个 KEK 完成了这次封装（§9.1） |
| `created_by`、时间戳字段 | 管理层面的归因信息 |

条目是**存放在同一行里的一整个加密 JSON 对象**。其值是一个 `map[string]string`——条目名到条目值的映射——被作为一个整体密封起来。这正是小型部署便于理解、备份能够整体携带、KMS 能够整体封装的形态，也正是让轮换在没有版本表的情况下依然正确的原因：替换整个映射是一次原子写入，因此一次运行读到的永远是一份自洽的集合。不会出现运行读到新的 `access_key_id` 却配着旧的 `secret_access_key` 这种窗口期——这正是这些条目必须放在一起存储的全部理由。

`item_names` 是明文的，因为名字本身不是值，而且 Portal 的列表展示与 §6 的校验都必须在不解密任何东西的前提下工作。条目名是一个标识符——`[A-Za-z_][A-Za-z0-9_]*`，写入时会校验——这样一整个分组才能作为环境变量整体注入（§6.2），而不会有某个条目因为命名不合法而悄悄注入失败。

每一个条目在 API 中都是只写的；§15 里没有回显操作。渲染出的文件还需要的那些非敏感参数——集群的 server URL 和 CA 证书、AWS 的 region——都不是条目：§6.3 让它们作为字面值挂在 Agent 上，在那里保持可读。用“放在哪里”来表达分类，因此没有哪个条目需要携带“是敏感值还是配置项”的标志位，创建一个 Secret 也就仅仅是键入条目名和值这么简单。

`(space_id, name)` 唯一。重命名只改变展示层的元数据，不改变身份。禁用会拒绝新的运行授权和新的具体化。销毁会在不再存在活跃引用之后清除可恢复的材料；它不会改写审计历史。

本设计有意不对一个 Secret 的条目做版本管理。分组本身已经带来了原子轮换，而这正是版本表原本要买来的唯一一项正确性；剩下的那部分——正在进行中的运行仍持有旧值——之所以无关紧要，是因为一次运行只在被领取时具体化一次，不会重新读取。在一次轮换前后分别被领取的两次运行，各自都会得到一份内部自洽的集合，这已经是诚实的保证。§17 记录了版本管理本可以带来什么，以及为什么它在这里不值得付出这个代价。

本设计有意不设 `kind` 字段。给一个 Secret 打上凭证家族的标签，会让存储层负责解释这个值，并且等于断言一个 Secret 就是一整个渲染出的文件——那会把 kubeconfig 里本非敏感的 server URL 和 CA 证书也一并封进加密的二进制块里。条目名足以承载一份凭证本身的结构，而渲染方式是在 Agent 一侧选择的。

### 5.2 `task_run_secret`

一份非敏感的审计快照，记录一次运行被授予了什么。

| 字段 | 含义 |
|---|---|
| `task_run_id` | 对应的运行 |
| `secret_id`、`item_name` | 具体解析出的是哪个 Secret 的哪个条目 |
| `agent_revision_id` | 授权这次使用的消费配置 |
| `provider_version` | 解析出的精确外部版本（如果可获取） |
| `delivery` | `env` 或 `file` |
| `env_name`、`file_target` | 解析后的交付目标 |
| `status` | `pending`、`materialized`、`revoked`、`expired` 或 `failed` |
| `expires_at` | 一个被交换或租用的凭证何时失效 |
| `materialized_at`、`revoked_at` | 运行时生命周期的证据 |

这张表不保存密文、明文、租约令牌、提供方的错误响应体，也不保存值的哈希。对低熵条目而言，哈希会让攻击者可以离线猜测，而解释一次运行的来龙去脉根本用不到它。

### 5.3 保持不同凭证类别相互独立

同一套存储与交付机制，不应该把生命周期本就不同的凭证都吸纳进来。

| 类别 | 示例 | 所有者 | 处理方式 |
|---|---|---|---|
| 部署引导凭证 | 数据库密码、JWT 签名密钥、Secret 的 KEK | 运维者 | 由部署注入；永远不是 Space Secret |
| 服务端管理的上游凭证 | 模型 API Key、对象存储管理凭证 | 运维者 | 加密存储或外部引用；永远不会交付给某个 Space 的运行 |
| Space 执行凭证 | GitHub token、Slack token、内部服务凭证 | Space | 由本设计管理 |
| 临时运行权限 | 运行令牌、预签名 URL、STS 凭证、Vault 租约 | Server 或外部签发方 | 在运行时铸造或交换；TTL 很短；不是可复用的 Space Secret |
| 用户认证凭证 | 密码校验值、刷新令牌、webhook key | 账户子系统 | 沿用既有的哈希、轮换与撤销模型 |

## 6. 消费配置

一次运行如何消费 Secret，配置在 Agent 上——这符合“Space 在定义 Agent 的地方完成这项设置”的要求。它不是一个独立的绑定资源：而是 Agent 定义上的一个结构化字段，被带入每一个仅追加的 Agent 修订版本，在保存时以及 worker 领取运行时，都由 Secret 服务负责校验。

把它放在修订版本上，正是替代版本表的做法。修订版本精确固定了一次运行消费了哪些条目、以何种方式消费，因此“这次运行用了什么”可以从不可变状态中直接回答，而这些名字背后的条目值依然保持鲜活、可以随时轮换。

### 6.1 一个 Agent 声明的内容

一个 Agent 的消费配置是一份条目列表，每一项要么是一个环境变量授权，要么是一个文件授权。一个授权项可以从该 Agent 所属 Space 拥有的任意 Secret 中取值；一个 Agent 混用好几个分组是很常见的情况。

每个授权项都带有 `required`（默认为 true）。一个必需的授权项如果无法生成，会在 Agent 开始执行之前就让运行失败；一个可选的授权项则会被跳过，并记录这次跳过。

### 6.2 环境变量

有两种形式，由 Agent 自行选择：

- **选定条目。** 指定一个 `secret`、一个 `item`，以及一个变量名。该条目就会以这个名字出现在环境中。来自不同分组的条目可以并排出现——一个 Secret 里的 `GITHUB_TOKEN` 和另一个 Secret 里的 `SLACK_TOKEN`——这是最常见的情况，也是推荐的默认做法，因为这样一份配置读起来就是 Agent 实际使用了哪些值的完整清单。
- **整个分组。** 只指定一个 `secret`，不指定 `item`，这样每一个条目都会以它自己的名字出现，还可以加一个可选的 `prefix`。这就是 Kubernetes 的 `envFrom` 那种形态。之所以支持这种便利写法，是为了让一个已经把凭证分好组的 Space 不必逐一重新列出每个成员，而 §5.1 对条目名的标识符约束，正是让这种写法能够良好定义的原因。

整组交付的形式，会把 Agent 没有逐一命名的条目也交给运行，这进一步扩大了 §3 已经承认的暴露面。这是一个 Space 自己的选择，而不是应该默认采用的做法；Portal 会把它展示成一个整体的分组授权，而不是展开成一份看起来像“每一项都被单独挑选过”的列表。

一个修订版本解析出的变量名之间不能冲突——无论是两个整组授权之间，还是一个整组授权和一个选定条目授权之间——配置保存时会拒绝这种冲突，并提供 `prefix` 作为解决办法。

### 6.3 凭证文件

一个文件授权项指定一个**渲染器**，并把它的参数一一映射好。渲染器是 BuildMax 内置的代码，了解某一类凭证家族的文件布局；Agent 为每个参数提供一个来自 Secret 条目的值或者一个字面值。

| 渲染器 | 目标文件 | 参数 |
|---|---|---|
| `aws_credentials` | `~/.aws/credentials` | `access_key_id`、`secret_access_key`、`session_token?`、`region?` |
| `kubeconfig` | `~/.kube/config` | `server`、`certificate_authority_data`、`token` |
| `git_credentials` | `~/.git-credentials`（+ `~/.gitconfig`） | `host`、`username`、`password` |
| `netrc` | `~/.netrc` | `machine`、`login`、`password` |
| `npmrc` | `~/.npmrc` | `registry`、`auth_token` |
| `docker_config` | `~/.docker/config.json` | `registry`、`username`、`password` |

一个参数，要么通过一个 `{secret, item}` 引用来满足，要么通过一个字面值来满足。字面值正是集群 server URL 和 CA 证书应该存放的地方——挂在 Agent 上，可读，不封在 Secret 里。`region` 就是一个字面值；只有真正敏感的那个参数才是一个条目。

`target_path` 和文件的 `mode` 由渲染器而非自由文本掌控，这正是让 §8.3 的写入约束能够被强制执行的关键：Agent 选择一个渲染器、填好它的参数，但从来不能自己指定输出路径，所以它没法渲染进 `.bashrc`。内置渲染器覆盖了常见的凭证家族；为 BuildMax 尚未内置支持的家族提供一个 Space 自定义模板，是 Phase 2 的一个开放问题（§20），不属于第一版形态的范畴。

一个文件在以下条件都满足时才算校验通过：每个必需参数都被满足、每个被引用的 Secret 都属于该 Agent 所在的 Space、每个被引用的条目都出现在该 Secret 的 `item_names` 中。

### 6.4 同一个条目被使用两次

没有什么能阻止同一个条目同时喂给一个环境变量授权和一个文件参数——比如同一个令牌，既作为 `GH_TOKEN` 有用，又可以作为 `git_credentials` 渲染出的 `password`。两者在给定的一次运行中都从该 Secret 当前的条目中解析，快照会分别记录每一个目标。

## 7. 运行生命周期

```text
Space Owner                 Server                         Worker
    |                         |                              |
    |-- write/rotate Secret -->| re-encrypt the item map    |
    |-- configure consumption->| validate same-Space ownership|
    |                         |                              |
    |                    dispatch TaskRun                    |
    |                         |-- resolve Agent revision     |
    |                         |-- read its consumption config|
    |                         |-- snapshot task_run_secret   |
    |                         |                              |
    |                         |<---- claim with run token ---|
    |                         |-- require live matching run  |
    |                         |-- decrypt current items      |
    |                         |-- exchange short-lived creds |
    |                         |-- return computed bundle --->|
    |                         |                              |-- set declared env grants
    |                         |                              |-- render declared files
    |                         |                              |
    |                         |<---- report terminal state --|
    |                         |-- revoke leases, close grant |
```

这份快照发生在 Agent 修订版本和插件的固定版本都已经解析完毕的那一刻——也就是 worker 领取运行的时候。条目只在领取时解密一次，因此即便一次轮换紧接着落地，这次运行读到的依然是一份自洽的映射。解析过程从不使用 worker 提供的任何值，worker 也无法浏览 Space 的状态。

面向 worker 的这个操作，返回的是为某一个 TaskRun 计算好的完整数据包。它不接受任何 Secret ID、名字或提供方路径作为输入。它的路由注册在 `internal/server/handlers/routes.go` 中，构建时在 `internal/server/static/openapi.json` 中描述。

具体化需要同时满足：一个有效的运行令牌，其对应的运行与路径匹配；一个处于预期执行状态、尚未终止的运行；已固定的修订版本对应的消费配置；一个已启用的 Secret，其当前条目仍然满足该配置；以及一个已配置、健康的后端。

响应通过 TLS 传输，设置 `Cache-Control: no-store`，并绕开请求体日志记录。允许对一次失败的拉取进行重试——如果一个丢失的响应会永久性地拖垮一次原本有效的运行，那“精确读取一次”就毫无意义——每一次成功的具体化都会被记录下来。

## 8. 交付方式

两种模式。每个 Agent 修订版本各自独立配置；§6 说明了具体方式。

### 8.1 前提条件：运行级的 `HOME`——已实现

在运行拥有自己的操作系统 `HOME` 之前，这两种模式都谈不上有良好定义。一个 worker 早已经拥有一个运行级的 `BUILDMAX_HOME`（该运行的全局目录，`RuntimeTaskRunGlobalDir`）和一个装着 space 持久化文件的运行级目录（`RuntimeTaskRunHomeDir`），但它的操作系统 `HOME` 此前一直是容器镜像设定的那个值，在同一个容器里的每次运行之间是共享的。

这个问题现在已经解决。`taskrun` 为每次运行都创建一个专用的、空的操作系统 `HOME`——`<run-dir>/oshome`，与上面两个目录都不同，以 `0700` 权限创建，在这次 Agent 运行期间被设置为 `HOME` 和 `USERPROFILE`，并随着这次运行的临时目录树一起消失。它刻意不是 `RuntimeTaskRunHomeDir`：那个目录装的是 space 具体化后的文件，不该用来放一次运行私有的工具状态或者渲染出的凭证；它也刻意不是 `BUILDMAX_HOME`，因为那个全局目录会在运行结束后被上传——而一个渲染出的凭证绝不能被上传。之所以需要它，有两个原因：渲染出的凭证文件需要一个工具默认会去查找的私有位置；以及任何工具写进 `~/.config` 的内容，都不能残留进一次无关的运行里。

### 8.2 环境变量

运行时会把每一个 `env` 授权项放进这次运行所执行命令的环境中：选定的条目以 Agent 指定的变量名出现，或者一个分组的每个条目以自己的名字出现，可以带一个可选前缀（§6.2）。

这是通用模式。它不需要工具方面的任何配合，覆盖非 HTTP 协议，也适用于运行过程中现写的程序。每当某一类凭证没有文件约定时，这就是兜底方式，也是最先实现的模式。

有两条规则约束它：

- 一个授权项只会出现在配置解析出的那个名字下，绝不会另外以一个猜测出来的别名重复导出；并且
- 除此之外，这次运行的环境仍然是 §13.1 描述的默认拒绝基线，而不是 worker 继承来的环境。交付已声明的授权项，不构成停止隐藏部署自身凭证的理由。

### 8.3 运行级凭证文件

运行时会执行一个渲染器（§6.3），按照凭证家族本身已经定义好的布局，把一个文件写进这次运行的 `HOME` 下，工具会自己找到它。每个参数都在 Agent 开始执行之前，从一个 Secret 条目或一个字面值解析出来。

这里的单元是凭证家族，而不是工具——这正是让工作量保持有限的关键。一份渲染出来的 `~/.aws/credentials`，可以同时服务 AWS CLI、每一种语言的 SDK，以及 Terraform。一份渲染出来的 `~/.git-credentials` 配上它的 `~/.gitconfig`，可以服务 `git` 以及所有会调用 `git` 的东西。这种模式的存在有两个不同的理由：

- 有些凭证家族根本没有可用的环境变量形态——`~/.kube/config` 和 `~/.docker/config.json` 承载的结构，单个变量装不下；并且
- 即便某种环境变量形态确实存在，文件形态还能额外触达那些只读配置文件的工具。

写入约束，全部强制执行：

| 约束 | 原因 |
|---|---|
| 目标路径解析后必须落在这次运行的 `HOME` 之内 | 工作区下的一个文件，离被一次 `git add -A` 提交只有一步之遥，也是 artifact 上传的候选对象 |
| 不允许 `..` 路径穿越，不跟随符号链接 | 出于同样的理由，防止另一条路径绕过限制 |
| 权限 `0600`，永不可执行 | 凭证文件是数据，不是程序 |
| 拒绝 shell 启动文件和携带命令的目标——`.bashrc`、`.profile`、`.zshrc`、git 配置里命名了一条命令的键 | 渲染进这些位置等于把代码注入了这次运行，而不是在交付一份凭证 |
| 运行结束时删除 | 运行目录反正也会被删除；但这一点不能依赖于那次删除 |

### 8.4 两者兼用

一个 Agent 可以把同一个条目既放进一个变量，又接入渲染器的一个参数（§6.4）。两者在给定的这次运行中都从该 Secret 当前的条目中解析，快照会分别记录每一个目标。如果某个凭证家族的文件形态本身引用一个变量而不是直接内嵌值，渲染器就会采用这种形态。

## 9. 存储后端

### 9.1 内嵌加密存储

这是开箱即用的私有化部署的默认选项。MySQL 中只存储密文和被封装的数据加密密钥。

每个 Secret 的条目映射都用 AES-256-GCM 或经过同等审查的 AEAD 算法加密，使用一个全新的随机 DEK 和 nonce，每次编辑都整体重写。关联数据（associated data）把密文绑定到 Space 的公开 ID 上，因此一份密文如果被搬到另一个 Space 的数据行里就会认证失败——这正是威胁模型要防御的那种跨 Space 隔离。除此之外，关联数据不绑定任何其他东西。不同部署之间的隔离本身已经是密码学层面的：另一个部署使用不同的 KEK，DEK 的解封装在触及 GCM 之前就会失败；反过来，如果把部署 ID 也写进关联数据，则会破坏一种灾难恢复副本——它故意共享 KEK 以便读取相同的数据行。关联数据也不绑定 Secret 的公开 ID：那个 ID 是在数据行插入时才铸造出来的，晚于值被密封的时刻；而在同一个 Space 内部调换密文，需要数据库写权限，而这正是威胁模型本就信任的部署运维者所拥有的权限。

DEK 由一个 KEK 封装，而 KEK 永远不属于数据库或 `server.yaml` 的内容。一个 KEK Provider 接口（§16）有三种实现，由部署方选择其一：作为可移植基线的、挂载进来的密钥文件，使用工作负载身份的云 KMS，或者部署方本就在运行 Vault 时使用的 Vault transit key。数据行上的 `key_id` 标明是哪个 KEK 封装了这个 DEK，因此解封装时能选中正确的密钥，而不必存储任何密钥本身的值。

**默认选项是挂载的密钥文件，以下这些属性是被明确决定的，而不是留给实现随意发挥：**

- 该文件以只读方式挂载进 Server 进程，权限为 `0400`，不能位于任何工作区、`BUILDMAX_HOME`、artifact 路径或轨迹路径之下。通过 Kubernetes Secret 或 Compose 卷来交付这个文件。
- **`key_id` 的格式是 `<backend>:<name>:<version>`**——比如 `file:root:1`、`vault:transit/buildmax:2`、`kms:<alias>:<ver>`。后端前缀不是装饰性的：一个从文件后端迁移到 KMS 的部署，会同时保有由这两种后端各自封装过的数据行，解封装时必须能路由到正确的那一个。`name` 允许存在不止一个逻辑根密钥，`version` 则是轮换计数器。对文件后端而言，这个字符串本身就是映射表的键。
- **文件里存放的是一组 KEK，而不是一个。** 它是一个从 `key_id` 到密钥材料的映射，外加一个指向“新写入使用哪个 KEK”的指针。如果只有单个密钥，数据行上的 `key_id` 版本号就毫无意义，KEK 轮换也会变成一次停机式的整体重新加密。有了一组密钥，轮换只需新增一个 KEK、挪动指针，再在后台把每一行的 `wrapped_dek` 重新封装一遍——`ciphertext` 从不改变，因为 DEK 本身没有变。
- **KEK 绝不通过环境变量传递**，哪怕只是为了 Compose 场景的便利。进程环境对该进程及其子进程可见，而这正是整个设计要为一个值刻意规避的那种暴露面；能解封装所有值的那把根密钥，是最不应该放在那里的东西。Compose 会像其他任何部署一样挂载这个文件。

DEK 的轮换不需要任何专门操作：每次编辑都会用一个全新的 DEK 重写这个 Secret 的数据行，因此一个被攻破或老化的 DEK 会被下一次写入自然替换掉。KEK 的轮换是一次运维者操作，`buildmax-server secret rewrap`，它的机制是这样确定的：

- 运维者生成一个新 KEK，以一个新的 `key_id` 把它加进密钥文件，并把当前指针挪到它上面。新的写入会立即使用它。已有的数据行保留原来的 `key_id`，依然可以解密，因为文件里仍然保留着旧的 KEK。
- `rewrap` 遍历每一行带有 `wrapped_dek` 的记录——Space Secret 的值和受管模型凭证（二者共用部署 KEK），以及日后的外部描述符——对每一行，用该行记录的那个 KEK 解封装出 DEK，再用当前的 KEK 重新封装，并更新 `wrapped_dek` 和 `key_id`。`ciphertext` 始终不变，因为 DEK 没有变。任何关联数据也不会变：DEK 的封装不绑定关联数据，因此一次重新封装不可能扰动其载荷密封时所用的 Space 或凭证 AAD。这个过程是批量执行、幂等、可在中断后恢复的，并且会跳过已经处于目标 `key_id` 的数据行，所以重复运行它总是安全的。它会报告从每个密钥上移走了多少行，然后报告文件中每个密钥仍在保护多少行。
- 它运行时没有停机，也不会锁住这项功能：整个过程中数据行始终可读可写，因为两个 KEK 都同时存在。如果一次并发的编辑已经用当前 KEK 重写了某一行，`rewrap` 在那一行上就无事可做；`rewrap` 使用乐观检查——每一行的写入都以它读到的那个已封装 DEK 为条件——因此它绝不会覆盖一次更新的写入。它不会改动数据行的 `updated_at`：没有任何值发生变化，而模型网关在该时间戳变化时会重建缓存的提供方客户端。
- 把旧 KEK 从文件中移除是一个独立的、显式的步骤，只要还有任何数据行引用着它，这一步就会被拒绝。密钥文件归运维者所有，且只在加载时读取，因此拒绝发生在文件被加载的地方：Server 以及 `rewrap` 本身都会按 `key_id` 统计密封数据行，只要某个被统计到的密钥不在文件中，就拒绝启动，并在错误中写明该密钥及其行数。于是，滚动重启到一份删掉了仍被引用密钥的文件时，会在旧副本继续服务的情况下停滞，而不是让数据行永久无法解密。Space Secret 行的 `key_id` 是它的明文列，因此统计只需一次分组 `SELECT`。模型凭证把 `key_id` 保存在它的密封 blob 内部，这是它唯一被写入的地方；模型目录规模小且由运维者维护，因此统计会读取这些 blob，而不是再保存一份可能与之不一致的副本。在没有配置密钥文件时同样会执行这次统计，因此缺少 KEK 的密封数据会让启动失败，而不是被当作空值读取。`buildmax-server model` 命令加载文件时不做这次统计，因此 `model set-key` 仍可以为一份密钥已丢失的凭证重新密封。

KEK 轮换是一次部署维护操作，不是一次 Space 操作：它会产生一条 Server 运维日志，而不是一条 Space 的 Secret 审计事件（§11），因为没有任何 Space 层面的值发生变化，而审计轨迹本身是按 Space 划分范围的。

当加密数据已经存在、而其 KEK 缺失或不可用时，Server 会启动失败。它绝不能生成一个替代密钥，也不能把值当作空值处理。丢失 KEK 就意味着丢失它封装过的每一个值，备份文档中明确要求：密钥文件要与数据库分开备份、分开托管——一份把两者都包含在内的备份，等于完全没有保护。

### 9.2 外部 Secret 引用

一个外部后端存储的是一个加密的描述符，其中命名了一个提供方、一个由该提供方管理的 Secret，以及一个版本选择器。BuildMax 不会把值复制进自己的数据库。解析时，Server 用自己的工作负载身份完成认证，取回值或一个动态凭证，在可获取的情况下记录精确的提供方版本，并应用与内嵌模式相同的授权与交付规则。

提供方配置是部署范围的，由运维者管理。一个 Space 不能提交任意的 Vault 地址或云端点，把 Server 的提供方身份发送到别处去：由运维者定义具名的提供方、TLS 根证书、region、允许的路径前缀，以及认证方式，一条 Space 记录只能在这些既定选项中挑选。

Vault 是第一个被集成的外部系统，因为私有化部署是一项产品承诺，而 Vault 服务于本地部署下的静态和动态 Secret。AWS 和 Google 会遵循同一套接口。提供方之间的功能对等不是首个切片的要求。

### 9.3 短期凭证

在目标支持的场景下，Server 会在运行开始时，把一个存储的长期凭证交换成一个短期凭证——比如一个 GitHub App 安装令牌、一次 STS `AssumeRole` 的结果、一个 Vault 租约——然后交付这个短期凭证。

这不只是一种便利。在 §2.1 所说的运行级交付之下，值本身是 Agent 可以触及的，因此有效期和提供方一侧的作用域，承担了剩余防泄漏能力的大部分。一个泄露出去的、有效期一小时且仅限某个仓库的令牌，是一次影响有限的事故；一个泄露出去的、存储着的、组织级别的令牌则不是。只要两者都可行，就应该优先选择交换出来的凭证而不是存储的凭证，而 `task_run_secret.expires_at`（§5.2）的存在，就是为了让一次运行和它的运维者能看到这个凭证何时会失效。

工作负载身份——一个专用的 OIDC 签发方，让一次正在运行的 TaskRun 直接与 Vault、AWS 或 Google 完成联合身份验证——是同一个想法去掉了“存储凭证”这一环，它属于最后一个阶段，而不是第一个。

## 10. 授权

角色分为 `owner`、`admin` 和 `member`，定义见 [space-governance.md](Space治理.md)。

| 操作 | Owner | Admin | Member |
|---|---:|---:|---:|
| 列出 Secret 元数据与消费健康状况 | 可以 | 可以 | 不可以 |
| 创建一个 Secret、编辑它的条目、禁用或销毁它 | 可以 | 不可以 | 不可以 |
| 配置一个 Agent 修订版本的 Secret 消费方式 | 可以 | 可以 | 不可以 |
| 保存一个引用了不存在的 Secret 的 Agent 修订版本 | 不可以 | 不可以 | 不可以 |
| 触发一次已经获得授权的 Agent 运行 | 可以 | 可以 | 可以 |
| 读取 Secret 审计事件 | 可以 | 不可以 | 不可以 |
| 回显一个值 | 不可以 | 不可以 | 不可以 |

成员可以通过运行一个由所有者授权过的 Agent 间接使用某个凭证。这对共享自动化来说是必要的，而根据 §3，这也意味着该成员能够读到这个值。这两个事实都必须体现在 Portal 界面上；都不能被暗中回避。

值层面的权限一直留在所有者手中，直到 BuildMax 具备更细粒度的 Space 授权机制；配置消费方式之所以交给 `admin`，是因为这项操作编辑的是 Agent，而 `admin` 本就拥有 Agent，而且这项操作并不会让人获得所有者没有放置过的值的读取能力。如果运维层面的证据表明所有者无法胜任日常的 Secret 管理工作，应该新增一个明确的 `secret_manager` 授权，而不是悄悄放宽 `admin` 的权限。

本设计不依赖尚未构建的审批系统。未来一个针对高风险场景或特定环境的审批机制，可以在不改变存储模型的前提下，对具体化过程加上一道关卡。

## 11. 审计与溯源

审计动作包括：`secret.created`、`secret.rotated`、`secret.disabled`、`secret.destroyed`、`secret.consumption_changed`、`secret.materialized`、`secret.revoked`，以及 `secret.access_denied`。

一条事件记录了操作者、Space、Secret 的公开 ID、Agent 修订版本或 TaskRun、动作本身，以及一份有限的非敏感细节，比如交付方式和目标名称。它绝不携带明文或密文、明文的哈希、提供方令牌、租约 ID、响应体或完整路径、HTTP 请求头或环境变量的值，也不携带 prompt、工具输出、命令参数或文件内容。

现有的审计表可以把一次具体化表示为：以 Secret 为目标、TaskRun 作为有限细节。如果数据量或查询需求让这样做变得笨拙，一个专用的仅追加访问账本是替代方案。两条部分重叠的记录轨迹会比只有一条更糟，所以对“哪些运行具体化过这个 Secret”这个问题，必须有且只有一个权威来源。

轨迹中的溯源信息记录句柄、Agent 修订版本 ID、交付方式、目标名称，以及具体化结果。它不记录任何提供方定位符，也不记录任何值。

## 12. 脱敏

在 Agent 开始执行之前，一次运行具体化出的静态值会注册进一个按运行隔离的精确值脱敏器。`secretscan` 为这些值新增了一个 `Redactor`，本设计所指的几个汇聚点都被覆盖到了：

- **持久化的轨迹**——轨迹的 `Recorder` 携带一个 `Redactor`，它写入的每一个自由文本字段都会先过一遍精确值脱敏，再过一遍基于形状的脱敏；
- **进入模型上下文之前的工具结果**——`RunLoop` 会在 `executeCall` 中对一次工具结果做一次脱敏，发生在它到达 `EventToolEnd` 事件、模型上下文、Hook，以及应用日志（`logToolResult`）之前；并且
- **流式输出**——worker 的流适配器会在每个增量到达观察者之前先对其脱敏。

工具结果和流式输出这两条路径只使用 `RedactExact`——只做精确值匹配，不做基于形状的扫描——因为这两处的输出仍然要被消费者继续阅读：一个正在基于工具结果继续工作的模型、一个正在观看流式输出的人，如果每一个看起来像令牌的子串都被抹掉，输出就会变得面目全非。而持久化的轨迹作为一份诊断用的 artifact，两种脱敏都会应用。

精确值脱敏会忽略空值和过短的值（小于六字节），因此普通输出不会被到处替换掉；它也会跳过过大的值，以免一份很大的证书让每一次脱敏都变得无界。这是纵深防御，而不是一条边界：一次持有某个值的运行，完全可以把它编码或变换成脱敏器认不出的形式，这正是为什么主要的控制手段仍然是不把值交给通用环境，而不是依赖脱敏。

在运行级交付之下，脱敏针对的是**意外**，而不是针对 Agent 本身。一次持有某个值的运行可以对它编码、拆分、变换或传输出去，一个被要求打印出凭证的模型也一定会做到。脱敏的目的是防止一个值意外漂进一份本不打算让它到达的持久 artifact——比如一份发给运维者的轨迹，或者被缓存进一段对话里的工具结果。每一处对它的描述都必须这样说明。

artifact 上传不在脱敏范围内。改写任意的 artifact 内容可能损坏输出，而宣称每一种二进制格式都是安全的又并不真实，所以本设计不对 artifact 做任何数据防泄漏（DLP）方面的声明。对有限长度的文本预览做精确匹配扫描、并给出警告或隔离，是以后可以单独衡量、单独决定的事情。

## 13. 现存的凭证债务

如果只新增 Space Secret，却不把部署层面更广泛的凭证从 worker 里移除，那就等于在一扇敞开的旧门旁边又开了一扇窄窄的新门。在运行级交付之下，这个问题只会更严重，而不是更轻：既然现在期望一次运行只持有属于自己的授权，那么它手里的其他一切东西，也都应该是刻意放进去的。

### 13.1 沙箱环境拒绝列表

`internal/infra/sandbox/env_scrub.go` 会从任何一个沙箱化的子进程中剥离形似 Secret 的变量——一份精确匹配的清单包括 `GITHUB_TOKEN` 和 `GH_TOKEN`，外加一条后缀规则，匹配 `_TOKEN`、`_KEY`、`_SECRET`、`_PASSWORD`、`_PASSWD` 和 `_PWD`。只要沙箱处于启用状态，`Bash.childEnv` 就会应用这条规则——而在 worker 基线上，沙箱始终是启用的。

这在当初是一个正确的直觉，只是用错了层次，并且直接把这个设计彻底挡住了：一个 Space 声明过的 `GH_TOKEN` 授权项，从来到不了 shell；而且因为沙箱在 CLI 基线上默认关闭、在 worker 上默认开启，同一份 Agent 配置在本地能正常工作，在 Pod 里却会静默失效。

**现在已经完成——它变成了在拒绝列表之上叠加的一份允许列表：**

- BuildMax 自身的凭证——`BUILDMAX_RUN_TOKEN`、`BUILDMAX_JWT_SECRET`、`BUILDMAX_API_KEY`——属于一个 `alwaysDenyExact` 集合，任何允许列表都无法把它们重新放行：它们是部署本身的权限凭证，永远不是授予给某次运行的值；
- 这次运行声明过的一个授权名，即便它形似敏感值，也会被放行——`Manager.AllowEnvNames` 记录下这次运行的授权名单，`ScrubEnvList` 会放行它们；并且
- 其余所有形似敏感值的名字，依然像以前一样被剥离。

`agentapp` 把这次运行的授权值设进进程环境，并把授权名传给沙箱，因此像 `GH_TOKEN` 这样的授权项可以到达 Agent 的命令，而运行令牌到达不了。把继承来的环境彻底翻转成默认拒绝——外加一份枚举好的运维基线（`PATH`、`HOME`、`LANG` 等等）——本设计有意不包含这部分：它需要先定义好那份基线，还牵涉到 §20 里的逃逸口开放问题，因此单独处理。删除这个文件从来都不是修复方式；运行令牌本身就是访问托管推理网关和 worker 路由的一份实时凭证。

### 13.2 对象存储

Worker 收到的是长期有效的对象存储凭证。替代方案包括 Server 中介的对象传输、限定运行前缀的预签名请求，或者云工作负载身份——三者分别以 Server 带宽、请求编排开销，或者在 MinIO 部署下的可移植性作为代价。Artifact 上传本就已经走一条运行级别的 Server 路由；工作区和运行状态传输方面的决定，将决定剩下的那份凭证能否被彻底移除。这是一项前置工作，不应该由 Space Secret 这个功能来吸收。

### 13.3 直连模式的模型凭证

托管推理是推荐的云端 worker 模式，因为提供方密钥和上游细节都留在 Server 上。直连模式可以继续用于可信的本地执行，但一个云端 worker 不应该默认收到一份部署范围的提供方密钥。明文存储的 `llm_model.api_key` 会迁移到 §9.1 的加密后端，或者迁移到一个外部的运维者引用。它仍然是部署范围的、仅 Server 可见的；它不会变成一个 Space Secret。

### 13.4 运行令牌的交付

Worker 读取完 `BUILDMAX_RUN_TOKEN` 之后会把它从自身环境中清除，但 Kubernetes 仍然把这个值保留在 Job 规格里（`internal/infra/k8s/job.go`）。为每次运行创建一个不可变的 Kubernetes Secret、以文件形式挂载、附带 owner reference 和收紧的 RBAC，可以把它从 Job 环境中移除，并让垃圾回收跟随 Job 一起进行。这属于纵深防御：无论采用哪种方式，运行令牌本身都始终限定于单次运行、会过期，并且会被终态检查拒绝。

## 14. 失败语义

| 失败情形 | 运行的行为 |
|---|---|
| 一个必需的授权项无法满足 | 在 Agent 开始执行之前失败，并指明是哪个 Secret 的哪个条目或参数 |
| Secret 被禁用、销毁，或缺少被消费的条目 | 在具体化之前失败，并指明是哪个 Secret 和条目 |
| 渲染器的某个参数未被满足 | 在 Agent 开始执行之前失败，并指明是哪个参数；不写出一个不完整的文件 |
| 内嵌的 KEK 不可用 | Server 健康状况降级；拒绝受影响的具体化，而不把值当作空值处理 |
| 外部提供方不可用 | 在一个有限的启动预算内重试，之后以一条脱敏后的、按提供方分类的错误失败 |
| 运行令牌无效或运行已处于终态 | 拒绝该请求，且不透露除了这次运行的授权之外是否还存在某个 Secret |
| 被交换出来的凭证或租约在运行中途过期 | 如果提供方支持，就续期；否则应该失败，而不是继续以未认证状态工作 |
| 到达终态之后撤销失败 | 保留终态结果，记录一条脱敏后的撤销失败信息，在带上限的范围内进行带外重试 |

## 15. API 形态

面向用户的操作是常规的资源型 API，对条目值来说是只写的：列出并获取 Secret 元数据（包括 `item_names`）；创建一个带条目的 Secret；编辑条目；禁用、重新启用，以及销毁。编辑条目在同一个操作上支持两种请求形态——供逐行编辑器使用的逐条目补丁（设置或删除指定的键），以及供原始 JSON 编辑器使用的整张映射替换——因为 Portal 同时提供这两种编辑方式，它们不能演变成两条互相分叉的代码路径。一个 Agent 修订版本的消费配置通过 Agent API 写入，并在那里针对该 Space 的 Secret 做校验；一个只读的消费健康视图，会报告某个修订版本消费的、Secret 已经不再拥有的条目，以及某个渲染器参数找不到任何东西可以满足它。

任何响应都不包含条目的值。一次写入只返回元数据和 `item_names`。携带值的请求字段会被排除在请求日志、校验错误信息和审计细节之外。

面向 worker 的这个使用面，只返回已经为这次运行计算好的授权集合——没有列表、按名字获取，或者提供方查询这类操作。它是 `GET /api/worker/task-runs/{task_run_id}/secrets`，由运行令牌完成认证，其响应携带解密后的值，因此它设置了 `Cache-Control: no-store`，并且走自己独立的路由，而不是走那条携带插件和指令的运行数据包路由。

路由字符串存放在 `internal/server/handlers/routes.go` 中，`internal/server/static/openapi.json` 必须准确描述它们，包括明确不存在回显操作这一点。

## 16. 包边界

| 区域 | 职责 |
|---|---|
| `internal/core/secret` | Secret 元数据、条目映射与密封字节的类型、消费配置、运行授权、错误，以及狭窄的存储接口 |
| `internal/service/secret` | Secret 的生命周期：条目名校验、通过一个 `Sealer` 完成密封、条目编辑（补丁与整体替换）、状态变更、Space 范围限定；后续还包括渲染器参数解析、具体化、交换与撤销 |
| `internal/service/agent` | 在一个 Agent 修订版本保存时，通过一个狭窄的 `SecretLookup` 校验其消费配置是否对应该 Space 现存的 Secret，方式与校验插件选择相同 |
| `internal/infra/secret` | AEAD/信封加密的具体实现、外部提供方适配器，以及凭证交换客户端 |
| `internal/bootstrap` | `buildmax-server secret rewrap` 这条 KEK 轮换命令，与既有的 `run-token` 管理命令并列 |
| `internal/infra/db` | 数据行结构体，以及元数据/密文的持久化；不发起任何提供方调用 |
| `internal/server/handlers` | 用户与 worker 的身份认证、Space 授权、请求/响应的整形。读取 Secret 元数据由 owner 或 admin 完成（`space.ActionReadSecrets`），管理值仅限 owner（`space.ActionManageSecrets`）；所有路由对值都是只写的，在没有配置 KEK 文件时返回 503 |
| `internal/agentapp/taskrun` | 消费一份已授权的内存中授权集合，设置环境变量授权，把渲染器运行进这次运行的 `HOME` |
| `internal/infra/sandbox` | 执行 §13.1 所说的默认拒绝环境策略，并只放行这次运行已声明的名字 |

`internal/core` 不引入任何配置、加密提供方、基础设施、GORM、Server 代码，或者 Agent 应用装配方面的依赖。配置在启动时选择具体的提供方实现；它不解析 Space 资源。Secret 服务采用一个小型的 KEK/提供方接口，因此内嵌、Vault 和云端的具体实现都不会泄漏进 handler 或运行时里。

## 17. 被拒绝的替代方案

### 只做按消费者的注入

只把值交付进被命名的进程——一个 stdio MCP server 的环境变量、一个类型化的 HTTP 授权槽位、交给单个消费者的一个文件——并拒绝交付给模型选择的命令。

这是唯一一个原本能把值挡在通用运行环境之外的被拒绝方案，也是唯一一个能把发行版摘要变成一个可强制执行的交付条件的方案。它被拒绝，是因为它只能触达 BuildMax 已经适配过的那些消费者，而这恰好站在了一个无界集合错误的那一侧：Agent 的核心能力就是在运行时调用它自己选择的工具，而在这种模型下，那些工具什么都收不到。对于未来真正只是单个具名进程的消费者而言，这仍然是正确的形态，而它所需要的那种插件摘要绑定，也会随之回归。

### 凭证助手与 `PATH` 包装脚本

注册一个凭证助手、一个 AWS 的 `credential_process`，或者一个指向某个 BuildMax 代理的 `kubectl` exec 插件；或者在运行的 `PATH` 上放置同名的包装二进制文件，让令牌只能到达其子进程。

这两种方案都是针对一个无界工具集合去做逐工具适配，理由和上面一样。一个通过运行级配置文件配置的版本控制凭证助手是个特例，它几乎不花什么代价，因为它不过是一行生成出来的配置，而不是一个适配器——在这种情况确实成立的地方，它应该归入 §8.3 的文件渲染，而不是作为一种独立机制存在。

### 在沙箱出站代理处注入凭证

在既有的回环代理（`internal/infra/sandbox/proxy.go`）上终止 TLS，为每个目标主机附加一个 `Authorization` 头，再向上游重新建立 TLS。这样值会一直留在 worker 的内存里，永远不会进入运行内部。

这是被评估过的方案中唯一一个能改变 §3 那句诚实表述的方案：Agent 能够行使这份权限，却永远不会持有这个值本身；而且因为代理能看到方法和路径，请求级别的策略也就变得可行了。它还能按目标主机而不是按工具来扩展。

它是因为代价而被拒绝的，不是因为方案本身不好。它需要一个运行级别的 CA，以及一次刻意在运行内部进行的中间人攻击；固定证书（certificate-pinning）的工具会因此崩溃；这个 CA 还必须按每种语言运行时分别安装，这本身就是另外一份清单；而且它对非 HTTP 协议完全无能为力。之所以在这里记录下来，是因为它所需要的那些部件——回环代理、`HostMatcher` 的逐主机匹配规则，以及 `Manager.ChildEnv` 的代理路由——都已经存在，所以以后重新拾起它，是一步比看上去更小的步骤。

### 在 Secret 上加一个 `kind` 字段

给每个 Secret 打上一个凭证家族的标签——`github_token`、`kubeconfig`——并用它来挑选一个默认的文件渲染器。

被拒绝，因为这会让存储层去解释这个值，并且等于断言一个 Secret 就是一整个渲染出的文件，那会把一份 kubeconfig 里本非敏感的 server URL 和 CA 证书也一并封进加密的二进制块里。条目名足以承载一份凭证的结构，而 §6.3 所说的渲染器是在 Agent 一侧选择的。

### 给每个条目加一个“敏感值/配置项”标志位

把每个条目标记为只写或可读，这样非敏感的配置就可以和凭证放在一起，同时依然保持可见——这正是 Kubernetes 在 Secret 和 ConfigMap 之间，以及 GitHub Actions 在 secrets 和 variables 之间划出的那条分界线。

被拒绝，因为这会让每一个 Space 在每一次写入时，都要为每个条目承担一次分类成本，而这个成本原本已经由“放在哪里”回答掉了。一个 Secret 装的就应该是只写的内容；§6.3 的渲染器字面值装的是一个集群本就共享、也理应可读的内容。配置内容在它所在的位置本就是可见的，创建一个 Secret 也就依然只是键入条目名和值。

### 给 Secret 的条目做版本管理

对每一次写入都保留一个不可变的版本，这样一次运行就能固定住一个精确的版本，轮换也就永远不会打扰到它。

被拒绝，因为这是一份没有对应收益的重量。版本表本可以带来的那份正确性——不让任何运行看到一份轮换到一半的凭证——已经由把一个分组的条目存成一整行原子数据（§5.1）实现了：替换那份映射是一次写入，一次运行只在被领取时解密一次。剩下的那个特性——一次进行中的运行仍然持有一个已被替代的值——之所以无关紧要，是因为一次运行不会重新读取，而“一次运行究竟用了什么”这件事，本就已经被 Agent 修订版本上的消费配置固定住了。一张版本表会带来第二份需要对账的历史记录、一个关于废弃运行的保留期问题，以及一条解密旧版本的代码路径，而这一切换来的，只是单行重写方案已经提供的那份保证。如果日后有证据表明确实需要按时间点恢复某个值，这个功能可以再加回来；这里的设计不会挡住那条路。

### 只靠部署环境变量

维持现状，让运维者把每一份凭证都放进 worker 的环境变量里。不需要新的数据库、加密、UI 或提供方代码——但也没有 Space 范围、没有按 Agent 的账号选择、没有轮换，也没有可用的审计。每个 Agent 的每一次运行都会拿到每一个值。

### 一个部署级的全局 Secret 范围

见 §4。被拒绝，因为一个全局值没有可归因的所有者，没有可以从中撤销它的 Space，也回答不了哪些 Space 的运行可以读取它这个问题。

### 只依赖外部 Secret 管理系统

要求必须使用 Vault 或某个云提供方，由 worker 通过工作负载身份检索值，这样能获得强大的提供方侧生命周期管理，但没有任何 BuildMax 自己的值存储。这违背了开箱即用的私有化部署承诺，不同提供方的授权方式各不相同，而且除非经过精心代理，否则会让 worker 具备提供方查询能力。外部后端应该归入 §9.2，而不是取代它。

## 18. 阶段

### 阶段 0 —— 解除阻塞并隔离运行

- **已完成**——为每次运行提供一个专属的、空的操作系统 `HOME`（§8.1），与 `BUILDMAX_HOME` 和 space 文件目录都不同；
- 用 §13.1 所说的默认拒绝、按声明放行的策略，取代 `env_scrub` 的拒绝列表，同时继续拒绝 BuildMax 自身的凭证。这一步会和 Phase 1 的授权交付一起落地，而不是单独落地：在存在一个被消费的名字之前，允许列表都是空的；默认拒绝基线需要先定义好那份运维环境集合；而且它牵涉到 §20 的逃逸口开放问题；
- 用 Server 中介或运行级别的访问方式，取代部署范围内的对象存储凭证（§13.2）；
- 让托管推理成为云端 worker 的默认选项（§13.3）；并且
- 把 Kubernetes 运行令牌的交付方式，从 Job 环境变量中移出来（§13.4）。

操作系统级 `HOME` 和 `env_scrub` 策略，是任何交付得以进行的前提条件；`HOME` 这一半已经完成。剩下的部分必须先明确落实，BuildMax 才能宣称一个 worker 手里只有它这次运行需要的东西。

### 阶段 1 —— 内嵌 Space Secret 与环境变量交付

- **已完成**——`secret` 和 `task_run_secret` 两张表，条目作为一整个加密映射，存储范围校验能在 MySQL 上通过；
- **已完成**——带一个可移植的挂载式 KEK 的信封加密；
- **已完成**——Agent 修订版本上的环境变量消费配置，在修订版本保存时针对该 space 现存的 Secret 做校验，并随修订版本一起打上版本；
- **已完成**——仅所有者可用的创建、条目编辑（逐条目补丁与整体映射替换）、禁用与销毁这几个 HTTP 操作，在一个已配置的 KEK 文件之上才开放，且 Agent 请求本身携带消费配置；
- **已完成**——一条运行令牌驱动的 worker 路由，解析这次运行的 Agent 消费配置，针对这次运行所属的 space 解密每一个授权项，并以一个 `no-store` 响应返回环境变量数据包；worker 拉取这份数据包，把这些授权项设进这次运行的环境，`env_scrub` 允许列表放行这些已声明的名字，同时依然拒绝 BuildMax 自身的凭证。一个被禁用、销毁或已不存在的必需授权项会让运行失败；一个可选授权项则会被跳过；
- **已完成**——一个无法生成的必需授权项，会在 Agent 开始工作之前就让运行失败；一个可选授权项则会被跳过；
- **已完成**——`task_run_secret` 审计快照：worker 路由为每一个被具体化的授权项记录一行，按（运行、Secret、条目）做幂等处理，因此一次重试的拉取只会记录一次，且不携带任何值；这次写入相对于一次已经拿到授权的运行来说是失败开放的；
- **已完成**——按运行隔离的精确值脱敏，把一次运行的授权值从持久化轨迹、从进入模型上下文之前的工具结果（连同 Hook 和日志一起）、以及从流式输出中移除；并且
- **已完成**——Portal 的 Secrets 页面（仅所有者可用，管理元数据与条目，支持行编辑器或原始 JSON 方式创建、逐条目编辑、禁用、销毁，并以一条提示呈现 §3 所说的后果）以及 Agent 一侧的消费编辑器（owner 或 admin 可以在创建和编辑弹窗中，针对该 space 的 Secret 配置一个 Agent 的环境变量授权）。消费健康检查会在编辑器里以及 Agent 卡片上的一个计数，标示出某个已经不可解析的 Secret 或条目授权。Phase 1 已经完成。

环境变量交付优先实现，因为它通用且不需要 renderer。Phase 1 已完成，包括 Portal 界面和精确值脱敏。凭据文件交付及后续后端仍属于 Phases 2–5。

### 阶段 2 —— 凭证文件交付

- §6.3 所说的内置渲染器，先从没有可用环境变量形态的家族开始——`kubeconfig`、`docker_config`——再到那些文件形态能额外提供帮助的家族：`git_credentials`、`aws_credentials`、`npmrc`、`netrc`；
- Agent 修订版本上的文件消费配置，把参数映射到条目或字面值；
- §8.3 的每一条写入约束，由拥有 `target_path` 和 `mode` 的渲染器负责执行；并且
- 同一个条目可以同时用作一个变量和一个渲染器参数。

### 阶段 3 —— 短期凭证交换

- 在目标支持的场景下，于运行开始时完成交换：安装令牌、STS `AssumeRole`、Vault 租约；
- 运行授权项上的 `expires_at`，并对外展示；
- 为那些比凭证寿命更长的运行制定续期行为；并且
- 只要两者都可行，就优先选择交换出来的凭证，而不是存储的凭证。

之所以刻意排在外部提供方之前：在运行级交付之下，凭证的有效期比提供方覆盖的广度，承担了这份设计更多的安全性。

### 阶段 4 —— 外部提供方引用

由运维者配置的提供方记录和路径上限；先接入 Vault，再基于证据决定是否接入 AWS 和 Google；记录精确的提供方版本和访问结果；在支持的地方使用动态租约；记录备份、故障和轮换方面的操作方式。

### 阶段 5 —— 工作负载身份

一个带有轮换签名密钥和 JWKS 的专用 OIDC 签发方；不可变的 TaskRun subject 和 audience claim；与 Vault、AWS 或 Google 交换短期权限；从受支持的路径中移除存储的静态云凭证。

## 19. 验收证据

Phase 1 要在以下条件全部成立之后才能发布：

1. 仅凭一份数据库备份无法恢复出任何值；
2. 没有任何面向用户的操作能回显一个值；
3. 一个 worker 无法获取存储的 TaskRun 授权之外的任何 Secret，一次运行也不会收到其 Agent 修订版本没有配置过的任何东西；
4. 一个消费了另一个 Space 的 Secret 的 Agent 修订版本，在保存时会被拒绝；一个引用了该 Secret 没有的条目的修订版本同样会被拒绝；
5. 轮换一个多条目的 Secret 是原子的：一次运行通过一次解密解析出全部条目，绝不会出现一个条目来自轮换之前、另一个条目来自轮换之后的情况；
6. worker 继承来的环境不会触达模型选择的命令，BuildMax 自身的凭证也绝不会作为授权项被交付；
7. 一次轮换只影响在它之后被领取的运行，绝不影响一次已经具体化过的运行；
8. 一次已到达终态的运行不能再次具体化；
9. 审计和轨迹元数据能解释清楚一次授权的来龙去脉，而不包含任何凭证材料；并且
10. 每一处描述这项功能的界面，都声明了一次运行可以读取它被授予的东西。

配套工作还包括：一次覆盖 nonce 生成、AEAD 关联数据、DEK 封装、KEK 丢失、轮换与销毁的 schema 与密码学审查；一次用正确的 KEK 恢复一份加密备份、并在没有 KEK 时安全失败的运维演练；一次证明 `rewrap` 能在零停机的情况下重新封装每一行数据、能在中断后恢复、并且在仍有数据行引用旧 KEK 时会拒绝移除它的 KEK 轮换演练；一次针对渲染文件的测试，证明每一条写入约束都生效，包括拒绝一个指向 shell 启动文件或运行 `HOME` 之外路径的模板；跨 Space、跨运行的授权矩阵测试；针对 KMS 与 Vault 超时、提供方拒绝、租约过期以及脱敏路径的故障注入测试；以及对 Secret 与对象存储代理环节的延迟测量，以确保这条边界不会形成一个未经审视的瓶颈。

因为这些数据行存在于 `internal/infra/db` 中，这部分范围需要用一个真实的 DSN 跑 `./make test mysql`；一次绿色的 `./make test` 对它们什么都说明不了。

## 20. 开放问题

1. **已决定**——读取 Secret 元数据（列出与获取，绝不包含值）由 owner 或 admin 通过 `space.ActionReadSecrets` 完成；管理值仍然仅限 owner，使用 `space.ActionManageSecrets`。admin 需要这份列表来配置一个 Agent 的消费方式，而元数据本身不携带任何值。
2. 外部提供方的定位符应该和值一起加密存储，还是需要一份数据库可见的提供方元数据来支撑运维和审计？
3. 哪一种对象存储替代方案，能在本地进程、Compose 和 Kubernetes 三种部署形态下，都保持大文件场景下的性能？
4. 一次具体化，应该追加进现有的审计轨迹、一个专用的访问账本，还是两者都要、并且明确以其中一个为准派生出另一个？
5. 当 Agent 循环正阻塞在一次长时间的工具调用中时，一个租约应该如何续期？如果续期无法完成，又会发生什么？
6. 哪些 OIDC claim 是稳定且对 Vault、AWS 和 GCP 都有用的，同时又不会暴露可变的名字？
7. 当一个携带凭证的进程把这个值、或者它的某种变换形式，写进一份输出文件时，什么样的 artifact 处理方式才算诚实？
8. 内置渲染器就足够了，还是某个部署需要 Space 自定义的文件模板——如果需要，`target_path` 和 `mode` 应该如何约束，才能确保一个模板不会渲染进一个 shell 启动文件？
9. 运行的环境基线，是否需要一个运维者逃逸口，以应对那些确实需要把环境层面的配置合法传入运行的部署？还是说一个授权项就能覆盖每一种真实场景？
10. 是否存在某个真实凭证，其在某个时间点恢复值的需求强烈到值得为此重新引入条目版本管理？§17 已经为此留了余地。
