## 1. 决策

P2 让 Portal 的结果呈现成为一等公民之后，平台的下一步是 P3：让私有部署变得平淡无奇、可重复、可诊断。

BuildMax 已经具备主要的运行时组件：

- 服务器二进制
- worker 二进制
- 调度器
- Portal 镜像
- MySQL 持久化
- 本地文件系统与 MinIO/S3 对象存储
- kind 环境搭建
- Kubernetes 部署 YAML

缺口在于部署的闭环。一个新环境应当无需阅读代码就能走完这条快乐路径：

1. 启动基础设施
2. 启动服务器和 Portal
3. 登录
4. 在 Space 中创建工作
5. 运行一个 worker 任务
6. 查看产出的结果

## 2. 产品目标

企业用户或自托管用户应当能够按照一条明确、可观测、可恢复的推荐路径私有化部署 BuildMax。

部署流程应当给人的感觉是：

> 我可以安装它、验证它，并通过清晰的消息理解故障原因。

而不是：

> 我得去翻引导代码、清单文件和历史文档，才能搞清楚哪些变量还有用。

## 3. 当前基线

现有的部署资产：

- `./make kind up` 掌管本地 Kubernetes 循环：创建固定版本的 kind 集群，安装 MySQL、MinIO 和 ingress-nginx，构建并加载镜像，应用清单，并运行确定性的部署冒烟测试。
- `./make kind reload`、`smoke`、`status`、`logs`、`forward` 和 `down` 暴露了更细粒度的生命周期操作，不需要另建一套并行的脚本工作流。
- `deployment/docker/Dockerfile.buildmax` 将 Go 二进制文件构建为一个容器镜像。
- `deployment/docker/Dockerfile.portal` 构建并提供 Portal 静态应用。
- `docs/deploy/local-kind.md` 记录了本地 kind 路径。
- `internal/bootstrap/server.go` 启动数据库、存储、HTTP 服务器和调度器。
- `internal/bootstrap/worker.go` 加载 `server.yaml`，从服务器获取一个已调度的运行，执行 Agent 运行时，并上传产物。
- `internal/config/server_config.go` 是当前生效的服务器/worker 配置加载器。

当前的配置现状：

- `BUILDMAX_HOME` 定位应用数据目录。
- `BUILDMAX_HOME/server.yaml` 是服务器和 worker 的主配置文件。
- `BUILDMAX_JWT_SECRET` 可以覆盖 `server.yaml` 中的 `jwt_secret`。
- `internal/config/env_spec.go` 有意只列出引导阶段的环境变量。
- 文档和清单已重新对齐到 `server.yaml`（见 §4.1）。

## 4. 主要差距

### 4.1 配置合约漂移 — 已解决

**这个差距已经解决。** 实际情况比这里描述的还要糟：清单中的环境变量不只是令人困惑，它们根本就是死代码——已经没有任何地方再读取 `BUILDMAX_DB_*`、`BUILDMAX_MINIO_*` 或 `BUILDMAX_WORKSPACES_DIR`，容器里也没有挂载 `server.yaml`，结果部署出来的服务器会退回内置默认值，并对着 `localhost` 上根本不存在的 MySQL 反复崩溃重启。Worker Job 有着同样的问题。

已经交付的内容：

- `deployment/buildmax-deploy.yaml` 中新增了携带 `server.yaml` 的 `buildmax-config` ConfigMap，通过 subPath 挂载，使 `BUILDMAX_HOME` 的其余部分仍然可写
- 凭证通过环境变量覆盖从 `buildmax-secret` 中读取，作用于 `database.password`、`storage.minio.access_key`/`secret_key` 以及 `conversation.model.api_key`
- worker pod 通过 `worker.k8s.config_map` 挂载同一个 ConfigMap，并将 `BUILDMAX_HOME` 设置为 `worker.k8s.home_dir`
- 运行时配置仍然记录在 `docs/reference/configuration.md` 中；仓库根目录的 `.env.example` 只列出仓库任务所需的个人凭据，不重复运行时配置的内容
- 如果清单和 `internal/config/server_config.go` 再次发生偏离，`TestDeploymentConfigMapLoads` 会让构建失败

尚未在真实集群上验证过——见 §10。

### 4.2 缺少推荐的部署形态 — 已解决

**这个差距已经解决。** `deployment/production/` 就是被认可的标准形态：一份纯 YAML 清单，面向一个已经自行运行着 MySQL、对象存储、ingress 和证书的集群，外加一份 README，写明每个依赖必须满足的契约。它刻意不做成一个 chart，这样才能转换成集群现有的任何管理方式；每个依赖地址都是占位符，因此未经修改直接 `kubectl apply` 会直接失败，而不是悄悄连到错误的数据库上。

它固定下来的架构是：

- Server Deployment
- Redis 协调 Deployment 与 Service
- Portal Deployment
- 由调度器启动的 Worker Job
- 外部 MySQL
- 外部 S3 兼容存储
- 承载非敏感 `server.yaml` 的 ConfigMap
- 承载 JWT、LLM API key、数据库密码、S3 secret 的 Secret
- 让 Portal 和 API 共用同一个源的 Ingress
- 使用 `coordination.mode: redis` 的两个 Server 副本

这个形态目前*还缺少*的是运营层面的证据：没有做过恢复演练，没有跨 schema 变更的升级/回滚演练，没有指标，也没有在真实云账号上跑过。这些是下文的待解决问题 6–9，而不是形态本身的缺口。

### 4.3 健康检查与启动诊断薄弱

部分已解决。`GET /readyz` 现在会报告服务器是否可以对外提供流量，`/healthz` 则保留其存活语义——见下文待解决问题 2。参考清单把就绪探针指向 `/readyz`，存活探针仍留在 `/healthz` 上。

已交付：

- 数据库可达
- 对象存储可达

仍未解决：

- worker 启动模式有效
- 在需要的地方（如对话标题生成、运行时路径），LLM 配置可用

存储写权限属于**部署初始化**阶段该关心的问题，不是就绪检查该关心的问题。生产参考要求对专用 bucket/prefix 拥有读、写、列举权限，而 `/readyz` 刻意只验证只读依赖的可用性。如果每次就绪检查都去写一次，就等于让 kubelet 的探测逻辑去持有对象及其保留策略，这不是它该管的事。

BuildMax 不会自己去证明这些权限是否到位，以后也不会。bucket、它的策略以及工作负载身份，都是由部署方自己来配置的，他们自己的工具链证明这项授权比启动探针重复验证一遍更可靠。kind 冒烟测试是针对开发环境的 MinIO 实例走通这条路径的；改造后的生产清单则需要由运维方自行验证。

### 4.4 Worker 端到端路径需要一次验证

验收路径不只是"服务器能启动"这么简单。

它必须证明：

- 调度器能够认领待处理的 task run
- worker 能以选定的模式启动
- worker 能调用服务器的 worker API
- worker 能物化 Space 的工作目录（home）
- worker 能写入 `artifacts/result.md`
- 服务器能通过 artifact 相关端点呈现结果

## 5. 范围内

### 5.1 部署配置标准化

定义唯一生效的部署配置契约：

- `server.yaml` 是服务器和 worker 配置的规范文件。
- 环境变量仅用于：
  - `BUILDMAX_HOME`
  - 类似 `BUILDMAX_JWT_SECRET` 这样的敏感值覆盖
  - 仅测试使用的值
- Kubernetes 使用：
  - 用 ConfigMap 承载 `server.yaml`
  - 用 Secret 承载敏感值
  - 只在代码明确支持覆盖的地方使用环境变量

### 5.2 本地 kind 路径

让本地 kind 路径完全打通端到端：

```sh
./make kind up
./make e2e kind
```

然后验证：

- Portal 能在 `http://localhost:8080` 打开
- API 健康检查在 `http://localhost:8080/healthz` 正常工作
- 登录正常
- 一个任务能够通过 worker Job 跑通
- 结果能在 Portal 中看到

### 5.3 生产参考路径

补充面向生产环境的部署文档：

- 所需服务
- 配置文件示例
- 敏感信息示例
- 镜像标签
- 迁移预期
- 存储持久化预期
- ingress/TLS 预期
- 备份边界

在第一个交付切片里，这不需要做成一个完整的 Helm chart。

### 5.4 启动错误与健康检查

改进启动和健康诊断，让常见的配置错误有一个清晰的失败表现。

必须的检查项：

- `jwt_secret` 已配置
- `workspaces_dir` 已配置
- 数据库连接成功
- 存储后端配置有效
- 在已配置的情况下，MinIO/S3 客户端能连通 bucket
- worker 模式有效
- 使用 `local_process` 时 `worker.binary` 存在
- 使用 `k8s_job` 时 Kubernetes job creator 可用
- `worker.llm.transport` 指定的是当前部署确实能提供服务的模型策略

### 5.5 初始管理员 / Space / 配额方案

引导方案已经落地。自助注册默认关闭。运维人员通过 `buildmax-server user create` 创建账号及其个人 Space，签发一次性登录码，再通过单独的 `buildmax-server admin grant` 授予部署管理权限。默认配额档位和 Space 所有者身份的创建都不需要手动改数据库。参见 M5 和[部署身份认证](../deploy/authentication.md)。另外，启用 OIDC 的部署可以在显式域名策略下 JIT 预配普通账户；该路径由[企业身份与访问](企业身份与访问.md)负责。

## 7. 目标部署架构

推荐的 MVP 拓扑：

```text
User
  |
  v
Ingress
  |---------------------------|
  v                           v
Portal Service                API Service
Portal Deployment             buildmax-server Deployment
                              |
                              v
                         Scheduler
                              |
                              v
                         Worker Job(s)

Shared dependencies:
  - MySQL
  - MinIO/S3
  - Kubernetes Secret
  - Kubernetes ConfigMap containing server.yaml
```

服务器进程同时拥有 HTTP API 和调度器。Worker 是独立的进程或 Job。服务器和 worker 读取同一份配置契约。

## 8. 配置形态

### 8.1 `server.yaml`

部署用的 ConfigMap 应当挂载一份完整的 `server.yaml`。

示例形态：

```yaml
port: 5678
cors_origin: "https://buildmax.example.com"
workspaces_dir: "/buildmax/workspaces"
default_quota_tier: "free_trial"

database:
  host: "mysql"
  port: 3306
  user: "buildmax"
  password: ""
  name: "buildmax"

storage:
  persist_backend: "minio"
  artifact_backend: "minio"
  minio:
    endpoint: "http://minio:9000"
    region: "us-east-1"
    access_key: ""
    secret_key: ""
    bucket: "bmstore"
    prefix: "workspaces"

worker:
  run_mode: "k8s_job"
  server_url: "http://buildmax.buildmax.svc.cluster.local:5678"
  run_token_ttl: 24h
  run_timeout: 6h
  k8s:
    namespace: "buildmax"
    image: "buildmax:local"
    resources:
      cpu_request: "500m"
      cpu_limit: "2"
      memory_request: "1Gi"
      memory_limit: "4Gi"

conversation:
  model:
    model: "openai/gpt-4o-mini"
    api_url: "https://openrouter.ai/api/v1"
    api_key: ""
    context_window: 0
    call_timeout: 60
```

生产参考把形态和非敏感值放在 ConfigMap 中，敏感字段则通过受支持的环境变量覆盖注入：

- 非敏感值放在 ConfigMap 中
- 敏感值放在 Secret 中
- 在必要之处，由少量引导代码支持敏感值的环境变量覆盖

### 8.2 敏感值

敏感值包括：

- `jwt_secret`
- 数据库密码
- S3 access key 和 secret key
- 对话模型 API key

受支持的覆盖变量是 `BUILDMAX_JWT_SECRET`、`BUILDMAX_DATABASE_PASSWORD`、`BUILDMAX_STORAGE_MINIO_ACCESS_KEY`、`BUILDMAX_STORAGE_MINIO_SECRET_KEY` 和 `BUILDMAX_CONVERSATION_MODEL_API_KEY`。它们的优先级和完整名称记录在[配置参考](../reference/configuration.md)中；本设计文档不重复维护第二份权威清单。

## 9. 实施计划

### M1. 配置合约清理 — 已完成

- ✅ 部署清单从 ConfigMap 挂载 `server.yaml`。
- ✅ 已删除过时的环境变量；保留下来的都是代码里实际绑定的覆盖项。
- ✅ 提供了文档化示例：`config-examples/server.example.yaml` 加上 `docs/reference/configuration.md`。
- ✅ 运行时配置不会重复写进 `.env.example`；这份文件专门留给仓库任务使用的个人凭据。
- ✅ `README.md`、`CONTRIBUTING.md` 以及 kind 指南（现为 `docs/deploy/local-kind.md`）都与 YAML 配置契约保持一致。

验收标准，两条均已满足：

- 新读者能准确说出每个配置值的来源——形态来自文件，凭据来自环境变量
- `deployment/buildmax-deploy.yaml` 与 `internal/config/server_config.go` 保持一致，现在由测试而非人工审查来保证

### M2. kind 端到端路径 — 已完成

`./make kind up` 掌管当前的本地 Kubernetes 路径：创建或复用固定版本的 kind 集群，安装配套的 MySQL/MinIO/ingress，构建并加载镜像，应用部署清单和确定性的模型配置，然后运行冒烟测试。基础清单通过 Redis 协调运行两个 Server。冒烟测试会登录、验证 Space 边界、创建并运行工作、读取其产物，证明重试会产生第二次真实执行的 run，并演练取消。托管（managed）变体还会验证运行范围的凭据和调用流水账（ledger）。

旧的 `./make setup && ./make deploy` 写法已经不存在了：`tools/mk` 不再响应这两个名字，`./make kind up` 是唯一的路径。

验收已满足：

- `./make kind up` 能看到 Portal 且 worker 能成功产出结果；
- 合并后与定时 CI 都会运行相同的 kind 和 Compose 冒烟路径。

### M3. 健康检查与就绪状态

- 保留 `/healthz` 作为低开销的存活检查。
- 新增一个就绪端点，或者在需要身份认证/管理员权限的路由后面丰富健康检查的输出。
- 检查数据库和存储依赖。
- 为 worker 模式和存储配置错误增加清晰的启动报错。
- 增加 Kubernetes 就绪/存活探针。

验收标准：

- 数据库故障、bucket 缺失或 worker 模式无效时，都有一项明确失败的检查项

### M4. 生产参考指南 — 已完成

`deployment/production/` 承载着清单和指南：镜像、配置、敏感信息、存储、数据库、ingress/TLS、worker 模式、备份边界和升级步骤，这份参考刻意没有覆盖的内容也明确写了出来，而不是留给读者自己去发现。`manual/support.md` 承载的是兼容性那一半——一次升级对 schema、API、配置键和已存数据能做什么、不能做什么。`internal/architecture` 用和服务器解析自身配置相同的方式去解析清单里的 ConfigMap，所以两者不可能出现偏差。

验收已满足：仅凭这些文档，无需阅读 Go 引导代码，就能规划出一次私有部署。尚未满足、且作为待解决问题而非本里程碑一部分来跟踪的是：这份参考从未在真实的托管数据库或对象存储上应用过。

### M5. 管理员引导方案 — 已完成

私有部署默认关闭自助注册。运维人员通过 `buildmax-server user create` 创建账号及其个人 Space，签发一次性登录码，再用单独的 `buildmax-server admin grant` 授予部署管理权限。这些命令都会记录审计日志；之后日常的 Space 管理交给 Portal 处理。具体流程及其恢复语义见[部署身份认证](../deploy/authentication.md)。

验收已满足：运维人员无需修改数据库，就能创建第一个用户、Space、角色、配额档位和系统管理员。


```sh

```

```sh

```

1. 打开 Portal。
2. 登录。
3. 创建或选择一个 space。

5. 运行工作。
6. 确认 worker 执行完成。
7. 确认结果/产物可见。

## 11. 风险

- **配置分裂带来的困惑**：如果文档和代码没有精确定义优先级，YAML 加环境变量覆盖的组合很容易让人搞不清楚。
- **敏感信息泄露**：开发环境的清单里带有明确标注的占位值；生产环境必须使用文档中记录的、由部署 Secret 支撑的环境变量覆盖。
- **kind 跑通掩盖生产环境的差距**：本地路径应当只是一份参考，而不是唯一有文档记录的形态。
- **worker 模式漂移**：本地进程模式和 Kubernetes Job 模式必须使用相同的运行生命周期和存储假设。
- **存储静默失败**：存储检查必须是显式的，因为结果能否可见取决于产物（artifact）。

## 12. 待解决问题

1. ~~BuildMax 应该为 `server.yaml` 中所有敏感字段都支持环境变量覆盖，还是挂载一份由 secret 渲染好的配置文件？~~ **已决定：使用环境变量覆盖。** 生产清单从 Secret 中取值，ConfigMap 只承载非敏感的形态。
2. ~~P3 应该引入 `GET /readyz`，还是让 `/healthz` 感知依赖状态？~~ **已决定：单独引入 `/readyz`。** 如果让 `/healthz` 感知依赖，两个探针就会得到同一个答案，而 Kubernetes 对它们的处理方式截然不同：就绪检查失败会停止流量，存活检查失败则会重启容器。共用一个端点，会导致每一次数据库抖动都变成对一个原本运行正常的服务器的重启。
3. ~~如果当前的服务器路径并不需要 Redis，环境搭建中是否还要保留它？~~ **已被后续的 Server 协调决策取代：基础/kind 和生产的多副本参考保留 Redis；单 Server Compose 不需要。** 两份集群清单现在都配置 Redis 与两个 Server 副本。参见[服务器协调](服务器协调.md)。
4. ~~推荐的生产路径应该只使用 Kubernetes Jobs，还是把 `local_process` 也记录为单节点选项？~~ **已决定：Kubernetes Jobs 是推荐的生产路径，`local_process` 作为单机选项继续得到支持，但要说明清楚它的信任域。** 本地 worker 是服务器在同一个 uid 下的子进程，不管怎么收窄它能继承的东西，都无法把它变成一个边界。与其去加固一个本来就撑不起边界的拓扑，不如在部署文档里说清楚：在这种情况下服务器和 worker 共享同一个信任域；如果某次部署需要把它们隔开，就用 `k8s_job`。
5. ~~私有部署是否应该默认允许自助注册？~~ **已决定：不允许。** `allow_signup` 默认是 `false`；账号由运维人员创建，并签发一次性登录码。

剩下的问题来自已退役的《私有生产运营》提案。它当初要求的参考拓扑现在已经存在；它要求但还没有得到的，是这套拓扑真的能被运营起来的证据。所需的演练及其仍待补齐的证据记录在[Beta 就绪记录](../deploy/beta-readiness.md)中：

6. 对第一个 Beta 来说，怎样的可用性和恢复目标才是现实的？部署参考文档写明了恢复的*操作步骤*——从备份恢复、回滚到上一个镜像标签——但没有说明它能达到什么样的目标。
7. 恢复流程真的演练过吗？要恢复一个 space 和一次已完成的 run，需要数据库和 bucket *一起*恢复，但目前没有任何证据证明两者恢复后是一致的。
8. 是否演练过候选版本声明的模式路径和恢复？Alpha 迁移可放弃兼容；须明确起始模式，测试声明支持的二进制回滚，或证明破坏性切换的恢复路径。`manual/support.md` 不承诺普遍的 N-1 兼容。
9. ~~哪些指标能让一次部署变得可支撑（supportable）？~~ **针对第一个 Beta 已决定：指标端点不是前提条件。** 最小的诊断集合是日志、`/readyz`、系统状态、TaskRun 与产物状态、运行轨迹、托管调用流水账和审计历史。资质演练必须证明这一集合足以解释所有必需的结果。只有当某次演练指出一个现有界面无法提供的具体信号时，才后续补上 `/metrics`。
10. JWT 签名密钥、access/refresh 会话、按次运行的令牌、数据库、存储以及模型凭证要如何**轮换**？注入方式已经定了——从 Secret 读取的环境变量覆盖——但没有任何文档说明一次轮换会对已有会话、正在进行的 task run，或是已经持有 run 令牌的 worker Job 造成什么影响。
11. Kubernetes、MySQL 和 S3 兼容存储的哪些版本构成受支持矩阵？`manual/support.md` 对各个界面和平台做了分级，却没有点名具体的依赖版本；`deployment/production/README.md` 给出的则是一份行为契约，而非版本列表。
