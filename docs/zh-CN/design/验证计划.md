## 1. 决策

BuildMax 将维护一套按风险加权、包含四道关卡的验证计划：

| 关卡 | 目的 | 依赖 | 预期节奏 |
|---|---|---|---|
| Pull Request | 快速拒绝确定性代码、契约、授权、持久化以及关键旅程方面的回归。 | Go、前端范围所需的 Node，以及 CI 中的原生 MySQL。 | 每一次变更。 |
| 计划部署 | 演练真实进程、浏览器、存储、直接与托管推理、Worker 生命周期，以及受控故障。 | Compose 与 kind。 | 合并之后、按计划，或手动触发。 |
| 发布候选 | 在带有外部依赖的私有部署中，证明不可变构建产物、恢复、升级、回滚，以及凭证轮换均可用。 | Kubernetes、外部 MySQL、S3、TLS。 | 每一个候选版本。 |
| 产品评估 | 衡量受支持的模型使用一个接线正确的产品时，可靠程度如何。 | 真实模型凭证，以及明确的 token 预算。 | 有意安排的资格认证运行。 |

这几道关卡回答的是不同的问题。一个真实模型的分数，不能证明授权、持久化或取消逻辑
接线正确。一次确定性冒烟测试，也不能证明模型确实能可靠地使用这个行为。两者都无法
替代一次外部的恢复与升级演练。

本计划扩展的是现有的任务运行器和它的工作流体系；新增的测试行为应当归属于
`tools/mk` 以及现有的工作流分组之下，而不能引入一套并行的 shell 脚本命令界面。

## 2. 验证矩阵

当下面的第一个旅程接入之后，创建 `docs/contribute/verification-matrix.md`。它是
一份从产品声明指向证据的、承载状态的索引，而不是一份测试文件目录。

矩阵的每一行记录：

| 字段 | 含义 |
|---|---|
| 旅程 ID | 本记录中稳定的 `Vxx` 标识符。 |
| 用户结果 | 用户或运维人员能够观察到的内容，而不点名某个具体的实现函数。 |
| 涉及界面 | 涉及的 CLI、Desktop、Portal、Server、Worker 或部署边界。 |
| 风险 | 安全性、数据完整性、执行安全、可靠性，或产品质量。 |
| 确定性证据 | 证明正常路径的确切测试或套件。 |
| 真实依赖 | 该证据所需要的 MySQL、对象存储、浏览器、Kubernetes 或模型。 |
| 故障证据 | 确切的受控故障，以及预期的终态。 |
| 关卡 | Pull Request、计划部署、发布候选，或评估。 |
| 最近一次验证 | commit、日期、环境，以及证据包引用。 |
| 缺口 | 当所需的某一层不存在时，填写 `missing` 并给出具体原因。 |

规则：

- 每一项被标记为完成的路线图能力，都必须至少对应一条旅程；
- 空单元格视为无效——要么填 `not applicable`，要么填一个明确的缺口；
- 一个通过的单元测试不算部署证据或运行证据；
- 矩阵链接的是证据，而不是照抄日志或状态描述；
- 自动化任务负责更新机器可读的结果数据，维护者则在某项能力的边界发生变化时更新
  这份承载状态的矩阵；
- 已经过时的旅程，连同它们描述的行为一起删除；Git 历史就是归档。

## 3. 关键用户旅程

第一份矩阵包含以下这些旅程。它们被有意选定为跨包、且用户可见的场景。

| ID | 旅程 | 必须满足的可观察结果 | 最低关卡 |
|---|---|---|---|
| V01 | CLI 修改一个工作区文件 | 目标内容发生变化，工作区之外的路径不受影响，会话历史与轨迹能够解释这次工具使用。 | Pull Request |
| V02 | CLI 恢复并压缩一个会话 | 选中的会话得以恢复，上下文来源保持正确，压缩过程保留了必要的状态，任务顺利完成。 | Pull Request |
| V03 | Desktop 完成同一个本地 Task | Desktop 的桥接层组装出共享运行时，正确呈现审批与事件，并以与 CLI 一致的方式持久化会话。 | Pull Request |
| V04 | 用户登录并结束一个会话 | 登录码一次性使用且会过期；刷新令牌轮换、登出以及被吊销的凭证，均针对真实存储表现正确。 | 带 MySQL 的 Pull Request |
| V05 | Space 之间相互隔离 | 即便拿到有效的公共 ID，Space A 的成员也无法读取、修改、流式获取或下载 Space B 的资源。 | 带 MySQL 的 Pull Request |
| V06 | Portal 完成一次前台 Conversation 回合 | 流式传输、持久化历史、刷新、重连，与最终呈现结果保持一致。 | 计划部署 |
| V07 | 多个回合指向同一个 Conversation | 各回合按提交顺序执行，队列有边界，不丢失任何一个，且不会有两个回合同时修改同一个 Conversation。 | Pull Request 加计划中的多进程验证 |
| V08 | 一个 Issue 产出一次后台结果 | Task、TaskRun、Worker 认领、模型/工具执行、Artifact 与 Issue 结果投影，在不要求 Conversation 的情况下构成一条可解释链路。 | 带 MySQL 的 Pull Request 加计划部署 |
| V09 | 直接 Task 结果经受重连与重启 | TaskRun 始终是权威结果；刷新后的 Task 页面能重建其线程；重连或 Server 重启不会产生重复的 run、输出、Artifact 或用量记录。 | 计划部署 |
| V10 | 一个正在运行的 Task 被取消 | 该次运行到达 `CANCELED`，停留在终态，不再产生新的工作，保留可用的证据，并且不暴露任何不可用的 Artifact。 | 计划部署 |
| V11 | 一个失败的 Task 被重试 | 重试会创建一次明确的新尝试，保留旧的尝试记录，并且不会重复输出、用量或 Artifact。 | 带 MySQL 的 Pull Request |
| V12 | 一个 Workflow revision 按线性方式运行 | 该次运行使用启动时锁定的 revision；步骤输出与故障传播都保持有序；取消操作会阻止剩余步骤继续执行。 | 带 MySQL 的 Pull Request |
| V13 | 托管推理同时服务本地和 Worker 客户端 | 任何提供商凭证都不会到达客户端或 Worker；按运行计算的授权、用量账本和配额均正确。 | 计划部署 |
| V14 | Artifact 同时保持授权和完整性 | 归属 Space 内的上传、列出、预览和下载均成功；跨 Space 访问失败；字节内容与元数据保持一致。 | 带 MySQL 的 Pull Request |
| V15 | 一个 Space 激活一个安全的插件发布版本 | 恰好只有被锁定版本的 skill/subagent 内容被物化；不被允许的 Hook 或 MCP 发布会被拒绝；不会有任何内容被隐式继承。 | Pull Request 加 Worker 冒烟测试 |
| V16 | Server 关闭时排空在制工作 | 新的认领和新的回合停止；正在进行的工作会给出文档化的结果；重启不会留下一条卡死的运行记录。 | 计划部署 |
| V17 | 一个 Worker 未上报就消失了 | 心跳过期，失联 Worker 的处理路径会以可预测的方式结束该次运行，部分证据得以保留，重试始终显式发起。 | 计划部署 |
| V18 | 数据库或对象存储变得不可用 | 就绪状态相应变化，用户可见的状态如实反映情况，不会发布任何幽灵 Artifact，恢复或重试的路径清晰明确。 | 计划部署 |
| V19 | 一对数据库与对象存储桶被恢复 | 恢复之后，关系型记录与存储对象保持一致；每一条被保留的 Artifact 引用，要么能解析成功，要么被明确标记为墓碑。 | 发布候选 |
| V20 | 一个候选版本完成升级并回滚 | 声明的模式路径、受支持的二进制回滚或破坏性切换恢复、排空及凭证轮换遵循文档约定，不产生含糊的数据丢失。 | 发布候选 |

每一条旅程测试都使用同样的断言结构：

1. 通过受支持的启动流程或公共接口来准备状态；
2. 通过公共界面执行用户或运维人员的操作；
3. 断言公共响应与可见结果；
4. 断言持久化的 MySQL 和对象存储状态；
5. 在适用的情况下，断言轨迹、审计、Artifact 和托管调用方面的证据；
6. 断言被禁止的副作用不会发生，包括跨 Space 读取、重复的行、重复的用量记录、
   工作区之外的文件，以及非终态的运行；
7. 清理现场，或使用一个隔离的命名空间，以避免执行顺序影响结果。

## 4. Pull Request MySQL 关卡

### 4.1 命令面

**已交付**，对应 `./make test mysql`（`tools/mk/test_mysql.go`），自身的命令面
测试提供覆盖，并记录在 `./make help test` 和
[../contribute/testing.md](../contribute/testing.md) 中。

该命令必须：

- 要求显式提供一个测试用 DSN，并拒绝回退到贡献者本地的数据；
- 创建一个具有唯一名字的临时数据库；
- 运行 `AutoMigrate` 以及每一条显式迁移；
- 运行 `internal/infra/db`，以及矩阵所选定的 service/handler 集成测试范围；
- 当该范围内的某个测试因为 DSN 缺失而被跳过时，判定失败；
- 只删除自己创建的、经过校验的那个临时数据库；
- 打印数据库名字、迁移版本、失败的包，以及复现命令，但不打印任何凭证。

CI 提供一个固定版本的 MySQL 服务容器，并调用与贡献者本地相同的任务运行器命令。
本地命令可以连接贡献者自己启动的 MySQL；但它不能把启动 Docker 当作
`./make test` 的一个隐式副作用。

### 4.2 首批持久化场景

目前已覆盖：用户与 Space 的创建、登录码、刷新令牌、公共 ID、系统授权、插件激活、
LLM 模型与调用、审计搜索、revision 查询、TaskRun 状态转换与认领、重试系谱、
直接 Task、checkpoint head 推进、Artifact 保留、Issue、Conversation、Space 邀请与所有权
转移的完整生命周期，以及
`internal/infra/db/concurrency_test.go` 中在并发场景下的四个存储层方法：
`ClaimTask`、`TransitionTaskRun` 和 `RequestTaskRunCancel` 各自作为一次条件
UPDATE 语句；而 `CreateTaskRun` 的“每个 Task 最多一个活跃 TaskRun”以及幂等键
保证，则是在同一个事务内，先对 Task 行做一次加锁读取，再做一次先计数后插入的
操作，因为这两条保证都不是针对一行已经存在的记录做条件 UPDATE。已移除的
Tier 1 结果投递队列已没有持久化验证义务；它以前的测试只是历史背景，不应重建。

上面这四个方法，都是靠突变检查而不是靠假设来验证的：去掉加锁子句，或者把条件
UPDATE 换成先读后写，都会让对应的测试失败。这一步才是关键所在。Task 认领测试的
第一版，在一个故意写坏的实现上居然通过了，原因是 MySQL 报告的是被*改变*的行数，
而不是被*匹配*的行数，于是七个写入了自己已经持有的状态、原本应当败给别人的调用者，
被计成了零受影响行。一个从未被证明能够失败的并发测试，算不上证据。

还需要补写：

- Workflow revision 在编辑与竞争下的推进，超越当前的初始 revision 创建与有序查询；
- 持久 Task/TaskRun/checkpoint 状态的重启恢复场景；以及
- 声明起始模式的迁移夹具。三个显式迁移包括 `issue_owner_executor_split`，其旧列回填已有
  MySQL 测试，但不是旧二进制回滚夹具。Alpha 可放弃兼容；按 Beta 就绪记录验证声明支持的
  升级/回滚版本组合或破坏性切换恢复；
- 已有线性 Workflow 的状态协调、幂等步骤接纳与 Agent 修订权威（R2），包括丢失/并发终态回调。

存储层的跨 Space 查找拒绝——这不同于处理器测试已断言的角色矩阵——现已由 MySQL scope 里的
`internal/infra/db/cross_space_test.go` 覆盖。它证明的是存储层
自己的 Space 守卫，而非边缘：一次从另一个 Space 发起的 Workflow 更新和 Issue 更新都是静默的
空操作，既不改写行也不泄露它的存在（各自给出真实的 revision 或 version，因此拒绝它的是 Space
守卫而非过期的前置条件），而一个插件激活对另一个 Space 的读取、列出和挂起都不可见——其中跨
Space 的挂起返回 `ErrNotFound`，而不是越过边界。既有的 `publicid_test.go` 判定（一个外部句柄
的应答与一个未知句柄完全一致）继续承担列表与聚合路径。

清单里还有一项是被撤回，而不是待办。**配额预留与计费边界**描述的是一种根本不存在
的设计：目前没有预留这回事。`internal/service/quota.Check` 通过
`SpaceUsageInWindow` 读取一个滚动窗口再做比较，而存储层只保留了 `GetQuotaTier` 和
`SeedDefaultQuotaTiers`。因此并发的运行确实可能突破一个限额，而这是当前设计本身的
特性，而不是一个应该靠测试钉死的缺陷。真正值得覆盖的是用量查询里窗口边界的算术
逻辑——这是查询正确性问题，不是并发保证问题——它应当归入 §3 的矩阵，而不是这里。
如果将来真的实现了预留机制，再把这一条加回来。

### 4.3 验收

- Pull Request 的 CI 里，MySQL 相关任务不出现 `BUILDMAX_TEST_DSN not set` 这种
  跳过；
- 重复运行和并行运行都不依赖测试顺序或共享 ID；
- 两次认领不可能同时赢下同一次运行；
- 反复执行取消、上报和重试操作，始终保持合法状态；
- 声明起始模式的夹具验证受支持升级或破坏性切换恢复，并通过关键流程；
- 失败输出能指明相关的 SQL 或状态转换，同时不泄露任何秘密；
- 覆盖率按关键包分别报告。本计划不设定一个仓库级别的整体覆盖率目标。

## 5. 确定性端到端验证

系统级接线验证使用已提交的确定性模型测试工具。真实模型被留给 §11 使用，因为它们
的不确定性，使它们很难充当授权、持久化和投递逻辑的判定依据。

### 5.1 测试工具的能力

只在矩阵中的旅程确有需要时，才扩展 `internal/testsupport/mockllm` 和
`deployment/smoke/mock-llm`。这套共享的场景词汇必须支持：

- 固定的流式响应，以及固定的工具调用序列；
- 在某个指定请求或迭代上注入一次失败；
- 一次由测试显式释放的停滞状态；
- 格式错误的工具参数，以及未知的工具名字；
- 一个中途断开的流；
- 延迟到达和重复到达的协议消息；
- 按运行区分的控制项，使并行测试互不干扰；
- 有边界地记录 prompt、工具、模型元数据以及请求顺序，供断言和排查问题使用。

这套测试工具不能重新实现 Agent Core 的决策逻辑。它只负责提供模型协议层面的事件；
每一个状态转换和策略决策，依然由被测试的产品代码本身拥有。

### 5.2 首批接入的 Pull Request 旅程

优先接入 V04、V05、V07、V08、V11、V12、V14 和 V15。这些旅程覆盖身份、授权、
持久化工作、revision 捕获、Artifact，以及插件选择，而且都不需要一个外部部署的
集群。

一条部署相关的旅程，绝不会止步于 HTTP 请求成功。以 V08 为例，它需要断言：

- Task 与 TaskRun 的公共状态；
- 恰好一次成功的认领，以及一个明确的上报者身份；
- 预期中的模型与工具调用记录；
- 精确的 Artifact 字节内容，以及可下载的授权；
- Issue 的 `latest_result` 以及输出投影；
- 在对应模式提供数据时，轨迹、审计与托管调用之间的关联；
- 不存在重复的 TaskRun、输出、Artifact 和用量记录。

### 5.3 现有套件的归属

- CLI 和 Desktop 仍然是 `./make test` 所包含的快速确定性套件；
- Portal 的浏览器行为仍然通过现有的 Playwright 和 `e2e` 相关设施来运行；
- `./make e2e local` 自己拥有一套 Compose 技术栈；
- `./make e2e compose` 和 `./make e2e kind` 仍然是某个部署的“客人”，由另一条命令
  或工作流负责启动；
- 部署冒烟测试与浏览器端到端测试尽量共享旅程 ID 和场景定义，而不是变成两套关于同一
  行为、彼此无关的独立说法。

## 6. 故障注入

故障必须是受控且可复现的。随意杀掉服务却不记录注入点，产生的只是噪声，不是证据。

每个故障控制都提供：

- 一个稳定的名称、目标运行、进程或依赖，以及明确的布置（arm）与释放点；
- 有边界的截止时间；
- 一个可观察的标记，证明故障确实发生，使测试能够区分有意注入与本来就不健康的环境；
- 幂等的清理；以及
- 当测试在未触发已布置故障的情况下完成时，判定失败。

控制可以延迟、断开、终止、暂停或拒绝，但绝不检查提示内容来推断产品“可能”的意图。
必须针对单次运行的控制以运行自有的不透明标识符为键；如果不改变产品权限就无法做到，
该用例回到设计阶段，而不是把按运行选择模型当作测试管道加入
（[端到端测试.md §6.1](端到端测试.md#61-server-与-worker-路径必须补上什么)）。

kind deployment smoke 现在已交付本节四个有边界的切片：执行中优雅丢失 worker、运行时
MySQL 拒绝与恢复、运行时对象存储 readiness 拒绝与恢复，以及拒绝 worker 自身的对象存储
写入（[端到端测试.md §6.6](端到端测试.md#66-拒绝-worker-的对象存储写入)）。由于
Kubernetes Job 删除会发送 `SIGTERM`，无声硬故障 reaper 仍由 store 测试覆盖；Server
重启/重连、已有部分工作的取消，以及负载下优雅关闭仍待实现。
Server 重启/重连用例在一个直接 Task 或前台轮次可被观察时重启服务路径；重连之后，
持久状态必须重建同一份工作，且不产生重复的 TaskRun、输出、Artifact、用量或消息历史写入。

### 6.1 Worker 生命周期

为终止一个 Worker 增加相应的控制手段和测试用例，覆盖以下时机：

- 认领之后、模型执行之前；
- 一次工具调用进行期间；
- 一个 Artifact 正在上传的过程中；
- 已经产出结果、但尚未出具终态报告之前；
- 已经出具终态报告、但可选的 Conversation 投影尚未完成之前。

每个用例都要断言文档化的终态、心跳与清理进程的时机、部分证据的保留情况、不存在
幽灵结果，以及明确的重试路径。任何一次运行都不得在有边界的恢复时间窗口之外继续
停留在 `RUNNING` 状态。同一组用例还必须证明：一个直接的 Agent Task 不需要经过
Conversation 投递，也能到达并暴露自己的终态结果。

### 6.2 MySQL

Compose 故障套件会在以下时机暂停或拒绝数据库访问：

- 一个 Worker 正在认领一次运行；
- 某个服务正在写入一次状态转换；
- Server 正在一个重启边界上记录或读取 TaskRun 状态；
- Server 正在关闭过程中排空工作。

断言需要覆盖 `/readyz`、有边界的重试、重连之后的幂等性、终态，以及错误分类。测试
必须能够区分“这是一次刻意的注入”和“这是一次无关的基础设施故障”。

### 6.3 对象存储

为以下情况提供受控的故障模式：

- 上传被拒绝；
- 下载被拒绝；
- 字节已经存好，但响应随后丢失；
- 元数据已经提交，但对象本身并不存在；
- 对象已经存好，但关系型关联写入失败。

任何一条失败路径，都不能对外展示一个实际上并不存在、却可以下载的 Artifact。恢复
操作必须显式地把不一致状态调和一致，或者明确标记为墓碑。

对于 worker 自身的写入——检查点与运行状态——上传被拒绝的情形已由 kind 写入拒绝演练
覆盖；其余四种模式仍然开放。

### 6.4 模型与流式传输

覆盖限流、服务端错误、超时、部分流、非法工具调用、重复的工具调用 ID、上下文耗尽，
以及 WebSocket 断开/重连。测试结果需要把故障分类为 Agent/模型、产品、评分器，或
基础设施四种；不能把所有故障都笼统地折算成一个虚假的能力分数。

## 7. 计划部署验证

在现有的部署冒烟测试工作流之上做扩展，而不是新增一套无关的编排系统。

计划中的验证矩阵如下：

| 环境 | 模式 | 所需范围 |
|---|---|---|
| Compose | 直接 | Server、local-process Worker、对象存储、Portal、Artifact，以及直接提供商路径。 |
| Compose | 托管 | 托管网关、按运行计算的授权、调用账本，以及配额。 |
| kind | 直接 | Ingress、Kubernetes Job Worker、Pod 边界报告、Artifact，以及取消。 |
| kind | 托管 | 经由部署路径的 Job Worker 令牌、托管网关、账本，以及配额。 |
| Compose | 故障 | 计划中的模型、worker 写存储与关闭注入。 |
| kind | 生命周期 | 取消，以及已交付的优雅 worker 丢失和依赖 readiness 探针；Server 重启、重连与无声硬故障部署证明仍待完成。 |

工作流规则：

- 针对被测的确切 commit 构建或选定镜像，并记录它们的摘要；绝不能用一个更旧的、
  可变的镜像来证明一个 commit；
- 每个矩阵单元都使用各自独立的 Space、用户、Task、Run 和 Artifact 标识符；
- 不允许把一次失败的任务重试到变绿为止。可以运行一次诊断性重试，但原始的失败结果
  仍然要保留在结果中；
- 无论成功还是失败，都要上传 §12 中的证据包；
- 在被排除出发布资格认证之前，先给每一次故障打上产品、测试/工具，或基础设施的
  标签；
- 一个被隔离的不稳定测试，依然要在矩阵中可见，并附带负责人和原因；隔离不等于静默
  放行。

## 8. 发布候选资格认证

每一个 Beta 及以后的候选版本，都要用即将发布的那份不可变构建产物来演练。

### 8.1 环境

- 私有 Kubernetes 环境；
- 外部 MySQL 和兼容 S3 的存储；
- 在对外发布的端点上启用 TLS；
- Kubernetes Job Worker；
- 使用两个 Server 副本与 Redis 协调，同时明确演练跨副本投递、并发回合、重连以及
  Redis 故障/恢复；
- 不使用任何固定的开发登录方式或提供商凭证；
- 直接推理和托管推理分别单独认证；
- 在执行之前记录确切的镜像摘要、依赖版本、配置摘要、操作人，以及日期。

### 8.2 运维人员的操作旅程

运维人员必须：

1. 引导创建第一个系统管理员；
2. 创建或配置一个普通账户与 Space；
3. 通过 Portal 登录；
4. 创建 Agent、Issue 和 Workflow 资源；
5. 完成一次前台 Conversation；
6. 完成一个后台 Task，并检查其结果；
7. 下载一个 Artifact，并检查轨迹、审计、托管调用和配额数据；
8. 取消一次正在进行的运行，并重试一次失败的运行；
9. 优雅地重启 Server；
10. 在没有优雅上报的情况下直接杀掉一个 Worker；
11. 分别中断数据库访问和对象存储访问；
12. 把数据库和存储桶作为一对一起恢复；
13. 演练声明的模式路径及受支持二进制回滚或破坏性 Alpha 切换恢复；
14. 按照文档化的排空/重启流程，轮换 JWT、数据库、对象存储和提供商凭证。

### 8.3 验收

- 每一次运行都到达一个可解释的终态；
- 没有任何悬空的运行超过文档规定的恢复时间窗口；
- 每一条被保留的 Artifact 引用，要么在恢复之后能够解析成功，要么被明确标记为墓碑；
- 配对恢复之后，数据库与存储桶的状态保持一致；
- 回滚行为符合受支持的迁移约定；
- 一个没有参与实现该变更的运维人员，能够仅凭文档化的界面和已收集的证据，诊断出每一
  次被注入的故障；
- [../deploy/beta-readiness.md](../deploy/beta-readiness.md) 引用了这份不可变的
  证据包，并记录下每一项被接受的局限。

## 9. 针对 AI 生成测试的质量把控

每一项改变行为的贡献，都要在其 Issue、变更说明，或 Pull Request 描述中包含以下
审查区块：

```text
Behavior:
Observable result:
Persistent result:
Forbidden side effects:
Failure cases:
Tests added:
Not tested:
```

实现和验收使用彼此独立的上下文。实现阶段可以顺带补充一些针对性的测试。而一次全新
的验收环节，只拿到需求描述、公共接口和 diff，尝试通过找出遗漏的结果、被禁止的
副作用，以及双方共享的错误假设，来证伪这个行为是否真的成立。

审查规则：

- 涉及授权、执行策略、配额、迁移和状态机的变更，至少要包含一个反例场景；
- 一个 bug 修复，要先补上一个使用独立判据的失败回归用例；
- 优先使用公共 API、文件系统、数据库、轨迹、审计或 Artifact 状态作为验收判据，
  而不是依赖私有实现调用；
- mock 只负责提供依赖和协议事件，不能重新实现被测的那条规则本身；
- 单独的 `err == nil` 不构成一个行为断言；
- 测试失败时，必须能给出有用的诊断信息；
- 审查者要问：如果去掉或反转被改动的那道守卫逻辑，这个测试是否依然会通过。

## 10. 模糊测试与突变测试

这两项技术只针对高风险的不变量有的放矢地使用，而不是不加区分地跑遍整个仓库。

### 10.1 模糊测试目标

为以下内容添加 Go 模糊测试目标：

- Workflow 定义的解析与校验；
- 公共 ID 与路径包含关系；
- 工具参数解码；
- webhook 载荷与消息路径提取；
- 轨迹脱敏与有边界的序列化；
- 配置层的合并与环境变量解析；
- 会话/历史记录的解码与恢复；
- 能够被隔离为纯领域逻辑的状态转换输入。

每一次发现的崩溃、挂起、路径逃逸，或不变量被违反的情况，都要转化为一颗被提交进
仓库的回归种子。

### 10.2 突变测试目标

从 Space 策略、Task/TaskRun 转换规则、登录码消费、配额、Workflow 校验、沙箱策略，
以及 Artifact 授权开始。

真正重要的突变包括：删掉某个授权检查、反转角色比较逻辑、改变终态判定条件、改动
配额边界、取消操作之后却报告成功，以及移除某个 Space 过滤条件。这些突变理应无法
存活。本计划不要求对 DTO、生成的结构体，或简单的适配器给出一个全局突变分数。

## 11. 产品评估与内部试用

### 11.1 产品自有的评估

在把评估用于发布资格认证之前，先把目前的三个任务扩充为一套具有代表性的、包含
12–20 个任务的套件。需要覆盖：

- 文件搜索与多文件编辑；
- 在不需要用到 Bash 的情况下正确作答；
- 从一次权限拒绝中安全恢复；
- 压缩与会话恢复；
- Project Memory 的读取与更新；
- subagent 委派；
- Artifact 产出；
- Worker 对 Space 文件的访问；
- 工具失败和格式错误结果的恢复；
- 取消和超时之后的响应；
- 借助轨迹对结果做出解释。

优先选用确定性的评分方式：文件哈希、JSON schema、命令、目录状态、轨迹事件、被
禁止的工具调用，以及数据库终态。只有在针对人工判断做过校准之后，才对真正主观的
质量问题使用模型评分器。

真实模型的运行，应当选定一小组受支持的模型，把每个任务重复足够多次以体现出变异性，
使用明确的 token 预算，并把 Agent、产品、评分器和基础设施方面的失败分开报告。
外部基准测试仍然只是一个参照坐标，不是产品发布的关卡。

### 11.2 内部试用

维护一份轻量级的手动验证日志，记录 commit、界面、模型、真实任务、是否成功、人工
介入情况、令人困惑的行为，以及关联的 Issue。反复执行一小组有代表性的任务：一次
Go bug 修复、一次涉及多个文件的配置变更、一个由 Worker 完成的 Portal Issue、一次
取消和重试、一次会话恢复，以及一次 Artifact 的生成/下载。

人工使用不能替代自动化测试。它能够发现另一类故障：每一个被断言的事实都成立，产品
本身却依然令人困惑或者不好用。

## 12. 证据约定

每一次计划内或发布相关的运行，都要在以下位置写入一份有边界的证据包：

```text
.artifacts/verification/<commit>/<environment>/<journey>/
  manifest.json
  result.json
  server.log
  worker.log
  portal.log
  trace.jsonl
  audit.json
  db-state.json
  artifacts.json
  screenshots/
  playwright-trace/
  junit.xml
```

不适用的文件会被省略，并在 `manifest.json` 中记为不适用；空的占位证据不算成功。

manifest 需要记录：

- commit 与是否存在未提交改动；
- 镜像摘要；
- 操作系统与架构；
- MySQL、对象存储、Kubernetes，以及浏览器的版本；
- 直接推理还是托管推理模式；
- 旅程与场景的版本；
- 开始与结束时间；
- 注入的故障及其注入点；
- 最终的通过/失败分类；
- 对无法导出的私有日志或 Artifact 的、有边界的引用。

证据包默认是私有的，会对凭证和模型敏感内容做脱敏处理，并遵循明确的保留期限。CI
的摘要会链接到这份证据包，并直接显示终态分类，维护者不需要下载每一份日志就能看懂
结果。

## 13. 交付顺序与完成标准

按依赖顺序实施：

1. 建立包含 V01–V20 的验证矩阵，并关联现有的证据；
2. 添加 Pull Request 的 MySQL 命令和 CI 任务；
3. 接入 V04、V05、V07、V08、V10、V11、V14 和 V15 这些确定性旅程；
4. 添加 Worker、MySQL、对象存储、模型，以及关闭相关的故障控制；
5. 让计划内的 Compose/kind 运行产出符合 §12 约定的证据；
6. 执行外部 Kubernetes 的恢复、升级、回滚，以及凭证轮换演练；
7. 补充有针对性的模糊测试、突变检查、更宽的评估覆盖面，以及持续的内部试用。

关卡规则：

- Pull Request 上的确定性检查，一次通过，无需重试；
- 计划内运行中出现的故障，在被分类之前始终保持可见，未分类的故障会阻止推进；
- 一个发布候选版本，要用自己独立的不可变摘要，重新走一遍每一项必需的证明；
- 一项路线图能力，只有当它在矩阵中对应的那一行同时具备单元/契约证据，以及与其
  边界相称的确定性端到端证据时，才算完成；
- Beta 阶段还额外要求真实部署、故障、恢复，以及运维人员相关的证据；
- 真实模型评估要与确定性的系统正确性分开报告。

当 V01–V20 的每一行都具备其最低关卡所要求的证据、发布演练已经由一位没有参与实现
该候选版本的运维人员执行过，并且没有任何生产就绪声明依赖于一个悄悄跳过了真实依赖
的测试时，本计划即告完成。
