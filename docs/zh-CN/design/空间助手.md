## 1. 决策

一个 Space 可以发布多个 **Assistant**。每个 Assistant 都是 Space 拥有的实体，
有自己的指令、模型、由 Agent 与已发布 Workflow 组成的名册、受众、担保人
（sponsor）以及 Telegram bot。请求者的消息到达 Assistant 的 bot 后，Gateway
通过请求者已有的聊天关联识别其身份，检查 Assistant 的受众，然后运行一个由该
Assistant 配置的 Tier 1 Conversation turn。该 turn 启动的工作是 Assistant 所在
Space 中的一个普通 Task。

这些工作以 Assistant 的 **service account** 身份运行：一个非人类用户，只属于一个
Space，不能登录，并通过一名人类担保人承担问责。请求者被记录为来源，而绝不作为
权限依据。service account 的 Space 成员资格就是组织授予的权限；Assistant 的名册
对其进一步收窄。

请求者能了解到什么，由 Assistant 能读取什么来界定，而不是靠过滤它说了什么。名册
成员返回结构化结果，其中的可放行字段是请求者唯一能看到的运行输出。

本记录不新增执行平面、运行类型或模型循环。个人助手和由运维人员配置的系统 bot
保持不变。

## 2. 两类对话界面

| | 个人助手（已交付） | Space Assistant（本记录） |
|---|---|---|
| 它是什么 | 用户的 Tier 1 Conversation，可从 Portal 或已关联的聊天访问 | Space 向某一受众发布的服务 |
| 它服务谁 | 它自己的用户 | 请求者，通常在该 Space 之外 |
| 谁拥有它 | 该用户 | 一个 Space，通过担保人承担问责 |
| 以谁的权限运行工作 | 该用户的 | Assistant 的 service account，受其名册约束 |
| 可以返回什么 | 用户本来就能看到的任何内容 | 仅 Space 向该受众放行的内容 |
| Bot | 部署在 `server.yaml` 中配置的系统 bot | Assistant 自己的 bot，在 Portal 中绑定 |

在个人助手中，请求者、会话所有者与权限主体是同一个人，这正是渠道设计可以说
“发送者就是行动者；不存在 bot 主体”
（[即时通讯渠道 §7](即时通讯渠道.md#7-授权与信息披露)）的原因。这在个人路径上
仍然成立。Space Assistant 把这三者分开，本记录中的每一项控制都源于这种分离。

## 3. 证据与采纳决策

驱动这一设计的是部门场景：HR 支持 bot、市场支持 bot、审计 bot。组织已经在运行
这类 bot，多数用于通知，而且许多中小型组织在 Telegram 上运行它们，而不是在企业
聊天套件中。聊天套件把面向团队的 bot 作为产品提供（飞书 aily、企业微信智能机器人、
钉钉的助理市场），企业级 Agent 构建平台也收敛到本记录所做的这些分离：Agent
定义、渠道绑定、触发器和运行是彼此独立的对象；在“以调用者身份行事”和“以 Agent
身份行事”之间做显式选择；以及为非人类身份强制配置担保人。已有记录的故障都是身份
故障：事件触发器以制作者的凭证运行并过度共享，以及定时 Agent 在某个人的令牌过期
后静默失败。

本记录之前的提案把这项工作搁置在 Beta 关口之后，直到有具名组织提出需求。
2026-10-04，维护者决定在没有这样的组织的情况下构建验证切片。Beta 关口本身已经
通过，因此这是按该决定排序的 R5 工作。§15 中的度量仍是扩大范围的证据；有团队
采纳仍是超出 §15 的任何工作的证据。

## 4. 概念

每个概念都附上没有它就会失败的需求。

**Assistant**（新增，Space 拥有）。

| 字段 | 没有它就会失败的需求 |
|---|---|
| Space、名称、描述 | 一个组织会运行多个 Assistant；请求者必须知道自己找的是哪一个 |
| 指令、模型 | HR 与审计需要不同的人设；Tier 1 在每个部署中只有一个固定的提示词和模型 |
| 名册：Space Agent 与已发布的 Workflow，每项都带放行契约（§8） | 前门必须派发选定的一组，而不是 Space 中的所有 Agent；名册同时界定权限与信息披露 |
| 可读文件：Space Artifact 的白名单 | 基于资料作答需要可读的内容，而可读的范围就是信息披露边界 |
| 受众：`space_members` 或 `all_users` | 谁可以提问是 Space 的决定，而不是成员资格的副作用 |
| Service account | 工作需要一个既不是请求者、也不是可能离职之人的权限主体（§6） |
| 担保人与状态（`active`、`paused`） | 必须有人承担问责，并且 Space 必须能够立即停止它 |
| 修订版本 | 回答必须能追溯到产生它的配置，就像 Agent 修订版本一样 |

Assistant 只存在于团队 Space 中。个人 Space 按构造只有一名成员，无法接纳
service account。

在知识源出现之前，知识范围就是可读文件白名单。之后的知识库会在 Assistant 上
设置其范围，因为范围是一项信息披露决策。

**Service account**（新的用户类型，§6）。一行 `kind` 为 `service` 的用户记录，
只属于一个 Space，没有任何登录方式。

**渠道绑定**（新增，Assistant 的子对象）。一个 Telegram bot 令牌，用 Secret 的
密钥加密密钥封存，连同该 bot 的 Telegram id 和用户名。移除绑定就是让 bot 不再
被服务的方式。暂停的 Assistant 仍保持其 bot 连接，并回复它已暂停，这样暂停期间
发来的消息不会在恢复后被集中补答。该令牌不是 Space
Secret：Space Secret 的存在是为了授予 Agent 并物化到 worker 运行中，而 bot 令牌
绝不能到达 worker。在本记录中，一个 Assistant 最多有一个绑定；之后的适配器可能
允许每个平台一个。

**聊天关联**（已有，用户级，不变）。`channel_identity` 仍是“某个聊天账号属于某个
BuildMax 用户”这一事实的唯一记录。Telegram 用户 id 在不同 bot 之间相同，因此一个
关联即可向系统 bot 和每个 Assistant bot 识别同一个人。Assistant 不保留自己的关联
表。

**Conversation**（扩展）。新增可选的 `assistant_id`。与 Assistant 的私聊
Conversation 以 Assistant、聊天和请求者为键。它的 `user_id` 是请求者，因此该
turn 按请求者计量和记录，而它的 Space 是 Assistant 的 Space。

**Task**（形态不变，新增来源信息）。由 Assistant 派发的 Task 会记录
`requested_by`（请求者）、`assistant_id` 和 Assistant 修订版本，与 `created_by`
并列，而 `created_by` 是 service account。

## 5. 角色分离

| 角色 | 是谁 | 记录为 |
|---|---|---|
| 请求者 | 提问的人，通过其聊天关联识别 | Conversation `user_id`；Task `requested_by` |
| Assistant（应答者） | 前门及其修订版本 | Conversation `assistant_id`；每条消息和每个 Task 上的修订版本 |
| 运行权限 | Assistant 的 service account，受名册约束 | Task 与 TaskRun 的 `created_by` |
| 执行行动者 | 被派发的 Agent 修订版本与 TaskRun | 现有的 Task 与 TaskRun 字段 |
| 担保人 | 对 Assistant 及其 service account 负责的 Space 所有者或管理员 | Assistant 与 service account 的 `sponsor` |

被派发 Task 的审计记录会保留全部五个角色。把它们重新合并为一个 `created_by`，就会
丢失身份提案指出的该字段被过度承载的那层区分。

## 6. Service account

### 6.1 为何需要独立的主体

Assistant 的工作需要一个权限主体。其他选择都行不通：

- **请求者。** 请求者通常在该 Space 中没有任何权限，而让每个请求者都成为成员，
  就会把每个受众都变成 Space 成员资格。
- **担保人或另一个具名用户。** 一旦那个人离职或变更角色，工作就会停止。它承载
  该人的完整 Space 身份，于是请求者的文本会驱动一名具名员工的权限，审计也会显示
  是这个人做的。未经本人同意就指定他人是冒充；即使经过同意，也只是把问题转移到
  另一个人身上。
- **把 Assistant 本身作为主体。** 这是身份提案中更简单的基线方案（B1）。它在
  这里有两点不成立。部门的权限是共享的：HR Assistant 与 HR 团队的 Schedule
  应该以同一个“HR 运营”主体运行，并且这份授权应在替换 Assistant 后依然存在。
  此外，系统中的每一项权限检查——`created_by`、资格判定、成员资格、审计行动者——
  都以用户 id 为键，因此非用户主体会迫使所有这些检查被泛化。

service account 是身份提案中的选项 D，即 Space 拥有的自动化主体。选择它是因为
其触发条件成立：这份授权跨越多个行动者，并且必须比其中任何一个存在得更久。

### 6.2 形态

service account 是一行 `kind = service` 的 `user` 记录。正因为它是用户，现有的
每项检查都能原样适用：被派发的 Task 完全像今天一样，依据 `created_by` 被准入、
派发、获取和协调。

| 属性 | 规则 | 原因 |
|---|---|---|
| Space | 恰好是一个团队 Space 的成员，角色为 `member` | 它的触达范围就是该 Space；它永远无法管理该 Space 或加入其他 Space |
| 登录 | 无：没有邮箱、密码、登录码、SSO 关联、刷新令牌、PAT 或 API key；每条登录路径都拒绝该类型 | 只有服务端组件能以它的身份行事，因此它没有可被窃取的凭证，也没有需要运营的凭证生命周期 |
| 聊天关联 | 无；配对会拒绝它 | 它永远不是请求者 |
| 担保人 | 同一 Space 的一名人类所有者或管理员 | 有人承担问责 |
| 状态 | 启用或禁用，使用现有的账号禁用机制 | 一次禁用即可停止以它身份进行的一切 |
| 可见性 | 在 Space 设置和管理后台的用户列表中列出，并标记为 service account；不出现在邀请、登录和人员选择器中 | 可以盘点，又不会被误认为是人 |
| 配额 | 用量计入其所在 Space，与所有用量一样 | 无需另行管理额度 |

创建 Assistant 时，默认会创建一个同名的 service account。Space 所有者也可以改为
选择该 Space 中已有的 service account，这就是 Assistant 与 Space 中其他自动化
共享同一权限主体的方式。删除 Assistant 会保留其 service account；禁用
service account 会停止所有使用它的 Assistant。

### 6.3 生命周期

- **谁来管理。** Space 所有者和管理员可以在其 Space 中创建、重命名、禁用、重新
  启用 service account 并更换其担保人，每项操作都有审计事件。部署管理员可以禁用
  任何 service account。
- **担保人离开。** 当担保人不再是该 Space 的所有者或管理员，或其账号被禁用时，
  该 service account 的 Assistant 会暂停，service account 被标记为需要担保人。
  某位所有者或管理员接手担保后，它们即恢复。暂停是失败即关闭的：面向广泛受众的
  Assistant 绝不会在无人负责的情况下运行。service account 保留其身份和授权，因此
  无需重新配置，这正是它与绑定创建者的 `created_by` 的区别。

### 6.4 与身份提案的关系

service account 的 Space 成员资格就是本记录中 `organization_grant` 的形式：一项
显式的、由担保人负责的、授予非人类主体的权限，通过禁用它来终止。它不提供该提案
中的每次运行工作负载身份、代理凭证、审查或到期日期，以及目标授权；这些仍留在该
提案中。Schedule 和入站 webhook 之后可能改为以 service account 而非其创建者身份
运行；这种转换不属于本记录。

## 7. 授权

### 7.1 请求者是谁

请求者是一名活跃的 BuildMax 用户，其聊天账号已通过配对完成关联。在 Telegram 上，
任何更弱的依据都不可信：Telegram id 只能证明某个 Telegram 账号发送了这条消息。
信任根是已登录、能看到聊天账号名的用户在 Portal 中对配对码的确认
（[即时通讯渠道 §6](即时通讯渠道.md#6-配对)）。

配对是用户级基础设施，而不是系统 bot 的一项功能：

- **任何由服务端管理的 bot 都可以发起配对。** 未关联的账号给某个 Assistant 的
  bot 发消息时，会像从系统 bot 那里一样拿到一个配对码，确认后写入的也是同样的
  `channel_identity` 行。配对会记录签发配对码的是哪个 bot，由该 bot 确认关联。
  一个有 Assistant bot 但没有系统 bot 的部署依然能够为用户建立关联。
- **一个关联服务于所有 bot。** 配对过一次的人会被系统 bot 和每个 Assistant 识别。
- **登录窗口同样适用**，与个人路径一致：只有当用户最近一次 BuildMax 登录处于
  `channels.sign_in_window` 之内时，关联才能生效。
- **解除关联仍在 Portal 中进行。**

### 7.2 谁可以提问

受众是一项针对 BuildMax 用户的策略：

- `space_members`：Assistant 所在 Space 的成员；
- `all_users`：部署中的任何活跃用户。

具名用户或具名 Space 列表要等到有团队需要时再做。受众之外的请求者会收到固定的
拒绝回复，且不会发生模型调用。受众、Assistant 的状态、service account 的状态以及
请求者的账号，都会在每条消息上、在任何模型运行之前进行检查。

### 7.3 以谁的权限运行工作

以 service account 的权限。该 turn 的工具以 service account 身份行事，并且只能
触达名册：StartTask 只接受名册中的 Agent，Workflow 工具也只列出和运行名册中的
Workflow。服务端在每次调用时检查名册；模型的选择永远不被信任。在被派发的运行内部，
worker 的运行作用域 API 一如今天那样为该运行的 Task 行事，因此运行的触达范围就是
service account 的 Space 成员资格。

名册成员执行的、在 BuildMax 之外产生后果的操作，受该 Agent 自身的 Secret 授权、
网络层级和审批策略约束。运行提出的问题或审批由 Space 成员回答，绝不由请求者回答。

## 8. 信息披露边界

**原则。** Assistant 能读取的任何内容，无论是直接读取还是通过其名册读取，都视为
已向其整个受众披露。

模型输出是自由文本，而请求者不可信。事后过滤输出会漏掉改写过的、部分的或推断出的
内容，因此控制点在于 Assistant 能读取什么。

| 层 | 是否在本记录中 | 机制 |
|---|---|---|
| 1. 可读范围 | 是 | 可读文件白名单与名册定义了一切可触达的内容。向名册添加一个 Agent，就把该 Agent 的文件、Secret 和网络触达范围加入到受众实际上可以了解到的内容中 |
| 2. 绑定请求者的查询 | 否（§16） | 调用以请求者身份运行，不接受模型提供的人员 id |
| 3. 放行契约 | 是 | 每个名册条目都有一个 `output_schema`，并列出其可放行的顶层字段。只有这些字段会到达前门模型或请求者 |
| 4. 上下文分离 | 部分，通过第 3 层实现 | 与请求者对话的模型永远不持有原始运行输出 |
| 5. 人工审阅 | 通过升级（§11） | 无法回答的请求会变成一个由人来回答的 Issue |
| 6. 审计 | 是 | 记录 Conversation、修订版本、请求者以及被派发的 Task；Space 所有者和管理员可以审阅（§12） |

**放行契约。** Workflow 本身没有输出 schema，它的结果是从某个节点的输出中选取
的。因此 Workflow 名册条目使用该节点的 `output_schema`，并且结果必须选取该节点
的完整输出。Agent
名册条目在条目上声明一个 `output_schema`，StartTask 把它作为 Task 的
`output_schema` 传入，因此运行必须满足它。条目会列出哪些顶层属性可以放行。从
Assistant turn 中调用 GetTask 和 GetWorkflowRun 时，只返回状态和可放行字段：
不返回原始输出、错误文本、对话记录或 Portal 链接。没有放行契约的名册条目无法
添加。结果按产生它的 Agent 或 Workflow 在 Assistant **当前**名册中的条目放行：
所有者确认的是这一声明；条目已移出名册的工作不放行任何内容。

**发布是一项信息披露决策。** 激活 Assistant，以及在其处于激活状态时保存对受众、
名册或可读文件的更改，都会向所有者展示一份生成的声明并要求确认：谁可以提问、它
可以读取哪些文件、可以运行哪些 Agent 和 Workflow，以及这些 Agent 持有哪些
Secret。一位理解这份声明的 Space 所有者，是比任何输出过滤器都更强的控制。

**告知请求者谁会读取他们的消息。** Assistant 在一个会话中的第一条回复会说明运营
它的是哪个 Space，并说明该 Space 可以审阅这段会话。bot 令牌的持有者无论如何都能
通过 Telegram 读取该 bot 的消息；该声明指明持有令牌的是这个 Space。

**残余限制。** 在第 1 层的范围内，聚合与推断仍然可能发生：请求者从许多回答中
了解到的可能比从单个回答中更多。这是一项已记录的限制，而不是保证。

## 9. 承载多个 bot 的 Gateway

如今，Gateway 按平台为 Connector、接收租约、去重、聊天队列、配对确认和结果报告
设定键，因为一个平台只有一个 bot。它将改为按 **bot** 设定键：

- **Connector 键。** 每个 Connector 都有一个键：`server.yaml` 中的 bot 为
  `system`，Assistant 的 bot 为其绑定 id。租约为
  `channel-connector:<platform>:<key>`；去重和聊天队列都包含该键。
- **配对记录其 bot。** `channel_pairing` 存储签发配对码的 Connector 键，确认消息
  通过该 Connector 发送。
- **会话记录其 bot。** 会话从哪个 Connector 进入，其结果报告就从哪个 Connector
  发出：个人会话为系统 bot，Assistant 会话为对应的绑定。
- **绑定在运行时变更。** 每个副本都会让自己的 Assistant Connector 集合与数据库中
  已启用的绑定保持同步，按较短的间隔进行协调，并在做出变更的副本上立即协调。接收
  租约仍保证每个 bot 恰好只有一个副本在接收。被禁用或删除的绑定会在下一次协调时
  停止接收。
- **每个令牌只有一个接收者。** Telegram 会把每条更新只投递给一个轮询者，因此一个
  令牌不能被服务两次。绑定会存储通过 `getMe` 获得的 bot Telegram id，该 id 在所有
  绑定中唯一，且不同于系统 bot 的 id；绑定时重复的令牌会被拒绝。
- **Gateway 始终存在**，只要可以绑定 Assistant，无论是否配置了系统 bot。

个人路径除了其键之外保持不变：系统 bot 继续在已关联用户自己的 Space 中为他们
服务。

## 10. 前门 turn

Assistant bot 上的一条消息按以下顺序处理，全部发生在任何模型调用之前：仅限私聊；
查找聊天关联，或提供配对；登录窗口；Assistant 与绑定处于激活状态；service account
处于激活状态且有担保人；请求者的账号处于激活状态；请求者在受众之内。每一种拒绝都是
一条不携带任何 Space 数据的固定回复。

该 turn 复用 Tier 1 运行时，并使用一个 Assistant 配置：

- **提示词。** Assistant 的指令替换个人助手的开场句。工具指引和信息披露规则（§8）
  保持固定，Assistant 的作者无法编辑。
- **模型。** 使用 Assistant 的模型；未设置时使用部署的会话模型。
- **身份拆分。** 该 turn 的模型调用计量到 Assistant 所在 Space 中的请求者名下。
  它的工具以 service account 身份行事。如今一个 `UserID` 同时承担这两种用途；
  turn 输入将新增一个单独的行事用户。
- **工具。** StartTask 和 Workflow 工具仅限名册；ListTasks、GetTask、
  GetWorkflowRun 仅限当前会话，且只返回可放行字段；面向可读文件的 ListFiles 与
  ReadFile（仅限文本媒体类型，每个文件 128 KiB、每个 turn 384 KiB；对白名单之外的
  任何 id 都给出同一种拒绝，因此无从得知别处的文件）；Escalate（§11）。没有
  ListSpaces，也没有 `/space` 命令。
- **命令。** `/new` 与同一个 Assistant 开始新会话；`/help` 显示 Assistant 的描述
  及运营它的 Space。
- **修订版本。** 每条存储的消息都记录产生它的 Assistant 修订版本。

模型用量与任何 Conversation turn 一样计入 Space 的 token 配额。所在 Space 已用完
配额的 Assistant 会以固定回复拒绝。

## 11. 结果、升级与投递

- **结果报告。** 当 Assistant 派发的 Task 结束时，请求者的聊天会通过 Assistant
  的 bot 收到一份报告：成功时为可放行字段，失败或取消时为一条固定消息。不发送原始
  输出、错误文本和 Portal 链接。个人路径的报告保持不变。
- **升级。** Escalate 工具在 Assistant 所在 Space 中创建一个 Issue，创建者为
  service account，并记录请求者和会话，同时告知请求者会有人跟进。Space 成员在该
  Issue 中通过显式的“回复请求者”操作作答，该回复经 Assistant 的 bot 发送，并记录
  在 Issue 上。只要 Assistant 自己不会回答该请求者——已暂停、未绑定 bot，或请求者
  已不在其受众内——回复就会被拒绝；回复也不会进入模型的上下文。
- **出站投递。** Space 中的 Schedule 可以指定一个 Assistant 和一名请求者作为投递
  目标。某次触发的运行结束时，可放行结果会通过 Assistant 的 bot 发送给该请求者。
  Telegram 只允许 bot 给已与它开始过聊天的人发消息，因此目标必须是已与该
  Assistant 有过会话的请求者。Schedule 触发的 Workflow 运行也以同样方式处理。
  聊天和群组目标要等到支持群组之后。保存目标时会检查：Assistant 的名册必须包含
  该 Schedule 的执行者，否则没有任何内容可放行。Agent 触发以该条目的 output
  schema 运行。选择目标、以及编辑带目标的 Schedule，需要管理 Assistant 的权限，
  因为这决定了 Space 的 bot 对某人说什么；成员仍可暂停它。每次启动了执行者的触发
  都会随触发一同记录一条待投递记录，每个副本上的清扫器在运行结束后依据持久状态
  结算它，并在发送前先认领，因此结果至多发送一次，且能跨越重启。发送时，凡是会让
  Assistant 自己不回答该请求者的规则都会生效，然后应用当前名册条目的放行契约；
  未通过的投递会被跳过并记录原因，显示在 Schedule 的运行历史中。失败或已取消的
  运行不发送任何内容。

## 12. 审阅与保留

- 被派发的 Task 是 Space 中的普通 Task，对其成员可见。它们的输入包含请求者所问的
  内容；这是 Space 能看到的一部分，首条回复中的告知也说明了这一点。
- Assistant 会话可由 Space 的所有者和管理员在 Assistant 页面中以只读方式查看。
  普通成员看不到。
- 请求者在 Portal 中看不到 Assistant 会话；他们的历史就是聊天本身。他们无法在
  BuildMax 中删除它。
- 如今 Conversation 没有保留策略或删除路径，本记录也不为 Assistant 会话新增这些。
  来自 Space 之外的请求者让这一缺口更加突出，因此它是一个待解决问题（§17）。

## 13. 已考虑的备选方案

| 方案 | 为何不采用 |
|---|---|
| 把 Assistant 作为 Space Agent 上的字段 | 把持有 Secret 的沙箱化 Task 执行者与服务端前门混为一谈，使信息披露边界与执行触达范围纠缠在一起 |
| 每个 Agent 一个 bot，每条消息都是一个 Task | 部门需要一个覆盖多个 Agent 的前门；每条消息都要承担 worker 延迟；也没有地方放置受众或可读范围 |
| 整个部署共用一个路由 bot | 部门无法在共享 bot 中拥有自己的人设、受众或信息披露边界 |
| 以 `created_by` 作为担保人 | 把授权绑定到一个人身上，并让请求者的文本驱动该人的权限（§6.1） |
| “以”某个选定用户的身份行事 | 未经同意的冒充；相比有其同意的担保人也没有任何收益（§6.1） |
| 把 Assistant 作为独立主体 | 无法与 Space 的其他自动化共享，并且会迫使每一项以用户为键的权限检查被泛化（§6.1） |
| 把 bot 令牌作为 Space Secret | Space Secret 会授予 Agent 并物化到运行中；bot 令牌绝不能如此 |

## 14. 风险

- **通过名册泄露信息。** Space 所有者添加了一个能力强大的 Agent，却没意识到受众
  会继承它的触达范围。缓解措施：发布声明与强制的放行契约。
- **来自请求者的提示词注入。** 请求者众多且不可信。缓解措施：第 1、3、4 层；服务端
  的名册检查；审批路由给 Space 成员。
- **service account 泛滥。** 缓解措施：强制担保人、担保人离开时暂停、在 Space 与
  管理视图中盘点。
- **广泛受众带来的成本。** 每个用户都能消耗该 Space 的模型预算。缓解措施：目前
  依靠 Space token 配额；当用量显示有需要时，再加入按请求者的限制。
- **bot 令牌持有者。** 持有令牌的人可以在 BuildMax 之外以该 bot 的身份读取和发送
  消息。这不会削弱配对，因为配对由服务端签发并在 Portal 中确认。缓解措施：告知
  请求者是谁在运营该 Assistant，且令牌被封存、永不离开服务端。

## 16. 推迟事项

- 绑定请求者的查询（“我的假期余额”），这需要连接器层面的 `user_delegated` 调用。

  或从企业身份提供方进行关联。

- 以 service account 身份运行的 Schedule 和 webhook。
- 面向 service account 的每次运行工作负载身份与代理凭证。
