# 实体身份与关系键

> **翻译说明：** 本文是[英文原文](../../design/entity-identity.md)的简体中文派生翻译。若中英文存在语义冲突，以英文原文为准。

> **受众：** 贡献者与数据库审阅者 · **状态：** 已实现，
> 有修正 — §17 将存储方式从 `BINARY(12)` 改为规范文本形式

BuildMax 服务器实体的命名方式：两个标识符，各司其职——一个作为 MySQL 内部关系键的
`bigint unsigned` 主键，以及一个随机、不透明的 `public_id`，它是唯一允许离开进程边界的句柄。

本记录取代了已经退休的《实体身份与关系键》提案。它延续了那份提案的方向，用当前代码树中的
证据回答了它遗留的四个开放问题，并纠正了三处基于旧模式编写的内容。Git 历史保留了那份提案
的完整记录。

相关文档：[数据模型](../contribute/architecture/data-model.md)、
[store](../contribute/architecture/store.md)、[util](../contribute/architecture/util.md)、
[约定](../contribute/conventions.md)，以及 [Beta 关卡](../ROADMAP.md#beta-gate)——它对
版本化迁移的要求应当以本方案的模式为起点，而不是延续 Alpha 阶段的模式。

**当前模式说明（2026-09）：** 下文的表清单和 PR 顺序记录的是当时设计的实体身份迁移，
并非今天的完整表清单。`workflow_node_run` 已取代 `workflow_step_run`；刷新令牌现在
引用 `auth_session.public_id`，而不是带 `as_` 前缀的登录链 ID。当前字段与关系以
行结构体和[数据模型](../contribute/architecture/data-model.md)为准。公共 ID 与关系键
的核心决策仍然有效。

## 1. 问题

大多数服务器实体携带两个标识符：一个自增的 `id`，以及一个带前缀的公共 `varchar(64)` ID，
例如 `t_9f3k2m8x1qwe7rt4zy0p`。数字键是内部使用的，但它并不是关系键——每一次外键引用、
连接、授权过滤和配额聚合用的都是那个公共字符串。模式为两个标识符都付出了代价，却没有从中
获得任何一个的好处：身份信息被重复存储，而关系字段则变成了又宽又依赖排序规则的字符串。

对当前代码树的完整清点证实了这一规模。在 `internal/infra/db` 的 28 个行结构体中，**有
99 个列被声明为 `varchar(64)`**。其中少数是普通值——层级名称、审计动作、版本号、摘要、
模型别名——其余的都是标识符，其中大多数是关系引用，会在每一条子行上被重复存储并重新建立
索引。承载这些列最多的表，恰恰是那些随业务活动增长的表——`task`、`task_run`、`llm_call`、
`conversation_message`、`workflow_step_run`、`issue_comment`、`audit_event`、
`artifact`——而不是那些随管理配置增长的表。

由此还带来了另外三项代价：

- MySQL 在数据库的 `utf8mb4` 排序规则下比较这些标识符。`database.go` 中的建库逻辑选择了
  `utf8mb4`，且没有任何列覆盖这一设置，因此身份比较变成了一个排序规则决策，而不是简单的
  字节比较。
- 核心模型同时携带 `ID uint`（标记为 `json:"-"`）和一个公共字段，例如 `TaskID string`。
  一个 MySQL 实现细节因此暴露在 `internal/core/model` 中，每一个 mock 和替代存储实现都
  必须复制这一细节。
- 类型前缀只是一种约定，而不是一道边界。生产代码中没有任何地方依据它来做分发或校验：整个
  代码树里仅有的三处 `HasPrefix` 检查都在测试代码中（`llm_call_test.go`、
  `routes_test.go`、`service_test.go`）。

BuildMax 尚处于 Alpha 阶段，不对标识符的兼容性做任何承诺。这是决定当前格式是否应当成为
一份契约的最后一个低成本时机。

## 2. 目标与非目标

**目标。** 普通关系使用数据库原生键。公共标识符保持不透明、不可枚举，并且独立于数据库
拓扑。每个标识符只承担一个角色。任何数据库主键都不会出现在 API 响应、URL、JWT 声明、
日志行、轨迹、Workflow 定义或对象存储路径中。这是一次连贯的 Alpha 阶段模式变更，不设
双读路径。

**非目标。** 标识符不是授权凭证——每一次查找依然强制校验 Space 成员资格，并且无论标识符
的熵有多高，返回的都是同样的 `404`。排序永远不使用公共标识符；持久化的排序方式仍然是
`created_at` 加上数字键作为决胜条件。提供商 ID、工具调用 ID、Agent 会话 ID、轨迹运行 ID
以及幂等键都由实体模型之外的机制拥有，本次变更不涉及它们。在 Portal 中用名称隐藏原始 ID
是另一项独立的展示层变更。仓库“数据库不设外键”的规则并未被悄悄推翻；§8 会对此作出明确
决定。

## 3. 决策

`internal/core/model` 是本文撰写时领域结构体所在的包名。此后它已经按领域拆分为多个
包——`core/task`、`core/space`、`core/issue`、`core/conversation` 等等，遵循
[约定](../contribute/conventions.md)。下面的每一项决策都同样适用于这些拆分后的包。

| # | 决策 |
|---|---|
| D1 | `id` 是 `bigint unsigned auto_increment`，是关系键。`public_id` 是对外的句柄，仅在确有需要时才存在。 |
| D2 | 公共 ID 是 96 位加密随机数据，渲染为 20 个小写 base32 字符。经 §17 修正：规范文本本身即为存储形式，即 `char(20)` ascii_bin，而不是原始字节。 |
| D3 | 严格的单一类型关系一律转为 `uint64` 列。本次变更不引入任何 `FOREIGN KEY` 约束。 |
| D4 | 核心领域结构体只携带公共身份信息。一个结构体自身的句柄字段是 `ID string`，序列化为 `id`。 |
| D5 | 18 张表携带 `public_id`，8 张表不携带，2 张表保留自然键。 |
| D6 | 只有当一个引用是多态的、由外部拥有的，或本身就是一个值时，它才保持为不透明字符串。 |
| D7 | 公共 ID 到数字 ID 的转换发生在 `internal/infra/db` 内部，且绝不产生 N+1 查询。 |
| D8 | 不设兼容层。Alpha 阶段的数据库和对象存储会被重置。 |
| D9 | 只使用一种标识符格式。只有当裸标识符会以自由文本的形式出现在读者面前时，类型前缀才会保留。 |

## 4. 公共 ID 格式

### 4.1 值本身

96 位来自 `crypto/rand` 的随机数据，以其规范文本形式存储在
`char(20) CHARACTER SET ascii COLLATE ascii_bin` 列中（见 §17；最初的决策是把原始的
12 字节存储在 `BINARY(12)` 中）。

在单张表中拥有十亿个值的情况下，生日悖论意义上的碰撞概率约为 `6.3e-12`。唯一索引仍然是
最后一道防线：一次创建操作如果撞上了 `uq_<table>_public_id` 上的重复值，会在一个较小的
固定次数内重新生成并重试；除此之外的任何重复键错误都会原样返回。在拥有十亿个存活值的
情况下，一次均匀的猜测命中其中某一个的概率约为 `1.3e-20`。这种不透明性是 Space 授权和
“无法区分的未找到响应”之外的纵深防御手段，而不是替代品。

该值不是 UUIDv7，不携带时间戳，也不会泄露插入顺序或资源数量的近似值。索引局部性来自
自增键；这个随机值只是一个次要的唯一索引，而不是一个会被复制进每一个其他索引里的聚簇键。

公共 ID 在每张表内部是唯一的。BuildMax 没有全局资源解析器，路由或 JSON 字段总会提供类型
上下文。搭建一个跨表注册表只会增加一个写入瓶颈，却换不来任何授权或防冲突上的好处。

### 4.2 文本形式

RFC 4648 base32，不带填充，全部小写：字母表为 `a-z2-7`，长度恰好 20 个字符，解码后
恰好是 12 个字节。

```text
ivyoh5qcfu6ypfkhyedq
```

此前的提案规定使用 16 个字符的 base64url。base32 多花 4 个字符，却消除了一整类边界
隐患——这类隐患是当前的小写 base36 格式在悄悄防范，而 base64url 并不会防范的：

| 边界情形 | Base64url (`A-Za-z0-9-_`) | Base32 (`a-z2-7`) |
|---|---|---|
| Kubernetes Job 名称——`util.WorkerJobNameForTaskRun` 会把运行 ID 转成小写，并把每个不符合 DNS-1123 规范的字符替换为 `-` | 大小写和 `-`/`_` 都会被折叠。同一秒内创建的两次不同运行可能生成同一个 Job 名称，因为唯一的后缀只是一个精确到秒的时间戳 | 原样通过该清理逻辑，不受影响 |
| 大小写不敏感文件系统上的本地文件系统对象存储（macOS 默认如此），它以 `spaces/<space>/artifacts/<id>/content` 作为 Artifact 内容的键 | 两个仅大小写不同的 ID 会静默共用同一个路径。数据库唯一索引作用于原始字节，看不到这种冲突 | 不会发生 |
| 对裸 ID 的复制、粘贴与口述 | 区分大小写，且 `_` 在加了下划线的场合难以辨认 | 不区分大小写，是可以双击选中的一个整词 |

大小写折叠之后残留的熵，正是本地文件系统隐患真实存在而非纸上谈兵的原因：把 base64url
折叠大小写后只剩 38 个符号的字母表，于是同一个 Space 中十亿个值发生折叠碰撞的概率约为
`2.6e-8`——比原始边界差了四个数量级，而且故障表现为静默的内容覆盖，而不是一次数据库
错误。

### 4.3 编解码器

`internal/util/id.go` 只有两个函数，别无其他（§17 把最初的一对解析/格式化字节的函数
合并成了一个，因为已经没有调用方还持有原始字节了）：

```go
func NewPublicID() (string, error)              // 20-char canonical text
func CanonicalPublicID(s string) (string, bool) // any-case text -> canonical text
```

`NewPublicID` 返回错误而不是 panic：`crypto/rand` 失败必须表现为一次创建失败，而不是
让请求内部的进程直接中止。

`CanonicalPublicID` 接受大小写不敏感的输入，并将其规范化为小写，因此即便 ID 是从一篇
被转成标题格式的文档中重新输入的，依然能够被正确解析。除此之外的一切输入都会被拒绝，
并且通过解码、再编码、要求结果一致这一步骤，保证每个值都只对应唯一一种规范文本形式。
正是这一步检查消除了 base32 尾部比特位的歧义：20 个字符携带 100 位信息，最后 4 位必须
为零——而在文本本身即为存储形式之后，这一步同样防止了一个值占据十六个不同的唯一索引
条目。

这项检查带来一个直观的推论：一个规范 ID 总是以 `a` 或 `q` 结尾，因为这是仅有的两个低
4 位为零的字符。凡是以其他字符结尾的、凭空编造出来的测试数据，都不是合法的公共 ID。
测试用的取值应当来自生成器，而不是来自臆造。

`FormatPublicID` 如果作用在一个长度不是 12 字节的切片上，属于编程错误，会返回空字符串，
存储层的读取路径会把它当作数据损坏来处理。

### 4.4 前缀被废弃

`id.go` 中的前缀常量连同
[约定文档](../contribute/conventions.md#entity-ids-are-opaque-public-handles)里的
前缀表一并被删除，`NewPrefixedID` 本身也是如此。登录链、轨迹文件和 Desktop Project
都不是数据库行，但这从来都不是保留前缀的理由——它们只是恰好落在这次变更的范围边界之外。
它们都不会被人直接阅读，也不会依据前缀做分发，因此都不再保留前缀。

只有一个例外。一个后台任务的 ID 会以裸字符串的形式出现在工具输出中，交给模型阅读——
例如 `job: jb_ivyoh5qcfu6ypfkhyedq` 会和一条命令行、一个文件路径并列出现——而自由文本
正是唯一一处、周围上下文不会预先说明其类型的地方。这个前缀归属于拥有该概念的
`internal/agentapp/job` 包，而不是 `internal/util`。

## 5. 模式结构

```sql
CREATE TABLE task (
    id              BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
    public_id       CHAR(20) CHARACTER SET ascii COLLATE ascii_bin NOT NULL,
    conversation_id BIGINT UNSIGNED NOT NULL,
    space_id         BIGINT UNSIGNED NOT NULL,
    issue_id        BIGINT UNSIGNED NULL,
    agent_id        BIGINT UNSIGNED NULL,
    last_run_id     BIGINT UNSIGNED NULL,
    created_by      BIGINT UNSIGNED NOT NULL,
    -- status, input, title, output, timings, session_id unchanged
    PRIMARY KEY (id),
    UNIQUE KEY uq_task_public_id (public_id),
    KEY idx_task_space_created (space_id, created_at),
    KEY idx_task_conversation (conversation_id)
);

CREATE TABLE task_run (
    id                   BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
    public_id            CHAR(20) CHARACTER SET ascii COLLATE ascii_bin NOT NULL,
    task_id              BIGINT UNSIGNED NOT NULL,
    previous_task_run_id BIGINT UNSIGNED NULL,
    retry_of_task_run_id BIGINT UNSIGNED NULL,
    PRIMARY KEY (id),
    UNIQUE KEY uq_task_run_public_id (public_id),
    KEY idx_task_run_task (task_id)
);
```

命名本身就承载了各自的角色：

| 名称 | 含义 |
|---|---|
| `id` | 该行内部使用的数字主键 |
| `public_id` | 该行对外暴露的不透明句柄，仅在确有需要时才存在 |
| `<entity>_id` | 指向数据库内该实体的数字关系 |
| `<concept>_public_id` | 一个被有意存储下来的外部或多态句柄。这种情况很少见，且都会被明确命名 |

与此配套的还有两条机械性规则。持久化的数字字段一律是 `uint64`，绝不使用依赖具体架构的
`uint`。而公共 ID 对应的 Go 字段类型是 `string`，并带有
`gorm:"type:char(20) CHARACTER SET ascii COLLATE ascii_bin"` 标签（§17）——存储层只会
写入编解码器生成或规范化过的内容，因此每个值最终落到列里的永远只有一种小写拼写，而
`ascii_bin` 让比较保持为 memcmp，而不是变成一次排序规则决策。

转向数字 ID，也正是把组合索引设计对的好时机。一个按 `created_at` 排序的 Space 范围列表
需要的是 `(space_id, created_at)` 这样的组合索引，而不是字符串模型遗留下来的单列
`space_id` 索引。

## 6. 逐表决策

本迁移计划编写时，`AutoMigrate` 中共有 28 张表。下述清单记录当时的决策；新增的表、
后续 Workflow 与身份验证变更参见当前数据模型。

### 6.1 携带 `public_id` 的表——18 张

以下每张表都会把当前带前缀的公共列替换为 `public_id BINARY(12)`。

| 表 | 新增的数字关系 |
|---|---|
| `user` | 无——没有实体父级 |
| `space` | `personal_for_user_id`、`created_by` |
| `issue` | `space_id`、`user_id`、`parent_issue_id`、`created_by` |
| `issue_comment` | `issue_id`、`source_task_id`、`source_task_run_id` |
| `agent` | `user_id`、`space_id` |
| `conversation` | `user_id`、`space_id`、`created_by` |
| `conversation_message` | `conversation_id` |
| `task` | `conversation_id`、`space_id`、`issue_id`、`agent_id`、`last_run_id`、`created_by` |
| `task_run` | `task_id`、`previous_task_run_id`、`retry_of_task_run_id`、`cancel_requested_by` |
| `workflow` | `space_id`、`created_by` |
| `workflow_run` | `workflow_id`、`issue_id`、`conversation_id`、`created_by` |
| `workflow_step_run` | `workflow_run_id`、`target_agent_id`、`task_id`、`task_run_id` |
| `user_webhook_key` | `user_id` |
| `llm_model` | 无——没有实体父级 |
| `llm_call` | `space_id`、`user_id`、`task_id`、`task_run_id` |
| `audit_event` | `space_id` |
| `system_grant` | `user_id` |
| `artifact` | `space_id` |

`workflow_step_run` 虽然没有对应的详情路由，却依然保留了公共 ID：Issue 的输出会把它
保存下来，作为一个溯源关联句柄。`system_grant` 保留公共 ID，是因为管理员 API 和运维
CLI 会把授权记录作为持久化的权威历史返回给调用方。`artifact` 不仅保留了公共 ID，对它的
依赖也比其他任何一张表都更深——`GET /api/artifacts/{artifact_id}` 这条路由本身不带
Space 路径段，而是先从记录中取出 Space，再据此完成授权。

### 6.2 不携带公共 ID 的表——8 张

| 表 | 身份标识方式 |
|---|---|
| `space_member` | 关联行。`space_id` 和 `user_id` 都改为数字 |
| `agent_revision` | 丢弃 `agent_revision_id`。改由数字 `agent_id` 加 `revision` 标识；`created_by` 改为数字 |
| `workflow_revision` | 丢弃 `workflow_revision_id`。改由数字 `workflow_id` 加 `revision` 标识；`created_by` 改为数字 |
| `task_run_artifact` | 数字 `task_run_id`，仍与相对路径成对出现 |
| `login_code` | 数字 `user_id`。代码哈希仍然是查找键 |
| `user_refresh_token` | 数字 `user_id`。令牌哈希以及 `as_` 登录链会话 ID 保留各自的身份验证格式 |
| `plugin` | 丢弃 `plugin_id`。`name` 是清单文件拥有的 slug，每条路由都以它寻址——`GET /api/plugins/{plugin_name}` |
| `plugin_release` | 丢弃 `plugin_release_id`。以 `(plugin_name, version)` 寻址，这本来就是其不可变性约束；`plugin_id` 改为数字，`plugin_name` 保持反规范化冗余 |

丢弃插件相关的公共 ID，是相对于原提案的新增内容——那份提案的写作时间早于这几张表的
出现。这样做是安全的：Portal 仅把 `plugin_id` 和 `plugin_release_id` 当作 React 列表
的 key 使用，可以直接替换为 `name` 和 `${plugin_name}@${version}`。

一张表失去自己的句柄之后，会连带两件事，而这两件事都是需要当场作出的决策，而不是留到
日后才发现的后果：

- 一条引用了该行的审计记录，改为按该行的自然键来命名。插件相关的审计事件携带插件的
  `name`，发布事件携带的是 `name@version`——它本身不可变，也正是每条路由已经用来寻址
  的值。
- 本地留存的溯源记录同理处理。`<BUILDMAX_HOME>` 中的 `PluginState.CatalogID` 记录了
  一份已安装的插件来自目录中的哪一条，如今它保存的就是插件的 `name`。这个字段因而可以
  说与该状态自身的键有些冗余；但把它去掉是另一项独立的变更，因为它同时也出现在一次
  运行的来源记录里。

### 6.3 使用自然键的表——2 张

| 表 | 原因 |
|---|---|
| `quota_tier` | `tier_name` 是由配置拥有的自然键。`user.quota_tier` 和 `space.quota_tier` 继续按名称引用它 |
| `schema_migration` | `id` 是该迁移永久沿用的、由作者赋予的名称 |

## 7. 哪些引用保持不透明

一个列只有在恰好命名了一种服务器实体类型、并且应用把这层关系当作实时数据模型的一部分来
对待时，才会转为数字。以下这些都无法通过这条判定，因此继续保留字符串列，并统一改名为
`<concept>_public_id`（此处的值是一个公共句柄）：

| 列 | 为什么保留 |
|---|---|
| `audit_event.actor_id` / `target_id` | 多态字段。`actor_type` 和 `target_type` 携带了具体类型；单一数字列无法寻址多张表中的行 |
| `issue.executor_id` | 多态字段。`executor_kind` 取值为 `agent` 或 `workflow`。`issue.owner_id` 不在此列——owner 始终是一个 user 行，因此它是一个已解析的数字引用 |
| `issue_comment.author_id` | 依 `author_kind` 而多态 |
| `artifact.created_by_id`、`artifact.source_id` | 依 `created_by_type` 与 `source_type` 而多态 |
| `task_run.created_by` | 由 `created_by_type` 定型，允许取值为 `user`、`webhook`、`system` |
| `system_grant.granted_by` | 授予部署权限的运维人员未必对应一行 user 记录 |
| `task.session_id`、`task_run.session_id`、`llm_call.session_id` | Agent 会话 ID 命名的是某次运行 `BUILDMAX_HOME` 下的一个文件，而不是一行数据库记录 |
| `task_run.trace_path` | 命名的是一个轨迹文件 |
| `conversation_message.tool_call_id` | 提供商自己的工具调用 ID |
| `llm_call.target_id`、`llm_call.alias`、`llm_call.upstream_model` | 见下文 |
| `login_code.code_hash`、`user_refresh_token.token_hash` / `session_id`、`user_webhook_key` 的密钥哈希 | 格式由各自的身份验证约定拥有 |
| Workflow 定义 JSON 内部的步骤 ID | 是在定义中手写出来的，而不是数据库行 |

`task.created_by`、`conversation.created_by`、`issue.created_by`、
`workflow.created_by`、`workflow_run.created_by`，以及两张 revision 表各自的
`created_by`、`plugin.created_by`，还有 `plugin_release.published_by` /
`yanked_by`，**都会**转为数字：它们都没有配套的类型列，并且无条件地对应一行 user 记录。
`task.created_by` 即便对 webhook 和 system 触发的运行来说，也是任务的所有者——这两种
触发方式都携带一个预先配置好的用户身份。

历史数据本身不构成保留字符串的理由。即便不设外键，一个可为空的数字引用依然能够记录下
一行已被删除的记录曾经的键值。

## 8. 数据库外键

不使用 GORM 关系，也不设置任何 `FOREIGN KEY` 约束。数字引用只是普通的带索引的列，引用
完整性仍然是应用层自己的责任。

这个问题此前一直悬而未决，等待一次删除语义方面的复查。复查结果如下，它会就此把问题彻底
了结，而不是再拖延一次。

**BuildMax 不会删除父行。** 存储层一共有五个删除方法，没有一个会移除被其他行引用的记录：

| 方法 | 删除的内容 |
|---|---|
| `RevokeKey` | 所有者主动吊销的 webhook 凭证 |
| `DeleteIssueComment` | 一条评论——这是整个模式中唯一一处针对用户内容的硬删除 |
| `PruneAuditEvents` | 超过留存窗口的事件，按时间清理，从不按目标清理 |
| `DeleteExpiredLoginCodes` | 已经无法再兑换的验证码 |
| `DeleteExpiredRefreshTokens` | 已过期的令牌 |

`DeleteAgent` 实际上是一次改名：它只是设置 `deleted_at`，这样引用了该 Agent 的记录依然
能够正常解析。其余一切“消失”的记录都以同样的方式处理——Artifact 上的 `deleted_at`，
插件上的 `archived_at`，授权记录上的 `revoked_at`，账户上的 `disabled_at`。不存在任何
路径可以删除一个用户、一个 Space、一个 Task、一次 Run、一个 Conversation、一个 Issue
或一个 Workflow。

所以 `RESTRICT` 约束防范的是一个根本不存在的风险，却要为此立即付出代价。每一个创建
用户的测试夹具都必须按依赖顺序拆除七张表——存储层测试里的 `deleteTestUser` 已经手工
完成了这件事，而这正是任何清理路径都必须采取的形状。这是一项实实在在的成本，对应的收益
眼下却是零。

等到真正的删除功能出现时，答案会随之改变——“删除这个 Space 及其中的一切”显然就是这样
一个功能。无论数据库是否强制执行，这个功能都必须自行规定一个删除顺序，而这些约束正适合
在同一次变更中一并加入，因为顺序反正都要被写下来。如果提前加入约束，只会导致这个顺序被
写两遍。

与此同时，数字引用绝不应被理解为隐含了 `CASCADE`。`internal/architecture` 中的
`TestNoDatabaseForeignKeys` 用来守住这一点：一个行结构体旁边的 bigint 列，只差一个
关系标签就会变成 `AutoMigrate` 会实际生成的约束，而树里的其他任何地方都不会注意到这一
变化。

## 9. 存储边界

公共 ID 会跨越进程边界和持久化系统边界。数字 ID 不会。

| 边界 | 表示形式 |
|---|---|
| HTTP 请求与响应 | 公共 ID |
| Portal 路由与客户端状态 | 公共 ID |
| Access Token 的 `sub`；Run Token 的 `sub`、`tid`、`rid`、`kid` | 公共 ID |
| 日志、轨迹、工具输出 | 公共 ID |
| 对象存储的键 | 公共 ID |
| Workflow 定义 JSON | 公共 ID |
| Kubernetes Job 名称 | 由公共 ID 派生 |
| `internal/core` 下的领域包及每一个仓储接口 | 公共 ID |
| `internal/infra/db` 内部的行结构体与 SQL | 数字 ID |

核心包绝不能为了省一次查询而长出第二套面向内部 ID 的 API。那样做只会把一个 MySQL
实现细节推到 `internal/infra/db` 之上，并迫使每一个 mock 和替代存储实现都去复现它。
行结构体同时拥有两种表示；领域模型只拥有公共表示这一种。

### 9.1 解析

一个未导出的辅助函数把公共 ID 解析为数字键，并由带类型的包装函数指明具体的表：

```go
func lookupKey(ctx context.Context, tx *gorm.DB, table, publicID string) (uint64, error)
```

无论是未能通过 `ParsePublicID` 校验的公共 ID，还是格式合法但未命中任何行的公共 ID，都会
返回 `apierr.ErrNotFound`——处理器层早已用 `400` 拒绝了格式错误的输入，而一个格式良好但
未知的取值绝不能变成一个可以用来探测存在性的探针。

### 9.2 无 N+1 地读取

一次以公共资源为根的读取，只需解析一次它自己的数字键，再连接查询出它必须返回的每一个
相关公共 ID。每一次连接都是一次基于主键的查找。提案中要求给出的原型——Task 聚合
查询——如下：

```sql
SELECT  t.*,
        c.public_id  AS conversation_public_id,
        tm.public_id AS space_public_id,
        i.public_id  AS issue_public_id,
        a.public_id  AS agent_public_id,
        lr.public_id AS last_run_public_id,
        u.public_id  AS created_by_public_id
FROM        task         t
JOIN        conversation c  ON c.id  = t.conversation_id
JOIN        space         tm ON tm.id = t.space_id
JOIN        user         u  ON u.id  = t.created_by
LEFT JOIN   issue        i  ON i.id  = t.issue_id
LEFT JOIN   agent        a  ON a.id  = t.agent_id
LEFT JOIN   task_run     lr ON lr.id = t.last_run_id
WHERE   tm.public_id = ? AND t.public_id = ?;
```

在 Go 代码里，这对应一个既持有行结构体、又持有各个连接出来的句柄的读取结构体，并且详情
读取、列表读取和运行输出读取共用同一个 `taskSelect()` 构建函数，这样它们各自的连接集合
就不会彼此漂移。

这一行必须是一个带 `gorm:"embedded"` 标签的**具名**字段，绝不能是匿名字段。GORM 在读取
一个自带 `TableName` 的匿名内嵌结构体时，会把它当成一次关联处理，而不去扫描它自身的任何
列——于是连接出来的那些句柄被正确填入，而这一行自身的字段却停留在零值，且不会报出任何
错误。结果就是一次 Space 读取返回一个“无名”的 Space，而不是直接失败，以至于在某个测试
对字段做断言之前根本没人能发现这个问题。列表形式用的是同一条语句，只是加上
`WHERE tm.public_id = ? ORDER BY t.created_at DESC, t.id DESC LIMIT ?`，这也正是
`idx_task_space_created` 存在的原因。

写入则反过来：先解析一次根，然后从已经读到的这一行里取出其余所有的键。创建一个 Task
时，先解析 Conversation，再从同一行里读出它的 `space_id`，而不必再单独解析一次 Space。

一次加锁读取绝不会带连接。`SELECT ... FOR UPDATE` 通过连接查询时会把被连接进来的行也
一并锁住，所以如果在锁定读取里顺带解析出一个刷新令牌所属用户，就会在整次令牌轮换期间
锁住该账户，并把该账户打开的每一个会话都串行化。当一行被锁定的记录必须报告某个句柄时，
这个句柄要改为单独按键查出。

### 9.3 键集游标

键集游标是调用方合理需要用到行键来打破平局的唯一场景。审计导出功能按 `created_at` 加
行键分页遍历，因为 `created_at` 的精度只到秒，而多个事件经常共享同一秒。

因此 `model.AuditCursor` 用**公共**句柄来命名上一页的最后一个事件，再由存储层在键集
查询条件内部把这个句柄解析为行键：

```sql
WHERE created_at < ?
   OR (created_at = ? AND id < (SELECT id FROM audit_event WHERE public_id = ?))
```

每一页只需一次索引查找，而不是每一行都查一次，也不必多一次往返——另一种做法是把行键
直接交给调用方，让它在下一次请求时再传回来，而这恰恰是本设计要防止的那种泄漏。未来任何
新增的游标都遵循同样的形状。

### 9.4 聚合

`SpaceUsageInWindow` 目前的连接条件是
`task ON task.task_id = task_run.task_id AND task.space_id = ?`——每一行要做两次字符串
比较。在顶层把 Space 的公共 ID 解析一次之后，这两个条件都会变成数字比较，查询过程中
不会再触碰任何字符串。这正是 §12 中要求给出 `EXPLAIN` 输出作为证据的那条查询。

### 9.5 冲突重试

`llm_call.go` 里的 `isDuplicateKey` 并不区分具体是哪个索引被违反，因此它无法把一次
公共 ID 冲突（应当重新生成并重试）与一次真正的唯一性冲突（例如重复的邮箱，或者一个
幂等键，这类情况应当原样返回错误）区分开。它需要一个能感知索引的兄弟函数，从 MySQL 的
`1062` 错误信息中读出具体的索引名称，并且只针对 `uq_<table>_public_id` 这一种情况最多
重试三次。

生成逻辑要下沉到 `internal/infra/db` 内部，对每种实体都是如此。目前
`internal/service/artifact/service.go` 是在存储层之上生成 Artifact ID 的，这使得重试
循环根本无法触及生成器。

## 10. API 契约

HTTP 资源的路由拓扑不发生变化。
[routes.go](../../../internal/server/handlers/routes.go) 以及 `space`、`work`、
`artifact`、`admin`、`worker` 各个处理器包中的每一条路径，都保持原有的形状和语义化的
参数名；发生变化的只是参数值本身的格式。

```text
GET  /api/spaces/{space_id}/tasks/{task_id}
GET  /api/spaces/{space_id}/task-runs/{task_run_id}/trace
GET  /api/artifacts/{artifact_id}
POST /api/worker/task-runs/{task_run_id}/llm/completions
```

`public_id` 是一个数据库层面的名字，永远不会出现在 JSON 里。一个资源用 `id` 来表示
自己的句柄；各种关系仍然使用语义化的名字：

```json
{
  "id": "ivyoh5qcfu6ypfkhyedq",
  "space_id": "lzmomgl6mzg2bve3bgka",
  "conversation_id": "2l73hqqx6fcl7eecggda",
  "status": "SUCCEEDED"
}
```

这会给每一种实体响应中的自身句柄字段改名——`task_id` → `id`，`task_run_id` → `id`，
以此类推——影响范围覆盖 `internal/core/model` 的 JSON 标签、
`internal/server/websocket/protocol.go`、`internal/infra/workerclient/api_types.go`、
Portal 的 `lib/api/types.ts` 与 `lib/api/mappers.ts`，以及 Desktop。像 `space_id`、
`conversation_id` 这样的关系字段不受影响。如果某个创建接口的响应里用语义化名字返回了
一个相关句柄，这个名字会被保留；本次变更不要求对无关的响应结构做额外改动。

Agent 和 Workflow 的 revision 响应会失去自己的 `id` 字段：一个 revision 是由它的父级
加上修订号来标识的，`POST .../revisions/{revision}/restore` 早已是这样寻址的。
revision 相关路径参数仍然使用整数。

有一个共用的编解码器负责校验来自路径参数、查询参数和 JSON 请求体中的 ID：

| 输入 | 结果 |
|---|---|
| 不是规范文本 | `400 Bad Request` |
| 是规范文本，但未命中任何行 | `404 Not Found` |
| 是规范文本，命中的行在调用方 Space 之外 | `404 Not Found` |

一次 Space 范围内的查找，会先解析出 Space 的公共 ID，再同时用公共 ID 和数字 Space 键
来约束目标资源，这样一个合法的公共 ID 就不可能变成一个跨 Space 的存在性探针。

Access Token 的 `sub`，以及 Run Token 的 `sub`、`tid`、`rid`、`kid`，继续携带公共 ID，
只是换成了新格式。Worker 相关路由仍然会比较规范化后的 `rid` 与路由里的 `task_run_id`
是否一致。`/api/webhook` 依旧只用 webhook 密钥本身来做身份验证，而不是用该密钥的公共
ID。

这次切换会让每一个 access token、刷新会话、run token、Portal 链接和书签同时失效。这是
不设双读路径必须付出的代价，而在 Alpha 阶段这样付出一次是可以承受的。

## 11. 非 HTTP 边界

| 界面 | 变化 |
|---|---|
| 对象存储 | `PersistObjectKey`、`RunOutputResultKey`、`RunOutputFileKey`、`TaskBuildmaxObjectKey`、`RunGlobalObjectKey`、`RunArtifactsObjectKey`、`ArtifactObjectKey` 都保持各自的结构和其中的公共 ID 片段不变。已有对象会变得不可达；§12 会重置存储 |
| Kubernetes | `util.WorkerJobNameForTaskRun` 保留其 DNS-1123 清理逻辑，一个 base32 ID 可以原样通过。有一个测试专门断言这一点，这样未来任何格式变更都不会悄悄地重新引入折叠碰撞的问题 |
| 轨迹 | Run 的轨迹已经同时携带 `rt_` 文件 ID 和公共实体 ID；这里只有后者的格式会发生变化 |
| WebSocket | `internal/server/websocket/protocol.go` 遵循 §10 中的字段改名 |
| 种子数据与样例数据 | `sample-data/` 以及任何持有带前缀 ID 的测试夹具都需要重新生成 |

## 12. Alpha 过渡

不设兼容层，不设双读，不允许新旧格式混用。

Alpha 阶段的数据库和对象存储会被重置。没有任何一个部署环境里存有谁真正需要的数据：
本地参考环境用 `./make kind down && ./make kind up` 从零重建，`./make e2e local` 也
只是在单次运行内自行拥有一套 Compose 技术栈。因此这次切换完全不带任何兼容性负担。

这也正是选择重置、而不是走迁移路线的原因所在。`AutoMigrate` 根本无法表达这样一次
变更——它同时是一次改名、一次改类型，还要一次性回填每一个关系列——如果把它写成
`schema_migration` 的条目，就等于把一种没有任何部署真正需要保留的数据形状固化下来，
还要让这段代码永远存在下去，却不会给任何人带来好处。

`internal/infra/db/migration.go` 中的 `migrations` 列表是只追加的，其中已有的三条
（`0001`–`0003`）描述的正是一种即将不复存在的模式。它们会随着这次重置一起被删除：
留着它们只会留下一些无法在这个二进制程序能够创建的任何数据库上运行的迁移。

## 13. 执行计划

六个层层递进的变更，均已落地。每一个都能独立编译、通过 `./make test`，也都能独立接受
评审。只有第 3 个及以后的 PR 需要重置数据库。

### PR 1 — 编解码器

`internal/util/id.go` 新增 `NewPublicID`、`ParsePublicID`、`FormatPublicID`，并保留
`NewPrefixedID`。其余部分不做任何改动；此时还没有任何调用方使用这几个新函数。

- 测试覆盖：字母表、精确的 20 字符长度、规范形式往返一致、拒绝非规范的尾部比特位、
  大小写不敏感的输入、错误的长度、空字符串、字母表之外的字符，以及 `crypto/rand`
  失败时表现为一个错误而不是 panic。
- 有一个测试断言 `WorkerJobNameForTaskRun` 对 base32 ID 原样保留不变。
- 检查项：`./make test ./internal/util`、`./make check go`。

### PR 2 — 模型身份结构

纯改名，不涉及格式变化，也不涉及模式变化。`internal/core/model` 去掉每一个
`ID uint`，把每种实体自身的句柄字段改名为 `ID string`，并打上 `json:"id"` 标签。
revision 相关结构体失去它们各自的公共 ID 字段。

波及范围：`internal/infra/db` 里的映射逻辑（行结构体本身不变——现有的 `task_id` 列

## 14. 实测计划

这是计划中列出的五条查询，在完成转换之后从 MySQL 8 里实际读取出来的执行计划。每一条
都最多通过唯一索引解析一次句柄，此后全部按行键连接。

| 查询 | 访问路径 |
|---|---|
| 配额：运行次数统计 | `task` 走 `idx_task_space_created`（`ref`，覆盖索引），然后 `task_run` 走 `idx_task_run_task_created`（`ref`，覆盖索引） |
| 配额：标题分词 | `task` 走 `idx_task_space_created`（`range`，索引条件下推） |
| Space 任务列表 | `task` 走 `idx_task_space_created` 做**反向索引扫描**——无需额外排序——然后全部六个连接都在 `PRIMARY` 上走 `eq_ref` |
| Conversation 消息列表 | `conversation` 走 `uq_conversation_public_id`（`const`，覆盖索引），然后 `conversation_message` 走 `idx_conversation_message_conversation`（`ref`） |
| 运行输出读取 | `conversation` 走 `uq_conversation_public_id`（`const`），然后 `user`、`task`、`task_run`、`task_run_artifact` 各自按键查找 |

这张表里有三点体现出这次转换真正带来了回报。任务列表通过反向读取组合索引来完成排序，
而不必对行本身排序，这是字符串模型遗留的单列 `space_id` 索引根本做不到的。两条配额
查询都仅凭索引本身就能给出答案——`Using index`，不必读取任何行——因为一个 `bigint`
类型的 Space 引用可以直接放进索引里。而每一次连接都是基于主键的 `eq_ref`，这正是让
一次列表查询保持为“一条查询”而不是“每行一条查询”的关键。

句柄在每条查询中只出现一次，表现为对 `BINARY(12)` 唯一索引的一次 `const` 查找。这正是
执行计划里那道转换边界：根部一次带索引的查找，此后全程都是数字。

## 17. 修正：文本形式即存储形式（2026-08）

D2 最初把原始的 12 字节存储在 `BINARY(12)` 中，只在 Go 代码里生成文本形式。存储方式的
这一条现在被反转了：`public_id` 改为 `char(20) CHARACTER SET ascii COLLATE ascii_bin`，
直接存放其他每一处边界早已展示出来的那 20 个小写字符本身。叙述最初那次转换过程的那些
章节（§5 最初的 DDL、§6.1、§13、§14）依然如实保留了那次工作当时的执行记录；凡是它们
写着 `BINARY(12)` 的地方，都以本修正案为准。

这次反转是一个运维层面的考量，和 §4.2 中选择 base32 而不是 base64url 是同一种论证：
格式会跟随 ID 走到它被读取的每一个地方。最初的决策权衡了存储宽度，却从未对可读性定过
价。而实际情况是，数据库正是人们阅读 ID 的场所之一——每一次调试和支持过程中，都少不了
在 MySQL 客户端里执行 `SELECT`——`BINARY(12)` 会把每一个句柄都渲染成一段无法辨认的
二进制内容。最先尝试过的几种替代方案——手工安装在 SQL 里做 base32 编解码的存储函数、
给每条查询套一层 `HEX()`——都是在每一次直接查询前面永远加上一道转换步骤。直接存储
文本本身，则彻底去掉了这道转换边界里“存储”这一半；`lookupKey` 依然会对输入做规范化
处理，但写出去的路径上不再有任何转换。

最初的决策换来了什么、其中又保留下来了什么：

- **宽度。** 每个值节省 8 个字节，包括列本身及其唯一索引。以本项目的数据规模来说，这点
  差异只是噪声；它也从来没有被当作一项真正的约束来衡量过。
- **memcmp 级别的身份比较。** 靠 `ascii_bin` 保留了下来：比较仍然是字节相等比较，不做
  大小写折叠，也不做排序规则展开。§1 中对字符串身份的反对意见，针对的是 `utf8mb4` 的
  通用排序规则，而不是一个字母表本就封闭、宽度固定的 ascii_bin 列。
- **每个值只有一种拼写。** 保留了下来，而且如今更加重要：编解码器的规范形式（小写、
  末位比特全零）会在每一次写入和查找之前被强制执行，因此唯一索引看到的永远只有一种
  拼写——换成一个不那么严格的存储方式，同一个值本可能以十六种不同的拼写作为不同的行
  同时存在。

这在编解码器上的连带结果记在 §4.3：既然已经没有调用方还持有原始字节，
`ParsePublicID`/`FormatPublicID` 就合并成了 `CanonicalPublicID`。原本强制执行
`binary(12)` 的那个架构测试，现在改为强制执行
`char(20) CHARACTER SET ascii COLLATE ascii_bin` 以及一个 `string` 字段。

已有的数据库不会被迁移，这与 D8 以及 §16 中关于重置的答案是一致的：目前仍然没有任何
正式部署环境，本地环境本身就是靠重新生成来更新的（`./make kind down && ./make kind up`，
或者直接删掉 Compose 的数据卷）。一个修正案之前创建的数据库，会在第一次读取 `public_id`
时就失败；重新创建它即可。
