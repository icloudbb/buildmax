## 1. 决策

聊天平台是进入 Portal 聊天已在使用的 **Tier 1 Conversation 的一种传输通道**。
服务端的 **Connector** 持有一个 bot 凭证，并对平台消息做归一化。与平台无关的
**Gateway** 在任何模型运行之前，判定发送者是谁、可以使用哪个 Space。随后它
通过与 Portal 消息相同的 turn 队列和 `conversation.Service` 运行该 turn，并把
回复发回去。当由该会话启动的 Task 结束时，Gateway 会把结果报告到聊天中。

只有当某个 BuildMax 用户**关联**了聊天账号之后，消息才以该用户身份行事。关联在
聊天中发起，在 Portal 中确认。每条消息都要经过唯一的资格判定权威检查，因此被禁用
或离开 Space 的账号会立即失去聊天访问权。

Telegram 私聊最先交付。群组、其他平台、流式回复以及在聊天中审批属于后续阶段
（§11）。

## 2. 为何选择 Conversation 平面

即时通讯聊天属于前台对话：一个人提问，助手回答，繁重的工作交给持久的 Task。
这恰好就是 Conversation 的定义（[Task 线程](Agent执行与Task线程.md) §4）。
cron 触发则不同。它不是对话，这正是 `ChannelCron`
[被移出此平面](定时Agent执行.md)的原因。聊天消息是唯一属于这里的来源类型，而且它
不会成为执行或授权的父级：它启动的 Task 仍归 Space 所有。

有四种备选方案被否决。

- **通过 n8n 或脚本桥接通用 webhook。** 一个 webhook key 只对应一个账号，因此
  每个聊天参与者都会以该 key 所有者的身份行事。这样既没有按发送者的授权，也没有
  线程和流式输出。
- **在 CLI 或 Desktop 中运行本地 gateway**，即 OpenClaw 和 Claude Code
  Channels 的形态。本地 Bash 沙箱默认关闭，因此一条聊天消息就能以用户的全部权限
  驱动一个未沙箱化的进程。而且也没有本地守护进程。这种形态的公开记录——暴露的
  gateway、令牌被盗、插件市场恶意软件——说明应当等到存在沙箱化的本地 runtime
  之后再考虑。
- **把聊天作为远程控制的查看端。** 它对于在手机上审批一个活的本地会话很有价值，
  但只能触达已经在一台开着的机器上运行的会话。它是建立在本记录所构建身份之上的
  后续投影（§11）。
- **把渠道做成外部插件。** 这会在两个适配器验证接口之前就冻结接口。取而代之的
  接缝见 §10。

## 3. 平台施加的约束

这些约束来自各平台截至 2026-09 的文档。Connector 契约正是围绕它们设计的。

| 平台 | 无公网 URL 时的入站方式 | 每个 bot 的消费者数 | 原生流式输出 |
|---|---|---|---|
| Telegram | `getUpdates` 长轮询 | 一个。Webhook 与轮询互斥 | `sendMessageDraft`（私聊） |
| Slack | Socket Mode | 最多 10 个 socket。每个事件只投递给其中一个 | `chat.startStream` / `appendStream` / `stopStream` |
| 飞书/Lark | 长连接 WebSocket | 最多 50 个。每个事件只投递给其中一个 | CardKit 流式卡片 |
| 钉钉 | Stream 模式 | 多个。每个事件只投递给其中一个 | AI 卡片流式输出 |
| 企业微信智能机器人 | 长连接 | 一个。最新的连接会挤掉旧连接 | `stream` 消息 |
| Discord | Gateway WebSocket | 分片 | 仅支持编辑消息 |

- **没有平台做广播。** 每条消息只到达一个消费者，且每个平台都是至少一次投递。
  因此接收需要每个 bot 只有一个持有者（§8），并需要去重。
- **出站连接模式只需要出口网络。** 这正是私有部署 BuildMax 的常见形态，因此
  connector 优先采用这类模式而非 webhook。
- **最终消息投递在所有平台上都可用。** 流式输出是增强，而非前提。

已有实践（OpenClaw、Hermes Agent、Claude Code Channels、Claude in Slack、
Slack 中的 Codex 和 Cursor）都收敛到本记录采纳的模式：

- 平台用户 id 通过带外方式绑定，访问默认拒绝；
- 会话以聊天和线程为键；
- 群组中需要 @提及；
- 每次审批都会重新授权点击者。

同样的实践也揭示了应当避免的失败：

- 任何能发消息的人都能驱动 agent；
- 任何能回复的人都能审批；
- 控制平面和令牌被暴露；
- 链接预览泄露数据。

## 4. 概念

每个概念都列出了缺少它就会失败的需求。

- **Connector 配置**不是实体。它是 `server.yaml` 中的
  `channels.telegram.bot_token`，通过 `BUILDMAX_TELEGRAM_BOT_TOKEN` 注入。
  - [Space 密钥 §4](Space密钥.md) 已经把 BuildMax 自身的凭证放在运维配置中。
  - 一个部署通常每个平台只有一个 bot。
  - Space 自有的 bot 要等到有团队需要自己的 bot 身份时再说。
- **`channel_identity`** 是平台、租户和外部用户 id 到用户的映射。
  - 没有它，消息就无法携带按发送者的权限。
  - 它刻意不是 `external_identity`。那一行是带 JIT 账号创建的登录凭证，而聊天
    关联绝不能让任何人登录。
  - 它的键是平台的不可变 id，绝不是显示名称。
  - `tenant` 在 Telegram 上为空。它之所以存在，是因为飞书、钉钉和企业微信的 id
    按组织或应用划分作用域，日后再把它加入唯一键就需要一次迁移。
- **`channel_pairing`** 保存待定关联码的哈希。没有它，关联就无法在可信界面上
  确认（§6）。
- **`conversation.channel_ref`** 是由平台承载的会话所应答的聊天。
  - 它让下一条消息能延续会话，也让结果能报告到正确的聊天。
  - 多行可以共享同一个 ref。最新的一行就是该聊天的当前会话。`/new` 和 `/space`
    就地开启另一个会话，不需要指针表。
  - 只有 Gateway 设置它。因此 `telegram` 不在 `ValidChannels()` 中，HTTP 和
    WebSocket 的创建路径都不接受它。

旧的 `channel.Adapter` 接口（`Receive(raw any)`，以及一个没人调用的 `Send`）
没有被扩展。它仍是 webhook 自己的类型，聊天平台则使用 `core/channel.Connector`。

## 5. 消息生命周期

1. **接收。** 在租约持有者上（§8），Connector 把平台消息归一化为 `Inbound`，
   Gateway 把它排在同一聊天中更早的消息之后。
   - 同一聊天按顺序应答，不同聊天并发进行。
   - 一个聊天最多有 10 条消息在等待。
   - 重复投递的事件 id 会被丢弃。
2. **把关，在任何模型调用之前。**
   - 私聊以外的一切都被忽略。
   - 未关联的发送者只会收到一条配对回复，别无其他。
   - 已关联发送者的会话是该聊天最新的会话，或者是在其个人 Space 中新建的会话。
   - 运行 `eligibility.Check(user, space)`，拒绝时回复固定文本，不含任何
     Space 数据。
3. **Turn。** `Handler.RunChannelTurn` 把 turn 提交给 `turnqueue`，并像 Portal
   消息一样运行 `conversation.Service.HandleTurn`。因此同一会话上的聊天 turn 与
   Portal turn 彼此串行。行事用户就是发送者，使用其配额。
4. **回复。** 回复以纯文本发送，并禁用链接预览。它会按平台上限拆分，Telegram 上
   是 4096 个 UTF-16 单元。
   - turn 运行期间会刷新"正在输入"指示。
   - 模型文本从不以 Markdown 解析模式发送，因为一个未转义的字符就会让整条消息
     发送失败。
   - 错误会变成固定语句，或者为调用方编写的 `apierr` 消息。其他错误会被记录日志，
     聊天中只收到一句通用语句和一个 Portal 链接。
5. **命令。**
   - `/new` 在当前 Space 中开启新会话。
   - `/space` 列出用户的 Space；`/space <n>` 切换过去并在那里开启会话。
   - `/help` 显示命令。
   - 解除关联只能在 Portal 中进行，这样它只有一条经过审计的路径。

## 6. 配对

1. 来自未关联聊天账号的消息会得到一个 8 字符的码。
   - 字母表不含易混淆字符，约有 40 比特熵。
   - 码 10 分钟后过期、只能使用一次，且只存储其 SHA-256。
   - 新码会替换该账号之前的码。
   - 回复中附带一个 `public_base_url/#/account/chat/<code>` 链接。hash 片段
     永远不会进入服务器日志。
2. 用户登录 Portal。**账号 → 聊天账号**通过
   `GET /api/channel-link-pairings?code=` 查询该码，请求日志会对 `code` 脱敏。
   页面显示正在关联的平台和用户名。
3. 确认后，`POST /api/channel-links` 在一个加锁事务中消费该码并创建关联。随后
   聊天中会收到已关联的通知。

与 OpenClaw、Claude Code Channels 和 Claude Tag 一样，码在可信界面上确认，而
不是把 Portal 签发的密钥粘贴到聊天中。在确认前显示用户名，是对同意钓鱼（有人把
自己的关联码发给受害者）的防御。

- 一个未关联的聊天账号每 30 秒最多获得一个码，这样陌生人给 bot 发消息也无法把它
  变成数据库写入器。
- 已关联到其他人的聊天账号会拒绝新的关联（`ErrAlreadyLinked`，409），直到那条
  关联被移除。
- 关联和解除关联分别审计为 `channel_link.created` 和 `channel_link.removed`。
  平台的账号 id 永远不会出现在审计记录中。

## 7. 授权与信息披露

- **默认拒绝。** 未关联的发送者、群聊、被禁用的账号或非成员都不会触发模型调用，
  也得不到任何 Space 数据。
- **发送者即行事者。** 每个 turn 和 Task 都记录关联的用户。没有 bot 主体，也没有
  后备账号，这与 webhook 路径中配置的 `user_id` 不同。
- **暂不支持群组。** 群组中的每条回复都会到达可能不属于该 Space 的人。服务群组
  需要由 Space 所有者或管理员进行显式、经过审计的绑定（§11）。
- **注入面。** 聊天文本与 Portal 文本一样，是 Tier 1 模型的不可信输入。
  - Tier 1 工具只能启动、继续和读取 Space 工作，从不读取 Secret。
  - Worker 运行保持其 fail-closed 沙箱。
  - 只有触发消息本身会成为 turn。
- **通过渲染外泄。** 每条 bot 消息都关闭链接预览。
- **凭证。** bot 令牌只存在于运维配置中。
  - 在脱敏配置中只报告它是否已设置。
  - Connector 的错误会被脱敏，因为令牌是每个 Bot API URL 的一部分。
  - 它永远不会传给 TaskRun。
- **保留。** 消息会持久保存在平台的服务器上。用户指南中对此有说明。

## 8. 跨副本接收

Connector 的 `Receive` 只在持有该 connector 租约的副本上运行。

- **单副本。** 在 `coordination.mode: local` 下只有一个副本，没有租约。
- **Redis 模式。**
  - 每个副本每 10 秒调用一次 `TryAcquireLock("channel-connector:<platform>")`，
    直到获胜。
  - 获胜者以 30 秒 TTL 持有锁，并在后台续期。
  - 当键消失，或在整整一个 TTL 内无法确认时，续期器会关闭 `Lease.Lost()`。
    Gateway 随即立刻取消 `Receive`。
  - 在此变更之前，锁不会报告丢失。一个无限期接收的持有者必须知道这一点，否则它会
    与下一个持有者并行消费。
- **偏移量。** Telegram 的偏移量保存在内存中。Telegram 会保留所有尚未通过越过它
  请求来确认的更新，因此新的持有者会从旧持有者留下的位置继续。停止时，connector
  会确认它已取走的更新，因此交接不会重放已应答的消息。
- **排空。** 服务器先停止接收器，然后等待 turn，再等待它们的回复。排在排空之后的
  消息会收到"正在重启，请重新发送"的回复。
- **发送不需要租约。** 回复、关联确认和结果报告由持有它们的任意副本发出。

## 9. 结果报告

`OnTaskRunTerminal` 也会调用 `Gateway.ReportRunTerminal`。

- **哪些运行。** 只有其 Task 携带带 `channel_ref` 的 Conversation 的运行才会被
  报告。
- **谁仍然能看到。** 只有当会话的所有者仍通过其 Space 的资格检查、并且在该平台上
  仍有关联时，才会发送报告。
- **内容。** 报告给出 Task 标题和状态、最多 1500 个字符的输出（错误为 500 个），
  以及一个 Portal 链接。

已知缺口：

- 由陈旧运行回收器结束的运行不会触发 `OnTaskRunTerminal`，因此不会被报告。同一
  缺口也影响 Issue 运行评论。
- 从聊天启动的 Workflow 运行不会被报告，因为其节点 Task 不携带 Conversation。

## 10. 添加平台

一个平台就是 `internal/infra/imchannel/<platform>` 下实现
`core/channel.Connector` 的一个包：

- `Platform()`
- `Receive(ctx, deliver)`，归一化为 `Inbound`，自行处理瞬时错误，只在不可恢复的
  错误时提前返回；
- `Send(ctx, Outbound)`，按平台上限拆分并禁用预览；
- `Typing`
- `Info`

然后在 `ServerConfig` 中添加一个 `channels.<platform>` 块，并在 `env_spec.go`
中添加其密钥覆盖及脱敏。在 `bootstrap/channels.go` 中构建该 connector。

Gateway、存储、路由和 Portal 都无需任何改动：配对、把关、turn、回复和报告都与
平台无关。`Inbound.Tenant` 和 `tenant` 列是为 id 按组织划分作用域的平台而存在的。

## 11. 分阶段

| 阶段 | 范围 | 状态 |
|---|---|---|
| 1 | Telegram 私聊、最终消息回复、配对与 Portal 关联管理、`/new` 和 `/space`、结果报告、接收租约 | 已交付 |
| 2 | 飞书/Lark 长连接。由 Space 所有者或管理员进行经审计的 Space 绑定的群聊、@提及把关、通过 `channel_ref` 实现线程 → Conversation、卡片渲染 | 未开始 |
| 3 | 通过各平台原生原语实现流式输出，并以节流编辑作为后备 | 未开始 |
| 4 | 远程控制投影：把用户活的本地会话审批和完成情况推送到其关联的聊天，按钮会重新授权点击者 | 未开始 |
| 5 | 钉钉、企业微信、Slack、Discord，各为一个适配器，按需求推进 | 未开始 |

设计过程中发现了两个普通修复项。两者都不阻塞第 1 阶段：

- 陈旧运行回收器应当触发终态 hook；
- 入站 webhook 的默认 `webhook.user_id: "webhook"` 会被当作用户查找，不可能
  成功。

## 12. 待解决问题

1. **企业身份捷径。** 当部署的 OIDC 签发方就是同一个飞书、钉钉或企业微信租户时，
   能否根据稳定的租户声明自动关联聊天账号，而不必配对？
2. **群组成员。** 显式的绑定决定是否足够，还是应当在包含非成员的群组中拒绝回复？
   大多数平台无法低成本地枚举成员。
3. **超出发起聊天的通知。** 已关联的用户是否应当让其聊天订阅并非从那里发起的事件，
   例如 Issue 指派、日程暂停或 Workflow 失败？每一种都需要一个目前尚不存在的服务器
   事件。
4. **Worker 运行中的审批。** 对服务端 TaskRun 进行聊天审批，需要一个可暂停、可恢复
   的"等待审批"运行状态。这是对执行平面的改动，需要其单独的设计。
5. **成本可见性。** 聊天 turn 与 Portal turn 一样消耗用户配额。聊天回复是否需要
   显示其成本？
