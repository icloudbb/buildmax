## 1. 决策

本节描述的是曾经实现并产出已交付成果与交付机制的模型。对于新的执行路径，
后续的[Agent 执行与 Task 线程](Agent执行与Task线程.md)记录才是权威依据：
Tier 1 是可选的，直接发起的 Agent 运行无需 Conversation 即可创建 Task 和
TaskRun，结果呈现也不需要 Tier 1 的合成。

以下四件事之所以分开描述，是因为把它们混为一谈正是本记录要修正的缺陷的
根源：

1. **Tier 1——前台编排 Agent。** 与用户保持联系，负责交互、理解意图、承担
   有限的前台工作、拆解工作、选择执行器、发起调度并合成结果。
2. **Tier 2——执行 Agent 平面。** 专注于后台工作。目前是单一的通用 Agent；
   这一形态允许未来引入专用 Agent，而无需一个仅供 Portal 使用的运行时。
3. **持久化执行基础设施。** Task、TaskRun、调度器和 worker 承载 Tier 2，
   并持久化状态、输出、Artifact、轨迹、用量和失败信息。它们本身不是 Agent。
4. **结果投影。** Conversation 的 Task 卡、Issue 结果和通知都是从持久状态
   *派生*而来的。它们的存在不应依赖于一个存活的浏览器连接，也不应依赖于
   一次额外的、成功的模型调用。

第 4 点是关键所在。此前绝大多数问题都源于在公告发出的那一刻临时拼凑出投影，
而不是从记录中派生出投影。

## 2. Tier 1 与 Tier 2 的划分

划分依据不是任务难度，也不是模型能力强弱，而是执行属性：

| 维度 | Tier 1（前台） | Tier 2（后台） |
|---|---|---|
| 与用户的关系 | 在当前交互中作答 | 无人连接时仍继续执行 |
| 时间 | 延迟预算短且可预期 | 可能持续较长时间 |
| 持久性 | 无需独立的重试或取消机制 | 必须持久化、可重试、可取消 |
| 隔离性 | 轻量的共享前台策略 | 拥有自己的 worker、工作区和资源策略 |
| 专业化 | 通用交互与协调 | 特定的工具、模型、记忆或 Agent |
| 并行度 | 一轮对话内的少量操作 | 多个可独立并行的任务 |

把工作分发给 Tier 2，并不意味着 Tier 1 做不了这项工作，而是说明这项工作的
执行属性不适合放进一轮前台交互里完成。

Tier 1 绝不能：承诺持久化交付；把模型记忆当作任务状态的来源；在没有结构化
状态的情况下猜测任务是否完成；把 worker 的输出重新标记为用户消息；成为从
Issue、Workflow 或 webhook 创建 Task 的必经路径；或者仅凭自己生成的总结是否
成功来决定结果卡是否存在。这些情况都曾经真实发生过，而且每一种都造成过 bug。

## 3. 转录与执行事件保持分离

用户消息和 Agent 的回复构成转录（transcript）。Task 卡则是一种结构化的执行
投影。Task 卡不会伪装成一条消息，消息也不会被合成出来承载执行状态。

两者按 `created_at` 合并显示；若发生在同一秒，则由一个稳定的类型优先级决定
顺序——Task 排在消息之后，因为这一轮交互是先读取消息、再启动 Task 的。如果
将来确实需要严格的全序，届时可以设计一个按 Conversation 划分的序列号；仅凭
第一张 Task 卡还不足以证明需要引入一个事件存储。

各类内容按信任级别彼此区分：

| 内容 | 生产者 | 是否为用户指令 | 默认是否进入 LLM 历史 |
|---|---|---:|---:|
| 用户消息 | 用户 | 是 | 是 |
| 规范化后的指令 | Tier 1，经服务器校验 | 派生而来 | 仅在目标 worker 运行中 |
| Worker 输出 | Tier 2 Agent 及工具 | 否 | 否；对呈现者而言是不可信数据 |
| Task 状态、用量、轨迹引用 | Runtime | 否 | 通过结构化工具 |
| 呈现者总结 | 呈现者模型 | 否 | 可能作为一条 Agent 回复被持久化 |

Worker 输出永远不会以 `role=user` 的形式重放。呈现者若没有一次单独授权的
编排轮次，就无法启动或继续一个 Task。

## 4. 已交付内容

### 4.1 结果投影来自派生，而非公告

一个 Conversation 会为它发起的每个 Task 携带一张卡片，这张卡片从 Task 路由
读取，并在 socket 报告的每次失效通知时重新加载：状态、输出、文件、运行详情、
停止、再次运行等信息都在其中。即使发生刷新、socket 断开，或者总结始终没有
送达，这些卡片依然存在。

一次终态运行会向该 Space 上的每一个连接广播 `task.status.changed`——这是一次
失效通知，而不是结果本身。此前的做法是挑选创建者的第一个 socket 来通知：
如果创建者没有任何在线连接，就什么也通知不到；如果创建者开着三个标签页，也
只有一个会收到通知。

转录不包含系统频道，因此 `[Task Result]` 消息不会再被当作用户自己发出的消息
来渲染。

### 4.2 交付具备持久性——已被取代

本小节曾描述过最初的机制：每次运行对应一行记录（`task_result_delivery`），
通过认领的方式保证两台服务器不会重复呈现同一次运行的结果，由一个定期扫描
任务负责重试，在尝试次数达到上限后放弃并保留放弃原因，呈现文本在每次尝试时
都从该次运行重新派生，而不是预先存储。

这套机制已经被彻底移除，而不是作为过渡方案保留下来。现在，一次终态运行只会
广播一个失效事件（`task.status.changed`）；不再有任何代码去排队一次呈现尝试、
重试它，或者要求先完成一次前台模型调用才能让结果变得持久或可见。本小节当初
主张的边界，如今已经变成了结构性事实，而不是一种重试策略：**TaskRun 的结果
无需任何一句话来描述它，就已经是持久的**，因为 Conversation 的 Task 卡直接
读取 `task_run`，从来就不曾需要任何代码路径去专门写一条呈现记录。参见
[Agent 执行与 Task 线程 §4](Agent执行与Task线程.md#4-支持的输入路径)以及
第 12 节。

### 4.3 意图与执行可追溯地关联

`task_run.source_message_id` 指明了一次运行是在哪条 Conversation 消息中被
请求的。每次运行都记录自己的来源消息：一个 Task 的首次运行指向创建它的那条
消息，后续的延续运行指向请求这次延续的那条消息。这个绑定是按轮次完成的，而
不是按工具调用传递的，因此模型无法自行选择或省略自己的工作应归因于哪条消息。

`GET /api/spaces/{space_id}/task-runs/{task_run_id}` 会把这条消息与交给
worker 的指令并排引用出来。两者是不同的文本，这正是关键所在：如果指令中
缺少某个约束，要么是模型在转述时遗漏了它，要么是用户本来就没有提出过，除此
之外没有别的办法能区分这两种情况。

### 4.4 记录实际运行的定义版本

`task_run.agent_revision` 记录了一次运行所使用的 Agent 定义版本。指令是在
worker 领取自己的运行任务时才解析的，因此编辑一个 Agent 会改变它下一次运行
的行为——这是有意为之的设计，也正是需要这个版本号的原因：同一个 Task 的两次
运行完全可能执行不同的文本。谁先写入谁生效，所以在一次运行进行期间编辑
Agent，不会改写这次运行已经拿到的内容。

**选择来源不需要单独一列来记录。** 每一个挑选 Agent 的地方都与一个独有的
`trigger_source` 一一对应：Tier 1 的 `StartTask` 对应 `portal_conversation`，
Task 路由对应 `portal_task_create`，Issue 运行对应 `issue_agent_run`，
Workflow 步骤对应 `workflow_step`。如果再单独记录一次同样的事实，只会让它
有机会与真实情况产生偏差。只有当某一种触发方式第一次出现两种可选路径时——
比如在一次 Conversation 运行中，用户指定了某个 Agent，而 Tier 1 只是原样
透传——这个字段才会真正变得不可派生，到那时再添加它也不迟。

### 4.5 合成 Conversation 已被彻底移除，而不只是隐藏——已被取代

过去，一个 Workflow 步骤和一次 Issue Agent 运行都会各自创建一个
Conversation，原因是 Task 要求必须有一个 Conversation 作为父对象；这些
Conversation 通过一个频道过滤器从 `ListConversationsBySpace` 中被隐藏起来。
现在两者都不再创建 Conversation：它们都直接创建一个 Space 拥有的 Task（见
第 5.1 节）。`workflow` 和 `issue_agent` 这两个合成频道、`SyntheticChannels()`，
以及用来排除它们的列表过滤器，都已经被彻底删除，而不是留在代码里却再也没有
任何代码去生成它们所过滤的内容。

## 5. 延后的内容及原因

### 5.1 Conversation 曾是每次执行的强制父对象——已交付

这一项当初之所以被延后，是因为它远不止是把一列改成可空这么简单：它需要把
worker 目录和对象存储的键都从依赖 `ConversationID` 改掉，需要改造通过
Conversation 授权的 Artifact 处理器，还涉及会话恢复逻辑，以及所有假定存在
Conversation 的 API 路径。这次切换后来在一次改动中一次性完成，正如当初延后
说明里指出的那样必须一次做完：`task.space_id` 现在是必需的，也是所有权的
权威来源；`task.conversation_id` 变成了一个可空的来源关联；运行的存储改为
按 space/task/task-run 寻址，而不再依赖创建者和 Conversation；Issue 运行和
Workflow 步骤都各自直接创建 Task；Task/TaskRun/Artifact/轨迹/模型调用的授权
全部通过 `task.space_id` 解析。参见
[Agent 执行与 Task 线程 §13.1](Agent执行与Task线程.md#131-所有权割接)。

### 5.2 Tier 2 目录

一个 Agent 定义究竟应该携带哪些能力、工具、输入/输出契约和执行画像字段，
**需要以证据为准入条件**。应当先由现有的定义和实际使用情况确立哪些类别是
稳定的，现在就把这些字段写死，等于是在凭空制造需求。

在证据出现之前，不要预先定义 `ResearchAgent`、`CodingAgent` 或类似的 Go
类型。

目前已经可行的做法是：Tier 1 通过 `StartTask` 根据 Space 的摘要信息推荐一个
Agent，而 Workflow、Issue 和 Task 路由则都会显式地指定一个。Space 成员身份
会被校验，但模型和执行策略目前不会。

### 5.3 Tier 1 的前台预算与 ExecutionSpec

前台的时间、工具、权限和资源预算，Tier 1 可以读取哪些上下文，以及一个经过
校验的 ExecutionSpec，这些目前都还是开放问题。

之所以可以安全地延后，是因为 Tier 1 在实践中已经受到了限制：最多十轮迭代、
非交互式策略，以及一小组没有文件系统或 shell 访问权限的 Task 与 Workflow
工具。它启动并观察持久化的工作——后台 Task，以及它可以列出、启动和读取的已发布
Workflow run——但无法触及文件系统或 shell，也无法创作 Workflow（见
[助理编排与 Workflow 边界 §9.5](../proposals/assistant-orchestration-and-workflow-boundary.md#95-从对话界面调用一个可调用单元)）。一旦
Tier 1 被允许读取 Space 的文件、Issue 和结果，这个预算就会立刻变成一个
**前提条件**——但在那之前不必着急。

附件和上下文引用目前也没有被记录下来。`source_message_id` 正是它们将来可以
挂靠的锚点，而这个字段现在已经存在。

### 5.4 Tier 2 执行期间的结构化总结

在 worker 运行内部直接生成总结，可以省下一次模型调用。但这仍然只是一个
待评估的想法，而不是一个已经做出的决定：目前还没有人真正衡量过那次调用的
成本。

### 5.5 产品语言

把 Tier 1 和 Tier 2 定义为按生命周期区分的前台层与后台层，并把 Task、
TaskRun、调度器和 worker 描述为基础设施而不是另一种 Agent 类型，这属于不
涉及任何行为改动的命名工作。它应当排在第 5.1 节之后再做，因为第 5.1 节改变
了这些对象本身的含义。

## 6. 不推荐的模型

- 为每一次终态运行都把完整输出复制进一行 `run_outcome` 记录；
- 在 Conversation 层面维护一个独立于 TaskRun 状态的 Task 状态；
- 把 Task 卡编码成一条 Markdown 格式的 Agent 消息；
- 为 Portal 的每一种对象都建立一张通用的多态事件表；
- 把每一个 Task 都自动提升为一个 Issue。

## 7. 被否决的替代方案

| 替代方案 | 为什么不采用 |
|---|---|
| 保持原有的 Tier 1 → Tier 2 路径不变 | 会丢失离线回复、产生无法追溯的改写、强制多出一次模型调用、并产生合成 Conversation |
| 合并成一个同步的 Agent | 长时间的工作会阻塞 Conversation；浏览器的生命周期会渗透进执行过程；持久化的重试、取消和隔离能力都会丢失 |
| 挂起并恢复单个 Agent 运行 | 需要持久化的续跑、检查点和跨进程流式传输，远远超出了这个问题本身的范围，留作后续研究方向 |

## 8. 仍需证据支持的问题

- **Tier 1 究竟应该具备哪些前台能力。** 也就是用户期望在 Conversation 中
  直接得到答案、而不是被分发出去处理的请求究竟有哪些。
- **是否已经存在稳定的专用 Tier 2 Agent。** 这些类别应当由实际使用情况来
  命名，而不是由本文档来定义。
- **用户是否真的想要自动生成的总结**，还是更倾向于只看 Task 卡、按需再要
  一份解释。这决定了第 4.2 节所描述的机制到底有多大价值。
- **Conversation 与 Issue 之间的产品关系**——一次聊天请求应该在什么时候
  转化为被追踪的工作。
- **是否确实需要严格的按 Conversation 划分的时间线全序**，还是 `created_at`
  加类型优先级就已经足够。就目前而言，后者已经足够。
