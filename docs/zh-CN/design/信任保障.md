## 1. 目的

已经完成的 P0 工作让共享的 Agent Core 稳定到可以支撑 CLI、Desktop、Portal 和 Worker 的任务运行。R0 随后关闭了绕过 Worker 边界的 stdio MCP 路径，并为受支持契约的各项控制提供了证据（§6.1）。

本文档刻意停留在产品能力层面：记录已经交付的信任能力以及范围明确的剩余工作。

## 2. 方向

剩余 R0 聚焦受支持的无人值守 Worker 配置。CLI、Desktop、Portal 和 Worker 仍应以各自界面适合的方式暴露共享核心能力。

目标是：

> 用户和运维人员能够理解、控制并调试 Agent 的运行。

## 3. 需要支持的关键能力

### 3.1 Runtime Hooks —— 已交付 ✅

Runtime Hook 系统已经实现，详细设计见[Hook 系统](./Hook系统.md)。要点如下：

**配置位置**——两层的配置项会叠加合并：
- 全局：`<BUILDMAX_HOME>/settings.yaml` 中的 `hooks:` 字段
- 工作区：`<workspace>/.buildmax/hooks.yaml`

**传输方式**——每个条目通过 `type:` 选择一种：
- `command`（默认）—— shell 命令，通过 stdin 传入 JSON
- `http` —— 向某个 URL 发送 POST JSON 请求
- `mcp_tool` —— 调用已连接 MCP Server 上的工具
- `prompt` —— 单轮 LLM 评审

**已交付的事件（13 个）**：

| 事件 | 是否阻断 | 锚点 |
|---|---|---|
| `SessionStart` / `SessionEnd` | 否 | `agentapp.OpenSession` / `CloseSession` |
| `UserPromptSubmit` | **是** | `agentapp.RunPrompt`（写入历史之前） |
| `PreToolUse` | **是** | `applyPolicyAndExecute`（策略检查之后、执行之前） |
| `PostToolUse` / `PostToolUseFailure` | 否 | 工具成功/出错路径 |
| `Notification` | 否 | 围绕审批流程（`approval_required`、`permission_denied`） |
| `PreCompact` | **是** | 上下文压缩之前 |
| `PostCompact` | 否 | 压缩成功之后 |
| `SubagentStart` / `SubagentStop` | 否 | 子代理运行器 |
| `Stop` | 否 | 主 Agent 成功退出 |
| `StopFailure` | 否 | 任意错误退出（主 Agent 或子代理） |

由此解锁的使用场景：格式化/静态检查（`post_tool_use`）、策略检查（`pre_tool_use`）、外部审批（`notification` + `pre_tool_use`）、审计导出（`stop` / `subagent_stop` / `post_tool_use_failure`）。

**子代理继承**：子代理共享父级的 HookManager；子代理运行产生的每个事件负载都会打上 `is_subagent` 和 `agent_type` 标记，方便审计 Hook 归因。子代理无法绕过父级 Hook。

**推迟**到某次运行确有需要时再做：Skill/子代理 frontmatter 中的 Hook（会话级生命周期）。详见[Hook 系统](./Hook系统.md) §10（实施阶段 F）。`agent` 传输方式、`async` 命令标志和 `buildmax hooks` 检查器不在 R0 范围内（§4）：13 个事件配合四种传输方式已经覆盖已验证的 Hook 使用场景，而 Hook 配置本身很小、由文件写就，专门的检查器命令暂时不值得做。

### 3.2 沙箱与执行边界 —— 已交付 ✅

命令执行现在拥有明确的沙箱模式，详细设计见[沙箱边界](./沙箱边界.md)，其中 A–E 阶段均已实现。沙箱隔离的是 **Bash 子进程**（macOS 上使用 Seatbelt，Linux/WSL2 上使用 `bwrap`，其他平台不可用）；非 Bash 工具仍然沿用既有的权限边界。配置由 `settings.yaml`、`policy.yaml` 与 `BUILDMAX_SANDBOX_ENABLED` 合并解析，并带有按使用面区分的默认值；`buildmax sandbox status|deps|mode|enable|disable` 以及 TUI 页脚会显示当前生效的模式。

对照上文清单，边界覆盖情况如下：

- 工作区文件系统访问 —— ✅ 操作系统后端的绑定/配置规则
- 外部目录访问 —— ✅ `filesystem.allow_write`、`deny_read` 等规则
- 网络访问 —— ✅ Go 端 HTTP/SOCKS 代理，按域名允许/拒绝
- 环境变量暴露 —— ✅ 形似密钥的变量会从 Bash 环境中被清除
- 进程执行限制 —— ✅ `sandbox.process.{max_cpu_seconds,max_memory_mb,max_processes,max_open_files}` 会转换为前置在包装命令之前的 `ulimit` 语句，每项限制单独一条；已经在真实的 Alpine 和 macOS shell 上验证，其中包括在 Linux 上由 CPU 时间限制实际杀死一个忙循环（`max_memory_mb` 在 macOS 上是文档记录过的无效项——Darwin 的 `setrlimit` 没有 `RLIMIT_AS`）。详见[沙箱边界](./沙箱边界.md) §13 阶段 D。
- Worker/容器执行模式 —— ✅ **已经接入，并针对生产环境的 Pod 安全上下文完成验证**：`agentapp/taskrun` 设置的是 `SandboxSurface: config.WorkerSandboxSurface()`，只有当 `BUILDMAX_SANDBOX_BACKEND_INSTALLED` 被设置（两个 Worker Dockerfile 中都有的一行 `ENV`）时，才会选中 `SandboxSurfaceWorker`——最初曾尝试无条件选中这个严格基线，结果在裸机 Linux 主机或原生 Windows 上直接搞垮了所有 Worker 任务（因为 `fail_if_unavailable: true` 却没有后端可以满足它），这个问题是被 CI 捕获的，而不是在本地开发时发现的，因为 Mac 上 Seatbelt 始终存在。`internal/infra/k8s/job.go` 原本使用的 `RuntimeDefault` seccomp 配置文件，会在 Worker Pod 的能力（capabilities）被清空后拦掉 `bwrap` 所需的系统调用，因此被替换成了专门为此构建的 `Localhost` 配置文件（[deployment/seccomp/README.md](../../../deployment/seccomp/README.md) 记录了完整的根因链路，包括另一个独立的内核限制——在容器内 `--unshare-pid` 下挂载 `/proc` 会被拦截）。已经针对一个具备 Worker 真实安全上下文的实际 Pod，以及参考 `DaemonSet` 实际分发的那份配置文件完成验证，并通过部署冒烟测试现在自动执行的一次自然端到端运行加以确认：让模拟模型驱动一次真实下发的任务经由真正的 server → worker → Job 路径调用 `Bash`，然后断言的是工具的执行结果，而不是任务预先写好的最终文本；详见[沙箱边界](./沙箱边界.md) §13 阶段 F。

`command` 和 `http` 这两种 Hook 传输方式现在也会咨询 `SandboxView`——Hook 会执行与 `Bash`/`WebFetch` 相同的 `WrapBashCommand`/`HostAllowed` 调用，而且没有类似 `dangerously_disable_sandbox` 的逃逸入口，因为 Hook 是配置写就的自动化流程，不是由运维者逐轮盯着、LLM 主动选择发起的调用。已经针对一个真实的 `sandbox.Manager`（Seatbelt）完成验证，而不只是一个测试替身。强制执行引擎、Worker 使用面、进程限制、降级标记和 Hook 边界都已经落地，因此 §3.2 已经收尾。唯一未构建的命令 `buildmax sandbox overrides`（[沙箱边界](./沙箱边界.md) §8）不在 R0 范围内（§4）：它只写入 `allow_unsandboxed_commands`——一个已经能在 `policy.yaml` 中设置的运维锁，因此没有哪次运行需要一个逐会话的便捷开关来收紧边界。

### 3.3 持久化运行轨迹 —— 第一阶段已交付 ✅

持久化运行轨迹现在会为每次运行保存运行时事件流，详细设计见[持久化运行轨迹](./持久化运行轨迹.md)。第一阶段已经交付：在唯一的 `agentapp.RunPrompt` 关卡处写入一份有界、脱敏的 JSONL 轨迹，因此 CLI/TUI、Desktop、评估和 Worker 的运行都能产生轨迹，而不需要各个使用面各写一份代码。每次运行会写入 `<DataDir>/sessions/<session_id>/traces/<run_id>.jsonl`（Run ID 前缀为 `rt_`），内容包括一条 `run_start` 记录、一条 `sandbox_boundary` 记录、逐轮迭代的 `llm_*`/`tool_*`/`context_compacted` 记录，以及末尾的 `run_end` 记录。可以通过 `BUILDMAX_TRACE_DISABLED` 关闭。失败即放行：轨迹写入失败绝不会打断或拖慢一次运行。

轨迹经过大小限制和脱敏处理，既能用于调试，又不会泄露密钥。

对照 §3.3 完整目标的覆盖情况（✅ 表示第一阶段已经支持）：

- 模型调用 —— ✅ `llm_start` / `llm_end`
- 工具调用 —— ✅ `tool_start` / `tool_end` / `tool_denied`
- 上下文压缩 —— ✅ `context_compacted`
- 错误 —— ✅ `run_end.error`；重试尚未在事件流中体现
- Token 用量与耗时 —— ✅ 每次调用的 Token 数、工具耗时、记录时间戳
- 审批决定 —— 部分支持：只有 `tool_denied`（原因为 `hook`/`user`）
- Hook 执行 —— ❌ 需要专门的 Hook 事件
- 文件变更 —— ❌ 需要文件变更事件
- 子代理的父子关系 —— ✅ 每个子代理的轨迹都携带其直接父级的 `parent_run_id`
- 沙箱模式与边界决策 —— 部分支持：每次运行都会写入一条 `sandbox_boundary` 记录，包含解析后的启用状态/模式/后端和来源链条，未受任何限制的运行会被明确标记为 `sandboxed: false`。逐条命令级别的边界决策与违规记录仍是 ❌（见 §3.2）
- 本次运行使用的记忆与指令来源 —— ❌ 推迟处理

上面标记为 ❌ 的记录（Hook 执行、文件变更、逐条命令的边界决策，以及某次运行加载的记忆/指令来源）才是真正剩余的轨迹工作，详见[持久化运行轨迹](./持久化运行轨迹.md) §7。它们能丰富诊断，但不是 R0 验收关卡（§6）。轨迹活动视图 UI、`buildmax trace` 检查器和轨迹目录的保留策略/垃圾回收不在 R0 范围内（§4）：JSONL 轨迹本身已经有界且可直接阅读，Portal 运行详情也已展示某次运行的边界与 MCP 处理，因此在轨迹量大到需要垃圾回收之前，再造一个查看器没有任何收益。

### 3.4 活动视图

在本地使用面中支持轻量级的活动视图。

TUI 和 Desktop 应当让用户能够查看：

- Agent 当前正在做什么
- 使用了哪些工具
- 发生了哪些审批
- 有哪些变更
- 运行为什么失败或停止

正常的对话界面应当保持简洁，活动信息通过渐进式披露呈现。

### 3.5 自检与诊断

支持一个针对本地环境搭建和运行时问题的诊断流程。

它应当检查：

- 模型配置
- 工作区权限
- Git 是否可用
- 当前生效的沙箱模式
- 当前生效的记忆和指令来源
- MCP 配置及其健康状况
- Skill 与子代理的发现情况
- Hook 配置
- BuildMax 数据目录的健康状况

诊断结果应当给出可执行的提示信息，以及一份脱敏后、可在调试时分享的摘要。

### 3.6 记忆与指令

三份契约需要保持彼此独立：指令是规范性的协议，记忆是 Agent 自行整理、可能出错的回忆，会话历史则是一次对话按顺序留下的证据。压缩摘要是一种有损的历史投影，即便它有助于回忆，也不能因此把它当作长期记忆。

记忆应当有明确的作用域并且可见。会话笔记和 todo 是目前已经交付的工作记忆作用域。CLI/Desktop 共享的 Project 身份以及有边界的 Project Memory 已按[本地 Project 记忆](本地项目记忆.md)实现。全局用户记忆、Space 记忆和可复用的 Agent 记忆仍然是各自独立的未来作用域，不应当把它们的含义强加给 `AGENTS.md` 或 Agent 指令。

Agent 应当暴露本次运行加载了哪些指令、记忆和历史投影来源。用户应当能够查看、更新、删除或禁用记忆。BuildMax 应当避免静默保留敏感或出人意料的信息，而且记忆绝不能覆盖 `AGENTS.md`、Skill、子代理定义或 Agent 指令等指令来源。

### 3.7 子代理可追溯性

为子代理的执行提供更清晰的可见性。

用户应当能够看到：

- 运行的是哪个子代理
- 为什么会调用它
- 它接收到了哪些记忆和指令来源
- 它使用了哪些工具
- 应用了哪些运行时边界
- 它返回了什么结果
- 它与父运行之间的关系

子代理不得绕过父级的运行时策略。

### 3.8 更安全的 Worker 执行

为非交互式运行提供 Worker 专属的信任行为。

Worker 运行应当：

- 在原本需要审批的场景下直接失败关闭
- 在明确的沙箱边界内运行
- 记录足够的轨迹数据以支持 Portal 诊断
- 只加载适合该 Space/运行作用域的记忆和指令
- 让被拒绝的操作有清晰、可理解的原因
- 避免掩盖本地与远程能力之间的差异

### 3.9 Worker Pod 全局出站网络——条件触发、暂缓实施

已经交付的命令边界会约束模型选择的 Bash 与 WebFetch 网络访问，Hook 传输也查询同一策略。
Worker 控制通道还有独立的 TLS 监听器与入站 NetworkPolicy；参见
[Worker API 网络边界](./Worker API网络边界.md)。这些控制不会为 Pod 中的每个进程
施加目的地允许列表。整个 Worker 的出站网络以及 Worker 可用的存储身份，仍是明确记录的残余限制。

这条更广的边界不是首个 Beta 的要求；首个 Beta 支持的是私有网络中的一个可信 Space。
如果把它设为 R0 门槛，BuildMax 就会在尚未掌握真实运行所需目的地的证据之前，
引入特定 CNI 或需要运维的代理；而已经允许的 Git 主机、软件包仓库、模型端点或上传服务，
依然可能接收有意外泄的数据。Beta 候选版本必须记录这项残余限制，不能暗示并不存在的约束。

当证据改变受支持的威胁模型时，再重新开启 Pod 级目的地强制，包括以下任一情况：

- 不互信的租户共享 Worker 基础设施；
- 任意不可信仓库成为受支持的输入；
- Worker 持有高价值凭证，其外泄风险需要 Pod 全局控制，而不仅是现有命令与 Hook 边界；或者
- 运维人员明确要求部署级出站允许列表，并愿意承担其运维成本。

选择实现前，先记录代表性运行实际需要的目的地，以及必须支持强制机制的部署环境。
可移植的 Kubernetes `NetworkPolicy`、Cilium FQDN 规则和专用出口代理，
在可移植性、主机名权威性、协议与运维成本上差异显著。
在证据作出选择之前，任何一种都不是 BuildMax 的无条件依赖。
按 Space 划分策略、替代 DNS 与直连 IP 旁路验证，以及 gVisor 这类外层 runtime，
都属于同一个条件触发的加固决定，而不属于当前 R0。

stdio MCP 子进程会在 Worker 命令边界之外启动。受支持的无人值守 Worker 配置现在
会拒绝它们：`AppConfig.UnattendedWorker` 把该配置作为显式事实携带，与沙箱后端标记
无关；一旦解析出 stdio Server，就会在任何子进程或模型调用之前令构造失败
（`internal/agentapp/mcp_manager.go`）。远程传输与本地使用面不受影响。该运行的轨迹会在
`sandbox_boundary` 旁写入一条 `mcp_boundary` 记录来记录这一处理方式，Portal 运行详情也会
展示它；在轨迹尚未创建之前被拒绝的运行，仍会留下一个指明该策略的 TaskRun 终态错误。
首个 Beta 可以禁用不受支持的传输；BuildMax 不需要先构建通用 Pod 出站产品，才能如实满足
这个更窄的契约。

## 4. 当前明确不在范围内

当前 R0 信任边界范围内不应包含以下内容：

- Pod 全局目的地策略、专用出口代理或 CNI 选择
- gVisor 或其他外层 Worker runtime
- 用户可选的检查点回滚或时间线恢复
- 自动写回工作区或合并
- 完整的 Portal 审计产品
- 重写 Workflow 引擎
- 插件市场
- IDE 扩展
- 用 Go 实现容器/seccomp
- 大范围的版本化工作区实现

以上前两项属于条件触发的加固：当支持的威胁模型发生变化时再重开（§3.9）。其余各项是独立的产品问题。下面这些则不同——它们是便捷界面，而强制执行的边界与那份有界、可直接阅读的轨迹已经让它们变得多余。它们是按奥卡姆剃刀砍掉的，不是推迟；只有当某项具体的运维或运行任务缺了它就做不成时，才把其中之一加回来：

- `buildmax sandbox overrides`、`buildmax hooks` 检查器和 `buildmax trace` 检查器——沙箱边界由配置和 `policy.yaml` 强制执行，Hook 配置很小且由文件写就，JSONL 轨迹也已经有界且可直接阅读，因此这几个第二命令界面都不值得保留
- 轨迹活动视图 UI 与轨迹保留策略/垃圾回收——轨迹在源头就已有界，Portal 运行详情也已展示某次运行的边界与 MCP 处理，因此在轨迹量大到需要垃圾回收之前，查看器和收集器都没有收益
- `agent` Hook 传输方式与 `async` 命令标志——13 个已交付事件配合四种传输方式已经覆盖已验证的 Hook 使用场景

Task 工作区 checkpoint 和 Continue 前恢复已经按照 [Task 工作区 Checkpoint](Task工作区检查点.md)交付。通用工作区历史、用户选择回滚、合并和自动写回 Space 文件仍是独立的产品问题，不阻塞 R0。

## 5. 建议优先级

R0 的实施顺序曾是：

1. 除非 stdio MCP 子进程能使用声明的边界，否则在 Worker 中拒绝它；并在 TaskRun
   已经可见的边界旁展示这一处理。—— 已完成。
2. 针对受支持的 Worker 配置演练命令、Hook、MCP、资源和 Worker API 边界。——
   已完成；§6.1 把每项映射到其证据。

其他信任保障改进由已经验证的用户或运维需求推动，不阻塞首个私有 Beta。

## 6. 验收标准

R0 信任边界工作已被接受；下列每一条都成立：

- 没有 stdio MCP 子进程在受支持 Worker 配置声明的边界之外运行——该配置会在装配期让解析到的 stdio server 失败；
- 必需的强制机制缺失时，运行会在模型执行前停止——无人值守 Worker 配置失败关闭；
- 运维人员能够看到 TaskRun 的实际边界与 MCP 处理——Portal 运行详情两者皆有展示；并且
- 部署证据以 §6.1 记录的层级覆盖受支持的 Bash、Hook、MCP、进程限制与 Worker API 控制。

Pod 全局出站和外层 runtime 隔离仍是首个私有 Beta 如实记录并接受的限制。
只有受支持的威胁模型发生变化，它们才成为发布门槛。经由运维旅程的完整不可变候选资格认证是单独的 R3 / [Beta 就绪记录](../deploy/beta-readiness.md)关卡；R0 关闭 Worker 契约并不代表已通过它。

### 6.1 证据

把每个受支持的 Worker 控制映射到其当前最强证据。Bash 与 Worker API 隔离经真实部署 Worker 路径证明；其余各项在控制实际执行的层面证明，运行于前两者已证明为真实的 Worker 配置之上。

| 控制 | 声明 | 证据 |
|---|---|---|
| Bash 限制 | 在部署 Worker 上，一条沙箱化 Bash 命令能运行，且工作区外的写入被拒绝 | 部署冒烟 `assertWorkerSandboxConfines`（[tools/mk/deploy_smoke.go](../../../tools/mk/deploy_smoke.go)）：一次真实下发的任务经 server → worker → Job 路径调用 Bash，断言探针执行了、工作区外写入被拒——而非任务预设的最终文本 |
| Worker API 隔离 | Worker 控制 API 从公网 Service 不可达，只接纳带标签的 Worker | kind 边界检查（[tools/mk/kind.go](../../../tools/mk/kind.go)）：`/api/worker/*` 在公网 Service 上 404，带标签 Worker 可达 Worker 端口，无标签 Pod 被拒；另有确定性的路由/令牌/TLS 测试（[Worker API 网络边界](./Worker API网络边界.md) §13.1） |
| stdio MCP 失败关闭 | 解析到的 stdio MCP server 在模型执行前让运行失败，且可读 | 装配期强制（[internal/agentapp/mcp_manager.go](../../../internal/agentapp/mcp_manager.go)）；该决策与环境无关——它在任何子进程或模型调用之前让构建失败——并在 taskrun-runtime、agentapp、trace 与 server-handler 各层证明（`worker_mcp_policy_test.go`、`mcp_boundary_test.go`，以及 work handler 的 trace 测试），且在 Portal 运行详情中展示 |
| 进程限制 | ulimit 包装路径约束一条沙箱化命令 | Worker 有意不设进程限制——由 Kubernetes Job 的 `resources` 负责（[internal/config/sandbox.go](../../../internal/config/sandbox.go)）；ulimit 包装机制已在真实 Alpine 与 macOS shell 上验证（[沙箱边界](./沙箱边界.md) §13.1） |
| Hook 边界 | `command`/`http` 钩子无法逃出沙箱 | 命令钩子执行的正是部署 Bash 探针所演练的同一条 `WrapBashCommand` 路径；已针对真实 Seatbelt `sandbox.Manager` 验证（[沙箱边界](./沙箱边界.md) §13.1） |

有两项是被接受、有记录的首个 Beta 限制，而非门槛：Pod 全局 Worker 出站目的地策略与外层 runtime（§3.9）。
