## 产品承诺

BuildMax 是一个开箱即用、可私有化部署的企业级 Agent 平台，由同一套共享的
Go Agent Core 驱动。

同一个运行时同时服务三种使用形态：

- 通过 CLI/TUI 与 Desktop 进行的直接本地执行；
- 通过 Server 与 Portal 进行的 Space 协作与治理；以及
- 通过 worker TaskRun 进行的持久后台执行。

对本地使用而言，Server 是可选的。接入一个 Server 会为本地客户端带来身份认证、
托管模型、Space 工作以及发布能力，但不会把本地执行变成一个只能远程使用的
产品。

## 产品模型

### 一个 Agent Core，多个使用面

重要的 Agent 能力首先属于共享运行时。CLI、Desktop、Portal 会话以及 worker
可以用不同的方式呈现和授权这些能力，但它们绝不能各自长出独立的工具调用循环，
或彼此不兼容的执行语义。

具体的划分由[《界面定位》](界面定位.md)负责：

- CLI/TUI 是速度最快的本地 Agent 使用面；
- Desktop 是本地个人 Agent 工作台；
- Portal 是面向企业运营的一层；
- worker 在不直接与用户对话的情况下执行持久的后台运行。

### Space 拥有共享资源

Space 是 Portal 资源的所有权与授权边界。角色、配额、Workflow、Issue、
Conversation、Task、Artifact、插件、审计和用量，都要放在这个边界内理解。
部署范围内的管理权限是单独授予的，并不意味着能访问其他 Space 的内容。

Issue 是面向用户的主要工作对象。它承载工作本身的表述，把讨论与执行关联
起来，让结果容易被找到，而不需要用户去理解调度器内部的实现细节。

### 前台交互与持久执行保持分离

Conversation 是一个独立的前台会话，同时也可以充当可选的编排者。它可以直接
给出回答，也可以在工作需要持久执行时创建一个由 Agent 支撑的 Task；但它不是
那个 Task 的强制性父对象。

Task 加上 TaskRun 构成持久执行平面。既可以通过它直接调用 Agent，Task 也会
在后续多次 TaskRun 之间保留同一个 Agent 会话。Conversation、Issue、
Workflow、API 请求或 Webhook 都可能是发起来源，但 Space 始终是所有者，任何
发起来源都不会成为执行或授权意义上的父对象。完整的边界与延续模型见
[《Agent 执行与 Task 线程》](Agent执行与Task线程.md)。

### 结果是一等公民

用户要的是结果，不是内部的任务图。因此 BuildMax 把结果摘要、Artifact 和
来源信息都当作产品对象来对待，而不是日志碎片。Task、运行、步骤、轨迹和
模型调用这些页面，都是围绕着那个结果展开的解释与下钻界面。

Artifact 是显式的、持久化的发布产物。一个 worker 的输出目录或一份本地文件，
不会仅仅因为它存在就自动成为 Artifact；必须由一个获得授权的产出方主动、
明确地把它发布出来。

## 运行时原则

### 本地模式与托管模式都保持诚实

一个本地客户端要么调用本地配置好的提供商，要么在登录之后调用其 BuildMax
部署所提供的模型。这两种模式不会合并模型目录或凭证。直接的本地模式在没有
Server 的情况下依然有用；托管模式则把提供商凭证留在服务器一侧。

### 信任边界必须可见

工具权限、Hook、沙箱、轨迹、worker 凭证和插件锁定，都必须如实描述实际生效
的边界。记录一次降级，总比暗示一个其实没有运行的沙箱更好，但涉及安全的策略
仍然可以选择直接失败关闭。BuildMax 不得声称自己实施了实际并未强制执行的
隔离、出站限制、审批或恢复行为。

默认情况下，每次运行都会产生有界、经过脱敏的轨迹证据。轨迹记录失败时按
“失败开放”处理，不影响执行本身，但对应界面应当说明证据缺失这件事。

### 持久性是限定范围的，不是变魔术

每一种持久化对象都要明确说明自己的持久化与恢复契约：

- 本地 Session 使用原子化的会话包与关联历史；
- TaskRun 及其结果投递是 Server 上的记录；
- Artifact 拥有稳定的身份标识和明确的保留行为；
- 审计记录与模型调用记录负责解释共享的运行过程。

BuildMax **没有**一个通用的、带版本管理的工作区服务，没有隐藏的 Git 状态
引擎，没有活动时间线式的恢复功能，也不承诺每一次文件改动都可撤销。Session
回退只会改变对话历史，不会撤销工具执行的效果，也不会恢复工作区里的文件。

[Task 工作区检查点](Task工作区检查点.md)是执行平面里一个经过认可的、范围
很窄的例外：一次已规划的 TaskRun 可以恢复某一个不可变的 `workspace/`
检查点，并在结束时发布下一个检查点，这样 Task 的延续就不会出现“记住的
Agent 历史”和“缺失的文件”对不上的情况。这属于执行层面的恢复，不是面向
用户的工作区历史功能。变更集、任意回滚、跨设备重建，以及把 Task 状态应用到
共享的 Space 文件上，这些能力仍然需要各自独立通过设计评审、明确所有权模型
并获得路线图优先级之后才能推进。

### 配置与执行始终保持可移植

Go 核心与 CLI/TUI 必须始终能够作为一个不依赖 Node 的单一二进制文件使用。
Portal 和 Desktop 可以使用各自的 React 前端，但运行时本身必须在所有受支持
的平台和模型提供商上，都适合本地部署与私有化部署。

## 现有概念

| 概念 | 产品角色 | 权威归属 |
|---|---|---|
| 本地工作区 | 本地 Agent 读取和修改的目录 | 本地用户与操作系统 |
| 本地 Session | 与一个本地 Agent 之间可恢复的交互 | 本地 Session 会话包 |
| Desktop Project | 围绕某个工作区的本地 UI 状态 | 仅存在于 Desktop；不是 Server 实体 |
| Space | 所有权与授权边界 | Server |
| Issue | 主要的共享工作对象 | Space |
| Workflow | 可复用的持久执行计划；目前是线性的，目标是演进为按版本锁定的自适应图 | Space |
| Conversation | 独立的前台会话，同时可选地充当编排者 | Space |
| Task / TaskRun | 持久的 Agent 线程及其执行轮次或尝试 | Space 与调度器 |
| Artifact | 拥有稳定身份标识的显式持久输出 | Space |
| 插件环境 | Space/Agent 层面的激活，加上仅限某个 Task 范围内的自主追加项；展开后的运行目录只是它们的投影 | 记录在 TaskRun 上的不可变包版本锁定与环境修订号 |

这张表是产品地图，不是数据库 schema。当前实际的字段与关系定义在
[数据模型](../contribute/architecture/data-model.md)中。

## 新产品方向

已开放的提案是可选方向，而不是这份愿景已经承诺要做的延伸。当前的候选方向
列在[提案索引](../../proposals/README.md)中。

一旦被接受，意味着要更新路线图、把持久性的设计理由写进正式的设计记录，并
删除对应的提案文档。在此之前，面向用户和运维者的文档只能描述已经实际交付
的能力。

## 决策标准

一项新能力是否适合 BuildMax，取决于它能否在不削弱共享运行时或 Space 边界
的前提下，至少强化一种使用形态，并且能否把它的权限归属、持久性、失败行为
和证据留存都讲清楚。

优先选择那些能让 Agent 的产出更容易获得、更值得信任、更便于复用的改动。
应当拒绝的捷径包括：造出一个只存在于 Portal 里的 Agent、让本地客户端变成
第二套管理界面、让 Conversation 成为强制性的执行父对象、让一次后台运行冒充
用户发出的消息，或者把尚未真正实现的恢复能力、安全边界包装成已经具备的
产品行为来呈现。
