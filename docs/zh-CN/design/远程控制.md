## 1. 决策

远程控制是凌驾于一个活的、设备驻留的 Agent 会话之上的**控制平面**：runtime、文件系统、
工具、MCP 服务器都留在用户机器上，服务器只是中继。本地进程**出站拨号**到服务器建立一条
WebSocket，把会话按用户账号注册、心跳，并中继其事件流；其他设备观测（Phase 1）、日后
驾驭（Phase 2+）该会话。

该平面刻意与 Task/TaskRun 分离。Task 是 bounded-turn、服务端执行的模型，其运行源自服务器
dispatch；而远程控制会话是持久、设备驻留的，其运行源自笔记本。把它建模成 TaskRun 会倒置
归属并扭曲两者，所以远程控制拥有自己的实体与自己的中继路径（[提案](../proposals/remote-control.md)
§5 记录了完整的"宿主 × 交互面"分解，以及为何控制面先行）。

## 2. 范围与定位

Phase 1 是**只读远程观测**：在笔记本上 opt-in，从另一台设备看到会话在线，并观看其流。
尚无入站驾驭。Phase 1 是全部的难点，因为服务器够不到笔记本；一旦出站通道、注册表、
presence 就位，后续阶段只是在同一通道上增加消息种类（§8）。

只引入一个真正新的网络原语：**笔记本→服务器的 agent WebSocket**（§4）。远端设备*观测*
所需的一切都复用既有服务端机制——带缓冲的、类似[持久化运行轨迹](持久化运行轨迹.md)的
`StreamHub`，以及已用于 Task 输出的 Server-Sent Events 模式——所以观测完全不碰 space 归属
的浏览器 WebSocket（§6）。

## 3. 归属与授权

一个活的远程控制会话是**账号归属，而非 Space 归属**。它属于某个 `UserID`，只对该用户
可见、可控。这是对 Portal"Space 拥有并授权资源"惯例（[Space 治理](Space治理.md)）的有意
偏离，也是对提案中"归属范围"开放问题的回答。

理由：被暴露的东西是用户自己的机器和其进行中的本地工作，在用户选择发布工件或开 issue 之前
它没有任何 Space。把笔记本会话绑到某个 Space，会强加一个并不存在的归属关系，还会让 Space
成员身份隐含地伸进某个成员的私人机器。账号才是真正的边界；日后若需要把活会话共享进某个
Space，那是一个增量授予，而非默认。

凭证是**既有的用户 JWT**（[客户端模式](客户端模式.md)之凭证部分）：本地客户端为托管推理
已持有的同一个 access token 用于给 agent WebSocket 鉴权。Phase 1 不引入设备令牌。按设备
信任（一个专用设备凭证，类似 [Worker 运行令牌](Worker运行令牌.md)，加上 Trusted-Devices
step-up）推迟到 Phase 5；在此之前，账号鉴权加 opt-in 与 kill switch（§7）就是边界。

## 4. Agent WebSocket

本地进程对服务器打开一条**出站** WebSocket，且不保留任何入站端口，因此机器绝不可被外部
触达——与 [Agent 桥接 CLI](Agent 桥接 CLI.md) 同一姿态、方向相反（那里是 subprocess 在
服务器拥有的运行期间触达服务器；这里是本地会话触达服务器以暴露自身）。该连接向外承载会话
事件，并在后续阶段向内承载命令；一条拨号连接即是双向的，无需任何监听套接字。

鉴权与浏览器 upgrade 一致：令牌以 `?token=` 查询参数传递（WebSocket upgrade 无法设置
header），并在提供套接字前校验为一个活跃的用户会话。客户端从用于托管推理的同一 HTTP 客户端
播种其 TLS 信任，因此该 WebSocket 恰好沿用客户端已在使用的信任。

消息集是一个小的类型化信封（`{type, payload}`，既有协议形状）：

- `agent.register` —— 客户端announce 一个会话（显示名、平台、主机）；服务器创建或
  重新挂接 `RemoteSession`（§5），并回复其 id，该 id 即流的键、也是用户在另一台设备打开的
  URL。
- `agent.heartbeat` —— 周期性存活；服务器记录 last-seen（§5）。
- `agent.event` —— 一条序列化的运行事件（§6），追加到该会话的流。

入站消息种类（`prompt`、`approval`、`cancel`）已定义但 Phase 1 不处理；加入它们是
Phase 2–4，且需要一个内存注册表把命令路由到持有该套接字的副本（§9）。

## 5. 活会话注册表与 presence

注册表是一个持久化实体 `RemoteSession`，由 `internal/core` 拥有、`internal/infra/db`
存储，遵循既有实体范式（public-ID 字符串标识、单数 snake_case 表、additive `AutoMigrate`）。
它记录归属用户、显示名、平台与主机、一个状态、一个 last-seen 时间戳。持久化它——而非只保留
一个内存套接字注册表——正是让 presence 与会话列表在多个服务器副本间正确的原因：数据库是
真相来源，任何副本都能据此回答"我的哪些会话是活的"。

presence 沿用既有存活先例，而非另造一个。`agent.heartbeat` 执行一次节流的 last-seen 写入
（auth session touch 的模式），一个调度器 reaper——仿照 stale-run reaper——在 last-seen
落到 grace 窗口之外时把会话标记为离线。干净断开立即把会话标记离线；reaper 是不干净掉线的
兜底。last-seen 列建索引，因为 reaper 按它扫描。

## 6. 事件中继与观测

**序列化。** 运行事件用既有的运行轨迹 record 类型（[持久化运行轨迹](持久化运行轨迹.md)）
序列化：它已经把每一种被持久化的事件种类映射为有界、脱敏、snake_case 的 JSON 行，也已处理
运行时事件里棘手的部分（error 值、超长字段）。复用它意味着中继天生就是脱敏且有界的，并产出
与轨迹相同的形状。轨迹刻意省略的逐 token 增量，走一条防抖 delta 路径，复用 worker stream
sender 的批处理，让实时打字得以保留而无需每 token 一次写入。

**tee 点。** 中继挂在运行时那个唯一的 chokepoint 上，事件在那里已扇向轨迹 recorder 与调用方
sink。挂在那里意味着每个表面——CLI、TUI、Desktop、print——都无需按表面写码即可中继；只有
opt-in 触发入口按表面不同（§7）。中继是**fail-open** 的：中继出错绝不扰动本地运行，与轨迹和
hook 的 fail-open 规则一致。

**观测。** 远端设备通过 Server-Sent Events 观测，而非 space 归属的浏览器 WebSocket，因为
会话是账号归属的（§3）。服务器把既有的带缓冲 `StreamHub` 按会话 id 作键：`agent.event`
追加，一个 SSE 端点订阅——先重放缓冲、再实时增量直到结束——与 Task 输出流相同的机制与多副本
行为。一个普通 HTTP 列表端点返回调用者的会话及 presence 供会话列表使用。这原样复用 Portal
的流式聊天渲染路径。

## 7. opt-in 信任与 kill switch

远程控制**默认关闭**，只在显式 opt-in 时激活、绝不隐式，因为暴露一个会话就是以用户账号在其
机器上远程执行代码。Phase 1 先在 CLI/TUI 上暴露 opt-in（一个 flag 和/或命令）；中继本身是
表面无关的（§6），所以 Desktop 与 print 模式的 opt-in 是日后的增量。

两个控制从一开始就限定风险：一个**kill switch** 设置，无视账号状态在机器上禁用远程控制；
以及终止某会话可触达性的能力。因为中继是用户自己的 `buildmax-server`，中继的转录从不离开
用户掌控的基础设施——比第三方中继更强的数据故事。本地沙箱姿态不变：远程控制不改变代码在哪
运行，这与网络暴露的 Environment 平面不同，后者另行主张 fail-closed 默认
（[Agent 沙箱策略](Agent沙箱策略.md)）。按设备信任是 Phase 5（§8）。

## 8. 分阶段

1. **只读远程观测** —— 实体、agent WebSocket（register/heartbeat/event）、presence、
   中继 tee、SSE 观测、会话列表，以及一个 Portal 只读视图。
2. **远程追加 prompt** —— 一条入站 `prompt` 投递进本地会话既有的 mid-run 输入接缝
   （[排队消息](排队消息.md)）；引入内存注册表用于跨副本命令路由。
3. **远程工具批准** —— 转发权限提示并取回决策。
4. **取消与重连加固** —— 入站取消；跨短暂断连排队并重放。
5. **通知与按设备信任** —— 第一个出站推送机制，以及一个设备凭证加 Trusted-Devices step-up。

把远程控制扩到*云端*宿主是建立在[提案](../proposals/remote-control.md) §5 环境底座上的
另一条轨道，不在这些阶段内。

## 9. 待解决问题

- **跨副本命令路由（Phase 2 已解决）。** 观测与副本无关，因为它经由持久化实体和协调总线
  支撑的 stream hub 流动。把命令投递到持有某会话套接字的那个副本，用一个按会话 id 作键的
  内存注册表加协调后端上一条专用命令通道实现：收到请求的副本若持有套接字就本地投递，否则
  发布该命令、由持有它的副本投递。形状与连接事件总线相同，但走各自的通道，二者互不交叉。
- **把活会话共享进 Space。** 账号范围（§3）是默认；若出现让某 Space 看到成员活会话的需求，
  应是一个显式增量授予，其形状本文未定。
- **转录保留。** 服务器只持有实时观测与短窗口重连所需的部分；中继流缓冲的确切保留窗口未定，
  且不应变成对本地历史的持久化存储。
- **Desktop 与 print 的 opt-in 人机工程。** 中继是表面无关的；按表面的 opt-in 呈现（Desktop
  开关、print 模式 flag）留给这些表面各自的后续。
