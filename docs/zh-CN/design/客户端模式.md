## 1. 决策

| | 本地模式 | 托管模式 |
|---|---|---|
| 触发条件 | 没有已存储的登录 | 存在已存储的登录（§3） |
| 模型列表 | `settings.yaml` 中的 `models[]` | 从服务器获取 |
| 提供商凭证 | 保存在本机 | 永不离开服务器 |
| LLM 调用 | 本机直接调用提供商 | 本机调用服务器 |

两种模式**互斥**。托管会话看不到本地模型条目，本地会话也看不到服务器模型。执行 `buildmax logout` 退出托管模式，执行 `buildmax login` 进入托管模式。

按重要性排列，这样做换来了三个特性：

- **由一个事实决定模式。** 没有模式开关，没有记住的偏好设置，两者之间也没有优先级规则。用户想知道“我现在处于哪种模式”时，只有一个地方需要查看，代码也一样。
- **不存在合并列表。** 如果把本地模型和服务器模型合并成一份列表，就需要为重名条目设计冲突规则、优先顺序，还要解释两边都匹配时 `--model` 到底指哪一个。只要列表只有一个来源，这些规则统统不需要。
- **不会残留隐式回退。** 服务器故障不可能把提示词悄悄转发到某个人的私人提供商密钥，因为托管模式下根本没有本地条目可以回退。这原本就是网关的规则；单一来源的列表把它变成了结构性的保证，而不再依赖人为约束。

代价是离线工作前必须先执行 `buildmax logout`。这个代价是可以接受的：它只是一条明确的命令，并且如实反映了发生的变化——提示词此后会被发往别的地方。

## 2. 本文解决的问题

托管模式过去要靠手工编辑 `settings.yaml` 来配置：

```yaml
- name: Space default
  model: default
  transport: buildmax
  server_url: https://buildmax.example.com
  space_id: tm_example
```

除 `model` 之外，其余每个字段其实都已经由登录过程确定，而 `buildmax models --space <space_id>` 干脆把这段配置打印出来让用户手动复制——这等于把设计缺口直接摆到了台面上。

根源是结构性的：**`settings.yaml` 只能读，不能写。** 仓库里唯一会写这个文件的只有 `buildmax init`，它是根据模板渲染出整个文件；`internal/config` 没有任何保存函数。于是登录这种有状态的动作，与“使用某个 Space 模型”这种配置编辑,两者从来没有被打通,也无法打通。

它还会留下悬空状态。执行 `buildmax logout` 之后，托管模式相关的条目仍然留在 `settings.yaml` 里，`buildmax doctor` 则会报告它们缺少登录。配置里保存着依赖会话状态的内容，两者迟早会不同步——事实也确实如此。

## 3. 模式解析

唯一的输入是是否存在已存储的登录：有,或者没有。

在写下本记录时，`auth.json` 就是登录信息的全部。此后操作系统的凭证存储接管了访问令牌和刷新令牌，文件里只剩下非敏感的那一半——服务器 URL、用户、邮箱。因此，“是否存在登录”现在由 `auth.Info` 同时读取这两部分来判断，而不再是一次简单的 `os.Stat`。模式所依赖的判断依据没有变，变的只是密钥存放的位置。

Desktop 的第三个模式开关已经被移除：`mode.go`、`desktopState`，以及 `UseLocalMode` / `ConnectToServer` 绑定都被删除了。`GetAuthStatus` 里那句“可用的登录胜过记住的本地选择”的注释，原本就是在两个事实来源并存时打的补丁，随着第二个来源一起消失了。现在 Desktop 和 CLI 一样直接进入 Agent，登录只是账户菜单里的一个操作，而不再是启动时的关卡。

因此启动阶段不再有模式问题需要回答：存在已存储的登录就是托管模式，什么都没有就是本地模式。

**存储了不等于可用。** 对于一个凭证已经失效的登录，`auth.Info` 会将其报告为已登出——这对于“是否要提供账户相关操作”这类判断来说是正确答案。但如果模式判断也依赖它，就会让一个过期会话自动变成本地模式——这正是 §1 和 §8 要防止的静默重定向。所以模式只取决于 `auth.StoredLogin`，它只回答凭证是否存在；凭证是否仍然有效则是[§8](#8-登录过期不会静默回退)要处理的问题。

## 4. 模型列表

服务器返回的是**去掉了凭证字段的 `ModelEntry` 列表**：`name`、`context_window`、`vision`、当前的 `pricing`，以及哪一个是默认项。没有 `api_url`，没有 `api_key`，没有端点信息，也没有上游模型标识符。

统一的数据形状意味着模型面板、默认模型规则、状态栏和 `buildmax models` 共用同一条代码路径，两种模式的区别只在于列表来自哪里。

只有客户端需要用到的信息才会跨越这条边界。客户端要根据上下文窗口压缩会话，也要判断某个模型能否读取图片再决定是否发送，所以这两项必须在本地就知道。推理强度、输出上限和缓存策略属于运营方的策略目标，留在服务器一侧。

价格也会跨越这条边界。它起初留在服务器一侧，理由是台账已经记录了成本，本地再算一遍就成了第二个答案。2026-09-24 的探索式测试暴露了这样做的代价：每个登入态的界面——会话页脚、`buildmax info`、`buildmax usage`、Desktop 的 `/info`——都对台账已经计价的调用显示 "not priced"，用户能打开的任何视图都看不到这笔花费。费率并不是秘密；无论如何用户都能看到自己调用的花费。因此列表以十进制字符串携带每个模型的费率，客户端用台账所用的同一个 `EstimateCost` 为每次调用计价。对相同的用量和费率，两者一致；台账在调用被接受时快照费率，所以当价格在会话期间变化时，台账仍然是权威，Portal 的用量页读取的也是台账（§9）。

模型条目上的 `transport` 字段随之一并消失。它之所以曾是每条记录自带的属性，是因为一份列表里混杂着两种模型；现在模式本身就说明了是哪一种，列表也就只需要一个来源。

## 5. 模型在部署范围内全局共享

Space 是协作边界——共享 Issue、Agent、Workflow，但**不是**模型授权边界。目录里的每个模型都对部署内的每个用户开放。

这是对 [llm-gateway.md §4.2](LLM网关.md) 的一次有意收窄：该文档原计划在数据库里实现按 Space 的模型策略。这项能力是被撤销了，而不是被推迟了。按 Space 门控模型意味着，一个属于多个 Space 的用户还得声明这次提示词是为哪个 Space 发出的——这是一个本产品没有、也不打算添加的“工作区选择”概念。

在做出这个决定时，代码事实上已经是部署范围全局共享的了：`server.yaml` 里的 `llm.aliases` 本来就把同一套模型暴露给每一个 Space，而按 Space 的数据库策略从未真正实现过。所以这一步删除的是一个从未构建出来的抽象，而不是改变现有行为。

## 6. 别名层被移除

`server.yaml` 中的 `llm.aliases` 和 `llm.default_alias` 已经消失。客户端通过 `llm_model.name` 来指定模型。`llm:` 块本身保留下来，其中只剩一个存活的键：`default_model`（[§7](#7-默认模型)）。

别名层原本的作用是，即便提供商路由发生变化，也要给 Space 一个稳定的名字。而 `llm_model.Name` 本身已经能做到这一点：它带有 `uniqueIndex; not null` 约束，面向运营人员，在整个部署范围内唯一。把某个名字重新指向另一个上游，只是编辑那一行的 `api_url` 和 `model` 字段——名字本身从不移动。在一个已经唯一的名字之上再叠加一层“别名到 ID”的映射，是没有第二个用途的间接层，连解析器自己都承认了这一点：它把别名描述为“本可以直接指向目录条目”的、面向 Space 的那一半。

既然 Space 已经从解析路径中出局，那一半也就没有存在的理由了。解析路径从：

```text
(space_id, alias) -> catalog ID -> LLMClient
```

变成了：

```text
name -> llm_model row -> LLMClient
```

## 7. 默认模型

两种模式都需要回答“新会话默认使用哪个模型”，并且在没有其他指定时都会回退到目录中的第一条记录。

- **本地模式：** `settings.yaml` 中新增的顶层键 `default_model`，指向 `models[]` 中的某一条记录。
- **托管模式：** `server.yaml` 中的 `llm.default_model`，指向 `llm_model` 表中的一行。服务器负责解析它，并在返回的模型列表中标记出该条目，客户端依然只需要读取一个标志位即可。

默认模型属于配置，而不是目录状态。[llm-gateway.md 的 §7](LLM网关.md) 认为目录不属于配置，理由是目录里保存着提供商凭证，这类信息不能随 ConfigMap 携带的文件到处传播。但模型名称不是凭证，所以这条理由并不适用于这个字段。

真正适用的理由有两条。第一，`server.yaml` 里已经保存着这个部署的其他模型选择——面向 Tier 1 的 `conversation.model`，以及面向任务运行的 `worker.llm.model`。如果把客户端默认值放到别的地方，就会把“这个部署默认使用什么模型”这一个问题拆成两处答案。第二，`worker.llm.model` 在为空时会回退到这个默认值；如果默认值存放在数据库里，`server.yaml` 就无法在不发起查询的情况下解释自己的行为。

修改默认值需要重启并不是新增的代价：`conversation.model` 本来就需要重启才能生效，而且更换一个部署的默认模型本身就该是一次审慎的、所有人都能察觉的变更，而不是日常操作。

因此解析链是：显式指定的名称，其次是 `llm.default_model`，最后才是目录中的第一行。如果 `default_model` 指向的行并不存在，**服务器会在启动时直接停止**，理由和“空目录检查”完全一致——配置本身能顺利解析通过，如果不在启动时拦截，就会导致每个会话在第一次调用时才失败。

`/model` 依然只作用于当前会话，不会被持久化，这和现有代码的行为一致。选用哪个模型是当前这次对话的属性，而不是一项设置；下一个会话仍然会从默认值重新开始。切换模型不需要写入任何磁盘状态，这正是切换成本低廉的原因。

## 8. 登录过期不会静默回退

登录可能存在但已经失效：刷新令牌过期了，或者会话被撤销了。托管模式绝不能在这种情况下悄悄退化成本地模式——这恰恰是“禁止回退”规则本就是为了阻止的、把受管流量重定向出去的行为。

界面会提示登录已过期，并只提供一个操作：回到本地模式。执行这个操作会**删除 `auth.json`**，这才是真正让客户端回到本地模式的动作，因为文件是否存在本身就代表着模式。在用户执行这个操作之前，会话不会运行。

在 CLI 上，这个操作就是 `buildmax logout`，它会直接写在错误信息里，而不是通过交互式提示询问——命令在终端里和脚本里读起来是一样的,而提示在脚本环境下根本无法读取。Desktop 则提供一个按钮，因为它本来就有地方可以放。

删除文件而不是把它标记为失效，是为了让 §3 的结论始终成立。如果保留一个已失效的 `auth.json`，就会多出第三种状态，届时每个读取者都得区分“有登录”和“有一个仍然有效的登录”。

只有用户才会删除它。客户端曾在服务器拒绝刷新时自行清除 `auth.json`，这让*下一条*命令在无人选择的情况下以本地模式运行——正是本节禁止的重定向，只是晚了一条命令。现在，被拒绝的刷新会被报告为 `ErrLoginExpired`，文件保持原样，直到用户重新登入或登出。

无法访问的部署并不是过期的登录。登录仍然有效，而针对已结束登录所提供的出路——登出——会把它丢弃。因此失败分为三类，每一类都有自己的下一步：`ErrLoginExpired`（重新登入，或登出）、`ErrAccountDisabled`（需要管理员重新启用，或登出）以及 `ErrServerUnavailable`（重试；登录保留）。Desktop 只对前两类显示登录已结束的页面；宕机则是一条会自行重试的横幅。2026-09-24 的探索式测试发现 Desktop 把每一种失败都当作第一类，这会促使用户在一次短暂宕机期间毁掉一个仍然有效的登录。

## 9. 用量归属到具体的人

`llm_call` 台账记录的是用户，而不是 Space：`space_id` **直接从这张表中删除**，而不是改成可为空。台账本来就带有 `task_run_id`，只要有人提问，就可以沿着 run → task → space 反推出所属的 Space。给每次调用都加一列 Space，只会是一种反范式设计，而唯一填不上这一列的恰恰是不属于任何 Space 的前台调用。

复合唯一索引 `idx_llm_call_client` 被重建为以用户键打头，这也是它所保护的幂等键的正确作用域：这个键本来就属于发送它的调用者。

读取某次 run 的台账,只需要授权这次 run 本身即可——它恰好只属于一个 Space——因此 `ListLLMCallsByTaskRun` 只接收 run 作为参数，由处理器先检查所有权。

前台调用不属于任何 Space，也意味着任何 Space 的用量都不包含它。因此调用者的个人视图 `GET /api/usage` 增加了 `managed_calls`：调用者自己在同一时段内、不属于任何 task run 的调用，按费率快照汇总，并用台账的公式计价。Space 范围的路由不包含它，因为某个成员自己的会话并不是该 Space 的花费。

按 Space 设置配额不在本文范围内。只有当“Space 工作区选择”被引入时,这个问题才会重新出现,因为按 Space 设置上限需要每次调用都恰好属于一个 Space,而如今的前台调用不属于任何 Space。

实现过程中发现了一件设计时没有预料到的事：对于一个凭证已经失效的登录，`auth.Info` 会将其报告为已登出——这对于“是否要提供账户相关操作”这类判断来说是正确答案。但如果模式判断也依赖它，就会让一个过期会话自动退化成本地模式——这正是 §1 和 §8 要防止的静默重定向。已存储的凭证决定模式；这些凭证是否仍然有效则是另一个有自己答案的问题。`auth.StoredLogin` 就体现了这一区分，`TestResolveModelSourceReportsAnExpiredLogin` 是保障这一点的测试。

## 12. 不在范围内

- **Space 工作区选择。** 没有它，按 Space 设置配额和按 Space 设置模型策略都无法实现，因此两者都被排除在外。按 Space 设置上限需要每次调用都恰好属于一个 Space，而前台调用不属于任何 Space。
- **迁移。** BuildMax 处于 alpha 阶段；`AutoMigrate` 直接应用了新的表结构，不欠现有部署任何兼容路径。
- **合并后的模型列表。** 已在 §1 中被否决，而不是被推迟。
- **缓存已获取的列表。** 托管模式在每次启动时都会重新获取，代价只是一次请求，却能保证答案始终是最新的。缓存会成为记录模式的第三个地方，过期的条目还会错误地反映某个部署实际提供的内容。

## 13. 会话停留在它开始时的模式中

§1 让两种模式对新提示词互斥，但会话带有历史，续接一个会话会再次发送那段历史。2026-09-24 的探索式测试在 `buildmax logout` 之后续接了一个针对部署写下的会话，指定一个本地模型，结果在没有任何提示的情况下把这段受治理的对话重放给了个人 key。反过来——登入后把一段本地对话交给部署——是方向相反的同一种重定向。

因此会话在它的元数据中记录提示词发往哪里，即 `prompt_destination`：`local`，或部署的 URL。第一轮设置它，此后不再改变。之后每一轮，在每个界面上，都会经过 `AgentApp.runTurn`，它会拒绝发往别处的一轮，并提示在会话开始时的模式中继续，或开始一个新会话。在第一轮而不是创建时记录，意味着一个从未运行过的会话会绑定到第一次运行它的模式。

只有本地 Project 的会话会被绑定。task run 的会话属于拥有该 run 的部署，继续它的 worker 可能通过另一个地址访问那个部署；把它绑定到某个 URL 只会破坏 Continue，而保护不了任何东西。
