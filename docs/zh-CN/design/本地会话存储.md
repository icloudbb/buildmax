## 1. 决策

将每个本地会话可变的整文件 JSON，替换为一个由该会话独占的目录，目录中的每类记录各自拥有自己的契约：

```text
<BUILDMAX_HOME>/sessions/
  index.json

  <session_id>/
    meta.json
    history.jsonl
    traces/
      <run_id>.jsonl
    writer.lock
```

- `meta.json` 是体积小、可原子替换的当前元数据记录。
- `history.jsonl` 是权威的、仅追加、可恢复的对话日志。
- `traces/<run_id>.jsonl` 延续现有的有界、脱敏、失败开放的运行诊断信息，每次运行一个文件。
- `writer.lock` 确保只有一个可变状态的所有者，而不会把已经过时的进程状态当作持久元数据来对待。
- `index.json` 是供会话选择器使用的、可重建的投影。

本设计借鉴了基于 JSONL 的编码类 Agent 中“持续追加条目、链式对话历史”的做法，但不会把元数据、可恢复内容与运行诊断混杂进同一个无边界的文件中。

## 2. 当前状态与问题

`internal/core/session.Session` 目前直接序列化到 `<BUILDMAX_HOME>/sessions/<id>.json`，其中包含：

- 用户、助手与工具消息；
- 助手发起的工具调用及其结果；
- 由模型提供方拥有的推理状态与非文本内容部分；
- 累计的提示词与补全令牌数；
- 压缩边界与摘要；
- 持久化的笔记与待办事项；以及
- 附加系统提示。

`SessionManager.Save` 会在一轮对话结束后，序列化整个对象并替换原文件。另一个 `sessions.json` 保存用于列表展示的标题、工作区、创建时间和置顶状态。所选模型只存在于 `SessionContext` 中，因此重新打开会话时目前会回退到默认模型。

这种结构存在四个问题，按严重程度从高到低排列：

1. 一轮较长的 Agent 执行可能在会话被保存之前，就已经完成了多次模型调用和工具步骤。进程崩溃后，系统就无法区分“从未开始的工作”与“可能已经改变了外部世界的工作”。
2. 扁平的 `Messages` 数组没有可供回退或分叉的、持久稳定的锚点。
3. 直接覆盖可能会在中断、磁盘耗尽或机器故障后，使唯一的文件变得无法解析。阶段 0 已经解决了这一项：这两个文件现在都通过 `util.WriteFileAtomic` 完成原子替换。
4. 每一轮都要重写此前所有的消息、工具结果、提供方状态和图像数据。

这里的排列顺序很关键。写放大是最显眼、却也是最不重要的问题：对本地单用户会话而言，它只造成浪费而非错误，单凭这一点只能支撑引入缓冲区，还不足以支撑更换存储格式。当前结构真正完全无法表达的是不确定的工具结果和缺失的条目标识，本文档余下的内容正是为了解决这两者。

原子替换本身值得做，也已经落地，但它只解决了第三个问题，并未解决增量持久化、工具结果的不确定性或链式历史，因此它只是权宜之计，而非最终答案。

## 3. 目标与非目标

### 3.1 目标

- 每个已完成、可恢复的条目只持久化一次，而不是每次都重写完整历史。
- 精确保留 `llm.Message` 的值，包括工具调用、提供方状态、内容部分和来源信息。
- 在一轮执行过程中提交足够的状态，以便在中断后能够安全恢复。
- 为每一条历史条目提供稳定的标识和逻辑父节点。
- 支持恢复、回退与分叉，同时不把运行轨迹当作权威状态。
- 保持标题查找和会话列表的响应速度。
- 将元数据、历史、轨迹与写入者锁各自的失败策略相互隔离。
- 使存储格式与产生某一轮对话的模型提供方无关，并可扩展以容纳当前版本尚未定义的记录类型。
- 为前台、后台和嵌套子 Agent 提供各自私有的持久会话，同时不将它们作为普通用户会话暴露出去。
- 保持单二进制的本地使用体验，并使 Agent Core 独立于具体的存储实现。

### 3.2 非目标

- 重放或回滚任意的外部副作用。
- 捕获或恢复工作区文件状态。回退移动的是对话本身，不会撤销对话已经造成的后果。
- 持久化凭证、审批授权、进程句柄或 Shell 会话。
- 把本地会话记录做成防篡改的审计证据。
- 实现 Server 端同步、Space 共享或远程授权。
- 在首个实现中让分叉出的会话共享物理历史前缀。
- 支持多个写入者同时写同一个会话。
- 保留或迁移 Alpha 阶段的整文件 JSON 格式。

## 4. 记录归属

| 数据 | 权威来源 | 原因 |
|---|---|---|
| 会话 ID、种类、创建时间 | `meta.json` 与历史文件头 | 目录和日志各自都能独立识别自身 |
| 标题、置顶状态 | `meta.json` | 展示层元数据不影响模型上下文 |
| 所选模型 | `meta.json` | 下一轮要使用的当前选择 |
| 下一轮使用的工作区根目录 | `meta.json` | 与所选模型一样，是一种当前选择 |
| 某一轮实际使用的模型与工作区根目录 | `turn_started` 历史记录 | 关于某一轮具体运行的事实 |
| 令牌总量 | `meta.json` | 本地聚合报告；单次调用的凭证保留在别处 |
| 消息与工具结果 | `history.jsonl` | 重建提供方历史所必需 |
| 工具是否跨越了执行边界 | `history.jsonl` | 安全地对中断产生的影响分类所必需 |
| 压缩摘要与边界 | `history.jsonl` | 会改变某个分支上模型可见的历史 |
| 笔记、待办事项、附加提示 | `history.jsonl` | 注入后续模型请求中的持久状态 |
| 当前历史头部 | `head_selected` 历史记录 | 在加载时推导得出，从不作为元数据存储，因此不会与其指向的分支产生分歧 |
| LLM/工具耗时、工作目录、沙箱、插件、拒绝诊断 | 每次运行的轨迹 | 有界的运维证据，而非恢复所需的输入 |
| 当前写入者 | 操作系统锁加 `writer.lock` 诊断信息 | 一种必须能够自动失效的进程事实 |

`meta.json` 与 `history.jsonl` 刻意不共用一次事务，两者也互不为对方的投影。它们各自拥有不同种类的权威性：

- `history.jsonl` 对重建对话所需的一切负责：消息、工具结果、压缩和持久状态。
- `meta.json` 对会话当前的各项选择与累计聚合值负责：标题、置顶、工作区、所选模型、令牌总量与累计成本。这些是设置项和计数器，不是日志的摘要——无论重放多少次都无法恢复它们，也不需要任何历史记录来记录它们。
- `index.json` 是本设计中唯一的纯投影，也是唯一声明可以通过扫描重建的文件。

这里存在两种权威来源之所以安全，是因为它们各自失败造成的影响并不对称：丢失一个当前选择只会降低展示效果、退回默认值，而丢失历史则会破坏恢复能力。过时的标题或索引行绝不能让对话的恢复结果出错。

这种拆分只有在没有任何字段同时跨越两者时才成立，因此 `meta.json` 中不保存任何由 `history.jsonl` 决定的内容。当前头部是一条 `head_selected` 记录，在加载时从日志中推导得出（§6.2）；它不会被镜像进元数据中。最后一个序列号同样不会被存储：这两个值在会话打开的那一刻就已经可以免费获得，因为打开操作本身就会重放整个日志，把它们缓存进元数据既换不来速度，还会多出一条一致性规则要维护。

不可变字段的重复则是另一回事，是被允许的：会话 ID、种类和创建时间会同时出现在 `meta.json` 与历史文件头中，这正是让两个文件都能独立识别自身的原因。创建时就已固定的值不会漂移，§6.1 也已经把二者不一致的情况定义为损坏，而不是把其中一方当作需要协调的过期副本。因此这条规则针对的是可变状态：两条记录可以重复同一个常量，但不能重复同一个变量。

## 5. `meta.json`

每个会话的元数据文件体积足够小，可以整体原子替换：

```json
{
  "version": 1,
  "id": "<uuid>",
  "kind": "user",
  "created_at": "2026-08-23T10:00:00Z",
  "updated_at": "2026-08-23T10:30:00Z",
  "title": "Design local session storage",
  "workspace": "/repo",
  "pinned": false,
  "selected_model": "anthropic/claude-opus",
  "prompt_tokens": 12000,
  "completion_tokens": 1800,
  "cache_read_tokens": 9000,
  "cache_write_tokens": 1200,
  "cost": {"currency": "USD", "total": 4200},
  "cost_incomplete": false
}
```

`kind` 取值为 `user` 或 `subagent`。子 Agent 会额外携带不可变的谱系元数据：

```json
{
  "kind": "subagent",
  "parent_session_id": "<uuid>",
  "parent_run_id": "<run id>",
  "parent_tool_call_id": "call_1",
  "agent_type": "explorer",
  "delegation_depth": 1,
  "hidden": true
}
```

分叉出的用户会话会额外携带：

```json
{
  "forked_from": {
    "session_id": "<parent uuid>",
    "head_id": "<history item id>"
  }
}
```

`cost` 完全就是 `llm.Cost`，包含其缓存与基础用量的明细拆分。`cost_incomplete` 表示某一轮使用了未定价的模型，或使用了本次构建无法换算的币种——把总额悄悄少算掉半个会话，要比明确标注“不完整”糟糕得多。缓存令牌计数是对 `prompt_tokens` 的拆分说明，而不是需要额外相加的部分；汇总一个会话的用量时不应把三者简单相加。

标题、置顶状态、工作区和所选模型的变更，会写入一个临时文件、执行同步，然后原子替换 `meta.json`。它们不会追加任何对话事件。

如果元数据损坏，会话仍会以保守的默认值恢复：无标题、不置顶、使用配置的默认模型、聚合值清零。此时上报的用量是错的，但这是可以接受的，因为它本来就只是一份报告。

这些默认值都不会导致恢复出错，因为本文件不包含任何模型可见的状态选择。真正会导致这种情况的是当前头部，而它并不在这个文件里：回退之后，最后一条物理记录可能属于用户已经放弃的分支，如果元数据里保留了一份头部副本、又没能及时更新，就会悄悄地恢复回那条被放弃的工作。§6.2 转而从日志中推导头部，从根本上消除了这种分歧，而不是为它规定一个“谁赢”的规则。

`workspace` 和 `selected_model` 一样是一种当前选择，而不是展示层元数据：它决定了下一轮工具在哪里运行，以及哪个工作区的 `AGENTS.md` 会被追加进系统提示。因此，丢失它只会让恢复后的会话退回到配置的默认根目录——这一点对用户可见且可以纠正，而不是悄无声息地发生。

如果历史被损坏，有效的元数据或许能让会话仍然可见，但无法让它恢复可续的能力。

`selected_model` 表示下一轮应当使用的模型；`turn_started.model` 记录的则是某一轮已完成或被中断的执行实际使用的模型。这个区分在保留来源信息的同时，避免了把每一次界面上的设置变更都变成一条对话历史。

## 6. `history.jsonl`

### 6.1 文件头

第一行是一条不可变的、自描述的文件头：

```json
{"type":"history","version":1,"session_id":"<uuid>","created_at":"2026-08-23T10:00:00Z"}
```

加载器会在解释任何记录之前，先拒绝不受支持的版本。如果文件头中的会话 ID 与目录名或 `meta.json` 不一致，这属于损坏，而不是一种可以接受的别名。

### 6.2 物理顺序与逻辑顺序

此后的每一行都同时具备物理序列号和逻辑历史身份：

```json
{
  "seq": 42,
  "id": "<history item id>",
  "parent_id": "<parent history item id>",
  "ts": "2026-08-23T10:01:02.123456Z",
  "type": "message",
  "turn_id": "<run id>",
  "data": {}
}
```

| 字段 | 契约 |
|---|---|
| `seq` | 从 1 开始的物理追加顺序；同时也是 §14 中 `Append` 所使用的乐观并发令牌 |
| `id` | 该历史条目的稳定标识 |
| `parent_id` | 该分支上的前一个逻辑条目；只有根条目才会省略 |
| `ts` | UTC RFC 3339 格式的诊断时间戳；从不作为排序依据 |
| `type` | 用于表达可恢复历史语义的封闭判别字段 |
| `required` | 无法识别 `type` 的读取方，是必须拒绝整个会话，还是可以跳过该记录；参见 §6.4 |
| `turn_id` | 与运行及其轨迹相关联的可选字段 |
| `data` | 带有明确 `snake_case` 字段的、类型专属的载荷 |

物理顺序在回退之后依旧保持仅追加。逻辑顺序则是终止于当前头部的父节点链：

```text
physical append: A B C D E F

logical history:
  A -> B -> C -> D
       \-> E -> F   (current head)
```

这样一来，被放弃的分支依旧保留可用，而不需要截断或重写日志。

头部是推导出来的，而不是与日志一起单独存储的，推导规则只有一条：**头部就是最后一条物理记录。**

回退不需要任何特殊处理，因为它是通过父节点链而不是与之并列的方式来表达的。除 `head_selected` 之外，每条记录的父节点都是它的物理前驱；而 `head_selected` 的父节点则是被回退到的那个条目。因此，追加一条 `head_selected` 记录就会重新定向这条父节点链，此后的所有记录都会沿着这个新目标继续生长。读取头部的代价只是查看最后一行，不存在第二个可能与之相悖的答案存放处。

### 6.3 记录类型词汇表

| 类型 | 载荷 | 恢复时的效果 |
|---|---|---|
| `turn_started` | 运行 ID、生效模型、工作区根目录、上下文窗口、输入种类 | 开启一轮执行，并确定其运行时身份 |
| `message` | 一条完整的 `llm.Message` | 追加一条用户或助手侧的提供方历史 |
| `tool_execution_started` | 工具调用 ID 与工具名称 | 标记一次已批准的调用已经跨越了副作用边界 |
| `tool_result` | 工具调用 ID、状态、完整文本、内容部分 | 投影为一条 `role: tool` 消息，并结束该次调用 |
| `compaction` | 覆盖的头部/范围、完整的累积摘要 | 替换该分支上模型可见的历史前缀 |
| `notes_replaced` | 完整的带时间戳笔记列表 | 替换持久化笔记 |
| `todos_replaced` | 完整的带时间戳待办列表 | 替换持久化待办事项 |
| `additional_prompt_set` | 完整的、经过校验的文本 | 替换持久化的附加系统提示 |
| `head_selected` | 原因；被回退到的条目即为其 `parent_id` | 将父节点链重新定向到更早的条目 |
| `turn_finished` | 终止状态——`completed`、`failed`、`canceled` 或 `interrupted`——以及可选的错误分类 | 结束这一轮 |
| `turn_recovered` | 被中断的这一轮及其状态不确定的工具调用 ID | 在开始新工作之前，明确地完成冷恢复 |

`message` 保留的是完整的、可移植的 `llm.Message`，而不仅仅是文本。因此，一条助手记录中会包含工具调用和不透明的提供方状态；一条用户记录会保留后台来源信息和内容部分。

`tool_result` 是作为其自身类型的历史条目单独存储的，而不是重复放进另一条通用消息里。归约器负责把它投影成提供方适配器所需要的 `role: tool` 消息。

标题、置顶、工作区、所选模型偏好、用量总计、插件、沙箱策略和耗时信息，都被有意排除在外，它们属于元数据或运行诊断，而不属于对话日志。

### 6.4 提供方中立性与向前兼容

这里有两个属性，其重要性超过它们在单一供应商的转录格式中所应有的份量，因为 BuildMax 面向许多提供方，并且预期会不断增加这份文档目前还无法预见的功能。

**对生产该记录的协议保持中立。** 历史存储的是可移植的 `llm.Message`，绝不是某个提供方的线上传输载荷。角色、工具调用、工具结果、内容部分和轮次生命周期，都是 BuildMax 自己的词汇表，因此在与某一个提供方对话时写下的日志，回放给另一个提供方时依然可以正常工作。

一条记录中唯一带有提供方特征的值是 `ProviderState`，它被标记上产生它的协议，正是为了让读取方能够判断它是否仍然适用。在不同协议下恢复——换了模型、切换了网关、重新指向了配置——都会丢弃标签与当前适配器不匹配的提供方状态，而不是把它继续转发下去。丢弃它意味着损失缓存的推理内容，这是一种降级；而转发它则意味着把一个供应商的不透明字节发送到另一个供应商的接口上，这是一个缺陷。因此，一个在对话过程中更换过模型的会话，其历史中会混杂着多种协议的消息，每一条都依据自己的标签来判断，而不是依据整个会话的统一假设。

**在不破坏旧读取方的前提下可扩展。** `type` 对于本文档定义的语义而言是一个封闭的判别字段，但格式本身仍然必须容许出现这个版本从未见过的记录——未来的新功能，或者由插件贡献的新类型。因此，每条记录都要声明：一个无法理解它的读取方是否可以跳过它。

- 只增加信息、不改变已有内容的记录是可跳过的。较旧的二进制程序会记录一条日志然后继续。
- 会改变模型所见内容的记录则是必需的。无法解释它的读取方必须拒绝整个会话，而不是继续恢复一段自己实际上已经错误归约的对话。

有一个具体的例子说明了为什么这个标志位是按记录、而不是按格式版本来决定的。今天，一次运行无法在不同目录之间移动：Bash 在工作区根目录下执行每一次调用，文件工具也会拒绝任何试图逃逸出这个根目录的路径，因此不需要任何记录来说明工具是在哪里运行的。但如果运行时以后获得了持久的 Shell 工作目录，那么对它的改变就是模型可见的，届时就应当作为一条必需记录出现——旧版本的二进制程序也能够正确地拒绝一个自己无法定位的会话，而不是把它错误地在错误的目录树上重放。

正是这一个标志位，让 §7.2 能够保持严格，同时又不至于把整个格式变成一个版本陷阱。未知且可跳过是一种警告；未知且必需则完全等同于损坏来处理，因为在这两种情况下，归约出来的历史都是错的。因此，扩展性最终归结为一个问题：一条新记录是否是模型可见的——而这正是本设计在 §6.3 中对每一种记录类型都已经回答过的问题。

## 7. 提交与恢复语义

### 7.1 轮次提交边界

```text
accept prompt
  append + sync turn_started
  append + sync user message

call model
  append + sync assistant message

for each approved tool call
  append + sync tool_execution_started
  execute external effect
  append + sync tool_result

before next model request
  verify the current history prefix is durable

finish turn
  append + sync state changes and turn_finished
  atomically refresh meta.json and index.json
```

任何会影响恢复的条目，在历史确认接受之前，绝不能被 Agent Core 看到。一旦持久化失败，这一轮就必须停止。会话持久化不能沿用运行轨迹那种“失败开放”的行为。

只有在不改变故障分类结果的边界之间，才允许批量处理。`tool_execution_started` 必须先到达稳定存储，工具才能够去改变外部世界；它的结果也必须先到达稳定存储，才能被下一次模型请求所消费。

这个保证的强度，恰好等于它底层同步操作的强度，而这个原语就是 `os.File.Sync`。Go 运行时已经把它映射到了每个平台上能提供的最强版本——macOS 上是 `F_FULLFSYNC`，它会一直等到设备真正写入完成，而不是在写入磁盘的缓存后就提前返回；Linux 和各种 BSD 上是 `fsync(2)`；Windows 上是 `FlushFileBuffers`。如果直接调用某个平台专属的原语，只是重新实现一遍这层映射，却不会带来任何改进。

进程崩溃和断电是两种不同的保证，本设计不会把它们混为一谈。§7.3 中的分类，在平台最强原语得到遵守的地方，对断电也是成立的；而在得不到遵守的地方，则会退化为仅对进程崩溃成立：当 `F_FULLFSYNC` 返回 `ENOTSUP` 时（某些网络文件系统和虚拟文件系统会如此），macOS 会回退到使用 `fsync`，而没有任何软件层面的原语能够在一个“谎报刷盘已完成”的设备上幸存。只有缓存层面的刷盘时，一条 `tool_execution_started` 记录可能会在工具已经执行之后才丢失，恢复流程就会把一个实际上已经改变了世界的操作错误地分类为 `not_started`。这两种退化都源自底层文件系统，而不是本协议本身，而且都不是无声发生的：回退行为本身在发生的地方是可以被观察到的。

目录项是一个单独的问题，而且有一个更廉价的答案。向一个已存在的日志追加内容不会改变它的目录项，因此这条热路径根本不需要任何目录同步。而创建一个会话目录则需要。至于原子替换 `meta.json`，则刻意不做目录同步：§4 已经确立了丢失一次元数据写入只会降级为丢失一个当前选择，而不会影响恢复能力，因此每一轮都为它多付一次目录同步的代价，买到的是错误的东西。

这个取舍既是延迟预算问题，也是正确性问题。这套协议每一轮至少同步五次，外加每次被批准的工具调用两次，所以一轮包含十个并行工具调用的执行，在交互路径上大约要经过二十五个同步点。这是用户每一轮都要付出的成本，如果将来需要做调优，这也是首先应该测量的对象——而打开一个会话的成本，则只需要支付一次。目前这两者都还没有被计量。

### 7.2 断尾与损坏

加载器会校验文件头、模式（schema）、ID 唯一性、父节点引用以及记录之间的关系。最后一行不完整属于断尾，可以在获取写入者角色的过程中被截断到最后一个换行符处。而在断尾之前出现无效的 JSON、无法识别的必需类型，或者无效的关系，则属于损坏，会连同路径和序列号一起使加载失败。

`seq` 出现跳号并不在上述损坏清单之内。由于只有一个写入者、且文件仅追加，只有文件末尾才可能被撕裂，因此出现跳号要么意味着 BuildMax 之外的某些东西截断或编辑了这份日志——§3.2 已经把防篡改排除在范围之外——要么意味着确实缺失了一条记录，而这种情况只要会改变归约结果，父节点链校验早就已经拒绝了它。局限在一条已放弃分支内的跳号，不会改变模型所看到的任何内容。为一个第一个信号已经报告过的故障再加一个第二重信号，换来的只是严格性而非安全性，因此 `seq` 仍然只是一种排序与并发控制手段，而不是一项损坏检查。

只读检查从不修复文件。以续写方式打开会话，则会修复断尾，并在接受新提示之前追加恢复状态。

拒绝续写并不等于没有出路。断尾之前出现的损坏记录，会使续写加载失败，但加载器同时也提供一种只读的抢救模式，它会把有效的前缀归约到第一条损坏记录为止，并将其导出为一个新的会话目录，原始的损坏文件则永远不会被原地重写。一个只能被报告为“已损坏”、却完全没有取回其中工作的路径的本地会话，要比“保守地拒绝，同时提供一条明确的恢复命令”糟糕得多。

### 7.3 未知的工具结果

一条助手工具调用只能证明模型请求了某项工作。一条 `tool_execution_started` 记录证明的是 BuildMax 已经批准了这次调用、即将进入工具执行。一条 `tool_result` 记录的则是实际观察到的结果。

| 持久化历史 | 恢复时的分类 |
|---|---|
| 只有助手调用 | `not_started` |
| 助手调用加上 `tool_execution_started` | `outcome_unknown` |
| 存在匹配的 `tool_result` | 已知的 `completed`、`failed`、`denied`，或恢复过程写入的 `unknown` 结果 |

`outcome_unknown` 永远不会被自动重试。恢复流程会要求模型先核实可能已经产生的效果，再重试任何非幂等的操作。

这种修复本身是一次历史写入，而不是归约时刻造出来的虚构结果。打开一个被中断的会话时，系统会追加一条 `turn_recovered` 记录，指明被中断的那一轮以及其中状态不确定的工具调用 ID，随后为其中每一个都追加一条状态为 `unknown` 的 `tool_result`。模型看到的这个合成结果本身也是持久化的，并且只会出现恰好一次：第二次打开这个被中断的会话，只会在分支上继续追加，而不会重放同一次修复；也没有任何读取方需要去分辨哪些工具结果是真实观察到的、哪些是重建出来的，因为记录本身已经说明了这一点。

日志记录的是 Agent 观察到的状态。它无法证明文件系统、某个 Shell 进程、某个 HTTP 端点，或者某个远程数据库，是否真的与这个状态相符。

### 7.4 取消与关闭

一轮执行以两种方式之一停止，区分这两者的轴线并不是“谁的本意如何”，而是“停止发生时，进程是否还活着，能不能开口说话”。

只要 BuildMax 还在运行，它就会自行结束这一轮：用户主动停止得到的是状态为 `canceled` 的 `turn_finished`；关闭动作在执行途中到达得到的则是 `interrupted`。这正是 [`graceful-shutdown.md`](优雅关闭.md) 在运行层面已经区分开的 `ErrRunCanceled` 与 `ErrRunInterrupted` 这两个原因，其背后的推理在这里同样成立、没有变化：一次进程提前知情的停止，可以让这次运行自己说明发生了什么，而不是悄无声息地消失，之后再被判定为被放弃。日志保留这一区别，原因和 Portal 保留这一区别是一样的——这是两种不同的事件，绝不能被当成一回事去读取。

一轮已结束的执行不同于一轮被中断的执行。下一次打开时看到的是 `turn_finished`，不会追加任何 `turn_recovered`，直接开始新的工作而不是修复。

结束一轮执行并不能解决其中工具调用的结果问题。一次跨越了 `tool_execution_started` 却尚未返回的调用，无论这一轮是被取消、被中断，还是随着进程一起丢失，都属于 `outcome_unknown`：BuildMax 只知道自己进入了这个工具，却不知道其效果是否已经产生，主动停止本身并不能让这一点变得可知。因此，正在运行的进程会趁着自己还持有这些调用 ID 的时候，写下与 §7.3 中恢复流程完全相同的内容——为每一个不确定的调用写下一条状态为 `unknown` 的 `tool_result`——而不是凭空捏造一种它并不掌握的确定性。

这两条路径最终汇合，而不是分岔。如果进程在自我取消的过程中，又遭遇了第二次中断或者一次 `SIGKILL` 而死掉，也不需要任何特殊处理：这一轮会被留在打开状态，下一次打开会像 §7.2 和 §7.3 所描述的那样正常恢复它。优雅关闭只是相对于恢复流程的一种优化，而不是它的替代方案。

## 8. 回退与分叉

### 8.1 为什么没有检查点

早期草稿中曾经有一条 `checkpoint` 记录，用来命名一个头部，以便日后可以回到那里。它已经被移除了，原因也被记录了下来，而不是留给别人去重新发现。

检查点是一种关于状态的承诺。在其他任何使用这个词的地方，它的含义都是“把一切恢复原状”——文件也包含在内。而这个设计无法兑现这个承诺：BuildMax 没有带版本的工作区能力，也没有相应的设计记录——此前的一份记录已经被撤回、而不是被实现，[`trust-harness.md`](信任保障.md) 对此有说明。

因此，一个仅限于对话层面的检查点，其名字所承诺的东西会超出它实际提供的能力，而这原本已经可以由回退来提供。更糟的是，这个名字会掩盖而不是暴露这个尖锐的问题：回退到某一轮编辑过文件、运行过 Bash 或调用过网络服务的时间点之前，那些效果全都原封不动地留在原地。模型的历史回到了更早的时间点，而现实世界却没有，于是模型接下来就会基于一幅已经不再真实的工作区图景进行推理。

这是一个真实存在的风险，理应由回退功能自己去承担、去呈现（§8.2），而不是被一个让人安心的措辞悄悄抹平。恢复一个 Agent 所做的改动，是一项值得拥有的能力，但那属于另一份设计记录；在这里预留一个槽位，只会把一项已经撤回的能力，描述成即将到来的功能。

### 8.2 回退

回退会取回用户自己发送过的某一条提示。被选中的这条消息，连同它之后的一切，会一起离开当前分支，而它的文本会回到输入框中，供用户编辑后再次发送——这正是这个操作存在的目的，也是它把这条消息本身排除在外、而不是包含进去的原因。

回退会追加一条 `head_selected` 记录，其父节点就是被回退消息之前的那条记录。这就是整个操作的全部内容。

落点是该分支上的物理前驱，而不是“上一条消息”：笔记、待办事项、一次压缩，以及前一轮的 `turn_finished`，都可能夹在两条消息之间，它们都属于需要保留下来的工作。唯一会被跳过的记录是 `turn_started`，因为 §7.1 会在开启一轮的那条提示之前先打开这一轮，如果落点选在这里，就会把分支留在被丢弃的那一轮内部。会话中的第一条提示，前面没有任何东西，因此不提供回退的落点；这种情况下，新建一个会话已经表达了同样的意思，无需再去发明一个空分支。

由此决定了每个界面可以提供什么样的选项。回退提供的是用户自己输入过的那些提示，因为一条回复没有什么可以“退还”给用户，而后台事件产生的消息又是用户从未亲手写过的。分叉则提供每一轮结束时所停在的那条消息，包括头部本身，但不包括那种以“请求调用工具”结尾的回复：停在那里的分支会带着一个没有结果的调用，而这种情况只有部分供应商适配器能够自行清理。目标位置不会重复出现在载荷里：这是唯一一种故意指向其物理前驱之外某处的记录，父节点链接本身已经说明了目标字段本应说明的一切，再存一遍只会制造出一对可能互相矛盾的数据。而且，因为头部是推导出来的，而不是被存储起来的，所以不存在需要同步维护的第二处写入，也就不存在崩溃可能让这个选择停留在“只完成一半”的状态的窗口。旧的分支尾部仍然留在 `history.jsonl` 中，回退之后追加的新提示，会把选定的头部作为自己的父节点，从而创建出一条新的逻辑分支，而不需要任何截断操作。

回退只移动对话，除此之外什么都不做。它不会恢复工作区（§8.1），也不会改变工作区根目录：根目录是 `meta.json` 中的一个当前选择，因此回退到某一轮在别处运行的执行，会把下一轮留在用户最后设置的位置上。被回退到的那一轮的 `turn_started` 记录仍然会说明它当时使用的根目录，这使得这种差异变得可以核查，而不是悄无声息。

压缩是限定在分支范围内的。一份摘要会准确记录它所覆盖的历史头部或范围。在分叉点之后生成的摘要，不能被一个并不包含被摘要记录的子会话复用。原始历史会一直保留，直到所有的回退与分叉保留规则都允许对其进行物理压缩为止。

### 8.3 分叉

分叉会把历史前缀——一直到选定的那条消息为止——物理复制到一个新的会话目录中。它会保留条目 ID，为子会话分配独立的会话 ID 和元数据记录，并把分叉的来源信息写入 `meta.json`。

被复制的是经过那条消息的*分支*，而不是物理前缀本身：一个曾经被回退过的父会话，同时也保留着被放弃的记录，如果子会话把这些记录也一并带走，就会携带父会话自己的父节点链根本不会经过的历史。序列号不会被保留——`seq` 只是一条记录在承载它的日志中的位置，因此子会话会从 1 重新编号，父会话中留下的任何跳号，也不会在子会话中留下痕迹。条目 ID 则会被保留，因为正是这种身份标识，才能让子会话中的记录被识别为与父会话所做的是同一份工作。

子会话的用量和成本总计会从零开始。如果继承父会话的总计，一旦有人把两个会话的用量加在一起，就会造成同一笔钱被重复计算。标题和工作区则会被继承下来，因为它们描述的是被延续下去的这段对话本身，而不是产生这段对话的那次运行。模型则不会被继承：与任何新会话一样，子会话选用发起分叉的界面的默认模型。继承工作区意味着分叉与父会话共享同一个工作目录；分叉时不做任何隔离，需要独立工作树的分叉通过 `Worktree` 工具进入一个（见[工作区根与工作树](工作区根与工作树.md)）。

物理复制的复杂度是 O(n)，但它为 Alpha 阶段的实现换来了清晰的所有权划分：

- 删除父会话不会破坏子会话；
- 加载子会话时永远不需要遍历另一个会话；
- 授权与保留策略都保持在会话内部；并且
- 不需要任何带引用计数的历史图。

分叉只复制日志前缀，除此之外不复制任何东西，因为历史本身已经把一个会话的全部内容内联保存了下来（§11）。这里不存在一个供子会话共享的独立内容存储，因此也就不存在需要正确处理的引用计数。

共享前缀、写时复制的分段，以及基于数据库的历史图，目前都不在计划之内。它们各自都能换来一份更小的副本，但代价是引入删除、保留和垃圾回收规则——而这些恰恰是物理复制完全不需要的东西。

轨迹不会被复制进子会话的续写上下文里。分叉元数据只记录它来自哪个会话、哪个头部；子会话的新运行会创建自己新的轨迹文件。

## 9. 子 Agent 会话

每一个前台、后台或嵌套的子 Agent，都拥有相同结构的目录，以及各自独立的历史写入者。它绝不会写入父会话的日志或状态存储。

子 Agent 会话的 `kind` 为 `subagent`，在普通的会话选择器中隐藏，也不会被 `--continue` 选中。它们的文件头和元数据会记录直接的父会话、父运行、父工具调用、Agent 类型和委派深度。面向模型的返回路径仍然是父级的 Task 结果。

私有日志消除了现有的这种行为：子 Agent 返回时，其整个 `session.Session` 会被直接丢弃。但它并不会把当前这种一次性的子 Agent，变成一个用户可见的分叉。父会话崩溃不会自动重启 Task 工具：父会话的历史负责对这次调用进行分类，而子会话自己的日志则说明子会话本身是否走到了一轮的终态。

一个已经封存的子会话，会依据选定的保留策略与其父会话一起保留下来。需要独立工作树的子 Agent 通过 `Task` 工具的 `worktree` 选项获得一个（工作区根与工作树，D7）。持久化的 fork 监督、持久邮箱以及自动的父会话续写均不在计划之中；[本地后台任务](本地后台任务.md#持久化不在计划之内)记录了原因。

## 10. 轨迹

现有的运行轨迹契约保持不变，唯一的变化是物理位置上的迁移：

```text
<session_id>/traces/<run_id>.jsonl
```

每次运行一个文件，保留了独立的容量上限、终止性质的 `run_end` 记录、保留策略、上传能力，以及父子运行之间的轨迹关联。整个会话共用一个 `trace.jsonl` 的方案被否决了，因为并发的子运行或后台运行、按运行清理，以及损坏处理，都会共同争抢同一个无边界的追加目标。

工具在哪里运行，这个问题也属于这里的范畴。一次运行无法在目录之间移动（§6.4），但单条 Bash 命令仍然可以在自己的调用内部执行 `cd`，或者引用一个绝对路径，因此某次调用实际触及的目录，是一种运维证据，而不是恢复所需要的输入。如果把它记录在每一次调用的历史里，就会在每条记录上都打上可变的、逐次调用的上下文，而这正是 §16.6 所反对的做法；轨迹是有边界的，也早已是存放这类信息的合适位置。

轨迹保持有界、脱敏且失败开放。历史则为了恢复而保持无损，并在提交边界处失败关闭。轨迹可以为了关联而摘录某条历史条目的 ID，但恢复流程从不会把轨迹内容当作状态来读取。

## 11. 会话内容与隐私

历史以内联方式存储内容：普通文本、结构化的工具结果，以及非文本部分，一视同仁。这里没有独立的内容存储，没有大小阈值，加载时也不需要解析任何引用——一个会话的对话内容，就在拥有它的这一份文件里。这里不对内容的大小设任何上限；§13 会说明这样做的代价，以及目前对此尚未采取的措施。

会话内容不会被脱敏，因为脱敏会改变续写时模型所看到的内容。会话目录使用私有权限（在支持的平台上，目录为 `0700`，文件为 `0600`）。凭证和审批授权永远不会作为会话状态进入元数据、历史或轨迹。

## 12. 索引、锁与生命周期

`sessions/index.json` 是选择器所使用的投影。它只包含用户可见的会话，记录 ID、标题、工作区、置顶状态、种类、更新时间，以及足以对分叉进行分组的谱系信息。它通过临时文件同步加原子重命名的方式写入，并在过期或损坏时通过扫描各个 `meta.json` 文件来重建。

列表展示只读取 `index.json`，不会去扫描目录。这层投影的存在，是为了让打开选择器只需要读取一个小文件，而不必为每个会话都读一次 `meta.json`；而如果一个过期的投影会悄悄地退回去遍历目录，这种节省也就没有意义了。因此，重建是一次显式的修复动作——只有在索引缺失、无法解析，或未能通过自身一致性检查时才会触发，它也是唯一会遍历会话目录的路径。

会话日志只有一个写入者。现有的进程内轮次守卫机制被保留，文件后端在此之上又加了一把跨进程锁。`writer.lock` 中可能包含 PID、进程启动时间或所有者诊断信息，但这些值都不具备权威性：真正决定归属权的是操作系统锁，而一个被遗弃的文件不能让某个会话永远处于“占用中”的状态。

这把跨进程锁是加在 `writer.lock` 文件上的操作系统建议锁：macOS 和 Linux 上是 `flock(2)`，Windows 上是带有 `LOCKFILE_EXCLUSIVE_LOCK | LOCKFILE_FAIL_IMMEDIATELY` 标志的 `LockFileEx`，两者都通过 `golang.org/x/sys` 调用，而这已经是一个现有依赖。

更“可移植”的替代方案在上述要求上会落败。一个 `O_CREAT|O_EXCL` 锁文件完全不需要任何平台相关代码，但它也无法自我清理：它的存活时间会超过创建它的那个进程，因此从崩溃中恢复就意味着要去判断记录下来的那个 PID 是否还存活——而这正是本设计拒绝当作权威来对待的、过时的进程状态。相比之下，内核锁会在持有它的进程退出时被释放，无论这个进程是以什么方式退出的，这才是“一个被遗弃的文件不能让会话永远处于占用状态”这句话唯一不需要任何启发式判断就能成立的版本。

之所以把锁加在 `writer.lock` 上、而不是 `history.jsonl` 本身上，是因为在写入者持有会话期间，读取方仍然必须能够查看一段稳定的前缀。如果直接锁住日志文件本身，要么会把这些读取方一并阻塞，要么——如果用 POSIX 记录锁——就会暴露出“关闭该文件的任意一个描述符，就会释放该进程持有的所有锁”这条规则。用一个独立的文件就不存在这两个问题，这也是为什么在 Unix 上更偏好使用 `flock` 而不是 `fcntl` 的同一个原因。

建议锁并非在所有环境下都可用：一些网络文件系统会直接拒绝加锁，另一些则会假装接受、实际上什么也不做。加锁失败会被明确报告，而不是被默认当作成功；一个无法加锁的文件系统，BuildMax 会如实说明这一点，而不是假装某个会话正被独占持有。

只读检查可以在写入者活跃期间读取一段稳定的前缀。而第二个进程在拿到写入者锁之前，无法续写、回退、从一个不稳定的头部分叉，或者追加内容。

删除一个会话会直接删除它整个目录。之所以可以这样做，是因为分叉是一次物理复制（§8.3）：没有任何其他会话的内容存活在这个目录里，也没有任何外部引用指向它内部。正因为这是一个具有实质性破坏力的操作，调用方必须指明确切的会话，而不能按前缀做匹配删除。

## 13. 日志增长

没有任何机制限制日志的大小。它会随着对话的进行而增长，随着每一个内联的工具结果而增长，并且永远不会被重写。

一个回退频繁的会话，增长速度会比它看起来的对话长度快得多，打开速度也会因此变慢——而这一点很容易被误解：重放需要解析整个文件才能找到那条存活分支，因此打开的成本取决于磁盘上的总字节数——包括那些已被放弃的分支——而不是模型实际看到的对话长度。两个展示出相同对话内容的会话，打开速度可能天差地别。

真正能限制这一点的是物理剪裁，但它目前尚未落地。在还有分支或分叉导出依赖某段前缀时，这段前缀就不能被移除，而在这条可达性规则及其对应的恢复行为被明确定义和测试之前，任何剪裁功能都不应该发布。这两者目前都还没有完成，今天也完全没有收集任何增长方面的度量数据，因此本节描述的是一项已知的成本，而不是一项已经被管理起来的成本。

## 14. 所有权与接口

```text
internal/core/session
  history item types, validation, linked-history reducer, recovery analysis

internal/agentapp
  SessionManager, commit orchestration, metadata/index policy, lifecycle

internal/infra/sessionstore
  JSONL codec, atomic metadata files, locking, append/sync, tail repair
```

`internal/core/agent` 继续依赖历史与持久状态相关的接口，但它不会导入任何文件、JSONL、数据库或 Server 客户端。这层持久化接口表达的是会话语义，而不是路径，它就定义在 `internal/core/session` 自身当中——完全用核心类型来表达，因此不依赖 infra，这也正是为什么 `internal/infra/sessionstore` 依赖它，而不是反过来：

```go
type Store interface {
    Create(ctx context.Context, meta Meta) error
    Open(ctx context.Context, id string) (Writer, error)
    Load(ctx context.Context, id string, mode LoadMode) (Loaded, error)
    UpdateMeta(ctx context.Context, id string, update MetaUpdate) error
    List(ctx context.Context, includeHidden bool) ([]ItemSummary, error)
}

type Writer interface {
    Loaded() Loaded
    Append(ctx context.Context, items ...Item) error
    Close() error
}
```

`Append` 并不是一个由调用方传入 `expectedSeq` 来标识状态的、扁平的无状态调用。构建这层接口的过程揭示了原因：写入者锁才是排除第二个写入者的机制，它保护的是整整一轮，而不是单次调用。如果做成单独一个 `Append(ctx, id, expectedSeq, items...)`，就必须在两者之间做选择——要么让这把锁在调用方发起的每一次调用之间一直保持持有，但函数签名本身并没有表达出这一点；要么就逐次调用重新获取锁，而这又会让第二个进程的某一轮执行插入到第一个进程的执行中间。`Open` 会获取这把锁，并返回一个 `Writer`，它会在整整一轮提交期间一直持有这把锁；`Writer.Close` 则负责释放它。一旦锁在这整段期间内都被持有，`expectedSeq` 也就不再必要了：在这期间不会有任何其他东西能够在调用方不知情的情况下移动日志尾部，因此 `Append` 只需要检查每个条目的 `Seq` 和 `ParentID`，是否恰好紧接着这个 `Writer` 自己所看到的分支末端。如果对不上，那就是需要上报的调用方缺陷，而不是需要重试的竞态问题。

`Open` 同时也是恢复机制真正发生的地方。它会修复一条断尾（§7.2），并且只有在它找到的这条分支上，确实还留有被中断动作所遗留的、状态不确定的调用时，才会在返回之前追加 §7.3 所描述的那些修复记录。触发条件是“是否存在需要处理的不确定调用”，而不是“这一轮是否被留在了打开状态”：一个已经被更早一次 `Open` 修复过的会话，在之后的某次打开时，仍然会显示出这一轮尚未结束——不会有任何 `turn_finished` 被追溯地补上——但由于已经没有任何不确定的内容，所以也不会有任何东西被重复写入。`Writer.Loaded().Recovery` 会向调用方报告刚刚修复了什么，即便这条分支自身其实早已修复完毕，调用方仍然可以据此告知用户。

`Load` 从不获取这把锁，也从不执行任何修复——写入者此时可能正处于打开状态，而检查操作只应该看到一段稳定的前缀（§7.2）。它仍然会计算出 `Recovery` 的结果，因此一个只想展示会话状态的调用方，也能够在什么都不写入的情况下，得知这个会话是否被留在了轮次执行的中途。

具体的命名今后可能还会变化，但边界不会：核心负责定义语义并执行确定性的归约；AgentApp 负责决定状态何时提交；infra 负责物理层面的持久性。

各种变更类 API 必须防止调用方在不追加历史的情况下，修改那些可恢复的、对外导出的字段。物化出来的 `Session` 或许仍然可以作为一个只读模型存在，但对消息、压缩、笔记、待办事项和附加提示的修改，都必须经过那个负责提交的会话上下文。

## 15. Alpha 切换

现有的 `<session_id>.json`、`sessions.json`，以及此前独立的轨迹存放结构，都不会被迁移。新的运行时不会读取、导入这种旧格式，也不会对其进行双写。

CLI、TUI、Desktop、评估、Worker 续写、跨运行的全局上传、Task 对话投影、重命名、置顶、删除、文档和测试，会一起完成切换。不会有任何生产路径继续把整文件的会话 JSON 当作当前的存储方式来对待。

旧文件可以保持原样、静置不动，直到被显式删除为止。它们的存在，既不会让它们出现在新的索引里，也不会在新的存储中占据一个身份。

## 16. 备选方案

### 16.1 原子式整文件 JSON

作为防范部分写入的权宜之计是有用的。但它仍然会重写完整的历史，并且会丢失执行中的工具状态、稳定的条目标识，以及低成本的分叉点。

### 16.2 单一混合的 JSONL 文件

单一的追加流会把元数据、历史、运行时状态和诊断信息统一放进一个总顺序里，使一个会话很容易被整体复制。但它也会把无损的续写数据，和脱敏、失败开放的轨迹耦合在一起，反复重写可变的元数据，妨碍各部分独立设定保留策略，并让一份没有上限的模式（schema）和文件不断膨胀下去。

这种方案适合那种把“单文件的可移植性”看得比“策略上的分离”更重要的单写入者转录类产品。而 BuildMax 已经拥有各自独立的会话、轨迹、Artifact、Worker 和 Portal 契约，因此目录捆绑才是更合适的边界。

### 16.3 扁平的、只有消息的 JSONL

这种方案消除了整份历史的重写，也支持续写。但由于没有稳定的条目 ID、父节点链接、工具执行边界、压缩和持久化记忆，它无法安全地实现中断恢复、回退或分叉。

### 16.4 所有本地会话都使用 SQLite

SQLite 提供事务、索引和并发读取能力。但在还没有查询性能或并发方面的证据要求之前，它会先给单二进制的本地路径添加一个数据库模式和一套迁移运行时。它也会是一项全新的依赖，而不是对现有依赖的复用：`internal/infra/db` 是 Server 端的存储，通过 GORM 使用 MySQL，因此今天没有任何本地路径链接 SQLite 驱动。

链式历史这个领域契约本身保持与后端无关，因此 SQLite 未来仍然可以被评估、被采用。

### 16.5 第一阶段就共享分叉前缀

引用共享可以降低复制成本，但会让子会话加载、父会话删除、授权和保留策略，以及垃圾回收都相互纠缠在一起。物理前缀复制对于 Alpha 阶段而言，是刻意选择的更简单方案。

### 16.6 与现有 JSONL 类 Agent 在字段层面兼容

让字段去匹配某个其他编码类 Agent 的记录字段——以便一份 BuildMax 日志可以在它们的工具里打开，或者它们的会话可以在这里重放——这个方案被否决了，因为它给这个项目指错了方向。BuildMax 是一个开放的、面向多个提供方的运行时，它的存储格式应当对是哪个模型或协议产生了某一轮对话保持中立，并且始终保有为任何供应商格式都未曾预见的功能扩展记录类型的自由。采用某一个供应商的模式（schema）会把这两者都牺牲掉：它会把一个开放的运行时和一个自己无法掌控的格式捆绑在一起，继承那个格式自身的演变变化，并把未来每一次扩展都变成对别人产品的兼容性问题。§6.4 所要保护的正是这一属性。

范围界定同样支持这个结论。只有当文件真的需要跨越边界时，兼容性才值得付出这种约束的代价，而导入外部转录格式，目前完全不在路线图之内。

其中一些结构层面的经验教训确实被吸收了，§1 也说明了这一点：带父节点链接的记录取代了扁平数组，每个已完成的条目都对应一条持久化记录，以及一个自描述的第一行。这些是任何一份格式良好的日志都应具备的属性，而不属于任何人的产品。而其中两种常见做法则被有意舍弃了。一种是单一的混合流，已在 §16.2 中被否决。另一种是把可变的、逐会话的上下文——工作目录、分支、构建版本——盖章到每一条记录上，这会让日志膨胀，并制造出和记录条数一样多种可能互相矛盾的答案；§4 把这些留在了 `meta.json` 里，§6.2 也把记录头部保持在最小限度。

§7.3 中的这条执行边界，在本设计所借鉴的那些格式里没有任何对应物。一条证明 BuildMax 即将进入某个工具的记录，和一条证明该工具已经返回的记录被区分开来，正是这一点让 `outcome_unknown` 能够被完整表达出来。这个差异，就是本设计不是一次移植的原因所在。

## 17. 验证

在测试验证以下各项之前，实现都不能算完成：

- 重放能够精确地重建消息、提供方状态、内容部分、压缩、笔记、待办事项、附加提示和工具结果；
- 逻辑父节点校验会拒绝重复 ID、循环引用、缺失父节点和不受支持的版本，并且一份在某条被放弃的分支上出现 `seq` 跳号的日志依然可以正常加载；
- 断尾会保留此前每一条已提交的记录，而断尾之前出现的损坏则会使加载失败；
- 在每个工具边界前后发生的故障，都会分别得到 `not_started`、已知结果或 `outcome_unknown` 这几种规定好的分类结果；
- 并行的工具完成会保留已提交历史的顺序和调用 ID；
- 回退会选中一个更早的头部，而不删除被放弃的分支，并把被移除的那条提示归还给用户；
- 回退会报告它所越过的那段范围内发生过的工具调用，包括一次被中断动作留在执行中的调用，而对于一段只有对话、没有工具调用的范围，则不报告任何内容；
- 回退是重新归约、而不是撤销：写在被放弃分支上的持久状态，在恢复后的会话中会消失，而回退之后追加的新一轮会延续被选中的分支；
- 一次回退在重新打开会话后依然有效——续写的会话就是被选中的那条分支，而不是文件中物理上最后的那条；
- 只有 `head_selected` 才可以指向当前头部之外的父节点，并且在同一个会话中只能有一条这样的记录被采纳；
- 分叉精确地只复制选定的那条分支前缀，并且在父会话被删除后依然存活；
- 对一个已经被回退过的会话进行分叉，复制的是当前存活的分支，而不是被放弃的那条；
- 分叉出来的日志能够被普通的读取流程正常加载，序列号从 1 重新编号，条目 ID 保持不变；
- 父会话和子会话彼此独立：写入其中一个不会改变另一个，子会话会作为独立的会话被列出，并携带自己的谱系信息；
- 压缩摘要绝不会跨越到一段它并未摘要过的分支上；
- 在不同协议下续写时，会丢弃标签与当前适配器不匹配的提供方状态，而不是继续转发它，并且一份混杂了多种协议消息的历史依然可以正常重放；
- 一条未知但可跳过的记录会带着警告被加载，而一条未知且必需的记录则会像损坏一样直接导致加载失败；
- 回退某一条提示，会精确复现它之前那条记录归约出来的状态，并且不会触碰任何工作区文件；
- 前台、后台和嵌套子 Agent 各自写入相互隔离、彼此隐藏的会话包，并带有直接父级的谱系信息；
- 隐藏的子 Agent 会话绝不会出现在选择器中，也绝不会成为 `--continue` 的目标；
- 第二个写入者无法修改一个正在使用中的会话，并且在持有锁的进程终止后——包括被 `SIGKILL` 杀死的情况——这把锁无需任何人工干预即可自动清除；
- 一轮以 `canceled` 或 `interrupted` 状态结束的执行，不会在下一次打开时被当作需要恢复的对象，而这次停止所留下的、执行中的工具调用，仍然会被正确地归为 `unknown`，而不是被伪造出一个结果；
- 一个在自我取消过程中被杀死的进程，会把这一轮留在打开状态，下一次打开会通过正常路径将其恢复；
- 过期的元数据和全局索引能够自我修复，而不会改动历史；
- 一份损坏的 `meta.json` 会以一个可见的、聚合值清零的会话形式恢复，而不是把它隐藏起来；而一个元数据无法读取的会话，在索引重建时会被跳过，而不是被凭空猜测；
- 打开一个被中断的会话会追加一次修复记录，再次打开同一个会话时不会再追加任何内容，同时依然会报告刚才修复了什么；
- 一次不能延续该 Writer 所打开分支的追加操作，会在任何内容写入文件之前就被拒绝；
- 一次回退之后即使丢失了元数据，续写的仍然是被选中的那条分支，而不是被放弃的物理尾部，也不需要修复任何元数据字段；
- 在没有回退、有一次回退，以及经过多次不同深度回退的各种日志上，头部推导的结果都与完整遍历分支得到的结果一致；
- 一个在不同轮次使用过不同工作区根目录的会话，会记录每一轮实际使用的根目录，重放时也不会用当前的根目录去改写更早轮次的记录；
- 抢救导出能够恢复一份损坏日志中有效的前缀，且不会修改原始文件；
- 反复打开一个被中断的会话，每次中断都只追加一条恢复记录，绝不会重复生成同一个合成的 `unknown` 工具结果；
- 旧的 Alpha 文件会被忽略，也没有任何代码路径会对它们进行双写；并且
- 所有测试都使用 `./make test` 提供的、隔离出来的 `BUILDMAX_HOME`。

属性测试会生成各种链式历史，并从每一个可达的头部出发，比较增量归约与完整重放的结果是否一致。崩溃测试使用真实的临时文件，并在文件同步、元数据重命名、工具执行和分叉复制等各个环节人为注入故障。

## 18. 交付阶段

### 阶段 0：权宜性的原子替换——已完成

- 如果最终实现无法立即落地，就先用临时写入、同步加原子重命名的方式，替换掉对整个会话文件和索引的直接覆盖写入。

已经落地。`util.WriteFileAtomic` 会在目标所在目录下写入一个临时文件、执行同步，再将其重命名覆盖到目标位置；会话文件、会话索引，以及 Worker 对前一次运行会话的续写，都在使用它。它只同步文件本身，不同步目录项，因此一次写入是要么全有要么全无，但还谈不上真正的持久——§7.1 现在已经明确说明了第一阶段使用的这个原语，以及它能保证什么、不能保证什么。

### 阶段 1：会话包与链式历史——已完成

- 添加元数据模式、历史文件头/条目、归约器、JSONL 后端、写入者锁和断尾修复。
- 把消息、工具、压缩、持久状态和附加提示的变更，都改为经过负责提交的上下文。
- 把轨迹移动到会话包内部，每次运行一个文件。
- 为子 Agent 提供各自隔离、隐藏的会话包。
- 把 CLI、TUI、Desktop、评估、Worker 各条路径，连同文档和测试，一并切换到新格式。

已经落地，并且是分三个阶段依次完成的：先是核心的条目类型和归约器，然后是 `sessionstore` 的编解码与加锁，最后才是各个使用界面的切换。只有第三步触及了面向用户的行为，而且它在 CLI、TUI、Desktop、评估和 Worker 各条路径上是原子地一起完成的，因为 §15 已经排除了双写这条路；但这项约束本身，并不要求下面这两层实现也必须在同一次评审中一起完成。

有两处本文档原先的描述，实现时发现比它们本应有的样子要更复杂，因此对照实现做了修正，而不是绕着它们打补丁：一旦 `head_selected` 直接链接到它的目标，头部推导就简化成了“最后一条物理记录”这一条规则（§6.2）；`Append` 也变成了 `Writer` 上的一个方法，在整整一轮期间持有锁，而不是携带 `expectedSeq` 的一次扁平调用（§14）。

有一件事是本文档没有预见到的：`AddCompaction`、`SetNotes` 和 `SetTodos` 原本都不返回错误，导致一次持久化历史根本没有办法报告一次失败的提交。现在这三者都会返回错误，因为 §7.1 要求这一轮必须停止，而不是继续在下一轮根本找不到的状态上运行下去。

### 阶段 2：回退与物理复制式分叉——已完成

- 加入对话回退功能：包括这项操作本身，以及提供它的各个界面，还包括它明确声明*没有*撤销的那些内容（§8.2）。已经落地，TUI 中对应 `/rewind`，Desktop 中对应历史选择器。
- 加入独立的子会话分叉功能。已经落地，TUI 中对应 `/fork`，使用的是与 Desktop 相同的选择器，二者都会提供这两种操作。每个界面在两种操作之间共享同一份列表，只是对同一个选择给出的说明各不相同。

头部选择和分支感知的重放没有被单独列出来：它们在阶段 1 就已经作为回退赖以构建的机制落地了，并且已经被那个阶段的属性测试覆盖到。

这是最后一个阶段。曾经被设想为第四阶段的内容——外部化的内容存储、共享的历史分段、基于数据库的存储——目前没有计划，本文档也不会把它们当作已经排定的内容来描述。它们每一项都只是一种缺乏度量数据支撑的优化；而 §13 也如实说明了目前完全没有收集任何度量数据。一份还挂着未排期工作的设计记录，读起来会像一项承诺；如果将来存储压力真的显现出来，届时可以拿着证据重新讨论是否要改变现状。

## 19. 开放问题

这里的任何一项都不会阻塞某个阶段的交付，因为每个阶段都已经交付完成。以下是实现过程中不需要回答、但如果要做得更多就必须回答的问题。

### 19.1 尚未解决

- 哪些工具可以把一次被中断的调用声明为可以安全自动重试，这种幂等性又该如何界定？在这个问题得到解答之前，一次被中断的调用只会被报告给用户（§8.2），永远不会代替用户自动重试。
- 隐藏的子 Agent 会话包，在父会话收到其结果之后应该保留多久？目前是无限期保留。
- 在存在分支和分叉导出的情况下，什么样的可达性规则才能判断某段日志前缀可以安全剪裁？在这个规则出现之前，§13 就没有对日志大小设任何上限——这是一项代价，而不是一个缺陷，也正是目前没有任何剪裁功能发布的原因。

### 19.2 已解决

**界面应该如何告诉用户，一次回退没有撤销哪些内容？** 做法是：在展示回退选择点的同时，列出即将被丢弃的这段范围内运行过的工具，让后果在做出选择之前就可见，事后也会再重复一遍。两个界面都是这样做的，并且分叉功能也复用了同一套计算逻辑，只是措辞相反：原会话什么都不会丢失，但复制出来的这一份不会知道那些操作曾经发生过。如果一个界面在提供这两个操作时没有做到这一点，那就是在回避 §8.1 要求它必须承担的风险。

哪一种已完成的内容单元会被写入历史——是某个提供方的响应条目、一个可移植的 `llm.Message`，还是二者都通过同一个适配器边界——这个问题已经由现有的类型给出了答案。`llm.Message` 携带一个 `ProviderState`，这是一个 `{protocol, data}` 组合，原样保存着产生它的那个协议所需要的、不透明的推理状态，此外还有用于非文本内容的 `Parts`，以及用于后台来源信息的 `Source`。它可以无损地支持续写，而不需要任何第二套存储表示。

那些会持久化原始提供方条目的日志格式之所以这样做，是因为它们的可移植消息类型本身无法承载不透明的协议状态。而这里的情况并非如此，存储线上传输载荷也会把日志与某一个供应商的格式捆绑在一起——这正是 §6.4 想要保护的中立性。历史存储的是可移植消息，§6.3 也就不需要另外一套平行的词汇表。
