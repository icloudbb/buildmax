## 用户结果与当前约束

企业应能让团队持续使用 Agent，同时控制身份、权限、数据、执行和成本，并通过
责任明确的运维流程从故障中恢复。

本备忘录记录企业能力与付费功能的讨论。具体关注点是 BuildMax 是否应将企业能力
作为商业产品提供。这次讨论尚未提供客户访谈、采购要求或付费意愿证据。以下能力
清单用于需求调研，不代表需求已获验证，也不是发布检查清单。

BuildMax 仍处于 Alpha。路线图的目标是面向私有网络中一个受信任 Space 的可靠
私有部署 Beta；SSO 不属于该门槛。现有 Space 边界与共享 Agent 运行时仍是约束。
企业产品必须保留独立本地使用能力，也不能引入另一套执行或授权归属。

## 目标与非目标

目标是为客户调研提供具体的能力基本盘，保留实用的社区产品，并找到能够围绕真实
客户流程交付和验证的小规模企业方案。

非目标包括批准企业版、修改价格或许可证、调整路线图、创建实施待办或承诺生产
就绪。本备忘录不授权新增组织层级、自定义策略语言、许可证服务器或独立运行时。
每个新增概念都必须对应现有概念无法满足的具体要求。

## 企业能力基本盘

以下是针对目标企业部署需要评估的结果，控制深度取决于用户和威胁模型。表中描述
期望能力，不是已交付功能清单。

| 类别 | 常见能力 | 验收问题 |
|---|---|---|
| 身份与人员管理 | 企业 SSO、停用账户、撤销 Session、有文档的入离职流程，必要时自动化 | 员工能否通过企业身份系统加入，并在离职后及时失去访问权？ |
| 授权与隔离 | Space 或团队角色、资源隔离，自动化需要时提供服务账号及可限定范围、可撤销的 API 凭证 | 用户或 Agent 是否只能访问工作授权允许的资源与凭证？ |
| 审计与追责 | 登录、权限变更、配置修改、凭证使用元数据和执行记录；授权查询与导出，必要时外部采集 | 运维能否还原谁授权、谁执行，并识别证据缺失？ |
| 数据与密钥 | 保留与删除规则、脱敏、传输和凭证存储加密、轮换，明确存储位置和模型提供方去向 | 能否说明数据流向、按策略删除数据并替换失陷凭证？ |
| Agent 执行治理 | 模型、工具、插件准入；强制执行边界；按需限制网络目的地；必要时审批高风险操作；取消和紧急暂停 | 能否约束执行并停止后续工作，同时明确控制的限制？ |
| 用量与成本 | 按客户需要的维度归属用量；预算与配额、告警、并发和速率限制 | 能否归属费用、限制无人值守消耗，并解释拒绝或超额行为？ |
| 运维与交付 | 监控告警、备份恢复、升级回滚、故障诊断、受支持的部署流程与支持责任 | 运维能否发现故障、恢复数据与执行状态，并维护部署？ |

执行 trace 本身不等于权限审计，配额计数器不等于严格的金额预算，多个副本的部署
清单也不等于高可用验收。每项承诺都需要覆盖完整行为的证据。审计记录不得暴露
密钥值。

## Agent 生命周期要求

企业需求调研与后续验收测试应覆盖状态变化，而不仅是管理界面：

- 员工被停用时，明确现有 Session、API 凭证、排队和运行中的 TaskRun、定时任务
  如何处理。区分阻止新工作与取消正在执行的工作。
- 成员失去 Space 访问权时，明确待执行和运行中工作的授权方式，以及结果是否仍
  可访问。继续 Task 不能悄然继承调用者已失去的权限。
- 需要审批时，将审批绑定到预期操作及相关参数，并定义变更、过期、重试和失败时
  的失效规则。聊天中的一句“同意”不足以构成完整授权机制。
- 模型、插件、工具或密钥被撤销时，明确生效时点。遵守按运行解析和插件版本固定
  的约束，不向正在运行的 Agent 悄然热加载另一套环境。
- 达到费用上限或运维暂停执行时，明确新任务准入、正在进行的调用、取消、部分
  结果和允许的有限超额。取消无法撤回已经完成的外部操作。

这些问题应在对应设计中解决；不代表现有生命周期行为都缺失，也不代表每次状态
变化都必须停止所有工作。

## 依赖客户条件的能力

| 能力 | 使其成为必要项的证据 |
|---|---|
| SCIM 或目录同步 | 人工入离职处理无法满足客户规模或访问撤销要求 |
| 同时支持 SAML 与 OIDC | 目标身份系统确实需要两者；首个客户只需可用的一种集成 |
| 自定义角色与跨 Space 管理 | 固定角色和现有 Space 管理无法表达已证实的职责划分 |
| 外部密钥提供方与工作负载身份 | 有明确的企业凭证系统或短期凭证要求；遵循路线图既有的密钥能力顺序 |
| SIEM 投递、可发现篡改的审计与特殊保留控制 | 明确的调查、保留或安全要求超出现有审计机制 |
| 高可用与多地域恢复 | 有文档的可用性、恢复时间与恢复点目标；基础恢复能力仍是基本要求 |
| 完全离线部署 | 目标环境禁止外部依赖，包括模型调用、更新或可能的许可证校验 |
| 认证、全天候支持与合同 SLA | 采购要求这些能力，且组织能够持续提供流程、人员和证据 |

部署所承诺的边界需要哪些安全控制，就必须提供哪些控制；不能因为相关集成属于
后续商业设想而推迟必要的安全保障。

## 商业方案与建议边界

| 方案 | 收费价值 | 权衡 |
|---|---|---|
| 开放软件，实施和支持收费 | 部署、集成、维护与责任明确的协助 | 初始产品投入较小，收入依赖交付能力 |
| 社区核心加付费企业扩展 | 企业集成与集中治理 | 可持续提供产品价值，但需要明确功能、打包、许可和维护决策 |
| 托管或专属部署 | 降低运维负担，提供受支持的环境 | 增加托管、安全、事故响应与持续服务责任 |

讨论倾向于保留完整的社区产品，同时验证付费企业扩展和实施服务。这是建议，尚未
成为商业或许可政策。

- 社区基础：独立本地执行、自托管、核心 Agent 能力、基本协作、现有权限/审计/
  配额控制、执行安全与基础恢复。避免收回既有开放能力来制造收费层。
- 可能的企业扩展：企业身份生命周期集成、集中策略与成本管理、企业审计和密钥
  系统集成、受控插件分发。基础 SSO 的收费归属仍开放；能力重要不自动决定价格。
- 商业服务：范围明确的部署与集成、升级恢复协助和专属支持。只有运行证据与人员
  能力足以支撑时，才提供相应服务等级承诺。

私有部署本身属于 BuildMax 的产品定位。建议的付费价值是额外的组织管理能力与
交付责任。本备忘录不改变现有[许可证](../../../LICENSE)。未来打包和许可条款
应独立决策，再实现商业授权控制。

## 开放问题与决策证据

先访谈三到五个潜在企业团队，记录场景、使用者、采购者、部署环境、阻碍条件、
验收测试和付费意愿。优先争取范围明确的付费试点，不从其他项目的功能列表推断
自身需求。

开放问题包括：先服务哪类客户，什么阻碍今天的部署，人员变化后谁负责无人值守
工作，哪些能力属于社区基础，以及客户主要需要软件、实施还是持续运维。计价
单位、采购条款和离线商业授权行为需要先取得证据，再投入实现。

可能的首个企业范围是把企业登录与访问撤销接入现有授权和审计生命周期。执行与
成本控制按首个客户证实的缺口推进。这是客户调研假设，不是另一套优先级队列；
当前 Beta 工作仍由路线图管理，并须支撑向试点客户做出的可靠性承诺。

采纳方向前，应有明确的运维流程和预算负责人、达成共识的社区/付费边界、归属与
失败行为清楚的有限实现范围，以及承诺的部署和生命周期结果的验证证据。未解决
的假设保持显式记录。

## 采纳后的归宿

已采纳的优先级进入路线图，长期决策进入对应设计记录。获批且已分解的主线工作
进入 backlog；行为交付时再更新运维文档。商业方向确定后，将长期理由移入设计
记录，并按文档规范退役本提案。
