## 1. 摘要

BuildMax Desktop 是一个 Wails 应用，其中间是单一的 session 聊天。一个项目被打开、
一个 session 占满中间面板、文件与 diff 待在右侧 inspector，并且——按
[session-tree 提案](session-tree-and-agent-mailbox.md) §2.4 记录的限制——每个
Project 至多一个 Agent 运行。真实项目上的工作并非一条串行对话：用户读一个文件、
跑一条命令、盯着一个 Agent、看一处变更，再回到线索。当前界面为此有三套互不相干的
机制——中间聊天、右侧 inspector，以及（来自本文早前草稿附带的原型）底部终端——而
它们都不让用户在视野里同时保留多于一个活动。

本提案评估把 Desktop 重塑为**一个中间面的异构 tab，由一个 Explorer 侧边栏喂入**
——这正是开发者在 VS Code 等编辑器里已经熟悉的排布，适配到 BuildMax 的
project/session 模型。其本质是单一新概念，即 tab，其*内容*是少数几种活动类型之一：

- **聊天 tab**——一个 Agent session，即 Desktop 今天已有的界面；
- **终端 tab**——一个用户直接驱动的交互式本机 shell；
- **文件 tab**——一个工作区文件的内容；以及
- **diff tab**——一个被修改文件的 diff。

导航移到左侧 **Explorer**——一个单一的侧边栏 section，带两种展示模式：Directory
与 Changes，用于索引 active project 的工作区及其被修改文件。Explorer 只负责浏览；
打开某个具体文件或变更是通过点击完成的，点击会在中间打开（或聚焦）一个内容 tab。
这就是浏览与内容如何连起来的：侧边栏是索引，中间是你正在做的事。

这次重塑是简化而非增加：它把三套并列的 UI 机制压成一个 tab 面加一个侧边栏，于是
用户的多个活动以 tab 的形式并行推进。本提案记录该模型、它的边界、分阶段交付，以及
方向获得路线图席位前所需的证据。它**取代**了早前的"Desktop 终端多 tab"草稿，把
本机终端折叠为一种 tab 类型。终端传输的探索性原型已经存在（见 §19）；它作为底部
面板的临时放置**不是**目标，将被一个终端 tab 取代。

## 2. 问题与当前背景

### 2.1 同一工作区的三套互不相干的界面

Desktop（`desktop/frontend/src/App.jsx`）通过三套独立机制呈现一个项目的工作：

- **中间**只显示一个 session 的聊天；
- **右侧 inspector** 在 Files、Changes（diff）与 Session Info 之间切换；以及
- 交互式终端只作为起草本提案时加入的探索性底部面板存在。

每一个都是自成一体的布局、状态与交互。文件与对话无法并排；终端是一种模式，而非
聊天的对等物；从"读这个文件"切到"看这个 diff"再切到"跟 Agent 对话"，意味着在三种
不同界面之间移动。

### 2.2 一次只有一个活动会把用户串行化

中间只放一个 session。无法在聊天时保留文件打开、无法在读 diff 时跑命令、无法在
视野里同时保留两个 session。用户被界面串行化，而非被工作串行化——对于天然并发的
活动，人却要在单焦点界面上等待。外部编辑器与终端来填补这一空缺，把项目上下文
拆散到并不了解 Agent 所操作工作区的多个窗口里。

### 2.3 并行方向本身就已假定一个多活动界面

本地体验方向指向并行工作。[session-tree 提案](session-tree-and-agent-mailbox.md)
把子 session fork 进隔离的 worktree 并扇回结果；其 §15.1 勾勒出一个展示子级、
收件箱与结果卡片的 Desktop，并指出"并发执行只在工作区隔离存在之后才暴露"。那个
界面需要展示多个活动。一个 tab 面是它诚实且最小的形态，而且它立即就有用——用于
文件、终端与 diff——远早于更难的并发机制落地。

### 2.4 构件已具备

Desktop 已经渲染一个 session（聊天）、一个文件树和一个 diff 视图；它已经通过
Wails 事件向前端流式传输字节；Go 侧也已 vendored `github.com/creack/pty` 并拥有
一个 Bash 沙箱。所缺的不是内容渲染器，而是组织界面——一个 tab 模型和一个
Explorer——让它们共存并成倍增加。

## 3. 用户场景

### 3.1 文件、终端与对话并排

用户在一个文件 tab 里读 `store.go`，在一个终端 tab 里跑 `./make test ...`，在一个
聊天 tab 里就一处失败向 Agent 提问。在三者间切换是在 tab 条上点一下，而不是在三种
不同界面之间移动。没有东西逼迫关掉文件才能看到对话。

### 3.2 先浏览，后打开

用户把 Explorer 切到 Directory，点击 `internal/infra/db/store.go`，一个文件 tab
打开。他们把 Explorer 切到 Changes，点击一个被修改文件，一个 diff tab 在旁边打开。
侧边栏作为索引不动；内容作为 tab 累积。

### 3.3 视野里两段对话

两个任务上的两个 Agent session 是两个聊天 tab。用户读一个的同时另一个在流式输出，
在一个里回答审批而不关掉另一个。（两者是否可以*同时运行*另受设闸；见 §12。）

### 3.4 在分屏里比较两个文件

用户把一个 diff tab 拖进第二个 pane，使变更紧挨它所触及的文件。同样的 tab，平铺
——没有新活动类型，只是一个布局（§15）。

## 4. 术语与心智模型

### 4.1 Tab

**tab** 是中间界面中一个独立存活、可切换的活动，拥有自身的创建、焦点与销毁。它是
唯一的新组织概念。一个 tab 渲染一种内容类型；它本身不是内容的后端。

### 4.2 Tab 类型

范围内的内容类型是 **聊天**（一个 session）、**终端**（一个 PTY）、**文件**（一个
工作区文件的内容）与 **diff**（一个被修改文件的 diff）。模型日后对更多类型开放，
但每种类型都必须以一个具体活动挣得其位置，而非因对称而存在。

### 4.3 Explorer

**Explorer** 是索引 active project 工作区的左侧边栏 section。它有两种展示模式——
**Directory**（文件树）与 **Changes**（被修改文件）——类比编辑器的 Explorer 与
Source Control，统一为一个 section 的两种视图。它负责浏览；不承载内容。点击某个
条目会打开一个内容 tab。

### 4.4 Pane

**pane** 是中间界面的一块矩形区域，一次显示一个 tab。今天只有一个 pane；§15 平铺
多个。一个 tab 的后端与 pane 无关，因此 tab 可在 pane 间移动而不扰动其内容。

## 5. 目标

- 让中间成为一个异构 tab 面——聊天、终端、文件、diff——使多个活动同时被保留与切换。
- 让用户打开一个本机终端并运行命令，而无需离开应用。
- 让用户把工作区文件与 diff 作为一等内容，与对话并排打开。
- 给左侧边栏一个 project 级的 Explorer，含 Directory 与 Changes 模式，通过
  点击打开与中间相连。
- 把 tab 归属到 active project，契合现有 project/session 模型与本地项目工作区边界。
- 让界面为分屏/grid 布局做好准备，而不把它变成新概念。
- 按 session 计键，使 agent tab 能并发运行，并把并发写者的隔离（按 session 的 worktree）
  交给用户（§12）。

## 6. 非目标

- 一个通用可扩展编辑器平台或插件贡献的 tab 类型。类型是一个小而封闭的集合，直到
  一个具体活动证明需要再加。
- 一个完整代码编辑器。文件 tab 是查看器，同时支持对文本文件的朴素"编辑并保存"；
  语言服务、多光标之类不在范围内。
- 远程或服务端终端，或 SSH 进入 worker 或 Space。终端仅本地（§11、§14）。
- 平台强制的并发 agent 运行之间的工作区隔离。运行按 session 计键，因此它们*可以*同时
  运行；避免两者把同一工作区互相覆盖（按 session 的 worktree）是用户的判断（§12）。
- 用用户终端替代 Agent 的 Bash 工具（§11.4）。
- 一个常驻终端守护进程，或跨应用重启重建终端回滚缓冲。
- 在第二个界面需要之前，就构建共享的 `@buildmax/gui` tab 框架。
- 改动 Portal，它是具有不同信任边界的浏览器界面（§16.3）。

## 7. 设计原则

### 7.1 一个组织概念

中间是 tab；侧边栏是 Explorer。两套机制，而非五套。一个新活动是一种新 tab 类型，
而非一个新界面。这正是这次重塑属于简化的全部原因。

### 7.2 侧边栏索引，中间承载内容

Explorer 浏览工作区及其变更；它从不自行渲染文件内容或 diff。内容总是待在一个中间
tab 里，通过点击打开。把导航与内容放在不同的家，避免了目录浏览器在两处变成两样
东西。

### 7.3 Tab 归属 project 级

一个项目拥有一个工作区（`internal/core/localproject`：一个 repo 或目录）。终端与
文件属于那个工作区，session 属于那个项目。因此 tab 集合归属 active project；一个
聊天 tab 是一个 session 的渲染，而终端、文件与 diff tab 是它的工作区兄弟。切换项目
就切换 tab 集合。

### 7.4 打开是幂等的

点击一个已打开的文件会聚焦它的 tab，而非打开一个重复项。单击浏览可复用一个预览
tab；显式打开则钉住一个 tab。界面不得每点一次就长出一个 tab。

### 7.5 后端不是 pane

一个 tab 渲染一个后端——一个 session、一个 PTY、一个文件、一个 diff——它独立于哪个
pane 显示它而存在。这让分屏/grid 保持为一个布局问题，并让 tab 在 pane 间移动而不
丢失状态。

### 7.6 人的并行是免费的，写者安全由用户负责

多个 tab，以及多个只读或空闲的活动，可以安全地同时展示。运行按 session 计键，因此
多个 agent tab 也可以同时运行；是否*安全*取决于它们是否共享工作区，而这由用户用按
session 的 worktree 控制。界面表达并发，用户负责隔离写者（§12）。

### 7.7 原型用于学习，提案用于决定

终端传输原型验证 PTY 机制。它不决定界面。是真实、反复的使用证据赢得路线图席位。

## 8. Tab 模型

一个 tab 拥有稳定的 id、一个类型、一个标题、一个焦点状态、一个 dirty/活动指示器，
以及一个销毁。中间界面拥有创建、切换、重排、关闭，以及——日后——在 pane 间移动一个
tab。每个后端拥有自身的生命周期。

打开规则：

- 打开一个已打开的活动会聚焦已有 tab；
- 一次浏览点击可填充一个复用的预览 tab；一次双击或显式动作把它钉为一个持久 tab；
- 关闭一个 tab 销毁其视图，对终端而言终止其 shell；对聊天 tab 隐藏该 session（仍
  持久化）；对文件或 diff tab 仅关闭视图。

tab 集合归属 project 级：它是 active project 打开的活动集合。切换 active project
显示那个项目的 tab。一个项目打开的 tab 集合是否跨重启记住，是界面状态，在 §13 决定。

## 9. Tab 类型

每种类型共享 tab 界面但不共享其后端：

| 类型 | 后端 | 驱动者 | 并发 | 持久化 |
|---|---|---|---|---|
| 聊天 | Agent session + 运行 | 用户 prompt，然后 Agent Loop | 每 session 一条运行；session 间并发，用户负责隔离写者（§12） | 现有 session 持久化 |
| 终端 | 交互式本机 PTY | 用户，逐个按键 | 自由并行（隔离进程） | 跨重启不保留 |
| 文件 | 一个工作区文件的内容 | 读，另加对文本文件的编辑并保存 | 自由并行；保存写入磁盘 | 无；从磁盘重读 |
| diff | 一个被修改文件的 diff | 读 | 自由并行（读） | 无；由工作区状态派生 |

Session Info 今天是右侧 inspector 的一种模式，将成为 active 聊天 tab 的一个属性
视图，而非自己的中间内容类型——它描述一个 session，因此属于那个 session 的 tab，
而非一个对等 tab。

类型刻意很少。一种新类型（例如搜索结果视图）必须由一个具体活动证明，按 Occam，
而非为了与编辑器对称而添加。

## 10. Explorer 侧边栏

### 10.1 结构

左侧边栏自上而下是 **Projects** 然后 **Explorer**。Projects 是现有项目列表，含其
session。Explorer 归属 active project，有两种展示模式：

- **Directory**——工作区文件树；以及
- **Changes**——工作区被修改文件，作为变更列表。

两者是一个 Explorer section 的模式，而非两个独立面板，因此侧边栏有一个浏览的家，
切换它所索引的东西。

### 10.2 点击打开把侧边栏与中间相连

Explorer 浏览；不渲染内容。交互：

- 点击 Directory 里的一个文件打开（或聚焦）一个 **文件 tab**；
- 点击 Changes 里的一个被修改文件打开（或聚焦）一个 **diff tab**；以及
- 一次浏览点击可复用单一预览 tab（§7.4），使扫视文件树不会喷出 tab。

这就是导航与内容之间的全部连接：侧边栏是索引，中间是内容，点击是链接。

### 10.3 从右侧 inspector 移出的东西

今天右侧 inspector 的 Files 与 Changes 模式移入 Explorer 侧边栏；它们的*内容*
（一个文件的文本、一个文件的 diff）移入中间 tab。Session Info 移到聊天 tab（§9）。
右侧 inspector 作为一套单独机制被退役，而非搬迁——它的职责被侧边栏与 tab 界面吸收。

## 11. 终端 Tab 语义

一个终端 tab 是一条 shell 工作线：一个用户驱动的交互式本机 PTY。

### 11.1 启动与工作目录

终端在 active project 的工作区根启动用户的 `$SHELL`（缺省时回退到合理默认值），
继承用户环境。终端是用户自己的权限——而非一次 Agent 工具调用——因此其环境不会像
Agent 子进程那样被清洗。

### 11.2 PTY 通道

Go 侧分配一个 PTY，启动附着其上的 shell，并把输出作为字节流通过按 tab id 分键的
Wails 事件推给前端。前端通过一个绑定方法把按键写回，并在几何变化时发送 resize
（列数与行数），使受控进程看到正确的窗口尺寸。控制序列、颜色与二进制输出原样透传；
前端模拟器负责解释它们。

### 11.3 生命周期

回滚缓冲在 tab 存活期间保存在模拟器中，不持久化。当 shell 退出时，tab 显示退出并
停止。关闭 tab 终止 shell。没有 shell 活过 Desktop 进程：关闭时 Go 侧回收它拥有的
每个 PTY。

### 11.4 用户终端不是 Agent 的 Bash 工具

终端 tab 是用户直接、无上限、交互式的权限；Agent 的 Bash 工具是受限、可沙箱化、
有上限的，且属于某次运行的权限与 trace。让二者保持区分，避免把用户 shell 输入
路由经过 Agent 策略，也避免借一个"用户"终端来洗白 Agent 权限。一个同处的 Agent
是否可以观察终端输出，是一个独立的、后续的决策；首切片让终端对用户私有。

## 12. 并发与 Agent 写者边界

运行按 session 而非按 project 计键：同一 session 同一时刻至多一条运行在飞（对同一
session 的第二条 prompt 排队），而同一 project 里的不同 session **并发** 运行。因此
打开多个聊天 tab 并让它们同时运行是一项真实能力，而不仅是查看上的便利。

剩下的隐患是两个 agent 写入同一工作区、互相破坏状态
（[session-tree](session-tree-and-agent-mailbox.md) §2.4）。本设计不让平台在能够强制
隔离之前一律禁止并发，而是把隔离交给 **用户**——用户本就有工具：一个 session 可以在
自己的、区别于项目默认的 Git worktree 中运行（`session.Meta.Workspace`，Desktop 的
文件绑定已按 session 解析它）。谁在同一共享工作区里跑两个 agent，谁就承担这个选择，
正如对同一工作区开两个终端一样。平台的职责是按 session 计键，使界面能表达这种并发，
并把每条运行的 stream 事件（都带 `session_id`）路由到正确的聊天 tab；判断并发何时安全
是用户的事。

终端、文件与 diff tab 同样没有写者问题——终端是隔离进程，文件保存是用户亲手发起的
磁盘写入，diff tab 是只读——因此它们自由并行。

每个聊天 tab 是一个绑定到单个 session 的自包含 `ChatSession`：它拥有该 session 的记录
与运行状态，只处理带它 id 的事件。全新的聊天起初没有 id，并从后端在运行开始时发出的
专用 `session-adopted` 事件中认领真实 id（只有新聊天的运行会发它，且每个 project 同时
至多一个新聊天，因此即使其它 session 正在流式，认领也无歧义）。仍有一处保留：工具审批
提示按 project 而非 session 计键，因此一个待决提示会显示在该 project 所有运行中的聊天
tab 上、且任一个都能作答——因为审批短暂且少见，这已足够，但按 session 归属的审批是后续
改进。

## 13. 持久化与生命周期

- 聊天 tab 保留 Desktop 已有的 session 持久化；关闭它隐藏该 session，它仍被存储。
- 终端 tab 没有持久状态；它随 tab 或窗口消亡，其回滚缓冲不持久化。
- 文件或 diff tab 是派生视图；打开时从工作区重读，无需持久化。
- 一个项目的布局作为界面状态被记住（按项目存于 local storage），使重启或切换项目后
  在相同的 pane grid 中重开相同的聊天、文件与 diff tab。终端 tab 不纳入保存——已死
  进程无法重开，只能新起一个——被该排除掏空的 pane 在恢复时被丢弃。
- 没有 tab 后端在不该存活处活过 Desktop 进程：session 持久化，但 PTY 在关闭时被
  回收，因此没有 shell 成为孤儿。

## 14. 安全、沙箱与成本

### 14.1 沙箱姿态

Bash 沙箱"对 CLI 默认关闭，对官方 worker 默认开启并 fail-closed 强制"
（[Agent 沙箱策略](../design/Agent沙箱策略.md)）。用户终端 tab 是 CLI 的交互式
本地类比：用户自己的权限，沙箱默认关闭。这是刻意的姿态，若被采纳须写入设计记录；
让用户把某个终端选择性加入沙箱是后续选项，不是首切片要求。

### 14.2 仅本地边界

终端、文件与 diff tab 是作用于项目工作区的本地 Desktop 能力。它们不暴露给 Portal、
worker 或任何网络界面，本提案也不创建路由、socket 或服务端绑定；终端传输仅为
进程内 Wails 桥。

### 14.3 资源卫生

每个终端是一个带文件描述符与输出 pump 的真实子进程；关闭一个 tab 回收其进程并停止
其 pump，关闭窗口回收全部。按事件的输出设界，使失控进程既不无界地淹没桥、也不淹没
模拟器。文件与 diff tab 读取有界内容，不持有进程。

### 14.4 成本

终端、文件与 diff tab 不花费模型 token。聊天 tab 并行现在会让多条运行同时花费 token；
这份花费由用户治理，正如同时跑多个 agent 一向如此。tab 界面本身不引入新成本。

## 15. 分屏与 Grid 布局

Grid 是 tab 模型之上的一个呈现层，而非新概念。中间界面可分裂为多个 pane，每个显示
一个 tab，平铺使用户同时看到多个活动——一个文件挨着它的 diff，一个终端在一段聊天
之下。

因为一个 tab 的后端与 pane 无关（§7.5），平铺只决定哪个 pane 渲染哪个 tab；它不
改变任何后端、生命周期或权限。无论布局如何，模型都持有这条约束：每种 tab 类型的
后端都与其 pane 解耦，因此添加 pane 无需返工 session、PTY 或文件视图。

### 15.1 已实现：pane 的 Grid

工作区是一个 grid——由若干行 pane 组成。每个 pane 有自己的 tab 条与自己的活动 tab，
其中一个 pane 处于 *焦点*。新打开的活动——来自 Explorer 的文件或 diff、一个新终端
——落在焦点 pane。每个 pane 的 tab 条带有 **向右分屏**（在本行加一个 pane）与
**向下分屏**（新增一行）控件；两者都会插入一个新的空 pane 并聚焦它。空 pane 是短暂
的：焦点一离开就被回收，因此布局不会堆积空白 pane。关闭一个 pane 的最后一个 tab 会
移除该 pane 并聚焦相邻 pane。

把一个 tab 从其 tab 条 **拖拽** 并放到另一个 pane，即可把它移动过去。因为一个 tab
的后端与 pane 无关（§7.5），移动携带的是活的内容，而不只是描述符。终端把这一点体现
得很具体：每个终端的模拟器都常驻在一个隐藏宿主中被挂载，并被 *portal* 到当前显示它
的 pane（`TerminalHost`），因此被拖动的终端会保留其回滚缓冲与光标——DOM 节点是被
迁移，而非重建。这正是模型坚持"后端与 pane 解耦"的原因。

tab 条支持常见的编辑器手势。跨 pane 移动 tab 的同一次拖拽也能在条内 **重新排序**——
放到指针下那个 tab 之前，或越过最后一个放到末尾。**右键** 打开上下文菜单，含 *关闭*、
*关闭其他* 与 *关闭右侧全部*；每一项都会保留不可关闭的 tab（当前聊天），与逐个 tab 的
关闭按钮一致。对文件或 diff 类型的 tab，菜单还提供 *复制相对路径* 与 *复制绝对路径*：
相对形式是工作区根下的路径，而绝对形式在 Go 侧针对 session 自身的工作区根解析——当
session 拥有 worktree 时即为该 worktree——因此它指向面板实际读取的那个文件，复制经由
原生剪贴板完成。

工作区底部有一条状态栏，作为全局一等面板——Home 与项目视图中都存在。其控件自左向右依次
为状态、打开项目时才出现的工作区动作，以及固定在最右侧的主题切换——这样主题按钮的位置
不会随项目控件的出现与消失而移动。工作区动作之一是一个图标按钮，在两种形态之间
**一键切换**，两者都无需手工搭建：从单个 tab 化 pane 出发，它把每个 tab
*平铺*（`tile`）成各自的 pane，排布为最多三列的近似正方形 Grid；从 Grid 出发，它把每个
pane *合并*（`collapse`）回一个按阅读顺序排列的 tab 化 pane。两者都是同一模型上的纯操作；
因为后端与 pane 无关，被平铺的终端和被拖动的终端一样完整保留其 session。

### 15.2 搁置：可调分隔条

pane 目前平均分配空间（flex）；用于调整大小的可拖拽分隔条、以及超出"行内 pane"的
任意嵌套分屏，均为后续工作。布局本身已按项目持久化（见 §13）。

## 18. 方案与权衡

| 方案 | 优势 | 主要顾虑 |
|---|---|---|
| A. 保留固定面板，仅加一个终端面板 | 改动最小 | 留下三套互不相干的界面；无并行活动；终端是模式而非对等物 |
| B. 中间 tab 面 + Explorer 侧边栏（本文） | 一个组织概念；并行活动；契合编辑器心智模型 | 比外挂面板更大的 UI 变更 |
| C. B 加上立即的分屏/grid | 完整的并行愿景 | 分屏在 tab 模型有证据之前增加布局复杂度 |
| D. 一个带插件 tab 类型的完整可扩展编辑器平台 | 最大灵活性 | 范围巨大；违背 Occam；无已证明的需求 |

候选建议是 **B，把分屏/grid（C）搁置**为纯布局层，待 tab 验证后再上。A 是这次
重塑取代的现状。D 被否决：tab 类型是一个小而封闭的集合，直到一个具体活动证明需要
再加。

## 19. 候选首个切片

首切片把中间做成一个 tab 面并立起 Explorer，用能证明模型的最小类型集合：

- 中间一个 tab 面，可打开、聚焦、切换与关闭 tab，打开幂等（§7.4）；
- 把现有聊天提升为一个 **聊天 tab**；
- 一个由 PTY 会话管理器支撑的 **终端 tab**（在工作区根打开、pump 输出、接受按键
  与 resize、关闭并回收）——其传输已被原型化（见下）；
- 一个由在 Explorer 点击打开的 **文件 tab** 与 **diff tab**；以及
- 带 Directory 与 Changes 模式的 **Explorer 侧边栏**，取代右侧 inspector 的 Files
  与 Changes。

最初的原型排除得更多；在其之上后续已构建的有：pane grid（§15）、按项目的布局持久化
（§13）、文件编辑，以及并发聊天 tab（运行按 session 计键，§12）。仍排除：沙箱选择性
加入与 Agent 对终端的观察。

终端传输已作为本文早前草稿的探索性原型存在：一个 Go PTY 会话管理器
（`internal/interface/desktop/terminal.go`）带 Wails 绑定与字节流事件、一个
`xterm` 前端，以及驱动真实 shell 的测试。它当前作为底部面板的放置是临时的；把它
折叠进一个终端 tab 是目标。原型验证的是传输，而非界面。

## 20. 分阶段交付

### 阶段 0：验证用户问题

- 观察 Desktop 用户是否会另开外部编辑器与终端，以及用来做什么。
- 了解真正的需求是"聊天旁的终端"、"聊天旁的文件"、"多个 session"，还是全部。
- 确认用户想要的是 tab 面与 Explorer，而不是单一外挂面板。

### 阶段 1：tab 面、聊天与终端 tab、Explorer

- 带幂等打开与关闭的中间 tab 面。
- 把聊天提升为聊天 tab；终端 tab 基于已原型化的 PTY 传输。
- 带 Directory 与 Changes 的 Explorer 侧边栏；文件与 diff tab 由点击打开；退役右侧
  inspector。

### 阶段 2：可读质量的文件与 diff tab

- 语法感知的文件查看、diff 渲染与大文件设界。
- 预览 vs 钉住的 tab 行为。
- 跨重启重新打开一个项目的聊天、文件与 diff tab。

### 阶段 3：多个并发聊天 tab

- 多个聊天 tab 打开、可切换，各自的 session 并发运行：运行按 session 计键，每条
  stream 事件都带 `session_id` 并路由到其 tab。
- 并发写者之间的隔离由用户负责，方式是按 session 的 worktree（§12）。

### 阶段 4：分屏与 grid

- 把中间平铺为 pane；在 pane 间移动 tab。
- 保持每个后端与 pane 无关。

### 阶段 5：改进

- 可选的终端沙箱选择性加入；可选的、经明确决策的 Agent 对终端的观察。（文件编辑已
  构建——见 §13。）

## 21. 原型验收标准

阶段 1 切片必须证明：

- 中间可打开、聚焦、切换与关闭 tab，且打开一个已打开活动会聚焦它而非重复；
- 聊天 tab 保留今天的 session 行为；
- 终端 tab 以用户的 shell 在工作区根打开，正确透传按键、控制字符、颜色与二进制
  输出，把 PTY resize 到 pane，并运行交互式程序；
- 关闭终端 tab 回收其 shell，关闭窗口回收全部 shell 且无孤儿进程；
- 点击 Directory 里的文件打开一个文件 tab，点击 Changes 里的变更打开一个 diff tab，
  各自复用已打开 tab 而非重复；
- Explorer 在 Directory 与 Changes 之间作为一个 section 的模式切换；以及
- 终端以用户自己的权限运行，不经过 Agent 策略路由。

## 22. 待解决问题与所需证据

### 产品与 UX

- 用户最常打开哪些活动——终端、文件，还是多个 session？答案决定各阶段次序。
- 浏览点击应使用单一复用的预览 tab（编辑器风格），还是每次点击都钉一个 tab？
- 已决：新聊天由项目列表的"新建聊天"动作创建（任一 session 也可从侧边栏作为聊天 tab
  打开）；每个 project 至多一个尚未发送的新聊天。

### 行为与传输

- 在 macOS、Linux 与 Windows（ConPTY）上，何种默认 shell 与启动模式最契合用户预期？
- 何种按事件输出上界能既防止失控进程淹没桥、又不损害吞吐？
- 一个文件 tab 在退化或拒绝之前的尺寸与渲染上界是什么？

### 边界与安全

- 终端 tab 是否应该可沙箱化，若可，是选择性加入还是策略驱动？
- 如果 Agent 日后可以观察终端，鉴于终端携带用户完整环境，应由何种权限与同意模型
  治理？
- 已决：文件 tab 支持编辑并保存；写入以用户自身权限（非 Agent）进行，限制在解析出
  的工作区根内，且对二进制或被截断内容拒绝写入（§13、§14）。

### 并发与布局

- 已决：并发 agent tab 按 session 运行；隔离写者是用户的责任，方式是按 session 的
  worktree，而非平台强制的闸（§12）。
- 已决：grid 布局按项目持久化（终端除外）；见 §13。

### 采纳前所需的证据

- 设计伙伴在真实工作中保留多个 tab 打开，而非出于新鲜感只用一次。
- 终端与文件/diff 查看器足够正确，可供日常使用。
- 在 Explorer 里浏览并打开 tab 比当前 inspector 更快，而不只是不同。
- 正常或异常的 Desktop 退出后都没有孤儿 shell 进程存活。
- 该界面可测量地减少窗口切换，而不是复制用户本就保留的工具。

## 23. 若被采纳后的去向

若证据支持该方向：

1. 把已接受的 tab 模型、Explorer 结构与终端沙箱姿态记入一份本地体验设计记录，与
   [界面定位](../design/界面定位.md)及 [Desktop 架构](../contribute/architecture/desktop.md)
   并列。
2. 把它的次序加入[路线图](../ROADMAP.md)，说明并发 agent tab 按 session 运行、由用户
   负责 worktree 隔离，以及它与 session-tree 工作区工作的关系。
3. 为 tab 面、Explorer、终端 tab、文件与 diff tab，以及任何分屏/grid 或沙箱选择性
   加入创建实现 issue。
4. 随切片落地更新 Desktop 与界面定位架构文档以及用户手册。
5. 在用户可见界面发布时添加 changelog 条目。
6. 一旦其决定移入路线图、设计与实现记录，即删除本提案；Git 历史保存讨论。

若证据仅支持"聊天旁的终端"，则接受终端 tab 并搁置 Explorer 重塑。若证据显示用户
只需要 Agent 并行而从不需要手动终端或文件视图，则投资 session-tree 界面。

## 24. 候选方向

候选方向是：

> BuildMax Desktop 应呈现一个异构 tab 的中间界面——聊天、终端、文件与 diff——由一个
> project 级的 Explorer 侧边栏（含 Directory 与 Changes 模式）喂入。侧边栏索引工作
> 区；一次点击打开一个内容 tab；中间承载用户正在做的事。tab 是唯一的新概念，分屏/
> grid 是其上的后续布局，agent tab 按 session 并发运行，由用户以按 session 的 worktree
> 负责写者隔离。终端是一种 tab 类型，而非一个特殊界面。

它提供的多于一个外挂式终端，少于一个可扩展编辑器平台。它是否赢得路线图席位，取决于
反复的证据：用户在真实工作中保留多个 tab 打开，且改变其节奏的是界面本身，而非
新鲜感。
