## 1. 决策问题与候选方向

System Administrator 是否应查看并管理所有 Space 的 Agent、Workflow、
Schedule 和 Issue？如果应该，是让管理员隐式进入每个 Space，还是在部署级
Administration 页面提供统一界面？

候选方向是**按用户结果划分**：

1. Administration 展示整个部署的**运维元数据**：工作是否推进、失败或消耗容量，
   哪个 Space 需要关注。它不会仅因为 System Administrator 打开页面，就列出
   四类 Space 工作内容的集合。
2. 属于多个 Space 的用户可以获得覆盖**自己有权访问的 Space**的导航或工作视图。
   即使从聚合视图进入，打开具体对象和修改对象仍通过原有 Space 路由与角色检查。
   System Administrator 授权不会扩大这个集合。
3. 非成员需要查看或修改某个 Space 内容，属于独立的支持访问决策。本文不提议
   自动进入所有 Space。

本文讨论这些视图的边界及所需证据，不承诺三个界面全部建设。它保留已接受的区分：
部署管理负责系统运维；Space 成员身份授权访问该 Space 的工作。

## 2. 用户结果与证据

运维人员在事故中的核心结果是：**判断 BuildMax 是否正在处理工作、进度停在何处、
由谁处理**，而无需阅读团队指令或工作产物。负责多个 Space 工作的人有另一种需求：
不用反复切换 Space，也能找到并管理自己本就有权访问的工作。

这个问题来自产品讨论：是否让管理员在一个地方看到各 Space 的 Agent、Workflow、
Schedule 和 Issue。这说明导航和运维问题值得探讨，却不能证明部署管理员需要读取
每个 Space 的内容。目前还没有量化事故、运维演练或多 Space 工作观察能够区分两种
需求。因此本文保留较广泛的访问决策，并说明支持每个切片所需的最小证据。

## 3. 当前边界

- 已接受的[系统管理设计](../design/系统管理.md)赋予 System Administrator 部署级
  权限，而非 Space 成员身份。没有成员身份的管理员不能读取 Space 提示词、
  Issue 文本、生成输出、文件、Artifact 或 trace。
- Administration 已提供 Space 元数据、成员、配额等级与聚合用量，并可搜索跨
  Space 审计记录及托管模型调用账本。系统视图包含按状态统计的 TaskRun 数量。
  这些是限定范围的运维投影，不是 Agent、Workflow、Schedule 或 Issue 清单。
- Agent、Workflow、Schedule 和 Issue 使用 Space 范围的路由与授权。改变浏览器
  导航不会安全地改变这些权限。即使在 Admin 页面提供，返回名称或定义的全局
  接口也等同于授予内容访问权限。
- [系统管理设计](../design/系统管理.md)已负责一般性的运行健康、
  容量与运维界面一致性（§6.1，运行时汇总见其 §17 第 16 个开放问题）。本文负责更窄的问题：何时从元数据进入具体 Space 工作，
  以及如何呈现用户已经拥有成员身份的多个 Space 的工作；不重复设计运行看板。
- [R2 与 R3](../ROADMAP.md)仍缺生命周期和候选版本的运维证据。只有当运维旅程
  证明现有视图无法支持必需的诊断或恢复时，新的跨 Space 界面才进入 Beta 门槛。

## 4. 目标与非目标

目标：

- 为运维人员提供可信的部署级工作进度与容量信号，并指出需要关注的 Space 或人员。
- 让拥有多个 Space 权限的人找到自己有权访问的工作，不扩大 System Administrator
  授权可读或可改的范围。
- 明确每个视图所依据的权限：运维元数据使用部署授权；工作内容和变更使用
  Space 成员身份及角色。
- 在增加宽范围查询或新的管理操作前，说明所需证据与验证边界。

非目标：

- 让 System Administrator 成为所有 Space 的通用 Owner、静默加入管理员为成员，
  或在 Admin 页面绕过 Space 授权。
- 跨部署搜索 Agent 提示词、Workflow 定义、Schedule 提示词、Issue 标题与描述、
  文件、输出或 trace。
- 跨 Space 批量编辑、发布、暂停、取消、重试或删除。
- 支持访问授权、紧急内容访问或新全局角色。这类权限需要独立决定同意、到期、
  撤销及审计机制。
- 持久保存第二份 Space 工作副本，或建立可读取所有领域表的通用 Admin store。

## 5. 各类使用者需要什么

| 使用者与任务 | 有用的视图 | 权限来源 |
|---|---|---|
| 诊断工作停滞或高成本运行的部署运维人员 | 部署级 TaskRun 状态与时长、安全的失败类别、依赖健康状况和 Space 级容量压力 | System Administrator 授权；不包含 Space 内容 |
| 管理多个 Space 工作的人 | 仅覆盖其成员 Space 的聚合导航或工作列表；沿用普通详情和操作 | 每个对象仍检查 Space 成员身份及角色 |
| 治理单个 Space 的 Owner 或 Admin | 现有 Agent、Workflow、Schedule 和 Issue 页面 | 该 Space 的角色策略 |
| 需要检查其他 Space 内容的支持人员 | 本文不建立通用访问权限 | 另行作出有证据支持的支持访问决策 |

这四类资源并非可互换的运维记录。Agent 可能包含指令；Workflow 可能包含任务
提示词和绑定；Schedule 包含将要运行的指令；Issue 包含人的描述和结果。名称本身
也可能泄露工作内容。因此，资源类型不足以判定 Admin 响应是否安全。现有 Admin
响应允许列表把运行状态、时间戳、聚合用量和不透明 ID 视作运维元数据；每增加
一个字段，仍需有具体运维问题和泄露审查。

## 6. 候选产品与权限模型

### 6.1 Administration 保持运维视图

Administration 的 Overview 与 Spaces 区域基于覆盖整个部署的持久事实回答运维问题。
现有 TaskRun 数量和每个 Space 的用量是起点。如果事故演练证明这些数据不足，
[系统管理设计](../design/系统管理.md)可以增加有界的状态与时长汇总、
安全的错误类别，或其他确实缩短诊断时间的元数据。不应只为填充四个标签页，
就增加四类内容列表接口。

投影必须描述多 Server 副本下的整个部署，而非某个副本的内存状态。依赖部分
失效时，应显示数据不可用，不能显示为零工作。专用响应类型须排除用户撰写和
Agent 生成的内容，包括原始错误与 trace 文本。

### 6.2 无需新授权即可聚合有权访问的工作

如果多 Space 用户确实遇到导航问题，Portal 可以提供“我的所有 Space”入口。
Space 集合来自用户当前的成员身份。结果标明所属 Space，详情与变更通过现有
Space 范围契约并重新检查角色。成员身份一旦撤销，下一个请求即失去访问权；
过期卡片不能赋予权限。此视图对任何多 Space 成员都有用，因此不必放在
Administration 中。

第一版应复用每个 Space 的查询，只有实测规模要求时才增加专用聚合查询。
如需新增，Server 必须应用相同的成员过滤与 Space 策略；只在浏览器中筛选
全局响应不构成授权。

### 6.3 例外的内容访问需要独立决策

当前设计允许管理员在共享 Space 的所有 Owner 均已停用时恢复所有权：把一名
现有的有效成员提升为 Owner。这不会给管理员内容访问权。如果真实支持或紧急
旅程要求直接访问，应先决定范围、授权者、期限、撤销、对 Space 的通知、审计，
以及与当前成员身份的关系。不能把这种新权限伪装成 Admin 页面链接。

## 7. 方案与权衡

| 方案 | 解决什么 | 成本或失效方式 |
|---|---|---|
| A. 隐式允许 System Administrator 进入每个 Space | 直接访问全部现有工作页面 | 推翻已接受的 Space 内容边界；所有 Space 路由及操作都成为全局权限 |
| B. 在 Administration 列出并管理全部四类资源 | 管理员有一个统一位置 | 仍通过其他路由授予同样的跨 Space 内容与变更权限；重复 Space 工作流程 |
| C. 将运维元数据与成员范围的工作分开（候选） | 分别解决部署事故与多 Space 导航 | 需用证据决定每个投影，并清楚标明所用权限 |
| D. 维持现有界面 | 无新增授权或查询工作 | 已证明存在的跨 Space 运维或成员导航问题得不到解决 |

方案 C 以最少的新权限和状态满足两类不同问题。A 或 B 都需要明确修改已接受的
系统管理决策，并建立新的威胁模型和策略；内容放在 Admin 页面不会降低敏感性。

## 8. 首个切片与验证

先进行有界运维旅程：在多 Space、双 Server 的部署中，使用现有 Administration
与 Space 视图诊断排队、失败或疑似卡住的运行。记录运维人员无法回答的问题、
缺失字段、采取的操作，以及是否真的需要内容。如果缺口属于运维元数据，只向
现有运行操作工作增加相应投影，然后重做旅程。另行观察管理多个 Space 的用户，
再决定是否建设聚合工作导航。

任何实现切片都需要：

- 授权测试覆盖没有成员身份的 System Administrator、没有系统授权的 Space
  Owner、多 Space 成员、已撤销成员和匿名调用者。Admin 状态不能让 Space 内容
  路由获得许可。
- 使用有明显特征的 Agent 指令、Workflow 输入、Schedule 提示词、Issue 文本、
  生成输出及原始错误进行响应泄露测试。运维投影的响应体、日志、审计事件和 UI
  状态均不得泄露这些内容。
- 新列表有分页与查询上限；数据来自持久状态或部署级协调视图，保证双 Server
  环境中的结果真实。
- 如果建设成员范围的聚合视图，Portal 旅程须证明成员身份撤销后即失去访问权，
  且不能通过过期结果进行变更。

提案本身不改变产品行为，因此无需 changelog，也不增加 Beta 门槛。

## 9. 开放问题与决策证据

- 哪次运维事故需要超出当前 TaskRun 数量、Space 用量、审计和计划中的运行健康
  汇总？哪个准确的元数据字段能缩短诊断时间？
- 多 Space 成员是否真的需要一份聚合工作列表，还是更快切换 Space 即已足够？
  他们会在同一任务中跨 Space 浏览哪些 Agent、Workflow、Schedule 或 Issue？
- 如果运维人员需要在没有 Space 成员身份时停止失控运行，哪种权限、审计、通知
  与多副本语义能支持这项具体操作？本文不授权此操作。
- 是否有无法由 Space Owner 或现有所有权恢复操作处理的真实支持案例？如果有，
  Space 能接受怎样的显式临时访问模型？
- 从 Admin 结果中去掉名称、提示词、原始错误和内容后，哪些字段仍有用？应使用
  逼真的敏感数据检验，而不能只核对字段名。

采纳某个切片需要运维演练或多 Space 用户观察指出缺失的结果，并对解决该问题的
最小响应进行隐私及授权审查。熟悉全局表格，不等于需要全局内容权限的证据。

## 10. 如获采纳的可能归宿

将获采纳的权限决定记入[系统管理设计](../design/系统管理.md)及相关 Space 治理
记录。将有证据支持的运行元数据切片纳入[系统管理设计](../design/系统管理.md)；
将仅限成员的工作视图纳入 Portal 的 Space 导航计划。
只有对应决策获采纳后，才增加路线图与 backlog 工作。支持访问设计如有必要，
仍应单独决策。届时删除本提案，Git 历史保留讨论。
