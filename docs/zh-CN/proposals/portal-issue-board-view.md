## 1. 决策问题与候选建议

Portal 是否应为 Space Issue 提供看板模式？如果应该，在证据足以支持一套规划系统
之前，BuildMax 应负责多大范围的看板产品？

候选建议是：

> 将由证据驱动的 **Board** 视图作为现有 Issue 集合的另一种投影。用三个权威
> Issue 状态作为固定列，让用户通过显式操作在列之间移动 Issue，并让 List 保持
> 同等地位。不要创建 Board 实体、可配置列、独立卡片顺序、WIP 限制、Sprint，
> 也不要根据执行状态自动移动卡片。

这一方向符合 Portal 作为 Space 运维层的定位，但不属于当前私有部署 Beta 门槛。
只有当运维旅程或早期采用表明现有列表确实让共享工作的浏览或推进变得困难时，才应
进入路线图。仅仅因为这种视觉模式很常见，并不足以构成证据。

## 2. 用户结果与当前证据

核心用户结果是：

> Space 参与者能够看清共享工作在各业务状态间的分布，识别下一步由谁或什么执行，
> 并在无需逐个打开 Issue、也不混淆工作状态与 runtime 状态的情况下，主动改变状态。

当前基础可以在不增加 domain 模型的情况下支持一个窄范围看板：

- Issue 是主要的用户可见共享工作对象，Task 与 TaskRun 则拥有执行生命周期。
- Issue 恰好有三个业务状态：`todo`、`in_progress` 和 `done`。
- 人类 Owner 与 Agent 或 Workflow Executor 相互独立，因此卡片可以同时表达责任
  与执行，而无需发明合并后的 assignee。
- 一层 sub-Issue 提供拆分，父级响应也已包含派生子项进度。
- Space Issue 路由已经支持按状态、Owner、Executor 与父级过滤，并返回每个过滤
  集合的总数。
- 每次 Issue 更新都携带版本，因此过期卡片会被拒绝，而不是覆盖较新编辑。

Portal 当前呈现一页十条的顶层 Issue。它适合阅读，但不能在内存中分组为真实看板：
某列可能仅仅因为其 Issue 不在当前未过滤页面中就显得为空。因此，看板必须从集合
语义开始，而不是从卡片样式开始。

## 3. 与现有决策的关系

本提案只拥有一个窄问题：Portal 中 Space Issue 的集合级呈现与状态交互。它不重新
打开下列相邻决策：

| [Portal 响应式与无障碍交互](../design/Portal响应式与无障碍交互.md) | Portal 全局键盘、焦点、目标尺寸、反馈、动效与窄屏规则 | 保持权威；本提案只补充 Board 特有交互要求 |

| [Issue 主题协调提案](issue-topic-coordination.md) | 面向人与 Agent 的父子 Issue 协调信息 | 共享“派生视图，而非另一事实来源”的原则，但不拥有状态列或整个 Space 工作管理 |

保持独立可以避免 Portal 集合视图继承本地 Issue 桥接的生命周期，也避免该跨界面提案
吸收不相关的卡片、分页与交互选择。

## 4. 目标与非目标

目标：

- 让等待、进行中和已完成的 Space 工作一眼可见。
- 在 List、Board、详情、CLI/TUI 与 Desktop 间保留同一 Issue 身份、生命周期、
  授权边界与更新路径。
- 展示 Owner、Executor 与子项进度，但不把它们视为状态权威。
- 通过每列总数与增量加载真实呈现大型集合。
- 通过现有乐观并发契约改变状态。
- 在增加规划概念前验证该视图是否改善真实协作。

非目标：

- 创建 `board`、`lane`、`card`、`sprint`、`backlog` 或 `rank` 实体。
- 增加自定义列、WIP 限制、估算、优先级、标签、截止日期、保存视图、Sprint 或
  手工列内排序。
- 因 Agent 启动、TaskRun 完成、Workflow 失败或所有子项变为 `done` 自动移动
  Issue。
- 通过移动卡片启动 Agent 或 Workflow run。
- 在整个 Space 看板中把 sub-Issue 显示为父级同级条目。
- 在 CLI/TUI 或 Desktop 中重建 Portal 看板。
- 在没有运维证据时把看板当成 Beta 前置条件。

## 5. 产品模型与权威边界

Board 是 Issue 的读取与变更界面，不拥有任何持久业务状态。

| 关注点 | 权威来源 | Board 职责 |
|---|---|---|
| Issue 身份、内容、状态、Owner、Executor、层级与版本 | 现有 Issue service 与 store | 呈现返回状态并调用现有 mutation |
| 所属列 | `issue.status` | 派生唯一一列；绝不持久化第二份 lane 值 |
| 状态变更 | 现有 Issue 授权与版本检查 | 发出显式请求并呈现成功、拒绝或冲突 |
| 执行生命周期 | Task、TaskRun 与 Workflow service | 链接执行详情；绝不推断列移动 |
| 子项进度 | 派生 Issue 子项计数 | 展示进度；绝不存储或汇总状态 |
| 过滤条件 | 现有列表查询契约 | 对所有列应用同一组过滤条件 |

在 List 与 Board 间切换不能创建、复制或重新分类 Issue。卡片使用与列表相同的 Issue
详情 URL。

## 6. 看板体验

### 6.1 固定列

第一个看板严格按 domain 顺序包含三列：

| 列标签 | 机器状态 | 含义 |
|---|---|---|
| To do | `todo` | Space 尚未声明工作已激活 |
| In progress | `in_progress` | Space 声明工作已激活；这不证明有进程仍存活 |
| Done | `done` | Space 认为工作完成；执行记录仍可单独检查 |

标签使用统一展示词汇，而不是原始 enum 字符串。

### 6.2 范围与卡片

整个 Space 的看板只包含顶层 Issue，与当前列表一致，也让一张卡片对应一个共享结果。
父级卡片展示派生子项进度，并链接到详情查看拆分。父级与子级状态保持独立。

第一切片卡片展示标题、人类 Owner 或 **Unowned**、Agent 或 Workflow Executor 或
**No executor**、子项进度与更新时间。描述、讨论、结果、run 与完整子项留在 Issue
详情中。Runtime 状态以后可以作为次要元数据出现，但绝不能选择列或取代 Issue 状态。

### 6.3 过滤与导航

List 与 Board 共享一套过滤词汇。候选第一切片支持 Owner（包括 **Me**）与 Executor，
因为 Server 已拥有这些语义。每个激活过滤条件都同样作用于所有列。

视图与过滤条件位于 Portal route 或 query state 中，使刷新和复制链接可以重现投影。
这是导航状态，不是保存视图实体。浏览器是否在 URL 之外记住个人上次视图仍是开放的
可用性问题。

## 7. 加载、分页与排序

第一版使用现有列表契约，不新增 board endpoint：

```text
GET /api/spaces/{space_id}/issues?parent_id=none&status=todo
GET /api/spaces/{space_id}/issues?parent_id=none&status=in_progress
GET /api/spaces/{space_id}/issues?parent_id=none&status=done
```

这些请求并发运行，并携带相同 Owner 与 Executor 过滤。每列独立拥有条目、总数、分页
与资源状态。共享 Portal 状态模型负责 loading、empty、stale、error、forbidden 和
retry 呈现。失败列不能静默变成空列；只有明确提示看板处于部分状态时，才可以继续
显示成功加载的列。

Issue 保留集合的 `updated_at` 降序。移动会更新 Issue，因此刷新后自然靠近目标列顶部。
不存在手工 rank 或持久化的列内拖拽位置。

只有测量表明三个过滤请求造成显著延迟或数据库负载时，才有理由增加聚合 endpoint。
它仍必须是 Issue 的读取投影，而非第二套写模型。

## 8. 状态变更与一致性

一次移动就是普通的带版本 Issue 状态更新：

1. 用户通过拖拽、键盘或 **Move to…** 选择目标；
2. Portal 用卡片版本和新状态发送现有 `PATCH`；
3. 只有被接受的响应才成为卡片新的权威状态；
4. 刷新或校正受影响的列总数。

移动不改变 Owner 或 Executor，也绝不调用 Run。请求挂起时卡片不能再次移动。

版本冲突不能自动重试。Portal 要说明 Issue 已变化，重新加载权威状态，并要求用户再次
决定。授权、校验与网络失败让卡片留在权威列中，并遵循现有 mutation 反馈契约。

分别加载的列在并发移动期间可能短暂不一致。Board 是最终刷新的运维视图，而不是事务
冻结快照，不能声称所有列来自同一个数据库时刻。

## 9. 交互与无障碍

现有 Portal 响应式与无障碍记录保持权威。Board 只增加三项特定要求：

- 拖拽是增强，不是契约；每次移动都可通过有名称的 **Move to…** 操作由键盘、辅助
  技术、触控与鼠标完成；
- 成功、冲突和失败后，焦点恢复或保留在有意义的卡片或列目标，并播报结果；
- 窄屏可以使用横向列或单个选中列，但列身份、总数、移动操作与 List 入口始终可见。

第一切片不需要拖拽。只有与非拖拽路径具备交互与测试等价性时才可交付。

## 10. 选项与权衡

### 选项 A：只保留列表

对活跃 Issue 较少的 Space 已经足够，也不增加交互界面。当集合跨越页面后，状态分布
与连续状态变更会更难理解。如果真实使用没有显示该成本，就保留这一选项。

### 选项 B：在客户端分组一个未过滤页面

只取当前列表页并分组为列。分页发生在分组前，会让列内容和数量以不可见方式不完整。
因此否决该选项。

### 选项 C：派生的三列 Issue 看板——候选建议

针对每个状态查询一次现有集合，并通过现有更新路径移动。它不增加 schema 或持久概念
就能闭合“浏览并移动”的用户结果，代价是更多 Portal 集合状态以及谨慎的并发与无障碍
处理。

### 选项 D：可配置规划看板

增加自定义列、rank、WIP 规则、保存视图、泳道与 Sprint。当前没有已证实的 BuildMax
结果要求这些独立概念，而且会产生与专用规划产品竞争的风险。在单独证据支持前否决。

## 11. 候选第一切片

1. 增加 List / Board 切换，但不改变默认视图。
2. 扩展 Portal Issue 客户端，使其表达现有顶层、状态、Owner 与 Executor 过滤。
3. 并发加载三列各自的第一页与总数。
4. 渲染包含标题、Owner、Executor、子项进度与更新时间的顶层卡片。
5. 通过现有带版本 Issue patch 增加无障碍 **Move to…**；除非完全等价，否则不做拖拽。
6. 让每列独立分页并使用共享模型的资源状态。
7. 在导航状态中保留过滤与视图，并让卡片链接到 Issue 详情。

该切片不增加数据库迁移、Server 实体、写路由、手工排序、保存视图或自动执行行为。

## 12. 证据与交付

进入路线图前，观察 R3 运维旅程与早期 Space 使用中，参与者是否反复尝试按状态比较
Issue、查找下一 Owner 或 Executor、连续改变多个状态，或因 Portal 无法显示共享工作
状态而维护外部看板。记录活跃顶层 Issue 集合的形态，但不要用任意条目数作为决策。

如果证据支持该方向：

1. 用真实每列分页与过滤验证只读原型；
2. 测试参与者能否区分 Issue 业务状态、Owner、Executor 与 TaskRun 状态；
3. 加入无障碍状态操作，测试并发编辑、部分失败、慢请求、权限拒绝与激活过滤；
4. 只有观察表明拖拽显著改善重复状态变更时才考虑加入。

## 13. 验收标准

- List 与 Board 在相同过滤下显示相同 Issue 身份。
- Board 严格使用三个现有状态，不在 Issue 外持久化列状态。
- 每列独立查询、分页并显示总数。
- 失败或过期数据与空列明确不同。
- 移动使用卡片加载时的 Issue 版本，绝不覆盖并发编辑，也绝不调度执行。
- 版本冲突重新加载权威状态并要求重新决定。
- 顶层卡片展示派生子项进度，但不改变父级或子级状态。
- 如果存在拖拽，则每个拖拽操作都有等价的有名称非拖拽操作。
- 窄屏保留列身份、总数、移动操作与 List 入口。
- 组件、API 与 Portal 浏览器测试在各自权威边界覆盖列状态、过滤、冲突反馈、部分失败
  与无障碍移动。
- 只有功能交付时才更新 Portal 用户手册与当前状态评估。

## 14. 开放问题

1. 真实 Space 是否积累足够多同时相关的顶层 Issue，使列比过滤和密集列表更能改善决策？
2. Board 主要用于浏览，还是用户会在一次访问中反复改变多个状态？
3. List 是否保持通用默认，还是浏览器应在本地记住上次视图？
4. Owner 与 Executor 过滤是否足够，还是文本搜索是大型 Space 导航的前置条件？
5. 更新时间顺序是否足够稳定，还是实际工作证明需要独立优先级？拖拽本身不是手工 rank
   的证据。
6. 团队是否需要父级范围子项看板，还是顶层进度加 Issue 详情已经足够？
7. 在合格私有部署和现实 Issue 数量下，三个并发过滤请求是否可接受？
8. 哪种窄屏呈现更好：横向列，还是一个选中列？

证据应来自运维旅程、有边界的可用性测试、支持或讨论反馈，以及 Portal/API 实测行为。
竞品功能清单和 Kanban 在其他产品中的普遍程度不能建立 BuildMax 需求。

## 15. 如获采纳的可能归宿

采纳后将：

1. 在 Beta 之后的路线图中加入有证据支撑的 Portal Issue 看板结果；
2. 把持久理由——Board 是投影、状态保持显式、执行永不隐式移动状态——移入
   [Portal 工作与执行体验](../design/Portal工作与执行体验.md)；
3. 为集合状态、呈现、mutation/无障碍行为与浏览器验证创建聚焦 backlog 工作；
4. 切片交付时更新 Portal 用户手册与当前状态评估；
5. 删除本提案。

若否决，则保留 List 与过滤器，作为完整 Portal Issue 集合界面。外部规划集成的证据将
另行评估，而不会被用于让本提案无限期保持开放。
