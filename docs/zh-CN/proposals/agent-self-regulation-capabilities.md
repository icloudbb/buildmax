## 1. 目的与建议

两项候选 Agent 能力促成了这份 proposal：

- **运行时自省**——Agent 可以观察上下文占用、已运行时间、剩余迭代次数、压缩
  状态与现有 Todo 状态；
- **能力发现**——Agent 可以搜索当前 Run 可用的工具，而不是预先接收全部工具
  schema，或猜测某项能力不存在。

二者都是自我感知的一部分，但任何一个都不能单独产生具备自我调节能力的 Agent。
Agent 可能知道上下文即将耗尽，却仍在追求错误目标；它也可能发现完美工具，却没有
权限、误解工具影响，或在没有证据时宣布完成。

暂定建议不是创建一个通用 `Reflect` 工具或新的自我管理实体。BuildMax 应评估一组
小型、类型明确的元能力，让 Agent 能回答十个具体问题：

1. 我负责交付什么结果？
2. 哪些已经证明、仍是假设、存在矛盾或未知？
3. 还剩哪些资源与限制？
4. 有哪些能力可用？
5. 哪些行动获得了授权？
6. 这个 Run 改变了什么？
7. 结果是否确实针对目标完成了验证？
8. 哪些内容能在中断、压缩或迁移后继续存在？
9. 还有哪些委派工作未完成？
10. 哪些知识应该持久化、重新验证或遗忘？

每个答案都应来自拥有该事实的组件。Agent 读取有界投影并提出行动；确定性的
runtime code 执行限制、提交转换、记录影响并决定哪些内容持久化。

这份 proposal 描述能力家族和候选优先级，但不批准新的平台层，也不声称任何候选
接口已经交付。

## 2. 必要用户结果

用户结果是：

> Agent 可以发现当前方法不太可能满足请求结果，寻找更安全或能力更强的下一步，
> 并在权限与资源耗尽前证明任务完成或向用户求助。

这比“模型进行反思”更具体。仅用另一段 prose prompt 表达的反思不可观察，无法与
叙述区分，并且往往只是重复同一个缺乏支持的判断。有用的自我调节会围绕外部事实
闭环：

```text
权威目标与约束
      |
      v
观察状态与证据
      |
      v
识别缺口或不确定性
      |
      v
发现能力与权限
      |
      v
预览或执行行动
      |
      v
检查影响并验证结果
   |             |
 继续        完成 / 升级求助
```

更强的模型可以改善这个循环内部的决策，但不会替代循环所需的权威输入、权限检查、
持久 journal 或验收证据。

## 3. 自我调节的含义

自我调节是使用可观察状态调整工作，同时留在系统拥有的边界内；它不是不受限制的
自主权。

四个区别具有承重作用。

### 3.1 观察不是权限

知道迭代上限不意味着可以提高上限。看到工具存在不意味着可以激活它所属的 plugin。
知道操作被拒绝，也不代表可以改用另一种 transport 达到同一效果。

### 3.2 计划不是目标

用户或所属产品对象提供目标与约束。Todo list 是 Agent 自己制定的计划，可以修改
或丢弃。把计划视为目标，会让 Agent 通过完成自己发明的步骤宣布成功，却遗漏请求
结果。

### 3.3 Trace 不是正确性证据

Trace 只能证明调用与转换被记录，不能证明观察结果支持某项主张、某个测试覆盖了
相关边界，或者验收标准已经满足。

### 3.4 自我调节不是披露隐藏推理

BuildMax 无需保存私有 chain-of-thought 才能让 Agent 行为可检查。它需要的是有界、
外部化的主张：目标、假设、证据引用、影响、验证结果、未解决问题和请求行动。这些
内容同时对 Agent、用户、evaluator 和恢复路径有用，又不会保存不受限的推理文本。

## 4. BuildMax 当前基础

BuildMax 已经实现了大部分确定性底座。缺口主要在面向模型的投影，以及现有事实之间
的契约。

| 能力领域 | 现有基础 | 重要缺口 |
|---|---|---|
| 目标与计划 | Task objective、prompts、持久 notes 与 Todos | 没有明确的目标—验收—证据完成契约 |
| 运行时状态 | Agent 事件、`RunStats`、用量界面、上下文估算、自动/手动压缩 | 没有有界的 LLM 状态视图 |
| 能力发现 | 已组装工具 registry、Skills、subagents、plugins、`LoadMcpTools` / `CallMcpTool` | 没有跨越已解析工具的通用搜索或渐进披露 |
| 证据 | 工具结果、持久 Run trace、notes、Artifacts | 没有主张、支持证据与矛盾证据之间的有界关系 |
| 权限 | 工具 policy、approvals、hooks、sandbox、Space 与 Run scope | Agent 在行动前无法检查安全的“可用/需审批”能力说明 |
| 影响 | 工具事件、worktrees、Task workspace checkpoints、外部工具结果 | 没有对尝试、确认、可逆与未决影响的统一视图 |
| 验证 | 可以调用测试与领域工具 | 没有把完成声明绑定到验收证据的协议 |
| 连续性 | Sessions、压缩 summaries、状态 checkpoints、Task/TaskRun、workspace checkpoints、排队输入 | Agent 没有关于哪些已持久化、哪些仍是临时内容的紧凑恢复就绪视图 |
| 委派 | subagents、后台 Jobs、Monitor、持久 Task 执行 | 父级没有对未完成工作、重叠、预算与综合就绪状态的统一有界视图 |
| 学习 | 有容量限制和陈旧写保护的 Session notes 与 Project Memory | provenance、重新验证、scope 与主动遗忘语义有限 |

存在基础并不证明把它暴露给模型就有价值。它确实意味着新提案应扩展当前 owner，
而不是创建平行状态。

## 5. 能力类别

### 5.1 目标与验收感知

Agent 需要一个权威、有界的答案来说明：

- 当前 Run 或 Task 应交付什么结果；
- 哪些约束是 invariant；
- 哪些验收标准必须满足；
- 哪些标准已经验证、失败或尚未验证；以及
- 后续用户输入是否修改了契约。

它不是第二段 prompt，也不是 Agent 拥有的 Todo list，而是请求及所属 Task、Issue、
Workflow step 或 Session turn 的投影。Agent 可以提出拆解，但不能静默降低验收标准。

它解决的最常见失败，是 Agent 在错误问题上富有成效地工作，随后按照自己的计划
宣布完成。

### 5.2 运行时与预算感知

Agent 应能检查当前 Run 的已运行时间、迭代预算、当前上下文占用、压缩状态、模型/
工具调用次数和相关 deadline。它必须区分当前上下文占用与累计 prompt token，并把
估算值标记为估算。

这使 Agent 可以停止探索、保存决策、在综合前压缩，或在硬限制前返回部分结果。
自动执行限制仍由 runtime 拥有。

两个候选工具使边界更加具体，但不把名称或 schema 确定为 API。

#### 只读运行时状态

只读 `RuntimeStatus` 工具默认返回小型摘要。可选的任务详情模式可以返回现有且有界的
Todo 状态；它不得查询或重新命名持久 Server Task。

```json
{
  "snapshot": {
    "run_elapsed_ms": 183420,
    "iteration": 12,
    "max_iterations": 50,
    "remaining_iterations": 38,
    "model_calls": 12,
    "tool_calls": 27
  },
  "context": {
    "tokens": 81200,
    "window": 128000,
    "utilization_percent": 63,
    "count_kind": "estimated",
    "measured_at_iteration": 12,
    "automatic_compaction_percent": 80,
    "compactions": 1,
    "compaction_available": true
  },
  "todos": {
    "pending": 3,
    "in_progress": 1,
    "completed": 7
  }
}
```

确切 JSON 留给 design 决策。Proposal 要求以下语义：

- 在四舍五入百分比之外同时返回整数源值，而不是用百分比替代；
- token 数标注为 `estimated`、`provider_reported` 或 `unavailable`；
- 标明上下文快照所属的测量迭代；
- 分开 Run 与 Session 总计；
- 不可用事实报告为 unavailable，而不是零；以及
- 把 Todo 详情标为 Todo 状态，而不是已处理的 Tasks 或 TaskRuns。

结果面向模型编写，可以在接近硬限制时添加一句有界且可执行的提示。Runtime 没有
证据表明阈值与当前任务相关时，不应规定策略。

最近一次准备请求必然只是快照：模型调用状态工具前已经收到了该请求，工具自身结果
还会让下一次请求稍大。未来的下一请求预测只有在避免递归估算自身输出时才有用。

#### 诚实的上下文计量

唯一权威的请求估算器应同时服务于 Agent events、`AgentApp.EstimateRunUsage`、
交互状态、traces 与运行时自省。它应计算 BuildMax 能观察到的所有请求组成部分：

- 有效 system prompt 与压缩块；
- 安全裁剪后的模型可见历史；
- 常驻 memory index 与 Session 状态；
- 可见工具定义及其 schemas；以及
- 估算器所表达的 provider framing 开销。

上次调用的 provider-reported usage 是计量证据，但可能包含 provider 特有缓存或
隐藏 framing，不能静默替代 scope 不同的估算值。一个 Run 可能累计发送 500,000
个 prompt token，而当前请求仅占用 60,000；把前者称为“已使用上下文”是正确性
缺陷。

#### 边界调度的上下文控制

独立的 `ContextCompact` 调用只请求压缩，绝不在 `Tool.Execute` 内改写历史。此时
assistant/tool group 可能仍在执行或等待提交，也可能包含并行同级工具。在这里修改
边界可能拆散必要消息对、与其他工具竞态，或使持久历史和内存历史不一致。

安全候选流程是：

```text
Agent 请求 ContextCompact
  -> 工具记录一个 pending request 并返回
  -> 整个工具调用批次按顺序提交
  -> Agent Loop 到达批次后边界
  -> 请求的压缩通过现有 compactOnce 路径执行
  -> 注入排队用户输入
  -> 下一次请求使用已经提交的压缩视图
```

排队输入位于请求压缩之后，使上一个批次运行期间到达的消息保持为新鲜指令，而不是
在 Agent 看见之前就被总结。即使当前 assistant/tool group 超过正常保留量，也要
作为原子尾部保留。一次自动压缩已经满足 pending request 时，不进行第二次压缩。

该调用不接受目标 token 数、任意消息范围、替换 summary 或 `force` 标志。它只报告
scheduled、already pending、unavailable 或没有有用内容可总结。实际压缩复用现有
checkpoint、`PreCompact` 与 `PostCompact` hooks、计量、summary 截断、event 与
持久提交语义。Summary 失败时保持历史不变；已经产出边界却无法持久化时仍然属于
致命错误，因为继续执行会使持久和内存视图不一致。

自动压缩继续在现有阈值拥有权威。Agent 请求的压缩只是优化提示，其价值与信息丢失
必须单独测量。

### 5.3 能力发现与渐进式工具披露

Agent 应能按意图搜索当前 Run 已解析的能力，检查少量结果，加载所需的精确 schema，
然后通过正常名称与权限路径调用选中工具。

候选生命周期是：

```text
resolved registry：当前 Run 可以知道存在的全部能力
        |
        +-- 始终可见的 kernel 工具
        |
        +-- ToolSearch(query) -> 有界匹配
                                  |
                                  v
                         ToolLoad(选中名称)
                                  |
                                  v
                    下一次请求的可见工具 registry
```

搜索不会安装 plugin、激活 Space integration、连接账户或扩大权限，只发现当前 Run
已经解析的能力集合。

BuildMax 的 MCP gateway 是渐进披露的早期形式：模型收到 gateway 工具，按需加载
一个 MCP 工具的完整 schema。通用设计必须决定扩展这种分发模式，还是把选中工具
提升到直接 LLM 工具列表。暂时看，直接提升更有利于参数质量，并能保留现有工具名、
hooks 与权限语义；它需要 per-run visible-registry state，而不是修改共享缓存 registry。

### 5.4 认知与证据感知

当区别会实质影响后续工作时，Agent 应区分观察事实、假设、推论、矛盾与未知。候选
有界记录如下：

```json
{
  "claim": "the failure is caused by transaction contention",
  "status": "hypothesis",
  "evidence": ["trace:abc#event-27"],
  "contradictions": [],
  "next_check": "reproduce against real MySQL"
}
```

这不是通用知识图谱，而是一组很小的工作主张；否则它们可能被错误提升为事实，或在
压缩后被忘记。证据引用应指向既有 trace event、Artifact、文件、测试结果或外部
记录，而不是把完整内容复制到另一份 store。

### 5.5 权限感知

能力发现必须配套安全的权限说明：

- 无需审批即可使用；
- 审批后可用；
- 被 policy 拒绝；
- 当前 surface 不可用；或
- 依赖参数，只有提出具体调用才能判断。

该视图不得暴露相邻资源或隐藏 plugin。它帮助 Agent 选择权限更小的路径，也避免
反复调用稳定拒绝的能力。拒绝仍然具有权威；Agent 不能把解释重新解读成授权。

### 5.6 影响与可逆性感知

在关键行动前后，Agent 应知道自己准备改变什么、runtime 观察到了什么、影响是否
确认，以及能否回滚或安全重试。

```json
{
  "kind": "external_comment",
  "target": "current_issue",
  "status": "confirmed",
  "reversible": false,
  "idempotency": "unknown"
}
```

Effect ledger 应从权威工具边界与 domain 转换推导，而不是来自 Agent 叙述。它无需
把无关影响伪装成事务原子性。它的价值是防止重复副作用、区分文件变更和已发布状态，
并在重试或完成声明前暴露未决结果。

### 5.7 验证与完成感知

Agent 不应把实现动作等同于请求结果：

```text
写入文件              != 行为正确
命令退出码为零         != 相关边界得到测试
HTTP 返回 success      != 持久状态正确
生成了 Artifact        != 人可以使用它
Agent 自拟 Todos 完成  != 用户验收得到满足
```

完成协议应要求 Agent 把每项权威验收标准绑定到证据，或明确标为尚未验证。根据风险，
确定性检查或独立 verifier 可以质疑该声明。系统应允许诚实的部分结果，而不应迫使
Agent 为了进入终态捏造确定性。

这可能是价值最高的缺失契约。它闭合了运行时自省与 Tool Search 只能帮助执行的循环。

### 5.8 连续性与恢复感知

Agent 应知道哪些内容能在压缩、取消、worker 丢失或恢复后存活：

- 目标与约束；
- 已提交的 notes 与 Todos；
- 压缩边界与 summary；
- 持久 workspace checkpoint；
- 已确认的外部影响；以及
- 仍只存在于活动上下文中的临时事实。

这不需要另一种 checkpoint，而需要在已经拥有持久性的 Session、TaskRun 与 workspace
机制上建立有界的 readiness projection。恢复路径应从已提交事实继续，并在重试前
识别不确定副作用。

### 5.9 委派与协调感知

父 Agent 需要子工作的有界视图：目标、状态、剩余预算、结果是否可用、是否重叠，
以及能否开始综合。默认不应接收每个 child 的完整上下文。

没有该视图，多 Agent 执行会放大不确定性：父级等待已经完成的 child、重复委派工作，
或在关键结果到达前开始综合。Runtime 拥有 child 生命周期与取消；父级在配置限制内
选择语义拆解与综合。

### 5.10 学习、重新验证与遗忘

持久 memory 应携带 provenance、scope 与继续有用的理由。Agent 需要知道记忆事实
何时陈旧、存在矛盾或超出当前 Project，并能在现有 store 的并发与容量规则下提出
替换或删除。

更多 memory 不会自动带来更高智能。无限累积会让过时结论永久保持显著。主动遗忘
和重新验证是能力，而不是“真正”memory 系统之后的清理工作。

## 6. Runtime 与 Agent 权威

这个能力家族遵循一条 ownership 规则：

> Runtime 事实与转换留在现有确定性 owner。Agent 接收有界投影，做出语义判断，
> 并提交可由 owner 验证、拒绝、提交和记录的请求。

| 主题 | Agent 可以 | Agent 不可以 |
|---|---|---|
| 目标 | 重述、拆解、指出歧义 | 静默改写用户约束或验收 |
| 运行时预算 | 检查并调整策略 | 提高限制或伪造计量 |
| 工具 | 搜索并请求可见 | 安装、激活或自行授权能力 |
| 证据 | 把主张与引用关联 | 把推论转成观察事实 |
| 权限 | 检查有界可用性并请求审批 | 通过其他 transport 绕过拒绝 |
| 影响 | 预览、通过工具执行、验证 | 宣称不确定外部影响已经提交 |
| 完成 | 提交带证据声明 | 仅以自拟 Todos 完成定义成功 |
| 恢复 | 通过受支持机制 checkpoint | 捏造 store 未提交的持久状态 |
| 委派 | 提议工作并综合结果 | 超出 roster、预算、深度或权限限制 |
| Memory | 读取、提出写入/删除、重新验证 | 积累无界或跨 scope 知识 |

这种分离允许模型能力提高，同时不会让更强模型成为事务日志、授权服务、配额账本或
恢复协调器。

## 7. 产品与工具形态

这些能力类别不应变成十个常驻工具。正确 surface 取决于 Agent 需要信息的频率，以及
操作是否改变状态。

| 形态 | 适用情况 | 候选示例 |
|---|---|---|
| 有界常驻投影 | 下一步决策缺少它就不安全 | 活动目标、硬约束、当前 Todo |
| 按需只读工具 | 详情偶尔有用且消耗上下文 | 运行时状态、Tool Search、证据引用、effect status |
| 独立控制请求 | 操作有损、计费或改变状态 | 压缩上下文、加载工具 schema、请求审批、checkpoint |
| 确定性完成 gate | 正确性不能依赖模型自律 | 验收—证据检查、未决 effect 检查 |
| 用户或 supervisor 升级 | 缺少权限或歧义会改变结果 | 澄清目标、批准 effect、选择权衡 |

一个万能 `Reflect` 工具是错误抽象。它的输出是模型 prose 而不是权威事实；随着 action
累积，权限语义会变得不清楚；测试也无法判断究竟哪类能力失败。

每轮注入全部状态、工具目录、主张、影响与 child 记录同样错误。它会在每次调用消耗
上下文和注意力，并削弱可缓存 prompt prefix。渐进披露不仅是 token 优化，也是
正确性模型的一部分。

共享工具 registry 不能保存某个 Session 或 Run 的可变状态。暂定合适的形态是：
由 `internal/core/agent` 拥有 runtime-facing interface，并通过当前调用的
`context.Context` 携带。Agent Loop 在发出 events 的同一转换上写入事实；handle
只是投影，不是第二个 owner。现有 Note 与 memory 工具已经展示了这种 layering。

Per-run 投影只保留有界临时状态：单调时钟的开始时间、当前与最大迭代、本 Run 计数、
最新请求上下文快照、压缩次数与 pending bit，以及在可用时访问当前 Todo store 的
能力。只读工具可能与其他只读工具并行，因此需要不可变 atomic replacement 或 mutex。
控制请求即使立即修改的只是 pending bit，也属于 write-class 调度屏障；真正转换由
Agent Loop 执行。

同一区别适用于 Tool Search。Resolved registry 是已经为当前 Run 组装并授权的完整
能力集合；visible registry 是单次模型请求发送的较小投影。加载工具在迭代边界改变
后者，绝不修改共享缓存 registry。

候选权限行为说明了为什么读取与控制 surface 必须分开：

| 候选能力 | Access | 默认方向 | 约束 |
|---|---|---|---|
| runtime status | read-only | allow | 仅当前 Run；可安全并行读取 |
| Tool Search | read-only | allow | 仅搜索已经解析且可安全披露的能力 |
| tool load | write-class 调度屏障 | allow | 只改变下一次请求的可见定义 |
| context compact | write-class 调度屏障 | 尚未决定 | 有损且计费；runtime 回收下限和 hooks 仍适用 |

每次压缩都要求交互审批会使该能力无法用于 worker；允许所有提前请求又可能浪费成本
和细节。一个候选 runtime invariant 是：只有旧材料足以回收达到最小有效量的上下文
时才允许。该决策属于聚焦 design 与 evaluation，而不是模型 prompt。

Surface 只暴露自身能够提供的控制。没有 compactor 的 loop 仍可提供状态，但省略
上下文控制。元工具不接受调用方选择的 Session、Task、user 或 Space 标识符；scope
来自活动 Run，使模型不能枚举相邻工作。

元工具输出排除原始指令、压缩 summary、notes、memory 正文、消息内容、Secret 值、
环境变量、隐藏路径、其他 Run 的身份或成本，以及进程级健康详情。普通工具 events
记录自省或控制请求；不得用新的未脱敏 trace 格式复制返回快照。

## 8. 优先级与候选工作流

重要性与实现顺序并不相同。目标与验证处于语义中心；运行时状态和 Tool Search 可能
是成本更低的实验，因为 BuildMax 已经拥有它们的大部分输入。

建议的决策顺序：

1. **目标与完成契约。** 定义权威目标、Agent 自拟计划、验收标准、证据与部分/
   完整结果之间的关系。
2. **运行时自省。** 测试模型在获得诚实预算与上下文状态后能否合理切换阶段，再
   单独评估边界调度的 Agent 请求压缩。
3. **能力发现。** 先将渐进披露与最佳固定工具基线比较，再设计通用目录。
4. **影响与权限投影。** 在不弱化现有权限边界的情况下，使计划与确认的副作用可见。
5. **恢复就绪。** 投影哪些状态已持久化，以及中断后仍有哪些影响不确定。
6. **委派协调。** 只有持久或并发 child 工作证明父级可见性缺口后才添加。
7. **认知记录与 memory 生命周期。** 只为必须跨压缩或 Session 存活的主张添加；
   在有界形态证明不足前，不建设通用知识底座。

候选工作流应能分别接受或拒绝：

- 运行时自省与上下文控制；
- 工具发现与渐进披露；
- 目标、证据与结果验证；
- 影响追踪与重试安全；以及
- 恢复与协调投影。

本 proposal 提供共同原则与评估语言，不应让接受一个工作流自动意味着接受其他工作流。

## 9. 选项与权衡

| 选项 | 收益 | 成本或失败 |
|---|---|---|
| A. 用 prompt 要求模型更多反思 | 几乎不需要 runtime 工作 | 产生更多 prose，却没有权威状态、证据或执行 |
| B. 根据需求逐个增加孤立工具 | 局部变更较小 | 重叠 scope 与矛盾事实来源逐渐累积 |
| C. 添加一个通用自我管理 API | 看似只有一个概念 | 变成模型拥有的控制平面，并混合读写、权限与持久语义 |
| D. 每轮注入完整 self-model | 始终可用 | 持续上下文与注意力成本高；快速变化状态破坏缓存 |
| E. 定义类型明确的能力类别，再暴露最小常驻、查询、控制与 gate surface | 权威一致，各切片可独立测试 | 需要跨域设计纪律，并在广泛实现前取得证据 |

暂定建议是 E。Occam's razor 同样适用于其内部：现有 event、Todo、Task transition、
checkpoint 或权限规则已经拥有事实时，添加投影或引用，而不是另一条记录。

具体到运行时自省切片：

| 选项 | 收益 | 成本或失败 |
|---|---|---|
| 状态仅面向用户并依赖自动压缩 | 没有新模型 schema | Agent 继续猜测剩余预算，也不能请求感知阶段的提前压缩 |
| 每次请求注入实时状态 | 无需发现调用 | 持续上下文与注意力成本；快速变化数据损害缓存 |
| 把状态和压缩合并为一个带 action 的 `Runtime` 工具 | 只有一个工具名 | 混合读写语义，形成不断扩张的控制杂物箱 |
| 同时暴露独立的状态和压缩工具 | 权限与行为清晰 | 在测量任一能力前假定两者都值得付出成本 |
| 先测试只读状态，再独立接纳请求压缩 | 最小初始变更面 | 延后取得按阶段提前压缩的证据 |

优先选择最后一个。接受观察能力不能静默批准有损控制。

## 10. 风险与失败模式

### 10.1 反思循环消耗它所检查的预算

Agent 可能反复调用状态、搜索、批评或验证工具而不行动。工具描述、loop guard、有界
输出与 evaluation 应测量轮询和元工作占比。泛化的“始终反思”要求很可能有害。

### 10.2 自我报告变成虚假权威

Agent 自己撰写的 confidence、completion、effect 或 permission 声明不能覆盖
runtime 记录。所有投影都要区分 observed、provider-reported、inferred、proposed
与 unavailable。

### 10.3 能力搜索变成能力获取

Tool Search 不得安装 plugin、激活 integration、连接账户或泄露被拒绝的相邻能力。
这些属于搜索契约之外的用户或管理员决定。

### 10.4 替代工具绕过稳定拒绝

搜索会让 Agent 更容易找到达到相同外部影响的第二条路径。因此权限要在每个工具
边界与 effect scope 执行，而不只检查 Agent 首次尝试的工具名。

### 10.5 Effect ledger 承诺了并不存在的原子性

共同记录两个 effect 不会使其成为事务。每个条目保留自己的 owner、确认语义、
可逆性和幂等性。Ledger 是推理与审计投影，不是分布式 commit log。

### 10.6 验证奖励简单检查

Agent 可能选择便宜的 passing test，而不是与验收边界相关的证据。验证必须从权威
标准出发并说明未测试限制；测试数量或退出码本身不是证明。

### 10.7 持久认知变成永久污染

缺少 provenance、scope、容量、重新验证与删除的主张和 memory 会不断制造错误。
默认应为临时；持久存储必须证明自己的成本合理。

### 10.8 更多元能力遮蔽用户体验

用户不应为了请求工作而理解内部自我调节机制。Surface 详情属于 trace 和诊断；
普通结果应以自然语言展示决策、重要影响、证据与限制。

### 10.9 运行时控制破坏它所检查的状态

运行时自省与控制存在几个必须由聚焦 design 保护的完整性失败：

| 失败 | 必须具备的行为 |
|---|---|
| 状态结果自身增加上下文 | 说明快照 scope，并保持默认结果小型 |
| 估算值看起来像精确值 | 返回精度与测量迭代 |
| 并行批次中请求压缩 | 记录同步请求；完整批次提交后才修改 |
| 排队输入在被看到前得到总结 | 在 pending-input 注入前执行此前请求 |
| hook 阻止压缩 | 返回有界拒绝并保持历史不变 |
| summarizer 失败 | 报告失败并保留原始历史 |
| 压缩边界无法持久化 | 停止，而不是让持久与内存视图不一致地继续 |
| surface 没有 compactor 或上下文窗口 | 省略控制或报告 unavailable；绝不捏造零值 |

现有自动压缩路径继续充当安全网。模型没有检查状态或请求提前压缩，不能导致 runtime
放弃自身硬保护。

## 11. 所需证据

每个工作流都应与最强的简单基线比较，而不是故意装备不足的 Agent。

### 11.1 场景类别

- 必须在紧张上下文或迭代限制下从探索切换到综合的长代码库调查；
- 包含多个看似合适但权限不同能力的大型工具目录；
- 具有明确验收标准和诱人但不足测试的任务；
- 关键操作超时或外部结果不明确的任务；
- 同时包含持久与临时状态的中断/恢复 Run；
- 包含重叠、分歧、迟到结果与部分失败的委派工作；以及
- Project Memory 中包含陈旧或矛盾事实的任务。

### 11.2 结果指标

- 用户验收是否满足，而不只是 Agent 自报完成；
- 重复或不必要工作；
- 缺少支持的主张与遗漏的矛盾证据；
- 过早完成与未报告验证缺口；
- 未授权或重复副作用；
- 中断后的恢复正确性；
- 模型调用、prompt/工具定义 token、已运行时间与成本；
- 元能力调用次数及其所占迭代比例；以及
- 向用户升级求助的频率与质量。

### 11.3 架构 invariant

- 每项事实与转换只有一个权威 owner；
- 元能力不会披露原始 Secret、指令、memory、相邻资源或隐藏工具；
- 一个 Run 不会修改共享缓存 registry；
- 工具调用组与压缩边界在并发下保持有效；
- 状态缺失不会被报告为零；
- Agent 不能扩大自身限制、权限、plugin activation 或持久 scope；以及
- 每项完成声明与关键 effect 都能引用权威证据，或明确说明缺少证据。

### 11.4 候选分阶段实验

各工作流仍可独立否决，但实用的实验顺序可以复用证据，而不一次引入所有元能力。

**Stage 0——观察基线。** 统一 `EventLLMStart`、`EstimateRunUsage`、traces、交互
状态、system prompt、常驻状态、历史与工具 schemas 之间的上下文估算。在没有任何
LLM 状态或搜索能力时，记录长脚本 Run 结果。

**Stage 1——只读运行时状态。** 测试并发读取、取消、未知上下文窗口、缺失 Todo
store、恢复 Session、Conversation 历史、subagents 与 worker 组装。测量小模型和
大模型是否能区分当前占用与累计用量，并在有用时机切换阶段，而不只是复述数字。

**Stage 2——能力搜索。** 比较固定直接工具集、现有 MCP gateway 模式和“搜索后直接
提升”。测量定义 token、额外发现 turn、工具与参数选择正确性、无效搜索、权限感知
选择，以及搜索无结果时的行为。

**Stage 3——边界调度压缩。** 覆盖重复请求、并发同级工具、自动/请求压缩冲突、排队
输入、hook 拒绝、summarizer 与持久化失败和取消。测量回收上下文、增加成本、过早
压缩、信息丢失、重复工作，以及 checkpoint 后的 notes 与 Todos 是否保留综合所需
内容。

**Stage 4——目标与验证契约。** 在“简单 passing check 不足”的任务中要求明确验收
标准与证据。与最佳普通 Agent 基线比较完成正确性、诚实部分结果、遗漏验证限制、
升级求助质量、成本与延迟。

只有早期证据识别出相应失败时，才接纳后续 effect、恢复、委派和 memory 实验，不能
把它们视为接受整个能力家族后自动产生的后果。

## 12. 目标与非目标

目标：

- 为 Agent 自我调节能力建立共同词汇；
- 明确哪些事实与转换继续由 runtime 拥有；
- 识别最小、高价值工作流及其依赖；
- 防止运行时自省与 Tool Search 成为孤立功能岛；以及
- 定义可以否决“复杂度超过收益”能力的证据。

非目标：

- 批准实现或路线图优先级；
- 定义最终工具名、JSON schema、数据库表或 UI；
- 暴露模型 chain-of-thought；
- 创建通用 planner、critic、知识图谱或控制平面；
- 让每项能力在每个 surface 都可用；
- 在目标模糊或权衡后果重大时替代用户判断；或
- 推断更多 autonomy、memory、tools 或 Agents 必然更好。

## 13. 开放问题

1. 能同时适用于本地 Session turn 和持久 Task、又不让二者互相拥有的最小目标与
   验收契约是什么？
2. 完成验证应由工作 Agent 内部执行、独立 verifier 执行、确定性标准执行，还是
   根据风险组合？
3. 哪些工具必须保留在始终可见的 kernel 中，使 Tool Search 失败也不会困住 Agent？
4. Tool Search 应在不提供详情的情况下披露被拒绝能力的存在，还是应完全省略，避免
   信息泄露与无效规划？
5. Effect scope 能否跨文件、Bash、MCP、Issues、消息和未来 integrations 一致表达，
   同时不假装它们共享事务模型？
6. 哪些认知主张值得进入持久存储，而不只是普通 notes 或压缩 summary？
7. Runtime 应在何时要求 recovery-readiness 或 outcome-verification 检查，何时这种
   仪式会损害简单对话工作？
8. 父 Agent 如何在不加载全部 child trace 的情况下识别重复或冲突工作？
9. 哪些自我调节事实应出现在普通用户结果中，哪些只属于 trace 和诊断视图？
10. 在 token 或 iteration 中，元工作占比达到多少才说明它是自我观察开销而非有用
    控制？
11. 最近一次准备请求的上下文快照是否足够，还是模型需要单独标注的下一次请求预测？
12. 运行时状态应暴露已完成 Todo 文本、仅数量，还是最近的有界子集？哪项已证实的
    决策需要这些详情？
13. 允许 Agent 请求压缩的最小可总结 token 数或可回收上下文比例是多少？因为操作
    有损且计费，无人值守 Agent definition 是否必须显式启用？
14. 没有 deadline 时，已运行时间能否改善行为？还是只有真实 deadline 存在时才应
    让 Agent 看到剩余时长？

## 14. 可能归宿

本 proposal 的 primary domain 是 **Agent Runtime and Models**，相关问题涉及 Product
and Execution Model、Trust and Security 与 Verification。

如果其框架获采纳：

- 持久的跨域原则进入聚焦设计记录或现有[产品愿景](../design/产品愿景.md)；
- 每个独立有价值的工作流获得自己的设计决策、证据计划、路线图位置与 backlog tasks；
- Agent Loop 与工具架构文档只描述已交付 runtime 边界；
- 用户手册只描述用户确实能够调用或配置的能力；以及
- 获采纳理由移入权威记录后删除本 proposal；如果证据否决整个能力家族框架，也直接删除。
