## 用户结果与证据

用户进入一个工作区，以聊天或语音告诉 Agent 目标，检查工作与证据，并有意识地
允许它代表自己使用选定应用。Desktop 可能成为这样的入口：对话是主线，工作区
是组织单元，文件、终端、浏览器和连接的应用都是可查看的界面。这是产品讨论中
的假设，并非已测量的使用事实。普通人的工作或许集中在少数应用，但我们尚无
证据证明人们偏好单一 Agent 入口，或愿意在工作、个人和敏感场景中委托同样的操作。

第一项实验比 Desktop 改版更窄：用户能否连接一个应用、允许两项有用的读取、
理解并批准一次草稿写入、看到结果？先验证委托边界，再决定 Desktop 形态。

## 当前约束

BuildMax 已有本地插件、Skill、MCP 工具、工具权限和供 BuildMax 登录使用的
系统凭证存储，但没有通用的应用连接契约。Skill 可以描述 CLI 用法；直接使用
`curl` 虽灵活，却让每份 Skill 重复处理 HTTP、OAuth 刷新、响应和密钥。MCP
提供类型化工具，但各应用仍需服务端和授权配置。应用 API 可能覆盖不全、不开放、
限流，或受服务商审核约束。UI 自动化是另一种后备方案，可靠性与同意方式不同。

本地 Agent 的 Bash 沙箱默认关闭。具有无限制 shell 与网络权限的模型，可以绕过
连接器 CLI，或者以用户身份调用它。单靠 YAML 白名单不是 Agent 安全边界。
隔离、进程内工具代理以及可撤销的单次运行授权，需要单独设计。

## 目标与非目标

目标是一条易懂的连接流程；由可信插件限定名称与范围的操作；凭证与插件、
工作区分开保存；用户可见的写入意图；可追查的结果；以及关于 Desktop 控制点
的用户证据。

本文不承诺万能 API 适配器、任意 OpenAPI 执行、无人值守写入、兼容所有 OAuth
服务商，也不声称本地 shell 权限已经能强制执行应用委托。连接是用户和服务商的
凭证关系；插件提供公开操作契约；授权是另一项运行时决定。无需把每个应用都
建成新的 BuildMax 实体。

## 委托的完整生命周期

1. **发现：** 用户查看插件来源、服务商、申请的 scope、API 主机、操作和影响。
   安装插件本身不授予访问权。
2. **连接：** 用户在外部浏览器完成带 PKCE 的 OAuth 授权码流程。令牌存于
   工作区之外。服务商的 scope 是可访问范围的外边界。
3. **授权：** 工作区或运行向 Agent 授予声明操作的子集。插件不能给自己授权。
   读取和写入可采用不同批准要求；原型尚未完成此步骤。
4. **执行：** 运行时固定目标地址、方法与操作名，校验输入、刷新令牌、应用
   策略并记录结果。写入前显示意图。服务商拒绝或超时后，用户能看到错误并重试
   或重新连接。
5. **查看与撤销：** 用户查看近期调用、停用授权、在本地断开连接，并可在服务商
   撤销访问。令牌被撤销后，后续调用必须停止；已完成的效果可能需要补偿操作。
   原型尚未提供这些控制。

Desktop 应把 Agent 提议的操作、来源对话和结果放在一起。语音可以发起请求，
高影响操作的批准仍需视觉方式或同等明确的确认。终端、文件、应用界面应能供
用户检查，而无需用户手工完成每一步。

## 方案与权衡

| 方案 | 优点 | 成本或边界 |
|---|---|---|
| 各应用的 MCP 服务端 | 类型化工具能接入现有运行时权限 | 重复安装、管理凭证和服务生命周期 |
| MCP 支撑的 CLI 加 Skill | 复用现有 MCP 服务；CLI 按需发现，Skill 表达工作流程 | MCP 服务质量与认证方式不同；单靠 CLI 调用无法强制执行 Agent 授权 |
| Skill 加原始 `curl` | 灵活、可移植 | HTTP 与密钥处理重复散落在提示词中，集中审计较弱 |
| 声明式连接器加 CLI，后续加入代理层 | 沿用 Skill，统一连接流程和固定操作 | 需要刻意收窄格式，并借助运行时策略才能安全 |
| UI 自动化 | 能接入缺少合适 API 的应用 | 界面状态脆弱、权限更宽、验证更难 |

原型选择在既有插件内声明连接器。`connector.yaml` 描述 OAuth 端点、客户端 ID
环境变量、scope、一个 API origin 和固定的 GET/POST 命名操作。它不包含令牌、
工作区授权、脚本或任意 URL。Skill 可以用 CLI 读取；写入需要终端确认。这是
界面与易用性的实验，不是已加固的 Agent 权限模型。

## 以应用为入口的连接器方向

下一项假设是把应用作为用户连接的稳定单元。`buildmax connect gmail` 查找经过
审查的连接器插件，展示服务商、申请的权限、操作和来源，再连接一个账户。安装
插件代码与授权服务商是两个明确的状态转换，即使一条命令引导用户完成两者。
`buildmax app gmail <operation> --json ...` 为人、Agent 和 Skill 提供相同
的 CLI 表面；内部可以使用 MCP、HTTP 或 gRPC。现有的 `buildmax connect mcp
<name> <url>` 是以传输协议为入口的实验，不是预期的应用入口命令。

一个插件可包含精简的 `connector.yaml` 声明、文档和可选 Skill。声明给出应用、
连接方式，以及具有稳定名称、输入输出形状和影响类别的操作。传输部分把操作
绑定到 MCP 工具、固定的 HTTP 方法与路径，或带有 protobuf 描述文件引用的
gRPC 方法。Skill 描述这些操作之上的任务步骤与判断。YAML 不包含实时凭证、
用户授权、shell 命令或任意可执行表达式。`buildmax connector new gmail
--transport http` 这样的脚手架命令可生成声明、Skill 样例、夹具测试和供插件
市场发布的元数据；确切语法仍待确定。

简单连接器可以主要靠声明创建，但 YAML 不能独自覆盖各服务商的 OAuth 差异、
分页、流式传输、二进制内容、重试和特殊 API 语义。第一版契约应围绕已经证明
有用的工作流程，只在遇到实际缺口时引入经过审查的扩展点。gRPC 需要 schema
来源，流式方法可能还需要专门支持。服务商 scope 是外层权限；实际调用入口还
必须强制执行账户选择、声明操作、单次运行授权、批准与脱敏审计。插件的
`effect` 字段和 MCP 服务端的只读标注都只是需要审查的声明，不能自行授予权限。

最有力的比较是让同一个任务通过两种传输实现，但保持相同的 `connect` 和
`app` 命令。测量配置耗时、schema 变化、凭证恢复、Agent 调用准确率，以及
用户能否理解授予了哪些操作。如果共同界面无法通过这个测试，说明抽象范围
过大或位置不对。

## 窄原型

示例 `gmail-connector` 声明两项读取（`profile`、`list_messages`）和一项
草稿写入（`create_draft`）。`buildmax connect gmail-connector` 通过本机回调
完成带 PKCE 的 OAuth；`buildmax app gmail-connector <operation>` 执行固定操作。
令牌默认放在操作系统凭证存储；明确设置 `BUILDMAX_CREDENTIAL_STORE=file`
时，才写入权限为 0600 的文件。示例需要用户自己的 Google 桌面 OAuth 客户端
ID 与 Gmail API 配置。相关 scope 可能需要 Google 审核；自动化测试没有使用
真实 Google 账户。Google 的 `gmail.compose` scope 还允许发送邮件，因此服务商
令牌的权限大于本连接器仅创建草稿的写入能力；本地 Bash 未隔离时尤需注意这道落差。

本地假服务测试覆盖回调 state、PKCE、令牌刷新、分离存储、两项读取、批准写入、
拒绝未声明操作和未批准写入，以及不安全 URL。原型尚无单次运行授权、持久调用
审计、断开连接、多账户、跨服务商写入预览或 Desktop 批准界面。这些都是证据
边界，不能当作已实现的承诺。

第二个本地原型检验 MCP 路径：`buildmax connect mcp <name> <url>` 检查远端
HTTP/SSE 端点并写入用户的 `mcp.json`；`buildmax mcp tools|schema|call`
通过现有 MCP 运行时在 CLI 中发现和调用工具。静态 Bearer token 可从指定环境
变量读取，不存入配置。CLI 每条命令建立新会话；除非服务器标注工具只读，否则
调用需终端确认。MCP OAuth、持久会话、单次运行授权和持久审计尚未实现。选择
主要连接路径前，应在同一用户工作流程中比较这两个原型。

## 待回答的问题与决策证据

对一个重复的真实工作流程观察 5 至 10 次使用，包括一次授权失败和一次写入
内容改变。记录用户是否找到连接入口、是否理解 scope 与具体写入、能否指出
哪个工作区和 Agent 拥有访问权，以及能否从令牌过期、服务商拒绝和部分成功中
恢复。统计委托调用与手动切换应用，并询问切换原因。对实际任务检查 API 覆盖，
不要猜测“大多数应用都有可用 API”。

开放问题：授权应绑定单次运行、工作区还是持久 Task；本地 shell 如何与凭证和
网络隔离，只能通过代理层访问；需要何种审计保证；多账户与组织策略如何组合；
API 和 UI 自动化如何共享面向用户的批准模型；哪些应用值得做第一方连接器。
加固版本应验证撤销、最小权限、令牌不可外泄，以及面对恶意工具输出时的授权。

## 可能的归宿

如果使用证据支持这一流程且用户理解控制方式，就把被采纳的授权与执行契约
移到 `docs/design/`，在 `docs/ROADMAP.md` 排期，并把连接与批准流程纳入
Desktop 入口设计。如果现有 MCP 工具或普通应用切换更适合观察到的任务，
就退役本提案，仅保留经过验证的窄能力。
