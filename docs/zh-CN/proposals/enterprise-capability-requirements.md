## 用户结果与当前约束

企业应能让团队持续使用 Agent，同时控制身份、权限、数据、执行和成本，并通过
责任明确的运维流程从故障中恢复。

本文盘点企业部署中常见的候选要求，以便需求调研结合真实环境逐项验证。它不定义
企业版，不为付费分发预留任何能力，也不对商业化、产品打包、定价、许可或服务作
出建议。这份清单不代表需求已获验证，不是路线图承诺、发布检查清单，也不描述已
交付行为。

BuildMax 仍处于 Alpha。路线图的目标是面向私有网络中一个受信任 Space 的可靠
私有部署 Beta；SSO 不属于该门槛。现有 Space 边界与共享 Agent 运行时仍是起点
约束。任何经验证的要求都必须保留独立本地使用能力，也不能引入另一套执行或授权
归属。

## 目标与非目标

目标是为需求调研提供具体词汇，识别功能列表经常遗漏的生命周期和失败场景，并明确
将候选要求提升为已采纳产品要求所需的证据。

非目标包括划分社区版与企业版功能、批准企业版、提出商业模式建议、修改价格或许可、
调整路线图、创建实施待办或承诺生产就绪。本清单不授权新增组织层级、自定义策略语言、
许可证服务器或独立运行时。每个新增概念都必须对应现有概念无法满足的具体要求。

## 候选要求清单

以下是针对目标企业部署需要评估的候选结果，并非适用于所有部署的最低要求。所需的
控制深度取决于部署的用户、运维模式和威胁模型；每项获采纳要求都需要可度量的验收测试。

| 类别 | 候选能力 | 验收问题 |
|---|---|---|
| 身份与人员管理 | 企业 SSO、停用账户、撤销 Session、有文档的入离职流程，必要时自动化 | 员工能否通过企业身份系统加入，并在离职后及时失去访问权？ |
| 授权与隔离 | Space 或团队角色、资源隔离，自动化需要时提供服务账号及可限定范围、可撤销的 API 凭证 | 用户或 Agent 是否只能访问工作授权允许的资源与凭证？ |
| 审计与追责 | 登录、权限变更、配置修改、凭证使用元数据和执行记录；授权查询、导出或按需外部采集 | 运维能否还原谁授权、谁执行，并识别证据缺失？ |
| 数据与密钥 | 保留与删除规则、脱敏、传输和凭证存储加密、轮换，明确存储位置和模型提供方去向 | 能否说明数据流向、按策略删除数据并替换失陷凭证？ |
| Agent 执行治理 | 模型、工具、插件准入；强制执行边界；按需限制网络目的地；必要时审批高风险操作；取消和紧急暂停 | 能否约束执行并停止后续工作，同时明确控制的限制？ |
| 用量与成本 | 按运维所需维度归属用量；预算或配额、告警、并发和速率限制 | 能否归属消耗、限制无人值守用量，并解释拒绝或超额行为？ |
| 运维与恢复 | 监控告警、备份恢复、升级回滚、故障诊断、有文档的部署流程和运维责任 | 运维能否发现故障、恢复数据与执行状态，并维护部署？ |

执行 trace 本身不等于权限审计，配额计数器不等于严格的金额预算，多个副本的部署
清单也不等于高可用验收。每项承诺都需要覆盖完整行为的证据。审计记录不得暴露
密钥值。

## Agent 生命周期要求

需求调研与后续验收测试应覆盖状态变化，而不仅是管理界面：

- 员工被停用时，明确现有 Session、API 凭证、排队或运行中的 TaskRun、定时任务
  如何处理。区分阻止新工作与取消正在执行的工作。
- 成员失去 Space 访问权时，明确待执行和运行中工作的授权方式，以及结果是否仍
  可访问。继续 Task 不能悄然继承调用者已失去的权限。
- 需要审批时，将审批绑定到预期操作及相关参数，并定义变更、过期、重试和失败时
  的失效规则。聊天中的一句“同意”不足以构成完整授权机制。
- 模型、插件、工具或密钥被撤销时，明确生效时点。遵守按运行解析和插件版本固定
  的约束，不向正在运行的 Agent 悄然热加载另一套环境。
- 用量达到上限或运维暂停执行时，明确新任务准入、正在进行的调用、取消、部分
  结果和允许的有限超额。取消无法撤回已经完成的外部操作。

这些问题应在对应设计中解决；不代表现有生命周期行为都缺失，也不代表每次状态
变化都必须停止所有工作。

## 条件性要求

以下候选项只有在目标部署提供相应证据时才成为要求。

| 候选能力 | 使其成为必要项的证据 |
|---|---|
| SCIM 或目录同步 | 人工入离职处理无法满足部署规模或访问撤销要求 |
| 同时支持 SAML 与 OIDC | 目标身份系统确实需要两者；初始部署可能只需可用的一种集成 |
| 自定义角色与跨 Space 管理 | 固定角色和现有 Space 管理无法表达已证实的职责划分 |
| 外部密钥提供方与工作负载身份 | 有明确的凭证系统或短期凭证要求；遵循路线图既有的密钥能力顺序 |
| SIEM 投递、可发现篡改的审计与特殊保留控制 | 明确的调查、保留或安全要求超出现有审计机制 |
| 高可用与多地域恢复 | 有文档的可用性、恢复时间与恢复点目标；基础恢复能力仍是基本要求 |
| 完全离线部署 | 目标环境禁止外部依赖，包括模型调用或更新服务 |
| 认证、正式鉴证报告或响应目标 | 有文档的治理或运维要求，且组织能够持续提供所需流程和证据 |

部署所声明的边界需要哪些安全控制，就必须提供哪些控制；不能仅因为只有部分环境
需要相关集成而推迟必要的安全保障。

## 要求评估

需求调研应逐项独立分类候选要求。分类只关乎证据和范围，不关乎产品打包。

| 分类 | 证据门槛 | 后续处理 |
|---|---|---|
| 已验证要求 | 有明确名称的用户或运维历程、当前约束和可度量的验收测试 | 通过路线图和归属设计评估是否采纳 |
| 条件性要求 | 只对有文档记录的部署、身份系统、威胁模型或运维目标成立 | 明确保留条件，不泛化到所有安装环境 |
| 当前无充分依据 | 没有观察到任何流程或约束会因缺少它而失败 | 暂不建设；有价值时将证据缺口保留为开放问题 |

优先选择满足已证实结果的最小控制集合。新增实体、层级、策略语言或管理界面之前，
先指出现有概念无法通过的确切验收测试。

## 问题与证据

访谈潜在企业团队，记录使用场景、用户和运维人员、部署环境、阻碍条件、威胁模型、
验收测试，以及要求未满足时的后果。优先采用成功和失败标准明确的有限试点，不从
其他项目的功能列表推断自身需求。

开放问题包括：先研究哪些部署类型，什么阻碍今天的部署，人员变化后谁负责无人值守
工作，哪些控制普遍适用、哪些依赖具体环境，以及运维如何证明恢复、撤销和成本控制
结果。

可能的首个调研范围是把企业登录与访问撤销接入现有授权和审计生命周期。执行与用量
控制按已证实的缺口推进。这是需求调研假设，不是另一套优先级队列；当前 Beta 工作
仍由路线图管理。

采纳要求前，应有明确的历程和责任人、归属与失败行为清楚的有限实现范围，以及承诺
的部署和生命周期结果的验证证据。未解决的假设保持显式记录。

## 采纳后的归宿

已验证的优先级进入路线图，长期决策进入对应设计记录。获批且已分解的主线工作进入
backlog；行为交付时再更新运维文档。当有价值的要求都已依据证据被采纳或拒绝后，将
长期理由移入归属文档，并按文档规范退役本清单。
