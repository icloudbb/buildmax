## 用户结果与当前约束

企业应能让团队持续使用 Agent，同时控制身份、权限、数据、执行和成本，并通过
责任明确的运维流程从故障中恢复。

本文盘点企业部署中常见的候选要求，以便需求调研结合真实环境逐项验证。它不定义
企业版，不为付费分发预留任何能力，也不对商业化、产品打包、定价、许可或服务作
出建议。这份清单不代表需求已获验证，不是路线图承诺、发布检查清单，也不描述已
交付行为。

BuildMax 仍处于 Alpha。企业部署、系统管理、治理与执行控制已是正在推进的产品工作。
企业 SSO 已有获采纳的设计：持久 Session 与 OIDC 登录/关联切片已经实现，Okta 是明确
的首个提供方，资格验证仍未完成。哪些切片已经实际交付，仍以当前代码和当前状态文档为准。
因此，本提案不重新讨论是否建设 SSO，也不重复其协议设计，而是定义这些基础能力要组成
一套可用的企业运维系统时所需的更完整功能边界。

现有 Space 边界与共享 Agent 运行时仍是起点约束。任何经验证的要求都必须保留
独立本地使用能力，也不能引入另一套执行或授权归属。

## 目标与非目标

目标是明确企业级 BuildMax 应覆盖的用户与运维历程，说明每项能力的最小行为，识别
功能列表经常遗漏的生命周期和失败场景，并明确将候选要求提升为已采纳产品要求所需
的证据。本清单还要指出已有规划能力之间必须打通的地方，避免用一组互不相连的页面
冒充完整控制闭环。

非目标包括划分社区版与企业版功能、批准企业版、提出商业模式建议、修改价格或许可、
重新设计 OIDC、调整路线图、创建实施待办或承诺生产就绪。本清单不授权新增组织层级、
自定义策略语言、许可证服务器或独立运行时。每个新增概念都必须对应现有概念无法满足
的具体要求。

## 覆盖层次

本提案使用三个覆盖层次，避免“企业能力”变成无边界的功能标签：

| 层次 | 含义 | 示例 |
|---|---|---|
| 已有归属的基础能力 | 本提案依赖并负责衔接的已有或在建工作，但不接管其详细设计 | 私有部署、系统管理、Space 治理、Space Secret、沙箱与 trace、企业 OIDC SSO |
| 核心功能覆盖 | 目标企业部署应作为同一个运维闭环评估的结果 | 人员生命周期、RBAC 与访问治理、执行控制、审计、数据治理、成本控制与恢复 |
| 条件性扩展 | 只有明确部署要求成立时才增加的集成或更强保证 | SCIM、SAML、自定义角色、SIEM 投递、外部密钥管理、严格出站策略、高可用、多地域或离线运行 |

一项基础能力可能已经部分交付，但端到端企业结果仍不完整。反过来，列入核心功能覆盖
也不意味着每个部署都需要最强实现。每个获采纳切片仍须有明确的用户、威胁或运维约束，
以及可度量的验收证据。

## 详细功能覆盖

### E1. 企业身份与人员生命周期

**用户结果：** 员工使用企业身份系统，只获得由 BuildMax 管理的权限，并在组织声明的
离职时限内失去这些权限。

功能覆盖包括登录方式发现、OIDC 登录、经过验证的外部身份关联、JIT 或
`existing_only` 预配、本地管理员应急登录、账户启停、活跃 Session 可见性、单个与全部
Session 撤销，以及有引导的入职/离职流程。离职流程必须说明其对人员 Session、机器凭证、
邀请、成员资格、定时任务、排队中的 TaskRun、运行中的 TaskRun 及保留结果的影响。企业
身份设计负责 OIDC 协议和浏览器细节；SCIM 与 SAML 仍是条件性扩展。

**最低证据：** 使用一个明确的 IdP 验证首次登录、重复登录、关联冲突、停用账户拒绝、
Session 撤销、仅依赖 IdP 时有界的离职处理、IdP 故障和管理员恢复，并证明提供方 token
没有泄露。

### E2. 部署与 Space 管理

**用户结果：** 有权限的运维人员无需检查数据库即可理解和操作整个部署；Space owner
可以治理单个 Space，而不会因此获得部署级权限。

部署管理界面覆盖脱敏的健康状态与版本总览、管理员、可搜索的账户与 Session、Space
元数据/成员/配额等级/汇总用量、模型与插件目录状态，以及持久化的队列、TaskRun 和
worker 诊断。日常变更通过同一个 Admin API，由 Portal 和 `buildmax admin` 作为对等客户端
调用。数据库直连的 `buildmax-server` 命令仅保留启动引导和应急恢复。Space 设置继续负责
成员资格、固定角色、所有权转移、配额可见性、共享 Agent 与 Workflow 治理，以及 Space
审计。

该覆盖不引入 Organization 实体，不默认允许部署管理员浏览 Space 创作内容，也不会把
进程启动时配置伪装成可动态编辑的配置。

**最低证据：** 入职、访问恢复、离职、配额分配、目录管理与卡住的 Run 诊断历程，通过
所有受支持的日常界面产生相同权威状态和审计记录；Portal 或 IdP 不可用时仍可恢复。

### E3. 基于角色的权限控制与机器访问

**用户结果：** 每个人类或无人值守调用方都有明确的所有者、范围、生命周期和撤销路径，
任何凭证都不能绕过当前 Space 策略而悄然获得更多权限。

BuildMax 需要基于角色的权限控制（RBAC），但最小需求不是一套用户可自定义的策略平台。
核心模型刻意分成四层：

| 层次 | 角色或 principal | 权限边界 |
|---|---|---|
| 部署 | 有效的 `system_admin` grant | 操作账户、部署元数据、目录、配额和恢复；不自动获得每个 Space 的成员资格或内容访问权 |
| Space | 具有 `owner`、`admin` 或 `member` 的成员资格 | 通过唯一权威的 Space action 矩阵授权，绝不授予该 Space 之外的访问权 |
| 受保护操作 | 管理成员、Secret、Agent、Workflow、定时任务或审计等命名的领域 action | 路由与归属 service 执行同一决定；未知角色和 action 默认拒绝 |
| 执行或集成 | worker、webhook、个人 token 或未来由 Space 所有的 service account | 使用特定用途的 audience 与 scope；不能伪装成人员角色或 Session |

核心功能覆盖包括集中式授权、跨 Space 隔离、固定角色说明与有效权限可见性、通过一个权威
service 完成角色分配/变更/撤销、最后一个有效 System Administrator 与 Space owner 保护、
权限变化和拒绝审计，以及在启动/继续/重试/定时执行工作时检查当前成员资格。所有决定都在
后端执行；Portal 可以解释或隐藏不可用操作，但绝不是执行边界。角色移除对下一次受保护请求
立即生效，已在运行的工作则遵循下文生命周期契约。

人员 Session、个人访问 token、Space 所有的 service account、webhook key 与 TaskRun
worker 凭证保持分离，因为它们的所有者和撤销语义不同。机器凭证需要最小范围、过期或
轮换、Secret 仅显示一次、最后使用元数据、停用/撤销操作，以及把机器身份而非其创建者
记为 actor 的审计。

IdP group claim 不得绕过 BuildMax 授权。只有明确运维人员需要职责分离时才增加新的内置
system role，只有固定角色无法表达已证实职责时才增加自定义 Space role，只有 Space 成员
资格被证明过于粗粒度时才增加资源级 ACL。service account 同样只在已证实的无人值守流程
无法安全使用人员凭证时建设。这些条件默认都不要求一套通用策略语言。

**最低证据：** 自动生成的清单展示每个角色的有效 action 与分配对象；授权矩阵覆盖每条
受保护路由、service 变更与凭证类型；测试包括未知角色/action、所有者停用、成员资格移除、
scope 过期、跨 Space 访问、最后持有者并发、轮换与立即撤销。仅在 Portal 执行规则的实现
不能通过验收。

### E4. Agent 执行治理

**用户结果：** Space 可以约束 Agent 的执行能力，了解某次 Run 获准的确切环境，并在事故
期间停止后续工作。

功能覆盖包括模型、工具、插件、hook 与 Secret 的准入；worker 沙箱姿态；所需的网络目的地
策略；不可变的按 Run 解析结果与插件 pin；明确的拒绝原因；暂停定时任务；取消 TaskRun；
以及阻止新工作准入的部署级或 Space 级紧急暂停。若目标流程要求审批高风险操作，审批必须
绑定操作及安全相关参数，并明确过期、输入变化、重试和失败行为。

仅为了暴露已有 allow/deny 与生命周期控制，并不需要一套通用策略语言。撤销会改变后续
工作的准入，但不会向正在执行的 Agent 悄然热加载新环境，也不能假装撤回已经发生的外部
副作用。

**最低证据：** 测试与部署历程覆盖允许/拒绝准入、Run 环境溯源、官方 worker 失败关闭、
定时任务暂停、取消、紧急暂停，以及在途工作的已声明有界行为。

### E5. 审计、调查与追责

**用户结果：** 获授权的审阅者可以还原谁或什么改变了权限、配置、凭证与执行状态，同时
不会让审计系统变成另一份 prompt 或 Secret 存储。

功能覆盖包括有类型的人类、service、worker 与 system actor；稳定 action 名；target 与
Space 标识；相关时记录 TaskRun；成功或拒绝结果；安全的时间戳与有界 detail；按 actor、
action、target、Space 和时间授权查询；CSV 或 JSONL 导出；以及明确的保留/清理策略，其
清理动作本身也可见。绝不能在没有证据时独立存在的身份关联与权限变更，需要事务性审计
语义。运行 trace、LLM 调用计量与权限审计保持为三个不同的数据产品，并有明确的关联和
保留规则。

**最低证据：** 审阅者可从登录或机器凭证追踪到受治理操作及相关 TaskRun，看到后续撤销，
导出同样的记录，并验证已知凭证、提供方 token、prompt 和工具输出不会出现在审计链路中。

### E6. 数据与 Secret 治理

**用户结果：** 运维人员可以解释企业数据和凭证存储或发送到何处，执行声明的生命周期，
并在不跨越 Space 边界的前提下恢复或轮换它们。

功能覆盖包括数据库、对象存储、日志、trace、备份、模型提供方、工具和插件的数据流清单；
部署边界 TLS；托管凭证加密；Secret 只写输入；按 Space 与 Run 隔离的 Secret 投递；脱敏；
密钥与凭证轮换流程；以及按数据类别定义的保留/删除行为。备份与恢复必须覆盖关系数据和
对象的配对，并说明审计、trace、凭证与在途执行能否一致恢复。

数据驻留、客户管理密钥、外部 Secret 提供方、工作负载身份、legal hold 与完全离线运行，
在明确环境提出要求之前仍是条件性能力。

**最低证据：** 数据流评审与轮换、删除、恢复演练证明所声明的位置及残留副本；植入的
Secret 值不会出现在响应、日志、trace、审计、Artifact 或另一个 Space 中。

### E7. 用量、容量与成本控制

**用户结果：** owner 可以归属消耗、预判容量压力，并为无人值守工作设置经过验证的边界。

功能覆盖包括按 Space、Task/TaskRun、模型/提供方与时间窗口统计用量；配额等级分配；部署
需要的 Run、token、存储、并发和速率限制；阈值预警；以及清楚的准入错误。每项限制都必须
定义检查时点、排队和在途工作的处理、重试行为与最大可能超额。成本视图必须说明价格来源
及更新时间；token 配额不得被描述为严格金额预算。

**最低证据：** 并发准入测试与无人值守工作历程证明确定性的归属、预警、拒绝、窗口结束
或运维变更后的恢复，以及经过测量的超额上界。

### E8. 运维、恢复与可支持性

**用户结果：** 运维人员能通过有文档的流程安装、观测、诊断、升级、恢复和支持 BuildMax，
并明确其恢复边界。

功能覆盖包括受支持的部署形态、配置校验、存活/就绪/依赖/队列/陈旧 Run 信号、脱敏日志
与诊断、构建与配置身份、备份恢复、schema 升级与回滚流程、丢失 Run 处理，以及明确的
运维责任。可用性声明必须观察 Server、协调组件、MySQL、对象存储、ingress 与 worker Job
之间的实际行为，而不是只统计副本数。

**最低证据：** 全新安装、依赖故障、备份恢复、升级回滚及卡住或丢失 Run 演练，记录发现
时间、运维操作、数据/执行结果及经过测试的 RPO/RTO 边界。高可用和多地域恢复仍是条件性
的更强保证。

执行 trace 本身不等于权限审计，配额计数器不等于严格的金额预算，多个副本的部署清单
也不等于高可用验收。每项承诺都需要覆盖完整行为的证据。审计记录不得暴露 Secret 值。

## 跨能力生命周期契约

验收测试必须覆盖状态变化，而不仅是管理页面：

| 事件 | 必须明确的契约 |
|---|---|
| 账户被停用或外部身份不再被接受 | 新登录与用户请求、现有 Session、机器凭证、邀请与成员资格、定时任务、排队及运行中的 TaskRun、结果归属 |
| Space 成员资格或角色被移除 | 新 Space 请求、继续/重试、排队工作、运行中工作、后续结果访问、最后 owner 保护 |
| Session 或机器凭证被撤销 | 已签发的访问权限、刷新/轮换、并发请求、定时工作、审计与最后使用状态 |
| 模型、插件、工具、hook 或 Secret 被停用 | 新准入、排队中的物化、固定的运行中环境、重试与后续 TaskRun、展示给运维的溯源 |
| 达到配额或执行被暂停 | 新工作、排队工作、在途模型/工具调用、有限超额、部分结果、恢复行为 |
| 审批过期或获批输入发生变化 | 操作绑定、失效、重试、重复投递、失败与审计行为 |
| 依赖或控制面不可用 | 现有 Session 与 Run、新准入、就绪状态、重试、应急恢复、恢复后的核对 |

这些契约应落入对应设计与服务。本清单要求它们在边界上相互一致，但不规定每个事件都
必须取消所有正在运行的操作。

## 条件性要求

以下候选项只有在目标部署提供相应证据时才成为要求。

| 候选能力 | 使其成为必要项的证据 |
|---|---|
| SCIM 或目录同步 | 人工入离职处理无法满足部署规模或访问撤销要求 |
| SAML 或多个同时存在的身份提供方 | 目标身份系统无法使用已采纳的 OIDC 路径，或者签发方迁移与多类员工身份无法通过运维流程处理 |
| 原生已连接客户端 SSO 或设备授权 | 明确的部署需要受管理的 CLI/Desktop 访问，且不能使用 Portal 或允许的本地登录 |
| 由 BuildMax 强制的 MFA 或 step-up | IdP assurance context 与普通 BuildMax 授权无法满足明确的敏感操作要求 |
| 自定义角色、访问复核与跨 Space 管理 | 固定角色和现有 Space 管理无法表达已证实的职责划分或复核义务 |
| 外部密钥提供方与工作负载身份 | 有明确的凭证系统或短期凭证要求；遵循路线图既有的密钥能力顺序 |
| SIEM 投递、可发现篡改的审计与特殊保留控制 | 明确的调查、保留或安全要求超出现有审计机制 |
| 审批门禁、内容控制或严格网络目的地策略 | 明确的高风险操作、数据泄露场景或 worker 威胁模型无法由现有准入与沙箱边界控制 |
| 高可用与多地域恢复 | 有文档的可用性、恢复时间与恢复点目标；基础恢复能力仍是基本要求 |
| 数据驻留、客户管理密钥或完全离线部署 | 目标环境限制存储位置、密钥托管、外部依赖、模型调用或更新服务 |
| 认证、正式鉴证报告或响应目标 | 有文档的治理或运维要求，且组织能够持续提供所需流程和证据 |

部署所声明的边界需要哪些安全控制，就必须提供哪些控制；不能仅因为只有部分环境
需要相关集成而推迟必要的安全保障。

## 要求评估

需求调研应逐项独立分类候选要求。分类只关乎证据和范围，不关乎产品打包。

| 分类 | 证据门槛 | 后续处理 |
|---|---|---|
| 已验证要求 | 有明确名称的用户或运维历程、当前约束和可度量的验收测试 | 通过路线图和归属设计评估是否采纳 |
| 条件性要求 | 只对有文档记录的部署、身份系统、威胁模型或运维目标成立 | 明确保留条件，不泛化到所有安装环境 |
| 当前无充分依据 | 没有观察到任何流程或约束会因缺少它而失败 | 暂不建设；有价值时将证据缺口保留为开放问题 |

优先选择满足已证实结果的最小控制集合。新增实体、层级、策略语言或管理界面之前，
先指出现有概念无法通过的确切验收测试。

## 问题与证据

访谈潜在企业团队，记录使用场景、用户和运维人员、部署环境、阻碍条件、威胁模型、
验收测试，以及要求未满足时的后果。优先采用成功和失败标准明确的有限试点，不从
其他项目的功能列表推断自身需求。

开放问题包括：先研究哪些部署类型，SSO 之后还有哪项非身份能力阻碍采用，人员变化后
谁负责无人值守工作，运维期待怎样的紧急停止边界，哪些控制普遍适用、哪些依赖具体环境，
以及运维如何证明恢复、撤销和成本控制结果。

SSO 实施应通过其归属设计提供身份专项证据，而不再成为首个调研问题。接下来更有价值的
调研切片是它暴露出的衔接处：贯穿 Session 与无人值守工作的完整离职历程；贯穿准入与在途
执行的配额/暂停历程；以及从发现到恢复和审计的事故历程。这些是需求调研假设，不是另一套
优先级队列；当前路线图仍决定交付顺序。第一个衔接处现已在
[人员停用与执行权限](personnel-deactivation-lifecycle.md)中形成待评审提案；这并不表示
该方向已经获采纳或成为可执行 backlog 工作。

采纳要求前，应有明确的历程和责任人、归属与失败行为清楚的有限实现范围，以及承诺
的部署和生命周期结果的验证证据。未解决的假设保持显式记录。

## 采纳后的归宿

已验证的优先级进入路线图，长期决策进入对应设计记录。获批且已分解的主线工作进入
backlog；行为交付时再更新运维文档。当有价值的要求都已依据证据被采纳或拒绝后，将
长期理由移入归属文档，并按文档规范退役本清单。
