# 会话与追踪记录

BuildMax 会保留两种不同的记录，用于回答两个不同的问题：会话是你可恢复的对话，
而追踪记录是某一次运行实际做了什么的详细日志。

| | 会话 | 追踪记录 |
|---|---|---|
| 回答 | “我们聊了什么？” | “它实际做了什么？” |
| 包含 | 可恢复的对话 | 一次运行中的每一次 LLM 调用和工具调用 |
| 存放于 | `<BUILDMAX_HOME>/sessions/<id>/` | 同一个文件夹，位于 `traces/` 下 |
| 谁来读 | 你，以及恢复时的 Agent | 你，在出问题时 |

## 会话

每个会话都是一个文件夹，关于它的一切都存放在其中：

```text
<BUILDMAX_HOME>/sessions/
  index.json                    会话选择器读取的内容
  <id>/
    meta.json                   标题、工作区、模型、令牌和费用总额
    history.jsonl               对话，每行一条记录
    traces/<run_id>.jsonl       每次运行一个文件
```

`history.jsonl` 是仅追加的：每条消息、工具调用和工具结果都是在发生时写入，
而不是在一个回合结束时重写整个文件。正是这一点让被中断的运行能被重新接上——
也让 BuildMax 能区分从未开始的工具调用与可能已经在磁盘上改动了某些东西的工具调用。
当它恢复一个在工具执行中途停止的会话时，它会明说，而不是任凭某一种假设。

令牌计数和费用覆盖整个会话：每一个回合、标题生成调用、每一次压缩，
以及运行委派给子 Agent 的任何工作。

标题是从第一次交流中生成的，这就是为什么 `/sessions` 是可读的，
而不是一串 id 的列表。

### 恢复

```bash
buildmax --continue              # 当前目录中最近的会话
buildmax --continue --project    # 扩展到该项目的每一个目录
buildmax --resume <session-id>   # 某个特定的会话
buildmax --session-id <uuid>     # 存在则加载，否则创建它
```

`--continue` 指的是你所在目录中记录的最新会话。机器上最新的会话很少是你想要的，
因为它跟随你最后接触的那个仓库——而*同级工作树*中最新的那个也不是它，
因为在那里继续会把你的工作根目录从你脚下挪走。当这个目录没有会话但项目有时，
`--continue` 会说明有多少个并指出 `--project`；扩展之后会在第一个回合前打印它将运行的目录。

`/sessions` 选择器的范围限定在项目内——一个仓库连同它的所有工作树，或一个普通文件夹——
并且可以跨目录，因为是你在读这个列表。记录在另一棵树中的会话会用那棵树的名字标注，
恢复它时会说明它实际将在哪个根目录中运行。

`--resume <id>` 仍然会在任何地方查找会话，但它会在该会话运行过的目录中恢复，
并且会拒绝继续一个属于不同项目的会话，而不是把它挪过来。

`--session-id` 是适合用于脚本的那个：它让一次运行相对于一个已知 id 幂等，
而不是取决于恰好最新的是哪个。

在 TUI 中，`/sessions` 打开选择器，显示当前项目的会话；按 `a` 显示机器上的每个项目。
对话是在发生时写入的，所以被中断的运行会保留到它停止那一刻的一切——
而不仅仅是到最后一次完成的回复。

一个会话同一时间只能在一处打开。打开一个另一个窗口或进程已经在运行的会话，
会报告它正在使用中，而不是任由两次运行相互覆盖。

### 回退

`/rewind` 收回你的某个提示词，好让你换个说法。从列表中选中它，
它会连同它之后的一切一起离开对话——并回到输入框中，随时可以编辑并再次发送。

列表保存你输入过的提示词。不包括 Agent 的回复，因为没有什么可以从中交回；
不包括后台事件，它们是你从未写过的消息；也不包括会话的第一个提示词，
它前面没有可返回的内容——那种情况请新开一个会话。如果输入框中已经有草稿，
那份草稿会被保留而被回退的提示词不会被恢复；报告会说明这一点。只有文本会回来，
所以提示词携带的图片会被标注为没有携带。

**它移动对话。它不撤销对话所做的事。** 一个编辑了文件、运行了命令或调用了 API 的回合
会把这一切留在原处——Agent 的历史退回去，工作区不会。选择器会在你选择之前说明
你即将移除的部分中运行了哪些工具，之后也会重复一遍，这样如果需要你可以自己把那些影响改回来。

什么都不会被删除。你回退越过的那些消息仍留在磁盘上，回退之后的新回复会开启一条新分支，
而不是覆盖旧的那条。

### 分叉

`/fork` 把直到某条选定消息为止的历史复制到一个**新会话**中并把你切换过去，
而不是改变当前这个。原来的会话未受影响，仍然在那里。

它的列表是更宽的那种：任何一个回合结束时所停在的消息，你的或 Agent 的，包括最新的——
从你已经所在的地方分叉出去是常见情况。一个请求了工具的回复处于回合中途，不会被提供，
因为在那里停下的副本会持有一个没有结果的工具调用。

用它来尝试第二种方法而不丢失第一种。这两个会话从那一点起彼此独立——
删除其中一个绝不会影响另一个。

同样的告诫从另一面也适用。分叉点之后发生的工作确实触碰了工作区，
而新会话的历史并不包含它，所以那里的 Agent 不会知道它发生过。选择器会在你选择之前指出那些工具。

### 在哪里找到它们

在 TUI 中它们是 `/rewind` 和 `/fork` 命令。在 Desktop 中它们是聊天状态栏里的一个
**History** 按钮，带有一个选项卡来选择你想要两者中的哪一个；每个选项卡列出该操作可以指向的消息。

在运行进行中时 Desktop 会拒绝这两者并说明原因；请先停止运行。打开选择器仍然有效——
它只是读取。

### 压缩

当一次对话接近模型的上下文窗口时，较旧的消息会被压缩成一段摘要，
在日志中记录为一条 `compaction` 记录，准确指明它覆盖了哪些消息。`pre_compact` 钩子可以阻止这件事，
`post_compact` 则观察它——见 [钩子](钩子.md)。

TUI 中的 `/compact` 在你主动要求时（而不是在窗口填满时）做同样的事，
并逐字保留一段短得多的末尾。在长会话中把一个新任务交给 Agent 之前使用它：
摘要覆盖的内容不再可引用，只能被概括。用于概括的模型调用像其他任何调用一样计入会话费用，
而消息本身仍留在会话文件中——摘要替换的是发送给模型的内容，而不是所记录的内容。

## 追踪记录

每次运行都写一个 JSONL 文件：

```text
<BUILDMAX_HOME>/sessions/<session_id>/traces/<run_id>.jsonl
```

运行 id 以 `rt_` 为前缀。文件以一条 `run_start` 记录开头，随后是三条描述该运行以什么开始的记录，
然后每个事件一条记录，最后是一条终结的 `run_end`：

| 记录 | 何时发出 |
|---|---|
| `run_start` | 运行开始时 |
| `sandbox_boundary` | 总是发出，紧跟在 `run_start` 之后——报告该运行实际所处的边界。`"sandboxed": false` 意味着没有任何东西约束该运行的 `Bash` 命令 |
| `context_sources` | 总是发出——该运行由之组装出来的每一个来源，按种类命名：各指令层及每层的大小、它携带的项目记忆索引连同其条目数和渲染后大小，以及是否有一段压缩摘要代替了消息。只有计数和大小；无内容。一次运行随后读取了哪些记忆正文，以及任何写入，都是会话日志中的工具调用，而不是在此再作一次描述 |
| `plugins` | 总是发出——该运行加载了哪些插件，对于从 Git 检出安装的插件还包括其提交和工作树是否有未提交改动 |
| `llm_start` / `llm_end` | 每次模型调用 |
| `tool_start` / `tool_end` | 每次工具调用 |
| `tool_denied` | 一次工具调用被阻止——被钩子，或被权限 |
| `context_compacted` | 对话被压缩，连同概括本身花费了多少 |
| `run_end` | 运行结束，连同其总额、失败时的错误消息，以及在它启动了子 Agent 运行时的 `delegated` 明细 |

因为它是 JSONL，普通工具就能用：

```bash
# 上一次运行中的每一次工具调用
jq -r 'select(.type=="tool_start") | .tool_name' \
   ~/.buildmax/sessions/<session>/traces/<run>.jsonl

# 什么被阻止了
jq 'select(.type=="tool_denied")' ~/.buildmax/sessions/<session>/traces/*.jsonl

# 运行是如何结束的
jq 'select(.type=="run_end")' ~/.buildmax/sessions/<session>/traces/<run>.jsonl
```

### 有界且已脱敏

自由文本字段会被截断，常见的密钥形态会在任何内容写入之前被脱敏。追踪记录在记录数量上也是有界的——
一旦达到上限，后续记录会被丢弃，但 `run_end` 仍会被写入，这样文件总能正确终结。

追踪**失败即开放**：无法写入的追踪永远不会中断或拖慢运行。

### 覆盖范围与禁用

追踪在每个界面都会经过的那一个点上挂接，所以 CLI、TUI、Desktop、评估和 worker 运行都会产生追踪记录。

```bash
BUILDMAX_TRACE_DISABLED=1 buildmax -p "…"
```

默认开启。若有理由可以关掉它；但当一次运行做了出人意料的事时，它正是你会想要的那份记录。

一个子 Agent 的运行与它的父运行并排被追踪，在同一个会话目录中，
带有 `is_subagent: true` 和 `parent_run_id`，后者指明委派给它的那次运行。

## 统计

`buildmax info` 把两种记录折叠成对一个会话的一个答案，并加上该会话所属项目所记住的东西：

```bash
buildmax info                   # 最近的会话
buildmax info <session-id>      # 某个特定会话
buildmax info --json            # 完整记录，包括被截断的末尾
```

它报告花费连同缓存明细以及缓存节省了多少、会话离它的上下文窗口有多近、
每个工具往那个窗口里放回了多少字节、模型时间与工具时间的划分，以及一次委派完成了运行中的多少。

在 TUI 和 Desktop 中，`/info` 有三个选项卡。`session` 显示屏幕上会话的相同数据，
取自实时会话而非最后一次保存的副本。`tree` 显示包含该会话的完整本地 fork 树、
标记当前分支，并在父级已删除时保留一个缺失来源占位。它从会话索引派生树，而不会
逐个重新打开会话。`memory` 列出项目所记住的东西；在 TUI 中，`enter` 打开一条
记忆以阅读它背后的原因。见 [项目指令与记忆](项目指令与记忆.md)。

令牌和费用来自会话文件；计时和每个工具的细节来自追踪记录。在缺少追踪记录的地方，
那些行会说明这一点而不是报告为零——见 [CLI 与 TUI 参考](命令行.md)。
